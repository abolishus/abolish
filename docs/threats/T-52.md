# T-52: Spam and flooding

- Area: Availability and censorship resistance (G-10)
- Adversary: A-5, A-1
- Status: **Planned.** Residual: Tier 0 polls can be flooded with Sybil votes (T-01).

## Threat

Fake polls, junk ballots or junk direct submissions exhaust storage, indexing or verifier time.

## Mitigation

Every board entry requires a valid proof; direct submissions cost gas; rate limits and Turnstile on Tier 0 actions (P2-5). The verifier rejects invalid entries cheaply before expensive checks.

## History

- 2026-10-11 (P1-17): direct-submit contracts must verify each ballot's membership proof under the pinned depth-32 key against the registered tier root, so non-members can't put entries on the board ([[membership]], Owned elsewhere).
- 2026-10-11 (P2-2): the public API contract bounds every input and output: a submitted ballot is at most `MAX_BOARD_PAYLOAD` bytes, a board page at most 256 entries and 8 MiB (unless it holds one entry), and a proof path at most 128 hashes. The schema rejects an oversize string before matching its pattern. Rate limits and request-body limits are still P2-3's.
- 2026-10-11 (P1-18, part 2): anyone can create elections in the registry for gas, and each creation enters its shared event sequence. [[contracts]] (The shared event sequence) requires the contract-event record and verifier 4.4 to replay that sequence from the archive under the accumulator's storage proof, with board entries only for an election's own events, so junk creations don't have to be boarded on every live election's board.
- 2026-10-11: [[verifier]], Bundle, states that `MAX_BOARD_PAYLOAD` bounds what is admitted to the board, not what a verifier hashes: the board checks hash an anchored copy before decoding it, so an anchored oversize entry costs verifier time, never its verdict (P1-19).
- 2026-10-11 (P2-5 part 1): signing up is registering a passkey, with no other step, so anyone can create accounts. With "none" attestation a scripted client makes a passkey in microseconds, so an account costs a few requests and rows, nothing more. Starting a ceremony costs one request and leaves a challenge row; the passkey plugin never deletes abandoned ones, so `pruneAccountVerifications` deletes expired rows by an index and must be scheduled (P2-4). Request bodies are bounded at 64 KiB, and better-auth's own rate limiter is off (it keys on addresses, T-11). Until Turnstile (P2-5 part 2) and the proxy's per-address limits (P2-11), nothing else bounds account creation or ceremony starts.
- 2026-10-11 (P2-6 part 1): [[0017-identity-recovery-backup]] adds an anonymous write surface, recovery envelopes stored through the ballot path with no account and no Turnstile (the ballot client ships no third-party code). Rows are fixed-size; per-address limits at the proxy (P2-11) are the only bound so far.
- 2026-10-11 (P2-10 part 2): `POST /moderation/reports` is another anonymous write surface. Reports are counted, one row per election and ground, so they can't grow storage past that; the counts can be inflated, which only reorders the moderators' queue. [[railway]] asks for a per-address rate limit on the route.
- 2026-10-12 (P4-1 part 1): only the anchoring authority fixed in the L1 board anchor can anchor, so no one can front-run an election's checkpoint with a bogus one ([[contracts]], Board anchor).
- 2026-10-12 (P2-9 part 2a): `apps/web`'s Node front bounds every request body at 64 KiB, refuses a GET with a body, handles at most 64 requests at once (503 past that) and destroys idle or overlong connections, as the API does. Sign-ups and ceremony starts are still unbounded until Turnstile (P2-5 part 2) and the proxy's per-address limits (P2-11).
- 2026-10-12 (P2-6 part 3): identity backups are an anonymous write surface. Each request and row has a fixed size (a 32-byte locator, a 63-byte envelope, decoded strictly before it is stored), and a row not rewritten for 24 whole months is deleted by `pruneIdentityBackups`, so abandoned rows don't accumulate. Nothing schedules the prune yet (the worker, P2-6 part 3b), and the number of rows a flood can write is bounded only by the proxy's per-address limits (P2-11).
- 2026-10-12 (P2-5 part 2): every passkey ceremony start (sign-up, sign-in, adding a passkey) needs a Turnstile token solved on `apps/web`'s host for that action, checked with Cloudflare before better-auth writes its challenge row; refusals and Cloudflare outages write nothing. Account creation and challenge rows now cost one solved challenge each. A forged token costs its sender nothing and us a siteverify call of up to 5 s, so a flood of them while Cloudflare is slow can hold `apps/web`'s request slots; only the proxy's per-address limits bound that. Turnstile raises the cost of automation, it doesn't bound it: solving services sell tokens, so the proxy's per-address limits (P2-11) are still needed. `apps/web`'s page sends no token until P2-9 renders the widget, so sign-up and sign-in on a deployment wait on that. The identity-backup and report routes stay without Turnstile (ballot path; T-25).
- 2026-10-12 (P2-6 part 3b): the worker runs `pruneIdentityBackups` daily, and once at start, on its `{identity-backup-prune}` queue, so expired identity backups are deleted within a day of the UTC month turning. The number of rows a flood can write is still bounded only by the proxy's per-address limits (P2-11).
- 2026-10-12 (P1-12 part 3b, [[delivery]], Direct submit): trustee nodes send a contract-path receipt for every ballot they receipted unless a passing receipt is anchored or the fully published anchored board shows the ballot absent, so an intake flood costs them gas only while the operator withholds board data; a node may skip a ballot a later anchored re-vote supersedes.
- 2026-10-12 (P1-12 part 3b, [[delivery]], Residuals): a trustee node's contract-path receipt obligation is unbounded while intake checks no membership: an ineligible-ballot flood plus an operator withholding board data until the node's cutoff can exhaust it and drop receipted ballots whose clients have gone away. The owner accepted this as a residual until [[P1-12c]] (membership-checked intake, obligations bounded by the electorate, batched contract receipts) closes it, before any election registry is deployed.
- 2026-10-12 (P2-3 part 2b): the API's board heads and inclusion and consistency proofs no longer read every entry hash per request. `appendEntry` stores the board tree's perfect subtrees as entries are appended, and each read folds O(log n) of them, so a flood of head or proof requests costs a bounded number of rows each, however large the board.
- 2026-10-12 (P3-2 part 4a, [[0024-tier0-registration]]): anyone can queue Tier 0 registrations at the price of a Turnstile solve each. A period's batch is bounded by the gas the paymaster sponsors, and the excess is carried to the next period, never dropped silently (P3-2 part 4b). The self-paid path (P3-2 part 5) must never make a signed batch revert, or one cheap transaction per period would stall sponsored registration: self-paid additions go only into self-paid groups, so they can't move a signed group's position, and the contract checks no duplicates across the two kinds of group.

A ballot that fails decoding or any admission check is listed in the report's `ballots` and fails its row only, which is an admission row: it never fails the election, and each ballot is judged from its own bytes, so no posted ballot changes another's verdict (tested over random subsets of a copy holding a ballot of each failure).
- 2026-10-13 (P2-14 part 1a, [[display-text]], Layout (version 2)): display-text version 2 lists up to 32 questions per translation, so its list maxima alone would allow a record of over 100 MB. Version 2 caps the whole record at `MAX_DISPLAY_TEXT` (4 MiB), checked on the input's length before decoding, so a hostile record is rejected on its length. - 2026-10-13 (P1-12c part 1, [[share-encryption]], Intake and receipts; [[delivery]], Direct submit): trustee intake takes the whole ballot record and runs the admission checks of verifier 5.1 to 5.4 on it, its membership proof included, before it decapsulates or receipts, so only a registered member's ballot makes a node verify validity proofs, decapsulate or store shares. A node owes a contract-path receipt only for the ballot [[revoting]]'s selection picks for each tier and nullifier from its view (the ballots it receipted, less those shown absent, with those it holds from the board), so its obligation is at most two receipts per member of each tier, whatever an operator withholds. Still open until P1-12c part 2: what the windows let a node send by its cutoff with P1-18's batched receipts, and a bound on complaints. A member can still make a node do intake work for any number of their own ballots; per-nullifier rate limits are now possible, since the node knows the nullifier is a member's. The node decides what it owes once, at the intake cutoff `c_I = t_D − F − R` that every node shares, keeps intake open until then (so retries after an outage at the close still get receipts) and refuses it afterwards, since the union of decisions over a changing view wouldn't be bounded; the delivery-window bound now reads `max(2 · period + deadline, W_C) + R + F`.
- 2026-10-13 (P2-14 part 2, `packages/crypto`): the version-2 display-text decoder rejects an input over `MAX_DISPLAY_TEXT` with `length-over-max` at offset 0 before reading its header, and the encoder refuses to build or commit to such a record, so a creator using `packages/crypto` can't register a poll whose text every client refuses (T-53); tested at the cap and one byte over.
- 2026-10-13 (P3-2 part 4b, [[registration]]): each Tier 0 group's registration queue holds at most 1,024 commitments; beyond that the route answers `REGISTRATION_BUSY`, checked before Turnstile and again atomically with the insert, so concurrent requests can't overfill it (only an abandoned record's commitments returning can, by at most one batch). A group adds at most one batch of 256 per boundary, chosen uniformly at random when more wait, so under any flood each queued commitment is selected with probability at least a quarter per batch, and the rest wait rather than being dropped. Residual: about 256 solves per group per batch keep a queue full and turn new registrations away for as long as the flood is paid for, at our paymaster's cost. The route's checks before Turnstile read a Tier 0 index the service keeps current, never an L2 node per request. Malformed, forbidden and unknown-region requests are refused before Turnstile is called.

- 2026-10-16 (P3-2 part 4d-1, [[registration]]): the registration route bounds each group's queue at `REGISTRATION_QUEUE_MAX` = 1,024 and checks it twice: before Turnstile, in the same Redis read as the index's freshness, and again atomically with the insert; a test sends 40 requests together at five below the bound and finds exactly five queued. - 2026-10-16 (P3-3 part 2b-2, [[vouching]], Batched verification): measured: batching cuts an honest replay's proof checks to about a sixth; proofs are batched 64 at a time, so an invalid proof costs batching only within its batch: one in every 64 leaves about 85% of the one-at-a-time cost, and a flood of junk costs about 1.35 times it. Junk additions about one in ten of a replay's take most of the gain away; not mitigated. Every proof of a replay is checked before the walk, only for additions that pass every check needing no pairing or counting state, and each Tier 2 group a vouch names is replayed once, its roots taken at every block named rather than rebuilt per block.
- 2026-10-16 (P3-3 part 3a, [[contracts]], Group registry, Tier 1 additions): specified, not built. The registry checks all six proofs of a Tier 1 addition, and everything else that depends only on the record, its block and the group table, before logging it, so on an honest chain no logged addition fails a proof, and a verifier that checks proofs last spends pairings only on additions that count. Not mitigated: additions naming made-up Tier 2 roots, and copies of counted additions, still pass, without bound, at about 1.3 million gas each to their sender, and cost a verifier their decoding and a lookup each. The API relays only additions that count under its own replay, at a limited rate, so it can't be made to pay for junk. The registry keeps no slot or commitment state, which would let a front-runner block an honest addition (T-25).

- 2026-10-16 (P3-3 part 3b-1, `packages/contracts`, [[contracts]], Group registry, Tier 1 additions): built. Contract-event version 6 decodes every logged addition (six proofs' points, `B`'s subgroup check included) for every verifier that checks the registry's events.
- 2026-10-17 (P4-3 part 2b-2b-2, [[verifier]], Board by CID, Gateways): a gateway's answer is read as it streams and dropped past the reader's limit (at most 1 MiB), whatever its `Content-Length` or encoding, and each request has a 30 s timeout for headers and body, so a hostile gateway costs the verifier at most a small multiple of one chunk of memory per request, and time, never memory beyond the copy's budget.
