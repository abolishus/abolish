2. **Board data availability** ([[0029-board-data-availability]], option D): 2a, the ADR (#N); 2b, checkpoint version 2 with the segment's CIDs, the new anchor (with P4-1) and the verifier's fetch by CID; 2c, availability attestations, `t_A` and the verifier's `unavailable` check (the L2 call with P1-18); 2d, the reference election's withholding run. Originally: make a withheld anchored extent attributable ([[board]], Residuals, withheld tails): a content address per anchored segment bound into what is anchored, and a publication deadline, so a node or verifier can tell non-publication from absence. An ADR first (what is anchored changes, and with it P4-1's contract). It also closes [[P1-12c]]'s residual on a newest ballot that never reached the board, and makes receipts' `unresolved` evidence attributable ([[receipts]], Residuals).
3. **Archive manifests and their Arweave layout** ([[0005-permanent-archive]], Consequences), with an Arweave test harness for the reference election. The first real upload spends money and waits for the owner.
4. **Mirroring**: the worker pins every segment object, entry-hash list and display-text record on IPFS, and the ballot client's releases; community nodes pin by default (P4-5).

## What was built (part 1)

- `packages/crypto`: `contentDag` (fixed 1 MiB raw leaves, a balanced tree of dag-pb UnixFS `File` nodes of at most 1,024 links, every block once in depth-first pre-order), `objectCid`, `cidText` (base32, `b` prefix) and `objectCar` (CARv1). dag-pb, UnixFS and the dag-cbor CAR header are written by hand, so the package keeps to `@noble/*`.
- [[content-addressing]]: the parameters are no longer provisional; how to set Kubo and ipfs-unixfs-importer to them (Kubo's default is 174 links per node, not 1,024); the encodings byte for byte; Test vectors.
- `docs/spec/vectors/content-addressing.json` from `packages/crypto/scripts/content-addressing-vectors.mjs`, run outside the workspace: each CID from Kubo 0.36.0 (its release tarball's sha512 recorded and checked) and from ipfs-unixfs-importer 17.1.1, and each CAR from Kubo's `dag export`, matched by @ipld/car 5.4.7 over the JavaScript blocks in pre-order; refused unless they agree byte for byte.
- T-51 history.

## Tested (part 1)

- 15 vectors: one byte, 100 bytes, exactly one chunk, one chunk and a byte, three chunks, two identical chunks of zeros (one leaf, carried once), and under a small layout profile (256-byte chunks, 4 links) trees of 1, 4, 5, 16, 17, 21, 64 and 65 leaves, with partial groups at every level, and 17 identical chunks. Each CID and CAR is reproduced byte for byte (small CARs whole, larger ones by length and sha256).
- Properties (`FC_NUM_RUNS`): an object of at most one chunk is one raw block whose CID hashes it; every block is listed once with the root first and each CID hashing its block; any changed byte changes the CID. Refusals: an empty object, limits outside the layout.

## Known-weak (part 1)

- Nothing reads or writes these yet: the worker's pinning and the verifier's fetch by CID come with parts 3 and 4, and P4-6.
- The vectors cover the layout's deeper levels only under a small profile; a two-level tree under the real parameters needs an object over 1 GiB, which no vector carries.

## Independent review (part 1)

An in-session subagent reviewed the diff against `.github/review/crypto-review.md`. It found nothing blocking. It also re-ran the generator to a byte-identical file and checked the code against Kubo beyond the vectors: 60 random cases (chunk sizes 1 to 1,000, fan-outs 2 to 174, heavy dedup), exact powers and power-plus-one leaf counts, and two-level trees at the real parameters (1,024 MiB, 1,024 MiB + 1 byte, 1,025 MiB). Every one matched byte for byte. Applied:

- The docs no longer say both implementations made the CAR. The CIDs come from both. The CAR is Kubo's `dag export`, matched by @ipld/car writing the JavaScript blocks in pre-order, an order the generator chooses.
- The generator records the Kubo release tarball's sha512 and refuses any other tarball.
- The spec lists every setting a pinner needs: `reduceSingleLeafToSelf`, `leafType`, and Kubo's hash, inline and trickle defaults.
- `encodeCar` accepts only a 36-byte root, the one length whose header byte form it writes.
- The generator's instructions say to copy the script into the install directory.
- The spec lists the 100-byte vector.
- A line under Still to come: a fetcher by CID must cap sizes, recompute the CID and check the bytes against the anchored roots (T-49, T-24).

## Decided (part 2a)

[[0029-board-data-availability]]: option D, `Accepted (agent) — owner may veto`.

- **Checkpoint version 2** names the segment object's and entry-hash list's CIDs on L1, so the verifier can fetch from chain + IPFS alone.
- **The trustee panels are the availability committee.** After the seal, each panel's threshold of seats must attest, by `t_A ≤ c_I`, that it holds every anchored object; otherwise the election fails `unavailable`, attributed to the anchoring authority. So availability rests on the secrecy assumption.
- **Rejected or deferred.** A reachability-judged deadline is rejected (verdicts would depend on the verifier's network, T-53). Archive listing alone is rejected (the authority can list and withhold). EIP-4844 blobs are kept as a later upgrade for entry-hash lists (capacity and cost rule out payloads).

Known-weak (part 2a):

- Nothing is built yet.
- Under the transitional panel, the attestation is the operator's own, so [[P1-12c]]'s residual stays until [[P1-7]] names independent trustees, or the owner accepts it for those polls.
- Withholding before the seal is judged only at the seal.
- A colluding panel threshold can attest to withheld data, as it can open ballots.
