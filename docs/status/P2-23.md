## Scope

The everyday stream: a calm way to find questions worth answering ([[language]], Two registers; [[PROJECT_BRIEF]], Priority). From `everyday-discover-page.tsx`, `everyday-stream.tsx` and `everyday-place-page.tsx` in `apps/web/src/mockups/`.

- **The stream**: one question per card, answerable from the card (handing off to the ballot client with the pick in the link's fragment, [[first-answer]]), with who asked, when it closes, and its results so far where results are live.
- **Ways in**: topics, places, "new", "closing soon" and "most answered this week" (a plain count over a fixed window), and search over question text.
- **Never**: infinite autoplay, personalised or engagement ranking, outrage ranking, counts of people viewing now, streaks.
- Delisted and hidden polls never appear ([[P2-10]]).

Rules for every part, as [[P2-19]]'s: everyday register by default ([[language]]); no hard-coded strings (`messages.ts`); CSP-safe (no inline `style`); server-rendered where the page is the website's; a fixed analytics template per route, never a path or poll ID (T-67); each component a story with a play function passing axe at desktop width and 360px; SSR and serve tests per route; the mockup's story deleted in the PR whose page matches it. Privacy holds everywhere: nothing an account does on the website (following, reacting, sharing, notifications) is ever stored, logged or keyed with a ballot, nullifier, receipt or the fact of having answered, and the T-10 no-join tests cover every new table, queue and log line ([[PROJECT_BRIEF]], Identity).

## Notes

- **Part 1a**: `listPolls` (`packages/core/src/listing.ts`) and `GET /elections` take `sort`: `id` (the default, every listed poll by election ID, as before), `new` (the polls open now, by the server's clock, latest registration on L2 first) and `closing` (the polls open now, soonest `closes_at` first, then election ID). Each definition's `opens_at` and `closes_at` are copied into `election_schedules` (migration 0023, board class, write-once) by `storeDefinition`, so the rebuild from chain writes them again; `fillElectionSchedules`, which the API's migrate step runs, writes those of definitions stored before the table existed. A cursor under `new` or `closing` is a poll the order can place (`CURSOR_NOT_FOUND` otherwise), even one closed or delisted since. Tested in `packages/core/tests/listing.test.ts` (open-window edges, both orders over every page size with ties, moderation, cursors; a fast-check property over `closing`'s ties) and `schedules.test.ts` (schema, write-once for the app and the owner, the times for versions 1 and 5 up to a u64, the fill), and in `apps/api/tests/api.test.ts`.
- **Part 1b**: `sort=answered` lists the polls open now, the most answered this week first, then by election ID. The count is of distinct voters, each (tier, nullifier) once, whose ballots our API boarded in the whole anchoring periods of the last seven days before the current one (`answeredWindow`; 168 segments under an hourly clock). It keeps no time of its own: every board entry already carries its segment, which is public, so anyone can recompute the count from a copy of the board (counting those ballots), and nothing new about when a ballot arrived is stored (T-11). A re-vote is the same nullifier, so one voter counts once however often they cast; lifting a poll takes more voters, which Tier 0 makes cost an account and a phone number each (T-01). Leaving out the current period means the order settles once a period rather than moving with each ballot; only a ballot labelled just before a boundary and boarded just after it lands in the window late. The API needs the worker's anchoring clock (`BALLOT_ANCHOR_EPOCH` and `BALLOT_ANCHOR_PERIOD`, both or neither) and answers `SORT_UNAVAILABLE` (503) without it. Migration 0024 indexes `board_entries` by `(election_id, segment)` for the count. Tested in `packages/core/tests/listing.test.ts` (the window's edges, its length against the week for any clock as a fast-check property, the u32 segment bound; order by voters with re-votes, tiers, ballots before the window and in the current period, closed polls; a property over ties at every page size; delisted and closed cursors; refusals) and `apps/api/tests/api.test.ts` (paging, `SORT_UNAVAILABLE`, the cursor, a malformed clock refused at start).
- **Part 2a**: `/discover` (in the site's nav) is the stream: the polls open now, ten a page, in one of the API's orders (`new` by default, `closing`, `answered`), each a plain link marked `aria-current`, with a line saying what the order counts; more comes only from a "More questions" link, never an endless scroll. Each card shows the poll's title (version 5) or its question (version 1, or a version 5 with no title), its one question beneath a title, how many questions it has and when it closes, in the translation the page's locale picks (exact tag, then primary language, then the record's first), with the text's own `lang` and `dir="auto"`. The display text reaches a card only through `checkElectionRecordToShow` against the served definition's own hash (the website reads no registry, as on the poll page; the ballot client checks both against the registry): text the definition doesn't commit to, with other questions or option counts, missing, withheld or not hex, and an ill-formed definition, give a card with the poll's ID and no words (T-34, T-41). "Answer the question" (or "Answer N questions") links to the ballot client at `BALLOT_URL` with `#election=<id>`, which no server sees (T-10, T-11); without `BALLOT_URL` the card says answering isn't set up here, and a malformed one stops the server at start. `SORT_UNAVAILABLE` and `CURSOR_NOT_FOUND` get pages of their own, quoting nothing. Analytics keeps `/discover` and never its query (T-67). Tested in `apps/web/tests/stream.test.ts` (both versions against the published display-text vectors, every refusal, a fast-check property that any changed byte of the text is refused, the translation pick as a property, `BALLOT_URL`'s forms), `tests/ssr.test.ts` (the built page against a stub API: words, links, refusals, paging in both orders, both error pages, bad search parameters, one page of requests carrying nothing of the visitor's, the CSP's one off-site link), `tests/deployable.test.ts` (a bad `BALLOT_URL` refused at start, quoting nothing), `tests/analytics.test.ts`, and the stories in `src/components/stream.stories.tsx` (play and axe, desktop and 360px, both themes).
- **Part 2a known-weak**: a card has no asker or results yet ("who asked" waits on [[P2-26]], results so far on [[P2-15]]'s live releases); its answer button opens the ballot client on the poll, but the pick in the fragment needs the client's link parser to accept it (part 2b, in the `crypto-review` gate). A page fetches up to ten display texts of up to 4 MiB each from our own API (T-52); poll creation's limits (T-72) are what keep them small. The mockup's story stays until topics and places land.
- **Part 2b**: a card offers its first question's answers, each a link to the ballot client at `BALLOT_URL` with `#election=<id>&pick=<option>` (`ballotLink`), under a line saying the answer opens in the voting app and nothing is sent until the voter casts it there ("question 1 of N" on a poll of several, [[first-answer]]'s open question 9 answered this way: the first tap is an answer). A card shows its first question under a title of its own whatever the question count. The ballot client (`src/link.ts`) reads the pick only in that one form: after the election, at most once, canonical decimal below `MAX_OPTIONS`; anything else is a broken link. `main.tsx` takes the pick out of the address once read (`history.replaceState`, no new history entry), once per fragment outside rendering, so the tab's history and a reload keep only the election (T-45). `openingAnswers` chooses the pick on the first question when it has that option, else nothing; it holds through a failed load tried again, and is dropped after a restart or "Answer again". Nothing is sealed or sent without the voter's tap (T-41). Tested in `apps/ballot/tests/load.test.ts` (the pick's form, every near-miss spelling refused, round trip, fast-check), `tests/answers.test.ts` (the opening answers as a property, out-of-range and non-integer picks), `tests/page.e2e.ts` (the built client, by `hashchange` and by a fresh load: the pick leaves the address and adds no history entry; a pick of 64 is a broken link), the stories `Ballot/Questions` (opened with a pick, a pick the question doesn't have) and `Ballot/Open` (a pick kept through a retried load, dropped after a restart and after a cast and "Answer again"); in `apps/web/tests/stream.test.ts` (the card's options from the published display-text vectors, `ballotLink`'s form as a property), `tests/ssr.test.ts` (every card's answer links, and the page's only off-site links) and the stream stories (names, links, `lang`, descriptions, desktop and 360px, both themes).
- **Part 2b known-weak**: the browser's history list, address-bar suggestions and session restore may still hold the URL as opened, pick included, so someone holding the unlocked device can learn which answer was tapped on a card, not what was sent (T-45). Whoever writes a link sets the voter's starting answer, and a card could label its links with words that don't match their picks; the voter's own screen shows the choice in the checked text's words before anything is sealed, which is the only defence (T-41). [[first-answer]]'s interstitial ("Opening the secure voting app") and the one-question arrival-as-review screen aren't built: the card's link goes straight to the client, and a one-question poll still has "Check your answers". A `hashchange` to the same election with a pick reopens it, discarding answers in progress, as any new link does.
- Search (part 4) needs the question text out of the display text, which a takedown deletes, so its index must be deleted with it.
- `fillElectionSchedules` throws on a stored definition that no longer decodes, which stops the API's migrate step and so the deploy: loud on purpose, since every stored definition decoded when it was stored.
- **Topics and places** wait on [[P2-26]], which sets them at creation.
- **Known-weak (part 1b):** `answered` counts only the ballots our API boarded (through the keys stored with them); a direct-submitted ballot reaches the board as a contract event and isn't counted yet, which only understates a poll. Under `answered` a poll whose count passes the cursor's between two pages can be skipped or listed twice; the period-long window makes that uncommon. Each request counts every open poll's ballots in the window, whatever its `limit`, bounded only by the API's slots and deadline (T-52); the counts, which change only around each period's boundary, should be cached once traffic warrants. The index is built inside the migration's transaction, holding appends for as long as it takes, which the board's size today keeps short.
- **Known-weak:** the open window is judged by the server's clock against `opens_at` and `closes_at`, not by L2 time, so a poll can appear a little before the chain accepts its first ballot or stay a little after its last; `new` lists only polls whose registration the registry sync recorded.
