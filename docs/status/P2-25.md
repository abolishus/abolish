## Scope

What makes a poll feel alive: results pages, live bars, the voter's own state, following and reactions ([[PROJECT_BRIEF]], Priority). From `everyday-poll-page.tsx`, `everyday-poll-closed-page.tsx`, `poll-results-page.tsx` and `receipt-page.tsx`.

- **Results**: sentences first, then bars with plain percentages and counts, the tier in words; live polls ease to each newly published batch and say when, never interpolating ([[language]], Motion; [[P2-15]]); sealed polls say when results appear.
- **The voter's own state**: "You answered" and "Change your answer" live in the ballot client on the device, never on the server.
- **Following**: an account may follow a poll and be told when results land or a live batch is published. Following is not answering and says nothing about it.
- **Reactions**: emoji reactions on the poll itself, one per account per emoji, counts public, never on an answer (owner, 2026-10-21). Comments come later.

Rules for every part, as [[P2-19]]'s: everyday register by default ([[language]]); no hard-coded strings (`messages.ts`); CSP-safe (no inline `style`); server-rendered where the page is the website's; a fixed analytics template per route, never a path or poll ID (T-67); each component a story with a play function passing axe at desktop width and 360px; SSR and serve tests per route; the mockup's story deleted in the PR whose page matches it. Privacy holds everywhere: nothing an account does on the website (following, reacting, sharing, notifications) is ever stored, logged or keyed with a ballot, nullifier, receipt or the fact of having answered, and the T-10 no-join tests cover every new table, queue and log line ([[PROJECT_BRIEF]], Identity).

## Part 5a: reactions in `packages/core`

For part 5b (T-10, T-11): the control is offered on the website's poll page whether or not the account answered, never in the ballot client, never gated on or prompted by answering, so a reaction says nothing about participation and isn't timed to a ballot.

Taken first: parts 1, 2 and 4 need published tallies, which nothing produces yet ([[P2-9]] part 4, [[P2-13]]), and part 3 is the ballot client's.

- **The set:** `REACTIONS` is fixed: `heart`, `laugh`, `wow`, `thinking`, `sad` and `clap`, stored by name; the website draws each. It holds no agree or disagree, thumbs or the like, so no count reads as a second, unverified tally beside the poll's own ([[PROJECT_BRIEF]]: on the poll, never on an answer). A fixed set carries no text to moderate (T-17, T-68).
- **Who:** an account verified by e-mail, the rule token issuance uses today ([[0038-verified-accounts]]); the phone joins both when [[P2-31]] adds it.
- **Tables** (migration 0032, account class, T-10): `account_reactions` (account, `election_id`, reaction; one row each, with no time column, T-11) and `account_reaction_hours` (account, UTC hour, changes; no poll). The app role may set and take back a reaction, never change one in place. No foreign key reaches the definitions; core checks the poll exists. The no-join test allows `account_reactions.election_id`, which names the poll reacted to, never an answer.
- **Rules** (`src/reactions.ts`): `setReaction` sets or takes back one reaction and says whether anything changed; refused, in order, outside the set (`invalid`), and when setting, for an unverified account (`account`), an unknown election (`unknown-election`) or a hidden poll (`hidden`, judged inside the write's transaction); taking one back is always allowed, so an account whose address is unlinked can still withdraw it; then past 60 changes in the UTC hour (`too-many-this-hour`, T-52), counted in the statement that checks it, so concurrent changes can't both take the last one, and rolled back with the reaction. A change that changes nothing isn't counted. `readReactionCounts` gives every reaction's count (zero included) and refuses a hidden poll; a delisted one keeps its reactions. `readOwnReactions` gives the account's own. `pruneReactionHours` drops hours before the last one (a margin, so an instance whose clock runs ahead never wipes the current hour's limits) and runs on the website's account prune timer.
- **Tested** against the database: the Drizzle tables match the migration and the set matches the table's check; columns (no time but the hour), grants, check constraints and the cascade on account deletion; a property test of any sequence of changes by several accounts against a model of the table; concurrent setting by two accounts and by one; per-poll counts; every refusal; the hour's limit, its concurrency, the next hour and pruning; and that the module touches no board table but the definitions.
- **Known-weak:** no column keeps a time, but the database still orders and dates each reaction (`xmin`, the WAL, backups, statement logs), so an insider or a dump can line up "account A reacted to poll P" with a ballot boarded on P moments before, which links A to having answered when few answer P at that moment (T-11; [[P2-11]] keeps statement logs and `track_commit_timestamp` off). A moderator hiding a poll while a reaction's transaction commits can still let that one land; the counts are refused from then on. A change that changes nothing is never counted, so its cost is bounded only by the proxy (T-52). The counts are as Sybil-resistant as e-mail verification, which is to say barely (T-01), and are never used to order or rank polls (T-68). A count is public the moment it changes, so whoever watches a poll's counts sees reactions arrive, though never whose.

## Part 5b: the website's route and the control

- **Routes** (`apps/web/src/node/reactions.ts`, mounted by the Node front as the `reactions` route class, T-10, T-67): `POST /reactions/counts` answers a poll's counts to anyone and never gets the session (the page sends it with `credentials: "omit"` and the front drops any cookie on that path); `POST /reactions/own` answers them with the signed-in account's own; `POST /reactions/set` sets or takes back one and answers both after the change. The poll travels in a strict JSON body, never the path; every POST carries our Origin; answers are no-store; core's refusals keep their codes (`ACCOUNT_UNVERIFIED`, `UNKNOWN_ELECTION`, `HIDDEN`, `TOO_MANY_THIS_HOUR`), and the request log keeps the route class only.
- **The control** (`src/components/poll-reactions.tsx`, on the poll page under "Answering", from `src/account/reactions.ts`): the six reactions, each drawn by the website with its name for screen readers, and their counts for every visitor; "React to this poll" reads the account's own and turns each into a toggle (`aria-pressed`), focus moving to the first. Signed out, unverified, past the hour's limit or hidden since, it says so plainly, with a link to sign in or to verify. Offered alike whether or not the visitor answered, never in the ballot client and never prompted by answering (T-10, T-11). Not shown on a hidden poll (T-68).
- **Counts after hydration, not server-rendered:** the page's server reads only the API and never gets the account cookie (`src/node/serve.ts`), so the server's HTML has the section and "Loading reactions…", and the counts arrive once the page's script runs. Asking for the account's own only when the visitor chooses to react means opening a poll page never tells the server which account opened it (T-11).
- **Tested:** over HTTP against the database as the app role: counts for anyone, own and set per account, an idempotent set, take-back, every refusal (unverified, unknown poll, hidden for counts, own and set, with a take-back that still lands), the hour's limit, malformed bodies, Origin, type, query and path refusals, that the counts never call `accountOf`, that the front hands the counts no cookie while own and set get it, that the page sends the counts without credentials, and that the log names neither the poll nor the reaction; the client's requests, its strict reading of every answer, and each refusal's wording (a property test over unknown codes); the client's set against core's `REACTIONS`; the deployable serving `/reactions/counts` as `abolish_app`; the poll page's SSR with the section, and without it for a hidden poll; stories for the counts, toggles, dark, signed out, unverified, the limit, an ended session, hidden and unread, each with a play function and axe at desktop width and 360px.
- **Known-weak:** whether an account is verified shows only when it tries to react, as the website has no keyless check of it. The counts don't follow others' changes until the page is read again. `/reactions/own` names the account beside the poll it opened, when it asks to react, which the server sees though nothing stores or logs it (T-11). The glyphs are the platform's emoji font, so they look different on each device. Taking a reaction back on a poll hidden since answers `HIDDEN` though the take-back landed; the page then shows the poll as hidden.
