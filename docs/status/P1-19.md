# P1-19: `packages/verifier` CLI

- State: in progress (parts 1, 2 and 3a merged in #57, #59 and #76; part 3c, the election identifier, version and anchor address from the definition, in review; 3b and 4 to follow)
- Branch: `claude/p1-19`
- Phase: Phase 1: Threat model, spec, crypto core, circuits, verifier, reference election (CLI only)

## Scope

`packages/verifier` CLI: download the board (from local files first), recompute and check everything, and check a served ballot client against a signed release. Spec in `docs/spec/verifier.md`. Per [[0005-permanent-archive]]: check the archived event sequence against each contract's event accumulator using archived storage proofs at output roots (reporting whether each root settled by TEE-only or ZK proof), walk the manifest chain and every anchor's `archiveLocator`, and pass with Arweave or IPFS unreachable.

## Built on #40

The verifier imports `@abolishus/crypto`, the first import between workspace packages. Crypto's `exports` point only at `dist/` (gated.ts), so CI builds crypto first; #40 (`ci:`) added that build to the setup action and before the gated check, and has merged.

## Plan

The item is built in parts, each its own PR on this branch's name:

1. **Library, bundle, report and board checks** (this part): local inputs only, checks 4.1 and 4.2, every other check reported unverifiable.
2. **Command line** (this part): `runCli`, its exit codes and summary, and an entry point run from a checkout. Installing it as a binary needs `src/bin.ts` packed as a second entry and a `bin` field, and `gated.ts` allows neither yet (the build script must be exactly `vp pack`, which packs `src/index.ts` only, no build config may configure `pack`, and `bin` isn't a permitted manifest key): a `ci:` PR first (#60, waiting on the owner), then a small follow-up.
3. **Inputs from L1 and the definition**, replacing bundle members:
   - 3a (this part): anchors and `now` from the board anchor's L1 state (P4-1 part 1, #73), given a header;
   - 3b: trusting the header (a pinned checkpoint and the beacon light-client protocol, or a block hash the user vouches for), the anchor's address and clock from the pinned roots once P4-1 part 2 deploys, and `f` from the creation event's evidence (4.4);
   - 3c (this part): the election identifier, the pinned board-entry version and the anchor's address from the definition (P1-10b, #35), with its decoding and well-formedness under 2.1. The seal `lastSegment` waits on the post-close windows `W` (P1-13, P1-18), and the rest of the clock on 3b's pinned deployment.
4. **Event-accumulator replay (4.4)**, once P1-18 part 4 defines the contract-event record and its evidence. Then archive walking (4.3) with P4-3, and the ballot, ceremony and tally checks as P1-12 to P1-15 land.

## What was built (part 3c)

## What was built (part 3a)

- [[verifier]], Anchors from L1: a format-2 bundle (`abolish-verifier-bundle/2`) gives an L1 header, the trie nodes `eth_getProof` returns, `f` and any checkpoints no copy matches. The verifier proves the anchor's account and every slot from `max(lowest, f)` to the last ended period against the header's state root, matches each non-zero word against the copy's checkpoint after that segment or a given checkpoint with that hash, and passes them to the board checks with `anchoredAt` the end of their period. Five L1 codes (`l1-proof-missing`, `l1-proof-malformed`, `l1-anchor-absent` (also for an account without code), `l1-range-too-long` (over `2^20` words), `l1-checkpoint-unknown`), each unverifiable, never failed. The report gains `l1` (block hash, number, time and the anchors read) and three inputs (`l1Header`, `anchorAddress`, `firstSegment`), still `local-file`, so every run stays unverifiable.
- [[contracts]], Board anchor, Verification: a word no copy matches needs only the checkpoint, from any source, since its hash is the word; no receipt proof.
- `packages/verifier/src/l1.ts`: strict RLP, the header, a Merkle–Patricia trie walk over a node pool keyed by Keccak-256 (`@noble/hashes`, a new dependency of the verifier), the anchor's slots and `anchorsFromState`. `packages/crypto`: `copyCheckpoints`, `encodeCheckpoint`, `decodeCheckpoint`.
- `docs/spec/vectors/l1-anchor.json` from `packages/verifier/scripts/l1-anchor-vectors.py`: BoardAnchor deployed on Anvil, `board.json`'s valid board anchored, Anvil's raw headers and proofs.
- Threat history in T-24, T-36 and T-53; a changeset (minor for both packages).

## Tested (part 3a)

Each checks the block hash, the anchors read and their source, the rows of 4.1 and 4.2, the inputs and that the verdict stays unverifiable.

- RLP: `decode(encode(x)) = x` against a reference encoder, and any decoded bytes are the canonical encoding of what they decode to (fast-check, `FC_NUM_RUNS=1000`); ten non-canonical or truncated forms rejected; 16 nested lists accepted and 17 rejected.
- Headers: fewer than 15 fields, a list field, a short state root, a number with a leading zero, a time over 64 bits and trailing bytes rejected; extra fields accepted.
- Trie: one-leaf tries prove every other key absent (fast-check); a branch, an extension and an embedded node followed; twelve malformed shapes rejected.
- Format-2 bundles: 20 malformed `l1` members rejected (strict keys, address length and case, `firstSegment` form and range, empty, odd, non-RLP and non-header headers, node and checkpoint shapes), and any member replaced by another shape is a `BundleError` (fast-check); a bad header exits 22 from the command line, never 1.
- The two slot formulas match `cast index`.
- A clock and `f` asking for `2^20` words are read; one more stops with `l1-range-too-long`.
- `copyCheckpoints` equals `checkpointOf` on every generated well-formed board, gives every `board.json` valid board's anchored hashes, never gives the honest hash for a changed copy, and stops at the first entry past the segment or at a short entry.
- Mutation checks by hand: ignoring `f`, reading one period too far, taking the copy's checkpoint without comparing its hash, and dropping each RLP, header and trie strictness check each fail a test.

## Known-weak

- **The L1 header is a local input** (part 3a). Anchors read from L1 are only as good as the header, the anchor's address and `f`, all local files until part 3b, so no run is verified or failed through them yet. The report gives the block's hash so a user can compare it with a node they trust.
- **A crafted `f` or clock still costs some time** (part 3a): until they are pinned, a bundle chooses how many slots are read, up to `2^20` (about a second here) before `l1-range-too-long`. Under a short testnet period an honest election reaches that bound sooner (about 12 days at 1 second), and is then unverifiable, never failed. It changes no verdict.
- **A wrong address holding some other contract reads as no anchors** (part 3a), so `unanchored` against the inputs; harmless while the address is a local input, and closed when part 3b pins it and 1.2 checks its code.
- **Extension and embedded trie nodes are tested only on hand-built tries** (part 3a): the Anvil tries in the vectors are too small to contain them.

- **No verdict yet.** Every input is a local file and most checks aren't implemented, so every run reports `unverifiable`. That is by design, not a gap in what's built.
- **The summary for authenticated inputs is untested.** It can't be reached while `local-file` is the only input source; part 3, which adds the first authenticated source, must test the one-line `verdict:` summary.
- **No installed binary yet.** The command line runs from a checkout (`src/bin.ts`); packing it and declaring `bin` need a `ci:` change to `gated.ts`, then a follow-up.
- **Anchored encodings `board.bin` can't carry.** If an operator anchors an entry that doesn't split back into itself (bytes past its payload), every copy is short or mismatched, and the election stays unverifiable for good, never failed. This is a residual in [[verifier]], Bundle, with the same candidate fix as [[board]]'s withheld tails: anchor a content address of each segment object (P4-1, P4-3).
- **An anchored oversize entry is hashed in full** (up to 4 GiB) before 4.1 rejects it. Only the anchoring authority or a mirror within the anchored extent can cause this, and it costs time, not the verdict (T-52).
- **`board.bin` is split by the version-1 layout.** An anchored entry in another layout (no other version exists) would leave the copy unsplittable or mis-split: unverifiable from that copy, never a failure. If a version 2 changes the layout, splitting must follow the pinned version.

## Independent review (part 3a)

A fresh in-session subagent reviewed the diff against `.github/review/crypto-review.md`: nothing blocking, no injection attempt. It confirmed the trie walk can't prove a wrong value or absence under a genuine state root, the RLP is strict, the slots match Solidity's layout, the segment range matches the contract's window, and no L1 failure can fail an election. Its findings:

- `copyCheckpoints` was O(segments × entries): now one pass over segments in ascending order.
- A ~1 KB bundle with an old epoch, `f = 0` and a one-node storage trie looped about 4·10⁹ times, and bundles may come from untrusted mirrors, so the user pays: now at most `2^20` words, then `l1-range-too-long`.
- The spec didn't fix which L1 code wins when two apply: it now says the account, the lowest word, the range, every word in segment order, then matching in segment order, as the code does.
- "Ended by `now`" is now `epoch + (s + 1)·period ≤ now`, and the hex rule says non-empty, as the parser does.
- An account without code (a wrong address that is an EOA) gave no anchors and so `unanchored`: now `l1-anchor-absent`, with a vector.
- Extension and embedded nodes are tested only on hand-built tries: listed under Known-weak.

A second pass over the fixes found nothing blocking. Its follow-ups, applied: the account's storage root is checked before its code hash, so a malformed account is `l1-proof-malformed` whatever its code hash; the boundary test asserts the walk starts at `2^20` words (it stops at a node the vector lacks), not just that it isn't refused; a property compares `copyCheckpoints` with the reference on any segment fields, short entries and shuffled, repeated segment lists; Known-weak notes a short period and a wrong contract address.
