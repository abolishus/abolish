# P2-21: The membership prover in the ballot client

- State: in progress (part 1, the prover's choice ([[0009-membership-proof]], Amendment), merged in #327; part 2, the prover core in `packages/crypto` (inputs, key check, self-verification, re-randomisation), merged in #331; part 3a, a fixed Tier 0 tier's cell from the board's group-registry events and the streamed path, merged in #338; part 3b, a fixed Tier 1 tier's leaves from the board, merged in #342; Tier 2 tiers wait on the registry's Tier 2 addition path ([[P3-4]]); the owner approved its `ci:` asks on 2026-10-17 and they landed; part 4a, the gated `packages/membership-prover` adapter with the vendored key and witness calculator, merged in #368; part 4b, the prover worker, the key's delivery and the proving screen, next)
- Branch: `claude/p2-21`
- Phase: Phase 2: Open polls end to end at Tier 0

## Scope

The ballot client's side of [[membership]]: from a voter's identity secret, their tier's additions and an election definition, produce the 256-byte `membership_proof` a ballot carries, in the Web Worker, on the voter's device. Nothing in the workspace proves membership today ([[P1-17b]] verifies, [[P2-8]] and [[P5-4]] were left to prove), so the API's admission ([[P2-3]] part 2d) and the verifier's 5.1 reject every real ballot. This item is the gate in front of casting: [[P1-20]] part 2b (the reference election's casting stage), [[P2-8]] part 3 (sealing and sending), [[P2-20]]'s sending, Done and receipt screens, and so every ballot on staging.

The obligations are already written; this item builds to them, it doesn't reopen them:

- **The circuit and keys.** Semaphore v4.14.3's circuit and Groth16 keys, unchanged, depth 32 passed explicitly, never inferred ([[membership]], Tree depth). The proving key is `semaphore-32.zkey` by its sha256 (`2e5f7a9f880c337134ee4c7fc4e53573813b4c9c6ae46221c0b56e7992304650`), the one [[P1-17b]] part 2 checked for well-formedness; any other key is refused, whatever its source ([[0009-membership-proof]], Consequences; T-07, T-12).
- **The prover is pinned by hash.** Whatever Groth16 prover runs is pinned, in the release record, like the key.
- **Randomisers from a CSPRNG**, and the identity secret used for Abolish proofs only (chosen-scope linkage, [[membership]], Security notes).
- **The path is built on the device.** The client rebuilds its 32-level path from every leaf of the tier's tree (or its cell's, [[membership]], Cell tree) and checks the rebuilt root against the definition's. It never asks a server for its own path, which would reveal its leaf index (T-10, T-13).
- **The client verifies its own proof** under the pinned verification key before it leaves the device ([[P1-17b]]: a witness that doesn't satisfy the circuit would leave a witness-dependent term in `C`).
- **The scope is derived, not supplied**: `membershipScope` from `packages/crypto` (fixed tier) or the rolling scope ([[0028-rolling-electorates]]), over the definition the client already checked.

## Rules

- **The bundle allow-list and CSP hold until the owner changes them.** The prover is third-party runtime code the allow-list doesn't admit (`tests/bundle.test.ts`, mirrored in `.github/tools/ci/src/ballot.ts`), a WebAssembly prover needs `'wasm-unsafe-eval'` in `script-src`, and fetching the key and the leaves needs `connect-src` (today `'none'`, so not even the client's own origin). Each is an owner-reviewed `ci:` change (rule B, T-43, T-59); an agent session proposes it in the PR and in the status file, as [[P2-8]] part 2b does for its origins, and builds everything that doesn't need it meanwhile.
- **No network in the prover itself.** The prover takes the key bytes, the leaves and the secret as arguments; fetching and caching are the client's (part 3), so the prover's tests run in Node with no server.
- **No motion on the ballot** ([[language]]): the proving screen is a still screen with words and a plain progress indicator that reports real progress, never an animation that stands in for it.
- **Phone-sized, and measured.** The depth-32 key is Semaphore's largest and a proof hashes 32 levels whatever the group size ([[membership]], Tree depth, Cost). This item measures proving time and memory on a desktop and a mid-range phone and records them here. If they're unacceptable, the answer is a new ballot version with a smaller protocol depth, decided by the owner, never a depth the client or a server chooses.
- **Protocol code**: the prover, its key handling and the path building are inside the `crypto-review` gate; `apps/ballot` needs the independent in-session subagent review (AGENTS.md, Before opening any PR, step 5).

## Plan

Each part is one PR on this branch's name.

1. **Choose the prover** (ADR amendment to [[0009-membership-proof]], and a prototype). Two candidates, decided by measurement against the rules above:
   - **snarkjs** (and its `ffjavascript`): the prover that made the pinned vectors; GPL-3.0, which sits under this repository's AGPL; a WebAssembly prover and a circom witness calculator (`semaphore.wasm`) that must be pinned too.
   - **An Abolish Groth16 prover over `@noble/curves`' BN254** with the witness computed in TypeScript: no third-party runtime code beyond what the allow-list already has, but a new primitive that the gate must review line by line, and slower in JavaScript. [[P1-17b]] already holds the field, curve and Poseidon pieces.

   The part ends with the choice, the exact versions and hashes, measured times on both devices, where the code lives (a new package if it isn't `apps/ballot`'s own), and the owner-reviewed asks: the allow-list entry, the CSP lines and the key's source. The key is pinned from `snark-artifacts.pse.dev`, which isn't a vendored or re-fetched source ([[P1-17b]], Known-weak), so the part also proposes how CI re-fetches and checks it.

2. **The prover core.** `prove(secret, leaves, definition, message)` returns the proof, built to part 1's choice and tested in Node against `docs/spec/vectors/membership-proof.json`'s Semaphore-made proofs: every proof it makes verifies under `packages/crypto`'s own verifier; its output for a fixed secret and path matches the vectors' public signals; a witness that doesn't satisfy the circuit, a wrong key hash, a path that doesn't climb to the definition's root, a depth other than 32 and a forbidden commitment are refused before any proving. fast-check properties over random trees and members; a mutation test that removes the self-verification fails.
3. **The tier path.** Rebuilding the 32-level path from the board's registration events (or the leaves the client fetches), the root check against the definition, and the cell tree for regional elections. The leaf source is part of the decision in part 1: reading the board's own entries through the API routes that exist is preferred, since each is checkable against the definition, and a new route for leaves is the fallback. Large tiers are streamed, not held twice.
4. **The worker and the key's delivery.** The prover in the existing Web Worker protocol (`apps/ballot/src/worker`): the key fetched once, hashed as it streams, kept in the browser's cache and re-checked on every use; progress messages; a proving screen in the style of the sending mockups (`everyday-sending.stories.tsx`, `sending.stories.tsx`) as a real screen with its messages, a story with axe at desktop width and 360px, and a plain refusal that names which check failed. Needs the `ci:` changes above.
5. **Wire it in.** [[P2-8]] part 3's sealing takes the proof; [[P1-20]] part 2b's casting stage uses the same prover (through Node, same code), and the reference election's membership-prover stub is deleted.

## Part 1 (#327)

Decided ([[0009-membership-proof]], Amendment, `Accepted (agent) — owner may veto`): **snarkjs 0.7.5 with ffjavascript 0.3.1, single-threaded, in a prover worker of its own.** The ballot worker verifies its output under the pinned key against public inputs it computed itself, re-randomises it with CSPRNG scalars in `packages/crypto` (`(t⁻¹·A, t·B + t·u·δ₂, C + u·A)`, Baghery, Kohlweiss, Siim and Volkhov, FC 2021) and verifies it again, so zero knowledge rests on `@noble/*` and the platform CSPRNG, not on snarkjs's randomness (an ffjavascript ChaCha stream seeded once from `crypto.getRandomValues`, or from `Math.random` without `crypto`) or its correctness. The separate realm keeps a hijacked snarkjs from patching the CSPRNG or the curve classes the re-randomisation uses. [[membership]], Security notes, now requires the self-check against recomputed inputs, the re-randomisation and the separate realm of every prover. An `@noble/curves` prover of our own was rejected: it needs a TypeScript witness generator for all 9,418 wires, a second implementation of Semaphore's circuit (its MSMs and FFTs are also estimated at 5.5× snarkjs's whole proof).

Measured (`packages/crypto/scripts/membership-prover-bench.mjs`, outside the workspace, 4-vCPU cloud host): one proof takes 3.7 s single-threaded in Node and in Chromium, 1.15 s with four threads in Node, 16.2 s and 24.1 s in Chromium at 4× and 6× CPU throttling; the `@noble/curves` estimate (random scalars) is 20.6 s; re-randomising takes 34 ms. snarkjs's threaded mode starts `blob:` workers the CSP refuses, so the client proves single-threaded and never calls snarkjs's verifier or key export (which build the threaded curve).

Where the code lives: inputs, the key-hash check, self-verification and re-randomisation in `packages/crypto`; the snarkjs call in a new gated package, `packages/membership-prover` (direct runtime dependencies `@abolishus/crypto`, snarkjs and ffjavascript only), imported by the prover worker alone and never by the verifier.

Owner asks, each a `ci:` change (rule B), listed in the Amendment: the new gated package and its dependency rule; a second worker URL for the `ballot-worker` policy; the bundle allow-list entry for snarkjs's and ffjavascript's browser builds in the prover worker's chunk, with the worker ban on `fetch` and `Worker` still applied (the build stubs fastfile's URL branch and ffjavascript's thread manager); `'wasm-unsafe-eval'` in `script-src` and `'self'` in `connect-src`; the zkey and witness calculator vendored in the package and re-fetched from `snark-artifacts.pse.dev` by CI; and, owner-only, GPL-3.0 code in the AGPL-3.0-only client.

Known-weak:

- No real phone was measured: the 4× and 6× rows are throttled Chromium. The phone measurement stays open for part 4, when the worker runs in the real client.
- snarkjs's prebuilt browser bundles and the witness calculator `semaphore-32.wasm` are trusted as published, not rebuilt from source.
- The Chromium rows ran snarkjs's IIFE build on the main thread, not the ESM bundles in a dedicated worker; part 4 re-establishes timing and CSP behaviour in the real worker, as assertions.
- A hijacked snarkjs can still leak bits of the secret by when or whether it succeeds; part 4 pads proving to a fixed duration, which bounds timing, not the failure bit.
- Single-threaded proving is about 3× slower than snarkjs's threaded mode.

Part 2 needs none of the `ci:` changes: the inputs, key check, self-verification and re-randomisation are `@noble/*` code in `packages/crypto`, tested in Node against `membership-proof.json`. Its snarkjs adapter waits on the gated-package `ci:` change; until it lands, part 2's tests drive snarkjs from a script outside the workspace, as the vector generators do.

## Part 2 (#331)

`packages/crypto/src/membership-prover.ts`, all `@noble/*` code, no `ci:` change needed:

- `membershipProverInput(secret, leaves, statement)`: from the 32-byte identity secret, the tier's (or cell's) leaves and a statement of values the client verified (definition hash, tier, root, `M`), the circuit inputs snarkjs takes (`MembershipWitness`: secret, `merkleProofLength` always 32, the index of the voter's first leaf, 32 siblings, `F(ŝ)`-mapped scope and message) and the public signals `[ρ, ν, m̂, ŝ]` computed here (scope from `membershipScope`, `ν = Poseidon2(ŝ, s)`). Refused before any proving, as `MembershipProverError` codes the part-4 screen can name: `secret` (not `1 ≤ s < l`), `not-a-member` (no leaf holds the commitment; a forbidden commitment can't be a leaf, so it lands here) and `root` (the path built from the leaves doesn't climb to the definition's root). No depth parameter exists.
- `checkMembershipZkey(zkey)`: `zkey` unless the bytes' sha256 is `MEMBERSHIP_ZKEY_SHA256`.
- `finishMembershipProof(input, proof)`: accepts only inputs `membershipProverInput` built (so never the prover's `publicSignals`); strict decode and verification under the pinned key (`proof`, before any randomness is drawn), Baghery–Kohlweiss–Siim–Volkhov re-randomisation with `t ∈ [1, r)`, `u ∈ [0, r)` drawn by rejection from `randomBytes` (`rerandomiseMembershipProof` in `membership-proof.ts`, not exported from the package), and verification again (`rerandomised`). The seam taking the randomness, `finishMembershipProofWith`, isn't exported either.

Tested (`tests/membership-prover.test.ts`) against a new independent vector file, `docs/spec/vectors/membership-prover.json` (`scripts/membership-prover-vectors.mjs`, outside the workspace: Semaphore 4.14.3's `Identity` and `generateProof`, poseidon-lite trees, ethers' keccak), over `membership-proof.json`'s identities, definition hash and trees plus a tree with one commitment at two leaves: the witness equals, field for field, what Semaphore's `generateProof` hands snarkjs; the signals equal Semaphore's; each member's secret finds exactly its own commitment; every Semaphore proof finishes into other bytes that verify, and twice into two different outputs. Refusals: out-of-range and wrong-length secrets, non-members, other roots and added, removed or reordered leaves, out-of-range statement values, a forbidden value among the leaves, wrong keys, another statement's proof, flipped, short, long and zero proofs. Mutation: removing the first self-verification fails the test that a bad proof is refused before any draw. Rejection sampling, `u = 0` and `t = 1` are driven through the seam; fast-check properties over random scalars (output verifies and each of `A'`, `B'`, `C'` equals the formula, so dropping the `u` terms fails) and random tiers (path, first-leaf index and signals; a random secret is never a member).

Known-weak:

- The positive path of `checkMembershipZkey` isn't tested: the 5.8 MB key isn't in the workspace until the vendoring `ci:` change; the comparison is with the constant `membership-proof.json` already pins.
- The secret becomes a BigInt and a decimal string in the witness, which can't be wiped; snarkjs takes it no other way.
- Nothing here enforces the separate realm: running `finishMembershipProof` where snarkjs can't reach is part 4's.
- The second verification can't fail for a correct implementation, so no test reaches `rerandomised`.
- BigInt arithmetic isn't constant time: `t⁻¹` is computed as `t^(r−2)` (a public exponent) rather than noble's variable-time Euclid, but noble's scalar multiplication and JavaScript BigInts still don't promise constant time.
- The leaves are held in memory whole (two copies); streaming large tiers is part 3.

## Part 3a (#338)

`packages/crypto`, no `ci:` change needed:

- `tierMembership(records, tier, commitment, group, pins)` (`src/tier-membership.ts`): the voter's cell in a fixed Tier 0 tier (definition versions 3 to 6), from the election board's contract-event records as `GET /board/entries` serves them, in any order. The leaf source is the board's own entries, as the plan preferred: no new route, and nothing asked that names the voter's leaf (T-10, T-13). Only the group registry's records are read; they are sorted by `n` (the board's order isn't fixed yet, [[verifier]] 4.4, Residuals), a record boarded twice is read once, and two different records at one `n` or blocks that go backwards refuse (`board-event`), as does a record failing the event check. A boarded `RegistrarsPinned` must name the release's pins (`registrars`). Each listed group needs exactly one `GroupCreated` by `root_l2_block` (`group-created`) of the definition's tier (`group-tier`), and is replayed strictly with `applyGroupRecords` under the release's registrars, threshold, chain ID and registry, with each addition's `firstIndex` topic checked against its record first, as 2.4 replays it (`group-history`; T-71). The regions and cells are recounted with `firstOccurrence` and `foldRegions` and must equal the definition's counts (`electorate`). The voter's commitment must be a live leaf of the group it registered in (`not-a-member`), and the group it is counted in after first occurrence must be in the same region, or the client alarms (`moved`, [[membership]], Cell tree; [[0019-regional-cells]], Consequences; G-2, T-06, T-16). It returns the cell's index, the definition's root for it and the cell's leaves as a re-iterable view over the groups' lists, never concatenated. The root isn't recomputed here: `membershipProverInput` checks it.
- `tierTreeMemberPath(leaves, member)` (`src/tier-tree.ts`): the first leaf equal to `member`, its 32 siblings and the root, in one pass over an iterable holding 32 nodes. `membershipProverInput` now takes any iterable of leaves and builds the path with it, so the cell's leaves are never copied or held with their levels, and it checks both the streamed root and the circuit's climb against the definition's root.
- `identityCommitment(secret)` (`src/membership-prover.ts`): the commitment the client looks for.

Tested (`tests/tier-membership.test.ts`, `tests/tier-tree.test.ts`): every tier of `regional-cells.json` (from an independent Python implementation) that a strict replay accepts, boarded as records signed under `group-registry.json`'s test registrars with `contract-event-v6.json`'s topics, gives each member in the vectors' paths its cell, the cell's root, leaf count and the vectors' siblings; the `repeat-moves-a-voter` tier alarms `moved` for the voter registered in group 33 and not for group 31; a Semaphore identity from `membership-prover.json` boarded in a one-group tier gives exactly the circuit inputs Semaphore's `generateProof` gives, and a definition root the board's leaves don't reach is refused by the prover (`root`). The same result whatever the records' order, with duplicates and other contracts' records (fast-check), and with records after `root_l2_block` and of unlisted groups. Each refusal has its test: a record failing the event check, two records at one `n`, blocks going back, other registrars or threshold, a missing, late, repeated or other-tier `GroupCreated`, Tier 1 and Tier 2 groups, an addition under the threshold, a replayed batch, a `firstIndex` topic other than the record's, region and cell counts off by one, a commitment not in the tier, in another group, in an unlisted group, or removed. `tierTreeMemberPath` against `tier-tree.json`'s independent paths and roots, and against `tierTreePath` and `tierTreeRoot` for random leaves (zeros included) at every size around a power of two up to 65 (fast-check, read through a one-shot iterable).

Known-weak:

- **Tier 1 and Tier 2 tiers are refused** (`tier-unsupported`). A Tier 1 group's leaves are its counted additions, which the board carries exactly ([[verifier]] 4.4, Tier 1 boarding) but the client can't recount without the archive; Tier 2 has no addition path yet ([[P3-4]]). Part 3b.
- **Rolling tiers** (definition version 7) aren't decodable in `packages/crypto` yet ([[P2-17]]); their path is the same builder over chain-ordered leaves at a step, added with that codec.
- **The replay still holds the tier's leaves**: each group's replayed list, then the first-occurrence copy and its set of seen commitments, so a tier's leaves are held about twice at the peak, before the path pass, which holds none. Removals name indices, so a replay that held nothing would need two passes over the records.
- **Strict replay costs a signature recovery per approval** (about 4,000 batches of 256 and 8,000 recoveries for a million members), which the client pays on top of the Poseidon hashes; not yet measured on a phone (part 4).
- **The cell's root isn't checked here**, only by `membershipProverInput`; other cells' roots aren't recomputed at all, since the client proves only against its own and the verifier's 2.4 checks the rest.
- **A malicious board can stop a voter**, never misplace one: any record the client refuses blocks proving, as it should (fail closed), and the refusal names the check, not who caused it.
- **A hidden move isn't named as one.** A board that leaves out the batch putting the voter's commitment in a lower group of another region (registrars repeating it, T-06) is refused as `electorate` or, by the prover, `root`, not `moved`: the voter still never proves in a cell it didn't register in, but the alarm is a count mismatch.
- **Member records before their group's `GroupCreated` in `n` order are accepted**, where the verifier's Tier 1 path calls that a break; the client doesn't authenticate `n`, and the replay's signed positions decide the leaves.
- **The registry address and chain ID come in the pins**, not from the definition the client checked; wrong ones are refused at `group-history` (the approvals don't verify) or by the prover's `root`.
- **Fetching must not narrow.** Whatever fetches the records (part 4) must read the whole board, never entries filtered by the voter's group, which would tell the server the voter's region (T-10, T-13).
- No API pagination or fetching here: reading `GET /board/entries` and decoding its records is the client's ([[P2-8]] part 3, this item's part 4).

## Part 3b (#342)

`tierMembership` (`packages/crypto/src/tier-membership.ts`) now takes fixed Tier 1 tiers too. A listed Tier 1 group's leaves are its boarded `Tier1MemberAdded` records in blocks up to `root_l2_block`, one leaf each in log order, read at their offsets after the event check has decoded each record strictly. The board must carry exactly the group's counted additions ([[verifier]], Contract events, Tier 1 boarding), so no new route and nothing asked that names the voter's leaf (T-10, T-13). Whether an addition counts rests on the registry's whole Tier 1 and Tier 2 history in the archive ([[vouching]], Counting across the deployment), which the client doesn't read, so no vouch is checked here: the definition's counts and the cell's root, which `membershipProverInput` checks over these leaves, bind them (T-06, T-53). A boarded addition no count can take (one logged before its group's `GroupCreated`, a forbidden commitment, or one already the group's leaf) is refused at once as `group-history`. `MembersAdded` and `MembersRemoved` naming a Tier 1 group change nothing ([[vouching]], Counted additions). The first-occurrence rule, the region and cell recount and the `moved` alarm apply as for Tier 0. Tier 2 tiers are still refused (`tier-unsupported`): the registry's `createGroup` refuses tier 2 until P3-4 specifies its additions ([[contracts]], Group registry).

Tested (`tests/tier-membership.test.ts`) against `vouch-count.json`'s deployment (an independent generator's counted additions and each group's leaves at each block): a board of the Tier 1 groups' creations and counted additions gives each listed group's leaves at every block where the vectors list any, for every member; three Tier 1 groups in two regions give the first-occurrence cell and alarm `moved` for a commitment counted in another region's group; a board carrying an uncounted copy of a counted commitment (`group-history`), a fresh uncounted addition or missing a counted one (`electorate`), an addition that doesn't decode (`board-event`), one logged before its group's creation or a forbidden commitment (`group-history`) is refused; other groups' additions, the group's own after `root_l2_block` and `MembersAdded`/`MembersRemoved` naming it change nothing; and `membership-prover.json`'s tree boarded as Tier 1 additions gives the prover the path Semaphore's `generateProof` takes.

Known-weak:

- **No vouch is checked on the device.** A board that shows other leaves than the counted ones stops the voter (counts or root), never misplaces one. But a board operator and a definition author who collude can give a Tier 1 cell fabricated leaves whose secrets they hold, consistent between board and definition, and the client proves in it: its anonymity set is then the insiders' padding, and the voter's nullifier the only one they don't know (T-13, T-06). The verifier's 2.4 fails that definition over the archive, but only after the ballot is cast. At Tier 0 the device checks the registrars' signed positions, which the same insiders hold; at Tier 1 it checks nothing an insider can't fake, until the client reads the archive.
- **A MOCK registry isn't refused.** [[vouching]] (MOCK Tier 2 members) fails a definition naming a Tier 1 group of a MOCK-type registry unless it carries the test flag on an allowed chain; that constant arrives with [[P3-4]], and the client doesn't check it. Harmless while the release pins the registry.
- **A broken Tier 2 history isn't seen** ([[vouching]], A broken Tier 2 history): the client never reads Tier 2 records, so a definition the verifier fails as `group-history` for that reason is one the client proves against.
- **Tier 2 tiers are refused** until [[P3-4]] specifies the registry's Tier 2 additions.
- **Rolling Tier 1 tiers** (definition version 7) wait for that codec ([[P2-17]]), as rolling Tier 0 ones do.

## Part 4a (#368)

Part 4 is split: 4a is the prover's own package, tested in Node; 4b puts it in the client (the prover worker, fetching and caching the artifacts, progress messages and the proving screen).

- `packages/membership-prover` (gated, source-only, AGPL-3.0-only; direct runtime dependencies exactly `@abolishus/crypto`, snarkjs 0.7.5 and ffjavascript 0.3.1, as `gated.ts` requires). `proveMembership(witness, { zkey, wasm }, onProgress?)` copies both artifacts, refuses them unless their sha256s are the pinned ones, refuses a path of other than 32 siblings, runs `groth16.fullProve` single-threaded on in-memory files only (never a path or URL, so fastfile never fetches), and returns snarkjs's affine proof as the 256-byte `membership_proof` encoding, discarding its public signals. `onProgress` counts steps done of `MEMBERSHIP_PROVER_STEPS` (10: the witness and the nine steps snarkjs 0.7.5's prover logs), never elapsed time.
- `packages/crypto`: `MEMBERSHIP_WASM_SHA256` and `checkMembershipWasm` (`MembershipProverError` `wasm`), beside the proving key's check: the witness calculator receives the secret, so it is pinned like the key ([[membership]], Verification key; T-12, T-55).
- `artifacts/`: Semaphore 4.13.0's `semaphore-32.zkey` and `semaphore-32.wasm`, byte for byte, in a manifest of `packages/crypto/test-vectors/`' format; CI's `vectors-provenance` re-fetches both from `snark-artifacts.pse.dev` (passing locally).

Tested (`packages/membership-prover/tests/prover.test.ts`): every case of `membership-prover.json` (Semaphore's identities over Abolish tier-tree paths) proves into bytes that `verifyMembershipProof` accepts against the signals `membershipProverInput` computed and that `finishMembershipProof` finishes, with progress reported 1 to 10 once each and in order; a witness one sibling off proves a statement finishing refuses; a key or calculator with one bit flipped, a truncated calculator or the key passed as the calculator is refused (`zkey`, `wasm`) before any progress; the caller zeroing its buffers after the call doesn't change the proof (the copies are the bytes checked); paths of 31 and 33 siblings are refused. The manifest lists exactly the two files, by the sha256s `packages/crypto` pins. In `packages/crypto`, non-pinned calculators are refused as `wasm`. The positive path of `checkMembershipZkey` is now exercised through the adapter.

Known-weak:

- **Nothing here runs in the client yet**: the separate realm, fetching and caching the artifacts, the bundle check over snarkjs's browser builds, the proving screen and the timing padding are part 4b. In Node, `snarkjs` resolves to its source (`main.js`), not the `build/browser.esm.js` bundle the client will ship, so the bundle's behaviour is 4b's to test.
- **The progress steps are snarkjs's log strings.** A snarkjs that logs others fails the tests; there is no progress inside the witness calculation, the longest single step.
- **The secret is a decimal string and BigInts** inside snarkjs and its witness buffers, which can't be wiped.
- snarkjs's own Groth16 randomisers come from ffjavascript's ChaCha stream; the ballot worker's re-randomisation, not this package, makes the proof zero-knowledge.
- Still no real phone measurement (part 4b, in the real worker).
