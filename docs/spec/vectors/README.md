# Test vectors

Cross-language vectors for the encodings and computations in this spec. TypeScript (`packages/crypto`), Solidity (`packages/contracts`) and Noir (`packages/circuits`) tests consume them, and so can any third-party verifier (T-36, T-31). Published vectors from outside sources (RFCs, library authors) live in `packages/crypto/test-vectors/` with their source URL and sha256 instead; this folder holds vectors for what this spec defines.

## Format

```json
{
  "format": "abolish-vectors/1",
  "title": "Primitive types and record framing",
  "spec": "docs/spec/notation.md",
  "generator": "How the vectors were produced and checked",
  "vectors": [
    { "id": "u16-max", "type": { "kind": "u16" }, "value": "65535", "encoding": "ffff" },
    { "id": "u16-truncated", "type": { "kind": "u16" }, "encoding": "ff", "error": "truncated" }
  ]
}
```

Top-level fields:

- `format`: always `abolish-vectors/1` for this layout. A consumer rejects any other value.
- `title`, `spec`: what the file covers and the spec page that defines it.
- `generator`: how the vectors were produced, and how they were checked against the spec tables independently of the encoder that produced them ([[0001-canonical-encoding]], Consequences).
- `vectors`: the list of vectors.
- `types` (optional): named type descriptors, an object from name to descriptor, which `ref` descriptors point to.

Each vector:

- `id`: unique within the file, lowercase words joined by `-`. Never reused for a different vector.
- `description`: optional, what the vector exercises.
- `type`: the type to decode `encoding` as (below).
- `encoding`: the complete input, as lowercase hex with no prefix. It is the whole input: a decoder that leaves bytes unread fails with `trailing-bytes`.
- Exactly one of:
  - `value`: the vector is valid. Decoding `encoding` gives `value`, and encoding `value` gives `encoding` byte for byte.
  - `error`: the vector is invalid. Decoding `encoding` fails, with this decode error code ([[notation]], Strict decoding).

Values:

- Integers of every width are JSON strings in decimal (`"18446744073709551615"`), so no JSON parser rounds them.
- `bool` is a JSON boolean.
- `bytes[N]`, `bytes<M>`, `utf8<M>` and `field<…>` values are lowercase hex strings of the content bytes, without the length prefix.
- Lists are JSON arrays of element values.
- Records are JSON objects keyed by field name, without the header; the header comes from the `type`.

Type descriptors:

| `kind`                            | Other members                                                                                                                         |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `u8`, `u16`, `u32`, `u64`, `bool` | none                                                                                                                                  |
| `enum8`                           | `values`: the allowed values, as decimal strings                                                                                      |
| `bytes`                           | either `length` (`bytes[N]`) or `max` (`bytes<M>`), as a JSON number                                                                  |
| `utf8`                            | `max`, as a JSON number                                                                                                               |
| `field`                           | `field`: the field's name (`bn254`)                                                                                                   |
| `scalar`                          | none; the value is a decimal string                                                                                                   |
| `element`                         | `identity`: `"allowed"` or `"rejected"`, whether the field may hold the identity; the value is the element's 32-byte encoding, in hex |
| `p256-key`                        | none; the value is the key's 33-byte compressed encoding ([[trustee-identity]], Identity key), in hex                                 |
| `list`                            | `max`, as a JSON number, and `of`: the element's type descriptor                                                                      |
| `record`                          | `recordType` (4 lowercase hex digits), `version` (a JSON number) and `fields`: an array of `{ "name", "type" }` in encoding order     |
| `struct`                          | `fields`: as for `record`. A structure nested in a record, with no header; its value is a JSON object keyed by field name             |
| `ref`                             | `name`: a key of the file's `types`; the descriptor it names                                                                          |

## Record vectors

`election-definition.json` and `display-text.json` add members to their vectors:

- In `election-definition.json`, a `0x0001` record is decoded the two-step way of [[election-definition]] (Decoding), so its own profile's pin is checked and can fail with `profile-mismatch`. Each valid vector carries `hash`, the definition hash, and `stubHash`, the stub hash, both as lowercase hex.
- In `display-text.json`, each vector carries `pinned`, the version the election's profile pins, and is decoded against it ([[notation]]: the pin is checked before the version is looked up). Each valid vector carries `commitment`, the display-text commitment as lowercase hex, and `definition`, the definition fields it is checked against: `optionCount` (a decimal string) and `displayTextCommitment` (hex).
- `election-definition-v3.json` and `election-definition-v4.json` are read the same way as `election-definition.json`. `election-definition-v4.json` also has `judging`: one listed key's record and the election's opening, each with `id`, `note`, and `registeredAt`, `retiredAt`, `opensAt` and `provenAt` (the timestamp of the L1 block the record was read at), all decimal strings, and either `judgement` (`judges`, `unregistered`, `retired` or `unsettled`; [[election-definition]], Receipt keys) or `error`: `impossible-record`, a record the anchor can't hold at that block (written after it, or retired without a registration before the retirement).
- `election-definition-v5.json` is read the same way. Its profiles exercise well-formedness only, which doesn't judge combinations: none is checked against [[verifier]] 2.3, and its typical profile's opening pin would fail it. A vector whose `illFormed` is `option-count` or `selections` also has `illFormedQuestion`, the first failing question's index as a decimal string ([[election-definition]], Well-formedness).
- `election-definition-v6.json` is read the same way, its profiles likewise unchecked against [[verifier]] 2.3. Each valid vector also has `authorStubHash`, the author panel's stub hash ([[election-definition]], Stub hash and the ceremony), and one whose definition has an author panel has `authorPanelId`, both lowercase hex. The file adds `tags` (`authorPanel`, the identifier's tag), `minLiveBatch` (`MIN_LIVE_BATCH`, a decimal string) and `authorPanels`: each with `id`, `description`, `threshold` (a decimal string) and `keys` (hex `p256-key` encodings in seat order), optionally `defaultKeys` (the default seats' keys, for rule 4), and either `authorPanelId` or `error`, the first failing rule's code (`size`, `threshold`, `key`, `duplicate-key` or `default-seat`).
- A vector whose `error` is `unknown-version` holds a record labelled with a version its file's types don't lay out, and is read by a decoder of those types only: once a later version exists, a decoder that reads it may reject the same bytes otherwise. `election-definition-v5.json`'s `definition-v5-version-six` is such a vector; `election-definition-v6.json`'s `definition-v5-labelled-six` gives what a decoder of version 6 reports for version 5's bytes labelled 6.
- `display-text-v2.json` is read as `display-text.json`, with `pinned` 2 (or 1, for a version-2 record where version 1 is pinned), and each valid vector's `definition` gives `optionCounts`, the definition's `m_q` in question order (decimal strings), in place of `optionCount`. Its top-level `maxDisplayText` is `MAX_DISPLAY_TEXT`, as a decimal string: no vector is that long, so a consumer checks the cap on an input it builds.
- `illFormed` (valid vectors only): the bytes decode and round-trip, but the record breaks the well-formedness rule with this code, the first in the spec's order. A valid vector without it is well formed.

## Board vectors

`board.json` covers [[board]] with its own format, `abolish-board-vectors/1`, and the same top-level fields, plus:

- `maxBoardPayload`: `MAX_BOARD_PAYLOAD`, as a decimal string.
- `clock`: the anchoring clock the board vectors use (`epoch`, `period`, `deadline`, `lastSegment`, decimal strings; [[board]], Timing). Real elections take theirs from P4-1.
- `entries`: board-entry codec vectors. Each has `id`, `description` and `encoding` (hex), and either `value` (`election_id`, `index`, `segment`, `payload`; integers as decimal strings, bytes as hex) with `entryHash`, or `error` (a decode error code).
- `tree`: `leaves` (32-byte hex, used as `D[n]`), `roots` (the root of every prefix, size 1 first), `inclusion` (`index`, `size`, `path`) and `consistency` (`size1`, `size2`, `path`) for every pair, and `rejected`: proofs that must fail, with `kind` (`inclusion` or `consistency`) and the arguments of that check.
- `boards`: board checks. Each has `electionId`, `now` (the finalized L1 time of the check), `entries` (hex encodings in order, possibly with unauthenticated entries after the anchored extent), `checkpoints` (each anchor: `electionId`, `segment`, `size`, `head`, `root`, `objectCid` and `hashesCid` (36-byte binary CIDs, hex), its `hash`, and `anchoredAt`, the L1 time it was anchored), and `result`: `"ok"`, with `extent` (how many entries the anchors authenticate) and `links` (their chain links), or `{ "code", … }` with `entry`, `checkpoint`, `segment` or `decodeError` saying where it failed ([[board]], Board checks).

## Hash vectors

`hash.json` checks computations rather than codecs, so it has its own format, `abolish-hash-vectors/1`, with the same top-level fields. Each vector:

- `id`, `description` (optional): as above.
- `function`: `H`, `hash-to-scalar` (`HashToScalar(message, DST)`) or `hash-to-group` (`hash_to_ristretto255(message, DST)`), as [[group]] defines them.
- `dst`: the `DST` as an ASCII string, for `hash-to-scalar` and `hash-to-group`.
- `message`: the input, as lowercase hex.
- `uniformBytes`: the 64-byte `expand_message_xmd` output, as lowercase hex, for `hash-to-scalar` and `hash-to-group`.
- `output`: the result: the 32-byte digest for `H`, the `scalar` encoding for `hash-to-scalar`, the `element` encoding for `hash-to-group`.
- `notEqual` (only on `generator-h`): encodings the output must differ from (`identity`, `g`, `minusG`).

## Event-accumulator vectors

`event-accumulator.json` checks a computation, so it has its own format, `abolish-event-accumulator-vectors/1`, with the same top-level fields, plus `tag` (the registered tag, as an ASCII string) and:

- `genesis`: each has `id`, `description`, `chainId` (decimal string), `address` (20 bytes, hex) and `accumulator`, the genesis value ([[contracts]], Values).
- `sequences`: each has `id`, `description`, `chainId`, `address`, `genesis`, `events` (each `{ "topics": [32-byte hex, …], "data": hex }`, in emission order) and `accumulators`, the value after each event in turn.
- `rejected`: inputs with no accumulator value. `kind` is `genesis` (with `chainId` and `address`: a chain ID with no `u64` encoding) or `step` (with `topics` and `data`: a log with no topics, more than four, or a topic that isn't 32 bytes). A Solidity consumer can't represent a non-32-byte topic and skips it.

`event-accumulator-2.json`, format `abolish-event-accumulator-vectors/2`, is the layout in use ([[contracts]], Event accumulator, under `abolish/v1/event-accumulator-2`). It has the same fields, with these changes:

- each event in `sequences` also has `block` and `timestamp` (decimal strings), which its step binds;
- `proofs`: each has `id`, `description`, `chainId`, `address`, `events` (as in `sequences`, each also with `n`, its position as the archive numbers it), `proof` (`count`, `block`, decimal strings, and `accumulator`: the values a storage proof gave after that block) and `error`, `null` when the archive matches the proof or the first failing rule's code otherwise (`index`, `order`, `block-range` or `accumulator`; [[contracts]], Event accumulator, Verification). Solidity doesn't consume these: the check is the verifier's;
- `rejected` steps also have `block` and `timestamp`, and include a block number and a timestamp of 2⁶⁴, which have no `u64` encoding.

## Contract-event vectors

`contract-event.json` covers [[contracts]], Contract-event record, with its own format, `abolish-contract-event-vectors/1`, and the same top-level fields, plus `recordType` (`"0x0008"`), `version` (1), `maxEventData` and `maxEventTopics`, `chainId` (decimal string) and:

- `contracts`: the definition's L2 contract addresses the event check runs against, by role (`election-registry`, `trustee-registry`, `group-registry`, `board`; 20 bytes, hex).
- `events`: each role's table, in order: `role`, the ABI `signature`, the `indexed` parameters' names and `topic0`, the signature's keccak-256.
- `records`: honest records, each with `id`, `description`, `fields` (`contract`, `topics`, `data` as hex; `n`, `l2Block`, `l2Timestamp` as decimal strings), the record's `encoding`, its `role` and the decoded `event` (its name and fields: bytes as hex, `u64`s as decimal strings, `u8`s as numbers, and each embedded record or definition as its bytes).
- `eventFailures`: records that decode but fail the event check, with `fields`, `encoding` and `error`, the code.
- `decodeErrors`: inputs rejected by strict decoding with version 1 pinned, with `error` and `offset`.
- `sequences`: for each registry, the ids of its records in order of `n`, the accumulator after each in turn (under `chainId` and the role's address) and the final `count`.

`contract-event-v2.json` has the same fields under format `abolish-contract-event-vectors/2`, with `version` 2, the board's role in `events` and `sequences`, and `decodeErrors` with version 2 pinned. A board event's decoded `event` has `definitionHash`, `ballotHash` (both hex) and `record`, the record it carries.

`contract-event-v3.json` has the same fields under format `abolish-contract-event-vectors/3`, with `version` 3 and `decodeErrors` with version 3 pinned; `sequences` has the board's only. A `RelayedBallotSubmitted` event also has `index`, `l1Block`, `stamp` and `gasLimit` (decimal strings), and a `CloseStatementSubmitted` event has `definitionHash` (hex), `signer` (a number) and `record`.

## Election-registry vectors

`election-registry.json` checks a computation, so it has its own format, `abolish-election-registry-vectors/1`, with the same top-level fields, plus `tag` (the registered tag, as an ASCII string) and:

- `electionIds`: each has `id`, `description`, `chainId` and `counter` (decimal strings), `registry` (20 bytes, hex) and `electionId`, the identifier ([[contracts]], Election identifier).
- `rejected`: the same inputs with no `electionId`, where `chainId` or `counter` has no `u64` encoding. A Solidity consumer can't represent them and skips them.

## Group-registry vectors

`group-registry.json` covers [[contracts]], Group registry, with its own format, `abolish-group-registry-vectors/1`, and the same top-level fields, plus:

- `domain`: the EIP-712 domain (`name`, `version`, `chainId` as a JSON number, `verifyingContract` hex), its `typeHash` and `separator`. Every record below is signed under it.
- `types`: `AddMembers` and `RemoveMembers`, each with its `type` string and `typeHash`.
- `constants`: `maxBatch`, `maxRegistrars`, the field modulus `r` and `Poseidon2(0, 1)` (hex).
- `registrars`: the `threshold`, the test `secretKeys` (32 bytes big-endian, hex; never real keys), their `addresses` in ascending order, as the registry pins them, and an `outsiderSecretKey` no registrar holds.
- `commitments`: values (32 bytes, hex) at the forbidden boundaries, each with `forbidden`.
- `additions` and `removals`: valid records. Each has `id`, `description`, `groupId`, `tier`, `firstIndex` (additions) or `size` and `indices` (removals) as JSON numbers (some exceed 2⁵³, so a consumer reads them exactly, not as doubles), `commitments` (hex, additions), `structHash`, `digest`, `record` (hex) and `approvals`: each with `seat`, `r` and `s` (hex), `v` and `signer`, the address `ecrecover` returns. Signatures are RFC 6979 (HMAC-SHA-256) over the digest, low-s, so a deterministic signer reproduces them byte for byte.
- `rejected`: records breaking one stateless rule, each with `id`, `kind` (`add` or `remove`), `description`, `record` and `error`: `length`, `batch`, `forbidden-commitment`, `index-order` and `index-range` (removals: an index not above the one before, or not below `size`), `approvals` (fewer than the threshold), `seat` or `signature`, the last two with the failing `seat`. The rules that need the registry's state (the group, the position, an index already removed) are tested against the contract instead.
- `sequences`: histories of group 0 as a verifier replays them ([[contracts]], Group registry, Verification). Each has `id`, `description`, `groupId`, `records` (each with `kind`, `add` or `remove`, and `record`, hex, in log order) and either `count` (additions), `leaves` (hex, `0` for a removed member) and `groupSize`, or `error` (`group-history`) with `at`, the first failing record's position, and `reason`: a record error code above, `group` (a record of another group), `position` (a `first_index` other than the replayed count), `size` (a removal's `size` above it) or `removed` (an index already removed). `omitted-tail` and `omitted-removal` replay cleanly: they show the residual a replay can't catch. `two-faults` fixes the report order.

## Membership vectors

`membership.json` covers [[membership]] with its own format, `abolish-membership-vectors/1`, and the same top-level fields, plus:

- `fieldMap`: `F`. Each has `id`, `input` (32 bytes, hex), `keccak256` (the Keccak-256 digest of `input`, hex) and `output` (`F(input)`, decimal).
- `depth`: the protocol-wide tree depth, as a JSON number.
- `scopes`: the nullifier scope. Each has `id`, `definitionHash` and `root` (32 bytes each, hex; `root` is read big-endian), `tier` (a JSON number) and either `scope` (`S_g`, hex) and `scopeField` (`F(S_g)`, decimal), or `error`: `non-canonical` for a root that isn't a canonical `field<bn254>`, `zero-root` for a root of 0 ([[membership]], Statement), `unknown-tier` for a tier other than 0, 1 or 2.

`tier-tree.json` covers [[membership]], Tier tree, with format `abolish-tier-tree-vectors/1` and the same top-level fields, plus `depth`, and:

- `poseidon2`: circomlib's `Poseidon2`. Each has `id`, `inputs` (two decimal field elements) and `output` (decimal).
- `zeros`: `Z_0` to `Z_32`, decimal.
- `trees`: groups replayed under the lenient rules of Commitments and removals. Each has `id`, `note`, `events` (in order, each `{"add": c}` with `c` a decimal `uint256`, possibly forbidden, or `{"remove": i}` with `i` a decimal leaf index, possibly stray), the resulting `leaves` (decimal, `0` for a removed or forbidden addition), `groupSize`, `root` (decimal), `emptyRoot` (whether `root = Z_32`, which fails a definition listing the tier) and `paths`: up to three members' `index` and `siblings` (32 decimal values, bottom up).

`rolling-tier-tree.json` covers [[membership]], Rolling tier tree, Root clock and steps and Scope (rolling), with format `abolish-rolling-tier-tree-vectors/1` and the same top-level fields, plus `rootPeriod`, `rootOffset` and `rootWindow` (decimal seconds, [[parameters]]), and:

- `trees`: each has `id`, `note`, the listed `groups` (decimal), `events` in log order (each with `block`, `timestamp` and `group`, decimal, and either `add`, the commitments in record order, or `remove`, the member indices of its group; every event replays strictly, and events of unlisted groups are there to be skipped), `rootL2Block` (the opening block), `registeredAt` (the timestamp of the definition's `DefinitionRegistered` event), `closesAt`, `opening` (`leaves`, `root` and `memberCount` of the tree over the blocks up to `rootL2Block`) and `steps`, each with `step`, `tau` (`τ_n`), the step tree's `leaves`, `root` and `memberCount`, and `accepted` (a JSON boolean: whether a poll with these groups, opening and close accepts the step).
- `windows`: each has `id`, `note`, `step`, `l1Timestamp` (an L1 reference's timestamp) and `window`: `in` if `t − ROOT_WINDOW < τ_n ≤ t`, `future` if `τ_n > t`, `stale` otherwise.
- `scopes`: each has `id`, `definitionHash` (hex), `tier` (a JSON number), `scope` (`S_t` under `abolish/v1/rolling-nullifier-scope`, hex) and `scopeField` (`F(S_t)`, decimal).

`rolling-report.json` covers [[membership]], Reported counts, with format `abolish-rolling-report-vectors/1` and the same top-level fields, plus `rootPeriod` and `rootOffset` (decimal seconds), `clock` (the anchoring clock's `epoch` and `period`, decimal, [[board]], Timing), and:

- `cases`: each has `id`, `note`, `groups`, `events`, `rootL2Block`, `registeredAt` and `closesAt` as in `rolling-tier-tree.json`'s `trees`; `ballotSteps`, the steps named by the tier's ballot entries whose membership proofs verify, in board order and with repeats (every one a step the poll accepts); `report`, with `opening` (`members`), `eligible` (the eligible count), `close` (`null` when no boundary falls in the poll, else `step`, `members` and `accepted`, a JSON boolean: whether the poll accepts that step), `smallestStep` (`null` with no such ballot, else `step` and `members`) and `growth` (rows in period order, each `period`, `added`, `removed` and `members`); and `releases`, each a snapshot's `segment` and `snapshotSteps` (the steps its verifying ballots name) with `step` and `count` (`E(step)`), or `step` `null` and `count` the opening count when neither term exists. Every number is a decimal string.

`membership-proof.json` covers [[membership]], Verification key, Proof encoding and Verification, with format `abolish-membership-proof-vectors/1` and the same top-level fields, plus `source` (Semaphore's commit and the artifacts' URLs and sha256s), and:

- `verificationKey`: `depth`, `encoding` (the 768-byte `vk`, hex), `zkeySha256` and `hash` (`membership_vk_hash`, hex).
- `definitionHash` (hex) and `trees`: each tree's `id`, `tier`, `leaves` and `root` (decimal), which a verifier rebuilds.
- `fieldMapping`: `scopeBytes` (`S_g` over `definitionHash`, the `tier` and the `root`) with `scope` (`F(S_g)`), or `messageBytes` with `message` (`F(M)`), all from Semaphore's own `hash`.
- `proofs`: each has `name`, `note`, `proof` (256 bytes, hex), `signals` (`root`, `nullifier`, `message`, `scope`, decimal, as given to the verifier), `snarkjs` (snarkjs's verdict), `valid` (the spec's) and, when invalid, `reason`: `proof` (the pairing check fails), `signal` (a signal at or above `r`) or `root` (`ρ = 0`, which snarkjs accepts).
- `decode`: proof encodings every decoder rejects, each with `name`, `note` and `proof` (hex). The errors are `truncated` for `short`, `trailing-bytes` for `long`, and otherwise `non-canonical` at the broken point's offset (0, 64 or 192).

The proofs are randomised: regenerating gives other proof bytes for the same statements, so the committed file is the record.

## Vouch vectors

`vouch.json` covers [[vouching]] with format `abolish-vouch-vectors/1` and the same top-level fields, plus `source` (Semaphore's commit and the depth-32 artifacts' URLs and sha256s), `parameters` (`k` and `slots`, JSON numbers), `context` (`chainId`, decimal, and `registry`, 20 bytes, hex), and:

- `tier2`: the Tier 2 group the vouchers prove against: `groupId` and `rootBlock` (decimal), `leaves` and `root` (decimal), which a consumer rebuilds as a tier tree ([[membership]], Tier tree).
- `scopes`: each has `id`, `kind` (`vouchee` or `slot`), `chainId`, `registry`, either `groupId` and `commitment` (decimal) or `slot` (a JSON number), `scope` (`S_V` or `S_j`, hex) and `scopeField` (`F` of it, decimal, from Semaphore's own `hash`).
- `messages`: each has `id`, `role` (0 or 1), `chainId`, `registry`, `groupId`, `commitment`, `tier2GroupId`, `rootBlock` and `otherNullifier` (decimal), `message` (hex) and `messageField` (decimal).
- `additions`: Tier 1 addition records. Each has `id`, `description`, `context` (as above; some differ from the file's), `groupId` and `commitment` (decimal), `record` (hex) and `valid`; an invalid one has `error`, the first failing check of [[vouching]], Checks of one addition (`forbidden-commitment`, `slot`, `root`, `duplicate-voucher`, `duplicate-slot` or `proof`), `vouch` (the failing vouch's position, except for the first) and, for `proof`, `which` (`vouchee` or `slot`). Every addition also has `snarkjs`: whether every proof in it passes snarkjs's `groth16.verify` with the signals recomputed from the spec. Cases refused by a cheap check have `snarkjs: true`, so each shows its check is needed; `root-zero` carries forged proofs of root 0 that snarkjs accepts. `pooled-slot` is valid (one vouch's two proofs come from two members), and so is `mixed-root-blocks` (its vouches name different root blocks).
- `decode`: records every strict decoder refuses, each with `name`, `record` (hex), `error` (`length` or `non-canonical`) and, for `non-canonical`, `offset` in the record. `two-vouches`, `four-vouches` and `no-vouches` are consistently framed records with a count other than `k`.

The proofs are randomised: regenerating gives other proof bytes for the same statements, so the committed file is the record.

## Trustee vectors

`trustee.json` covers [[trustee-identity]] with its own format, `abolish-trustee-vectors/1`, and the same top-level fields, plus `tags` (the panel and registration tags, ASCII) and:

- `keys`: `p256-key` encodings. Each has `id`, `encoding` (hex), an optional `description`, and `secretKey` (the test secret scalar, 32 bytes big-endian; never a real key), or nothing more for a valid key with no known secret (the two points with `x = 0`, which some decoders wrongly reject), or `error`, a decode error code ([[notation]], Strict decoding): `non-canonical`, `truncated` or `trailing-bytes`.
- `signatures`: each has `id`, `key` and `message` (`m`, hex), `dsMessage` (`DS(tag, m)` under the registration tag, hex), `signature` (hex) and `valid`. Valid ones also give `digest` (`H(DS(tag, m))`). All but one are RFC 6979 signatures after the low-s rule, so a deterministic signer reproduces them byte for byte; they include a digest at or above `n` (`sig-digest-at-least-n`). The exception, `sig-x-of-r-at-least-n`, has `x(R) ≥ n` and a key constructed for it with no known secret; it must verify. Invalid ones have a `description`; they cover high `s`, `r` and `s` out of range, a flipped bit, another message, key or tag, wrong lengths, DER, and the signing key's own uncompressed and hybrid SEC 1 forms (valid signatures, rejected only for the key's encoding).
- Two vectors published in the first version are kept unchanged although their names mislead: `key-x-above-p` encodes `x = p` with prefix `0x03` (the same bytes as `key-x-equals-p-prefix-03`; `key-x-p-plus-on-curve-x` is the real aliasing case), and `sig-key-uncompressed` pairs G's uncompressed form with key-1's signature, so it is invalid for two reasons and is superseded by `sig-key-uncompressed-own` and `sig-key-hybrid`, which only the encoding rule rejects.
- `panels`: each has `id`, `threshold`, `keys` (hex, seat 1 first) and either `panelId` (hex) or `error`: `threshold` (`k` outside `2 ≤ k ≤ n`), `size` (`n` over `MAX_TRUSTEES`), `duplicate-key` or `key` (a key that isn't a `p256-key`).
- `registrations`: ceremony registrations signed by a seat of the panel named in `panel`. Each has `id`, `l2ChainId` (decimal), `trusteeRegistry`, `index`, `stubHash`, `ceremonyTranscriptHash`, `message` (the 125-byte `m`) and `signature`, by the key in seat `index`. These are statements of the first layout, under `abolish/v1/sig/ceremony-registration`, which was retired before any trustee registry was deployed: they are frozen and read by nothing. `key-set.json` has the current statements.

## Key-set vectors

`key-set.json` covers [[ceremony]] (Key set hash) and [[trustee-identity]]'s current ceremony registration with its own format, `abolish-key-set-vectors/1`, and the same top-level fields, plus `tags` (`kemKey`, `keySet` and `registration`, ASCII) and:

- `kemKeys`: `kem-key-1` to `kem-key-16`, `share-encryption.json`'s `panel-16` keys. Each has `id`, `kemKey` (the 1,216-byte `kem_key` encoding, hex) and `kemKeyHash`. Seat `i` of every key set below has `kem-key-i`.
- `keySets`: each has `id`, `description`, `entries` (each with `index`, `kemKeyHash`, `signingKey`, the `p256-key` hex, and its point's `x` and `y`, 32 bytes big-endian, hex), `encoding` (the `list<key_set_entry, MAX_TRUSTEES>` that is hashed, hex) and `keySetHash`.
- `rejectedKeySets`: lists of entries no seat should sign, each with `id`, `description`, `entries` (as above, without the point) and `error`: `empty`, `seat-order` (seats not strictly increasing from 1 to `MAX_TRUSTEES`) or `non-canonical` (a signing key that isn't a `p256-key`).
- `statements`: ceremony registrations by a seat of `trustee.json`'s panel named in `panel`. Each has `id`, `l2ChainId` (decimal), `trusteeRegistry`, `index`, `stubHash`, `ceremonyTranscriptHash`, `keySet` (the `id` of the key set signed), `keySetHash`, `message` (the 157-byte `m`), `digest` (`H(DS(tag, m))`) and `signature`, an RFC 6979 signature after the low-s rule by the key in seat `index`, which a deterministic signer reproduces.

## Ballot-validity vectors

`ballot-validity.json` covers [[ballot-validity]] with its own format, `abolish-ballot-validity-vectors/1`, and the same top-level fields, plus `tags` (the statement, option and sum tags, ASCII), `generatorH` (`h`'s encoding, hex) and:

- `ballots`: each has `id`, `description`, `context` (`definitionHash` hex; `optionCount`, `minSelections`, `maxSelections`, `threshold`, `panelSize` and `tier` as JSON numbers; `nullifier` decimal), `encoding` (the committed vote, hex) and `result`: `"ok"`, or `{ "code" }` with the first failing check's code, plus `option` for `option-proof`. Valid ballots also carry what made them, so an implementation reproduces `encoding` byte for byte: `votes`; `randomness`, with `polynomials` (per option, `f` and `g`: the `k` coefficients of `f_j` and `g_j`, constant term first, decimal) and the proof randomness `options` (per option) and `sum`, each `{ "w", "simulated": [{ "c", "z" }] }` (decimal; the simulated branches in branch order, skipping the real one); `shareHashes` (hex, seat order); `statementHash` (hex); and `shares` (each trustee's `list<share>` encoding, hex, seat 1 first).
- `shareChecks`: each has `id`, `ballot` (the `id` of the ballot whose `vss` it is checked against), `index` (the trustee's seat), `shares` (hex) and `valid`.
- `decode`: rejected encodings. Each has `id`, `description`, `type` (`committed-vote` or `shares`), `encoding` (hex) and `error`, a decode error code.

## Share-encryption vectors

`share-encryption.json` covers [[share-encryption]] with its own format, `abolish-share-encryption-vectors/1`, and the same top-level fields, plus `tags` (the combiner, associated-data, ciphertext, ephemeral-proof and complaint tags, ASCII) and:

- `panels`: trustee KEM keys by panel name (`panel-3`, `panel-2`, `panel-16`), seat 1 first. Each has `seed` (`d ‖ z`, hex), `x` (decimal) and `publicKey` (the `kem_key` encoding, hex).
- `ballots`: each has `id`, `description`, `context` (as in the ballot-validity vectors), `panel`, `votes`, `randomness` (the sharing polynomials and proof randomness, as in the ballot-validity vectors), `encapsulation` (per seat, `m` hex, and `e` and the proof nonce `w` decimal), `ciphertexts` (hex, seat order), `intermediate` (per seat: `kemSharedSecret`, `dhSharedSecret`, `aeadKey` and `associatedDataHash`, the SHA-256 of `aad`, hex), `shareHashes`, `committedVote` (hex; it passes the validity check) and `decryptions` (per seat, `result`: `"ok"` with `shares` hex, or a decryption code). Four ballots are dishonest: their `intermediate` values are those of the ciphertext actually sent (`aeadKey` is `null` for `copied-ephemeral`'s seat 1, whose seal is garbage).
- `decryptFailures`: decryptions under the wrong context or of altered ciphertexts, all with the `panel-3` keys. Each has `id`, `description`, `definitionHash`, `seat` (in the associated data), `keySeat` (whose secret key decrypts), `vss` (hex), `ciphertext` and `result`.
- `postings`: each has `id`, `description`, `ballot`, `seat`, `ciphertext`, `m` and `result`: `"ok"` or a posting code.
- `complaints`: each has `id`, `description`, `ballot`, `seat`, `ciphertext`, `m` (the posting complained about), `proof` (the `complaint_proof` encoding, hex), `w` (decimal, where the proof is honest and reproducible) and `result`: `"ok"` for a proven complaint, or a posting or complaint code.
- `decode`: each has `id`, `description`, `type` (`kem-key`, `kem-secret`, `share-ciphertext` or `complaint-proof`), `encoding` (hex) and `error`: a decode error code, or `null` for an encoding that must decode and re-encode to itself.

`share-encryption-v4.json` covers [[share-encryption]] (Ballot version 4) in `share-encryption.json`'s format, `abolish-share-encryption-v4-vectors/1`, with `recordType` and `version` (4), the same `tags` (`complaint` is `abolish/v1/fs/share-complaint-2`), and:

- `elections`: definition-version-6 elections, as in `ballot-v4.json`.
- `keySets`: trustee KEM keys by name (`default-3`, `author-3`, `author-2`, `default-2`, `default-16`, `author-16`), seat 1 first, each as in `share-encryption.json`'s `panels`.
- `ballots`: each has `id`, `description`, `election`, `definitionHash`, `cell`, `nullifier` (decimal), `keys` and `authorKeys` (the key sets of the default and author panels, `authorKeys` `null` without an author panel), `votes`, `randomness` (as in `ballot-v4.json`), `committedVote` (the version-4 committed vote, hex; it passes version 4's validity check with these share hashes) and `seats`: every seat of the default panel, then of the author panel, each with `panel` (1 default, 2 author), `seat`, `shares` (its `list<share>`, hex), `encapsulation` (`m` hex, `e` and `w` decimal), `intermediate` (as in `share-encryption.json`), `ciphertext`, `shareHash` (its hash, in its own panel's list of the committed vote) and `decryption` (`"ok"` or a decryption code, by the seat's own key). Six ballots are dishonest: their `intermediate` values are those of the ciphertext actually sent.
- `decryptFailures`: each has `id`, `description`, `ballotVersion` (4, or 1 for a version-4 ciphertext decrypted under version 1's rules), `definitionHash`, `panel` and `seat` (in the associated data), `keyPanel` and `keySeat` (whose secret key, of the `author` ballot's key sets, decrypts), `vss` and `authorVss` (hex; version 1's rules read only `vss`), `ciphertext` and `result`.
- `postings`: each has `id`, `description`, `ballot`, `panel`, `seat`, `keyPanel` and `keySeat` (whose public key the check uses), `ciphertext`, `m` and `result`.
- `complaints`: each has `id`, `description`, `ballot`, `panel`, `seat`, `keyPanel` (the panel of the seat key the check uses), `ciphertext`, `m`, `proof`, `w` (where the proof is honest and reproducible) and `result`, as in `share-encryption.json`.

## Share-receipt vectors

`share-receipt.json` covers [[ballot-validity]] (Ballot hash) and [[share-encryption]] (Intake and receipts) with its own format, `abolish-share-receipt-vectors/1`, and the same top-level fields, plus `tags` (the ballot-hash and share-receipt tags, ASCII) and:

- `panels`: by the names of `share-encryption.json`'s panels, each seat's `seat`, `signingSecret` (32 bytes big-endian, hex; test data), `signingKey` (its registered per-election key) and `identityKey` (a key that is never a receipt signer), as `p256-key` encodings, hex.
- `ballotHashes`: each has `source` (`ballot-validity.json` or `share-encryption.json`), `ballot` (the `id` of a valid ballot in that file, whose `context` and committed vote it hashes) and `ballotHash` (hex).
- `intakes`: the share checks of intake (`validity-shape`, `share-hash`, the validity proofs, decryption: the steps after a record's membership proof passes, without it; `intake.json` has whole records) for every seat and every `share-encryption.json` ballot, with that file's KEM keys and this file's signing secrets. Each has `ballot`, `seat` and `result`: `"ok"`, with `ballotHash`, `shareHash`, `statement` (the signed `m`, hex) and `receipt` (the signature, RFC 6979 after the low-s rule, hex), or an intake code.
- `intakeFailures`: intakes by `panel-3`'s seats that fail. Each has `id`, `description`, `context` (as in the ballot-validity vectors), `seat`, `committedVote` (hex), `ciphertext` (hex), `result` (the first failing code) and, for `option-proof`, `option`.
- `receiptChecks`: each has `id`, `description`, `panel` (whose signing keys are registered), `definitionHash`, `ballotHash`, `seat`, `shareHash` (the statement the checker builds, hex), `signature` (hex) and `valid`.

## Intake vectors

`intake.json` covers [[share-encryption]] (Intake and receipts) on whole ballot records with its own format, `abolish-intake-vectors/1`, and the same top-level fields, plus `tags` (the share-receipt tag, ASCII) and:

- `elections`: by name, each has `version` (the ballot version its definition pins: `plurality` is `ballot.json`'s election, version 1; `regional` is `ballot-v2.json`'s, version 2), `definition` (the encoding, hex) and `definitionHash` (hex).
- `panel`: seats 1 to 3, each with `seat`, `kem` (`seed`, `x` and `publicKey`, as in `share-encryption.json`'s panels), `signingSecret` (32 bytes big-endian, hex; test data) and `signingKey` (its registered per-election key, a `p256-key`, hex).
- `cases`: each has `id`, `description`, `election`, `registered` (the qualified seats; their keys are the panel's), `seat` (the trustee taking the delivery), `record` (the delivered ballot record, hex), `ciphertext` (hex), `snarkjs` (where the membership step's signals were checked: snarkjs's verdict on them) and `result`: `"ok"`, with `ballotHash`, `shareHash`, `statement` (the signed `m`, hex), `receipt` (RFC 6979 after the low-s rule, hex), and what the re-vote rule ranks the ballot by (`tier`, the cell's tier under version 2; `nullifier`, decimal; `message`, `M`, hex; `l1RefNumber`, decimal; `l1RefHash`, hex), or the first failing code (`delivery-malformed`, an admission code, `share-hash` or a decryption code) and, for `option-proof`, `option`. The `delivery-malformed` cases are labelled by hand from the strict-decoding rules.

`intake-v3.json` covers the same on version-3 records in the same format: its one election, `questions`, is `ballot-v3-records.json`'s (`version` 3), `option` is the flat option, and a `sum-proof` result has `question`, the first failing question. The tier of an admitted ballot is its cell's.

`intake-v4.json` covers [[share-encryption]] (Ballot version 4) on version-4 records in its own format, `abolish-intake-vectors/2`, with `tags` (`receipt` is `abolish/v1/sig/share-receipt-2`), `panels` (`default` 1, `author` 2) and:

- `elections`: `panels` (a 2-of-3 author panel) and `default-only` (none), `ballot-v4-records.json`'s, each with `version` (6), `definition` and `definitionHash`.
- `seats`: `default` and `author`, seats 1 to 3 of each panel, each as in `intake.json`'s `panel`, plus `identityKey` (a key that is never a receipt signer). The author seats' KEM keys are test keys: an author panel's come from its own ceremony (P2-16 part 3).
- `cases`: as in `intake.json`, with `registered` and `authorRegistered` (each panel's qualified seats), `panel` and `seat` (the seat taking the delivery), and the `statement` of version 4's receipt; an admitted ballot also has `cell`. A `share-hash-unqualified` result has `unqualifiedPanel` and `unqualifiedSeat`, the first such seat.
- `checks`: each has `id`, `description`, `definitionHash`, `ballotHash`, `panel`, `seat`, `shareHash` (with the others, the statement the checker builds; hex), `authorRegistered` (the author seats whose signing keys are registered; every default seat's is), `signature` (hex) and `valid`.

## Challenge vectors

`challenge.json` covers [[challenge]] and [[ballot-validity]] (Core hash) with its own format, `abolish-challenge-vectors/1`, and the same top-level fields, plus `recordType` (`0x0003`), `version` (1), `tag` (the core-hash tag, ASCII) and:

- `panels`: KEM keys by panel name (`panel-3`, `panel-2` and `panel-16` are `share-encryption.json`'s), each seat's `seat`, `seed`, `x` (test data) and `publicKey` (its `kem_key` encoding, hex).
- `elections`: by name, each `definition` (an election definition, hex), `definitionHash`, `panel` and `registered` (the seats of the registered key set; the other seats are outside it).
- `openings`: each has `id`, `description`, `election` (the one it is checked against), `encoding` (hex), `coreHash` (hex) and `result`: `"ok"`, with `votes` (each `v_j`, decimal) and `withinRules` (`false` is `opening-vote-outside`), or the first failing check, with `option` for `opening-vss` and `seat` for `opening-ciphertext`. An opening an honest client made also has `randomness`: `polynomials` (each option's `f` and `g`, decimal) and `encapsulation` (every seat's `m` (hex), `e` and `w` (decimal), registered or not, as the client's encryption draws them), from which `openChallenge` re-makes `encoding`.
- `decode`: rejected encodings, as in the ballot vectors.
- `openedCommitments`: each has `id`, `description`, `opening` (the `id` of an opening in this file), `core` (`definitionHash`, `tier`, `vss` as its encoding and `shareHashes`, hex), its `coreHash`, and `opened`: whether the opening opens a commitment of that core ([[challenge]], Opened commitments).
- `castBallots`: `ballot` (the `id` of an admitted ballot in `ballot.json`) and its `coreHash`.

## Ballot vectors

`ballot.json` covers [[ballot-validity]] (Ballot record) with its own format, `abolish-ballot-vectors/1`, and the same top-level fields, plus `recordType` (`0x0002`) and `version` (1), and:

- `groups`: the tier groups the elections list, plus `outsiders` (a tree no election lists). Each has `id`, `tier`, `secrets` (each member's identity secret `s`, decimal; test data), `leaves` (their identity commitments `Poseidon2(s · B8)`, decimal) and `root` (the depth-32 tier tree's root, decimal).
- `elections`: by name (`plurality`: 3 options, `k = 2`, `n = 3`, tiers 0 and 2; `approval`: 4 options, 1 to 2 selections, `k = 3`, `n = 4`, tier 1). Each has `definition` (the election definition's encoding, hex), `definitionHash` (hex) and `tiers` (each listed tier's `tier`, `group`, `root` and `scope`, `F(S_g)`, decimal).
- `ballots`: each has `id`, `description`, `election` (the one it is checked against), `registered` (the seats of the registered key set), `encoding` (the record, hex; it decodes and re-encodes to itself), `ballotHash` (hex, over the record's own fields) and `result`: `ok` or the first failing admission code, with `option` for `option-proof`. Where the admission check reaches the membership step's inputs (the definition hash and tier match), it also has `message` (`M`, hex), `signals` (`root`, `nullifier`, `message` and `scope`, decimal: the public signals the check derives from the record and the definition) and `snarkjs` (snarkjs 0.7.5's `groth16.verify` on the record's proof with those signals).
- `decode`: each has `id`, `description`, `encoding` (hex), `error` (the decode error code) and, where fixed, `offset`; the pinned version is 1, and the only known record type is `0x0002`.

The proofs are randomised: regenerating gives other proof bytes for the same statements, so the committed file is the record.

`ballot-v2.json` covers [[ballot-validity]] (Ballot record (version 2)) in the same format, `abolish-ballot-vectors/1`, with `version` 2, and:

- `groups`: each group of the election's electorate (`groupId`, `tier`, `region`), its `leafCount`, the indices first occurrence set to 0 (`zeroedByFirstOccurrence`) and its `voters` (`index` in the group, a `label` and the identity secret, decimal; test data). The other leaves are filler commitments derived from fixed labels by `ballot-v2-vectors.py`; the cell roots, which the definition states, cover them.
- `elections`: by name (`regional`: plurality over 3 options, `k = 2`, `n = 3`; `other`: the same electorate under another `election_id`). Each has `definition` (a version-3 definition's encoding, hex), `definitionHash` and `cells` (each cell's `cell`, `tier`, `regions`, `groups`, `root`, `members` and `scope`, decimal).
- `ballots`: as in `ballot.json`, plus `statementHash` (hex) and, for an admitted ballot, `tier`, its cell's tier. `message` and `signals` are present where the definition hash and cell match.
- `decode`: as in `ballot.json`, with the pinned version 2.

## Ballot version 3 vectors

`ballot-v3.json` covers [[ballot-validity]] (Ballot record (version 3)) with its own format, `abolish-ballot-v3-vectors/1`, and the same top-level fields, plus `recordType` (`0x0002`), `version` (3), `tags` (the statement, ballot, core, option and question-sum tags, ASCII) and:

- `elections`: by name, each a version-5 definition: `definition` (hex), `definitionHash` (hex), `definitionVersion` (5), `ballotVersion` (3), `questions` (each `optionCount`, `minSelections`, `maxSelections` and `offset`, its first flat index `o_q`), `optionTotal` (`T`), `threshold`, `panelSize` and `cells` (the partition's number of cells).
- `ballots`: each has `id`, `description`, `election`, `context` (`definitionHash`, hex, the election's except in a copy to another election; `cell`; and `nullifier`, decimal), `encoding` (the committed vote, hex) and `result`: `"ok"`, or the first failing check's `code` with `option` (the flat index) for `option-proof` and `question` for `sum-proof`. A valid ballot also has `votes` (flat, in order), `randomness` (`polynomials`: each flat option's `f` and `g`; `options`: each option proof's `w` and the simulated branch's `c` and `z`; `questions`: each range proof's `w` and its simulated branches' `c` and `z`, in value order without the real one; all decimal), `shareHashes` (random test bytes, hex), `statementHash`, `ballotHash` (over the record's fields with these values, as Hashes (version 3) states), `coreHash` and, except `same-shape`, `shares` (each seat's `list<share>` encoding, hex, seat 1 first). An implementation re-makes `encoding` from `votes` and `randomness`.
- `decode`: each has `id`, `description`, `encoding` (a committed vote, hex), `error` and `offset`.

`ballot-v3-records.json` covers [[ballot-validity]] (Decoding and Admission (version 3)) on whole records, in `ballot-v2.json`'s format, `abolish-ballot-vectors/1`, with `version` 3, over `ballot-v2.json`'s electorate and cells, and:

- `elections`: by name (`questions`: pick one of 3, pick up to 2 of 4, pick exactly 1 of 2, `k = 2`, `n = 3`; `other`: the same under another `election_id`). Each has `definition` (a version-5 definition's encoding, hex), `definitionHash`, `questions` (as in `ballot-v3.json`) and `cells` (each cell's `cell`, `tier`, `root` and `scope`, decimal).
- `ballots`: as in `ballot-v2.json`, except that `option` is the flat option for `option-proof` and `question` the first failing question for `sum-proof`.
- `decode`: as in `ballot-v2.json`, with the pinned version 3.

`spoiled-opening-v2.json` covers [[challenge]] (Opening version 2) with its own format, `abolish-spoiled-opening-v2-vectors/1`, the challenge vectors' top-level fields, `recordType` (`0x0003`), `version` (2) and `tag`, and:

- `panels`: as in `challenge.json`, under this file's own names.
- `elections`: by name, as in `ballot-v3.json`, plus `panel` and `registered`; `opening-four` is a version-5 definition (ballot version 3) and `opening-regional` a version-4 one (ballot version 2, its one question at `offset` 0); both name the published membership key (`membership-proof.json`), so an implementation makes its ballot context from them as it would for a registered election.
- `openings`: as in `challenge.json`, except that a passing opening has `voteOutside` (`question`, the first question outside the rules) when `opening-vote-outside` applies, and no `withinRules`; `coreHash` is under the election's `ballotVersion`.
- `decode`: as in `challenge.json`, under a profile pinning version 2. `decodedCells`: encodings that must decode, each with the `cell` it names.
- `coreHashVersions`: for two openings, `coreHashVersion2` and `coreHashVersion3`, the same core's hash under each ballot version.

`spoiled-opening-v3.json` covers [[challenge]] (Opening version 3) with its own format, `abolish-spoiled-opening-v3-vectors/1`, the top-level fields of `spoiled-opening-v2.json` (`version` 3), and:

- `panels`: `default` (1) and `author` (2), and `keys`, KEM key sets by name as in `spoiled-opening-v2.json`'s `panels`. The author panels' keys are test keys: the author panel's ceremony is [[P2-16]] part 3's.
- `elections`: by name, as in `ballot-v4.json`, each naming the published membership key, plus `panel` and `authorPanel` (key-set names; `authorPanel` `null` without an author panel), `registered` and `authorRegistered` (each panel's qualified seats).
- `openings`: as in `spoiled-opening-v2.json`, with `coreHash` ballot version 4's. A passing opening also has `voteRandomness` (each flat option's `r_j`, decimal), and a failing one `panel` beside `option` (`opening-vss`) or `seat` (`opening-ciphertext`). `randomness` has `polynomials` and `authorPolynomials` (as in `ballot-v4.json`) and `encapsulation` and `authorEncapsulation` (every seat's `m`, `e` and `w` in each panel, an unregistered seat's included, seat 1 first).
- `decode` and `decodedCells`: as in `spoiled-opening-v2.json`, under a profile pinning version 3.
- `opened`: each has `id`, `description`, `opening` (an opening's `id`), a version-4 ballot's `definitionHash`, `vss` and `authorVss` (elements, hex; only each row's first element, the constant term, is read) and `opens`: whether the opening opens one of its commitments.

`tally-questions.json` covers [[tally]] (Opening checks) under definition version 5, with its own format, `abolish-tally-questions-vectors/1`, the same top-level fields, `election` (as in `ballot-v3.json`) and `cells`: each has `id`, `description`, `ballots` (each counted ballot's `vss`, encoded as the committed vote encodes it, hex), `aggregate` (each flat option's `Ĉ_{c,j}`, identity allowed, hex), `opening` (each option's `v` and `r`, decimal; `S_c` is `ballots`) and `result`: `"ok"`, or the first failing code with `option` (`tally-opening`, `tally-range`) or `question` (`tally-question-range`).

## Ballot version 4 vectors

`ballot-v4.json` covers [[ballot-validity]] (Ballot record (version 4)) in `ballot-v3.json`'s layout, with its own format, `abolish-ballot-v4-vectors/1`, `version` 4, and:

- `elections`: as in `ballot-v3.json`, each a version-6 definition (`definitionVersion` 6, `ballotVersion` 4), plus `authorThreshold` and `authorPanelSize` (`k_A` and `n_A`, both 0 without an author panel).
- `ballots`: as in `ballot-v3.json`. A valid ballot's `randomness` has `polynomials` (each flat option's default-half `f^D` and `g^D`, `f^D`'s constant term `v_j − a_j` and `g^D`'s `r_j − s_j`) and `authorPolynomials` (each option's `f^A` and `g^A`, constant terms `a_j` and `s_j`; empty without an author panel), and the ballot has `authorShareHashes` and `authorShares` (each author seat's `list<share>`, hex, seat 1 first) beside `shareHashes` and `shares`. `C_j` is never listed: an implementation computes it from `encoding`.
- `decode`: as in `ballot-v3.json`.
- `crossPanelShares`: each has `id`, `ballot` (a valid ballot's `id`), `commitments` (`default` or `author`: the half whose VSS commitments the shares are checked against), `seat`, `shares` (the other panel's seat's `list<share>`, hex) and `result` (always `false`).

`ballot-v4-records.json` covers [[ballot-validity]] (Decoding and Admission (version 4)) on whole records, in `ballot-v3-records.json`'s format with `version` 4, and:

- `panels`: the panel byte's values, `default` 1 and `author` 2 ([[ballot-validity]], Context (version 4)).
- `elections`: as in `ballot-v3-records.json` (`panels`, `default-only` and `other`, each a version-6 definition), plus `threshold`, `panelSize`, `authorThreshold` and `authorPanelSize` (both 0 without an author panel).
- `ballots`: as in `ballot-v3-records.json`, with `authorRegistered` (the author panel's registered seats) beside `registered`, and the outcome under `admission`: `code`, then `option` or `question` as in `ballot-v3-records.json`, `panel` and `seat` for `share-hash-unqualified`, and for an admitted ballot its `ballotHash`, `message` (`M`, hex), `tier` and `cell`. The top-level `ballotHash` is the record's whatever its outcome.
- `intakes`: intake's admission steps ([[share-encryption]], Intake and receipts; Ballot version 4) on a delivered `record` (hex) at `seat` of `panel` with the delivered ciphertext's hash `shareHash` (a label here), under `registered` and `authorRegistered`, with `snarkjs` where the membership proof is reached and the outcome under `admission` as for `ballots`; `delivery-malformed` for a record the pinned version can't decode.
- `decode`: as in `ballot-v3-records.json`, with the pinned version 4.

`ballot-v5-records.json` covers [[ballot-validity]] (Decoding and Admission (version 5)) and the window of [[revoting]] (Admission, step 5) on whole records, in `ballot-v4-records.json`'s format with `version` 5, without `intakes`, and:

- `rootPeriod`, `rootOffset` and `rootWindow`: the root clock's constants ([[parameters]]), decimal strings.
- `events`: the group registry's events in log order, as in `rolling-tier-tree.json`'s `trees`.
- `elections`: `rolling` (a 2-of-3 author panel), `default-only` (none) and `other` (`rolling` under another `election_id`), each a rolling version-7 definition, with `ballot-v4-records.json`'s fields and `rootL2Block`, `registeredAt` (the L2 timestamp of its `DefinitionRegistered` event) and `closesAt`, decimal strings; `cells`, one per rolling tier in order, each with `cell`, `tier`, `groups` (decimal strings), `openingRoot` and `openingCount` (the tier's rolling tree at `rootL2Block`), `scope` (the rolling scope's field element) and `steps`, each with `step`, `tau`, `root`, `memberCount` and `accepted`.
- `ballots`: as in `ballot-v4-records.json`, with `coreHash`; `signals` are present wherever the verifier has a step root to check against (the ballot's election and cell, and a step the poll accepts), whatever the outcome; an admitted ballot's `admission` adds its `step`.
- `references`: the window on admitted ballots, each with `id`, `ballot` (a ballot's `id`), its `step`, `l1Timestamp` (the named block's timestamp, decimal string) and `expect` (`ok`, `root-step-stale` or `root-step-future`).
- `decode`: as in `ballot-v4-records.json`, with the pinned version 5.

## Delivery vectors

`delivery.json` covers [[delivery]] with its own format, `abolish-delivery-vectors/1`, and the same top-level fields, plus `tags` (the share-receipt and share-complaint signature tags, ASCII), `windows` (`delivery` and `complaint`, `DELIVERY_WINDOW` and `COMPLAINT_WINDOW` in seconds, decimal), `definitionHash` (every election's, hex) and:

- `panel`: a 2-of-3 panel; each seat has `seat`, `kemKey` (its registered `kem_key` encoding, hex; from `share-encryption.json`'s `panel-3` seeds), `signingSecret` (32 bytes big-endian, hex; test data), `signingKey` (its registered per-election key) and `identityKey` (a key that never signs a receipt or complaint), as `p256-key` encodings, hex.
- `records`: valid records, each with `id`, `description`, `type` (`share-receipt`, `share-posting` or `share-complaint`), `encoding` (the full record, hex), `seat` and, for a receipt or complaint, `statement` (the signed `m`, hex); a complaint also has `w` (its proof nonce, decimal). The complaint's signature is RFC 6979 after the low-`s` rule, so it is re-made byte for byte from the seat's `signingSecret`. Each must decode and re-encode to itself.
- `decode`: each has `id`, `description`, `type` (the record it is decoded as), `encoding` (hex) and `error`, the decode error code.
- `boardEntries`: each has `id`, `description`, `version` (1 or 3, the pinned board-entry version), `encoding` (the entry, hex) and `error`: the decode error code, or `null` for an entry that must decode and re-encode to itself.
- `segments`: each has `id`, `epoch`, `period`, `closesAt`, `l1InclusionBound`, the resulting `delivery` (`s_D`) and `complaint` (`s_K`), and `deliveryDeadline` (`t_D`) and `complaintDeadline` (`t_K`), all decimal.

## Receipt-key record vectors

`receipt-key-record.json` checks reading the board anchor's receipt-key record from L1 state for [[verifier]] 2.9, with its own format, `abolish-receipt-key-record-vectors/1`, the same top-level fields, plus `clock` and `electionId` (as in `l1-anchor.json`) and `opensAt` (decimal), the election's `opens_at`. ## Rules

- The record types a file's decoder knows are exactly those that appear as a `recordType` in that file, and the versions it knows of each type exactly those that appear with it; any other type is unknown ([[notation]], Strict decoding).
- A vector, once its layout is frozen ([[versioning]]), is never edited or removed. New vectors are added. `packages/crypto/tests/vectors/trustee-published.json` pins every published `trustee.json` vector by the sha256 of its JSON; a PR that adds vectors there adds their digests in the same PR.
- Every rejection rule in a spec section has at least one invalid vector, and every field type at least one valid vector at each boundary (zero, maximum, maximum plus one where representable). Rejections that need an election's context (`profile-mismatch`) are covered by the record vectors above.
- Generated vectors are checked by hand, or by a second implementation written independently from the spec, before they are committed. The `generator` field says which.
