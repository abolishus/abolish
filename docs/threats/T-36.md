# T-36: Verifier monoculture

- Area: Integrity and verifiability (G-7, G-8, G-9)
- Adversary: A-2
- Status: **Planned.** Residual: until a third party writes one, there is one verifier.

## Threat

Our verifier and our server share a bug, so the "independent" check passes a wrong result.

## Mitigation

The verifier's trust base is the `crypto-review`-gated packages and never imports `core` or `sdk` (AGENTS.md). The public spec plus cross-language vectors invite third-party verifiers (P1-8, P1-19). Verifier tests run on reference-election fixtures, not on output of the code under test.

## History

- 2026-10-11 (P1-13): every verifier reaches the same L1-reference verdict for any head past close, and needs L1 only from an hour before opening to the first block after close ([[revoting]], Admission).
- 2026-10-11: [[verifier]] gains "Inputs, procedure and report" (P1-19, part 1): the bundle a run reads, how board-check outcomes map onto checks 4.1 and 4.2, the verdict rules and the JSON report, so a third party can build a verifier that reports the same checks.
- 2026-10-11 (P1-12, part 2): the share KEM isn't X-Wing, so no published vectors apply; `share-encryption.json` comes from an independent Python implementation with its own ML-KEM-768 and ChaCha20-Poly1305, each checked against published vectors first ([[share-encryption]], [[0016-share-kem-dh-group]]).
- 2026-10-12 (P1-19 part 3a): [[verifier]], Anchors from L1, specifies how a format-2 bundle's anchors and `now` are read from one L1 header and its trie nodes, with the L1 codes, so two verifiers given the same evidence read the same anchors; `l1-anchor.json` vectors come from Anvil's own headers and proofs.
- 2026-10-12 (P1-20 part 1): the reference election runs `packages/verifier` from its built package in a process of its own, with an empty environment, over the bundle the fixture wrote and nothing else, and requires the ceremony and board checks to pass on it.
- 2026-10-12 (P1-15 part 4b-2b): 2.3 no longer fails a profile pinning ballot version 2 beside a spoiled-ballot opening version the release doesn't know: it is `unsupported-version`, since a later release may know that version to open version-2 cores, so the two releases can't give opposite verdicts. Opening version 1, which opens version-1 cores only, still fails, and so does a profile that fails on another ground. The same holds for a ballot version the release doesn't know under definition version 3 or 4.
- 2026-10-13 (P3-4 part 2b-3a): no outside vectors exist for `H1` or `H2`; `keyed-nullifier-hashes.json` comes from an independent Python implementation that first reproduces Noir's Poseidon2 known answer, the Poseidon2 reference code's width-3 answer and TACEO's three `encode` answers, so the map the spec defines is shown equal to the gadget the circuits will use ([[keyed-nullifier-hashes]]).
- 2026-10-13 (P2-14 part 5a): a release that reads definition version 5 reports its decoding, rules (with the first failing question) and ballot admission, while 6.2 stays `unsupported-version` under definition versions 3 to 5 until a release reads spoiled-ballot opening version 2 (part 5b), so no two releases can give opposite verdicts on an opening. Definition version 6 and later stay unverifiable at the version byte, before any field.
- 2026-10-13 (P2-14 part 5b): the verifier reads spoiled-ballot opening version 2, so 6.2 runs under definition versions 3 to 5 wherever admission does. A profile pinning an opening version the release reads beside a ballot version whose cores it doesn't open (a profile 2.3 fails) leaves 6.2 `not-reached`, never `unsupported-version`, since no later release can read such an opening as one of the election's ballots; an unknown opening version, or a ballot version neither the definition's own nor version 1, stays `unsupported-version`. Under definition version 1, an opening pin of version 2 moves from `unsupported-version` to `not-reached` for the same reason.
- 2026-10-15 (P1-19 part 4p, [[verifier]] 2.3): a contract-event version the release doesn't read (it reads 1 to 3) leaves 2.3 unverifiable (`unsupported-version`) unless the profile fails on another ground, since a later release may read one that names the close rule's events; versions 1 and 2, which it reads and which name none, fail.
- 2026-10-17 (P3-4 part 2b-3b-1): every vector of `keyed-nullifier-hashes.json` now runs through the Noir code the circuits will use (Noir's width-4 Poseidon2, our sponge, TACEO's vendored Elligator 2 and rational map, `H1` and `H2`), each map's Montgomery and Edwards points asserted before the cofactor is cleared, so the circuits agree with the independent Python generator exactly, not only up to 8-torsion.
- 2026-10-17 (P1-20 part 2b-1): the reference election boards ballots made by the ballot client's own prover and `@abolishus/crypto`, and requires the verifier, in its own process, to admit every one (5.1 to 5.5, 5.7, with the admitted count pinned so the rows can't pass on an empty board) and, in a control election, to reject a ballot carrying another ballot's proof at 5.1 to 5.3 alone.
- 2026-10-27 ([[P2-17]] part 4b-2b-1, [[verifier]], Definition, step 1): the verifier reads definition version 7, so its rules are reported on 2.1 and a fixed one is judged as version 6 is rather than left unverifiable at its version byte. A rolling one stays unverifiable at 2.3 (`unsupported-version`) with the board checks not reached until 2.4's rolling replay and the rolling 5.1 and 5.2 exist, and fails 2.3 only when its profile fails `profile-combination`, which every later release fails too; version 8 is now the unknown version left unverifiable at its version byte.
- 2026-10-27 ([[P2-16]] part 5e-5c, [[verifier]] 2.3): this release passes 2.3 for a sealed definition with an author panel that every earlier release fails. The releases can't split on a real election: no registry a release pins registers an author panel, and part 5e-5d serves them only from a new registry deployment, which every earlier release fails with `registries` whatever its 2.3 says.
