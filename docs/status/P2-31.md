## Scope

The owner's decision of 2026-10-21 ([[PROJECT_BRIEF]], Identity; [[0024-tier0-registration]], Owner decision): every account is verified by email and by phone, one account per phone number, so a second account, and with [[P2-30]] a second Tier 0 identity in a group, costs a second phone number. Accounts today are passkey-only ([[P2-5]]).

## Rules

- **Email** is kept, since notifications and account recovery need it ([[P2-27]]); verified by a one-time code or link; one account per normalised address.
- **The phone number is never kept in the clear.** It is verified by a one-time code sent through an SMS provider, then stored only as a keyed hash (HMAC under a server secret, rotated by re-keying) for the one-account-per-number check, and dropped. Changing it re-verifies; a number freed by account deletion stays held for a cooling-off period, so a number can't be cycled through accounts.
- **Virtual and VoIP numbers are refused** where the provider's line-type lookup says so; the refusal says plainly why.
- **The provider sees each number and when it was verified.** That is a new party that learns who uses Abolish (beside T-11's), and gets a threat entry; nothing about polls, answers or ballots ever reaches it.
- **Nothing joins accounts to ballots** (T-10): the verification tables are account-side, and the no-join tests cover them. Verification happens before the account takes a Tier 0 token ([[P2-30]]), never at the moment of voting, so its timing joins nothing.
- Turnstile stays on sign-up and on sending codes; codes are rate-limited per account, per number and per address.
- The owner signs up for the SMS provider and holds its keys (Twilio Verify recommended: it sends and checks the codes and offers the line-type lookup). Staging uses the provider's test credentials.

## Plan

1. ADR: the provider, the number's keyed hash and its key's rotation, the cooling-off period, the countries served at launch, and the threat entry.
2. Email verification in `packages/core` and `apps/web` (codes, rate limits, the account's state), with the sending service shared with [[P2-27]].
3. Phone verification: the provider's adapter, the keyed hash, one account per number, line-type refusal, cooling-off.
4. The sign-up and account screens: verify email, verify phone, change either; existing accounts verify at their next sign-in.
5. Gate voting: an account takes a Tier 0 token ([[P2-30]]) only once both are verified.

## Known-weak

- A phone number costs cents to a dollar at SMS-activation markets, and a state makes numbers at will: Tier 0 stays not Sybil-resistant (T-01).
- Whoever holds the account table and every phone-hash key recovers every verified number; each provider keeps its own record of who verified and when (T-73).
- A dump can narrow an address that was sent a message to the accounts that asked for a code in that hour: the per-address rows are timed to the hour, the per-account ones to the second (T-73).
- Accounts made in bulk can spend an address's 5 daily messages and keep its owner from verifying it that day (T-52).
- During a provider outage the page is told a code went when none did; the person asks again, spending their hourly limit, and only the operator's log shows the outage.
- A send still in flight when an instance shuts down may be lost; the person asks again.
- Postmark may refuse an address whose local part isn't ASCII (SMTPUTF8); that person is told a code went and never gets one. Not confirmed against Postmark either way.
- Twilio may answer 20404 both for a verification that isn't waiting and for a Verify service SID that doesn't exist, so a misconfigured service could read every check as wrong; its sends would fail first (logged as `PhoneSendUnavailable`), so no code would reach anyone to check.
- The guess bound (5 codes a number a day, 5 checks a code) assumes the Verify service keeps its defaults: 6-digit codes or longer (the adapter refuses shorter), a 10-minute lifetime (`PHONE_CODE_SECONDS`) and 5 checks per verification. Nothing reads the service's settings; the [[account-keys]] runbook says to check them.
- A check Twilio approves but answers after the 5-second timeout is told `CHECK_UNAVAILABLE`; the code is spent at Twilio, so the retry is wrong and the person asks for a new code.
- Not tried against Twilio itself (no account yet): the field names and status codes are Twilio's documented ones, and the adapter treats anything else as `unavailable`.
- During a provider outage the page is told a phone code went when none did, as with e-mail; only the operator's log shows it.
- An account that changes its number and changes back within 90 days is refused its own old number: a hold doesn't record who freed it, by design.
- A phone-hash keyring that dropped, reordered or inserted a key anywhere but at the end would stop matching the values made under it, letting a number verify a second account; every key is kept for good, in order, a rule of the [[account-keys]] runbook, not enforced by code. A dropped key shows as `PhoneHashKeyMissing` in the log only once rows under it exist; an inserted or reordered one shows nothing.
- A rotation reaches only the live tables: dumps and backups taken before it, dead row versions until `VACUUM FULL`, and the provider's recovery log and replicas still hold chains under the older keys (T-73); the runbook says to delete those backups and shorten or wait out the recovery window after an exposure.
- Each instance counts the rows of all four phone tables under a key it lacks every 10 minutes, scans the `hash_key` indexes don't serve; cheap at today's size, worth an index-only path if the tables grow large.
- A rotation is one transaction per verified number, so a shutdown mid-rotation waits for the run (each row commits alone, and the next tick resumes).
- Not tested: a phone or e-mail rotation racing an account's deletion, or an e-mail rotation on one configuration racing an answer on the staged one; the reviews' reading is that each holds, the rotations taking the account's lock before the number's or address's, as answers do.
- A key check is compared when an instance starts and before each rotation, not on every request: an instance started before another stored a different check for the same ID keeps running on its bytes until restarted, logging `PhoneHashKeyMismatch` or `EmailKeyMismatch` each tick.
- A waiting e-mail code's hash stays under the hash key it was made with for its 15 minutes, and the per-address send counts, which aren't keyed, under theirs for a day: an old hash key is retired a day after it stops being current, a rule of the [[account-keys]] runbook.
- A stored check value written by an instance with wrong bytes keeps every correct instance from starting, and blocks every rotation under that key ID, until the operator settles it by hand, as the runbook says.
- Each account asking for a code for a number gets its own 5 tries, while the provider keeps one code per number: the bound on guesses is Verify's own cap of 5 checks per verification, which the adapter reads as `wrong` (part 3b). That holds only while the Verify service keeps its default cap.
- The provider's check runs inside the account's transaction, holding a connection for up to the adapter's 5 seconds.
- Accounts made in bulk can spend a number's 5 daily codes and keep its owner from verifying it that day (T-52), as with e-mail.
- Holds and moves count whole UTC days: a number verified at 23:59 can move 89 days and a minute later.
- Whoever has the phone learns, from `number-held`, that the number is some account's: the ADR's refusal "in plain words".
- The holds' trigger stamps the database's own day, not the injected clock; only tests notice.
- Postmark refuses a recipient on its suppression list (an earlier bounce or complaint) as it would any failure, so that person is told a code went and never gets one.
- Making a new hash key current before every instance holds it could let two accounts verify one address or one number; the two-deploy order is a rule of the [[account-keys]] runbook, not enforced by code.
- Turnstile's script runs on `/account/verify` once a code is asked for, with the page's origin, so a compromised or compelled script could read the address or number typed there and the verified address shown (T-55). A frame on a separate challenge origin removes this; that origin isn't deployed yet.
- Only a Tier 0 token waits on both verifications (a reaction waits on the e-mail alone): an unverified account still signs in, drafts and reads, by design, since none of those registers an identity.
- Anyone without a US or Canadian number can't verify an account, so can't vote at Tier 0, until the country list widens.

## Owner decision (2026-10-22): phone verification optional

[[0038-verified-accounts]], Owner decision (2026-10-22). Today the token gate requires a verified phone and, with no provider configured, the phone routes are off, so no account can vote: the app must work without a provider.

6. **Phone verification as a deployment setting** (in the `crypto-review` gate where it touches the token issuer): one explicit setting, off by default, read by the token issuer in `packages/core`/`apps/api` and by `apps/web`. Off: tokens need a verified email only, and no screen asks for a phone. On: as built. Asked for at the point an account first takes a token (first vote), never at sign-up. Tests for both settings, and for turning it on with accounts that hold no phone (they verify before their next token). Results and the account page name Tier 0 as email-verified while it's off.
   - **6a**: the setting, `PHONE_VERIFICATION`, in the token issuer and on the verification and account pages.
   - **6b-1**: a freed e-mail address held for 90 days as a number is, under the e-mail hash keyring (with its rotation), so that while phone verification is off one address can't verify account after account (T-01; found in 6a's review).
   - **6b-2a**: results naming Tier 0 by the setting (`tier0`'s label in `poll-summary.tsx` and `poll-form.tsx`).
   - **6b-2b**: the first-vote ask: the ballot client's token flow ([[P2-30]] part 4, not built yet) sends an `ACCOUNT_UNVERIFIED` refusal to `/account/verify` and back.
7. **The adapters** (when the owner turns it on): WhatsApp authentication codes, and Amazon SMS (AWS End User Messaging) as the fallback, behind the existing adapter beside Twilio's, with the line-type check from whichever provider offers it.

## Built (part 6a)

- **The setting**: `PHONE_VERIFICATION` in `apps/web`'s environment, `on` or `off`, off unless set; `on` refuses to start without the phone provider's five variables, and any other value refuses to start. It is explicit, never inferred from which provider variables are set: a deployment with Twilio configured and the setting unset is off.
- **The issuer** (`packages/core/src/tier0-tokens.ts`): `tier0Issuer` takes `phoneVerification`, a required boolean (anything else throws, so a raw environment string can't pass as on or off). Step 2.1 reads and locks the account's e-mail row, and the phone row only when it's on. Off, an account holding a verified phone is treated as one that doesn't, so turning it on later refuses every account without one its next token, a retry of a token taken while off included, until it verifies a number; no migration. `docs/spec/tier0-token.md`, Who may take a token, says so.
- **The phone routes**: off, every `/phone` route answers `PHONE_UNAVAILABLE` (503), so nothing goes to a provider; the phone-hash keys, where set, are still checked at start, rotated and pruned, so 90-day holds keep ageing and turning the setting off and on again frees no number early (T-01, T-73).
- **The pages**: `fetchPhoneVerification` (`src/data.ts`) reads the same setting for `/account` and `/account/verify`. Off, the verification page shows only the e-mail step, the account page only the e-mail row, and the signed-out page's list of what the account holds drops the phone's fingerprint. On, the account page presses only for the e-mail and shows a missing number as asked for at the first vote, and the verification page keeps the phone step for anyone who wants to do it early. The sign-up text names the e-mail only.
- **Tested**: core, with phone verification off, an account verified by e-mail takes its token with or without a phone and one without an e-mail doesn't; turning it on refuses the next request (a retry and the next key) of an account that took its token without a phone, and answers the retry once a number is verified; the option is refused unless a boolean. The deployable starts with it off by default (Twilio configured), with no phone step on `/account/verify`, and with it on shows the phone step; it refuses `on` without a provider and a value that isn't `on` or `off`. Stories for both settings on both pages.
- **Known-weak**: while the setting is off, a second account, and so a second Tier 0 identity per group, costs a verified e-mail address, which costs almost nothing; and since an address, unlike a number, isn't held once let go, one address can verify account after account (change it away or delete the account, verify it on the next), up to its 5 messages a day, each account taking a token (T-01). Results still label Tier 0 as before until part 6b. Not tested end to end: a `/phone` request reaching a signed-in session with the setting off (the handler's 503 without a service is tested in `serve.test.ts`), and `/token` under each setting in the deployable (core tests both; the wiring is one line).

## Built (part 6b-1)

- **The hold** (`packages/core/src/account-emails.ts`, migration `0037_account_email_holds.sql`, [[0038-verified-accounts]], Amendment (P2-31 part 6b-1)): an address an account lets go, by deleting itself (the table's trigger, whatever path deleted it) or verifying another address, goes to `account_email_holds` as its hash, its hash key's ID and the UTC day, with no account and no box, for `EMAIL_HOLD_DAYS` (90). Always on, whatever `PHONE_VERIFICATION` says. No move, as an address isn't recycled.
- **Answers**: a request for a held address sends the mailbox an `email-on-hold` notice instead of a code and answers as for any address (T-11); a code sent before the hold began answers `address-taken`, whose message now names both cases. The account that let it go is refused it too. The check for another account's row and for a hold is one statement, so a deletion or change committing meanwhile is seen as one or the other.
- **Keys**: a hold can't be re-hashed, so it stays under the key it was made with; the rotation leaves it and counts it in `unknownKeys` once that key leaves the keyring, and the [[account-keys]] runbook now retires an old hash key no sooner than 91 days after it stops being current. An operator settling a skipped row deletes it under `abolish.email_unheld`, which skips the hold.
- **Prune**: `pruneAccountEmails` deletes ended holds and returns their count as `holds`.
- **Tested**: a changed-away address held from another account (notice, no code that verifies) and from the account that let it go; the hold's columns (hash, key, day, nothing else); the same address re-verified holds nothing; a deleted account's address held through the trigger, and not under `abolish.email_unheld`; a code sent before the hold refused; an answer racing an uncommitted deletion sees the row, and one after it the hold; the last held second and the first free one; a hold under an older key still holding after a rotation and counted once its key is gone; prune deletes ended holds and keeps the rest; the app's grants on the table.
- **Known-weak**: addresses stay nearly free (a catch-all domain, or `+tags` and dots, which are deliberately not folded), so while phone verification is off the hold bounds one address to one account per 90 days, not one person (T-01). A change of address writes its hold beside the account's `verified_at`, to the second, so on a quiet day a dump's row order can pair the two and, with the hash key, confirm a guessed old address for that account (T-73). After a hash key is exposed and rotated away, holds under it stay matchable with it for up to 90 days, and the key can't leave the keyring sooner without freeing them. A hold lasts 89 to 90 days (UTC days, as the phone's). The trigger dates a deletion's hold by the database's clock, a change's by the injected one. `abolish.email_unheld` can be set by any session, the app's included, which may delete holds anyway.

## Built (part 6b-2a)

- **The names**: `tierMessage` (`apps/web/src/messages.ts`) names Tier 0 "verified e-mail" while `PHONE_VERIFICATION` is off and "verified e-mail and phone" while it's on, read through `fetchPhoneVerification`, the setting the token issuer reads, so a poll never claims a phone check the issuer doesn't make (T-01). A poll's page (`/polls/<id>`, on the surface and in the evidence) and the poll editor (its "Who can answer?" section and its review) both use it; Tiers 1 and 2 are named as before.
- **Tested**: `tierMessage` under both settings, and no name for a tier a definition can't hold; the poll page's server HTML with the setting unset and `on`; stories for both settings on both components.
- **Known-weak**: the name follows the deployment's setting now, not the one a poll's tokens were taken under, so a closed poll's page changes its name for Tier 0 when the setting is turned on or off. "How it works" (its tiers diagram and copy) still calls Tier 0 a passkey account; that copy is [[P2-29]]'s.
