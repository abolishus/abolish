# T-20: Account-to-identity linkage through the recovery backup

- Area: Ballot secrecy, unlinkability and privacy (G-3, G-4, G-5, G-12)
- Adversary: A-2, A-1
- Status: **Planned** ([[0017-identity-recovery-backup]], P2-6; accepted by the agent, owner may veto). Residual: whoever serves the ballot client's RP ID can ask for the PRF output, so T-41 (malicious client) also defeats this, and on any device the backup passkey syncs to, not only where the voter ran the ballot client. A served `/.well-known/webauthn` that differs from the signed release could let `apps/web` in for a targeted voter; only someone checking the served file against the release (P1-19) catches it.

## Threat

If the PRF-encrypted Semaphore secret is stored keyed by account, or the same passkey and relying party serve both login and the PRF, the operator holds account ↔ backup. A malicious `apps/web` or ballot client we serve (A-2) can request a PRF evaluation and decrypt the secret, which links the account to every nullifier the voter ever produces.

## Mitigation

The backup is never stored keyed by account or retrievable with an account session; the PRF key comes from a credential separate from the account passkey (separate relying party or origin, the ballot client's); design and tests in P2-6, cited from T-10.

[[0017-identity-recovery-backup]] fixes the design (option A):

- The PRF comes from a backup passkey the ballot client creates on a dedicated RP ID host that serves only the ballot client, on a registrable domain other than `apps/web`'s, with no other subdomains; its user handle is random, its name generic, and every evaluation requires user verification.
- The RP ID's `/.well-known/webauthn` and associated-domain files are part of the signed ballot client release, never list an `apps/web` origin, and the verifier's served-client check covers them.
- The PRF output derives a wrap key and a locator. The envelope (fixed length, AEAD under the wrap key, bound to the locator) is stored through the ballot path, with no account session, under `H(tag, locator)`, in an operational table with no account column. Only a locator holder can read, replace or delete it, and a copy of the table can do none of these.
- Envelopes are never archived, mirrored or anchored.
- Where the PRF is unavailable there is no backup. A plaintext recovery code was rejected because the brief keeps the secret on the device; the owner may still ask for one.

Spec and `packages/crypto` code are P2-6 part 2; storage and the refusal of account credentials on the backup routes, part 3; the ballot client's flows, P2-8.

## History

- 2026-10-11 (P2-6 part 1): status moved from Needs design to Planned: [[0017-identity-recovery-backup]] chooses a separate, UV-gated backup passkey on a dedicated ballot RP ID and an envelope stored under a PRF-derived locator. Joining a backup's id to an account through timing or addresses (T-11) gives nothing usable without a PRF evaluation, which only code inside the RP ID's boundary can ask for.
