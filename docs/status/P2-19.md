- State: in progress (part 1, the frame and the system pages, merged in #230; part 2, home, merged in #231; part 3, how it works, merged in #232; part 4, the poll register and the poll page, merged in #241; part 5, the moderation log and the account page, merged in #244; next, the later pages as their data arrives)
- Phase: Phase 2: Open polls end to end at Tier 0

## Scope

Turn the page mockups in `apps/web/src/mockups/` (Storybook `Mockups/Web/…`) into the real `apps/web` routes, on the data that exists today. The mockups are the reference for layout, copy and motion; [[language]] is binding (two registers, everyday by default; square corners; motion only reveals real data; no motion that loops or counts). Nothing here waits on protocol work: every part uses routes the API already serves, and leaves out what it can't show yet instead of faking it.

Rules for every part:

- **No hard-coded strings.** The mockups hard-code English; the real components take translated text from `apps/web/src/messages.ts` (`useTranslate`), as the existing components do.
- **CSP-safe.** The page's CSP has `style-src 'self'`, which blocks inline `style` attributes. Kit components that set one (`TallyBars`' bar width; check `BoardMap`, `InclusionPath`, `QrCode`, share parts and the mockup helpers too) must draw the same thing another way before a real page uses them: SVG geometry attributes, `<meter>`/`<progress>`, or classes. Widening `style-src` is a `security.ts` change for the owner, not a fix.
- **Server-rendered.** Nothing reads `window` or `document` during render; scroll hooks and the motion utilities already render the final state on the server.
- **Analytics stay fixed.** Every new route gets a template in `src/analytics.ts` (`PAGES`) and its test; no path or poll ID is ever kept (T-67).
- **Tested like the kit.** Each new component has a story with a play function that passes axe at desktop width and 360px (`test:storybook` runs both); SSR and serve tests cover each route. A mockup stays in Storybook as the reference until its real page matches it; then its story is deleted in the same PR.

## Plan

Each part is one PR on this branch's name. None is protocol code, so none is inside the `crypto-review` gate.

1. **The frame** (done in #230). The everyday shell from `EverydayShell` (wordmark and tagline, the site's links with `aria-current`, skip link, footer claim) replaces `SiteLayout`'s old header, and `NotFound` and `Failed` are restyled from `system-pages.tsx` (their mockup stories are deleted; Servers unreachable stays as the reference). The nav, footer and "other places to go" link only routes this server has; each mockup link joins with its page. The footer leaves out the entry points and the ballot app's release fingerprint: the server has neither to show yet (P4-4). The SSR test now fails any page whose HTML carries a `style` attribute. 2. **Home** (done in #231), from `everyday-home-page.tsx`: the prompt with the lookup form beside it, the first six listed polls with a link to the rest, and the "why you can trust a casual poll" scroll scene (`TrustScene`, on `StepScene`, which moved from the mockups into `src/components`). Later, as their data arrives: results pages from `poll-results-page.tsx` and `everyday-poll-closed-page.tsx` (P2-9 part 4), poll creation from `everyday-create-*.tsx` (P2-9 part 3), the board pages and "your place on the board" from `board-*.tsx`, and the sharing surfaces ([[sharing]]).

## Tested and known-weak (part 4)

- Built: `/polls` is the register (`PollRegister`): the lookup form, then a page of the listing with status (All, Open, Scheduled, Closed) and counting (All, One choice, Approve any number) filters in a plain GET form, each option counting the page's polls it matches, and rows (`PollRows`, which home's list now shares) with each poll's fingerprint, counting rule and status. Filters apply to the page in hand, never to a search our server runs, and keep `after`; a poll the page can't read never matches a filter. Each group is one radio group and one search parameter, so the router keeps the address as sent (repeated parameters, as checkboxes would send, it rewrites as JSON). `/polls/:id` shows the status, who can vote, the times and the counting rule on the surface, says answers are cast only in the ballot app, and keeps everything `PollSummary` showed (the definition and board facts as claims, the hashes, the short link) behind "How do we know this is real?" in a native `<details>`, so it is in the server's HTML and opens without script. A poll's status is read from its definition's times against the server's clock when the page loaded (`pollStatus`, open through `closes_at`), carried in the page's data so hydration agrees (T-24, T-34).
- Tested: `ssr.test.ts` covers the filters without script (none open, all closed, `all` as sent, a definition naming another election never matching, the next page and Clear filters keeping the page and filters, an unknown or repeated value meaning no filter), that a filter asks the API for the same page (T-10), the poll page's status, its closed note and the disclosure in the HTML; `poll.test.ts` has a fast-check property for `pollStatus` and its boundaries past what `Date` holds; the `PollRegister`, `PollList` and `PollSummary` stories check the statuses, the filters' state and counts, the links, the empty and no-match states and opening the evidence, with axe at desktop width and 360px.
- Known-weak: the mockups' featured referendums, kind filter, title search, entry counts, page numbers, ballot preview, participation, results and answer link are left out (no route serves question text, poll class, per-poll counts or a ballot link yet), so the three mockups stay in Storybook as their reference; the listing is in order of IDs, not closing time; status is the definition's stated times against our clock, not the close rule.
