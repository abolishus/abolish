# Contracts

What our L2 contracts commit to, for a verifier that reads them from the chain and the archive alone. So far this page specifies the event accumulator every Abolish contract keeps, the contract-event record (`0x0008`) that archives each of its events, the election registry, the trustee registry, the group registry with its Tier 0 additions (P3-2), the board, our direct-submit contract, with its ballot and delivery checks, calls and events, and the board anchor, our one contract on L1 (P4-1). The group registry's Tier 1 and Tier 2 additions (P3-3, P3-4) and the close rule are still P1-18's, and are added here as they are built. Notation is from [[notation]], tags from [[domain-separation]].

## Event accumulator

Threats: T-71 (L2 governance or our server hiding an event), T-25 (a direct-submitted ballot withheld from the board), T-24 (equivocation). Decided by [[0005-permanent-archive]], Consequences, "L2 events".

Our server writes the board, and inclusion proofs show only that an event exists, never that none was left out. So every Abolish contract keeps a running hash and a counter over every log it emits, in its own storage, and each step also binds the block that emitted the log. Storage is committed by the L2 state root, which L1 output roots commit to, so an account and storage proof (`eth_getProof`) of these two values at an L2 block pins the contract's whole event sequence up to that block, each event with its block number and timestamp. The block is always the emitting chain's: the board anchor, our one contract on L1, binds L1 blocks, and its evidence is L1's own state (Board anchor). A verifier replays the archived sequence and compares ([[verifier]] 4.4, P1-19). This is the only evidence archived for our contracts' events: no transaction, receipt or block header ([[0025-contract-event-evidence]]).

The tag is `abolish/v1/event-accumulator-2`. The first layout, under `abolish/v1/event-accumulator`, bound no block; it stays frozen with its vectors (`vectors/event-accumulator.json`) and no Abolish contract is deployed with it ([[0025-contract-event-evidence]], Consequences).

### Values

- **Genesis.** At deployment the contract stores

  ```
  acc_0 = H(DS("abolish/v1/event-accumulator-2", u8(0) ‖ u64(chain_id) ‖ bytes[20](address)))
  ```

  and a count of 0, where `chain_id` is the chain's EIP-155 identifier (`block.chainid`) and `address` the contract's own address. Binding both means one contract's event sequence can't be presented as another's, here or on another chain where the same address is deployed (T-71). It doesn't separate the two sides of a fork after deployment, which share the stored value: that is the job of the pinned L2 and the output root the storage proof is checked against (Verification). A contract MUST revert its deployment if `chain_id` is 2⁶⁴ or more, since it has no `u64` encoding.

- **Step.** For its `n`-th log (0-based), emitted in the block with number `b` and timestamp `τ` (`block.number` and `block.timestamp`, read in the call that emits it), with topics `t_0 … t_{k−1}` and data `d`, the contract sets

  ```
  acc_{n+1} = H(DS("abolish/v1/event-accumulator-2",
                   u8(1) ‖ acc_n ‖ u64(n) ‖ u64(b) ‖ u64(τ) ‖
                   u8(k) ‖ t_0 ‖ … ‖ t_{k−1} ‖ u32(len(d)) ‖ d))
  ```

  and the count to `n + 1`. A contract reverts the emitting call if `b` or `τ` is 2⁶⁴ or more, since it has no `u64` encoding. Each topic is the log's 32-byte topic as emitted, and `d` its data bytes as emitted (the ABI encoding of the event's non-indexed fields). `k` is 1 to 4. A log with no topics (a Solidity anonymous event) is never emitted, so `t_0` is always the event's signature hash.

The leading `u8` separates the two input layouts, and fixed widths plus the length of `d` make each input parse one way. The index `n` is redundant with the chain but makes each step's position explicit, so a verifier can report which event diverged. `b` and `τ` place each event on L2 for the checks that compare it with a block or a time ([[verifier]] 2.4, 5.5), with no header or receipt: the accumulator authenticates them with the rest of the step.

### Rules for every contract

- Every log a contract emits goes through the accumulator, in the same internal call that emits it, with no external call in between. No contract emits an anonymous event or any log the accumulator doesn't cover. A reverted call reverts both its logs and its accumulator update, so the two can't drift apart.
- The two values live at fixed storage slots, independent of the contract's inheritance, so a verifier can request them by slot. The base slot is the [ERC-7201](https://eips.ethereum.org/EIPS/eip-7201) namespace `abolish.event-accumulator`:

  ```
  S = keccak256(abi.encode(uint256(keccak256("abolish.event-accumulator")) − 1)) & ~0xff
    = 0x1073a090f5464cb55b258e445c2f90eb0f9b00fb8b1700430d20b9c53b939600
  ```

  The accumulator is the 32-byte word at `S`. The count is the word at `S + 1`, as a big-endian 256-bit integer whose top 192 bits are zero; a proven word with any of those bits set fails the check. ERC-7201's keccak derivation is an external format ([[domain-separation]]), not a protocol hash.

- `eventAccumulator()` returns `(bytes32 accumulator, uint64 count)` for convenience. A verifier relies on the storage proof, never on a call answered by an RPC node.

### Verification

Given a contract's address, the chain ID, its archived logs in order of `n`, each with its `b` and `τ`, and a storage proof of `S` and `S + 1` at an L2 block `B`, a verifier recomputes `acc` and the count from genesis over the logs. The archive matches the contract at `B` exactly when, for the proven count `c`:

1. the logs are numbered `0, 1, …` with no gap, and `b` and `τ` never decrease from one log to the next;
2. every log with `n < c` has `b ≤ B`, and the log `n = c`, if the archive holds one, has `b > B`;
3. the accumulator over logs `0 … c − 1` equals the proven value.

The rules are checked in that order, and the first that fails is reported: `index` (a log out of sequence: rule 1's numbering, checked over the whole archive first), `order` (a block number or timestamp that decreases, checked only once every log is numbered in sequence), `block-range` (rule 2) or `accumulator` (rule 3, including an archive holding fewer than `c` logs).

Anything else (a log left out, added, altered or reordered, a log from another contract or chain, or a log moved to another block) gives a different accumulator or breaks rule 1 or 2, except with negligible probability under SHA-256's collision resistance. The proof at `B` is of the state after `B`, so it covers `B`'s own logs; rule 2 keeps a log from being counted on the wrong side of `B` without changing the accumulator, and rule 1 holds for every honest history, since L2 block numbers and timestamps never decrease. This assumes the genesis and count the release constructor writes; until [[verifier]] 1.2 binds each deployment to the release creation code (Board anchor, Known-weak, Constructor effects aren't bound), a deployer's own initcode could start the accumulator elsewhere. The storage proof is an account proof for the contract's address as the verifier pins it ([[verifier]], Pinned trust roots; its bytecode is checked by 1.2) under the state root that the output root commits to, plus a storage proof of each slot. The storage trie holds each value as the RLP of its minimal big-endian bytes, and omits a zero value: the verifier decodes the value, left-pads it to 32 bytes, and reads an absent slot as zero. The accumulator commits to each log's order and block, never to its transaction: nothing about the transaction is archived ([[0025-contract-event-evidence]]). [[verifier]] 4.4 says when this is checked and what the result is worth: a storage proof is only as good as the output root it is proven against ([[0004-l2-choice]], T-71 residual).

### Vectors

`vectors/event-accumulator-2.json` (format `abolish-event-accumulator-vectors/2`, see [[vectors/README|vectors]]) gives genesis values, event sequences with each event's block and the accumulator after every step, proof checks, including histories that break each rule of Verification, and rejected inputs. TypeScript (`packages/crypto`) and Solidity (`packages/contracts`) tests both consume it. `vectors/event-accumulator.json` is the frozen first layout's, consumed by nothing.

### Known-weak

- The accumulator proves that the archive matches the contract's storage, not that the storage is honest: L2 governance that rewrites state can rewrite it too. A verifier that derives the L2 from L1 itself while the data is retrievable detects it; afterwards only the output root vouches for the storage, as for everything else on L2 (T-71, [[0004-l2-choice]], Finality; [[0025-contract-event-evidence]], Known-weak).
- Each event costs one SHA-256 precompile call over its log, plus two storage writes: 60 gas plus 12 per 32-byte word for the hash; binding `b` and `τ` adds at most one word. Voters don't transact to vote, so it is mostly our gas, but a direct submitter (T-25) pays it for their own submission.

## Contract-event record

Threats: T-17 (chosen bytes in the archive), T-31 (two readings of one record), T-71 (an event the chain's history doesn't hold), T-25 (a direct-submitted event withheld from the board), T-52 (oversized input), T-53 (a submitter failing an election it can't win). Decided by [[0025-contract-event-evidence]] (option B).

Every event of every one of our L2 contracts is archived, and the ones an election's checks use are boarded ([[board]], Payloads; [[verifier]] 4.4), as record type `0x0008`: exactly what its contract's accumulator step hashes, nothing more. A record says which contract emitted the log, its place in that contract's sequence, its L2 block and the log itself; the accumulator's storage proofs authenticate all of it at once (Event accumulator, Verification), so no transaction, receipt or block header is archived, and no byte the sender chose outside our events' own fields reaches the archive (T-17).

### Layout (versions 1 and 2)

| Field          | Type                    | Meaning                                                                             |
| -------------- | ----------------------- | ----------------------------------------------------------------------------------- |
| `contract`     | `bytes[20]`             | The emitting contract's address on the definition's L2 (`l2_chain_id`)              |
| `n`            | `u64`                   | The log's index in that contract's event sequence, from 0 (Event accumulator, Step) |
| `l2_block`     | `u64`                   | `b`: the number of the L2 block that emitted it                                     |
| `l2_timestamp` | `u64`                   | `τ`: that block's timestamp                                                         |
| `topics`       | `list<bytes[32], 4>`    | The log's topics as emitted, `topics[0]` its event's signature hash                 |
| `data`         | `bytes<MAX_EVENT_DATA>` | The log's data as emitted: the ABI encoding of the event's non-indexed fields       |

`MAX_EVENT_DATA` is 2²⁰ (1,048,576) bytes, a framing bound checked before anything is allocated (T-52); every event of the tables below is far smaller: under version 1 the largest, a `MembersAdded`, is at most 25,120 bytes; under version 2 a `CeremonyRegistered` at most 41,472, a `DefinitionRegistered` about 66 KB, and a `BallotSubmitted` at most about 175 KB as framed (the most 32 questions of 65 branches can frame; an admitted ballot's shape bounds it far lower). An event that needs more is a new record version.

The fields are the step's input, re-framed in [[notation]]'s primitives: the step counts topics with a `u8`, the record with a `list`'s `u32`, so a third-party decoder needs no construct of its own, and the step is recomputed from the decoded values, `k` being the number of topics. Decoding is strict ([[notation]], Strict decoding) and context-free; a record with no topics, or with topics or data that aren't an event of its contract, decodes and then fails the event check below. A record's `chain_id` is the definition's `l2_chain_id`, never a field.

The board anchor, our one contract on L1, has no contract-event records: a verifier reads its anchors and locators from L1 state, never from its logs (Board anchor, Verification).

Version 2 has version 1's layout, field for field; the two differ only in their event tables (Event check). The election's profile pins one version for every contract's events, and a record of the other is `profile-mismatch` ([[versioning]], Election profile).

### Event check

A record that decodes counts only if it passes these checks, in order, against the definition's L2 contract addresses and the event tables of the record's version; the first that fails is the result, and [[verifier]] 4.4 fails, naming the record:

1. `unknown-contract`: `contract` is the definition's `election_registry`, `trustee_registry`, `group_registry` or `board`, which the `chain` rule keeps pairwise distinct, giving the record's **role**. Any other address, the L1 anchor's included, fails.
2. `unknown-event`: the record has at least one topic and `topics[0]` is the keccak-256 of an event signature in its role's table for the version (below). An anonymous log, or another role's event, fails.
3. `event-topics`: the record has exactly the event's topics, one per indexed parameter after `topics[0]`, and each is the canonical ABI word of its type: an `address` or `uint<M>` word has no bit set above its width (a `bytes32` word is any 32 bytes).
4. `event-data`: `data` is exactly the canonical ABI encoding of the event's non-indexed parameters (the [Solidity ABI specification](https://docs.soliditylang.org/en/v0.8.30/abi-spec.html), as `abi.encode` produces it): one head word per parameter, a static value's word canonical as in check 3, each dynamic value's offset word pointing exactly past the head and the dynamic values before it, each dynamic value a length word (below 2⁶⁴) and that many bytes, or words for an array, padded with zero bytes to a whole word, and nothing after the last. Each embedded value also meets the bound and the stateless checks of its contract, as the table says.

So each event has exactly one record: the data and topics of every passing record are exactly those re-encoded from its decoded event (the property tests rebuild both), and none carries a byte its event doesn't define (T-17, T-31). The check is of the record's form only. Whether the log is the contract's own is the accumulator's to show (Event accumulator, Verification, over the contract's records in order of `n`); what each field means, and whether it agrees with the others (a definition's hash with its bytes, a group record's identifier with its topic), is for the checks that use the event ([[verifier]] 2.1, 2.4, 2.5, 3.1).

**What the board frames.** The event check is context-free, so it runs the board's framing, which needs no election, and nothing more: the steps below. The board also refuses a few records without reading its registries (seat 0, a vote whose counts or degrees disagree with each other, a posting whose `sealed` length fits no option count), which the event check leaves to the verifier, as it does every shape check: each check added here would be one more way a record the board emits could fail it (T-53), and the accumulator already shows that every archived record is a log the board emitted.

- A ballot record: record type `0x0002` and a version from 1 to 3 (step 1, and step 3 without the pin); step 4's fixed fields (version 1's `tier` at most 2, `nullifier` below `r`); step 5's committed vote, framed under the record's own version, with nothing after it; and the membership proof's three points canonical and each in its group, as [[membership]] (Proof encoding) decodes them, `B`'s order-`r` subgroup included, which the board's `ecPairing` checks (Membership proofs). Whether the version is the one the election pins, and steps 6 to 9 but the proof's points, read the registries, so the board judged them when it accepted the record and the verifier judges them again ([[verifier]] 5).
- A delivery record: its call's type, version 1, and step 4's framing: a receipt of exactly 164 bytes with a `p256-sig` whose `r` and `s` are in range, a posting with its `ct_dh` framed, `pok_c` and `pok_z` below `ℓ` and `sealed` at most 4,116 bytes, a complaint of exactly 228 bytes with its `D` framed, `c` and `z` below `ℓ` and a `p256-sig` in range. The seat, the signature's verification and a posting's length and ballot read the registries.

An element is framed as the board frames it, never decoded: an even value `s` with `0 < s < 2²⁵⁵ − 19`, read little-endian. The board accepts a member's ballot whose elements frame but aren't ristretto255 points, which the verifier rejects later as an entry that counts nothing (Board, Ballots, What it leaves out); if the event check decoded them, that member could fail every election through the board's shared sequence with one ballot ([[verifier]] 4.4; T-53). The ballot hash is recomputed from the record's bytes, `H(DS("abolish/v1/ballot", record[3:35] ‖ record[0:3] ‖ record[35:68] ‖ record[364:]))`, which is [[ballot-validity]]'s (Ballot hash; Hashes (version 3)) for versions 1 to 3, so a topic that disagrees with its record's bytes fails `event-data` and no record has two readings (T-31). Every log the board emits passes, since it emits a record only after its own check, which runs all of these.

Version 2 freezes with its vectors as version 1 did, and every event a later contract adds comes in a version 3. So does every record a later board frames: version 2's framing reads ballot versions 1 to 3 and delivery version 1 only, and a board's sequence is shared by every election on it, so a board that accepts ballot version 4 or a version-2 delivery record ([[delivery]], Version 2; P2-16 part 5) MUST come with a contract-event version whose framing reads them, and every profile naming that board MUST pin that version, or each election pinning version 2 fails 4.4 at the board's first such event (T-53). A profile that pins version 2 reads every contract's events under these tables, the registries' included; version 1's `CeremonyRegistered` check refuses every record the current trustee registry emits, and its tables name no board event, so version 1 MUST be retired before any registry or board is deployed, and the election registry MUST refuse a profile pinning it, with the profile combinations it doesn't yet refuse (Election registry, Registration). Until then [[verifier]] 2.3 still admits a profile pinning version 1; such an election fails 4.4 at its first board event or key-set registration.

### Evidence

The only evidence archived for contract events is, per contract and per anchored period in which its count changed, and at close, the account proof and the storage proofs of `S` and `S + 1` at the first L2 block at or after the period's end for which an output root is posted on L1, with the output root's preimage and the L1 dispute game that carries it ([[0025-contract-event-evidence]], Consequences; P4-3 lists them in the period's manifest). A verifier replays each contract's records against every proof (Event accumulator, Verification): rule 1 orders them, rule 2 places each on its side of the proof's block, and rule 3 shows that none is missing, added, altered or moved. Nothing per event is archived, so checking one event waits for the next proof (Known-weak below).

### Vectors

`vectors/contract-event.json` (format `abolish-contract-event-vectors/1`, see [[vectors/README|vectors]]) gives the event tables with each signature's topic 0, honest records of every event with their encodings and decoded fields, records failing each event-check code, decode rejections, and each contract's records replayed into its accumulator. `vectors/contract-event-v2.json` (format `abolish-contract-event-vectors/2`) does the same for version 2: definitions of versions 1 and 3 to 6 and a version 7 that fails, key-set registrations at their boundaries and the first layout failing, and the board's four events carrying ballots of versions 1 to 3 (one the verifier rejects at a validity proof, one whose element frames but isn't a point) and delivery records, with records failing each of the board's framing checks, a topic disagreeing with its record, and every ballot and delivery decode rejection that needs no election. `packages/crypto` consumes both, and checks that every version-1 vector of an event version 2 keeps has the same verdict under version 2; `packages/contracts` compares each contract's compiled ABI with each version's tables, the board's with version 2's.

### Known-weak

- **Version 1 checks the trustee registry's first registration layout and names no board event.** Its `CeremonyRegistered` check is frozen with its vectors and predates the registered key set, so it fails every record the current registry emits with `event-data`, and a member's direct submission under it fails `unknown-event`. Version 2 reads both, but the election registry doesn't yet refuse a profile pinning version 1: until it does (Election registry, Registration, before any registry is deployed), such a profile would let one direct submission fail its election through 4.4 (T-53). No registry or board has been deployed.
- **Version 2 checks a board record's form, not its meaning.** A record the board accepted for one election is in every election's shared sequence and passes the check whatever it says; whether it counts, and whether its signature, seat, cell or proof hold, is the verifier's ([[verifier]] 5; [[delivery]], Delivery check). So the archive keeps every chosen byte the board accepts (Board, Known-weak; T-17).
- **One event is checked only with its period.** Until the next storage proof covers it, a direct submitter's client sees its own event only through an L2 node it trusts (T-25), and must not stand down on it ([[delivery]], Client rules).
- **The output root is the root of trust for position and completeness** once L1 data has expired (T-71): a false, unchallenged TEE-only root can rewrite blocks and timestamps as it can the sequence. [[verifier]] 4.4 reports TEE-only roots.
- **Chosen bytes inside our events' own fields remain**, bounded by what each contract accepts: a creator's address and the free bits its creations buy, a registration's definition, a quorum's stub and transcript hashes and its key set's KEM-key hashes and signing keys, registrars' nonces and commitments (T-17's residuals list each).

## Election registry

Threats: T-34 (definition substitution), T-24 (equivocation), T-23 (board tampering), T-17 (chosen bytes in the archive), T-37 (a ceremony carried into another definition), T-08 and T-13 (an electorate that isn't public before voting), T-25 (blocking a legitimate election), T-71 (trusting who sent a transaction).

The election registry assigns each election its identifier and records the hash of its one definition ([[election-definition]]), write-once. It is immutable: no owner, proxy, pause or upgrade path, and it inherits the event accumulator above. Every rule below is fixed when it is deployed.

### Deployment

The registry is deployed with the deployment it belongs to, as immutable values: the `board`, `trustee_registry` and `group_registry` addresses on its own chain, the L1 chain ID, the `l1_anchor` and `l1_relay` addresses, and `epoch`, the anchoring clock's start of the anchor contract `l1_anchor` names (P4-1; [[election-definition]], The seal). Its own chain ID is `block.chainid` and its own address is `election_registry`. An L2 contract can't read the L1 anchor's clock, so `epoch` is an input: the deploy script MUST read it from the deployed `l1_anchor`, and the deployment record (`packages/contracts/deployments/<chain-id>.json`) MUST carry it, so a verifier can compare it with the clock its release pins. An `epoch` set too low only weakens the registry's early refusal, since [[verifier]] 2.6 still fails an election that opens before the real one; one set too high refuses legitimate elections until a corrected registry is deployed (liveness only). Deployment reverts unless these could appear in a well-formed definition (the `chain` rule: no zero address, the four L2 addresses including its own pairwise distinct, the two L1 addresses distinct, the L1 chain ID non-zero and different from its own), and, as for every contract, unless its chain ID fits a `u64`.

### Election identifier

```
election_id = H(DS("abolish/v1/election-id", u64(chain_id) ‖ bytes[20](registry) ‖ u64(counter)))
```

where `chain_id` is the registry's chain, `registry` its address and `counter` the number of elections it created before this one, from 0. The input after the tag is exactly 36 bytes. Binding the chain and the address makes the identifier unique across every registry, here or on another chain, so a redeployed registry can't reuse one and have its checkpoints attributed to another election ([[board]], `election_id`; T-23, T-24). It is a hash output, so the creator chooses none of its bytes, beyond the few bits that creating many elections and keeping one buys at the gas cost of each (T-17). Creation reverts rather than wrap the counter.

`createElection()` takes no arguments (calldata of exactly its 4-byte selector) and makes the caller the election's **creator**, the only account that can register its definition. Anyone can create an election. Doing so costs gas and blocks no other election's registration, because no one else can register under the identifier it gets; what it does cost others is below (Events, The shared event sequence). The identifier depends only on the counter, so if an L2 reorganisation reorders two creations, each creator ends up with the other's identifier. A creator MUST therefore wait until its `ElectionCreated` event is in finalized L2 history before putting the identifier in a stub and asking the panel for a ceremony; otherwise a reorg could hand the ceremony's identifier to someone else, who could then withhold its registration (T-25). They could only ever register the exact definition the panel approved.

### Registration

`registerDefinition(bytes definition)` registers the definition of an election. It checks, in this order, and reverts on the first failure:

1. **Canonical calldata.** The calldata is exactly the standard ABI encoding of one `bytes` argument: offset `0x20`, the length, the bytes, zero padding to a 32-byte boundary, and nothing after. Solidity's decoder accepts other offsets and trailing data, so without this a transaction could carry bytes no record defines ([[notation]], Result-critical fields; T-17).
2. **Strict decoding** of `definition` as record type `0x0001` under the layout its version byte names, version 1 or 3 to 6 (2 is never assigned, and any other is `unknown-version`), including the profile check of [[election-definition]] (Decoding), with the decode error codes of [[notation]]. The contract knows the record types specified when version 1 was frozen: `0x0007` and `0x0009` are `unexpected-record-type`, and every other type but `0x0001`, including any specified later, is `unknown-record-type`. A listed `p256-key` (version 4's receipt keys, version 6's author keys) is canonical only if its prefix is `0x02` or `0x03` and its `x`, below `p`, is the `x` of a point on P-256, which the contract checks with OpenZeppelin's audited code: `Math.modExp` gives the candidate square root `(x³ − 3x + b)^((p + 1) / 4)` (P-256's `p ≡ 3 mod 4`) and `P256.isValidPublicKey` checks the point; a key that fails is `non-canonical` at its first byte, as [[trustee-identity]] (Identity key) decodes it. A definition version a later release specifies is `unknown-version` to a deployed registry, which can't change.
3. **Well-formedness**: every rule of [[election-definition]] (Well-formedness) for the definition's version, reporting the first that fails.
4. **This deployment**: `l2_chain_id` is the registry's chain, `l1_chain_id` the deployment's L1, `election_registry` the registry's own address, and `board`, `trustee_registry`, `group_registry`, `l1_anchor` and `l1_relay` the deployment's ([[election-definition]], What gets admitted).
5. **The election**: `election_id` was created by this registry, the caller is its creator, and it has no registered definition. One definition per election, write-once (T-34, T-24). Restricting registration to the creator stops anyone who learns a pending definition's fields (a trustee, whoever relays ceremony messages) from registering first and blocking it (T-25). This is the only check that uses the caller, and it guards only the creator's own identifier: the caller (possibly an aliased L1 sender, or a delegated account) is never trusted for anything else ([[notation]], Result-critical fields).
6. **Timing**: `opens_at ≥ epoch` (no ballot before the anchoring clock starts, [[verifier]] 2.6) and `block.timestamp < opens_at` (registered before voting opens, [[verifier]] 2.1).
7. **The electorate is in the past**: every tier's `root_l2_block` (from version 3, each `tier_electorate`'s one block) is below `block.number`, the registering block ([[election-definition]], The electorate is in the past; T-08, T-13).
8. **The ceremony**: `ITrusteeRegistry(trustee_registry).ceremonyRecorded(stub_hash, ceremony_transcript_hash, panel_id, threshold, panel_size)` is true, where `stub_hash` is computed from `definition` and the other values are the definition's ([[election-definition]], Stub hash and the ceremony). The trustee registry returns true only for a pair that a quorum of distinct seats signed, of a panel it pins whose identifier, threshold and size are exactly those ([[trustee-identity]], Ceremony registration). Passing the panel fields means a quorum of one pinned panel can't approve a definition that names another panel or another threshold, even when the deployment pins more than one panel (a civic panel, [[0006-trustees]]; T-14, T-37); verifier 2.5 and the client's panel check still apply. The check compares hashes; it never relies on who sent either transaction (T-37, T-71). A transcript hash may repeat across definitions.

It then stores `definition_hash` for `election_id`, records the board's parameters for `definition_hash` (Parameters, below) and emits `DefinitionRegistered`. A registered definition can't be changed or removed, and neither can its parameters.

The registry doesn't check what only the board can show: that each root is the root of its tier's additions at `root_l2_block`, each `group_size`, each group's tier, the panel against the pinned panels, or the version pins against a verifier release ([[verifier]] 2.3 to 2.5). It doesn't yet refuse a profile that fails [[verifier]] 2.3's `profile-combination`: one pinning ballot version 1 or 2 without board-entry version 3 or 4 ([[delivery]], Versions), tally-opening version 1 without board-entry version 4 ([[tally]], Destruction), definition version 3 or 4 with any ballot version but 2, ballot version 2 with any other definition version ([[ballot-validity]], Ballot record (version 2)), or ballot version 2 with a spoiled-ballot opening version that doesn't open its cores, which today is every one ([[challenge]], Versions); and ballot version 4 with any definition version but 6 (or 7 under `electorate_mode` 1) or any opening version but 3, or definition version 6 with any ballot version but 4 ([[ballot-validity]], Ballot record (version 4)). It also doesn't check ballot version 4 or accept version-2 delivery records yet, so it MUST refuse every definition pinning ballot version 4 until the board contract does ([[delivery]], Version 2; P2-16 part 5). Both pages require the registry to refuse such a profile, and that check MUST be added before any registry is deployed, with a refusal of any profile pinning contract-event version 1, whose tables can't read the deployed registries' and board's events (Contract-event record, Event tables (version 2)). It doesn't bound `l1_inclusion_bound`, `sequencing_window` or `max_sequencer_drift` either: the close rule (P1-18, direct submission) says what values it needs, and no registry may be deployed before it does, since a deployed registry's rules can't change.

### Parameters

The board checks a direct submission against its election's definition ([[ballot-validity]], Residuals; [[delivery]], Direct submit), but takes nothing about the election from the submitter ([[0028-board-contract-checks]], 1C; T-25, T-71). So at registration the registry also records, keyed by `definition_hash`, what those checks read:

| Field               | Type                                      | Value                                                                                                                                                                                       |
| ------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ballot_version`    | `uint8`                                   | The version the definition's profile pins for the ballot (`0x0002`). Every pin is at least 1 (`profile-version`), so 0 means no definition with this hash is registered (`ballot-stray`).   |
| `threshold`         | `uint8`                                   | `k`, the default panel's threshold.                                                                                                                                                         |
| `panel_size`        | `uint8`                                   | `n`, the default panel's size.                                                                                                                                                              |
| `author_threshold`  | `uint8`                                   | `k_A`, the author panel's threshold; 0 with no author panel (version 6; The author panel, below).                                                                                           |
| `author_panel_size` | `uint8`                                   | `n_A`, how many `author_keys` the definition lists; 0 with no author panel.                                                                                                                 |
| `option_count`      | `uint16`                                  | `T`, every question's options together: the length of the committed vote ([[ballot-validity]], `validity-shape`).                                                                           |
| `cell_count`        | `uint16`                                  | How many cells the definition's partition has ([[election-definition]], Tally partition).                                                                                                   |
| `questions`         | list of `(uint8, uint16, uint16, uint16)` | Each question's `method`, option count, `min_selections` and `max_selections`, in the order the ballot asks them.                                                                           |
| cells               | `(uint8, uint256)` each                   | Each cell's tier and root, the root its ballots prove membership against ([[membership]], Owned elsewhere), in partition order.                                                             |
| ceremony            | `(bytes32, bytes32)`                      | The `stub_hash` the registry checked the ceremony under (the default panel's, under version 6) and the definition's `panel_id`: where the trustee registry recorded the election's key set. |

Four view calls read them, so the board reads only what one submission needs, never every cell of a large partition: `parameters(definition_hash)` returns every field but the cells and the ceremony, `cellTiers(definition_hash)` every cell's tier, in order, `cell(definition_hash, c)` cell `c`'s tier and root, reverting unless `c < cell_count`, and `ceremony(definition_hash)` the stub hash and panel, both zero for a hash never registered. A ballot of version 1 names a tier, which the board finds among the cells' tiers (`ballot-tier`); one of version 2 or 3 names a cell by its position (`ballot-cell`).

Each definition version records them from its own layout:

- **Questions.** Versions 1, 3 and 4 have one question, `(1, option_count, min_selections, max_selections)`, method 1 being selection, which plurality is with the limits `(0, 1)`; versions 5 and 6 record their `questions` as listed. `option_count` is their total `T`, at most `MAX_OPTIONS` by `option-count`.
- **Cells.** Version 1's cells are its tiers, one per `electorate` entry in order, each with its tier and `root`. Versions 3 to 6 record every `tier_electorate`'s `cells` in order, tier by tier, each with its tier's label and its `root`: the partition order a ballot of version 2 or 3 names ([[election-definition]], Tally partition). `cells` bounds them at 256.
- **The ceremony.** The stub hash is the one registration already computes to ask the trustee registry whether the ceremony was recorded, so the board's key set is the one the registry admitted the definition on (Board, Delivery records; [[0028-board-contract-checks]], 2B). An author panel's ceremony isn't recorded here: its seats receive no share of a ballot until [[P2-16]] part 2, which adds its own.
- **The author panel.** `author_threshold` and `author_panel_size` are both 0 for a poll with no author panel and for every version before 6. The ballot that carries the author half is [[P2-16]] part 2's, so its check reads them.

The close rule's fields are added before any registry is deployed (part 4c), since a deployed one's can't change.

The parameters are a function of the registered definition alone, which `DefinitionRegistered` carries, so they need no event of their own. Counting never depends on them: [[verifier]] reads the definition, never the registry's storage, and a ballot the board admitted under a wrong parameter is still judged by the definition's own rules (5.1 to 5.4). Admission does: a wrong parameter would make the board refuse honest direct submissions, which the definition can't show, on the path a censored voter relies on (T-25). So the registry records them with the same code that decodes and checks the definition, and the tests compare each recorded field with the definition registered.

### Events

Each event goes through the event accumulator, with topic 0 the keccak-256 of its signature (the standard ABI):

| Event                                                                                                                                                                       | Topics                                       | Data                                                                                                                                                        |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ElectionCreated(bytes32 indexed electionId, address indexed creator, uint64 counter, uint64 l1OriginNumber, uint64 l1OriginTimestamp, bytes32 l1OriginHash)`               | `election_id`, the creator as a 32-byte word | `counter` and the block's L1 origin, ABI-encoded (128 bytes)                                                                                                |
| `DefinitionRegistered(bytes32 indexed electionId, bytes32 indexed definitionHash, uint64 l1OriginNumber, uint64 l1OriginTimestamp, bytes32 l1OriginHash, bytes definition)` | `election_id`, `definition_hash`             | The block's L1 origin, then the definition's full canonical encoding as `bytes`, ABI-encoded, so the board and any verifier rebuild it from the chain alone |

**The L1 origin.** Both events carry the L1 origin of the L2 block that emitted them: the number, timestamp and hash that the OP Stack's `L1Block` predeploy (`0x4200000000000000000000000000000000000015`) reports in the emitting call, as `uint64`, `uint64` and `bytes32`. The predeploy's address is a constant of the contract, never a deployment input, and on a chain without it both calls revert. The accumulator authenticates the three values with the rest of the event, so no L1-attributes transaction, header or receipt is archived for them ([[0025-contract-event-evidence]]). The creation's origin fixes the election's first segment `f` (Board anchor, Verification); the registration's is compared with a retired version's cutoff ([[versioning]], Old versions stay verifiable; [[verifier]] 2.3).

The registry doesn't check them, since it can't see L1, and a sequencer chooses a block's origin within `max_sequencer_drift`, so a verifier never takes them as read. For each of the two events it checks, failing 4.4 and naming the event otherwise ([[verifier]] 4.4):

1. `(l1OriginNumber, l1OriginTimestamp, l1OriginHash)` is one block of finalized L1: the block with that number has that hash and that timestamp, by the verifier's own trust in L1 headers ([[verifier]], Pinned trust roots);
2. `l1OriginTimestamp ≤ τ ≤ l1OriginTimestamp + D`, where `τ` is the event's L2 timestamp (Event accumulator, Step) and `D` the `max_sequencer_drift` the verifier's release pins for the deployment's L2 (1,800 seconds on Base, [[0004-l2-choice]]). Never the definition's own `max_sequencer_drift`: its creator chooses it, unbounded above ([[election-definition]]; [[verifier]] 2.6 only requires the chain to stay within it), so it can't bound its own registration's origin;
3. for `DefinitionRegistered`, the origin's number and timestamp are at or after those of the same election's `ElectionCreated`. Only the election's own two events are compared: other elections' events in the shared sequence are archived but never checked (The shared event sequence), so comparing with them would let one unchecked junk creation under a rewritten predeploy, naming a maximal origin, fail every later election through the registry.

Honest derivation passes with one exception: an L2 block's timestamp is at or after its origin's, and the OP Stack's derivation drops a batch whose non-empty block runs more than the drift ahead of its origin, which every block holding one of these events is, unless the event came from a deposit (a creation or registration forced through the L1 portal) in an epoch's first block with no batched transactions, which after an L1 block-production gap longer than the drift can be more than `D` past its origin and fail check 2 honestly (Known-weak). So neither the sequencer nor L2 governance rewriting the predeploy (T-71, T-69) can name an origin that isn't a real L1 block, or one more than `D` before the event's own block, or a registration origin earlier than its creation's. Within `D` an earlier origin moves `f` down by at most `⌈D / period⌉` periods (one on Base, with hourly periods), which the creator's per-slot check covers, since it starts from the same event's `f` (Board anchor, Verification, Pre-creation anchors), and moves a registration's origin back past a retired version's cutoff only if the cutoff is less than `D` before the registration (T-34, [[versioning]]). A client checks the creation's origin the same way before it takes `f` from it ([[board]], Segments).

**The shared event sequence.** One registry serves every election it creates, so its accumulator covers every creation and registration, including elections that never get a definition (anyone can create one, for gas). The contract-event record (`0x0008`, P1-18 part 4) and [[verifier]] 4.4 (P1-19) MUST therefore replay a shared contract's whole event sequence from the archive, authenticated by the accumulator's storage proof, and require board entries only for the events the election's checks use: those that name the election, each of its tiers' group creation and group additions and removals up to each `root_l2_block`, and its panel's key and ceremony registrations ([[verifier]] 4.4). Every other event of a shared contract need only be in the archive, which the deployment keeps for every event of each of its contracts, independent of any one election's board (P1-16, part 4). Otherwise every junk creation would have to be boarded on every live election's board, a cost that grows with elections times junk creations (T-52), or a verifier looking only at the election's own board would fail every election through that registry (T-53). Whatever a creation's transaction carries besides its 4-byte calldata (an outer call from the creator's own contract, an access list) never reaches the archive: each event is archived as its contract-event record alone, with no transaction, receipt or header (Contract-event record, Evidence).

A verifier takes the definition's registration from `DefinitionRegistered` on the registry its release pins, recomputes `definition_hash` from the bytes, and finds the election's creation, and no second registration, in the same contract's event sequence ([[verifier]] 2.1, 4.4). The creator's address is public; it is the account that runs the election, not a voter.

### Vectors

`vectors/election-registry.json` (format `abolish-election-registry-vectors/1`, see [[vectors/README|vectors]]) gives election identifiers and inputs with no `u64` encoding. TypeScript (`packages/crypto`) and Solidity (`packages/contracts`) tests both consume it; the Solidity tests also run every vector of `vectors/election-definition.json` through the contract's decoder, rules and hashes.

### Known-weak

- **No close-rule bounds** on the definition's timing fields (above).
- **Creation is permissionless**, so anyone can make the counter grow. Each creation costs its sender gas and reserves nothing anyone else needs.
- **The L1 origin is checked only by verifiers and clients** (The L1 origin, above): the registry records what the predeploy reports, and within the drift the sequencer, or L2 governance rewriting the predeploy, chooses it (T-71, T-69).
- **The pinned drift must keep up with the chain.** If the L2 raises its `max_sequencer_drift` above the one a verifier release pins (Base can, without delay, [[0004-l2-choice]]), honest events whose origin lags by more than the pinned value fail 4.4, attributed to no one, until a release pins the new value; a pinned value raised past a period lengthens the creator's per-slot check to match. Liveness only.
- **A forced event can fail check 2 honestly.** A creation or registration sent as a deposit lands in its epoch's first block, which carries no batched transaction and so isn't bound by the drift: after an L1 block-production gap longer than `D` it can be more than `D` past its origin. Liveness only, and only for forced calls, which an honest creator makes only when the sequencer censors it (T-25); it creates again or registers later.
- **The registry depends on the predeploy.** L2 governance that makes `L1Block` revert stops every creation and registration, a denial of service it can already cause in other ways (T-69, T-25).
- **Versions 1 and 3 are still admitted.** [[election-definition]] requires both to be retired before any registry is deployed, so that every election a deployed registry admits binds receipt keys; the registry decodes them until then, and refusing them MUST come before deployment, with the `profile-combination` check above.
- **Large definitions may not fit one transaction.** Decoding and checking a version-6 definition with one tier at its list limits (1,024 groups and regions, about 29 KB) costs about 7.7 million gas, mostly memory; with all three tiers at their limits and 256 cells (about 66 KB, the largest that passes `cells`) about 29 million, and registering it, with its calldata, event, hashes and up to 256 stored roots, about 37 million or more. A typical version-6 definition costs about 96,000. If the L2 caps a transaction's gas (EIP-7825 sets `2^24`, about 16.8 million), a well-formed definition much above half a full tier per tier can never be registered, and a deployed registry can't change (T-54, liveness). Before any registry is deployed, the decoder MUST be made cheap enough for the record's limits under the target L2's cap, or the limits lowered in a later definition version; a test at the three-tier limits then fixes the budget. Only the creator pays, once per election.
- **Gas.** Registering a two-tier definition (about 500 bytes) costs about 350,000 gas in the tests: about 125,000 for decoding, the ceremony check, three SHA-256 calls (stub, definition, accumulator) and the three reads of the L1 origin, and about 225,000 for the ten storage words of its parameters and ceremony (Parameters), one more for each further cell's root and one for each further 32 cells' tiers; creating an election costs about 108,000. Each runs once per election, so neither is a hot path.

## Trustee registry

Threats: T-71 (trusting who sent a transaction), T-37 (a ceremony carried into another definition, a stolen identity key), T-14 (fewer than `k` parties opening ballots), T-31 (malleable signatures), T-17 (chosen bytes in the archive), T-25 (blocking a legitimate election).

The trustee registry pins the deployment's trustee panels and records, for each definition stub, the one ceremony transcript a quorum of a panel's seats approved. The election registry asks it `ceremonyRecorded` before admitting a definition (Election registry, rule 8). It is immutable: no owner, proxy, pause or upgrade path, no way to add, change or remove a panel, and it inherits the event accumulator above.

### Deployment

The registry is deployed with a non-empty list of panels. For each it takes the threshold `k`, a **quorum** `q`, the seats' keys as their `p256-key` encodings in seat order ([[trustee-identity]], Identity key), and each key's point `(x, y)`. It refuses the deployment, naming the panel's position and the first failing check, in this order (checks 3 and 4 run seat by seat, so a seat's key is checked, then compared with the earlier seats', before the next seat's):

1. `n ≤ MAX_TRUSTEES`, where `n` is the number of points (`size`);
2. `2 ≤ k ≤ n` (`threshold`);
3. the encodings are exactly `33 · n` bytes, and each seat's encoding is the encoding of its point: first byte `0x02 + (y mod 2)`, the same `x`, and `(x, y)` on the curve with `x, y < p`, checked with OpenZeppelin's `P256.isValidPublicKey` (`key`). An encoding passes this for some point exactly when `p256-key` accepts it, so the deployment pins exactly the keys a verifier decodes, the two points with `x = 0` included;
4. no point repeats an earlier seat's (`duplicate-key`);
5. `k ≤ q ≤ n` (`quorum`);
6. its `panel_id` ([[trustee-identity]], Panel identifier), computed from `k`, `n` and the encodings, isn't an earlier panel's (`duplicate-panel`). Another quorum doesn't make another panel.

Checks 1 to 4 are [[trustee-identity]]'s panel rules, with its codes. Each pinned panel is logged as `PanelPinned`, so the board and any verifier read the deployment's panels and quorums from the chain alone. As for every contract, deployment reverts unless the chain ID fits a `u64`, which the registration statement's `l2_chain_id` needs.

**The quorum.** `q` is how many distinct seats must sign a registration. It is at least `k`, because a transcript fewer than `k` seats approved could register keys no `k` honest seats checked, and at most `n`. A deployment sets it per panel, and its deployment record (`packages/contracts/deployments/<chain-id>.json`) MUST carry it. Every deployment MUST set `q = max(k, n − 1)` for every panel it pins ([[0006-trustees]] rule 7, adopted by the owner on 2026-10-12: an election opens only when at least `n − 1` seats, and never fewer than `k`, take part). The contract itself still accepts any `k ≤ q ≤ n`, so the rule binds the deployment and the release: a release pins `q = max(k, n − 1)` for each panel it pins, [[verifier]] 3.1 requires that many approvals in `CeremonyRegistered` whatever the contract's `q`, and a release MUST NOT pin a deployment whose `PanelPinned` events show another `q` for any panel. A deployment with a lower `q` could only register a transcript the verifier then fails (an election discredited and stalled, never one with weaker secrecy); checking `q` in the constructor would remove even that. A panel pinned with a lower `q` would let fewer seats register a transcript, never fewer than `k`. The participation rule is also enforced where it matters for the result, whatever `q` is: an honest seat approves only a transcript with at least `max(k, n − 1)` qualified seats ([[ceremony]], Approval and re-runs), and [[verifier]] 3.2 fails any other (`ceremony-participation`); that is a property of the transcript, not of who approved it.

### Registration

`registerCeremony(bytes registration)` takes one record:

```
registration = panel_id ‖ stub_hash ‖ ceremony_transcript_hash ‖ u8(seats) ‖ seat × seats ‖ u8(count) ‖ approval × count
seat         = u8(index) ‖ kem_key_hash ‖ x ‖ y
approval     = u8(index) ‖ p256-sig
```

`panel_id`, `stub_hash`, `ceremony_transcript_hash` and `kem_key_hash` are `bytes[32]`, and `p256-sig` is [[trustee-identity]]'s 64-byte `r ‖ s`. The `seat`s are the registered key set ([[ceremony]], Key set hash), each with its signing key as the point `(x, y)`, two 32-byte big-endian coordinates, rather than its 33-byte encoding: the contract checks a signature against the point and can't decompress an encoding without implementing a square root, so it takes the point and computes the encoding, `u8(0x02 + (y mod 2)) ‖ x`, which is the only one that point has. The record is exactly `98 + 97 · seats + 65 · count` bytes. Anyone may submit it. The registry checks, in this order, and reverts on the first failure (checks 7 and 8 run seat by seat, and 9 and 10 approval by approval: a seat's or approval's checks, in order, before the next one's):

1. **Canonical calldata**, as for the election registry's `registerDefinition` (T-17).
2. **Length**: at least the 97-byte header, at least `98 + 97 · seats` bytes, and exactly `98 + 97 · seats + 65 · count`. Nothing can be appended, so the record carries no bytes the layout doesn't define (T-17).
3. **The panel** is pinned.
4. **The transcript hash** isn't zero, the value a stub carries in its place ([[election-definition]], Stub hash and the ceremony).
5. **Quorum**: `count ≥ q`.
6. **Write-once**: nothing is recorded yet for this `stub_hash` and panel.
7. **The key set's size and seats**: `seats ≥ k`, so the panel can open a ballot ([[ceremony]], Transcript check, 5) (`KeySetTooSmall`), and the seats' indices are strictly increasing, the first at least 1 and the last at most `n` (`KeySetSeatsOutOfOrder`).
8. **The key set's signing keys**: each seat's `(x, y)` is a point of P-256 with `x, y < p`, checked with OpenZeppelin's `P256.isValidPublicKey` (`InvalidSigningKey`), and is neither an earlier seat's point nor any pinned identity key of the panel (`DuplicateSigningKey`). An honest key set always passes: the transcript check disqualifies a seat whose signing key repeats another qualified seat's or any identity key (`duplicate-key`), so this only keeps one key from signing receipts for two seats, or an identity key from signing as a per-election key, on the board ([[trustee-identity]], Which key signs what; T-37).
9. **The approvals' seats**: strictly increasing, the first at least 1 and the last at most `n`, so each seat counts once. ECDSA lets one key make many valid signatures on one statement, so counting signatures instead of seats would let one seat, or one stolen key, reach a quorum alone ([[trustee-identity]], Ceremony registration; T-14, T-37). An approving seat needn't be in the key set: a seat the check disqualified can still have checked the transcript.
10. **The signatures**: each approval's signature verifies, under its seat's pinned key, on the ceremony registration statement ([[trustee-identity]], Ceremony registration) with `l2_chain_id = block.chainid`, `trustee_registry` this contract, the record's `panel_id`, the approval's `index`, `stub_hash`, `ceremony_transcript_hash`, and `key_set_hash` computed from the record's seats. The registry builds `key_set_hash` and the 157-byte statement and its digest `H(DS("abolish/v1/sig/ceremony-registration-2", m))` itself, and verifies through OpenZeppelin's `P256.verify` after checking `1 ≤ r < n` and `1 ≤ s ≤ (n − 1) / 2` itself ([[trustee-identity]], On chain). Every approval must verify, including any beyond the quorum, so no record holds a signature the panel didn't make.

It then records, for (`stub_hash`, `panel_id`), `ceremony_transcript_hash`, `key_set_hash`, the key set's seats and each one's signing key, and emits `CeremonyRegistered`. Nothing recorded can be changed or removed, and a second registration for the same stub and panel reverts, with the same transcript or another: a quorum can't hold a second set of keys in reserve for a definition ([[ceremony]], Approval and re-runs). The sender is never checked or recorded (T-71).

**The registered key set** is read with `keySetOf(stub_hash, panel_id)`, which returns `key_set_hash` and the seats as a bitmask (bit `i` set for seat `i`, so bit 0 never), and `signingKeyOf(stub_hash, panel_id, index)`, which returns seat `index`'s signing key as `(x, y)`, both zero for a seat outside the set or a stub and panel with nothing recorded. The board takes an election's qualified seats and its trustees' signing keys from these, under the stub hash and panel its definition gives, never from a submitter ([[0028-board-contract-checks]], 2B; Board, Ballots, step 8). They are what a quorum signed, not what the transcript check returns: [[verifier]] 3.1 compares the two and fails an election whose recorded set differs, so a set a corrupt quorum signs makes the board accept the wrong keys only until that election fails (Known-weak).

**Per stub and panel.** A stub names one panel, and an honest seat signs only for a stub that names its own ([[ceremony]], Stub checks). Recording per stub alone would let a quorum of another panel the deployment pins register first and block the stub's own panel for good (T-25); keyed by panel, its record is simply never asked for, since the election registry passes the definition's own panel.

`ceremonyRecorded(stub_hash, transcript_hash, panel_id, threshold, panel_size)` returns true exactly when `panel_id` is pinned with that threshold and size, and the transcript recorded for (`stub_hash`, `panel_id`) is non-zero and equals `transcript_hash`. `panel_id` already binds `k` and `n`; comparing them as well costs nothing and keeps the answer right whatever the caller passes.

### Events

Each event goes through the event accumulator, with topic 0 the keccak-256 of its signature:

| Event                                                                                                                       | Topics                                              | Data                                                      |
| --------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- | --------------------------------------------------------- |
| `PanelPinned(bytes32 indexed panelId, uint8 threshold, uint8 quorum, bytes keys)`                                           | `panel_id`                                          | `k`, `q` and the `33 · n` bytes of encodings, ABI-encoded |
| `CeremonyRegistered(bytes32 indexed stubHash, bytes32 indexed panelId, bytes32 indexed transcriptHash, bytes registration)` | `stub_hash`, `panel_id`, `ceremony_transcript_hash` | The whole registration record, ABI-encoded as `bytes`     |

The panels are logged at deployment, so they are the first events of the registry's sequence (which, until 1.2 binds creation code, only the release constructor guarantees: Board anchor, Known-weak, Constructor effects aren't bound). A verifier finds an election's ceremony registration by its stub and panel, checks every approval against the panel its release pins ([[trustee-identity]], Ceremony registration), and counts the distinct seats whose approvals verify against the quorum its release pins for that panel, never the `q` in `PanelPinned`, which it compares with its own and reports if they differ (P1-19, [[verifier]] 3.1). It recomputes `key_set_hash` from the record's seats, which is the one every approval signs, and compares it with the hash of the key set its own transcript check returns ([[verifier]] 3.1). It needs nothing else from the contract's state. Like the election registry, the trustee registry is shared by every election, so its event sequence is replayed whole from the archive ([[verifier]] 4.4; Election registry, The shared event sequence). Only a quorum can add an event to it, so it grows with ceremonies, not with junk.

### Vectors

The Solidity tests consume `vectors/trustee.json`: the deployment check accepts every key vector `p256Key` accepts and refuses every other, at any length; every signature vector verifies exactly when it is marked valid; every panel vector is pinned with its `panel_id`, or refused with its code. `trustee.json`'s `registrations` are statements of the retired first layout and are read by nothing ([[trustee-identity]], Ceremony registration). The tests also consume `vectors/key-set.json`: every key set's `key_set_hash` is the one the registry computes from its seats' points, each point is the one its `p256-key` encodes, and every statement's message and digest are the ones the registry builds, with a signature that verifies only under its seat's key; registrations that carry the file's key sets record them, with their seats and signing keys, and the key-set checks (size, order, points, repeated and identity keys) each have a refusal test.

### Known-weak

- **The precompile is the chain's code, not ours or OpenZeppelin's.** The contract is built for `cancun`, which has no `P256VERIFY`, so the tests' default run takes `P256.verify`'s Solidity fallback (about 250,000 gas a signature). The package's test script runs the trustee registry's tests again on `osaka`, where Foundry provides the precompile (EIP-7951), so both paths pass every vector; a 7-seat registration then costs about 570,000 gas with its key set (Gas, below). Base implements the precompile itself (RIP-7212), and a disagreement between its implementation and Foundry's would first show on a testnet deployment.
- **The vendored library is checked against itself.** `test/vendor.test.ts` pins the vendored files' hashes, which the package README records with their upstream tag and commit; re-fetching them from upstream in CI needs a `ci:` change (rule B).
- **A quorum can register a transcript for any stub**, including one no election will register. It costs gas, blocks nothing, and needs `q` seats' signatures, but each such event puts bytes the quorum chose into the shared archive every verifier replays: 64 for `stub_hash` and `ceremony_transcript_hash`, and about 64 per seat of its key set, since the registry can't check a `kem_key_hash` against any key and a signing key need only be an unused point (about half of all `x` values give one, so about 32 chosen bytes), up to `MAX_TRUSTEES` seats: about 1 KB per registration (T-17).
- **A key set a corrupt quorum signs is recorded.** The registry can't run the transcript check (it needs ML-KEM), so it records the set the quorum signed, and the board accepts receipts and complaints under its keys until [[verifier]] 3.1 fails the election for a set that isn't the transcript's. A quorum of `max(k, n − 1)` corrupt seats can already break the election's secrecy, so this adds a way to fail, not a new attack ([[0028-board-contract-checks]], Known-weak; T-14).
- **Gas.** In the tests, registering the 7-seat panel's transcript with all 7 seats in the key set and 4 approvals costs about 1.5 million gas under OpenZeppelin's Solidity fallback and about 570,000 through the precompile, against about 1.1 million and 130,000 for the same approvals without a key set: most of the difference is the 16 storage words of signing keys and the set. It runs once per election and panel.
- **The quorum is the deployer's choice.** `q` is a constructor input held in storage, so verifier 1.2's bytecode check doesn't pin it, and a deployer can pick any `q` from `k` to `n`, or pin extra panels. The `k` floor holds whatever it picks. A verifier must not inherit the choice: it counts the distinct valid seats in the `CeremonyRegistered` record itself (Events, above), against the quorum its release pins.

## Group registry

Threats: T-06 (group stuffing by the operator), T-62 (contract admin abuse), T-71 (trusting who sent a transaction), T-08 and T-13 (an electorate that isn't public before voting), T-31 (malleable signatures), T-17 (chosen bytes in the archive), T-52 (junk in a shared event sequence), T-12 (linking a member to a poll).

The group registry holds the deployment's Semaphore groups. It fixes each group's tier when it creates the group and logs every addition and removal together with the authorisation a verifier rechecks, so [[verifier]] 2.4 rebuilds each tier tree ([[membership]], Tier tree) from the chain and the board alone. It keeps no Merkle tree: the roots elections use are tier-tree roots that verifiers compute from these events, and direct submission checks a ballot's proof against the root registered with its definition ([[membership]], Owned elsewhere), so a root kept on chain would be a second answer nothing may use. It is immutable: no owner, proxy, pause or upgrade path, and it inherits the event accumulator above.

This version adds members to **Tier 0** groups only. Tier 1 additions (anonymous vouches, [[0014-tier1-vouching]], P3-3) and Tier 2 additions (document proofs, [[0010-tier2-identity-provider]], P3-4) will be specified here before any group registry is deployed, since a deployed registry's rules can't change; until then `createGroup` refuses those tiers.

### Deployment

The registry is deployed with its **registrars**: `n` Ethereum addresses (secp256k1 keys) and a threshold `t`. [[0004-l2-choice]] (Governance as an adversary) has Tier 0 additions carry a threshold signature of our Safe's owners, checked by the contract and again by the verifier. This registry keeps that rule's purpose (no transaction spoofed from any address, by L2 governance or anyone else, adds members without `t` keys) with two departures, listed under Decisions to review in STATUS:

- **Pinned, not read from the Safe.** A Safe's owners, threshold and modules can change after deployment (Board anchor, Known-weak), and a verifier reading them would have to prove the Safe's state at every addition's block. Pinned, the set a verifier checks is the one the registry's first event logs and its release pins.
- **Dedicated keys, not the Safe's owner keys.** Tier 0 registration is automatic, so the signing service holds `t` registrar keys online (Known-weak). Registrar keys MUST be used for nothing else, never as owners of the Safe that holds the anchoring authority or any timelock, so that seizing the registration service seizes Tier 0 additions and nothing more (T-69, T-62). The deployment record names the registrars and who holds each key.

`t`, the cached EIP-712 domain separator and the chain ID it was computed for are immutables, which [[verifier]] 1.2 masks and compares with the values its release pins; the addresses are in storage, so the verifier checks them through `RegistrarsPinned` (Verification). Rotating the registrars means deploying a new registry, whose groups are new groups. Deployment reverts unless, in this order:

1. `2 ≤ n ≤ MAX_REGISTRARS = 16` (`size`);
2. `2 ≤ t ≤ n` (`threshold`): no single key adds or removes members (T-62);
3. no address is zero, and the addresses are strictly ascending as 160-bit integers (`order`), so none repeats and the set has one encoding;
4. the chain ID fits a `u64`, as for every contract.

`RegistrarsPinned` logs `t` and the addresses, and the deployment record (`packages/contracts/deployments/<chain-id>.json`) carries them.

### Groups

`createGroup(uint8 tier)` takes calldata of exactly its 4-byte selector and one word holding the tier, and creates group `group_id`, the number of groups the registry created before it, counted from 0 (the `group_id` of [[election-definition]]), with that tier, fixed for good. It reverts unless the tier is 0 (`1` and `2` are refused until their addition paths exist), and rather than let `group_id` leave the `u64` range.

Anyone can create a group. A new group has no members until the registrars add some, so creating one gives its sender nothing, and costs others only an event in the registry's shared sequence (Election registry, The shared event sequence; T-52). A group's tier is the one its `GroupCreated` event logs: the verifier takes it from there, never from a definition's label ([[election-definition]], A group's tier; [[verifier]] 2.4).

The identifier depends only on the counter, so an L2 reorganisation that reorders two creations swaps their identifiers. Every signed message binds the group's tier as well as its identifier (Signed messages, below), so a batch signed for one group can never land in a group of another tier; registrars MUST still sign for a group only once its `GroupCreated` event is in finalized L2 history, or a reorg could move a batch into a stranger's group of the same tier.

### Additions

`addMembers(bytes record)` takes one record:

```
record   = u64(group_id) ‖ u64(first_index) ‖ u16(count) ‖ field<bn254> × count ‖ u8(approvals) ‖ approval × approvals
approval = u8(seat) ‖ bytes[32](r) ‖ bytes[32](s) ‖ u8(v)
```

so the record is exactly `19 + 32 · count + 66 · approvals` bytes, with `approvals` the byte at offset `18 + 32 · count`. `r` and `s` are big-endian integers. Anyone may submit a record. The registry checks, in this order, and reverts on the first failure (the approvals are checked one by one, seat then signature, in record order):

1. **Canonical calldata**, as for the election registry's `registerDefinition` (T-17).
2. **Length**: at least 19 bytes, and exactly `19 + 32 · count + 66 · approvals`. Nothing can be appended (T-17).
3. **The group** was created by this registry, and its tier is 0.
4. **The batch**: `1 ≤ count ≤ MAX_BATCH = 256`, which bounds the gas, the log and the accumulator step of one call.
5. **The position**: `first_index` equals the group's member count, the number of commitments added to it so far (removals don't lower it), and `first_index + count ≤ 2³²`, the leaves of a tier tree ([[membership]], Tier tree).
6. **The commitments**: none is forbidden ([[membership]], Commitments and removals). Each is a canonical `field<bn254>` (below `r`), and none is `0`, `1` or `Poseidon2(0, 1)`:

   ```
   Poseidon2(0, 1) = 0x1bd20834f5de9830c643778a2e88a3a1363c8b9ac083d36d75bf87c49953e65e
   ```

   (circomlib's Poseidon with two inputs, the hash of the tier tree; Vectors, below, says where the value comes from).

7. **Enough seats**: `approvals ≥ t`.
8. **The seats and signatures**: each approval's `seat` is greater than the previous one's, at least 1 and at most `n`, so each registrar counts once; its `v` is 27 or 28, `1 ≤ r < N` and `1 ≤ s ≤ (N − 1) / 2` with `N` secp256k1's group order (the low-s rule of EIP-2, so a signature has one encoding, T-31); and `ecrecover` of the `AddMembers` digest (Signed messages) under `(v, r, s)` returns registrar `seat`'s address. Every approval must verify, including any beyond `t`, so no record carries a signature the registrars didn't make.

It then adds `count` to the group's member count and emits `MembersAdded`. Member `first_index + i`, leaf `first_index + i` of the tier tree, is the record's `i`-th commitment.

**Why the position is signed.** Binding `first_index` makes each signed batch land at one place, at most once: a replay, or a batch submitted out of order, reverts. So the group's sequence is exactly the one the registrars signed, and no relay can inflate a group's size by replaying a batch (T-06, T-13). Two batches signed for one position can't both land; the one submitted second is dead, and its members must be signed again at a later position. So the signing service MUST sign at most one batch per position, submit its records itself, and sign the next position only once the previous batch is final; a record handed to anyone else could be withheld to stall the group's queue (liveness only).

A commitment may repeat, within a group or across groups ([[membership]], Commitments and removals): the registry can't refuse a repeat without storing every commitment, and a repeated commitment is one identity with two leaves, which adds no voting identity but counts twice in `group_size`. The signing path MUST refuse a commitment the group already holds, and the forbidden ones (above).

### Removals

`removeMembers(bytes record)` takes one record:

```
record = u64(group_id) ‖ u64(size) ‖ u16(count) ‖ u64(index) × count ‖ u8(approvals) ‖ approval × approvals
```

exactly `19 + 8 · count + 66 · approvals` bytes, with `approvals` the byte at offset `18 + 8 · count`. `size` is the group's member count when the registrars signed. The registry checks, in this order: canonical calldata; the length; the group, as for additions (it exists and its tier is 0); `1 ≤ count ≤ MAX_BATCH`; `size` is at most the group's member count; index by index, that it is greater than the one before, below `size` and not removed already; then rules 7 and 8 of Additions over the `RemoveMembers` digest. It then marks each index removed and emits `MembersRemoved`. A removal sets that leaf of the tier tree to 0 ([[membership]], Commitments and removals); the member count doesn't change, so leaf numbering never shifts.

**Why `size` is signed.** Without it, a removal signed (by mistake or in a race) for an index no member has reached yet would stay valid for good: whoever holds it could submit it once a legitimate member lands there, removing that member at a moment of their choosing, just before an election's `root_l2_block`, say. With it, every index a signed removal names was a member's when it was signed. The signing path MUST set `size` to the member count in finalized L2 history and remove only members it has identified there.

[[membership]] lets a verifier meet stray removals (an index no addition has reached, a leaf already removed) and ignore them. This registry refuses them, so each of its removals changes exactly the leaves it names; a replayed removal reverts.

### Signed messages

Registrars sign [EIP-712](https://eips.ethereum.org/EIPS/eip-712) typed data, an external format ([[domain-separation]]), so a registrar's signer, and anyone auditing it, sees what is signed in the standard's readable form ([[0004-l2-choice]]). The domain is

```
EIP712Domain(string name,string version,uint256 chainId,address verifyingContract)
name = "Abolish group registry", version = "1", chainId = block.chainid, verifyingContract = the registry
```

and the two message types are

```
AddMembers(uint64 groupId,uint8 tier,uint64 firstIndex,uint256[] commitments)
RemoveMembers(uint64 groupId,uint8 tier,uint64 size,uint64[] indices)
```

with `tier` the group's tier as the registry recorded it, `commitments` and `indices` the record's in record order. As EIP-712 defines them, `hashStruct(s) = keccak256(typeHash ‖ enc(s))`, where each integer is one 32-byte big-endian word and an array is `keccak256` of its elements' words concatenated, and the digest is

```
keccak256(0x19 ‖ 0x01 ‖ hashStruct(domain) ‖ hashStruct(message))
```

The domain binds the chain ID and the registry's address, and the message the group, its tier and, for additions, the position (for removals, `size`), so a signed batch can't be replayed on another chain or deployment, into another group or tier, or at another place in its group ([[verifier]] 2.4; T-30, T-32, T-06). The record carries the signatures, never the digest: the registry and every verifier recompute it.

### Events

Each event goes through the event accumulator, with topic 0 the keccak-256 of its signature:

| Event                                                                           | Topics                                         | Data                                              |
| ------------------------------------------------------------------------------- | ---------------------------------------------- | ------------------------------------------------- |
| `RegistrarsPinned(uint8 threshold, address[] registrars)`                       | none beyond topic 0                            | `t` and the addresses, ABI-encoded                |
| `GroupCreated(uint64 indexed groupId, uint8 indexed tier)`                      | `group_id` and the tier, as 32-byte words      | empty                                             |
| `MembersAdded(uint64 indexed groupId, uint64 indexed firstIndex, bytes record)` | `group_id` and `first_index`, as 32-byte words | the whole addition record, ABI-encoded as `bytes` |
| `MembersRemoved(uint64 indexed groupId, bytes record)`                          | `group_id`, as a 32-byte word                  | the whole removal record, ABI-encoded as `bytes`  |

The registrars are logged at deployment, so they are the registry's first event (which, until 1.2 binds creation code, only the release constructor guarantees: Board anchor, Known-weak, Constructor effects aren't bound).

### Verification

Like the other registries, the group registry is shared by every election, so a verifier replays its whole event sequence from the archive, authenticated by the accumulator ([[verifier]] 4.4; Election registry, The shared event sequence). For each tier group a definition names, the verifier ([[verifier]] 2.4):

- requires the registry's `RegistrarsPinned` to name exactly the set and `t` its release pins, and otherwise fails every group of that registry: a registry deployed from the release's bytecode with other registrars would accept additions the verifier doesn't count, and its removals, which name indices in the registry's numbering, would then zero other members' leaves in the verifier's;
- takes the group's tier from its `GroupCreated` event;
- selects the group's records by their events' `group_id` topic, and fails the group (`group-history`) if a record's own `group_id`, or an addition's `first_index`, differs from its event's topic;
- **replays the group's records itself**, in log order up to the tier's `root_l2_block`, keeping its own member count `c` (from 0) and removed set, and applies to each record every check the registry applies, with no state taken from the chain: the record decodes strictly as above (no forbidden commitment); its digest, recomputed with the chain ID and registry address its release pins and the tier from `GroupCreated`, carries at least the threshold its release pins of approvals, by distinct registrars of the set its release pins, in increasing seat order, every one of which verifies (rules 7 and 8); an addition's `first_index` equals `c` and `c + count ≤ 2³²`, after which its member `i` is leaf `c + i` and `c` grows by `count`; a removal's `size` is at most `c`, its indices are below `size` and none is removed already, after which those leaves are 0. For each record the verifier reports the first failing check in this order, so conforming verifiers name the same reason: decoding (`length`, `batch`, `forbidden-commitment`, `index-order`, `index-range`), the group (`group`), the approvals (`approvals`, `seat`, `signature`), the position or size (`position`, `size`), then removed leaves (`removed`). The registry's own revert order differs; only the verifier's is fixed;
- rebuilds the root and the member count from those leaves as [[membership]] defines them.

**A record that fails any of these checks fails every definition naming the group** (`group-history`, naming the record): the chain then shows a history this registry's rules forbid, so it was rewritten by L2 governance or a false output root (T-71), or comes from code other than the release's (1.2), and the verifier fails closed rather than guess which leaves were meant. On the release's bytecode with the pinned registrars, on an honest chain, no logged record fails them, so no registrant or relay can trigger this (the registry refuses forbidden commitments, so [[membership]]'s leaf-0 rule never applies to this registry's records). Rechecking the signed `first_index` and `size` against the verifier's own count is what makes a rewritten history detectable: a replayed or reordered batch, or one omitted before a later batch, breaks the signed sequence (T-71, T-06, T-13). Two omissions still check, and are caught only by an honest accumulator storage proof (4.4, the T-71 residual): dropping the **latest additions** before `root_l2_block`, which leaves a shorter sequence; and dropping **any removal**, anywhere, since removals don't move the count and carry no sequence number of their own, which keeps a member the registrars removed in the electorate. A per-group counter signed by every record would narrow the second to the tail as well; it isn't worth a second sequence while the first residual stands.

`applyGroupRecords` in `packages/crypto` performs exactly this replay for one group, with vectors for honest sequences and for replayed, reordered, omitted, stale and unsigned records, so independent verifiers agree (T-36).

`packages/crypto` decodes both records, computes both digests, counts a record's valid seats and replays a group (`group-registry.ts`), for the verifier and for the signing service; the contract and that code are checked against the same vectors.

**No member is linked to a poll.** The registry takes no election identifier, definition or nullifier, and an addition names only a group, a position and commitments. An election names a group and a root, never a member; a ballot proves membership in zero knowledge and carries a nullifier unrelated to the commitment ([[membership]], Scope). So nothing on chain joins a member to the polls they vote in (T-12, T-13). When a commitment is added is public, to about the registration period of the batch that added it ([[registration]], The batch); T-13 records that residual.

### Vectors

`vectors/group-registry.json` (format `abolish-group-registry-vectors/1`, see [[vectors/README|vectors]]), printed by `packages/crypto/scripts/group-registry-vectors.py`, an implementation written from this page and the EIP-712 and secp256k1 standards with Python's standard library only, gives: the domain separator and type hashes; addition and removal records with their digests, signed by fixed test keys, and each approval's recovered signer; records each check refuses; and the forbidden commitments. TypeScript (`packages/crypto`) and Solidity (`packages/contracts`) tests both consume it.

`Poseidon2(0, 1)` can't be computed by the generator, which has no Poseidon: the value was computed with `poseidon-lite` 0.3.0 (circomlib's constants), which in the same run gave circomlib's published `Poseidon2(1, 2) = 0x115cc0f5…189a` and the tier tree's `Z_1 = Poseidon2(0, 0)`. P1-17b's Poseidon, built from circomlib's parameters, MUST check this value.

### Known-weak

- **Tier 0 is the registrars' word** (T-06, not mitigated): any `t` registrars can add any commitments. What this registry adds is that each addition is attributable to `t` named keys, that no one else (no relay, no single registrar) can add, replay or reorder one, that L2 governance rewriting the history to do so is detected by every verifier (Verification; dropping the latest additions, or any removal, isn't), and that group sizes are public.
- **The quorum is held online.** Tier 0 registration is automatic (one Turnstile solve per registration and no account, [[registration]]), so the signing service holds `t` registrar keys hot, and seizing it is seizing Tier 0 additions (T-69). Hardware-held keys would need a person per registration.
- **The registrars can't rotate.** A lost or compromised key means a new registry, and every member registers again in its new groups. That is the cost of a set a verifier can check without the Safe's history.
- **Duplicates are the signing path's to refuse** (Additions): a repeated commitment overstates `group_size` by one.
- **Tiers 1 and 2 have no addition path yet** (P3-3, P3-4), and no registry may be deployed until they do.
- **No paymaster yet.** [[0004-l2-choice]] sponsors registration through our own ERC-4337 paymaster (P3-2 part 4c); until then whoever submits an addition pays its gas.
- **Gas.** In the tests, adding one member with two of three approvals costs about 67,000 gas beyond the transaction's base cost and calldata, each further commitment in the same batch about 1,500, and a batch of 256 about 430,000: two `ecrecover` calls, the keccak hashes of the digest, the storage write and the accumulator step. Removing one member costs about 85,000, mostly its first write to the removed-index bitmap.

## Board (direct submit)

Threats: T-25 (a ballot or delivery record kept off the board), T-05 (an unsound proof check), T-31 (two readings of one proof), T-17 (chosen bytes in the archive), T-52 (input that costs others work). Decided by [[0028-board-contract-checks]].

The `board` contract on L2 is the direct-submit path: anyone submits a ballot there, bypassing our servers ([[0004-l2-choice]]), and every share receipt, complaint and posting has its contract path there ([[delivery]], Direct submit). It is immutable, inherits the event accumulator above, and emits its events as contract-event records ([[0025-contract-event-evidence]]). It is specified and built in parts of P1-18 part 4b-3 ([[0028-board-contract-checks]], Consequences): the membership check and the ballot check below, the parameters they read from the election registry (Election registry, Parameters), the registered key set the trustee registry records (Trustee registry, Registration), which gives the ballot check its qualified seats and the delivery paths their signing keys, the contract's deployment, delivery checks, calls and events (4b-3d-1), and the contract-event record's version 2, which archives its events (4b-3d-2; Contract-event record, Event tables (version 2)). The close rule (part 4c) follows, and no board may be deployed before it is specified here and built.

### Membership proofs

The board accepts a ballot only if its membership proof verifies ([[membership]], Owned elsewhere), so non-members can't post at all, and it accepts exactly the proofs [[membership]] (Proof encoding, Verification) accepts, so the contract and the verifier never disagree about one (T-31; [[verifier]], Principles). `MembershipProofLib` (`packages/contracts`) checks a proof `A ‖ B ‖ C` against signals `[ρ, ν, m̂, ŝ]` in this order, and the first failure is its verdict:

| Verdict          | When                                                                                                                                                                                                                 |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `truncated`      | The proof is shorter than 256 bytes (at offset 0)                                                                                                                                                                    |
| `trailing-bytes` | It is longer (at offset 256)                                                                                                                                                                                         |
| `non-canonical`  | At offset 0 or 192: `A` or `C` has a coordinate at or above `p`, is the identity (both coordinates 0), or isn't on `y² = x³ + 3`. At offset 64: `B` has a coordinate at or above `p` or is the identity (all four 0) |
| `signal`         | A signal is at or above `r`. Signals are never reduced                                                                                                                                                               |
| `root`           | `ρ = 0`, which any secret can prove membership of ([[membership]], Statement)                                                                                                                                        |
| `non-canonical`  | At offset 64: `B` isn't on the twist or isn't in the order-`r` subgroup, which only `ecPairing` checks (below), so it is reported after `signal` and `root`                                                          |
| `pairing`        | Groth16's equation fails                                                                                                                                                                                             |

The equation is [[membership]]'s, under the pinned depth-32 key, which the contract holds as constants (the 768-byte `vk` of [[membership]], Verification key; a test compares it and its hash with `vectors/membership-proof.json`), never an input, a depth or another contract's key. It computes `L = IC_0 + ρ·IC_1 + ν·IC_2 + m̂·IC_3 + ŝ·IC_4` with the `ecMul` and `ecAdd` precompiles (EIP-196) and checks `e(−A, B) · e(α, β) · e(L, γ) · e(C, δ) = 1` with one `ecPairing` call of four pairs (EIP-197), in the precompiles' encoding, which is the proof's. `ecPairing` fails on a G2 point that isn't on the twist or isn't in the order-`r` subgroup; every other input is a valid point by then, so a failed call is `B`'s `non-canonical`. A failed precompile call consumes all the gas it was given, so the pairing is given exactly 600,000 gas, over three times what four pairs cost under EIP-1108 (181,000), and the check reverts unless that much is available (with the 1/64 a call keeps back, EIP-150): a call that ran out of gas never reads as a broken `B`. The whole check costs about 200,000 gas, but needs about 620,000 available to run; every decode failure except `B`'s twist and subgroup check is found before any precompile runs. The cap is a trade-off: a successful call consumes only the pairing's price, so a larger cap costs nothing but gas limit, which a forced deposit buys on L1 ([[0004-l2-choice]], Forced-deposit limits), and a smaller one sooner fails every proof after a repricing (Known-weak).

The signals come from the definition the registry recorded and from the ballot itself, never from the submitter: `ρ` is the tier's (or cell's) root, `ŝ = F(S)` with `S = H(DS("abolish/v1/nullifier-scope", definition_hash ‖ u8(tier) ‖ encode(root)))` computed on chain, refusing a tier other than 0, 1 or 2, a root of 0 and a root at or above `r`, in that order ([[membership]], Scope), and `m̂ = F(M)` with `M` from [[revoting]] (Message), `F(x) = int(keccak256(x)) >> 8` ([[membership]], Field mapping). Proofs are malleable, so nothing compares proof bytes to detect a repeat (T-38).

### Ballots

The board accepts a ballot record (`0x0002`) only if it passes every admission check of [[ballot-validity]] that needs no ristretto255 arithmetic ([[0028-board-contract-checks]], 3B), so a non-member can't post, and a member's record carries chosen bytes only where the contract can't look (T-25, T-17, T-52). `BallotCheckLib.check(record, registry, qualified)` (`packages/contracts`) takes the record, the election registry, which the board pins, and the registered key set's seats; it reads the election's parameters from the registry by the record's `definition_hash` (Election registry, Parameters) and nothing about the election from the submitter. It runs these steps in order and reverts on the first failure, with a decode error and its offset ([[notation]]) or an admission code:

1. **Header.** A record shorter than its 2-byte type is `truncated` at 0, and one ending after a valid type is `truncated` at 2. A record type other than `0x0002` is `unexpected-record-type` if [[versioning]] lists it (`0x0001` to `0x0014` when the board is built, which it can't learn past), and `unknown-record-type` otherwise, both at 0.
2. **The election.** `definition_hash` at offset 3 (`truncated` if the record ends first). If the registry recorded no parameters for it (`ballot_version` 0), `ballot-stray`: the election is found first, since the version a record must have is the one its election pins.
3. **The version.** A version other than the one the election pins is `profile-mismatch` at 2, checked before whether the version is known, as [[notation]] (Strict decoding) orders it; a pinned version other than 1, 2 or 3 is `unknown-version` at 2, so a profile the board can't read admits no ballot.
4. **The fixed fields.** Version 1's `tier` above 2 is `invalid-enum` at 35 (versions 2 and 3 take any `u8` as `cell`); `nullifier` at or above `r` is `non-canonical` at 36; a record ending before the committed vote is `truncated` at the field it ends in, the proof's at 108. The proof's points are decoded in step 9.
5. **The committed vote**, framed strictly at 364 under the record's version ([[ballot-validity]], Committed vote; Committed vote (version 3)), left to right: each count above its maximum is `length-over-max` at the count, before anything it counts is read (T-52); each `element` is `non-canonical` at its offset unless its 32 bytes, read little-endian, are a value `s` with `0 < s < 2²⁵⁵ − 19` and `s` even, which is RFC 9496 §4.3.1's canonical and non-negative checks and the identity's refusal; each `scalar` is `non-canonical` unless below `ℓ`; a record ending inside a field is `truncated` at that field; bytes after the last field are `trailing-bytes`. Whether an element decodes to a point (a square root in that field, then the sign of `x·y` and `y ≠ 0`) is the verifier's (Residuals below).
6. **`ballot-tier` or `ballot-cell`.** Version 1 names a tier: it must be the tier of exactly one cell of the registry's `cellTiers`, which is that cell; a tier no cell has, or several have, is `ballot-tier`. A definition that splits a tier into cells pins ballot version 2 or 3 by [[verifier]] 2.3's `profile-combination`, which the registry doesn't yet refuse, so refusing such a ballot refuses nothing honest. Versions 2 and 3 name a cell, `ballot-cell` unless it is below `cell_count`. The cell's tier and root come from `cell(definition_hash, c)`.
7. **`validity-shape`** against the parameters: `T` options of exactly `k` commitments each, `n` share hashes, `T` option proofs, and, under ballot versions 1 and 2, one sum proof of `max − min + 1` branches for the one question (parameters with several questions fit no version-1 or version-2 shape), or under version 3 one range proof per question with its question's `max_q − min_q + 1` branches.
8. **`share-hash-unqualified`**: a seat from 1 to `n` outside `qualified` whose share hash isn't 32 zero bytes. `qualified` is the seats of the registered key set the trustee registry records for the election's stub and panel (Trustee registry, Registration; [[0028-board-contract-checks]], 2B), as `keySetOf` returns them; the library takes it as an input, which the board reads from the trustee registry (Calls).
9. **`membership-proof`**: `ballot_hash` from the record ([[ballot-validity]], Ballot hash; Hashes (version 3)), `M` from it, the definition hash, the cell's tier and the record's L1 reference ([[revoting]], Message), and Membership proofs above with `[ρ, ν, m̂, ŝ]` the cell's root, the record's `nullifier`, `F(M)` and the scope of the cell's tier and root. A proof whose `A`, `B` or `C` is broken is `non-canonical` at 108, 172 or 300 (a `B` off the twist or outside its subgroup is found only by the pairing); any other failure, and a cell root of 0, which anyone can prove membership of, is `membership-proof`.

An admitted ballot gives its `definition_hash`, version, cell, tier, `nullifier`, `ballot_hash` and `M`, which the board's event uses (Events).

**What it leaves out.** The validity proofs (`option-proof`, `sum-proof`) need ristretto255 arithmetic and are checked by the verifier alone; so is the rest of an element's decoding (step 5) and the L1 reference ([[revoting]], Owned elsewhere), which a contract on L2 can't check. A record that passes here and fails any of them is boarded as a rejected entry ([[verifier]], Principles): it counts nothing and fails no election (T-53). So the board refuses only records the verifier rejects, never an honest ballot (T-25), and its order differs from [[ballot-validity]]'s only in finding the election before the version and the proof's points last, which changes no verdict, since the board refuses on any failure.

**Gas.** Checking a ballot of three options at `k = 2` and `n = 3` costs about 272,000 gas, most of it the membership check; framing grows with the committed vote, about 400,000 gas for the 16.8 KB vote of 32 two-option questions at `k = 2` (about 700 gas per element or scalar framed, so about a million at `MAX_OPTIONS` and `MAX_TRUSTEES`, about 1,400 of them), plus the record's calldata.

### Deployment

The board pins the election registry and the trustee registry at construction, as immutables, and reverts its deployment unless both addresses are non-zero, distinct and not its own. It reads every election's parameters, ceremony and key set from these two alone, never from a caller ([[0028-board-contract-checks]], 1C and 2B). The registry pins the board in turn (Election registry, Deployment), so the three addresses are fixed before any is deployed, from the deployer's nonces or by CREATE2 ([[0028-board-contract-checks]], Consequences). The two addresses are immutables, which [[verifier]] 1.2 MUST mask and compare with the definition's `election_registry` and `trustee_registry`, as it does the group registry's immutables, so a board pinning other registries never verifies (T-64); the definition's `chain` rule names all three. It has no admin, owner, pause or upgrade path, and holds no funds.

### Delivery records

The board takes a share receipt (`0x000c`), share posting (`0x000d`) or share complaint (`0x000e`) for any election its registry registered, as [[delivery]] (Direct submit) requires, checking only what needs no ML-KEM or ristretto255 arithmetic ([[0028-board-contract-checks]], 3B). `DeliveryCheckLib` (`packages/contracts`) runs these steps in order and reverts on the first failure, naming the record's position in its call, with a decode error and its offset ([[notation]]) or one of the codes below:

1. **Header.** As the ballot check's step 1, with the call's type in place of `0x0002`: a record of another type that [[versioning]] lists is `unexpected-record-type`, any other `unknown-record-type`, both at 0.
2. **The election.** `definition_hash` at offset 3. If the registry recorded no parameters for it (`ballot_version` 0), `delivery-stray`.
3. **The version.** Ballot versions 1 to 3 fix every delivery type at version 1 ([[delivery]], Versions). If the election pins a ballot version above 3, which the board can't read, the record is `unknown-version` at 2; otherwise a version other than 1 is `profile-mismatch` at 2.
4. **The fields**, framed strictly ([[delivery]], Records): a record ending inside a field is `truncated` at that field, and bytes after the last are `trailing-bytes`. Each `element` (a complaint's `D`, a posting's `ct_dh`) is framed as the ballot check's step 5 frames one, each `scalar` (a complaint's `c` and `z`, a posting's `pok_c` and `pok_z`) is below `ℓ`, each `p256-sig` has `1 ≤ r < n` and `1 ≤ s ≤ (n − 1) / 2` ([[trustee-identity]], Signatures), else `non-canonical` at the field; a posting's `sealed` longer than 4,116 bytes is `length-over-max` at its count, before anything it counts is read (T-52), and one whose bytes end early is `truncated` after its count, where its bytes start, as `packages/crypto` reads every `bytes<M>`.
5. **`delivery-seat`**: `seat` is a seat of the registered key set that `keySetOf(stub_hash, panel_id)` returns for the election's `ceremony(definition_hash)` (Election registry, Parameters). Seat 0 fails whatever the set says, and so does any seat outside it.
6. **`delivery-signature`** (receipts and complaints): the signature verifies under the seat's registered per-election signing key, `signingKeyOf(stub_hash, panel_id, seat)`, never its identity key ([[trustee-identity]], Which key signs what), over `m` under `abolish/v1/sig/share-receipt` (the 97 bytes before the signature) or `abolish/v1/sig/share-complaint` (the 161 bytes before it), with the digest computed on chain as [[trustee-identity]] (On chain) requires.
7. **A posting's ballot.** `posting-length`: `sealed` is `4 + 64 · T + 16` bytes for the election's `option_count` `T` ([[share-encryption]], Ciphertext), so its length is fixed. Then the ballot record the call carries passes the whole ballot check (Ballots), membership proof included, with `qualified` the key set of the election it names, with that check's errors; `posting-ballot`: its `definition_hash` is the posting's, and its `ballot_hash` (Ballots, step 9) is the posting's (the ballot hash binds the ballot's definition, never the posting's own field, so both are compared, or the seat, key set and length above would be judged against another election than the ballot's); `posting-hash`: `H(DS("abolish/v1/share-ciphertext", ct))` over the posting's `ciphertext` as encoded equals the ballot's `share_hashes[seat]`, which exists, since the ballot passed `validity-shape` and the seat is a key-set seat (a seat beyond the ballot's share count fails all the same).

So only a registered seat can put a receipt or complaint on the contract path, and a posting carries only `m`, which the board can't check, and the ciphertext that a ballot passing the ballot check committed to, so only a member can choose a posting's ciphertext. What each can still choose is listed under Known-weak (T-17). What the board leaves out is everything [[delivery]] says it can't check: whether a receipt's `share_hash` is the ballot's, whether a posting passes the public check, whether a complaint is proven, and whether a record is in time. The delivery check reads every accepted record as it reads the record itself ([[delivery]], Delivery check), so one that fails it is ignored, and none ever blocks a passing one: the board accepts any number per seat and ballot (Calls).

A posting's ballot is checked, never admitted: it isn't emitted, and it counts only if its own ballot entry or direct submission is admitted ([[delivery]], Direct submit). It passes the whole ballot check because a ballot only framed would let anyone make one up, with no options and one share hash of a ciphertext of their choosing, and archive that ciphertext, over a kilobyte of chosen bytes per posting, as a posting (T-17, T-52). Every ballot a client casts passes the check, whatever path it took, since the check refuses only what the verifier rejects (Ballots), so no honest posting is refused (T-25). The call carries the whole ballot record, so a client posts with the record it cast; nothing of the ballot reaches the archive. The check costs the poster about 250,000 more gas, mostly the membership proof.

### Calls

Each call takes canonical calldata only: exactly the standard ABI encoding of its `bytes` arguments, every offset the one `abi.encode` writes, zero padding and nothing after (`CanonicalCalldata`), so a transaction carries no bytes the records don't define (T-17). A call accepts every record it is given or reverts whole.

| Call                                         | Accepts                                                                                                                                                                                                                    |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `submitBallot(bytes record)`                 | A ballot record that passes Ballots, with `qualified` the seats of `keySetOf(ceremony(definition_hash))`, read before the check (zero for a record too short to name an election, which its header refuses first).         |
| `submitReceipts(bytes receipts)`             | One or more share receipts, concatenated: each is 164 bytes, so the argument's length must be a non-zero multiple of 164 (`ReceiptBatchLength` otherwise), and each passes Delivery records, named by its position from 0. |
| `submitPosting(bytes posting, bytes ballot)` | A share posting that passes Delivery records against the ballot record `ballot`.                                                                                                                                           |
| `submitComplaint(bytes record)`              | A share complaint that passes Delivery records.                                                                                                                                                                            |

**Repeats.** A record byte-identical to one the board already accepted, by any call, is accepted again as a no-op: the call succeeds, checks nothing and emits nothing ([[0028-board-contract-checks]], Consequences). So a client's retry never reads as a failure, and nothing is archived twice (T-17, T-52). Any other record that passes is accepted, however many the board holds for the same seat, ballot hash or nullifier: a different encoding of the same ballot (proofs are malleable, T-38), a re-vote, a second receipt or posting for a seat, or junk signed by a registered seat. No record occupies a slot, so neither an operator nor a seat that signs junk can stop the honest record that follows ([[delivery]], Direct submit; T-25, T-54). A posting's repeat is the posting's bytes alone, whatever ballot record carries it. The board remembers each accepted record by the keccak-256 of its bytes, a storage key nothing outside the contract recomputes, never a protocol hash; records begin with their type, so no two types' records share one. A record is remembered only once it is accepted, so a repeat is always a record that passed.

The board doesn't check time: a record it accepts is boarded as a contract event, late or not, and is in time by its submission time ([[delivery]], Windows; [[verifier]] 4.4). The close rule (part 4c) bounds when it takes ballots. Who pays is never checked or recorded: a voter's client pays from a fresh, privately funded address or through a relay ([[delivery]], Direct submit; T-11, T-13).

### Events

Each event goes through the event accumulator, with topic 0 the keccak-256 of its signature, and carries its record whole as `bytes`, so the delivery check and [[verifier]] 5 read the event as the record itself ([[delivery]], Direct submit):

| Event                                                                                               | Topics                                                                             | Data                                         |
| --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------------- |
| `BallotSubmitted(bytes32 indexed definitionHash, bytes32 indexed ballotHash, bytes record)`         | The record's `definition_hash` and its `ballot_hash`, recomputed (Ballots, step 9) | The ballot record, ABI-encoded               |
| `ShareReceiptSubmitted(bytes32 indexed definitionHash, bytes32 indexed ballotHash, bytes record)`   | The record's `definition_hash` and `ballot_hash`                                   | The share receipt (164 bytes), ABI-encoded   |
| `SharePosted(bytes32 indexed definitionHash, bytes32 indexed ballotHash, bytes record)`             | The record's `definition_hash` and `ballot_hash`                                   | The share posting, ABI-encoded               |
| `ShareComplaintSubmitted(bytes32 indexed definitionHash, bytes32 indexed ballotHash, bytes record)` | The record's `definition_hash` and `ballot_hash`                                   | The share complaint (228 bytes), ABI-encoded |

The topics repeat what the record says, so a reader can find an election's records by topic; the record decides, and a record whose topic disagrees with its bytes fails the contract-event record's version-2 check (`event-data`), so 4.4 fails against the deployment (Contract-event record, What the board frames). Every record an event carries passed the board's checks; none is a ballot entry or a board-path record, and none counts until the verifier's own checks pass. The board's sequence is shared by every election its registry creates, as the registry's is (Election registry, The shared event sequence): a verifier replays it whole and requires board entries only for the events that name its election.

### Vectors

`packages/contracts` runs every proof and decode vector of `vectors/membership-proof.json` through `MembershipProofLib` (each gets the spec's verdict, and each broken point its offset), its field mappings, and every scope and `F` vector of `vectors/membership.json`, including the three rejected scopes. It also checks `A.y + p`, `C.y + p` and a `C` off the curve at their offsets, and runs under the `osaka` EVM as well as `cancun`. Fuzz tests: no one-bit change to an honest proof, no other value of one signal, and no arbitrary input passes, and none reverts.

The ballot check runs every record of `vectors/ballot.json` and `vectors/ballot-v2.json` against parameters taken from the file's own election (its definition's panel, question and ballot pin, its tiers' or cells' roots), with its listed key set: each admitted ballot gives the file's `ballot_hash`, `M` and tier, a ballot the verifier rejects only at `option-proof` or `sum-proof` is admitted, and every other gets the file's code; every decode rejection gets its code at its offset, except that `0x000c` is a type the board knows (`unexpected-record-type`, where the file, which knows only `0x0002`, says unknown). Every committed vote of `vectors/ballot-validity.json` and `vectors/ballot-v3.json` frames and has the file's shape verdict, each version-3 vote's ballot hash is the file's, and each codec rejection of a committed vote is refused with its code (and, for version 3, its offset). A test runs it against a real election registry, and the tests run under the `osaka` EVM as well as `cancun`. Fuzz tests: no one-byte change to an honest record and no arbitrary record, or arbitrary body after an honest header, is admitted, and every refusal is one of the library's two errors.

`test/Board.t.sol` runs every ballot of `vectors/ballot.json` through `submitBallot` under its file-listed key set, read through the ceremony, and every delivery record of `vectors/delivery.json`'s elections through the contract path (each posting with the ballot record it binds, built from the file's ballot and checked against its `ballot_hash`), against stubs set from those files' elections and key sets. Each delivery decode rejection of `vectors/delivery.json` gets its code at the offset the layouts above give, except that a receipt one byte short or long, or a complaint sent as a receipt, fails the batch's length first (`ReceiptBatchLength`). Every receipt check of `vectors/share-receipt.json` is accepted exactly when the file says it verifies. Each refusal code and the checking order have tests, as do a byte-identical repeat in and across calls emitting nothing, a failing receipt reverting its whole batch, canonical calldata on every call, each event's exact topics, data and accumulator step, and the board reading a real election registry's ceremony and a real trustee registry's key set and signing keys; the tests run under the `osaka` EVM, where P-256 goes through its precompile, as well as `cancun`. Fuzz tests: no arbitrary input to any call is accepted, every refusal is one of the board's errors, and no one-byte change to an honest receipt or complaint, or to a posting outside `m`, is accepted. An invariant suite (`test/invariant/Board.invariant.t.sol`) interleaves honest, repeated, changed and mixed submissions of every type and holds that the event count is the number of distinct records accepted, that every emitted record passes its check again and is emitted once, that a refused record is never remembered, and that accepting one record never makes another passing record fail (T-25, T-54).

**Gas** (measured from the caller under `cancun`, where OpenZeppelin's `P256` falls back to Solidity, including calldata, the record's storage key and the accumulator step): a ballot of three options at `k = 2` and `n = 3` about 393,000; one share receipt about 343,000 and three in one batch about 950,000; a complaint about 342,000; a posting at three options, with its ballot's check, about 422,000 (the tests mock the pairing for postings, since no vector pairs a real membership proof with ciphertexts, and add its measured cost, about 183,000); a byte-identical repeat about 29,000. On an L2 with the `P256VERIFY` precompile a receipt or complaint costs about 120,000.

### Known-weak

- **A pairing repriced above 600,000 gas** for four pairs would make every proof fail as `non-canonical`, and the immutable board would need replacing. `ecPairing` has only been repriced downwards (EIP-1108), but other precompiles have gone up (EIP-7883 raised `ModExp`), which is why the cap is over three times today's price.
- **What a member's direct submission can still carry.** Through the contract path the archive keeps records the verifier rejects, so the fields the ballot check can't judge are free to a member with a valid membership proof: the L1 reference (40 bytes), each validity-proof scalar below `ℓ` (about 252 bits, 64 bytes per option and per branch), and the VSS commitments as any even values below `2²⁵⁵ − 19` (about 254 bits each, `32 · k · T` bytes), against random-looking bytes on the board path (T-17; [[ballot-validity]], Residuals).
- **`qualified` is an input** to the library: the board MUST take it from the trustee registry's `keySetOf`, never from a submitter, or a submitter could name the seats whose share hashes it fills.
- **Contract-path receipts and complaints carry their seat's chosen fields.** The board path refuses a receipt for a ballot not on the board, or whose `share_hash` isn't the ballot's ([[delivery]], Boarding, rules 2 and 4); the contract can't see the board, so a registered seat can archive a receipt with any `ballot_hash` and `share_hash` (64 chosen bytes), or a complaint with any `ballot_hash` and an unchecked `D`, as often as it pays for, each attributed to its seat by its signature (T-17, T-52). The delivery check ignores every such record.
- **Anyone who saw a ciphertext can post junk.** A posting's `m` is free (32 bytes), and the board accepts any number of postings per seat and ballot, so whoever saw `ct_i` and its ballot (in the voter's pending transaction, or on the board) can archive 32 chosen bytes per posting, each with about 1.5 to 5.4 KB of calldata and a ballot check to pay for (T-17, T-52). Refusing them would let a junk posting occupy the voter's slot ([[delivery]], Direct submit), so the verifier ignores them instead (`posting-encapsulation`).
- **A member can post chosen ciphertexts.** A member can make up a ballot that passes the board's check (its validity proofs and elements unchecked, Ballots, What it leaves out) whose share hashes commit to ciphertexts of its choosing, never submit it, and post each: `n` ciphertexts of about 1.2 to 5.4 KB of chosen bytes per ballot made up, any number of ballots, each costing a membership proof's check and the postings' gas (T-17, T-52). The archive keeps them, and the delivery check ignores postings for a ballot not on the board. Requiring the ballot to be on the board first would need the contract to see the board, which it can't, or every posting's ballot to be direct-submitted as well, which archives it twice; the member can already put about as many chosen bytes in its own ballots (the item before).
- **Nothing bounds a call's batch or count but gas.** A trustee node's receipts are bounded by what it owes ([[delivery]], What a node owes); everything else on the contract path, a member's re-votes included, is bounded only by what its sender pays, as [[delivery]] accepts. Every accepted record is archived and replayed by every verifier of every election through the board (The shared event sequence above; T-52).
- **The board's events are archived only under contract-event version 2.** Version 1 names none (Contract-event record, Event tables), and the election registry doesn't yet refuse a profile pinning it (Contract-event record, Known-weak).
- **Soundness rests on the L2's precompiles**: a bug in its `ecPairing`, or one that skips G2's subgroup check, would admit forged proofs on chain, though never past the verifier, which checks every proof with `@noble/curves` ([[membership]], Verification; T-05, T-71). The vectors include a `B` outside the subgroup, so a test run against an EVM that skips the check fails.

## Board anchor

Threats: T-23 (board tampering), T-24 (equivocation), T-52 (front-running an election's anchor), T-53 (discreditation), T-49 and T-50 (outages and censorship that miss a deadline, and finding the archive once our domain and hosting are gone), T-51 (data loss), T-17 (chosen bytes on L1), T-69 (a compelled or seized anchoring key), T-26 (unprovable drops: receipt keys fixed before voting).

The board anchor is our one contract on L1. It records, once per election and segment, the hash of the board's checkpoint after that segment ([[board]], Segments and checkpoints), and publishes the checkpoint itself in the same log, so every checkpoint is attributable to its election and segment from L1 alone. Each call may also carry the `archiveLocator` [[0005-permanent-archive]] requires (Archive objects and how they are found), so the archive is found from L1 alone. It also keeps the record of receipt keys that [[0023-receipt-evidence]] requires (Receipt keys, below), so the keys that judge an election's receipts are the same authority's. It is immutable: no owner, proxy, pause or upgrade path. Its clock and its anchoring authority are fixed at deployment as immutables, which solc writes into the runtime code. A verifier release pins the anchor's address together with its `epoch`, `period`, `deadline` and `authority`; [[verifier]] 1.2 compares the runtime code with the release build with the immutables' byte ranges masked, and requires the masked words to equal those pinned values, so the clock a verifier applies is the deployed one, read from code, never from a call. The definition's `l1_anchor` names it.

### Deployment

The anchor is deployed with the anchoring clock of [[board]], Timing, and the address of the anchoring authority, all immutable:

| Value       | Deployed value            | Meaning                                                                                                                                                                           |
| ----------- | ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `epoch`     | a whole hour, in L1 time  | The start of period 0. The L2 registry carries the same value (Election registry, Deployment).                                                                                    |
| `period`    | 3,600 seconds             | Hourly anchoring, as the brief sets.                                                                                                                                              |
| `deadline`  | 43,200 seconds (12 hours) | How long after a period ends its checkpoint may still be anchored.                                                                                                                |
| `authority` | our Safe on L1            | The only account that can anchor. Version-1 definitions bind no authority of their own ([[election-definition]], The seal), so this is the authority [[board]], Anchoring, means. |

Deployment reverts if `period` is 0, or if `authority` has no code or only an [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702) delegation (`0xef0100 ‖ address`): both are a single key. Code doesn't prove a multisig (a 1-of-1 Safe passes), so the deployment record (`packages/contracts/deployments/<chain-id>.json`) names the Safe, its owners and its threshold at deployment. A Safe's owners and threshold can change afterwards; nothing here pins them over time (Known-weak). Because the clock is in the anchor, never in a definition, no one can choose a deadline after seeing a board (T-24, T-53).

**Why 12 hours.** [[board]], Residuals, asks P4-1 to justify the deadline against two costs. A missed deadline fails the election permanently (T-49, T-50, T-53): 12 hours covers an overnight outage of the anchoring service before anyone is paged, a fee spike that prices out a few hourly attempts, a Safe signer offline for part of a day, and L1 censorship far longer than Ethereum's observed inclusion delays, with twelve hourly retries from independent runners inside the window. It assumes the custody P4-1 part 2 sets up: hourly anchoring is unattended, so each runner holds a signer key online, and the Safe's threshold is met by runners on independent hosting (T-69, Known-weak). The fork window it opens is bounded the other way: a voter's client can check a receipt against its segment's checkpoint as soon as it is anchored (the anchor admits no second one), and completes [[board]] client rule 2, which also needs every earlier segment's checkpoint, after its segment's deadline, at most `period + deadline` (13 hours) after casting; and a closed election is verifiable at most 12 hours after its seal's period ends. Elections run for days, so a same-day confirmation is enough, and anchoring runs hourly regardless: the deadline is the bound on a failure, not the normal delay. A shorter deadline would make one bad night fail an election; a longer one would let a voter's receipt stay unconfirmed into the next day.

### Anchoring

`anchor(bytes checkpoints, bytes locator)` takes zero or more checkpoints, each `encode(checkpoint)` of [[board]] (checkpoint version 2, 180 bytes: `election_id ‖ u32(segment) ‖ u64(size) ‖ head ‖ root ‖ object_cid ‖ hashes_cid`; [[0029-board-data-availability]]), concatenated, so one transaction can carry several elections' checkpoints, and an archive locator, possibly empty (Archive locator, below). The call reverts, anchoring nothing, unless:

1. the caller is `authority` (T-52: no one else can front-run an election's checkpoint with a bogus one);
2. the calldata is exactly the ABI encoding of the two `bytes` arguments (offsets `0x40` and `0x60 + pad32(len(checkpoints))`, tails in that order, zero padding, nothing after the second), the call carries a checkpoint or a locator, `checkpoints` is a multiple of 180 bytes, every checkpoint's `object_cid` and `hashes_cid` start `0x01 ‖ codec ‖ 0x12 ‖ 0x20` with `codec` `0x55` (raw) or `0x70` (dag-pb), the only CIDs [[content-addressing]] makes, so that of each CID only its 32-byte digest is the authority's choice (whether the digest names the right bytes needs the board, so that is the verifier's check, `checkpoint-cid` in [[board]], Board checks), and a non-empty `locator` is well framed (T-17);
3. every checkpoint has `size ≥ 1`: an empty board's checkpoint fails the election (`checkpoint-size`), so it is never stored;
4. for every checkpoint, `end ≤ block.timestamp ≤ end + deadline`, where `end = epoch + (segment + 1)·period` is the end of its period ([[board]], Timing);
5. no checkpoint has been stored for its election and segment, in an earlier call or earlier in this one, even an equal one. Refusing an equal one too keeps the rule a plain write-once; the job that anchors (P4-1 part 2) reads the slots first, so a batch never carries a checkpoint another runner already anchored.

For each checkpoint, in order, it stores `checkpoint_hash = H(DS("abolish/v1/board-checkpoint-2", encode(checkpoint)))` for `(election_id, segment)`, lowers the election's lowest anchored segment if `segment` is below it (or sets it, for the election's first anchor), and emits

| Event                                                                                                                                                                               | Topics                                                        | Data                                                                                          |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `CheckpointAnchored(bytes32 indexed electionId, uint32 indexed segment, bytes32 indexed checkpointHash, uint64 size, bytes32 head, bytes32 root, bytes objectCid, bytes hashesCid)` | `election_id`, `segment` as a 32-byte word, `checkpoint_hash` | `size`, `head`, `root`, `object_cid`, `hashes_cid`, ABI-encoded (each CID as 36-byte `bytes`) |

through the event accumulator (above), which the anchor inherits like every Abolish contract, with `chain_id` the L1's. After the checkpoints, a non-empty locator is logged as

| Event                                                   | Topics                      | Data                                      |
| ------------------------------------------------------- | --------------------------- | ----------------------------------------- |
| `ArchiveLocated(uint16 indexed version, bytes locator)` | `version` as a 32-byte word | the whole locator, ABI-encoded as `bytes` |

### Archive locator

[[0005-permanent-archive]] has every L1 anchor carry a generic, versioned `archiveLocator` naming the latest confirmed archive manifest, with no storage scheme fixed in the contract, so the archive can change without a redeploy. The anchor frames it and doesn't interpret it: `locator = u16(version) ‖ body`, with `version ≠ 0` (so a zero word never reads as a locator), a body of at least 1 byte, and at most `MAX_LOCATOR_LENGTH = 128` bytes in all, which bounds the authority's chosen bytes per locator, not in total (T-17, Known-weak). Each version's body, starting with version 1 for an Arweave manifest, is specified with the manifest by P4-3, as a fixed length per version, with vectors. A verifier ignores versions it doesn't know, reporting them ([[verifier]] 4.3), and, once P4-3 fixes each version's body length, reports a locator of the wrong length for its version.

A call may carry a locator alone, with no checkpoint, at any time: the locator isn't tied to a period. Two readings of [[0005-permanent-archive]] follow, listed under Decisions to review in STATUS:

- Its "final anchor", which waits until every manifest holding a closed election's CARs is confirmed, is a locator-only call made whenever the archive confirms. The seal's checkpoint doesn't wait for it, so a slow archive can't push the seal past its deadline, and the deadline justification above is unchanged.
- "Each L1 anchor carries" a locator: the contract allows a call without one (there is none before the first manifest confirms), but the job that anchors (P4-1 part 2) MUST include the latest confirmed locator in every call that carries checkpoints once one exists, so no anchored period lacks a locator at or after it.

The anchor also keeps the last locator and the number posted in state, so the archive is found from a storage proof alone, even once the logs that carried locators have expired from L1 history ([EIP-4444](https://eips.ethereum.org/EIPS/eip-4444)):

- the last locator is a Solidity `bytes` at slot `A + 2`: for a locator of `len ≤ 31` bytes the slot holds the bytes left-aligned with `2·len` in its lowest byte; for a longer one it holds `2·len + 1`, and the bytes start at slot `keccak256(abi.encode(A + 2))`, 32 per slot;
- the count is the word at `A + 3`.

A verifier proves both at `B`, follows the last locator to its manifest, and from there walks the manifest chain back ([[0005-permanent-archive]]), which names every confirmed manifest. Every earlier locator is in an `ArchiveLocated` log; while L1 history serves them, a verifier that wants them all replays the anchor's logs against its event accumulator ([[contracts]], Event accumulator, Verification), which covers every checkpoint of every election as well, about 100 logs an hour at 100 live elections, so the latest locator from state is the path that scales.

### Receipt keys

[[0023-receipt-evidence]] has the anchoring authority register every receipt key on L1 before any election lists it, and retire it there, so the keys that judge an election's receipts ([[election-definition]], Receipt keys) are fixed by L1 records only that authority writes, and evidence under them is attributed to it alone (T-26). The anchor keeps the record itself, so the writer is the deployment's immutable `authority` with no second contract, address or verifier pin. L2 governance can forge any sender on the L2, which is why the record is on L1 (T-71, [[0004-l2-choice]]).

`registerReceiptKey(bytes key)` and `retireReceiptKey(bytes key)` each revert unless:

1. the caller is `authority`;
2. the calldata is exactly the ABI encoding of one `bytes` argument of 33 bytes: the selector, offset `0x20`, length 33, the 33 bytes, 31 zero bytes, nothing after (T-17);
3. `key[0]` is `0x02` or `0x03`.

The contract doesn't check that `x` is on the curve, which would need a modular square root on chain: a definition can list only canonical keys ([[trustee-identity]], Identity key), so a registered non-key judges nothing, and only the authority can pay to register one. Then:

- `registerReceiptKey` reverts if the key has ever been registered, retired or not, or if its twin has: the key with the other prefix and the same `x`, which is its negation, whose secret key anyone holding the key's own also holds (so retiring a seized key also keeps its negation out); otherwise it sets the key's `registered_at` to `block.timestamp`.
- `retireReceiptKey` reverts unless the key is registered and not retired; otherwise it sets its `retired_at` to `block.timestamp`.

Nothing else writes either field and neither is ever cleared, so the record is append-only: a key is registered once, retired at most once, and never re-registered (T-69). Each emits, through the event accumulator,

| Event                                                   | Topics                       | Data                             |
| ------------------------------------------------------- | ---------------------------- | -------------------------------- |
| `ReceiptKeyRegistered(bytes32 indexed x, uint8 prefix)` | `x`, the key's last 32 bytes | `prefix` (`key[0]`), ABI-encoded |
| `ReceiptKeyRetired(bytes32 indexed x, uint8 prefix)`    | `x`                          | `prefix`                         |

The record of key `p ‖ x` is the word at `keccak256(abi.encode(x, keccak256(abi.encode(uint256(p), A + 4))))`: `registered_at` in its low 64 bits, `retired_at` in the next 64, the rest zero (Solidity's `mapping(uint8 => mapping(bytes32 => Record))` at `A + 4`, with `struct Record { uint64 registeredAt; uint64 retiredAt; }`). Zero means never registered, or not retired. A word with any of its high 128 bits set, with `retired_at` set and `registered_at` zero or above it, or with either time after the timestamp of the block it is proven at (the anchor writes `block.timestamp`), can't be written by the release code, so [[verifier]] 2.9 fails the election on it (`receipt-key-record`) rather than reading either field from it, and the client refuses to cast. A verifier proves each listed key's word with `eth_getProof` at its finalized L1 block `B`, as it proves anchors (Verification, below), never from an `eth_call` or a list of logs, and applies [[election-definition]]'s judging rule ([[verifier]] 2.9); the ballot client reads the same words before casting. The words stay in state, so they survive L1 history expiry as the anchors do.

Custody and use:

- The receipt keys themselves sit in the board server's key service ([[receipts]], Residuals); the authority's quorum only registers and retires them, so it holds no receipt key.
- The authority registers a key well before any election lists it, and retires it as soon as a leak is suspected, and every key when it rotates it, so a seized key can't be listed in a later election by a hostile creator ([[0023-receipt-evidence]]). A retirement after an election's `opens_at` changes nothing for it.
- A registration costs about 65,000 gas, its transaction's base cost included (a new storage word, the accumulator and a log), once per key, never per election.

The anchor doesn't know an election's seal ([[board]], Timing): it is computed from the definition, which lives on L2. A verifier ignores an anchor for a segment after the seal. Nor does it check that an election's checkpoints grow with their segments: with a 12-hour deadline, a later segment can be anchored before an earlier one, and [[board]], Board checks, catches an inconsistent pair from L1 alone (`checkpoint-inconsistent`).

### Verification

Rule 5 means L1 never holds two checkpoints for one election and segment, and rules 1 and 4 mean every stored one counts: it came from the authority, inside its window. So a verifier reads an election's anchors completely from state, never from a list of logs an RPC node could shorten (T-24):

- The hash for `(election_id, s)` is the word at `keccak256(abi.encode(uint256(s), keccak256(abi.encode(election_id, A))))`, where `A` is the [ERC-7201](https://eips.ethereum.org/EIPS/eip-7201) namespace `abolish.board-anchor`:

  ```
  A = keccak256(abi.encode(uint256(keccak256("abolish.board-anchor")) − 1)) & ~0xff
    = 0x16eba4501d0a9dddbfa03518d843c364be664629e6d99efb7169d8f090095b00
  ```

  Zero means none was anchored. The election's **lowest anchored segment** plus one (0 if it has no anchor) is the word at `keccak256(abi.encode(election_id, A + 1))`. An election's board carries entries from before voting opens (the ceremony transcript, the contract events of its creation and registration), so no bound derived from `opens_at` would do. The election's **first segment** `f` is the period containing `l1OriginTimestamp` of its `ElectionCreated` event, the L1 origin of the L2 block holding it, which is on its board and authenticated by the registry's accumulator, and which the verifier checks against finalized L1 and the event's L2 timestamp (Election registry, Events, The L1 origin; [[verifier]] 4.4). Every entry of an honest board is appended after creation, so none has a segment below `f`. The verifier proves the lowest-segment word, then the word for every segment from `max(lowest, f)` to the seal, all with `eth_getProof` against the state root of one finalized L1 block `B` (how it trusts L1 headers is [[verifier]]'s), and never trusts an `eth_call` answer. `B`'s timestamp is the `now` of [[board]], Board checks: proving at one block and taking `now` from a later one would read a segment anchored in between as `unanchored`, or miss a checkpoint anchored there, so two verifiers could disagree (T-36).

  An anchor for a segment below `f` doesn't count for the election: it isn't passed to [[board]], Board checks, and an entry with a segment below `f` is in no counted checkpoint's segment, so it fails `unanchored` once its window has closed. A segment from `f` up and below the lowest anchored one has no anchor, so its entries fail `unanchored` the same way. The verifier proves the `lowest` word only to take that maximum; the range is then as long as the election's board is, in hours.

  **Pre-creation anchors.** Election identifiers are predictable (`electionIdAt` is a public view of the registry's counter), so whoever holds the anchoring quorum at some moment (a compelled or seized one, T-69) could anchor checkpoints with random heads and roots for elections not yet created. Rule 5 would keep them, and once those elections run, a verifier would find a word no board matches and fail them (`checkpoint-inconsistent`): one short compulsion failing elections that didn't exist yet. Two rules stop that:

  - The `f` rule above ignores every anchor for a segment that ended before the election's L1 origin, which covers any anchor made before the creation's L1 origin block.
  - That leaves anchors made between the origin block and the creation itself, at most the L2's `max_sequencer_drift` (1,800 seconds on Base, [[0004-l2-choice]]) plus a period boundary. So a creator MUST, after its `ElectionCreated` event is final ([[contracts]], Election registry, Election identifier) and before it asks the panel for a ceremony, prove at a finalized L1 block `C` whose time is after the creation's L1 origin plus `max_sequencer_drift` that the checkpoint word is zero for every segment from `f` to the last period that ended before `C` (a handful of slots: no later segment can have been anchored by then), or, if any of them is set, abandon the identifier and create another. It checks those slots, never `lowestSegmentPlusOne`: anchors below `f` don't count, and a quorum held briefly could anchor the current segment for thousands of upcoming identifiers in one transaction, so refusing any identifier with an anchor at all would let one compulsion block every future election. An abandoned identifier gets no definition, so it holds no result. After that check, an anchor no board matches can only be made while the election exists, the residual [[board]] already states (attributable, and only while it runs).

- For each non-zero word it needs the checkpoint itself. A word equal to the hash of the checkpoint a board copy gives at that segment's boundary needs nothing more: the contract stored it only inside its window, so its `anchoredAt` for [[board]], Board checks, may be taken as the end of its period, which gives the same result as the true time (timely, and at most `now`, since the word is proven at `B`). Only a word no copy matches needs the checkpoint itself, to name it and attribute the failure. Its hash is the word, so it is authenticated by the word whatever its source, typically the `CheckpointAnchored` log that wrote it; the word, proven at `B`, already attributes it to the authority inside its window, so no receipt proof is needed ([[verifier]], Anchors from L1). So old elections stay verifiable from state and the archive, without old L1 receipts, which ordinary nodes drop under history expiry ([EIP-4444](https://eips.ethereum.org/EIPS/eip-4444)). A non-zero word that matches no checkpoint anyone can produce makes the election unverifiable ([[board]], Anchoring).

The anchor's own event accumulator gives the same completeness for its log sequence, but the per-segment words are what a verifier needs, and they need no archive replay.

### Vectors

The checkpoint hash and the window rule are the ones `vectors/board.json` already exercises: the Solidity tests hash every checkpoint there and compare it with the published `hash`, and anchor the `valid` board's checkpoints, with their CIDs, at their vector times, under the vectors' own clock.

### Known-weak

- **The anchoring authority can fail a running election** by anchoring a checkpoint no board matches, before the honest one (rule 5 then keeps it). That is attributable on L1, but nothing prevents it (T-24, T-53, T-69). A late anchor can't do it: the window closes 12 hours after each period, and no anchor lands before its period ends.
- **The quorum is held online.** Unattended hourly anchoring means the runners hold enough signer keys to meet the Safe's threshold, so seizing or compelling those runners (T-69) is seizing the quorum. The Safe protects against one leaked key and one rogue runner, not against whoever controls the runners' hosting.
- **The Safe's configuration can change after deployment**, and the anchor pins only its address. A quorum can reduce the owners or threshold, or make one key the authority without touching either: by enabling a module (which executes as the Safe with no signatures, a common way to automate jobs), setting a guard or fallback handler, or delegatecalling to replace the proxy's singleton. P4-1 part 2 MUST use no module or guard that bypasses the threshold, and the verifier's check of the Safe (owners, threshold, modules, guard, fallback handler and singleton at each anchoring block) is still to come; until then such a change is visible only in the Safe's own public transactions.
- **Pre-creation anchors depend on the creator's check.** An anchor for a not-yet-created election in the drift window before its creation counts, and fails the election if no board matches it, unless the creator ran the per-slot check above and abandoned the identifier. A creator that skips the check can lose its election to an earlier compelled quorum; nothing on L1 enforces the check, and the anchor can't see L2. An anchor made after creation but before the check also forces a discard, which costs liveness only. A creator-chosen salt in `election_id` would make identifiers unpredictable before creation and remove the check; that is a registry change (P1-18), cheap while nothing is deployed.
- **Constructor effects aren't bound.** [[verifier]] 1.2 compares runtime code only, so a deployer's own initcode can do anything a constructor can and then return the release runtime code. That covers its whole effect: storage (here checkpoint words for predictable future elections or segments past the creator's check, `lowestSegmentPlusOne`, the latest archive locator, receipt-key words; in every contract, the accumulator's genesis and count) and every log it emits. Examples: a pre-written anchor word fails an election with the blame on an authority that never anchored; a constructor-emitted `DefinitionRegistered` for a predictable future `election_id` makes verifier 2.1 find two registrations and fail that election; a `PanelPinned` or `RegistrarsPinned` log naming the pinned keys while storage holds others lets the deployer block ceremony registrations or group additions, or record ones signed by its own keys, which the verifier refuses, failing every election that names that group (`group-history`) or stub (T-25). A pre-written receipt-key word is worse than a forged failure: it registers a key the authority never registered, so receipts under a deployer-held key would yield `unanchored`, `forked` or drop verdicts attributed to the authority; attributing receipt verdicts is sound only once 1.2 passes. Apart from that, none makes a false result verify: the verifier rechecks every signature- and hash-based rule itself (approvals against its pinned panels and registrars, definition and transcript hashes, timing). But it does forge failures: while 1.2 isn't a pass, a failure that rests on contract storage or constructor logs may be the deployment's doing, so a report naming such a failure must name the unbound deployment as a possible cause, and attributing it to an authority isn't sound until 1.2 passes. The creator's check, the accumulator's Verification argument and the registries' first-event rules hold only for the release constructor. The fix binds each deployment to the release creation code plus pinned constructor arguments, never to selected slots (a pinned CREATE2 factory with the address recomputed from both, or the creation transaction's input with inclusion evidence); until it is specified and checked, 1.2 is unverifiable, and it MUST be specified before anything is deployed (T-64).
- **`f` rests on the creation's L1 origin.** `ElectionCreated` carries it, authenticated by the registry's accumulator, and the verifier checks that it names a finalized L1 block no more than `max_sequencer_drift` before the event's L2 timestamp (Election registry, Events, The L1 origin): a forged, lower `f` would let pre-creation anchors count. Within the drift a sequencer or a rewritten predeploy can still name an earlier origin, moving `f` down by at most `⌈D / period⌉` periods for the release's pinned drift `D` (one on Base), which the creator's per-slot check covers, since it starts from the same event's `f` (T-71, T-69).
- **Withheld tails and late forks** remain [[board]]'s residual until P4-3 part 2c: an authority that anchors a checkpoint extending every receipt with entries it never publishes makes the election unverifiable, not failed. Checkpoint version 2 names each segment's CIDs on L1 ([[0029-board-data-availability]]), so what was withheld is named, but only part 2c's availability attestations make withholding the ballot or counted extent fail the election (`unavailable`). The anchor only frames the CIDs; one that doesn't name its segment's bytes fails the election at the verifier (`checkpoint-cid`).
- **The authority can fail an election through its receipt keys.** Retiring a key a registered definition lists, at or before its `opens_at`, fails the election ([[verifier]] 2.9), as a bogus anchor does: attributable on L1, not prevented (T-53, T-69). A quorum seized for good can also register a key of its own, and a creator working with it can list that key and forge evidence against the authority; that authority can fail elections anyway ([[board]], Residuals).
- **Receipt keys aren't checked on the curve,** only framed: the authority can register 33 bytes of its choice per call, once per value (T-17). No definition can list one that isn't a key.
- **No checkpoint for a segment past the seal is refused on L1**: the anchor can't read the definition. Verifiers ignore it; it costs the authority gas and changes no result.
- **The authority chooses 180 bytes per checkpoint (of which the CIDs' 8 framing bytes are fixed) and up to 126 per locator**, with no limit on how many beyond gas (locator-only calls at any time, checkpoints for any identifier), that land on L1 for good, such as a checkpoint for an election that doesn't exist, or a locator body of a version no one defined (T-17). Only the authority can, and the deployment's Safe is accountable for it.
- **The latest locator in state can be overwritten** by the authority at any time, so a seized quorum can replace it with one naming a fake or empty archive. Earlier locators stay in `ArchiveLocated` logs while L1 history serves them, and the manifest chain names every earlier confirmed manifest from any genuine one; once the logs have expired, a verifier with no earlier locator or mirror is left with the overwritten one, which makes elections unverifiable, never verified (T-69, T-51).
- **A locator only names where the archive is.** A wrong or stale one can send verifiers nowhere, which makes an election unverifiable, never verified: everything found is checked against the anchored checkpoints. The manifest chain ([[0005-permanent-archive]]) gives a second path to every manifest.
- **Gas.** In the tests a call with one checkpoint costs about 89,000 gas, and each further checkpoint in the same call about 39,000: a storage write, a read of the lowest-segment word, two SHA-256 calls (the hash and the accumulator) and a log. The two CIDs of checkpoint version 2 cost about 5,000 of that per checkpoint (72 more bytes of calldata, and their framing, hashing and logging). A locator adds about 24,000 (its slots and log). An election's first anchor costs about 22,000 more, for its lowest-segment word. At 100 live elections, hourly, that is about 3.9 million gas an hour, a recurring L1 cost: on testnets it is free, and spending real funds on it is the owner's decision.
- **The deployment, the Safe and the hourly job don't exist yet** (P4-1 part 2, with the worker and a `ci:` deploy workflow for Sepolia). Until then, nothing is anchored and every board is unanchored.
