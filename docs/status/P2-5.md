- State: in progress (part 1: accounts with better-auth and passkeys, in review; part 2, Turnstile on Tier 0 actions, to follow)

- PR: #65
- Phase: Phase 2: Open polls end to end at Tier 0

## Scope

Accounts: better-auth + passkeys (accounts only), and Turnstile on Tier 0 actions.

## Plan

1. **Accounts** (this part): the account tables, better-auth configured for passkeys only, and the handler `apps/web` serves; the API refuses account credentials (T-10).
2. **Turnstile on Tier 0 actions**: server-side verification of Turnstile tokens for account sign-up and Tier 0 registration. The ballot client ships no third-party code (AGENTS.md), so where its Tier 0 actions get a token has to be worked out with P2-8; `apps/web` mounting the handler is P2-9.

## Built (part 1)

- `packages/core`:
  - migration `0004_accounts.sql` (renumbered from 0002, then 0003, after P2-10's `0002_moderation.sql` and `0003_moderation_reports.sql` merged first): `account_users`, `account_sessions`, `account_passkeys`, `account_credentials` and `account_verifications`. Checks refuse a real e-mail address, a name, a picture, a session's address or user agent, and any row in `account_credentials` (passwords and OAuth tokens). The app role has `SELECT`, `INSERT`, `UPDATE` and `DELETE`, and only `SELECT` and `DELETE` on credentials.
  - `createAccounts` (`src/accounts.ts`): better-auth 1.7.7 with the passkey plugin over the Drizzle adapter. Passkey-first sign-up with discoverable credentials; user verification required at registration and sign-in and checked server-side (the plugin doesn't check it); adding a passkey to an existing account only from a session of that account under a day old; a passkey `name` and the plugin's `context` parameter refused; a route allow-list (12 routes; better-auth's password, e-mail, social and profile routes, and renaming passkeys, are 404); 64 KiB body bound; `__Secure-abolish-account.*` cookies, host-only, `HttpOnly`, `SameSite=Strict`; the origin and CSRF checks pinned on; IP tracking and better-auth's address-keyed rate limiter off; telemetry off, and a refusal to start if `BETTER_AUTH_TELEMETRY` is set; better-auth's log lines by level only.
  - `pruneAccountVerifications(sql, now)`: deletes expired WebAuthn challenges (indexed by expiry), which anyone can create and the plugin never deletes.
  - `TABLE_CLASSES.account`, and a no-join test extended to it.
- `apps/api`: any request carrying an account cookie or an `Authorization` header is refused with 400 before anything is read.
- Threats: T-10, T-11, T-52, T-55.

## Tested (part 1)

- Against Postgres as the app role, through the handler with a software authenticator (`packages/core/tests/authenticator.ts`: ES256, "none" attestation, real CBOR and signatures): sign-up, sign-out and sign-in; a second passkey joins the signed-in account; registration and sign-in without user verification refused (and nothing created); an assertion for another origin refused; a replayed assertion refused; account deletion removes passkeys and sessions and the passkey no longer signs in; a request from another origin can't sign a session out.
- Adding a passkey: a ceremony begun signed in can't finish after sign-out (shared browser), a session over a day old can't add one, a ceremony begun signed out can't finish in another account's session, and a registration for another origin creates nothing. A passkey name and a `context` parameter are refused and appear nowhere in the database. Expired challenges are pruned and live ones kept.
- Sessions keep no address or user agent when the request carries `user-agent`, `x-forwarded-for`, `x-real-ip` and `cf-connecting-ip`, and the database refuses each kind of personal data by check constraint. Every cookie set is `__Secure-`, under the account prefix, `HttpOnly`, `SameSite=Strict` and host-only.
- Every route outside the allow-list is 404 (12 paths, both methods), every listed route exists, and oversize bodies (declared and chunked) are 413.
- The Drizzle tables match the migrated ones; the app role's grants; the owner can't insert a credential row either.
- No-join: every foreign key from or to an account table stays among them; no account column has a ballot-like name; no views; no function names tables of both classes.
- API: eight kinds of account credential refused on every route (reads, unmatched, `ballots.submit`); unrelated cookies served.
- Mutation checks, by hand: removing either user-verification check, the fresh-session check, or the hook that clears the user agent, fails a test; so does leaving better-auth's origin check at its test-runner default.

## Known-weak

- Anyone can create accounts, and with "none" attestation a scripted passkey costs microseconds: until Turnstile (part 2) and the proxy's per-address limits (P2-11), nothing bounds sign-ups or ceremony starts (T-52, T-01). `pruneAccountVerifications` has no scheduler until P2-4.
- At sign-in the passkey plugin only prefers user verification, and we require it, so a security key without a PIN is refused rather than prompted for one.
- A registration for another origin gets a 500 (SimpleWebAuthn throws and the plugin answers that with 500), not a 400; nothing is created.
- The authenticator model (AAGUID) is stored with each passkey, as the plugin does; most platform authenticators report zeros.
- Session tokens are stored as issued, so a copy of `account_sessions` can act as any signed-in user until their sessions expire (14 days, extended daily on use). better-auth has no hashed-session option.
- better-auth reads the system clock itself; session expiry isn't on an injected clock.
- The no-join checks are by name and by schema object: a join written in application code, or a renamed linking column, isn't caught by them (T-10).
- `pnpm-workspace.yaml` is owner-reviewed (CODEOWNERS), so this PR waits on the owner for the two catalog entries.
