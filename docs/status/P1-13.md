# P1-13: Challenge/spoil, receipts and re-voting

- State: in progress (part 1: re-vote rule, in review; receipts and challenge/spoil to follow)
- Branch: `claude/p1-13`
- Phase: Phase 1: Threat model, spec, crypto core, circuits, verifier, reference election (CLI only)

## Scope

Benaloh challenge/spoil, ballot receipts, and re-voting semantics (last ballot counts).

## Plan

Built in parts, each its own PR on this branch's name:

1. **Re-vote rule** (this part): [[0011-revote-rule]], [[revoting]], the membership message `M`, and selection in `packages/crypto`.
2. **Receipts** (`0x0004`): what the voter keeps (entry hash, index, chain link, the operator's signature on the size and root it was shown, the proofs of [[board]]) and the client's alarm. Needs a signature scheme for the board operator, so an ADR first.
3. **Challenge and spoil** (`0x0003`): Benaloh openings, how challenged ballots are built and placed so they can't be tied to the cast ballot ([[verifier]] 6.2, T-42, T-47). Waits for P1-12's ballot format (owner questions).

## What was built (part 1)

- [[0011-revote-rule]] (`Accepted (agent) — owner may veto`): option C. Each ballot's membership proof binds a recent L1 block by number and hash; per tier and nullifier the admitted ballot naming the highest block counts; two distinct ballots naming that block tie and count nothing. Rejected: board order (fails R3), client sequence numbers (fail R2 or R3), and C with a sequence-number tie-break (reopens the dead zone).
- [[revoting]], new spec page: `M = H(DS("abolish/v1/membership-message", definition_hash ‖ u8(tier) ‖ ballot_hash ‖ u64(l1_ref_number) ‖ l1_ref_hash))`; admission checks `l1-ref-unknown` and `l1-ref-after-close`, with unfinalized blocks pending; selection (repeats by (tier, ν, `M`), grouping, ranking, ties, no fallback, no spoiled ballots); client rules; how R1–R6 are met; residuals.
- [[verifier]] 5.3, 5.7, 6.1 updated and 5.8 added; [[membership]] Message points at `M`; `abolish/v1/membership-message` specified in [[domain-separation]]; [[versioning]]'s ballot row names the new fields.
- `packages/crypto/src/revoting.ts`: `membershipMessage`, `membershipMessageField`, `selectBallots`.
- Threat files T-33, T-38, T-45.

## Tested

- `docs/spec/vectors/revoting.json`, from an independent Python implementation (`packages/crypto/scripts/revoting-vectors.py`, hashlib plus membership-vectors.py's self-checked Keccak; selection by sorting rather than scanning): 9 messages and 2 rejections; 10 selection cases (re-vote posted before the coerced ballot, withheld coerced ballot, tie voiding the group with no fallback, a tie below the top, repeats, replay after re-vote, a repeat of a tied ballot, tiers kept apart, a mixed board) and 4 rejected inputs.
- fast-check properties (passing at `FC_NUM_RUNS=1000`): `M` changes with every input; `F(M) < 2²⁴⁸`; malformed inputs rejected; selection partitions its input with at most one selected ballot per group; what counts is unchanged when ballots move to other positions and arrive in another order (R3); a ballot naming a newer block than its group always counts (R2); a second distinct ballot on the top block voids the group with no fallback; replaying any ballot never changes what counts (R1).

## Known-weak

- Nothing verifies the L1 reference yet: the admission checks of [[verifier]] 5.8 need finalized L1 data, which the verifier reads (P1-19). The ballot record carrying the fields is P1-12's, blocked on owner questions.
- The last blocks before close stay coercible (every last-ballot-counts scheme has this window; the rule widens it by about 36 seconds), re-votes are public to anyone who knows the nullifier, and a closed election verifies only once L1 has finalized every named block ([[revoting]], Residuals).
