# @abolishus/worker

Background jobs on BullMQ, over Redis in development and CI and Dragonfly in deployment. Internal and source-only; AGPL-3.0-only. Handlers parse, call `@abolishus/core` and log; no protocol logic lives here.

## No joins (T-10)

- **Sides.** Every queue in `src/queues.ts` is a board queue, an account queue or an operational one. A board queue's data names no account, session or person; an account queue's names no ballot, nullifier, poll or election; an operational queue (upkeep such as the identity-backup prune) names neither. No job crosses sides. `tests/no-join.test.ts` checks every queue's fields against both deny-lists, so a renamed field would pass; review of each new queue still has to catch that.
- **Strict data.** Job data is a `z.strictObject`, parsed again by the worker before a handler sees it; data with a field the schema doesn't name, or a job named other than its queue's key, fails as `invalid-job-data` without being handled. Job IDs are BullMQ's counters, never derived from data.
- **Nothing kept.** A job's data, error and stack trace leave Redis as soon as it finishes (`removeOnComplete` and `removeOnFail` on the worker, so a producer can't opt out by omission). BullMQ also writes every failure's message to the queue's events stream, which those options don't clear and which keeps each job's ID, name and timestamps (up to about 10,000 events), so names are fixed to the queue's key and the worker turns any error into a `JobError` whose message is its fixed kind. Two tests fail if anything reaches a log line or any Redis key, the events stream included: one queues an account field on a board queue, the other makes a handler throw a message that quotes data.
- **Producers.** None exists yet. The first one (ballot admission) gets a helper that parses the data, forces `JOB_OPTIONS` and the job name, and refuses a custom job or deduplication ID.
- **Log.** One line per job: queue, outcome, error kind from a fixed list, duration. Never the data, the job ID or an error message, since messages can quote data. An audit finding adds the election ID and entry index, and an anchoring finding the election ID and segment, all public on the board, and no person's request leads to either.

## Keys (Dragonfly)

Every key is `abolish:{<queue>}:…`. The braces are a hash tag: BullMQ's Lua scripts touch several keys of one queue, which Dragonfly (with `--cluster_mode=emulated --lock_on_hashtags`) and Redis Cluster need in one slot, while separate queues can live on separate threads or shards. A test checks every key the worker creates.

## Tier 0 batch job

`src/tier0-chain.ts` is the batch job's chain adapter (docs/spec/registration.md, The batch): `ViemTier0Chain` reads the group registry from one L2 node at a pinned pair of finalized and latest blocks, and `checkTier0Deployment` refuses to start a job whose chain, registrars, threshold or keys aren't the registry's. Submission is passed in; through the paymaster's bundler it is P3-2 part 4d-2b-2's, and until then `main.ts` doesn't run the job. `tests/tier0.test.ts` runs it against the group registry on Anvil, so the tests need the toolchain (`.github/scripts/install-toolchain.sh`).

`src/anchor-chain.ts` is the anchoring job's chain adapter (docs/spec/contracts.md, Board anchor): `ViemAnchorChain` reads the board anchor from one L1 node at the block its `now()` pinned, refusing a node behind a block or time already read; it simulates each `anchor` call from the authority before sending it, and fails a call whose sender resolved while the anchor doesn't hold its checkpoints. `checkAnchorDeployment` refuses to start a job whose chain, clock or authority aren't the anchor's finalized ones, or whose authority is a single key. Sending is passed in; through the Safe it is P4-1 part 2b-2's. `tests/anchor-chain.test.ts` runs core's `anchorBoards` through it against the anchor on Anvil.

## Running

`vp run --filter @abolishus/worker start` (plain Node, as `apps/api`; `erasableSyntaxOnly` keeps it that way) with `DATABASE_URL` (a user granted `abolish_app`, never the owner), `REDIS_URL` and optionally `AUDIT_EVERY_MS` (at least 60000).

## Tests

`vp run --filter @abolishus/worker test` needs `TEST_DATABASE_URL` and `REDIS_URL`, and runs uncached. Each run uses its own key prefix and removes its keys afterwards.

## Decisions

- **ioredis as BullMQ's client.** BullMQ 6 takes ioredis or node-redis; ioredis is the one BullMQ's own tests pin and the one its Dragonfly guidance uses.
- **`msgpackr-extract` isn't installed** (`ignoredOptionalDependencies`). msgpackr, which BullMQ uses, loads this optional prebuilt native binary whenever it is present, install scripts or not; without it msgpackr uses its pure-JS codec. A test checks it doesn't resolve and that msgpackr's native acceleration is off.
