# P3-6: Per-tier results

- State: in progress (part 1, the verifier's per-tier results in its summary, merged in #291; part 2a, the counted set under definition version 5 (the delivery check reading ballot version 3), merged in #400; part 2b, per-question results in the report and the summary, next)
- Phase: Phase 3: Tier 2 ZK identity, Semaphore groups, indexer, per-tier results

## Scope

Per-tier results everywhere (API, web, verifier). The brief: every result is reported per tier, with the tier as a first-class layer (a tier switcher, never a footnote) with counts and scope, and tiers are never blended into one headline number. [[verifier]] 8.1 and 8.2 fix what a result carries (T-01, T-16, T-53).

## Parts

1. **The verifier's summary** (this part). `abolish-verify` already wrote each tier's `counted` and `counts` into the JSON report (`tiers`, P1-19 part 4o), but its stderr summary showed only the verdict and the failed checks. It now prints the results: one line per tier in `electorate` order, Tier 0 labelled not Sybil-resistant, each cell under a tier that has more than one, and no line that sums two tiers. The header says the figures aren't verified unless `verdict` is `verified`, so a crafted bundle's counts never read as the election's result. [[verifier]], Command line, states the format.
2. **Per question.**
   - **2a, the counted set under definition version 5** (#400): the delivery check (5.9) reads ballot version 3, so 6.3, 7.1 to 7.3 and 8.5 run there and the report carries `cells` and `tiers`, as flat option lists.
   - **2b, per question** (next): under definition versions 5 and 6 the report's `tiers` and `cells` carry each question's slice (`questionResults` in `packages/crypto`), each question with its method rendered from its limits (8.1), and the summary prints them per question; [[verifier]]'s report table gains the field.
3. **Scope: anonymity-set size and turnout** per tier and cell (8.1) and the small-count flags (8.2). Wait on 2.4's recomputation from the board's group additions (the archive replay, [[P4-3]]) and on a spec that fixes the small-count threshold.
4. **API and web.** A results route serving each tier's result from the board and the tier switcher on the poll's results page. The results pages are [[P2-9]] part 4's; this part supplies the per-tier data they show.

## Part 1

- `packages/verifier/src/cli.ts`: `summary` (now exported for its tests) appends the result lines.
- [[verifier]], Command line: the result lines' format.
- Tests (`packages/verifier/tests/cli.test.ts`): no results before the report has `tiers`; the exact lines for three tiers (Tier 0's label, a two-cell tier with its cells, a tier without counts); the not-verified header under `failed` and `unverifiable`; a cell without counts shown by its code; and a property that each tier's line carries exactly its own figures, once and in order. No vector's bundle reaches a counted tally, so the tests set `tiers` and `cells` on a real report.
- Threats: T-01 (Tier 0 labelled and never summed with another tier), T-53 (figures labelled unverified unless the verdict is verified).

## Part 2a

Nothing outside the tests counted a version-5 election: `countedChecks` returned `not-implemented` for 5.9 to 8.5 because `checkDelivery` took ballot versions 1 and 2 only. Ballot version 3 keeps version 1's delivery records and windows ([[ballot-validity]], Shares and delivery (version 3)); only the ballot hash a record names differs, version 3's covering the question range proofs.

- `packages/crypto/src/delivery.ts`: `DeliveryBallot` gains a version-3 variant (cell, nullifier, `CommittedVoteV3`), and `deliveryBallotHash` recomputes the hash a delivery record names under the ballot's own version (`ballotHashV3` for version 3), which `checkDelivery` and the verifier's close check both use, so a receipt binds the whole version-3 ballot and no other version's hash (T-38, T-41).
- `packages/verifier`: admission hands a version-3 ballot's delivery fields to the tally (`ballots.ts`), the close check recomputes its hash with `deliveryBallotHash` (`close.ts`), and `countedChecks` no longer stops at definition version 5 (`counted.ts`), so the version-1 delivery check, 6.3, the tally with the definition's questions (`tally-question-range` included) and 8.5 run there.
- [[verifier]], Counted set and tally: step 1 drops definition version 5's `not-implemented`, step 3 names ballot version 3's cell and hash, step 4 lists version 5 among the definitions whose ballots name their cell.

Tested:

- `packages/crypto/tests/delivery-v3.test.ts`: `deliveryBallotHash` equals `ballot-v3-records.json`'s ballot hash (independent Python) for every record; every seat's receipt over the version-3 hash delivers a vector ballot; one over the same ballot named in another cell, or over its fields hashed under version byte 2, delivers nothing; a version-3 ballot that failed `validity-shape` is refused.
- `packages/verifier/tests/counted-v3.test.ts`, over `verifier-ballots-v3.json`'s `admitted` case (definition version 5, independent Python) and ballots cast here with `shareVoteV3` and `proveValidityV3`: an honest election's rows; delivery order changes nothing (fast-check, R3); exclusion naming the missing seats; a receipt over the ballot under another cell or nullifier delivers nothing; board-path and contract-path windows (`delivery-late`, nothing read above `s_K`'s floor, a contract-path record waiting on 4.4); a forged signer, a void complaint and a stray record; 6.3 over version-3 hashes; the tally over the three questions passing with each cell's counts the votes cast and tier 0's derived sum, an opening over a delivery-excluded ballot failing as over another set, and a tampered option failing 7.2 at that option.
- `counted.test.ts` loses the test that definition version 5 stopped at `not-implemented`.
- Threats: T-38 and T-41 (receipts bind the version-3 ballot hash), T-25 and T-54 (a ballot missing a qualified seat's delivery isn't counted), T-29 (the tally's question range checked once counted).

Known-weak:

- The report's `cells` and `tiers` and the summary give a version-5 tally as one flat list of the poll's options, with no question boundaries (part 2b); they never join two questions, since every figure is one option's count.
- An obligation root naming the definition still leaves the rows `not-implemented`, as under every definition version that reads version-1 delivery records ([[P1-12f]]).
- The reference election's multi-question poll doesn't reach selection yet ([[P1-20]]), so this path is tested against vectors and locally cast ballots, not a run.
- No version-3 test has a proven complaint or a passing contract-path posting: both read the ballot's `vss` and share hashes through version 1's code, whose shapes `validity-shape` fixes the same way, but only receipts are exercised for version 3.

## Known-weak

- The summary prints a tier's counts as one flat list of options; under definition version 5, counted since part 2a, the questions' boundaries aren't shown (part 2b).
- No anonymity-set size, turnout or small-count flag yet (part 3).
