# Deployment record

What a ballot-client release is built for, byte for byte: the deployment record (record type `0x0020`), its strict decoding, its well-formedness rules, the Tier 0 token issuer's keys it lists from version 2 and the rules they meet across releases, the deployment hash a release record carries, and the rules a release and its deployment must meet together. [[0036-release-record]] (Recommendation, item 5) has the release bind "the deployment the client is built for", so that the client and its record can't disagree; [[release]] binds it by hash, and this page fixes what that hash commits to. Notation is from [[notation]], `H` from [[group]], origins and hosts from [[release]] (Well-formedness). Threats: T-41, T-34, T-37, T-71, T-43, T-20, T-16, T-64, T-31, T-52, T-74, T-10.

A release's client trusts nothing a server or an RPC tells it about where the deployment is: it reads the election registry at the address its build pins, never at the one a served definition names (T-34), checks ceremonies only under the panels its build pins (T-37), rebuilds a voter's cell under the registrars its build pins (T-71), and makes requests only to the origins its build lists (T-43). The deployment record is that build's pins as one record, so whoever reads a release (the verifier's 1.1, `apps/node`, the release Safe's signers, a third party) reads the same pins the client runs with, and a release that pinned another registry, panel or registrar set would have another release hash.

What this page doesn't cover:

- **The operators' deployment file.** `packages/contracts/deployments/<chain-id>.json` records each deployment for the people running it: besides everything here, who holds each registrar key, the anchoring Safe's owners and threshold at deployment, the registration paymaster, account and EntryPoint, and each contract's creation transaction ([[contracts]]). Those are checked by the release Safe's signers and the runbooks, never by a client, so they aren't in the record.
- **What the verifier's own release pins.** The verification keys of every proof system, the L2's derivation rules, the trustees' names and the release registry itself are pinned by the verifier's release ([[verifier]], Pinned trust roots). A verifier release compares the deployment records it accepts with its own pins (part 2c); this record doesn't replace them.
- **Reading it.** `packages/crypto`'s codec and rules and the client's build from the record are [[P4-4]] part 2c; until then only the generator checks these rules.

## Not a result-critical record

Like the release record ([[release]], Not a result-critical record), a deployment record decides no election result. It is never on the board and never in an election's profile; it is published to IPFS and the archive beside each release record that names it, and it counts only through a release whose hash the release Safe appended. Its only text is origins and RP IDs, under [[release]]'s grammars, so every field has one reading (T-31). It names no person: seats are listed by key, and their holders' names are the verifier release's ([[0027-trustee-panels-and-live-results]], Part 3), so nothing here is personal data (T-17).

`group`:

The encoding is the record header, then the fields in table order, each `panel`, `seat` and `group` as its fields in order with no header of its own ([[notation]], Records). A seat's key is `bytes[33]` rather than `p256-key` so that a record with a bad key still decodes and fails `panel-key`, as a panel with one fails [[trustee-identity]]'s `key`.

**Decoding.** A strict decoder reads a deployment record where only `0x0020` is expected, so `0x0020` is the only type its decoder knows: any other type is `unknown-record-type`, as for a release record ([[release]], Decoding). Versions 1 and 2 are its versions (Record (version 2)); any other is `unknown-version`. A deployment belongs to no election, so no profile pins its version and `profile-mismatch` never applies. Each length and count is checked against its maximum before anything it describes is read (T-52). At its maximums a version-1 record is 9,779 bytes.

## Well-formedness

A record that decodes is **well formed** if it breaks none of the rules below. A reader rejects an ill-formed record with the first rule it breaks, in this order: the rules from `chain-id` to `panels-empty`; then each panel in list order, all of its rules before the next panel's: `panel-threshold`, then seat by seat in seat order `panel-key` and `panel-duplicate-key` (a seat's key, then whether an earlier seat has it, as [[trustee-identity]]'s rule 3 and the trustee registry check them), then `panel-kind`; then `panel-order` and `initial-panel`; `groups-empty`; each group's `group-self-paid` in list order; `group-order`, `group-repeated` and `group-region`; then `api`, `l2_rpc` and `l1_rpc` in that order, each list's `origin`, `origin-order` and `origin-missing` before the next list's; then `origin-shared`; `rp-id` for `backup_rp_id` and then `account_rp_id`; `rp-id-shared`; and `endpoint-rp`. A panel's rule names it by its index in `panels` (`{"panel": i}`), a group's by its index in `groups` (`{"group": i}`), an origin rule its list by field name (`{"list": "api"}`) and an `rp-id` its field (`{"field": "backup_rp_id"}`).

| Code                  | The record breaks the rule if                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `chain-id`            | `l1_chain_id` or `l2_chain_id` is 0, or they are equal ([[election-definition]]'s `chain` rule)                                                                                                                                                                                                                                                                                                                                                                                          |
| `address`             | An address is 20 zero bytes; or `election_registry`, `board`, `trustee_registry` and `group_registry` aren't pairwise distinct; or `l1_anchor`, `l1_relay`, `l1_portal` and `anchor_authority` aren't. So every well-formed definition of this deployment passes `chain`, and no L1 contract is named as another                                                                                                                                                                         |
| `clock`               | `anchor_period` or `anchor_deadline` is 0: the anchor refuses a zero period at deployment, and with a zero deadline no anchor could ever count ([[board]], Timing)                                                                                                                                                                                                                                                                                                                       |
| `drift`               | `l2_max_sequencer_drift` is 0 or above `MAX_SEQUENCER_DRIFT` ([[parameters]]): the election registry admits no definition assuming more                                                                                                                                                                                                                                                                                                                                                  |
| `game-types`          | `dispute_game_types` is empty, or isn't strictly ascending (so no type appears twice): with none counted, every close statement's floor would be unknown ([[close]], The floor)                                                                                                                                                                                                                                                                                                          |
| `registrar-size`      | `registrars` has fewer than 2 addresses (the group registry's `size`, [[contracts]], Group registry, Deployment)                                                                                                                                                                                                                                                                                                                                                                         |
| `registrar-threshold` | `registrar_threshold` isn't between 2 and the number of registrars (its `threshold`): no single key adds or removes members (T-62)                                                                                                                                                                                                                                                                                                                                                       |
| `registrar-order`     | A registrar is 20 zero bytes, or the registrars aren't strictly ascending as 160-bit integers (its `order`)                                                                                                                                                                                                                                                                                                                                                                              |
| `panels-empty`        | `panels` is empty: a client with no panel seals no ballot                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `panel-threshold`     | The panel's `threshold` isn't between 2 and its number of seats ([[trustee-identity]], Panel identifier, rule 2; T-14). An author panel may have `k_A = 1`, but an author panel is the election's, never the deployment's ([[0027-trustee-panels-and-live-results]])                                                                                                                                                                                                                     |
| `panel-key`           | A seat's `key` isn't a `p256-key` encoding ([[trustee-identity]], Identity key; its rule 3, `key`)                                                                                                                                                                                                                                                                                                                                                                                       |
| `panel-duplicate-key` | A seat's `key` is an earlier seat's (its rule 3, `duplicate-key`: one holder would have two shares of every ballot)                                                                                                                                                                                                                                                                                                                                                                      |
| `panel-kind`          | The panel is `independent` and more than one of its seats is ours: [[0006-trustees]] rule 3 allows us at most one seat, and only the transitional panel suspends it ([[0027-trustee-panels-and-live-results]], Part 3)                                                                                                                                                                                                                                                                   |
| `panel-order`         | The panels' identifiers, each `panel_id` computed from the panel's `threshold` and keys in seat order ([[trustee-identity]], Panel identifier), aren't strictly ascending (so no panel is listed twice)                                                                                                                                                                                                                                                                                  |
| `initial-panel`       | `initial_panel` isn't the `panel_id` of a listed panel: the group registry accepts the Tier 2 key only from a panel the trustee registry pins, and the client must know the panel that registers it. A release for this deployment therefore keeps pinning the initial panel; a handover that retires it is a new trustee registry and so a new group registry and deployment ([[0027-trustee-panels-and-live-results]], Part 3, Handover)                                               |
| `groups-empty`        | `groups` is empty: a client with no published group registers no one                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `group-self-paid`     | A group is `self_paid` and its `tier` isn't 0: `createSelfPaidGroup` creates only Tier 0 groups                                                                                                                                                                                                                                                                                                                                                                                          |
| `group-order`         | The groups' `group_id`s aren't strictly ascending                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `group-repeated`      | Two groups have the same `region`, `tier` and `self_paid`: each region has one published group of each kind, so the client and the service never choose between two ([[registration]], Groups; [[tier1-relay]])                                                                                                                                                                                                                                                                          |
| `group-region`        | A region with a group has no signed Tier 0 group, or no self-paid group: a region the service registers in has both, so a registrant who goes direct is in the same electorates ([[registration]], Groups)                                                                                                                                                                                                                                                                               |
| `origin`              | An origin in the list isn't an origin by [[release]]'s grammar (Well-formedness): HTTPS, a lower-case host in its A-label form whose last label starts with a letter, no default port                                                                                                                                                                                                                                                                                                    |
| `origin-order`        | The list's origins aren't strictly ascending in byte order                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `origin-missing`      | The list is empty: the client can't work without an API, an L2 endpoint and an L1 endpoint                                                                                                                                                                                                                                                                                                                                                                                               |
| `origin-shared`       | An origin is in two of the lists: each request the client makes goes to an origin it trusts for that purpose only, and the CSP's `connect-src`, which lists them all, can't tell them apart                                                                                                                                                                                                                                                                                              |
| `rp-id`               | The RP ID isn't a host by [[release]]'s grammar (the `host` of an origin, with its last label starting with a letter)                                                                                                                                                                                                                                                                                                                                                                    |
| `rp-id-shared`        | `backup_rp_id` and `account_rp_id` are equal, or one ends with `"."` followed by the other: the backup's RP ID is never `apps/web`'s or under it, so no page of `apps/web` can evaluate the backup passkey's PRF (T-20)                                                                                                                                                                                                                                                                  |
| `endpoint-rp`         | An origin in `api`, `l2_rpc` or `l1_rpc` has a host that is `backup_rp_id` or ends with `"."` followed by it: a page may name as its RP ID any registrable suffix of its host, so an endpoint there could ask for an assertion under the backup's RP ID and open a voter's backup, and the backup's host serves the signed client and nothing else ([[0020-entry-points]], A; T-20). An endpoint under `account_rp_id` is allowed: `apps/web`'s own domain already serves unsigned pages |

The rules check only what the record says about itself. That the addresses hold the contracts the record names, built from `contracts_commit`, with these immutables, registrars and panels, is [[verifier]] 1.2's and the release Safe's signers' (T-64); that the origins answer, and serve what they should, is the client's own checks' (every answer is checked against the chain before it is used, so an origin can refuse service but not change a ballot). `rp-id-shared` is the part of the RP IDs' separation a reader can decide without the Public Suffix List: that the backup's RP ID is a registrable domain of its own, not merely a different host under `apps/web`'s, needs the list, and the signers check it (part 2e).

A deployment with no election registry, panel or published group (staging today, `apps/ballot`'s `STAGING`) has no well-formed record: no release is made for it, and its builds are never published.

```
deployment_hash = H(DS("abolish/v1/deployment", encode(record)))
```

over the record's whole encoding, header included ([[domain-separation]]). A release record carries it as `deployment_hash` ([[release]], Record).

## Record (version 2)

Version 2 is version 1 with the Tier 0 token issuer's public keys appended ([[tier0-token]], Keys; [[P2-30]] part 3c), so a client takes each period's `pkS` from the release it runs and from nowhere else. Every version-1 field keeps its type, meaning and place, and one field follows `membership_wasm_sha256`:

| Field              | Type                  | Meaning                                                                                           |
| ------------------ | --------------------- | ------------------------------------------------------------------------------------------------- |
| `tier0_token_keys` | `list<token_key, 16>` | The issuer's key for each period the release lists (Token keys in a release), in ascending period |

`token_key`:

| Field     | Type        | Meaning                                                                                                                                                    |
| --------- | ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `period`  | `u32`       | Its key period `q` ([[tier0-token]], Values): the key issues during `q` and redeems during `q` and `q + 1`                                                 |
| `key`     | `bytes[32]` | Its `pkS`, as [[group]] encodes an element                                                                                                                 |
| `retired` | `bool`      | Whether the key was retired early (T-74): it issues and redeems nothing, and an account holding a token under it re-issues at once ([[tier0-token]], Keys) |

`period` is a `u32` because `key_id` hashes it as one ([[tier0-token]], Keys). `key` is `bytes[32]` rather than `element` so that a record with a bad key still decodes and fails `token-key`, as a seat's bad key fails `panel-key`.

**Decoding.** As for version 1. A reader of both versions reads the header's version and then that version's layout, so a version-2 record labelled 1 has `trailing-bytes` and a version-1 record labelled 2 is `truncated`. At its maximums a version-2 record is 10,375 bytes. The deployment hash is the same formula over the whole encoding, header included (Deployment hash), so the version byte keeps a version-1 and a version-2 record of one deployment apart.

A release whose client takes Tier 0 tokens names a version-2 record. A version-1 record lists no key, so its client takes no token: a client never accepts a key the API offers alone ([[tier0-token]], Keys).

## Well-formedness (version 2)

A version-2 record is well formed if it breaks no rule of Well-formedness and none below. A reader rejects an ill-formed one with the first rule it breaks: version 1's rules first, in their order, then `token-keys-empty`, then key by key in list order `token-key` and `token-key-repeated` (a key, then whether an earlier entry has it, as for a panel's seats), then `token-key-order`.

| Code                 | The record breaks the rule if                                                                                                                                                                                                                                                 |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `token-keys-empty`   | `tier0_token_keys` is empty: every well-formed record has a signed Tier 0 group (`groups-empty`, `group-region`), and a version-2 client registers a voter there only with a token. A release whose client takes none names a version-1 record                                |
| `token-key`          | A key isn't the canonical encoding of an element other than the identity ([[group]], Encodings): RFC 9497's `GenerateKeyPair` never makes one, and the client's `Blind` refuses it ([[tier0-token]], Issuance, step 1)                                                        |
| `token-key-repeated` | A key is an earlier entry's: each period has a key pair of its own, whose `skS` is destroyed when `q + 1` ends ([[tier0-token]], Keys), so a key listed for two periods would outlive its window                                                                              |
| `token-key-order`    | The periods aren't consecutive and ascending, each the previous one's plus 1: one key per period (T-74), and no period inside the list without one, since a key retired early stays listed with `retired` set, so a client always knows whether its token's key still redeems |

As for version 1, these rules check only what the record says about itself. That the issuer holds `skS` for each listed key and answers under no other is the operator's to keep ([[P2-30]] part 3c checks `apps/web`'s keys against its release's record at start), and the client's proof check refuses any answer under another key ([[tier0-token]], Issuance, step 5).

## Across releases

A period's key is fixed once a release lists it ([[tier0-token]], Keys), so two well-formed version-2 records named by releases of one release registry ([[release]]) are judged together: the **earlier**, named by the release of lower `sequence`, and the **later**. [[verifier]]'s report is to judge every such pair of the registry's releases ([[P2-30]] part 3c), whatever deployment each names, since one issuer serves every deployment and `info` keeps their groups apart ([[tier0-token]], Group info). A rule below is broken at a period both records list, and a reader reports the first rule broken, in this order, at the lowest such period:

| Code                  | The pair breaks the rule if                                                                                                                                                                   |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `token-key-changed`   | The later lists another `key` for the period: two keys for one period split its clients into two sets the issuer chose, and a release served to one account would mark its token (T-74, T-10) |
| `token-key-unretired` | The earlier lists the period's key `retired` and the later doesn't: a retirement stands, since accounts holding tokens under the key were told to re-issue ([[tier0-token]], Keys)            |

A period only one record lists breaks nothing: a later release drops the periods that have ended and adds new ones (Token keys in a release). A version-1 record lists no key, so a pair with one has nothing to compare.

## Token keys in a release

A record has no clock, so how far its keys reach is the release Safe's signers' check at signing, not a rule. A release lists the key of the period it is signed in, the period before it, and at least the six periods after it, so about half a year. The period before is still redeeming, so listing it carries an early retirement of its key to clients. The bound of 16 leaves room for a release signed late in a period, and for one that lists further ahead. The issuer generates its keys that far ahead and keeps each `skS` apart from every other secret ([[0039-tier0-token-issuance]]). A client running past its release's last listed period takes no token: it tells the voter that a newer client is needed, rather than taking a key from anywhere else ([[P2-30]] part 4).

Why six: a release has to keep working between client releases, which ship on review rather than on a schedule, while each period listed ahead is an `skS` held for longer before its period starts, and a stolen future key mints identities from the start of its period until it is retired (T-74). Half a year keeps a client that hasn't been updated working through a slow release cycle, and keeps fewer than a year's keys waiting.

## Against its release

A release record and the deployment record it names are judged together after each is found well formed (the release first). The pair is **consistent** if it breaks none of the rules below, and a reader rejects an inconsistent pair with the first it breaks, in this order:

| Code                 | The pair breaks the rule if                                                                                                                                                                                                                                                                                                                                                                                                                       |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `deployment-hash`    | The release's `deployment_hash` isn't the deployment record's deployment hash                                                                                                                                                                                                                                                                                                                                                                     |
| `prover-files`       | The release's ballot site lists no file whose `sha256` is `membership_zkey_sha256`, or none whose `sha256` is `membership_wasm_sha256`: the client fetches both from its own release and checks them against these hashes ([[P2-21]]), so a release without them can't prove membership                                                                                                                                                           |
| `backup-origin`      | `backups` is true and the ballot site doesn't list `"https://" ‖ backup_rp_id` among its origins: the client offers a backup only where it is served from the RP ID's own host, so it evaluates the passkey's PRF as the RP ID's own origin ([[0017-identity-recovery-backup]], Option A; T-20). Whether a release may offer backups at all also waits on what [[0017-identity-recovery-backup]] (Consequences) asks for, which the signers check |
| `challenge-rp`       | The release has a challenge site, and its origin's host is `backup_rp_id` or `account_rp_id`, or ends with `"."` followed by either: the challenge page must not be able to name either RP ID ([[registration]], Challenge page; T-20, T-41)                                                                                                                                                                                                      |
| `ballot-rp`          | An origin of the ballot site has a host that is `account_rp_id` or ends with `"."` followed by it, so the client would be same-site with `apps/web` and in its cookies' scope (T-10; [[0020-entry-points]], A); or has a host under `backup_rp_id` (ending with `"."` followed by it) other than `backup_rp_id` itself: no other host under the backup's RP ID serves anything (T-20)                                                             |
| `endpoint-site`      | An origin in `api`, `l2_rpc` or `l1_rpc` is an origin of either site: an endpoint at the client's origin could serve unsigned script at a path the record doesn't list, same-origin with the client and its stored identity, and [[verifier]] 1.1 asks for no such path; at the challenge origin it would break that origin serving the challenge page and nothing else ([[registration]], Challenge page)                                        |
| `challenge-webauthn` | The challenge site lists a file at `.well-known/webauthn`: it would let the challenge origin claim a passkey RP ID as a related origin, which [[registration]] (Challenge page) forbids. A ballot site may list one; that its origins are the ballot site's and none is under `account_rp_id` is the signers' check (part 2e)                                                                                                                     |

`challenge-rp` and `ballot-rp`, like `rp-id-shared` and `endpoint-rp`, are the part decidable without the Public Suffix List: [[registration]] (Challenge page) forbids the challenge origin under either RP ID's registrable domain, which the signers and [[verifier]] 1.1 check with the list ([[release]], Security notes). Nothing here compares the ballot site's `content-security-policy` with the record's origins: a header value is free text ([[release]], Security notes), and the bundle check of each build (`apps/ballot`) and the signers do.

Nothing relates the release record's `l1_chain_id` to the deployment's: the first is the release registry's chain, the second the deployment's L1. They are the same (Sepolia) until the owner deploys a mainnet release registry, and a mainnet deployment's releases are then appended there; a test deployment's releases may be recorded on either, and a verifier release pins the one registry it reads ([[0036-release-record]]).

## Security notes

- **The record is only as good as its signers.** A release Safe quorum, or whoever compels one, can publish a release built for another registry, panel or registrar set. The record makes that public, beside every other release (T-41, T-69), and a verifier release that pins its own trust roots reports the difference (part 2c).
- **Pins aren't proofs.** The record says which addresses the client trusts, not what is deployed there; until [[verifier]] 1.2 binds each deployment to its creation code, a contract at a pinned address is trusted as deployed (T-64).
- **Endpoints are untrusted.** An origin in `api`, `l2_rpc` or `l1_rpc` is one the client may ask, never one it believes: a lying endpoint can refuse service, and the client's checks against the chain decide everything else. A second L2 endpoint of another operator is what the client needs before it acts on a `moved` registration (T-16, T-11); the record allows up to four, and a client release that needs two says so in its own rules, not here.
- **`contracts_commit` is a SHA-1 name.** As for the release record's `source_commit` ([[release]], Security notes), the deployed bytecode is bound by [[verifier]] 1.2's build, not by SHA-1, but the link to the reviewed source is; the signers' runbook binds a SHA-256 of the contracts tree as well (part 2e).
- **Derived, not listed.** The trustee registry's quorum is `max(k, n − 1)` for every pinned panel ([[contracts]], Trustee registry, The quorum), so it isn't a field; the contract-event version a client reads logs under is the client release's code, not the deployment's. Nothing checks that `anchor_epoch` is a whole hour or a multiple of `anchor_period`: the anchor doesn't require it, and the deployed value is the deploy script's ([[contracts]], Board anchor, Deployment).
- **Holders aren't named.** `ours` says only whether a seat is ours. Who holds the other seats is the verifier release's, and the client shows only how many seats are ours ([[0027-trustee-panels-and-live-results]], Part 3).
