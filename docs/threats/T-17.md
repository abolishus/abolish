# T-17: PII on-chain or on IPFS

- Area: Ballot secrecy, unlinkability and privacy (G-3, G-4, G-5, G-12)
- Adversary: A-2, A-9, A-10
- Status: **Planned.** Residual: a poll creator can put personal data in a poll's text, which copies on IPFS may keep; a malicious client can hide chosen bytes, up to the full width of each field that must be random (salts, CSPRNG outputs), since random and chosen bytes look alike ([[notation]], Result-critical fields); a poll creator can likewise hide chosen bytes in an election definition: somewhat over 70 bytes in its display-text commitment and the free bits of its bounded integers (the registry assigns `election_id` as a hash output, P1-18), plus about 180 more in fields that neither the registry nor, so far, the trustees check before the definition reaches the board (the tier roots, group IDs and sizes, `membership_vk_hash`, and the pinned versions of types 2 to 9; the trustee node ([[P2-13]] part 1) runs every one of them except 2.4 (the tier roots, group IDs and sizes against L2), which waits on `packages/verifier`, so no ceremony runs on a real node until it does; a quorum of a pinned trustee panel can register a transcript for any stub, archiving about 64 chosen bytes for its stub and transcript hashes and about 64 per seat of its key set (a KEM-key hash the registry can't check and the free bits of a signing key's point), about 1 KB at `MAX_TRUSTEES` seats per registration ([[contracts]], Trustee registry, Known-weak); data in result-critical fields is archived for good; anyone who registers at Tier 0 chooses their identity commitment, about 253 bits the signing service can't tell from a real Poseidon output, logged on L2 for good with each group addition (bounded by registration rate limits; one for any election identifier) and up to 126 per archive locator, unbounded in number beyond gas ([[contracts]], Board anchor, Known-weak); a member can direct-submit a ballot whose fields the contract doesn't check are chosen, which the verifier rejects while the archive keeps it: the 40-byte L1 reference, the validity proofs (64 bytes per option and sum branch, each scalar below `ℓ`) and the VSS commitments (any even, non-zero encoding below `2²⁵⁵ − 19`, which the contract doesn't decode to a point), even with P1-18's ballot check, which runs the record's cheap checks and frames every field strictly ([[contracts]], Board, Ballots; a registered trustee seat can put its own failing tally opening, about 4 KB per seat and cell, on the board through the contract path P1-18 must provide, while a boarded passing opening carries only its 64-byte ECDSA nonce choice ([[tally]], Opening record, Residuals); the seats of a poll's author panel can archive up to about 43 KB of chosen bytes per election in its ceremony transcript (about 1.2 KB with one seat; about 17 KB of it through the one seat rule 7 lets be unqualified), signed by their identity keys, or its creator about 32 bytes in one author key nobody holds in place of that seat's share, accepted under [[0034-author-transcript-bytes]] ([[ceremony]], Author panel, Residuals); T-68.

## Threat

A poll title, election definition, registration or ballot carries personal data into permanent storage.

## Mitigation

Contract inputs are fixed-size commitments, hashes and proofs, never free text tied to a person; Foundry tests assert this (P1-18). Display text is committed by salted hash and kept off the permanent archive, so it can be taken down while the result stays verifiable ([[0005-permanent-archive]], P1-8); otherwise moderation can hide poll content in our front ends, never erase it (P2-10, T-68).

- 2026-10-13 (P1-18 part 4b-3b-3, [[contracts]], Board, Ballots): the board's ballot check frames a direct-submitted ballot record strictly (every count, enum, `field<bn254>` and scalar, and each element's encoding canonical, even and non-zero, the cheap part of RFC 9496's decoding) and runs `ballot-stray`, `ballot-tier` (`ballot-cell`), `validity-shape`, `share-hash-unqualified` and the membership proof before anything is boarded, so the record after the membership proof is no longer wholly free to a member: what stays free is the L1 reference, the validity proofs' scalars and the VSS commitments' encodings that frame but don't decode (Status). The board contract that calls it, with the registered key set it reads `qualified` from, is part 4b-3c and 4b-3d.
- 2026-10-13 (P2-16 part 1b, `packages/crypto`): `results` keeps `live_every` and `live_batch` zero in a sealed definition and `author-panel` keeps the author threshold and transcript hash zero with no author panel, so a production reader refuses chosen bytes there. The author keys' roughly 32 chosen bytes each stay a residual until part 3 has every default seat check the author panel's approved transcript, under `author_keys`, before taking part.
- 2026-10-13 (P1-18 part 4b-3d-2, [[contracts]], Contract-event record, Event tables (version 2)): the board's events are archived only as records the board frames, with topics that must equal the record's own `definition_hash` and `ballot_hash` (a ballot's recomputed), so no event carries a byte its record doesn't define; the trustee registry's key-set registration is read at exactly its length. The chosen bytes the board accepts inside those records remain, as part 4b-3d-1 lists.
- 2026-10-13 (P2-13 part 1): the trustee node runs the stub checks before round 1 and before approving: the stub decoded under its own profile with `stub_hash` recomputed, the pinned panel, chain and registry, `membership_vk_hash` against the pinned key, and every pinned version one its release reads (types 2 to 9, the ceremony transcript only at the version it checks). The electorate's fields (2.4) are checked only through a function the deployment supplies, which nothing provides yet, so the tier roots, group IDs and sizes stay in the residual until then.
- 2026-10-13 (P2-3 part 2d, `packages/core`, `apps/api`): the API boards a ballot only once `@abolishus/verifier`'s `electionAdmission` admits it (strict decoding and 5.1 to 5.4 against the key set the board's transcript registered), so the server's board path takes no undecodable payload and no ballot the verifier rejects by those rows; the L1 reference (5.8) and repeats (5.7) are still left to the verifier, so a member can board ballots with a stale reference or repeats, each a whole valid ballot.
- 2026-10-13 (P1-19 part 4k, [[verifier]], Contract events): the verifier fails 4.4 at a boarded contract-event record that doesn't decode strictly or whose topics or data aren't exactly an event of its contract's table, so a record carrying bytes its event doesn't define is reported against the operator, inside the anchored extent. The archive's records wait on the replay (P4-3).
- 2026-10-16 (P3-3 part 3b-1, [[contracts]], Group registry, Known-weak): a junk Tier 1 addition naming a made-up Tier 2 root carries a commitment `C_V` of its sender's choosing, about 31 bytes per addition at about 1.5 million gas, into the group registry's archived sequence. Not mitigated; the gas is the bound.
