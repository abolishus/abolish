# T-38: Ballot substitution and re-vote replay

- Area: Integrity and verifiability (G-7, G-8, G-9)
- Adversary: A-4, A-2, A-9
- Status: **Specified** (P1-13): the message `M` binds the ballot hash, definition, tier and L1 block ([[revoting]]), and repeats are recognised by (tier, nullifier, `M`), never by bytes; implemented in `packages/crypto` (`membershipMessage`, `selectBallots`). The ballot hash and the ballot record are specified ([[ballot-validity]], Ballot hash and Ballot record; `ballotHash`, `checkBallot`), and the admission check verifies each ballot's Groth16 proof against `M` recomputed from the record (P1-17b's verifier). Residual: a coercer holding the voter's secret can always re-vote (T-45, T-46).

## Threat

Re-voting means a nullifier legitimately appears more than once, so (a) anyone who sees a voter's membership proof (on the board, or in the L2 mempool on direct submit) attaches a different ciphertext to it, and that ballot becomes "last"; or (b) after the voter re-votes, someone (a coercer, say) resubmits the voter's earlier ballot-and-proof pair so the coerced ballot is "last" again.

## Mitigation

The membership proof's signal binds the hash of the ballot (ciphertext and validity proofs) and the election definition, so a proof can't be moved to another ballot. Board and contracts reject a byte-identical repeat of an earlier ballot entry, and the re-vote rule rejects a replayed earlier pair whatever its bytes (requirement R1 in [[verifier]] check 6.1), so an old pair can't become last again. The re-vote rule must reject replays whatever their bytes (Groth16 proofs are malleable), must not let any value chosen at cast time freeze a ballot as last (T-45), and must not let the board operator choose the counted ballot by withholding or reordering unanchored entries (T-23, T-25); [[verifier]] check 6.1 states these requirements and the candidate constructions, and P1-13 specifies a rule that meets them (P1-8, P1-13, P1-17).

## History

- 2026-10-11 (P1-13): `M` specified; repeats recognised by (tier, nullifier, `M`) ([[revoting]]).
- 2026-10-12 (P1-12 part 3a): the ballot hash is specified: the statement hash's inputs (definition, ballot version, tier, nullifier, commitments, share-ciphertext hashes) and the validity proofs. It leaves out the membership proof, so a re-randomised copy keeps its hash and is a repeat, and the L1 reference, which `M` binds itself ([[ballot-validity]], Ballot hash).
- 2026-10-12 (P1-12 part 4): the ballot record carries `tier`, `l1_ref_number` and `l1_ref_hash` beside the fields the ballot hash covers, and its admission check recomputes `M` from them and the definition and verifies the membership proof against it (`membership-proof`), so a proof moved to another ballot, L1 block or tier fails, and a re-proved or re-randomised copy has the same `M` and is a repeat ([[ballot-validity]], Ballot record).
- 2026-10-13 (P1-19 part 4f): the verifier finds repeats (5.7) among the ballots 5.1 to 5.4 admit by (tier, nullifier, `M`), with `M` recomputed from the record, so a copy with its membership proof negated (re-randomised without the witness) is found; a vector has one. It doesn't reject them until the close rule (5.5) can say which copies are admitted ([[verifier]], Ballot admission).
- 2026-10-13 (P2-3 part 2e-1, `packages/core`, `apps/api`): the API never boards a repeat of a ballot it boarded. Each admitted ballot's (tier, nullifier, `M`), from the verifier's admission of its own bytes, is stored with its entry (`board_ballot_keys`) and read under the board's lock: a copy in other bytes, such as one with its membership proof re-randomised, is refused with `repeat`, and the same bytes again get the entry that carries them. The earlier copy is a board-path ballot boarded in the window, so it stands under the close rule, and the verifier still finds repeats itself. A voter whose ballot someone else copied to us first gets `repeat`, not a receipt for its own bytes: its ballot counts through the copy, which keeps its ballot hash, and it can still submit directly (T-25).
- 2026-10-13 (P2-17 part 2a, [[ballot-validity]], Hashes (version 5)): a rolling ballot's step is an input to its ballot hash, and so to `M`, so a membership proof can't be relabelled to another step, even one with the same root; the root it is checked against is always the verifier's own step root, never one from the ballot or a submitter.
- 2026-10-13 (P1-19 part 4l): once 5.5 judges each copy's window, the verifier rejects every repeat among the ballots 5.1 to 5.5 admit with `repeat`, of either path, so a late copy never stands in for a timely one; 5.8 can't change which copies are rejected, since `M` binds the L1 reference ([[verifier]], Ballot admission).
- 2026-10-14 (P1-19 part 4n): selection (6.1) takes the ballots 5.7 left after rejecting every repeat, so a replayed or re-randomised copy never forms a group of its own or ties with its original; the verifier treats an admitted repeat reaching selection as its own bug, never as a selection.
- 2026-10-22 (P2-13 part 4c-2a, `apps/trustee-node` `ComplaintDuty`): under definition version 5 the complaint duty takes a scope ballot's vote only from a record whose ballot hash, recomputed under the version its version byte names (version 3 by its cell), is the scope's: the hash binds the ballot version and the cell, so a source can't pass a record of another layout or cell for it.
- 2026-10-30 ([[P2-17]] part 4d-2b-2b-2a, [[verifier]], Counted set and tally, step 3): under a rolling definition the delivery check names each selected ballot by version 5's ballot hash, which binds its step, so a receipt or posting for the same fields relabelled to another step, or read as ballot version 4, names no selected ballot and delivers nothing (`deliveryBallotHashV2`; the close check recomputes the same hash). Vectors: `verifier-counted-v5-rolling.json`'s `step-relabelled` and `version-4-hash` cases.
- 2026-10-30 ([[P2-17]] part 4d-2b-2b-2b-2b-1, [[verifier]], Counted set and tally, step 3): beside a rolling author panel an author seat's receipt is read by the same hash, so one for the fields at another step names no selected ballot; `checkDeliveryV2`, given a rolling definition, refuses a ballot that names no step, and given any other one that names a step, so the definition fixes which version's hash a record must name. Vectors: `verifier-counted-v5-rolling-author.json`'s `author-step-relabelled` and `counted` cases.
