# P2-28: The installable app and quality targets

- State: in progress (part 1a, the web app manifest and icons, merged in #574; part 1b, the offline shell, merged in #579; part 2, performance budgets in CI and the measurements, next)
- Phase: Phase 2: Open polls end to end at Tier 0

## Scope

Making the everyday app feel like an app, and fast, everywhere.

- An installable web app (manifest, icons, offline shell) for `apps/web`; the ballot client's own install stays under its CSP and entry-point rules ([[0020-entry-points]]).
- Targets, measured on staging and recorded here: the first answer in three taps ([[first-answer]]); a poll open within a minute of submitting; proving on a mid-range phone ([[P2-21]]); page loads on a slow phone connection.
- An accessibility audit of every everyday screen against WCAG 2.2 AA, and translations for at least one language beside English, end to end.

Rules for every part, as [[P2-19]]'s: everyday register by default ([[language]]); no hard-coded strings (`messages.ts`); CSP-safe (no inline `style`); server-rendered where the page is the website's; a fixed analytics template per route, never a path or poll ID (T-67); each component a story with a play function passing axe at desktop width and 360px; SSR and serve tests per route; the mockup's story deleted in the PR whose page matches it. Privacy holds everywhere: nothing an account does on the website (following, reacting, sharing, notifications) is ever stored, logged or keyed with a ballot, nullifier, receipt or the fact of having answered, and the T-10 no-join tests cover every new table, queue and log line ([[PROJECT_BRIEF]], Identity).

## Notes

- **Part 1a**: `apps/web` is installable. `src/app/install.ts` holds the icon's SVG (the receipt's ticket stub with its perforation and a tick, white on the primary green, everything inside a maskable icon's safe zone so one drawing serves both purposes), the PNG sizes (192, 512, and 180 for iOS) and the manifest, built from the message catalog (`siteName`, `appDescription`): `id`, `start_url` and `scope` all `/`, `display: standalone`, the light background as its colours. The files are static in `public/` (`manifest.webmanifest`, `icons/`), copied into `dist/client` by the build, and `tests/install.test.ts` holds them to the module: the manifest byte for byte, and each PNG as the SVG rendered by the link previews' resvg at its size (`rasterise`, factored out of `src/og/render.ts`), so the shipped bytes are always what the source says; `UPDATE_APP_FILES=1` rewrites them. `src/node/serve.ts` serves exactly the names in `APP_FILES` from `clientDir`, classed as assets (never page views, T-67), with `appFileHeaders` (a refuse-everything sandboxed CSP, `nosniff`, same-origin CORP, cached a day since the names carry no hash); a query, another name under `/icons` or a listed file the build lacks is never a file. The root route links the manifest, the SVG icon and the apple-touch icon on every page. Tested in `tests/install.test.ts`, `tests/serve.test.ts` (types, headers, HEAD, 404s, not page views), `tests/ssr.test.ts` (the head's links) and `tests/deployable.test.ts` (every listed file served from the real build).
- **Part 1a known-weak**: no service worker, so no offline shell yet (part 1b). The window's colour is the light background in dark mode too: TanStack's head keeps one `theme-color` meta per name, so the light and dark pair can't both be set there, and the manifest has one colour. The embed's page links the manifest like every page, which its policy (no `manifest-src`) refuses to fetch; harmless.
- **Part 1b**: the website has an offline shell. `src/app/offline.ts` holds a service worker, served at `/sw.js` (scope `/`) as the text of one self-contained function with its configuration, and registered from every page (`updateViaCache: "none"`). It passes every page through from the network (navigation preload where the browser has it) and answers a top-level `GET` navigation from its cache only when the fetch fails before any answer; a server's own error page passes through. What it keeps is `/offline`, its stylesheet and the fonts that stylesheet names, filled when it installs (all or nothing) and served cache-first by their content-hashed names; nothing a visitor opens is ever stored (T-45, T-10). `/offline` is the site's frame and a notice ("You're offline", what is kept, and "Try again", a plain link to the address in the bar), rendered as static HTML with no script (`src/app/offline-page.tsx`, `offlineHeaders`: no `script-src`, no framing, no form action), the same bytes for everyone; the worker's cache is named by its hash, so `/sw.js` changes whenever the page does and the browser installs it again, dropping the older cache. The worker gets `workerHeaders` (`default-src 'none'; connect-src 'self'`, `no-cache`), the pages' policy gains `worker-src 'self'`, and the front classes both paths as `offline`: no cookie, never a page view (T-67). Frames, posts, other origins and every other file are left to the browser. The build no longer inlines a font under 4 KiB as a `data:` URL, which `font-src 'self'` refused on every page. Tested in `tests/offline.test.ts` (the served text run in a context of its own against a stand-in scope: what install keeps and refuses, activation's clean-up, pass-through, the offline page on failure, what it leaves alone, and a fast-check property that no request, online or not, stores anything), `tests/security.test.ts`, `tests/serve.test.ts` (class, cookie, not page views), `tests/ssr.test.ts` (the built page and worker: headers, no script, the empty "Try again" link, the worker's configuration matching the page's hash, the built worker run in a bare context, `worker-src` on pages), `tests/offline.e2e.ts` (Chromium against the built site behind the real front: it installs and keeps only those files; with the server gone a page shows the offline page with the site's font and no policy violation; "Try again" opens the page once the server is back) and the stories `OfflinePage` and `OfflineDark` in `src/components/site-layout.stories.tsx`.
- **Part 1b known-weak**: a service worker outlives the page that registered it, so a `/sw.js` served by a compromised host would keep running on visitors' devices until the browser next fetches `/sw.js` from a fixed host (every navigation, with `updateViaCache: "none"`); it reaches only this origin, never the ballot client's (T-43). Removing the shell means serving a `/sw.js` that unregisters itself, never just deleting the route. Each navigation can make the browser fetch `/sw.js` to check for a new one, a small uncounted request with no ETag yet. Offline, only that one page shows: no poll, list or result is readable without a connection. A page already open stays as it was; its server functions fail as before.
