## Scope

`apps/indexer` (Ponder), including direct-submitted ballots.

## Plan

1. **The scaffold and the group registry** (this part): `apps/indexer` on Ponder 0.18, storing `GroupCreated`, `MembersAdded` and `MembersRemoved` verbatim, and `readIndexedGroups` for readers, who replay the records through `@abolishus/crypto`'s `applyGroupRecords`.
2. **Completeness and the board's events** (2a, the group registry's logs as emitted, and 2b, the other contracts): store each log's raw topics, data and block timestamp and every event the contracts emit (`RegistrarsPinned` included), so a reader can check the index against the event accumulator's storage proofs ([[contracts]], Event accumulator); then the board's events, including direct-submitted ballots (T-25), stored as the contract-event records the verifier reads ([[0025-contract-event-evidence]]), and the election and trustee registries'.
3. **Readers**: the API and worker reading the index where they now read nothing from the chain, each rechecking what it reads. In parts:
   - **3a, registrations** (this part): the worker records each finalized `DefinitionRegistered` from the index and stores its definition (P2-18's short codes, P2-8's definitions), after the registry's logs replay to its accumulator at the L2's finalized block, read from the worker's L2 node.
   - **3b, proven slots**: the accumulator's two slots proven under an L2 output root the sync checks against L1 (an account and storage proof, as [[verifier]] 4.4 does), so the L2 node is no longer trusted for them.
   - **3c, the other readers**: P3-6's per-tier results and the group roots a rolling electorate needs ([[P2-17]]), from the group registry's logs, checked the same way. (P2-3's L1 reference reads L1 itself since its part 2e-2, so it needs no index.)

The catalog change routes the PR to the owner (CODEOWNERS).
- Independent review (in-session, `crypto-review` checklist): nothing blocking. Applied: the threat and status text no longer claim a corrupted row always fails a replay (a deleted removal or tail doesn't); `reorgWindow` set to Ponder's maximum and its wall-clock finality documented; both reads in one repeatable-read snapshot; event IDs ordered bytewise (`collate "C"`); a non-hex record fails as corruption; tests for a reordered row and a dropped removal. Left for part 2: storing raw logs and `RegistrarsPinned` for the accumulator check.
- Tested: on Anvil, records sent through both Ponder's backfill and its live indexing replay, under the pinned registrars, to exactly the leaves sent, an empty group included; a wiped index, with Ponder's RPC cache dropped, is rebuilt from the chain to the same result; under another registrar set every group's history fails at its first record; a reordered row fails and a dropped removal still replays; the deployment's parser refuses malformed values (property tests).
- Known-weak: the index trusts its L2 node for which logs exist, and anyone with write access to its database can delete rows: a dropped removal or a dropped tail of additions still replays, to another tree, and no reader checks completeness yet (the verifier's accumulator check does; part 2 stores what readers need for it). Ponder's finality is a wall-clock window (600 s, its maximum), not the L2's safe head, so a reorganisation of the unsafe chain after it leaves orphaned records that still replay; readers must treat rows above the safe head as provisional. Ponder's tree is large for what it does here, and runs in the indexer's process with the database credential; its RPC cache lives in Postgres schemas of its own beside the index, and the test drops every `ponder_` schema in the test database.

## Part 2a (#269)

- Built: `contract_log` in `ponder.schema.ts`, every log the group registry emits as emitted (contract, block number and timestamp, topics, data), the constructor's `RegistrarsPinned` included through a handler of its own; `readContractEvents` in `src/records.ts` returns a contract's rows as contract-event records (`0x0008`), `n` being each row's position in chain order rather than a stored number, so a deleted row shifts every later `n` instead of leaving a gap. Ponder's backfill returns a cached log's topics padded to four with nulls; the handler cuts them at the first null.
- Tested: on Anvil, every indexed log (from the backfill, live, and after the index and RPC cache are wiped and rebuilt) round-trips through the record's codec, passes `checkContractEvent` under version 2 with the registry's role, starts with `RegistrarsPinned`, and passes `checkEventAccumulatorProof` against the registry's accumulator and count read from storage at the head, the slots derived in the test from the spec's ERC-7201 namespace. A dropped log (the removal replay misses), a dropped middle log, an altered log and a log moved to the next block fail; a row deleted from the index itself fails as `accumulator`; an index longer than an older block's proof still checks.
- Known-weak: the check runs only in tests, against storage read from the node; no production reader runs it yet, and a reader must prove the two slots under an output root itself (part 3; the verifier's 4.4 is its own). Only the group registry is indexed: the board's and the election and trustee registries' events, direct-submitted ballots among them, are part 2b. `group` and `group_record` are still written beside `contract_log` rather than derived from it, so the two can disagree in a tampered index; readers that check completeness should read `contract_log`.

## Part 2b (#310)

- Built: the indexer reads all four L2 contracts (`ELECTION_REGISTRY_*`, `TRUSTEE_REGISTRY_*`, `GROUP_REGISTRY_*`, `BOARD_*`, each address and start block, the addresses distinct). `src/events.ts` subscribes to every event of each contract's generated ABI, since Ponder fetches only the logs of handled events: every log of every contract lands in `contract_log`, and an event a later contract version adds is indexed without a new handler. `group` and `group_record` are still written for the group registry.
- Tested: on Anvil, the four contracts deployed (the board reading its registries through `BoardFixture`'s stubs set from `ballot.json`, the election registry with `MockL1Block` at the predeploy); elections created and `ballot.json` ballots submitted directly to the board, before the backfill and live. Each contract's indexed logs frame, pass the event check under version 5 with their role, name the events sent in order and replay to the contract's stored accumulator and count, from the backfill, live and after a rebuild; the board's logs are exactly the ballots submitted. Mutation: without the board's `BallotSubmitted` handler the test fails. `tests/events.test.ts`: every ABI event subscribed once, covering the newest contract-event table for each role.
- Known-weak: only `PanelPinned`, `ElectionCreated` and `BallotSubmitted` among the new contracts' events are produced on Anvil; the others (ceremony and definition registrations, the board's receipts, postings, complaints, batches, roots, relayed ballots and close statements) go through the same handler and are proven subscribed, not emitted. The board reads stub registries in the test. No production reader proves the accumulator slots yet (part 3). No deployment sets the indexer's variables yet.

## Part 3a (#345)

- Built: `packages/core` `syncRegistrations` (`src/registry-sync.ts`) and `latestRegistration`; `apps/indexer` `readIndexedLogs` (each log's record with its index in its block; `readContractEvents` is now its records); `apps/worker`'s `{registry-sync}` queue, every minute when configured (`REGISTRY_SYNC_*`, `src/registry-env.ts`): `ViemRegistryAccumulator` reads the election registry's accumulator and count at the L2 node's finalized head from the spec's ERC-7201 slots, `RegistrySync` reads the registry's logs from the index and calls core. Core replays every log against the accumulator before trusting one, requires each log's index (which the accumulator doesn't bind, and by which the table orders same-block registrations) to rise within its block, and requires the registrations already recorded to be exactly the registry's first ones; then, after the latest recorded registration and up to the finalized block, runs the event check under the deployment's pinned version, stores each `DefinitionRegistered`'s definition and records the registration in chain order. A refused log, a log naming another contract or a definition filed under another election stops the run there; a definition `storeDefinition` refuses (a later version, or one 2.1 fails) is still registered and logged as unstored. Findings are log lines of public chain data; a refusal fails the job as `registry-sync-refused`.
- Independent review (in-session, `crypto-review` checklist): one blocking finding, fixed: an index could swap two same-block registrations' log indices, which the accumulator doesn't bind, and so hand one poll's code to the other; log indices must now rise within a block. Also applied: the skip past recorded registrations is checked (the table must hold exactly the registry's first registrations, the latest at its position), a definition filed under another election is refused before anything is written, a log naming another contract is refused by its address before the event check, and the residuals below are recorded. Left as they are: the two structurally identical `IndexedLog` interfaces (core and the indexer don't depend on each other), and index values outside a `u64` failing as `internal` rather than as a finding (both fail closed).
- Tested: core against Postgres: registrations recorded in chain order with their positions and definitions stored, a rerun recording nothing; logs above the finalized block left for a later run; an ill-formed definition registered but not stored; a property that runs at rising finalized blocks record every registration once, in order; a dropped, altered or moved log, a gap in the numbering and another registry's logs refused as `incomplete`, nothing recorded; two same-block registrations with swapped log indices refused (`log-index`), nothing recorded, and recorded in order once they rise; another registry's logs over a table holding this one's, a latest registration moved in its block and a stray row refused as `recorded`; an unknown event, a missing topic and short data stop the run after the logs before them; a log naming another contract; a definition filed under another election; a duplicate registration stops with the table's error. Mutations dropping the accumulator check, the log-index check or the recorded check each fail their tests. Worker: the slot equals the spec's derivation; the node adapter reads both slots at the finalized head by number, refuses another chain and a count above a u64; the sync over a Ponder-shaped `contract_log` records registrations with their positions and definitions across two finalized heads, and an index missing a counted log records nothing and the scheduled job logs `incomplete` and fails, its keys under its own hash tag; the configuration's parser (all or none, malformed variables named, never quoted). Indexer, on Anvil: `readIndexedLogs`' log indices equal the node's for every contract's logs.
- Known-weak: the L2 node is trusted for its finalized head and the registry's storage there (`eth_getStorageAt`, no proof; part 3b), so a lying node with a matching index can vouch for a registration the registry never made, which the verifier, reading the registry itself, still refuses, and a recorded registration is permanent. Each run reads the registry's whole log from the index, definitions included, and replays it (linear in registrations, every minute). An index behind the finalized head fails the job as `incomplete` until it catches up, the same finding as a dropped tail. A Ponder orphan (a row left from a reorganisation past its 600-second window) at or below the finalized block fails every run the same way until the index is rebuilt, which is the recovery. A log the event check refuses though the registry accepted it (a decoder bug, or the wrong `REGISTRY_SYNC_EVENT_VERSION`) halts every later registration until a fix ships: halting is deliberate, since skipping it would move every later code (T-53). The stored log indices are the index's, checked only to rise within a block, so they order registrations correctly but may not be the chain's own numbers. Two workers running the sync at once race on the table's constraints, and the loser's job fails until the next run. Display text isn't stored (it isn't on chain; P2-8 and [[P2-22]] store it). No deployment sets the variables yet, and the indexer doesn't yet run in any environment.
