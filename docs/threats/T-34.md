# T-34: Election definition substitution

- Area: Integrity and verifiability (G-7, G-8, G-9)
- Adversary: A-2
- Status: **Planned.**

## Threat

Options, rules, electorate, trustee keys or the closing time change after voting opens, or different voters see different definitions.

## Mitigation

The definition's hash is registered on L2 before opening; the ballot client and the verifier check it; ballots bind to it (P1-18, P1-12). Display text, kept outside the definition, is checked against the definition's commitment by the ballot client and any challenge checker before it is shown ([[display-text]], P1-8, P2-8).

- 2026-10-12 (P2-8 part 2a): `packages/crypto`'s `checkElectionToShow` holds every check before an election is shown: the definition must decode under its own pin, name the election asked for, hash to the hash the caller read from the L2 election registry and be well formed, and the display text must decode and match the definition's commitment and the spec's rules. The ballot client runs it in its worker; reading the registry is part 2b, which must also check the chain IDs and the registry and anchor addresses against the deployment the signed client release pins, or a registry elsewhere could vouch for a forgery.

Index: [[THREAT_MODEL]].

## History

- 2026-10-11 (P1-10b): the election-definition record and its hash are specified and built, the definition is decoded only under its own profile's pin, and clients check the display-text commitment before showing any text ([[election-definition]], [[display-text]]). A ceremony transcript is bound to one definition by the stub hash; `election_id` is assigned by the registry and has exactly one definition, write-once; the transcript hash need not be unique. Still to come: registration on L2 and the registry's admission rules (P1-18), and ballots binding the hash (P1-12, P1-17). Residual: translations aren't checked against each other, so the cast-confirmation screen and challenge checkers show every translation's label (T-41).
- 2026-10-11 (P1-18, part 2): the election registry is built ([[contracts]], Election registry): it assigns `election_id` from the chain, its address and its counter, and admits one definition per election, write-once, from its creator only, if it decodes strictly, is well formed, names the deployment, opens after the anchoring epoch and after registration, has its electorate in the past, and its stub was recorded with its ceremony transcript hash by the trustee registry. Still to come: the trustee registry (P1-18, part 3), which the ceremony check depends on, and ballots binding the hash (P1-12, P1-17).
- 2026-10-12 (P2-9 part 1): `apps/web`'s poll page decodes the definition with `@abolishus/crypto`, refuses one that doesn't decode or names another election, and shows its hash for comparing with the registry. It doesn't read the registry itself yet.
- 2026-10-12 (P1-19 part 3c): the verifier decodes a definition under its own pin and checks its well-formedness (2.1), reports its hash for comparison with the registry's, and runs the board checks under its `election_id`, its pinned board-entry version and its `l1_anchor`; checking the hash against the L2 registry is still to come ([[verifier]], Definition).
- 2026-10-12 (P1-15 part 3, [[tally]], Destruction): board-entry version 4 allows the destruction statement, and a profile that pins tally-opening version 1 must pin it ([[verifier]] 2.3, `profile-combination`), so an election's creator can't pin board-entry version 3 to leave its trustees no way to state destruction. Not built yet: 2.3's combination rules wait for P1-19, and the registry's refusal for P1-18.
- 2026-10-12 (P1-19 part 4b): the verifier reads board-entry versions 1, 3 and 4 and fails 2.3 with `profile-combination` when a definition pins ballot version 1 without version 3 or 4, or tally-opening version 1 without version 4; the other checks still run, so the report shows the board. The election registry's refusal still waits for P1-18.
- 2026-10-12 (P1-19 part 4c): the profile combination is `@abolishus/crypto`'s `profileCombinationRule`, which the verifier calls, so a client can refuse an election bound to fail 2.3 with the same code; the ballot client must call it before it casts (P2-8).
- 2026-10-13 (P1-18 part 4b-2a, [[contracts]], Election registry, Events): a definition's registration carries its block's L1 origin, which a retired version's cutoff is compared with (2.3). The verifier bounds it by the release's pinned `max_sequencer_drift`, never the definition's own (its creator chooses that, unbounded above), so a sequencer or a rewritten `L1Block` predeploy can backdate a registration past a cutoff only if the cutoff is less than that drift before it.
- 2026-10-13 (P1-18 part 4c-2b-2b-1, [[board]], Allowed payloads): board-entry version 5 allows the close statement and fixes its version, 1, so a statement of another version on such a board is `profile-mismatch`, never read under looser rules. Version 5 also allows everything version 4 does, so [[verifier]] 2.3 now admits it wherever it requires version 3 or 4 (delivery) or 4 (destruction); `profileCombinationRule` reads the allowed sets, so the rule moved with the version. Until [[P1-18]] part 4c-2b requires it, a profile without version 5 isn't refused, and its seats have no board path for the close statement.
- 2026-10-15 (P1-19 part 4p, [[verifier]] 2.3): 2.3 now requires board-entry version 5 and contract-event version 3, as the election registry's rule 9 does, whatever the definition version: `profileCombinationRule` fails a profile pinning board-entry version 1, 3 or 4 or contract-event version 1 or 2 (`profile-combination`), so no profile can leave the close statement off the board or the close rule's events unarchived, and a contract-event type pinned twice or not at all is refused like the ballot's. The verifier's fixtures and the reference election pin both.
- 2026-10-17 (P2-22 part 1, [[0032-poll-creation-operations]]): before a website poll opens, the worker decodes the definition the registry holds and compares it with the author's draft, failing the poll on any difference; nothing the author signs binds the two yet ([[T-72]]).
- 2026-10-17 (P2-8 part 2b-1): the API stores display text only once `checkElectionToShow` passes it against the stored definition, the ballot client's own check, and serves it at `GET /elections/display-text`. Serving it is no claim: the client checks it again against the definition whose hash it reads from the registry (part 2b-2).
- 2026-10-17 (P2-3 part 2e-2, `apps/worker`, `ViemL1Source`): the worker's L1 reference check reads finalized L1 blocks from one configured node and trusts its answers (only the chain ID, each block's number and a hash being present are checked). A lying or load-balanced node can cause wrong refusals at submission, which direct submission answers (T-25); it never changes what the verifier counts, which reads L1 itself.
- 2026-10-17 (P3-5 part 3a, `apps/worker` registry sync): definitions reach `election_definitions` only from `DefinitionRegistered` logs at or below the L2's finalized block that replay to the registry's accumulator there, under the deployment's pinned event check, and each is stored under the election the event names or the sync stops. The finalized head and the accumulator come from one configured L2 node and are trusted, as the L1 check's node is: a lying node can hold registrations back or, with a matching index, vouch for a definition the registry never registered, which the verifier, reading the registry itself, still refuses.
- 2026-10-17 (P3-5 part 3b, `apps/worker` registry sync): the sync's accumulator is now proven under an output root a dispute game claims on L1 ([[contracts]], Event accumulator, Output root), so a lying L2 node can no longer vouch for a definition the registry never registered; it can only hold registrations back. The L1 node is trusted for its finalized head and the game it names, as the L1 check's node is, and an unresolved game's root is its proposer's word ([[T-71]]).
