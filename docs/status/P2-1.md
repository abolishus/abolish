# P2-1: `packages/core` and Drizzle schema

- State: in review (part 2: appending through `@abolishus/crypto`, #54; part 1 merged in #42)
- Branch: `claude/p2-1`
- PR: #42 (part 1), #54 (part 2)
- Phase: Phase 2: Open polls end to end at Tier 0

## Scope

`packages/core` + Drizzle schema: append-only board tables (grants + triggers), the account/ballot no-join test, and migrations roles.

## Plan

Built in parts, each its own PR on this branch's name:

1. **Package, roles, migrations and the board table** (this part): `packages/core`, the two database roles, the migration runner, `board_entries` with its grants and triggers, and the no-join test.
2. **Appending through `@abolishus/crypto`** (#54): `appendEntry` computes the entry hash and link with the crypto package and inserts the row; `readBoard` reads it back. #40 made CI build `@abolishus/crypto` first.
3. **Rebuild from chain + IPFS**, when there are chain-index tables (P3-5) and IPFS mirroring (P4-3).

## Built (part 1)

- `packages/core`, private, AGPL-3.0-only, source-only. Dependencies: `drizzle-orm` 0.45.3 (no dependencies of its own) and `postgres` 3.4.9 (postgres.js, no dependencies).
- `src/db/roles.sql`: `abolish_migrator` and `abolish_app`, `NOLOGIN`, idempotent and safe to run concurrently; it pins both roles' attributes (no login, superuser, role or database creation, RLS bypass or replication) and refuses an `abolish_app` that is a member of `abolish_migrator`.
- `src/db/migrate.ts`: forward-only runner with a sha256 ledger. It refuses changed or missing applied migrations and takes an advisory lock per schema.
- `src/db/migrations/0000_board.sql`: `board_entries` with CHECKs on every field's length and range, append-only triggers (for every role, owner included), an append-order trigger (contiguous index, non-decreasing segment, `prev_link` = previous `link`, entry 0 from zeros), and grants (`abolish_app`: SELECT, INSERT). Payloads must start with an allowed record type (`0x0002`, `0x0003`, `0x0005`, `0x0006`, `0x0008`; [[board]]). Both trigger functions run with a fixed `search_path` (`pg_catalog`, the schema, then `pg_temp`), so a temporary table can't stand in for the board.
- `src/db/schema/`: the Drizzle table and `TABLE_CLASSES`.
- Decision: hand-written SQL migrations, no `drizzle-kit` (see the package README). A test ties the Drizzle schema to the migrated table.
- Threats: T-23, T-10.

## Tested

- As `abolish_app`: appending and reading a chain through Drizzle; UPDATE, DELETE and TRUNCATE fail; it can't disable triggers or drop the table.
- As `abolish_migrator` (the owner): UPDATE, DELETE and TRUNCATE fail; it can't set `session_replication_role`.
- A temporary `board_entries` created by `abolish_app` can't fake the previous entry (the in-session review's blocking finding; the test fails without the pinned `search_path`).
- `abolish_app` isn't a member of `abolish_migrator` and has no elevated attributes.
- Every append rule and field CHECK rejects its mutation, with the expected error code. A fast-check property interleaves well-formed appends with mutated ones and checks the table accepts exactly the well-formed ones.
- No-join: every table is classified, no foreign key touches a board table, and no board column has an account-like name.
- Migrations: idempotent; a changed or missing applied migration is refused; bad file names and schema names are rejected.

## Built (part 2)

- `@abolishus/core` depends on `@abolishus/crypto` (`workspace:*`), allowed by the architecture rules: core calls the gated code and never reimplements it.
- `src/board.ts`: `appendEntry` (encode, hash and chain with the crypto package; a transaction-scoped advisory lock per election; typed `AppendError` for an entry that doesn't encode, a decreasing segment, or a broken opening order) and `readBoard` (encoded entries in index order).

## Tested (part 2)

- A board appended through `appendEntry` passes `@abolishus/crypto`'s `checkBoard` on `readBoard`'s output, and the stored `entry_hash` and `link` columns equal what it recomputes; entry 0 chains from 32 zero bytes.
- 40 concurrent appends from 4 connections give indexes 0 to 39 and a verifiable chain, also when the connections default to REPEATABLE READ (`appendEntry` sets READ COMMITTED); without the advisory lock, or without the isolation level, a test fails.
- Boards of different elections stay separate.
- Each refusal: a decreasing segment, the four opening-order cases, payload types the board doesn't allow (definition, board entry, receipt, display text), a payload shorter than a header, election IDs that aren't 32 bytes, a string or number array where bytes are expected (refused, never coerced), and out-of-range segments. Nothing is written on a refusal.
- fast-check (capped at 200 runs against the live database, as `board.test.ts` does): random sequences of ballots and openings with random segment steps leave exactly the appends an independent model of the rules accepts, and the result passes `checkBoard`.

## Known-weak

- **The schema owner can bypass the triggers**: `ALTER TABLE … DISABLE TRIGGER`, `DROP TRIGGER`, replacing a trigger function, adding a rule or dropping a CHECK. A superuser-owned event trigger, or a third owner role no service belongs to, could close this; not done yet, so a malicious or mistaken migration could rewrite board rows. Postgres isn't authoritative: the rebuild from chain + IPFS and the anchored checkpoints catch it (T-23).
- **The table doesn't hash.** It checks that `prev_link` equals the previous `link`, not that either is the right hash. `appendEntry` computes them with `@abolishus/crypto`, but a writer that inserts directly as `abolish_app` could store wrong hashes; the verifier recomputes everything from the payloads, so that would show as a board that fails, not as a wrong result.
- **`appendEntry` doesn't decode payloads.** It enforces the envelope's rules only. Admission (P2-3) must decode each payload strictly under the election's profile before appending, or the board can carry undecodable bytes into the archive (T-17, [[board]], Allowed payloads).
- **The advisory lock's second key is 4 bytes of the election ID** (two-key form, class `0x0b0a4d`, separate from the migrations' one-key locks). Two elections sharing them only serialise each other's appends.
- **Core repeats the opening-order rule** as a pre-check, beside `checkBoard`, which stays the authority; the property test ties the two. A laxer copy would let the server write a board that permanently fails. Follow-up in a gated PR: export a per-step check (`checkNextEntry(prev, next)`) from `@abolishus/crypto` and call it from both.
- **The caller picks the segment.** Nothing checks it against the anchoring clock or the seal yet, so a caller bug that appends a far-future segment would refuse every later on-time append (`segment-decreased`) for the rest of the election. P2-3 and P4-1 must derive the segment from the clock, capped at the current period and `lastSegment`.
- **`readBoard` loads a whole board into memory.** Fine at Tier 0 scale; it needs paging or a stream before large elections.
- **The no-join column check matches names**, so a linking column with an innocent name would pass. Logs, caches and queues aren't covered yet (P2-3, P2-4; T-10).
- **Local sessions:** `roles.sql` runs `ALTER ROLE … NOSUPERUSER NOCREATEDB NOBYPASSRLS NOREPLICATION`, which only a superuser can do (a `CREATEROLE` user can't change those attributes), so these tests need a superuser. CI's service user is one, and since 2026-10-11 the session hook makes the local `abolish` user one too (owner change).
- **Deployments:** whoever applies `roles.sql` on staging or production needs superuser on that cluster. Check this before P2's first deploy, since managed Postgres may not grant it; if it doesn't, `roles.sql` needs a variant without the attribute changes.
