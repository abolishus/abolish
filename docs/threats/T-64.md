# T-64: Deployed bytecode differs from reviewed source

- Area: Development, supply chain and operations (G-14)
- Adversary: A-2, A-6
- Status: **Planned.**

## Threat

Deployed bytecode differs from reviewed source.

## Mitigation

Every deployed contract's source is verified on the explorer (P1-18); the verifier checks the bytecode at each address against the release build (P1-19). The release build is `forge build` alone (default profile), on a fresh runner in a job that runs no npm code, of the contracts commit on `main` the verifier's release pins, by the pinned forge from `packages/contracts` with no `.env` outside it and no `FOUNDRY_*`/`DAPP_*` variables or global config, with `out/build-info` removed and the remaining artifacts hashed before anything else runs there; never the output of the package's `vp run build`, which runs npm code after forge (`packages/contracts` README, Release build).

Index: [[THREAT_MODEL]].

## History

- 2026-10-12 (P1-18 part 5 follow-up): `crypto-review` on #109 found that the contracts package build now runs `@wagmi/cli`'s closure and any Prettier config it finds after `forge build`, with write access to `out/`, so a malicious dependency or config could rewrite bytecode identically in both `repro-build` builds without changing an ABI. The release build is now defined as forge-only; P1-19 (verifier 1.2) and P4-1's deployment must build that way. Nothing builds or consumes it yet.
- 2026-10-12 (P1-18 part 5 second follow-up): `crypto-review` on #112 found two more gaps. forge's own inputs (`.env`, `FOUNDRY_*`/`DAPP_*` variables, global config) could change the release build; now fixed by the definition. And 1.2 compares runtime code only, so a deployer's own initcode can pre-write storage (board-anchor checkpoint words the verifier would attribute to the authority) and still pass, in every contract 1.2 checks (the anchor's checkpoint words and archive locator, the registries' storage): **open**, to be designed (a pinned CREATE2 factory and an address recomputed from the release creation code, or the creation transaction bound with inclusion evidence) before anything is deployed.
