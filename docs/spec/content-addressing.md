# Content addressing

How board data becomes IPFS blocks, CIDs and CAR files, so that every party holding the same bytes can derive the same CID and CAR, and anyone can pin or re-upload a copy that matches what was published ([[0005-permanent-archive]], CID parameters). Threats: T-51 (data loss: independent pinners must reproduce our CIDs), T-49 (verification without us), T-24 (a gateway serving different data to different viewers can't pass a CID check).

Integrity never rests on a CID alone: every byte is checked against the L1-anchored roots (P1-16, P4-1). CIDs are for finding and deduplicating data.

## Parameters

IPFS implementations disagree on defaults (chunk size, leaf encoding, links per node), so every parameter is fixed here and implementations MUST set them explicitly. The values follow the `unixfs-v1-2025` profile proposed in [IPIP-499](https://github.com/ipfs/specs/pull/499). Two independent IPFS implementations, Kubo 0.36.0 (Go) and ipfs-unixfs-importer 17.1.1 (JavaScript), set to them, produce identical blocks and CIDs for every vector, and Kubo's `ipfs dag export` gives the same CAR as @ipld/car 5.4.7 writing those blocks in depth-first pre-order (Test vectors), so an independent pinner using either reproduces our CIDs (T-51). Kubo needs `Import.UnixFSFileMaxLinks` set to 1024 (its default is 174), `--cid-version=1 --raw-leaves --chunker=size-1048576`, and its defaults `--hash=sha2-256`, no `--inline` and no `--trickle` (with `Import.HashFunction` left at sha2-256); ipfs-unixfs-importer needs `rawLeaves: true`, `cidVersion: 1`, `reduceSingleLeafToSelf: true`, `leafType: "file"`, `fixedSize({ chunkSize: 1048576 })` and `balanced({ maxChildrenPerNode: 1024 })`.

| Parameter      | Value                                                                                                                                                                                                                                                                      |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CID version    | CIDv1                                                                                                                                                                                                                                                                      |
| Multihash      | sha2-256 (`0x12`), 32-byte digest                                                                                                                                                                                                                                          |
| Text form      | multibase base32, lowercase (`b` prefix)                                                                                                                                                                                                                                   |
| Leaf blocks    | raw (`0x55`), each holding one chunk of the object's bytes                                                                                                                                                                                                                 |
| Chunking       | fixed size, 1,048,576 bytes; the last chunk holds the remainder                                                                                                                                                                                                            |
| Interior nodes | dag-pb (`0x70`) UnixFS v1 `File` nodes: `Data` sets `Type = File`, `filesize` and one `blocksizes` entry per child, and nothing else (no `mode`, `mtime` or inline data); each link has an empty `Name` and `Tsize` equal to the total encoded size of the child's subtree |
| DAG layout     | balanced, at most 1,024 links per interior node: the chunks, left to right, are grouped into parents of up to 1,024, and those again, until one node is left                                                                                                               |
| Small objects  | an object of at most 1,048,576 bytes is a single raw block; its CID is that block's CID                                                                                                                                                                                    |
| Empty objects  | not allowed: nothing the protocol stores is empty                                                                                                                                                                                                                          |
| CAR            | CARv1 with the dag-cbor header `{roots: [root], version: 1}`, exactly one root (the object's CID), blocks in depth-first pre-order from the root, each block exactly once, no other blocks                                                                                 |

An object is any one encoded byte string the protocol stores: a board segment ([[board]], Segments and checkpoints), a display-text record ([[display-text]]), an archive manifest (P4-3) or a ballot-client release (P2-8).

Encodings, byte for byte as both implementations write them:

- A dag-pb node encodes its links (protobuf field 2) before its data (field 1), and each link its `Hash` (1), its empty `Name` (2, present with length 0) and its `Tsize` (3), in that order. The UnixFS `Data` encodes `Type` (1), `filesize` (3) and each `blocksizes` entry (4, not packed), in that order.
- A CID is `0x01 ‖ codec ‖ 0x12 ‖ 0x20 ‖ sha256(block)`, with `codec` `0x55` for a raw leaf and `0x70` for a dag-pb node.
- The CAR header is the dag-cbor map `{"roots": [root], "version": 1}`, keys in dag-cbor order (`roots` first), the root as tag 42 over `0x00 ‖ cid`; each block follows as a varint length, its CID and its bytes. Identical chunks (a run of zero bytes, say) share one leaf, which the CAR carries once, where the walk first reaches it.

## Reading by CID

A reader that knows an object's length `L` (an obligation root's leaf object, `64·c` or `128·c` bytes for its signed `count`, [[delivery]], Leaf availability) reads it from its sources block by block, walking only the DAG these parameters give for `L` bytes: `⌈L / 1 MiB⌉` raw leaves under a root of height `h`, the least with `1024^h` at least the number of leaves (0 for one leaf). A node of height `h > 0` is dag-pb, even with one child, and covers `1024^h` consecutive leaves from its first (the last node of a level fewer), so how many links it has, every node's size and `Tsize`, and the length of every leaf are fixed before anything is fetched. For each block the walk reaches, depth first and left to right, it asks its sources and reads the first answer of at most 1 MiB whose SHA-256 is the CID's digest; a longer answer is a failed fetch from its source, never hashed (no block of the layout is longer: a node of 1,024 links is under 64 KiB), and so is any other. A node is checked as soon as it is read, before any of its children is asked for. The read stops at the first of:

- **unavailable**: no source serves a block the walk reaches. It is never a verdict on the object: the sources may not hold it, or no one may.
- **inconsistent**: a CID the walk reaches isn't `0x01 ‖ codec ‖ 0x12 ‖ 0x20 ‖ digest` with the codec its place takes (raw at a leaf, dag-pb above), a leaf isn't exactly its chunk's length, or a node's bytes aren't exactly the node the encodings above give for its links' CIDs and the sizes and `Tsize`s its place fixes. Every block read hashes to its CID, so this is a function of the CID and `L` alone, and every source that serves the blocks gives it.

Otherwise the leaves, in order, are the object, and its `objectCid` is the CID. So no CID makes a reader fetch more blocks, or keep more bytes, than an object of `L` bytes has, whatever `filesize`, `blocksizes` or `Tsize` its nodes claim, and no source can make an object inconsistent or consistent (T-49, T-52, T-53, T-24). `packages/crypto`'s `readObject` is this reader.

### Reading within a bound

An object whose length no signed record fixes but only bounds, a board segment object whose length its checkpoints bound ([[board]], A copy from L1's CIDs), is read within a bound `M`. The reader asks for the root first, as the walk does, and takes the object's length `L` from it: a raw root's own length, which must be from 1 to 1 MiB, or a dag-pb root's `filesize` (its UnixFS `Data` field 3, after `Type`), which must be over 1 MiB, since an object of at most one chunk is one raw leaf and only those are. If the root carries no such length, the read is **inconsistent**, and if `L` is over `M` it is **over-bound** (with `L`), each before any other block is asked for. A raw root over 1 MiB is never hashed (Reading by CID), so it is **unavailable** from every source. Checking the root costs at most three node shapes per level of the tree its `L` gives, and the object is kept as its leaves arrive and hash, so a root's claim alone costs nothing that grows with it. Served blocks may repeat, though: a DAG of identical chunks has one distinct block per level, which any caching source serves again and again, so whoever chooses the CID can make a reader fetch and keep up to `L` bytes for the cost of a few blocks. `M` is therefore the reader's only bound, and a reader sets it to what it can spend, never only to what the protocol allows. Otherwise the object is read as above for `L` bytes, without asking for the root again. A canonical root's `filesize` is its object's length, so every outcome but unavailable stays a function of the CID and `M` alone. No CID makes a reader fetch or keep more than `M` bytes, or more than its object has, and no source can make an object inconsistent or consistent (T-49, T-52, T-53). `packages/crypto`'s `readObjectWithin` is this reader, and `readObjectAsync` and `readObjectWithinAsync` are the same readers over sources that wait on the network.

## Test vectors

`docs/spec/vectors/content-addressing.json` ([[vectors/README|vectors]]): objects of one byte, 100 bytes, one chunk exactly, one chunk and a byte, three chunks and two identical chunks under these parameters, each with its CID and CAR (whole when small, by length and sha256 otherwise); and the balanced layout's deeper trees (from one to 65 leaves, a partial last group at each level, identical chunks) under a small chunk size and fan-out no protocol object uses, since a second level needs more than a GiB at the real ones. Every CID is what Kubo and ipfs-unixfs-importer both produced, and every CAR is Kubo's `dag export`, matched byte for byte by @ipld/car writing ipfs-unixfs-importer's blocks in depth-first pre-order; the generator refuses any disagreement, and `packages/crypto/scripts/content-addressing-vectors.mjs` prints them. `packages/crypto` (`contentDag`, `objectCid`, `objectCar`, `cidText`) reproduces each, and `readObject` reads each back from its blocks (Kubo's, where the CAR is whole): under its own profile every one reads, and under the protocol's parameters the layout profile's trees are inconsistent, except the one-leaf tree, which is the same raw block.
