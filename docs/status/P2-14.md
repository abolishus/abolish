# P2-14: Multi-question ballots

- State: in progress (part 1a, definition version 5 and display-text version 2 in the spec with vectors, merged in #183; part 1b, ballot version 3, spoiled-ballot opening version 2 and the tally's question range in the spec with vectors, merged in #190; part 2, `packages/crypto`'s definition and display-text codecs, in progress)
- Phase: Phase 2: Open polls end to end at Tier 0

## Scope

Several questions on one ballot, cast once with one nullifier per poll and tier (or cell), one membership proof and one receipt, each question tallied on its own and never cross-tabulated, as the owner decided on 2026-10-12 ([[PROJECT_BRIEF]], Election types). The design is [[0026-multi-question-ballots]] (option B, the owner's; the flat option vector, the limits and the checks are the agent's under rule A): election-definition version 5 with a list of questions (method, option count, minimum and maximum selections each), display-text version 2 with a title and per-question text, ballot version 3 with one range proof per question beside the per-option proofs, the spoiled-ballot opening for its cores, `tally-question-range`, `MAX_QUESTIONS = 32`, `MAX_DISPLAY_TEXT` and at most `MAX_OPTIONS` options over the whole poll. Definition versions 1, 3 and 4 and ballot versions 1 and 2 are unchanged; a one-question poll under version 5 is the one-question case. Ranked-choice questions wait on the mixnet ADR ([[0003-tally-scheme]], [[P5-1]]).

## Notes

- Threats: T-28, T-30, T-31, T-32, T-34, T-41, T-42, T-45, T-47, T-16, T-17, T-52, T-29, T-36 ([[0026-multi-question-ballots]]).
- Known-weak, from the ADR: a small cell reveals every answer of its voters at once; a pick-exactly-N question can't be skipped (settled in part 1a: no blank; the voter leaves out the whole poll, or the creator asks pick up to N); blank counts are derivable only for questions with a maximum of one; more than 64 options in a poll needs new versions of every per-option record; ranked-choice questions aren't available.

## What was built (part 1a, #183)

- [[election-definition]], Layout (version 5) and Questions: `questions` (method, option count, limits) in place of version 4's one question, the flat index, methods as limits; well-formedness `questions`, `option-count` (each `m_q ≥ 2`, running total within `MAX_OPTIONS`, first failing question reported) and `selections` per question, at version 4's place in the order.
- The ADR's open point, settled by the agent (owner may veto; [[0026-multi-question-ballots]], What remains open; STATUS, Decisions to review): a pick-exactly-N question has no blank.
- [[display-text]], Layout (version 2): a title, per-question text and options, `MAX_DISPLAY_TEXT` checked on the input's length before decoding, rules `question-count`, `option-count`, `question`, `labels` (per question) and `question-texts`.
- [[parameters]] (`MAX_QUESTIONS`, `MAX_DISPLAY_TEXT`, `MAX_OPTIONS` over the whole poll), [[versioning]]'s registry, [[verifier]] 2.1, 2.3 (`profile-combination`: definition version 5 with ballot version 3 and display-text version 2 only, older definitions with display-text version 1) and 2.7. T-41 and T-52 history.
- `docs/spec/vectors/election-definition-v5.json` (34 vectors) and `display-text-v2.json` (34 vectors) from `packages/crypto/scripts/definition-v5-vectors.py`, written from the spec with the standard library, reusing the version-4 generator's values and rules; its encoder is checked against version 4's on a one-question definition.

## Tested (part 1a)

- `packages/crypto/tests/questions-vectors.test.ts` decodes every vector with codecs built from the files' own type descriptors (version 4's and display-text version 1's beside them, so mislabelled versions read the other layout), re-encodes it, recomputes the definition and stub hashes and the commitment, checks each decode error, and that the files label every question rule with its question.

## Known-weak (part 1a)

- No production codec or rule check reads either version yet (part 2); the well-formedness labels are checked only by the generator's own rules until then.
- No vector carries a record at or over `MAX_DISPLAY_TEXT`; consumers build one.
- The released profile check (`packages/crypto`, 2.3) doesn't yet refuse a definition of version 1, 3 or 4 pinning a display-text version other than 1; part 2 adds it with the version-2 codec.
- Until part 1b specifies ballot version 3 and its opening, no version-5 profile passes 2.3, so no version-5 election can be registered.

## Known-weak (part 1b)

- No production code reads ballot version 3, opening version 2 or `tally-question-range` yet (parts 3 to 5); the test-only reading above stops before `opening-ciphertext`, which part 3 checks with the production share encryption.
- `packages/crypto`'s `profileCombinationRule` doesn't know opening version 2 yet: a profile pinning ballot version 2 or 3 with it is `unsupported-version` (as the spec says for a version a release doesn't know), and one pinning ballot version 1 with it passes 2.3 where the spec now fails it, though 6.2 is then unverifiable, so no such election verifies. Part 3 adds opening version 2 and the rule.
- `ballot-v3.json` has no ballot records with membership proofs: admission is version 2's order with version 3's checks, and its vectors come with the verifier's reading (part 5).
- Part 1a's definition vectors pin opening version 1 beside ballot version 3 in their profiles; they exercise well-formedness only, which doesn't judge combinations, and 2.3 fails that profile.
