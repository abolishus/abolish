# @abolishus/crypto

The protocol core of [Abolish](https://github.com/abolishus/abolish): canonical encodings, ballot encryption, validity proofs, threshold decryption and the bulletin-board model. Depends only on `@noble/*`.

**Status: early.** The first APIs are the canonical encoding layer of [`docs/spec/notation.md`](../../docs/spec/notation.md) (P1-10), the group and hash layer of [`docs/spec/group.md`](../../docs/spec/group.md) (P1-11), and the bulletin board of [`docs/spec/board.md`](../../docs/spec/board.md) (P1-16); ballot commitments and proofs follow. Prereleases are published as `next`, signed and with provenance (see the repository README, "Releases").

## Canonical encoding

Strict encoders and decoders for the primitive types of the spec, following option A of ADR 0001 (explicit byte layouts):

- Primitives: `u8`, `u16`, `u32`, `u64` (a `bigint`), `bool`, `enum8([...])`, `bytesFixed(n)`, `bytesVar(max)`, `utf8(max)` (the exact bytes, never normalised) and `fieldBn254` (a `bigint` below `BN254_R`). `list(of, max)` and `struct([...])` compose them.
- `encode(codec, value)` and `decode(codec, bytes)` handle a value that isn't a record. Records go through a `RecordSchema` built from `recordType(number, { version: layout })`. Its `decode` requires the version the election's profile pins and rejects any other version (`profile-mismatch`, checked before the version is looked up, so it wins over `unknown-version`). Skipping that check means passing `UNPINNED` explicitly: tests and vector files do, and so does `decodeElectionDefinition`, because a definition carries its own profile and is checked against it once decoded. A production schema accepts only the record-type numbers the registry assigns. Inputs are copied once into a plain `Uint8Array`, so decoded values never alias the caller's buffer.
- Decoders reject and never repair. A `DecodeError` carries the spec's error code (`truncated`, `trailing-bytes`, `length-over-max`, `unknown-record-type`, `unexpected-record-type`, `unknown-version`, `invalid-enum`, `invalid-utf8`, `non-canonical`, `profile-mismatch`) and the offset where the failing field starts. Encoders throw `EncodeError` instead of emitting bytes the spec doesn't define (T-31).
- `ds(tag, m)` builds `u8(len(tag)) ‖ tag ‖ m`, only for a tag the registry marks specified. `TAG_REGISTRY` and `RECORD_TYPES` are checked against the spec's registries by tests.

## Election definition and display text

Version 1 of record types `0x0001` and `0x0009` ([`docs/spec/election-definition.md`](../../docs/spec/election-definition.md), [`docs/spec/display-text.md`](../../docs/spec/display-text.md)). Both are frozen by their vectors; a change is a new version (T-34, T-31). The entry point exports no generic record decoder, so a definition is decoded only with its self-pin check.

- Version 3 of `0x0001` (regional cells): `encodeElectionDefinitionV3`, `decodeElectionDefinitionRecord` (any version, with the self-pin check; `decodeElectionDefinition` returns version 1 and treats any other as `unknown-version`, so callers that read only version 1 refuse it), `electionDefinitionV3Hash`, `electionStubV3Hash` and `electionDefinitionV3Rule`. `foldRegions`, `firstOccurrence`, `deriveTierCells` and `tierElectorateMismatch` recompute a tier's region counts and cells from its groups' leaves (`docs/spec/election-definition.md`, Regional cells).
- Version 4 of `0x0001` (receipt keys, [`docs/spec/election-definition.md`](../../docs/spec/election-definition.md), Layout (version 4)): `encodeElectionDefinitionV4`, `electionDefinitionV4Hash`, `electionStubV4Hash` and `electionDefinitionV4Rule` (version 3's rules, then `receipt-keys`); `receiptKeyJudgement(record, opensAt, provenAt)` applies the judging rule (Receipt keys) to a listed key's registration and retirement times as read from the anchor's L1 record at a finalized block, for [`docs/spec/verifier.md`](../../docs/spec/verifier.md) 2.9 and the ballot client; `receiptKeyRecordFromWord(word, provenAt)` reads those times from a key's storage word, or refuses a word the release code can't write ([`docs/spec/contracts.md`](../../docs/spec/contracts.md), Board anchor, Receipt keys); and `receiptKeysCastCheck(words, opensAt, provenAt)` is the ballot client's check before casting (`receipt-key-unjudged` at the first listed key not registered before `opens_at` or retired by then). `scripts/definition-v4-vectors.py` prints `election-definition-v4.json` (`python3 -I -B packages/crypto/scripts/definition-v4-vectors.py docs/spec/vectors`, then `vp check --fix`).
- `encodeElectionDefinition` and `decodeElectionDefinition`. The decoder decodes strictly, then rejects with `profile-mismatch` unless the definition's own profile pins `0x0001` at the record's version. `electionDefinitionHash` is `H(DS("abolish/v1/election-definition", ·))`. `electionDefinitionRule` returns the first well-formedness rule a decoded definition breaks.
- `encodeDisplayText`, `decodeDisplayText` (against the version a definition pins), `displayTextCommitment` and `displayTextRule`, which a client runs before showing any text: commitment first, then shape.
- `checkElectionToShow`: every check software must pass before it shows an election to a voter or labels a Benaloh opening ([[display-text]], Checks): the definition decodes, names the election asked for, hashes to the hash the caller read from the L2 election registry, and is well formed, and the display text decodes under its pin and passes `displayTextRule`. Returns the decoded records or the first check that failed (T-34, T-41).
- `newDisplayTextSalt` draws 32 bytes from the platform CSPRNG (`@noble/hashes` `randomBytes`). `election_id` isn't drawn here: the election registry assigns it (P1-18).
- `PARAMETERS` mirrors `docs/spec/parameters.md`. The production record schema (these types and no others) stays internal.

## Group and hash

The prime-order group and hashes of ADR 0007 (option A), as thin wrappers over `@noble/curves` and `@noble/hashes` (T-39, T-31, T-30, T-15):

- `scalar`: 32 bytes little-endian, below `GROUP_ORDER` (ℓ), a `bigint`; a value at or above ℓ is rejected, never reduced. `element` and `elementOrIdentity`: the 32-byte RFC 9496 encoding of a ristretto255 `Element`; `element` rejects the identity. Both fail with `non-canonical`. The element encoder accepts only points built by `@noble/curves` and re-decodes its own output, so it writes nothing but valid encodings.
- `H(m)`: SHA-256. Plain hashes are `H(ds(tag, m))`.
- `challenge(tag, t)`: a Fiat–Shamir challenge, RFC 9497 `HashToScalar` with the tag as `DST`; it accepts only specified Fiat–Shamir tags (today the two ballot-validity tags, the two share-encryption tags and the ceremony's possession tag). `hashToGroup(tag, m)`: RFC 9380 `hash_to_ristretto255` under a specified hash-to-curve tag. Both always pass the `DST` to `@noble/curves`, which would otherwise use its own.
- `G` (the RFC 9496 generator), `GENERATOR_H` (`h = hash_to_ristretto255("", DST = "abolish/v1/generator-h")`) and `IDENTITY`.

## Ballot commitments and validity proofs

The public part of a plurality or approval ballot, per [`docs/spec/ballot-validity.md`](../../docs/spec/ballot-validity.md) (ADR 0002 option B, ADR 0003; T-15, T-28, T-30, T-32):

- `shareVote(rules, votes)` draws each option's sharing polynomials from the CSPRNG and returns the `VoteSharing`: the Pedersen VSS commitments (`vss`, the first of each option being its commitment `C_j`) and every trustee's shares. It refuses a vote the rules don't allow.
- `proveValidity(context, sharing, shareHashes)` adds an option proof per option and the sum proof, under challenges bound to `statementHash` (definition hash, ballot version, tier, nullifier, every commitment and every share-ciphertext hash). It returns the `CommittedVote`, which `COMMITTED_VOTE` encodes.
- `checkValidity(context, vote)` is the admission check: `validity-shape`, then `option-proof` (naming the option), then `sum-proof`. Its context comes from the registered definition and the ballot's own tier and nullifier, never from the committed vote.
- `checkShares(vss, index, shares)` is trustee `index`'s check of its shares (`SHARES`) against the VSS commitments.

The caller erases a `VoteSharing` once the voter casts. `ballotHash(context, vote)` names the ballot's public part: the statement hash's inputs followed by the validity proofs, which the membership proof's message and every share receipt bind.

The ballot record (record type `0x0002`, version 1; [`docs/spec/ballot-validity.md`](../../docs/spec/ballot-validity.md), Ballot record; T-28, T-38, T-17):

- `encodeBallot` and `decodeBallot` (`BallotRecord`): the definition hash, tier, nullifier, L1 reference and membership proof at fixed offsets, then the committed vote. A challenged ballot isn't one (P1-13).
- `ballotElection(definition, registered)` derives the context once: the definition hash, rules, each tier's root and scope, and the qualified seats, from a key set `checkCeremonyTranscript` returned for the transcript the definition names. `checkBallot` and `ballotSignals` take only contexts it made.
- `ballotSignals(election, ballot)` gives the public signals `[ρ, ν, F(M), ŝ]` a ballot's membership proof is made over; the ballot client proves over exactly these (P2-8).
- `checkBallot(election, ballot)` is the admission check of verifier 5.1 to 5.4, in order: `ballot-stray`, `ballot-tier`, `validity-shape`, `share-hash-unqualified`, `membership-proof`, `option-proof`, `sum-proof`. An admitted ballot gives its ballot hash and the `(tier, ν, M, l1_ref_number)` that `checkL1Reference` and `selectBallots` take next. The ballot client runs it on its own record before sending it.
- `stepBallot` to `stepBallotV4` run a ballot's admission checks up to its membership proof, and `finishBallotSteps(steps)` finishes many at once, their membership proofs verified together by `verifyDecodedMembershipProofs` and each ballot's validity proofs run only once its proof passes ([`docs/spec/ballot-validity.md`](../../docs/spec/ballot-validity.md), Batched admission). Every result is the one `checkBallot` (or its version's) gives the ballot alone; only steps these functions made are accepted (T-52).

## Share encryption

Each trustee's shares travel under the hybrid KEM of [`docs/spec/share-encryption.md`](../../docs/spec/share-encryption.md) (ADR 0002 option B, ADR 0016 option A; T-15, T-39, T-41): ML-KEM-768 from `@noble/post-quantum` combined with Diffie–Hellman in ristretto255, X-Wing style, and ChaCha20-Poly1305 from `@noble/ciphers`.

- `kemKeygen()` makes a trustee's per-election key pair: `KEM_PUBLIC_KEY` (the ML-KEM encapsulation key, modulus-checked, and the DH key) and `KEM_SECRET_KEY` (the ML-KEM seed and the DH scalar), every secret from the CSPRNG.
- `encryptShares(context, sharing, keys)` encrypts each seat's shares of a `VoteSharing` from `shareVote` to its registered key and returns the ciphertexts (`SHARE_CIPHERTEXT`), their hashes for `proveValidity` (`shareCiphertextHash`) and the encapsulation randomness, which the client keeps only until the voter casts or spoils.
- `openShares(context, seat, secretKey, vss, ciphertext)` is a trustee's decryption: `share-malformed`, `share-proof` (each ciphertext proves knowledge of its DH ephemeral, so no one can reuse another's), `share-decrypt`, then `share-check`.
- `intakeBallot(election, keys, record, ciphertext)` is a trustee node's whole intake of one delivered ballot ([`docs/spec/share-encryption.md`](../../docs/spec/share-encryption.md), Intake and receipts): the ballot record decoded strictly under the version `election` pins (`delivery-malformed`), the admission checks of verifier 5.1 to 5.4 with `share-hash` (the ciphertext is the one the ballot names for the seat) before the membership proof, then `openShares`'s checks. So a node receipts only a registered member's ballot (ADR 0002, Decision, 2026-10-12; T-52). Only if all pass does it sign a share receipt with the seat's per-election signing key over `shareReceiptStatement` (the definition hash, the ballot hash, the seat and the ciphertext's hash), and return it with the shares to store and what the re-vote rule ranks the ballot by. `intakeShares(context, keys, vote, ciphertext)` is the share half alone, with no membership check, for simulations whose ballots carry no proof; a node never receipts with it. `checkShareReceipt(registered, context, vote, seat, signature)` is anyone's check of a receipt (`share-receipt`): it builds the statement from the ballot itself and verifies it against the seat's registered signing key only.
- `checkPosting(context, seat, key, vss, shareHashes, posting)` is anyone's check of a ciphertext the client posted with its ML-KEM message: `posting-malformed`, `posting-hash`, `posting-proof`, `posting-encapsulation`.
- `proveComplaint(context, seat, keyPair, vss, shareHashes, posting)` reveals the DH value of a posted ciphertext with a Chaum–Pedersen proof (`COMPLAINT_PROOF`), and refuses unless the posting passes and its shares fail the trustee's own intake; `checkComplaint` checks the posting, the proof (`complaint-proof`) and that the shares really fail (`complaint-unfounded` otherwise).

`@noble/post-quantum` is self-audited only. The owner allowed it on testnets, with an audit before mainnet, in a hybrid with X25519 (ADR 0002, Decision); on 2026-10-12 the owner confirmed that this ristretto255 hybrid counts (ADR 0016). The audit covers the hybrid's combiner and composition too.

## Key ceremony

How a panel registers its per-election keys for one election (`docs/spec/ceremony.md`, ADR 0018; T-37, T-40, T-14, T-54):

- A seat's node: `ceremonyKeygen` (a fresh KEM key and signing key), then one call per round: `keysMessage` (keys, a Schnorr proof of knowledge of the DH key and the signing key's signature), `challengesMessage` (an ML-KEM encapsulation to every other seat, keeping the `μ`s), `answersMessage` (a pair-bound hash of each decapsulation) and `revealsMessage` (the `μ`s, once every answer is fixed; at most once per run). Before round 1 and before approving, a node also runs the stub checks of `docs/spec/ceremony.md`, which need L2 state and so live outside this package. Each refuses to sign over earlier rounds that fail the transcript check, or for a seat whose identity key isn't the caller's.
- `encodeCeremonyTranscript` and `decodeCeremonyTranscript` (record type `0x0005`, version 1), `ceremonyTranscriptHash` and `ceremonyContext`.
- `checkCeremonyTranscript`: verifier checks 3.1 and 3.2. It rebuilds the context from the election and the pinned panel, checks order, shape and every signature, works out each seat's disqualification reasons from the transcript alone, requires `k` qualified seats, and returns the registered key set.

## Delivery

Share delivery on the board, from [`docs/spec/delivery.md`](../../docs/spec/delivery.md) (ADR 0002, Deadline, Complaints and the owner's 2026-10-12 decision; T-41, T-29, T-25, T-54):

- The records: share receipts, postings and complaints (`encodeShareReceipt`, `encodeSharePosting`, `encodeShareComplaint` and their decoders; record types `0x000c` to `0x000e`, version 1, fixed by ballot version 1). A trustee node turns its intake result into a record with `shareReceiptRecord` and sends it through the contract path as well as the board path (the ballot client resubmits the receipts it holds too, docs/spec/delivery.md, Client rules), and signs a complaint with `signShareComplaint`. Board-entry version 3 carries receipts and complaints, never postings: a posting delivers only as a contract event.
- `deliverySegments`: the last segments in which a board-path receipt or complaint is in time; `deliveryDeadlines`: the deadlines a contract-path record's submission time is compared with; `deliveryWindowFits`: the bound on the anchoring clock and contract-event window that lets trustee nodes see every counted ballot and still send its receipts in time; `intakeCutoff`: `c_I = t_D − F − R`, when every trustee node decides what it owes and stops intake; `owedReceipts`: the receipts a trustee node owes through the contract path, at most two per tier and nullifier (the ballot the re-vote rule selects from its view, if it receipted its ballot hash, and its newest receipted ballot whose L1 reference fails), so its obligation is bounded by the electorate (docs/spec/delivery.md, What a node owes).
- A verifier: `checkDelivery` over the selected ballots and every delivery record in the counted extent, each with its path (a board entry's segment, or a contract event's submission time). A ballot stays counted only if every qualified seat has a passing receipt or contract-path posting in time and no complaint about it is proven; a board-path posting is a rejected entry; the verdict doesn't depend on the records' order.

## Tally

The homomorphic tally of [`docs/spec/tally.md`](../../docs/spec/tally.md) (ADR 0015 option C; T-29, T-54, T-16):

- A trustee's node: `aggregateCell`, `sumShares`, `checkSummedShares` and `openCell` (check every received summed share, combine the `k` lowest passing seats and check the result), then `signTallyOpening` with its per-election signing key.
- A verifier: `checkTally` over every tally opening on the board (`encodeTallyOpening` and `decodeTallyOpening`, record type `0x0006`, version 1): each cell's openings are checked in the order `tally-missing`, `tally-opening`, `tally-conflict`, `tally-range`; a passing opening counts whoever signed it, and every failing or stray opening is reported with the seat its signature attributes it to, or as unattributed. `deriveTotal` adds cells into coarser totals.

## Bulletin board

The board of `docs/spec/board.md` (T-23, T-24, T-42):

- `encodeBoardEntry` and `decodeBoardEntry` (record type `0x0007`, versions 1 and 3, always given explicitly; version 3 also allows the delivery records): the envelope of an election, a position, an anchoring segment and one payload record of a type allowed on the board, at most `MAX_BOARD_PAYLOAD` bytes. Only the payload's header is read; the record itself is decoded where it is used.
- `boardEntryHash`, `chainLink` and `checkpointHash`: `H` under `abolish/v1/board-entry`, `abolish/v1/board-chain` and `abolish/v1/board-checkpoint-2`. A checkpoint (version 2, ADR 0029) also names the CIDs of the segment object and entry-hash list of its last entry's segment, so the board can be fetched by CID from L1 alone.
- The RFC 9162 Merkle tree, generic over its two hashes (`TreeHash`), with `BOARD_TREE` using tagged `H`: `merkleRoot`, `merkleRoots` (every requested prefix root in one pass), `inclusionProof`, `consistencyProof`, and `verifyInclusion` and `verifyConsistency`, which return false for any malformed argument and never throw.
- `verifyBoard` checks one election's board against every anchor for it, given the anchoring clock (`AnchorClock`) and the latest finalized L1 time. Only timely anchors count (`isTimely`). It checks only the prefix those anchors cover and ignores entries past it. Within that prefix it checks strict decoding, election, positions, segments, the order of spoiled-ballot openings, equivocation, each checkpoint's boundary and CIDs (`checkpoint-cid`, the anchoring authority's), unanchored segments and the seal, after first checking the copy's raw bytes against every anchored head and root (a mismatch, `copy-mismatch`, means the copy is wrong, not the election; `checkpoint-inconsistent`, a checkpoint no board can match, from L1 alone or against the copy, fails the election, attributably to the anchoring authority). A failure throws a `BoardError` with the spec's code. `checkBoard` runs the entry checks alone, and `checkpointOf` builds the checkpoint after a segment.

## Content addressing

From [`docs/spec/content-addressing.md`](../../docs/spec/content-addressing.md) (T-51, T-49, T-24): `contentDag(object)` turns one stored object (a board segment, a display-text record, an archive manifest) into its IPFS blocks under the spec's fixed parameters (1 MiB raw leaves, a balanced tree of dag-pb UnixFS `File` nodes of at most 1,024 links), `objectCid` gives its binary CIDv1, `cidText` the base32 text form and `objectCar` its CARv1. dag-pb, UnixFS and the CAR header are written by hand as the few shapes the spec allows. Every value matches what Kubo and ipfs-unixfs-importer both produce (`docs/spec/vectors/content-addressing.json`). `readObject` reads an object of known length back from any sources' blocks by its CID, and `readObjectWithin` one whose length is only bounded (a segment object), each walking only the canonical DAG; `readObjectAsync` and `readObjectWithinAsync` take sources that wait on the network. `readBoardCopy` reads a board copy from the CIDs its counted checkpoints name (`docs/spec/board.md`, A copy from L1's CIDs). A CID only finds bytes: integrity is checked against the L1-anchored roots.

## Receipts

What a voter keeps after casting through the API (`docs/spec/receipts.md`, ADR 0013; T-25, T-26, T-24):

- `encodeReceipt` and `decodeReceipt` (record type `0x0004`, version 1), and `receiptStatement`, the 173 bytes the operator signs under `abolish/v1/sig/receipt` with the trustee signature suite. `signReceipt` is the operator's side.
- `checkReceiptAtCast`: before the client tells the voter the ballot was received. Rebuilds the entry from the payload the client sent and checks the pinned key, the signature, the election, the segment and the audit path. The later checks are P1-13b's.

## Benaloh challenge

Cast-as-intended by challenge and spoil (`docs/spec/challenge.md`, ADR 0021; T-42, T-44, T-47):

- `coreHash`, the tracking code over a ballot's nullifier-independent core (`abolish/v1/ballot-core`); `ballotCoreHash` computes it from a cast ballot record and `openingCoreHash` from an opening. `ballotCore(election, tier, encrypted)` is the core of shares `encryptShares` made (a zero hash for each seat outside the registered key set), and `trackingCode` its hash, the code the client shows before the cast-or-challenge choice; the client proves over that core's share hashes, so the code shown, the core opened and the core cast come from one place.
- `openedCommitments(opening)` and `opensBallotCommitment(opened, ballot)`: what a published opening opens, built once per opening, and whether a ballot carries any of it: an opened `C_j = E_{j,0}`, or `h^s` or `g · h^s` for a scalar `s` the opening reveals (any coefficient of `f_j` or `g_j`, any seat's shares, any seat's `e_i` or `w_i`) other than the public 0 and 1, which would let one ballot carrying `g` or `h` block every opening. Whether a published opening would open a cast vote (`opening-cast`, the checker's warning) is decided by this, never by tracking codes; randomness derived by a chosen relation is a residual. It takes an opening that passed `checkChallengeOpening`.
- `encodeOpening` and `decodeOpening` (record type `0x0003`, version 1): the core, both sharing polynomials of every option and every registered seat's encapsulation randomness.
- `openChallenge(election, tier, encrypted)`: the client's side. It opens only shares `encryptShares` made, for this election, to the registered keys, and marks the sharing opened, so `proveValidity` refuses it; it refuses a sharing that was proved. An `EncryptedShares` holds every seat's encapsulation randomness, and this package keeps a private copy for `openChallenge` as long as the object lives: once the voter casts, the client copies out the `ct_i` and `m_i` it may still need and drops the whole object (T-18, T-45).
- `checkChallengeOpening(election, opening)`: anyone's check, rebuilding every VSS commitment and every registered seat's ciphertext; a passing opening gives its core hash and votes, and `withinRules: false` for a vote no valid ballot could carry. The board's publication rules (`opening-cast`, `opening-early`, `opening-late`, `opening-repeat`) are the verifier's.

## Membership

What Abolish derives around Semaphore v4's membership circuit (`docs/spec/membership.md`, ADR 0009; T-12, T-13):

- `nullifierScope(definitionHash, tier, root)`: `S_g = H(DS("abolish/v1/nullifier-scope", definition_hash ‖ u8(tier) ‖ root))`, one scope per poll and tier group, even for tiers with equal roots. `membershipScope` maps it into the field as the circuit's scope input.
- `semaphoreField(x)`: Semaphore's `hash`, `keccak256(x) >> 8`, for 32-byte inputs.
- `MEMBERSHIP_DEPTH`: 32, the one tree depth (and so verification key) every membership proof uses, so no server can steer it.

The proofs themselves (`docs/spec/membership.md`, Verification key, Proof encoding and Tier tree; T-03 to T-07, T-38):

- `verifyMembershipProof(proof, signals)`: Groth16's verification equation under Semaphore's pinned depth-32 key, on `@noble/curves`' BN254 pairing. Fails on a proof that doesn't decode, a signal at or above `r` and a root of 0.
- `membershipProof`, `decodeMembershipProof`, `encodeMembershipProof`: the 256-byte `membership_proof`, A ‖ B ‖ C in EIP-197's encoding, every point canonical, on its curve, in the order-`r` subgroup and not the identity.
- `membershipVkHash()`: the election definition's `membership_vk_hash`, over the depth, the key and the proving key's sha256 (`MEMBERSHIP_ZKEY_SHA256`).
- `poseidon2(a, b)`: circomlib's two-input Poseidon over BN254, on `@noble/curves`' permutation with constants from its Grain generator.
- `tierTreeRoot(leaves)`, `tierTreePath(leaves, index)`, `tierTreeZeros()`: the depth-32 tier tree verifiers rebuild from a group's additions. `replayTierGroup(events)` is the lenient replay for group contracts without a signed sequence; the group registry's groups replay strictly through `applyGroupRecords`.

The ballot client's side of a proof (`docs/spec/membership.md`, Security notes; ADR 0009, Amendment of 2026-10-17; T-05, T-07, T-12):

- `membershipProverInput(secret, leaves, statement)`: the circuit's inputs for snarkjs (`MembershipWitness`, a path of exactly 32 siblings at the voter's first leaf, rebuilt from every leaf of the tier) and the public signals, each derived here: the scope from the definition hash, tier and root, `F(M)`, and `ν = Poseidon2(ŝ, s)`. Refuses (`MembershipProverError`) a secret that isn't an identity secret (`secret`), a voter who isn't a leaf (`not-a-member`) and leaves that don't climb to the definition's root (`root`), before any proving.
- `checkMembershipZkey(zkey)`, `checkMembershipWasm(wasm)`: refuse (`zkey`, `wasm`) a proving key that isn't `semaphore-32.zkey`, and a witness calculator that isn't `semaphore-32.wasm`, by sha256 (`MEMBERSHIP_ZKEY_SHA256`, `MEMBERSHIP_WASM_SHA256`). `packages/membership-prover` checks both before every proof.
- `finishMembershipProof(input, proof)`: the prover's proof verified under the pinned key against `input`'s signals (only inputs `membershipProverInput` built are accepted), re-randomised as `(t⁻¹·A, t·B + t·u·δ₂, C + u·A)` with CSPRNG scalars and verified again; refuses with `proof` or `rerandomised`. Only its output leaves the device. Run it in a realm the prover's code can't reach.

Sealing a version-3 ballot, the only way the ballot client reaches the plaintext votes and the encryption randomness (`docs/spec/ballot-validity.md`, Casting (version 3); `docs/spec/challenge.md`, Client rules; T-42, T-45, T-47, T-55):

- `sealBallotV3(election, cell, votes)`: the sharing, each registered seat's shares encrypted to its registered key and the core's tracking code (`SealedBallotV3`), shown before the voter chooses. A seat outside the registered key set has no ciphertext and a zero share hash.
- `challengeSealV3(sealed)`: the encoded opening (`0x0003` version 2) of exactly that core; the seal is then never cast.
- `castSealV3(sealed, secret, leaves, l1)`: `ν` under the cell's scope, the validity proofs (kept for every later cast of the seal, so a retry or a recast under a newer L1 block carries the same committed vote), the ballot hash, `M` and the prover's witness (`BallotCastingV3`), with `membershipProverInput`'s refusals before any proving. A cast seal is never opened, and never cast with another identity.
- `finishSealV3(casting, proof)`: the proof finished by `finishMembershipProof`, the record assembled, its core checked against the code shown and the record run through `checkBallotV3`; returns the encoding, the ballot hash, `ν` and each qualified seat's ciphertext for its intake (`CastBallotV3`), or throws (`BallotSealError` with the admission code). Nothing here sends anything.

The proving key's reference string was checked well formed, once and publicly, by `scripts/membership-crs-check.ts` (`docs/spec/membership.md`, Reference-string check; T-07, T-12). Its tests run on a toy key; set `MEMBERSHIP_CRS_DIR` to a directory with `semaphore-32.zkey`, `ppot_0080_14.ptau` and `semaphore-32.r1cs` to rerun it on the real one.

## Circuit-facing values

How tags and bytes become BN254 field elements, exactly as `packages/circuits` does in Noir (`docs/spec/notation.md`, Circuit-facing values; `docs/spec/domain-separation.md`, In-circuit hashes; T-30, T-31):

- `circuitTagField(tag)`: `int(H(DS("abolish/v1/circuit-tag", tag))) >> 8`, the constant by which a tag enters a circuit, only for a tag registered In-circuit (none yet), so no plain-hash tag gets a second layout (T-30).
- `packBytes(bytes)`: `bytes[N]` as `ceil(N / 31)` big-endian chunks. `packBoundedBytes(bytes, max)`: the length, then the content zero-padded to `max` and packed.

## Rules

- Runtime dependencies are `@noble/*` only, pinned to exact versions in the workspace catalog, with an `@noble`-only transitive closure, no node built-ins and no workspace imports. CI's `gated` check (`.github/tools/ci/src/gated.ts`) enforces this from the lockfile, the `src` imports and the packed bundle, which must inline nothing from `node_modules` (T-55, T-36).
- No primitive is implemented here. Every hash, curve, cipher and KDF comes from the audited `@noble/*` libraries; this package composes published protocols, cited in `docs/spec/`.
