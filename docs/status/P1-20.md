# P1-20: Reference election fixture

- State: in progress (part 1, the runner with the key ceremony, Anvil anchoring and the verifier's run, in review; each later stage comes with the item that builds it; the `ci:` part that arms the check waits until every stage is covered)
- Branch: `claude/p1-20`
- Phase: Phase 1: Threat model, spec, crypto core, circuits, verifier, reference election (CLI only)

## Scope

Reference election fixture (`vp run reference-election`), CLI only: ceremony → tiers (stubbed until Phase 3, with the stubs clearly marked) → cast/challenge/re-vote → direct submit → close → threshold decrypt → tally → anchor (Anvil) → wipe + rebuild → independent verification offline. Makes the `reference-election` check real. The same PR sets `EXPECT_FIXTURE: "true"` in `.github/workflows/reference-election.yml` (a `ci:` change), so removing the script later fails the check. The workflow must call a fixed, owner-reviewed entry point rather than whatever the root script says, independently run `packages/verifier` over `reference-election-output/`, and require the transcript to cover every stage the brief lists.

## Plan

The fixture grows with the items it proves, so it is built in parts:

1. **The runner** (this part): `apps/reference-election` and the root `reference-election` script, with stage 1 (the key ceremony), stage 7 in part (anchoring on Anvil) and stage 9 in part (the verifier in a process of its own over the output bundle). `stages.json` lists every stage with its coverage, so a run never reads as the whole proof.
2. **Each later stage** with the item that builds it (stages.ts names them): the ballot record and casting (P1-12, P1-13), the tally (P1-15, once there are ballots), direct submit (P1-18 part 4, P4-2), registration and groups (P2-5, P2-6, P3-2 to P3-4), the wipe and rebuild (P2-1, P4-3) and verification from chain and IPFS alone (P4-6). Every feature PR extends the fixture (AGENTS.md).
3. **`ci:` arming** (owner review): `EXPECT_FIXTURE: "true"`, a fixed entry point in the workflow rather than the root script, the verifier run independently over `reference-election-output/`, and `stages.json` required to show every stage `covered`. It waits until that is true, since the check would fail before.

## What was built (part 1)

- `apps/reference-election` (internal, AGPL-3.0-only, no domain logic) and the root `vp run reference-election`, which builds `@abolishus/crypto`, `@abolishus/verifier` and `@abolishus/contracts` and runs the fixture uncached.
- Stage 1: a 4-of-7 panel with fresh identity keys runs the four ceremony rounds through `@abolishus/crypto`, every seat taking part ([[0006-trustees]] rule 7); the definition (plurality, three options, the profile with board-entry version 4) binds the transcript, which binds its stub hash (T-37, T-34). The display text is real and committed to, though nothing shows it yet.
- Stage 7, in part: `BoardAnchor` from forge's build on Anvil with a 1-hour period and the 12-hour deadline; the ceremony's segment and the seal anchored inside their windows from a stub authority; a finalized header rebuilt to RLP and checked against its block hash, and `eth_getProof` nodes for the lowest-segment word and every segment's word.
- Stage 9, in part: `packages/verifier` from its built package, in its own process with an empty environment, over the bundle directory alone (T-36). 3.2, 4.1 and 4.2 must pass, no check may fail, and the verdict must be `unverifiable` (every input is a local file), with the matching exit code. A control copy with one transcript byte flipped must not pass 3.2.
- Every stub is named in `STUBS` and written to `stages.json`: placeholder L2 addresses, a placeholder Tier 0 group and membership key hash, the panel as a local file, the authority, and a seal one segment after the ceremony's.

## Tested (part 1)

- The run itself, locally and as the `reference-election` check: exit 0 with 3.2, 4.1 and 4.2 passing.
- Mutation by hand: anchoring a seal whose head is zeroed fails the run (4.1 not reached, 4.2 `l1-checkpoint-unknown`).
- `apps/reference-election/tests`: the RLP encoder against the published examples and a fast-check round trip through an independent decoder (`FC_NUM_RUNS`); the anchor calldata's one canonical layout as a property; a Prague header from Anvil rebuilt to its hash, and a changed or missing field refused; the report expectations (each required row, a failed row, a failed or verified verdict, a wrong exit code, the control); the nine stages in order.

## Known-weak (part 1)

- Stages 2 to 6 and 8 aren't covered, and 7 and 9 only in part: the check proves a ceremony, its board and its anchors, not an election. `stages.json` says so on every run.
- The check isn't armed: until the `ci:` part sets `EXPECT_FIXTURE`, a PR that removes the root script turns it back into a warning.
- The verifier's verdict is `unverifiable` by design: the definition, panel, header, clock and first segment are local files, and 3.1 (the trustee registry on L2) isn't implemented. The run checks that the rows that can pass do.
- The seal is chosen by the fixture (the segment after the ceremony's), not computed from the definition, since no post-close window is fixed yet.
- The clock starts one period before Anvil's genesis time, and the fixture moves Anvil's time forward to anchor; nothing runs in real time.
