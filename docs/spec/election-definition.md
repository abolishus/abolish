# Election definition

The election definition fixes everything about an election that a result depends on: its profile, its rules, its electorate, its trustee panel, its timing, where it lives on chain and which display text it commits to. Its hash is registered on L2 before voting opens and bound into every ballot and proof, so none of this can change after voting opens or differ between voters (T-34). This page specifies versions 1, 3, 4, 5 and 6 of record type `0x0001` ([[versioning]]) and the definition hash. Notation and decoding rules are from [[notation]]. Threats: T-34, T-31, T-30, T-32, T-17, T-28, T-35, T-37, T-16, T-26, T-69, T-14, T-54.

Version 1 is frozen by its vectors ([[versioning]], Frozen; [[0008-draft-record-layouts]]). Items not yet written own several of its fields (the panel and ceremony from P1-14, the electorate and verification key from P1-17, the contracts and timing from P1-18); a change any of them needs is a new version, and version 1 is then retired. Version 3 (Layout (version 3), below) replaces the electorate with regional cells ([[0019-regional-cells]]; P1-15). Version 4 (Layout (version 4), below) adds the receipt keys that judge the election's receipts ([[0023-receipt-evidence]]; P1-13b). Version 5 (Layout (version 5), below) replaces the one question with a list of questions ([[0026-multi-question-ballots]]; P2-14). Version 6 (Layout (version 6), below) adds the poll class, the results mode and the author panel ([[0027-trustee-panels-and-live-results]]; P2-16). Versions 1 and 3 bind no receipt keys, so a receipt in their elections is never evidence a third party can attribute ([[receipts]], Receipt keys): both MUST be retired ([[versioning]], Change rules, Old versions stay verifiable) with a cutoff before the first election registry is deployed (P1-18), so every election a deployed registry admits is version 4 or later. Version 2 is never assigned: a frozen vector of version 1 (`definition-version-unknown`) uses it as the version that has no layout, as [[board]] leaves its own version 2 unassigned.

Every field is a fixed format: integers, enums, a `field<bn254>`, and `bytes[N]` holding hashes, addresses or a CSPRNG output. The definition carries no free text; the election's question and option labels are in its display text ([[notation]], Result-critical fields; T-17). The residual of [[notation]] applies, and T-17 records it: a creator can hide chosen bytes in `display_text_commitment` (`election_id` is a hash output the registry assigns, [[contracts]], Election registry), which only the report-only check 2.7 compares with real text, and chosen bits in every integer whose value is only bounded, not fixed: the low bits of `opens_at` and `closes_at`, `l1_inclusion_bound`, the high bits of `sequencing_window` and `max_sequencer_drift` (2.6 only requires the chain to stay within them), and `root_l2_block` (any block at which the root was unchanged). So a malicious creator can put somewhat over 70 bytes of their choice into the permanent archive per definition, and about 180 more in fields only the verifier checks against the chain and its pins (the roots, group IDs and sizes, `membership_vk_hash` and the pins of types 2 to 9; [[verifier]] 1.3, 2.3, 2.4), since such a definition is still registered and its registration event archived. [[ceremony]] (Stub checks) closes the second part by having trustee nodes run those checks on the stub before taking part in a ceremony and before signing its registration. P1-18's timing bounds narrow the integer part. Version 3 adds the creator's grouping of each tier's groups into regions, a few chosen bits per group, and its roots and counts, which only the verifier checks against the board, as it does version 1's. Version 4 adds up to 4 receipt keys, about 32 chosen bytes each (any `x` on the curve), which only the verifier checks against the anchor's receipt-key record on L1 (2.9), and the ballot client before casting: a definition listing a key the anchoring authority never registered fails, but is still registered on L2 and archived, since the L2 registry can't read L1. Version 5's questions add a few chosen bits in bounded integers (up to 32 questions, each an option count and two limits within it), and nothing a verifier can't check from the definition alone. Version 6 adds `live_every` and `live_batch` (both 0 when sealed) and up to 16 author keys, about 32 chosen bytes each (any `x` on the curve), which nothing on chain checks. `author_transcript_hash` is in the default panel's stub, so the default seats' registration binds it (Stub hash and the ceremony); a default seat takes part only once the author panel's approved transcript, hashing to it, is on the board with approvals under `author_keys` (P2-16 part 3), so a definition whose author keys no one holds is never registered, as [[ceremony]] (Stub checks) does for the stub's other fields. Until part 3 specifies that check it is a residual (T-17). `live_every` and `live_batch` are bounded below only, so a live definition carries about 8 chosen bytes in them, and one whose schedule outlasts the poll or whose batch exceeds its electorate never releases a running total; [[P2-15]] bounds both against the poll's timing and electorate (a 2.6-style check) or records the residual.

## Layout (version 3)

Version 3 has every field of version 1, in the same order with the same types and meanings, except `electorate`, which becomes a list of `tier_electorate`, so a tier can be split into regional cells ([[0019-regional-cells]]; T-16):

| Field        | Type                       | Meaning                                                                       |
| ------------ | -------------------------- | ----------------------------------------------------------------------------- |
| `electorate` | `list<tier_electorate, 3>` | One entry per tier that may vote, with its groups, regions and cells (below). |

`tier_electorate`:

| Field           | Type                       | Meaning                                                                                                                                                                                                                                                |
| --------------- | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `tier`          | `enum8<0, 1, 2>`           | The identity tier, a label as in version 1: a verifier takes every group's tier from the group registry, and a definition whose label disagrees for any of the tier's groups fails ([[verifier]] 2.4).                                                 |
| `root_l2_block` | `u64`                      | The one L2 block at which every group of the tier is read, every count is taken and every cell tree is built. It is strictly before the L2 block that registers the definition (The electorate is in the past, below).                                 |
| `groups`        | `list<region_group, 1024>` | The tier's groups, in strictly ascending `group_id`, each naming the region it belongs to.                                                                                                                                                             |
| `regions`       | `list<u64, 1024>`          | `regions[i]` is region `i`'s member count at `root_l2_block` (Regional cells, below). The verifier recomputes it from the board and fails a definition that states another value ([[verifier]] 2.4, T-13, T-16).                                       |
| `cells`         | `list<cell, 256>`          | The tier's cells, as the fold derives them from `regions` (Regional cells): each region at or above the floor, in region order, then the remainder cell. The creator states them; the rule `cells` and the verifier recompute them ([[verifier]] 2.8). |

`region_group`:

| Field      | Type  | Meaning                                                                                                             |
| ---------- | ----- | ------------------------------------------------------------------------------------------------------------------- |
| `group_id` | `u64` | The group's identifier in `group_registry`, as in version 1.                                                        |
| `region`   | `u16` | The index in `regions` of the region the group belongs to. Each group is in exactly one region of exactly one tier. |

`cell`:

| Field     | Type           | Meaning                                                                                                                                                                  |
| --------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `root`    | `field<bn254>` | The root of the cell's cell tree at `root_l2_block` ([[membership]], Cell tree). Ballots in the cell prove membership against this root and no other ([[verifier]] 5.1). |
| `members` | `u64`          | The cell's member count: the sum of its regions' `regions` entries, so its anonymity set, reported with its results ([[verifier]] 8.1, T-16).                            |

A definition's **cells** are numbered in order, `0, 1, …`: the cells of its first `tier_electorate`, then those of the next. A cell's number is its **position in the partition**, the value a ballot names to say which cell it was cast in ([[0019-regional-cells]], Ballot version 2; P1-12).

The limits keep a definition small whatever it lists: at most 1,024 groups and 1,024 regions per tier, and 256 cells in the whole definition (the rule `cells`), so a definition is at most about 90 KB. The cell limit is the range of the `u8` `cell` that tally-opening version 1 and the summed-share message carry ([[tally]]); a fold that would give more cells can't be stated, and the creator must draw coarser regions. A national referendum by state fits, and so does one by congressional district (435 regions) as long as at most 256 of them, with the remainder, are cells; a precinct-level split doesn't, and would need later versions.

### Regional cells

How a tier's groups become its regions' counts and its cells, the owner's rule ([[0006-trustees]], Small cells) as [[0019-regional-cells]] applies it. Every step is computed at the tier's `root_l2_block`:

1. **Leaves.** Each group of the tier is replayed as [[membership]] (Tier tree, Commitments and removals) replays a tier group, giving its leaves in index order, 0 for a removed or forbidden addition. Then the **first-occurrence rule** ([[membership]], Cell tree): walking the tier's groups in ascending `group_id`, each group's leaves in index order, a nonzero leaf equal to a nonzero leaf earlier in the walk is set to 0. So one commitment counts at most once per tier, in the first group that holds it (T-01, G-2).
2. **Region counts.** Region `i`'s member count is the number of nonzero leaves of its groups after step 1.
3. **The fold.** With `F = MIN_CELL_ELECTORATE` ([[parameters]]), a region is **large** if its count is at least `F` and **small** otherwise. The candidate cells are each large region on its own, in region order, then one **remainder cell** holding every small region, if there are any. The tier is **split** into the candidate cells if there are at least two of them and either there is no small region or the small regions' counts sum to at least `F`. Otherwise it isn't split: it is one cell holding all its regions. A tier that isn't split has no floor; its size is reported, and 8.2 flags it when small.
4. **Cells.** A cell's groups are its regions' groups, in ascending `group_id`; its tree is the cell tree over their leaves after step 1 ([[membership]], Cell tree); its `members` is the sum of its regions' counts.

The fold is fixed: no region at or above the floor is ever merged to rescue a split, and no region is withheld. The creator chooses only which groups make up each region, before voting opens, never from turnout or ballots ([[0019-regional-cells]], Recommendation; T-16, T-34). A region of one tier with one group, and so a tier with one region of one group, gives exactly version 1's tier: one cell whose tree is that group's tier tree (unless a commitment repeats in it, which step 1 counts once).

| Field          | Type                | Meaning                                                                                                                                                                                                                                                                                        |
| -------------- | ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `receipt_keys` | `list<p256-key, 4>` | The receipt keys ([[receipts]], Receipt keys) whose receipts are evidence for this election, each a `p256-key` ([[trustee-identity]], Identity key), in strictly ascending order of their 33-byte encodings. At most 4, so the operator can rotate a key during an election without a new one. |

### Receipt keys

`receipt_keys` is in the stub (Stub hash and the ceremony, below), so the creator fixes it before the ceremony, and every key that judges the election's receipts is fixed before voting opens: no release, operator or later definition can add or drop one (T-26, T-34).

A listed key **judges** the election if the receipt-key record of the anchor that `l1_anchor` names ([[contracts]], Board anchor, Receipt keys), read from L1 state at a finalized L1 block `B` whose timestamp is at or after `opens_at`, holds `0 < registered_at < opens_at` and either `retired_at = 0` or `retired_at > opens_at`. Both are L1 `block.timestamp` values, compared with `opens_at` as numbers. A block at or after `opens_at` settles the question: a later registration or retirement has a later timestamp, so it is after `opens_at` and changes nothing for this election, which is why a retirement never voids receipts already given. So every key that judges an election was registered by the anchoring authority before voting opened and wasn't retired by then, and evidence under it is the anchoring authority's alone ([[0023-receipt-evidence]], option A).

- [[verifier]] 2.9 fails a version-4 election any of whose listed keys doesn't judge it.
- Before casting, the ballot client reads the record for every listed key at the latest finalized L1 block it knows, from L1 state as a verifier does, and refuses to cast (`receipt-key-unjudged`) unless each is registered with `registered_at < opens_at` and not retired with `retired_at ≤ opens_at`. During the first minutes of an election that block is still before `opens_at`, so a retirement between it and `opens_at` can't be seen yet; such a retirement fails the election (2.9), which the client's later checks report ([[receipts]], Verdicts, `board-failed`), and only the anchoring authority can make it, on L1, where it is attributable.
- The board operator signs receipts for an election only under a key its definition lists ([[receipts]], Signing).
- The anchoring authority registers a key well before any election lists it (a day ahead, say), since a registration counts only if it is before `opens_at` in L1 time, and L2 timestamps, which `opens_at` otherwise meets, may run ahead of L1's by up to `max_sequencer_drift`.

| Field            | Type       | Meaning                                                                                                                                                                                                                          |
| ---------------- | ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `method`         | `enum8<1>` | 1, selection: each of the question's options is selected or not, the number selected lies in `[min_selections, max_selections]`, and the question is tallied by `tally_scheme` 1. Ranked choice takes a later value and version. |
| `option_count`   | `u16`      | `m_q`, the question's number of options, named by index 0 to `m_q − 1` within the question; only the display text says what they mean ([[display-text]], Layout (version 2)).                                                    |
| `min_selections` | `u16`      | Least number of the question's options a counted ballot selects.                                                                                                                                                                 |

### Questions

- **Flat index.** Option `j` of question `q` has the flat index `o_q + j`, where `o_q = m_0 + … + m_{q−1}`, and `T = m_0 + … + m_{Q−1}` is the poll's total option count, at most `MAX_OPTIONS` (`option-count`, below). The ballot, the shares, the openings and the tally work over the `T` options in flat order, question-major; results and display text name an option by (question, option).
- **Methods are limits.** The owner's four methods are ranges: pick one is `(0, 1)`, pick any is `(0, m_q)`, pick up to N is `(0, N)` and pick exactly N is `(N, N)`. The definition carries the limits the validity proof enforces and no label that could disagree with them, so the instruction a voter reads is rendered from `(min_selections, max_selections, m_q)`, the values the proof checks (T-34, T-41). Any other range the rules allow (pick one with an answer required, `(1, 1)`; pick two to four) is valid; which ranges the creation screens offer is P2-9's.
- **Pick exactly N has no blank.** Under `(N, N)` with `N ≥ 1` a ballot selects exactly `N` of the question's options, so a voter who wants to leave that question blank can only leave out the whole poll; the range is contiguous, so no version-5 question allows `{0, N}` alone. A creator who wants a skippable question asks pick up to N. Settled in [[0026-multi-question-ballots]], What remains open; a skippable form needs a new definition version.
- **No cross-tabulation.** Nothing in the definition relates two questions: each is tallied on its own, and no joint figure is ever opened ([[0026-multi-question-ballots]], No cross-tabulation).
- **One question.** A version-5 definition with one question is the one-question poll: its options are version 4's, and its limits are any version 4 allows (version 4's plurality is `(0, 1)`, its approval any range), with no `election_type` beside them.

### Poll class and results

- **The class decides the register and the panel, not the protocol.** A poll of class 2 or 3 is on the civic record: it is shown in the civic-record register, and it may run only under a default panel its release pins with the kind `independent` ([[verifier]] 2.5, `panel-kind`; Pinned trust roots there). A class-1 poll is shown in the everyday register and may run under any pinned panel, the transitional one included ([[0027-trustee-panels-and-live-results]], Part 3, rule 2). A creator who labels a civic question everyday gets an everyday poll, shown as one with the transitional label, never a poll on the civic record. Definitions of versions 1 to 5 carry no class and are everyday polls.
- **Civic referendums are always sealed** (owner, [[PROJECT_BRIEF]]): the `civic-sealed` rule. Organisational votes may be live; whether they should is an open question for the owner ([[0027-trustee-panels-and-live-results]], Open questions).
- **Everything about releases is fixed before opening.** `results_mode`, `live_every` and `live_batch` are in the stub (Stub hash and the ceremony, below), so no one, the author and the operator included, chooses when running totals are released or how large a batch is after seeing the board (T-16, T-34). Which ballots a release counts, the batch rule and the running opening are [[P2-15]]'s. The running opening's version is fixed by the pinned tally-opening version, never pinned itself, as the summed-share message's is, so `profile-types` is the same for sealed and live polls.

### Author panel

- **No author panel** is `author_threshold` 0, `author_keys` empty and `author_transcript_hash` zero: the poll's ballots open under the default panel alone, as under version 5.
- **With one**, each ballot's opening is split additively in two, the default half shared to the default panel and the author half to the author panel, so a ballot opens only with `threshold` default seats and `author_threshold` author seats together, and the author panel can never lower secrecy below the default panel's (T-14). The ballot's two sharings, and every receipt, posting, complaint and opening naming its seat's panel, are [[P2-16]] part 2's; each panel's ceremony and tally are part 3's.
- **Its identifier** is `author_panel_id` ([[trustee-identity]], Author panel identifier), recomputed from `author_threshold` and `author_keys`, never stored. Its validity, `1 ≤ k_A ≤ n_A ≤ MAX_TRUSTEES` with distinct keys (`author-panel`, below), allows `k_A = 1`; that no author key is a default seat's is [[verifier]] 2.5's (`default-seat`), since only the release pins the default panel's keys.
- **Not pinned.** Releases pin default panels; an author panel comes from the definition alone, checked off chain by the verifier, the ballot client and every default seat before any share is made, since a bad author panel can only stop a poll, never weaken it ([[0027-trustee-panels-and-live-results]], How the ceremonies compose). A creator, or the operator assembling the stub, who substitutes author keys leaves the poll with the default panel's protection, never less, but the author would believe otherwise (T-37): each author trustee's node checks that the registered definition names its own key, and the creation flow and evidence view show each key's fingerprint.
- **Liveness.** If fewer than `author_threshold` author seats take part at the tally, the poll can never be counted, by anyone (T-54). The author trustees' display names belong in the display text, as the author's claim; the display-text version that carries them comes with the creation screens ([[P2-16]], part 7).

## Definition hash

```
definition_hash = H(DS("abolish/v1/election-definition", encode(definition)))
```

`encode(definition)` is the record's full canonical encoding, header included. `definition_hash` is what the election registry stores, what the nullifier scope is derived from (P1-17) and what every Fiat–Shamir statement in the election starts from ([[domain-separation]]), so it binds the chain IDs, contract addresses and `election_id` into every proof made after the definition exists (T-30, T-32). Key-ceremony proofs come first and bind the stub hash instead (below).

## Stub hash and the ceremony

The key ceremony runs before the definition is registered, so its proofs can't bind `definition_hash`, which includes the ceremony's own transcript hash. They bind the stub hash instead:

```
stub_hash = H(DS("abolish/v1/election-stub", encode(stub)))
```

where `stub` is the definition with `ceremony_transcript_hash` replaced by 32 zero bytes, header included.

Under version 6 a poll with an author panel has two ceremonies, run one after the other ([[0027-trustee-panels-and-live-results]], How the ceremonies compose, as amended by P2-16 part 1a):

```
author_stub_hash = H(DS("abolish/v1/election-stub", encode(author_stub)))
```

1. The author panel's ceremony runs first and binds `author_stub_hash`, where `author_stub` is the definition with both `ceremony_transcript_hash` and `author_transcript_hash` replaced by 32 zero bytes.
2. The default panel's ceremony then binds `stub_hash` as above, whose stub keeps `author_transcript_hash`: the hash of the author transcript a quorum of the author panel approved. Every default seat checks that transcript and its approvals before its round-1 message (P2-16 part 3).

So the default seats' ceremony registration, which the trustee registry records and the election registry checks, binds the author panel's transcript too. Once the default panel has approved, no one can register the definition with other bytes in `author_transcript_hash`, an abandoned author run's transcript, or another author transcript of the same author stub (T-17, T-34, T-37). The cost is that the ceremonies are sequential, so a poll with an author panel takes two ceremonies' time to open. With no author panel the two stubs are the same bytes, and only the default ceremony runs. The creator fixes every other field, `election_id` and the electorate roots included, before asking the panel for a ceremony.

- The ceremony context ([[domain-separation]], Fiat–Shamir) binds `stub_hash` as well as the chain ID, registry address, `election_id`, panel and run identifier. `trustee_registry` records the pair (`stub_hash`, transcript hash) only with signatures over both by the identity keys of a panel the deployment pins, never on `msg.sender` alone (P1-14, P1-18).
- The election registry admits a definition only if its stub hash is the one `trustee_registry` recorded for its `ceremony_transcript_hash`. The check compares hashes and never relies on `msg.sender` alone ([[0004-l2-choice]], T-71).
- Verifier 3.1 rebuilds the context with the stub hash recomputed from the definition being verified.

So a default panel's transcript is valid for exactly one definition (under version 6 the author panel's transcript is valid for every definition sharing its author stub, and the default panel's registration picks the one): a definition that reuses another's `ceremony_transcript_hash` but differs in any other field, its registry addresses and chain IDs included, fails 3.1 wherever it is registered. Without this binding, anyone who saw the transcript hash on L2 could register their own options, electorate or timing under the victim's ceremony (T-34, T-37).

`election_id` is unique by construction, because the registry assigns it ([[board]]); the registry admits a definition for an `election_id` only from whoever created that election, and only once: it stores one definition hash per `election_id`, write-once (P1-18). Otherwise a creator could register two definitions under one `election_id`, serve each to different voters on the one board, and have one group's ballots rejected at admission while the other definition verifies (T-34, T-24). Nothing else is first-come: `ceremony_transcript_hash` need not be unique, and neither the registry nor a verifier rejects a repeat, since the stub hash already makes a transcript valid for exactly one definition. A first-come uniqueness rule over values that someone other than the creator learns before registration (any trustee, or whoever relays ceremony messages) would let them block or retroactively fail a legitimate election by registering a definition that can never verify (T-25).

## Decoding

A definition carries its own profile, so no version can be pinned before it is read. It is decoded in two steps:

1. Decode the bytes strictly as record type `0x0001` with no pin ([[notation]], Strict decoding).
2. Take the pins for `0x0001` in the decoded `profile.pins`. Unless there is exactly one, at the record's own `version`, reject with `profile-mismatch`. A second pin for `0x0001` is a mismatch wherever it appears, so the result doesn't depend on which pin a decoder finds first.

Step 2 means a definition can only be read under the layout its own profile names, so once a second definition version exists, no one can create an election under a retired layout by labelling it with an older version byte (T-34, T-31; [[verifier]] 2.3).

Notes:

- **Tally partition.** In version 1 the partition is the tiers only: one cell per `electorate` entry. Because entries are in strictly ascending tier order, no tier is repeated and each cell is exactly one tier; the electorate is the list of tiers, so none is omitted ([[verifier]] 2.8). In version 3 the partition is every tier's `cells`, numbered as Layout (version 3) says: each cell lies in one tier, the cells of a tier hold all its regions and each region is in exactly one cell, so the cells of one tier partition it and the tiers' totals are sums of cells, derived, never opened ([[0002-everlasting-privacy]], Tally). Version 4's partition is version 3's, and so is version 5's. Versions 3 and 4 need a ballot that names its cell: a profile pinning definition version 3 or 4 must pin ballot version 2, which does, and ballot version 2 pairs with no other definition version ([[ballot-validity]], Ballot record (version 2); [[verifier]] 2.3, `profile-combination`). Until a spoiled-ballot opening version opens version-2 cores ([[challenge]], Versions), 2.3 refuses every profile pinning ballot version 2, so versions 3 and 4 can't yet be registered. Version 5 needs a ballot with one range proof per question, so a profile pinning definition version 5 must pin ballot version 3 and display-text version 2; ballot version 3 pairs with definition version 5 only, and display-text version 2 with versions 5 and 6 ([[verifier]] 2.3, `profile-combination`); ballot version 3 and the opening of its cores are P2-14 part 1b's, and until they are specified no version-5 election can be registered. Version 6's partition is version 5's. A profile pinning definition version 6 must pin display-text version 2 (display-text version 2 pairs with definition versions 5 and 6) and the ballot version [[P2-16]] part 2 specifies, which carries the author half beside the default half (empty with no author panel); until that version exists [[verifier]] 2.3 refuses every version-6 profile (`profile-combination`), so no version-6 election can be registered, and a live one also waits on [[P2-15]]'s tally-opening version.
- **What well-formedness doesn't check.** Whether the verifier supports each pinned version, and whether any is retired or broken ([[verifier]] 2.3, 8.3); whether the roots, group sizes, panel and ceremony hash match the chain and the board (2.4, 2.5); whether the timing bounds held (2.6); the close rule itself (P1-18).
- **A group's tier.** `tier` is the creator's label. A verifier takes each group's tier from the group registry, which fixes a group's tier when it creates the group (P1-18, P3-2), and counts an addition toward a tier only if its authorisation binds that tier's group ([[verifier]] 2.4). A definition whose label disagrees fails [[verifier]] 2.4. Otherwise a group of sock-puppet Tier 0 commitments could be reported as a Sybil-resistant Tier 2 result (T-01, T-06, T-08).
- **The electorate is in the past.** Each tier's `root_l2_block` (version 3: each `tier_electorate`'s, which every cell of the tier uses) is strictly before the L2 block in which the election registry records the definition, so every addition behind a root is public on L2 before anyone can vote against it. This is a chain-context check, like `opens_at ≥ epoch`: a definition that breaks it fails [[verifier]] 2.4, and P1-18's registry rejects any definition with a tier whose `root_l2_block` is at or after the registering block. Before casting, the ballot client checks that `root_l2_block` and the definition's registration are both in finalized L2 history and that the root it rebuilt from the additions up to that block equals `root` (version 3: its cell's root, rebuilt from every group of the tier, and that its own leaf is the counted occurrence in the region it registered in, [[0019-regional-cells]], Consequences); otherwise it refuses to cast and alarms. No honest flow needs a later block, since the root is fixed in the stub before the ceremony. Otherwise an insider operating a group's signer could name a future block and commit to the root of a planned addition sequence (honest registrants plus sock puppets) while holding the additions back: honest voters couldn't rebuild the root or prove membership during the poll, the insider's own commitments could, and posting the additions after close would make the election verify with the whole group reported as the anonymity set (T-08, T-13, T-25, T-34).
- **The panel is checked before any share exists.** `panel` well-formedness only rules out `k = 1`. Before making any share, the ballot client checks that (`panel_id`, `threshold`, `panel_size`) equals a panel its release pins, and that every key a share is encrypted to comes from the transcript `ceremony_transcript_hash` names, signed by that trustee's pinned identity key. Trustee nodes run the same checks before receipting a share ([[verifier]] 2.5, 3.1). Under version 6 the client and every seat of both panels also check the author panel before any share exists: its validity against the default panel (`default-seat`), its keys from the transcript `author_transcript_hash` names, and, for a poll on the civic record, the default panel's kind. Otherwise a creator could set `threshold = 2` against a 4-of-7 panel: shares made at that threshold can't be taken back when 2.5 fails afterwards (T-14, T-37).
- **Deadlines owned elsewhere.** Which ballots count also depends on the share-delivery deadline and the complaint window of [[0002-everlasting-privacy]]. Version 1 has no fields for them: both are constants of the delivery records' version 1, which the pinned ballot version fixes ([[delivery]], Windows), so no operator can choose one after seeing the board (T-34, T-25, T-35). The re-vote rule's window on L1 block references is a protocol constant of [[revoting]], not a definition field.
- **The seal.** [[board]]'s `lastSegment`, the last anchoring period an election's board may use, is a function of the registered definition and of constants fixed before the election exists, never a value anyone supplies per election: `lastSegment = ⌊(closes_at + l1_inclusion_bound + W − epoch) / period⌋`, computed over unbounded integers, the period containing the end of the last post-close window.
  - `W`, in seconds, is the latest end, counted from `closes_at + l1_inclusion_bound`, of every post-close window, where a window ends when its entries must be on the board (the operator's boarding latency included), not when they are sent: publishing spoiled-ballot openings (ending at `t_S + OPENING_WINDOW`, a constant of opening version 1 counted from the counted extent's due checkpoint, so it ends with the tally window: [[challenge]], Publication), the trustees publishing the tally and their destruction statements (P1-15; every profile pinning tally-opening version 1 pins board-entry version 4, which carries them, [[verifier]] 2.3; [[tally]], Destruction window), and contract events and close-time accumulator data going from submission to the board, as one summed contract-event window ([[tally]], Tally window; P1-18). Each window is a constant of the record version the profile pins (openings, P1-15) or of the immutable contracts the definition names (P1-18), never set per election, by a verifier release or by an operator. P1-18 justifies the post-finality window against the L2's worst-case settlement delay: events that settle after it miss the seal, and the election fails (T-50, T-53).
  - `epoch`, `period` and the anchoring `deadline` are the anchoring clock of the anchor contract `l1_anchor` names: immutable, and the same for every election through it (P4-1). A verifier release pins that contract's address and its deployment's clock, never a clock value for one election, since a `deadline` chosen after close could make an honest checkpoint untimely or a late one count.
  - A definition with `opens_at < epoch` fails ([[verifier]] 2.6), and P1-18's registry rejects it: no ballot is cast before the anchoring clock starts, and the seal is never before the period containing `opens_at`.
  - Version 1 binds no anchoring authority of its own, so a version-1 election uses the one its verifier release pins for `l1_anchor` ([[board]], Anchoring).
  - If any window has to vary per election, version 1 can't carry it, and version 2 must be specified before any election registry is deployed (P1-18).

  Otherwise whoever supplied the seal could choose it after seeing the board: seal before the tally is boarded, so the election has no verifiable result (T-54, T-53), or seal late, to admit a second tally or late openings (T-23, T-24). A third-party verifier couldn't recompute it either (T-36).

- **What gets admitted.** The creator-chosen bytes counted above assume that only well-formed definitions reach the board and the archive. P1-18's registry admits a definition only if it is well formed and its chain IDs and addresses are the deployment's own; otherwise a strictly decoding but ill-formed definition could carry about 700 chosen bytes (T-17).
- **Tally scheme.** Version 1 lists one scheme, which both election types use, so `tally_scheme` needs no rule beyond its enum. A later version that adds a scheme adds a rule pairing schemes with election types.
- **Civic elections.** Versions 1 to 5 have no marker: the panel is identified by `panel_id`, and every such election is an everyday poll. Version 6's `poll_class` is the marker the owner's decision on trustee panels needs ([[0027-trustee-panels-and-live-results]], Part 3): a class on the civic record needs a default panel the release pins as `independent` ([[verifier]] 2.5, `panel-kind`), so no poll under the transitional panel is ever on the civic record.
- **Timing bounds.** Well-formedness doesn't bound `l1_inclusion_bound`, `sequencing_window` or `max_sequencer_drift`: zero is accepted. What values the close rule needs is P1-18's to specify, with a rule here.
- **Approval with a minimum.** For approval, and for any version-5 question, `min_selections` lets a definition require a non-blank answer. The validity proof proves the range, so a ballot outside it is rejected at admission ([[verifier]] 5.4).
