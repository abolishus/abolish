# P4-2: Direct submit end to end

- State: in progress (part 1, the ballot client's direct submission to the board contract in `packages/sdk`, merged in #297; part 2a, the forced path's client through the L1 relay in `packages/sdk`, merged in #308; part 2b, the relay's price measured against the real portal on a testnet, next)
- Branch: `claude/p4-2`
- Phase: Phase 4: Censorship resistance

## Scope

Direct-submit path, end to end, with servers refusing.

## Plan

The contracts are P1-18's (the board, its ballot check and the L1 relay); this item is the client side and the end-to-end proof.

1. **The board's ordinary path** (this part): a client in `packages/sdk` that sends a cast ballot record to the board contract on L2 through the voter's own wallet, with the board's refusals decoded, repeats found rather than resent, and the board's event confirmed.
2. **The forced path:** the same ballot through the L1 relay (`relayBallot`) when the sequencer censors the voter, with the gas limit the board's check needs, watching for the deposit's `RelayedBallotSubmitted` on L2 (part 2a); and the relay's price, which [[contracts]] (Board, Known-weak) leaves to this item to measure (part 2b): only the real `OptimismPortal` meters deposits, so it is measured against the relay and portal on a testnet, read-only (`eth_estimateGas` needs no key), once the relay is deployed there.
3. **The ballot client's fallback** in `apps/ballot`: when our API refuses or can't be reached, or the operator's receipt fails its checks at cast ([[receipts]], Checks at cast), offer direct submission, telling the voter that the paying account is public (T-25, Residual) and that a direct-submitted ballot still needs its receipts or postings ([[delivery]], Client rules).
4. **The reference election's stage 5:** a ballot submitted directly while the API refuses it, counted from the board's event. Waits on casting in the reference election ([[P1-20]] part 2b), which waits on a membership prover: the board admits only ballots whose Groth16 membership proof verifies.

## Part 1

- `packages/sdk/src/direct-submit.ts`, exported from the package:
  - `directSubmitBallot` takes an EIP-1193 provider, the definition's `l2_chain_id` and `board`, the paying account, the record and the block to search for copies from (the election's registration block). It holds no key, and the record's definition and ballot hashes are `@abolishus/crypto`'s `frameBallot`'s, never the caller's. One call is one attempt: it refuses a wallet on another chain, checks again after sending, and names the chain in the transaction (T-34, T-41); asks the board with `eth_call`, without the account, and returns its refusal without sending (so a voter's gas isn't spent on a revert), and does the same for a refusal at the estimate; looks for a byte-identical copy the board already holds, from either path (`BallotSubmitted`, or a relay deposit's `RelayedBallotSubmitted`), since a repeat is a silent no-op on chain ([[contracts]], Board, Calls, Repeats; Relayed ballots; T-17); and otherwise sends the call with a quarter more gas than the estimate (the membership check reverts unless the pairing's gas is left) and reports where the board's event is: from the board, not removed, under the record's definition and ballot hashes, carrying the record whole, in its own transaction's receipt. A reverted transaction is reported by the board's answer afterwards (the window closed, gas ran short, or another call put the bytes on first).
  - `submitBallotCalldata`: `submitBallot(record)` in the one encoding the board accepts (`CanonicalCalldata`).
  - `decodeBoardBallotRevert`: the board's revert data as the spec's codes, in the contracts' enum order: `malformed` (a decode error and its offset), `refused` (an admission code), `window`, `gas`, `calldata`, and `unknown` for anything else, including a known error with extra bytes or a code past the enum.
  - `revertDataOf`: the revert data wherever a node or wallet puts it in its error; an error without it (a rejected request, a network failure) is passed on.

## Known-weak (part 1)

- The paying account is public and linked to the ballot on chain, so funding it can link the voter (T-25, Residual; T-11); the client neither chooses nor checks the account, and the warning to the voter is part 3's.
- What the client reports is what the provider's node says. A wallet's node can lie about a log or a receipt, so `submitted` and `already-on-board` are never grounds to stand down: until a storage proof covers the event, the voter's client keeps resubmitting by every path ([[delivery]], Client rules; [[contracts]], Contract-event record). Checking the event against the board's event accumulator is left to the client rules' later checks.
- The search for an earlier copy reads from the caller's `fromBlock` to the head in one request; a public RPC that caps `eth_getLogs` ranges fails it, as a provider error, for a long election.
- A refusal is the provider's report too: a censoring RPC can forge one, so the ballot client (part 3) must confirm a refusal through a node the voter chose before giving up on this path.
- No forced path yet: a sequencer that censors the voter's transaction leaves the ballot off the board until part 2's relay path, and a transaction that never lands ends in `receipt-timeout`.
- No end-to-end run with our servers refusing until the reference election casts (part 4).

## Part 2a

- `packages/sdk/src/relay-submit.ts`, exported from the package:
  - `relayBallot` takes the voter's L1 wallet (EIP-1193), a read-only L2 provider, the definition's `l1_chain_id`, `l1_relay`, `l2_chain_id` and `board`, the paying L1 account, the record and the L2 block to search from. It holds no key. One call is one attempt, and each call that lands is paid for and archived (the board takes every relayed deposit it accepts, repeats included), so before sending it: frames the record as the relay does, locally (`relay-too-large`, `relay-truncated`, `relay-record-type`), asking no node; checks each provider's chain (T-34, T-41) and that the relay's `board()` is the election's board; looks for a relayed copy of the record the board already holds whose call the relay's stored word matches (read with `eth_call` on L1, so a deposit L2 governance forges from the alias, which 4.5 rejects, never stops it; T-71) and returns it (`already-relayed`) rather than paying for another, never counting an ordinary copy, whose batch the sequencer can withhold past `L_δ` ([[contracts]], Relayed ballots, No repeats on this path), and before asking the board, so a copy is found after close too; asks the board on L2 with `eth_call` from the relay's alias, with the relay's next index, the next L1 block and the L1 head's time as the stamp, and returns its refusal decoded (`decodeRelayedBallotRevert`: the ordinary path's codes, `window` from `RelayWindow` with the stamp, and `sender` for a board deployed for another relay), sending nothing; gives the deposit the board's own `eth_estimateGas` from the alias and a quarter, never below `relayDepositGasFloor`, what the deposit needs by its size alone whatever a node answers (its intrinsic gas at EIP-7623's floor price with every call word at its widest, the membership check's pairing reserve of about 610,500, 40 gas a record byte for the ballot check, about twice what framing costs, and 150,000 for the rest), nor below the OP Stack portal's floor of 21,000 and 40 a byte of deposit data (`portalMinimumGasLimit`), so an L2 node that understates its estimate can't make the deposit run out of gas, which the verifier would read as the caller's mistake (T-50); asks the relay with `eth_call`, without the account, and returns its refusal decoded (`decodeRelayRevert`); and returns `over-cap` without sending when the L1 estimate, which includes the portal's metered burn at the current deposit price, passes EIP-7825's 2²⁴ (`MAX_TRANSACTION_GAS`), or the node finds no estimate under its cap (an error without revert data saying so), sending otherwise with a quarter over the estimate, capped at 2²⁴, and the chain named. After the receipt it requires the transaction to come from `from` (the account is linked to the ballot for good; T-11), takes exactly one `BallotRelayed` event of the relay in its own transaction, under the record's definition hash, reads the stamp from the call's block by its hash, recomputes the call hash (`@abolishus/crypto`'s `relayCallHash`) and requires the stored word to equal it (`event-mismatch` otherwise), and returns the call: index, L1 block, stamp, gas limit, call hash, transaction and block. A reverted transaction is reported by the relay's answer afterwards, or as `reverted`.
  - `findRelayedBallot`: the board's `RelayedBallotSubmitted` on L2 carrying the record and naming exactly the call's index, L1 block, stamp and gas limit, or `undefined` while the deposit hasn't been included.
- `packages/sdk/src/direct-submit.ts`: a relayed event's location now carries the call it names (`call`), and the ordinary client's search takes an optional filter, which the relay's uses to count only relayed copies; `wrong-relay` joins the error codes.

## Known-weak (part 2a)

- The price isn't measured yet (part 2b): the tests' portal records deposits without metering, so what a forced ballot costs on L1, and how far a filled deposit market raises it, is known only from the OP Stack's metering rules. The client protects against it only by estimating the call at the current price and refusing past 2²⁴ (`over-cap`).
- The board is asked at the L1 head's time, but the call is stamped by the block it lands in, seconds later: a ballot relayed in the last seconds before `closes_at` can be accepted by the question and refused on L2 (`relay-window`), leaving a recorded call with no event, the caller's loss. A client relays well before close ([[contracts]], Board, Known-weak, The window is the block's time).
- The size floor is a generous bound from the record's size and Board, Gas's figures, not a release-pinned per-version figure: a future ballot version whose check costs more than 40 gas a byte beyond the pairing could need more, and a node that understates its estimate could then still starve it. Pinning the board's cost per ballot version in the release, as delivery's capacity figures are, would close it.
- A call made but not yet included on L2 isn't found: the search reads the board only, so a client that relays again before the deposit arrives pays for a second copy. The caller keeps the call `relayBallot` returned and waits on `findRelayedBallot`; the ballot client's handling of that is part 3's.
- What the client reports is what the providers' nodes say: a node can hide a relayed copy (the voter pays for another) or show a false one (the voter doesn't relay), and a refusal can be forged. As on the ordinary path, `relayed` and `already-relayed` are never grounds to stand down until the event is derivable from finalized L1 through a node the client chose ([[delivery]], Client rules), and part 3 confirms a refusal through a node the voter chose.
- The paying L1 account is linked to the ballot for good, in the call, the portal's log and the deposit (T-25, Residual; T-11); the client neither chooses nor checks it, and the warning is part 3's.
- No end-to-end run with the sequencer censoring until the reference election casts (part 4).

## Independent review (part 2a)

A fresh in-session subagent reviewed the diff against `.github/review/crypto-review.md`.

- **Blocking, fixed:** the deposit's gas limit rested only on the L2 node's estimate, so a node that understated it (plausibly the censoring sequencer's own RPC) could make the deposit run out of gas on L2, read by the verifier as the caller's mistake. The limit now never falls below `relayDepositGasFloor`, which no node's answer lowers, and an Anvil test relays through a node that answers every estimate with 21,000 and shows the deposit accepted at that floor.
- **Fixed:** a relayed copy is taken only if the relay's stored word matches its call, so a deposit forged from the alias doesn't make the client stand down (T-71); the copy is searched before the board is asked, so a ballot already relayed is found after close; a node's "needs more than the cap" error is `over-cap`; the receipt's sender must be `from` (T-11); a full relay's count is no longer a bad response.
- **Known-weak, not fixed:** retrying before a deposit reaches L2 pays for a second copy, since only the board is searched (above); scanning the relay's L1 logs is left to the ballot client, which keeps the returned call (part 3).
