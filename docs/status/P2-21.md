# P2-21: The membership prover in the ballot client

- State: in progress (part 1, the prover's choice ([[0009-membership-proof]], Amendment), merged in #PR; its owner asks open; part 2, the prover core in `packages/crypto` (inputs, key check, self-verification, re-randomisation), next)
- Branch: `claude/p2-21`
- Phase: Phase 2: Open polls end to end at Tier 0

## Scope

The ballot client's side of [[membership]]: from a voter's identity secret, their tier's additions and an election definition, produce the 256-byte `membership_proof` a ballot carries, in the Web Worker, on the voter's device. Nothing in the workspace proves membership today ([[P1-17b]] verifies, [[P2-8]] and [[P5-4]] were left to prove), so the API's admission ([[P2-3]] part 2d) and the verifier's 5.1 reject every real ballot. This item is the gate in front of casting: [[P1-20]] part 2b (the reference election's casting stage), [[P2-8]] part 3 (sealing and sending), [[P2-20]]'s sending, Done and receipt screens, and so every ballot on staging.

The obligations are already written; this item builds to them, it doesn't reopen them:

- **The circuit and keys.** Semaphore v4.14.3's circuit and Groth16 keys, unchanged, depth 32 passed explicitly, never inferred ([[membership]], Tree depth). The proving key is `semaphore-32.zkey` by its sha256 (`2e5f7a9f880c337134ee4c7fc4e53573813b4c9c6ae46221c0b56e7992304650`), the one [[P1-17b]] part 2 checked for well-formedness; any other key is refused, whatever its source ([[0009-membership-proof]], Consequences; T-07, T-12).
- **The prover is pinned by hash.** Whatever Groth16 prover runs is pinned, in the release record, like the key.
- **Randomisers from a CSPRNG**, and the identity secret used for Abolish proofs only (chosen-scope linkage, [[membership]], Security notes).
- **The path is built on the device.** The client rebuilds its 32-level path from every leaf of the tier's tree (or its cell's, [[membership]], Cell tree) and checks the rebuilt root against the definition's. It never asks a server for its own path, which would reveal its leaf index (T-10, T-13).
- **The client verifies its own proof** under the pinned verification key before it leaves the device ([[P1-17b]]: a witness that doesn't satisfy the circuit would leave a witness-dependent term in `C`).
- **The scope is derived, not supplied**: `membershipScope` from `packages/crypto` (fixed tier) or the rolling scope ([[0028-rolling-electorates]]), over the definition the client already checked.

## Rules

- **The bundle allow-list and CSP hold until the owner changes them.** The prover is third-party runtime code the allow-list doesn't admit (`tests/bundle.test.ts`, mirrored in `.github/tools/ci/src/ballot.ts`), a WebAssembly prover needs `'wasm-unsafe-eval'` in `script-src`, and fetching the key and the leaves needs `connect-src` (today `'none'`, so not even the client's own origin). Each is an owner-reviewed `ci:` change (rule B, T-43, T-59); an agent session proposes it in the PR and in the status file, as [[P2-8]] part 2b does for its origins, and builds everything that doesn't need it meanwhile.
- **No network in the prover itself.** The prover takes the key bytes, the leaves and the secret as arguments; fetching and caching are the client's (part 3), so the prover's tests run in Node with no server.
- **No motion on the ballot** ([[language]]): the proving screen is a still screen with words and a plain progress indicator that reports real progress, never an animation that stands in for it.
- **Phone-sized, and measured.** The depth-32 key is Semaphore's largest and a proof hashes 32 levels whatever the group size ([[membership]], Tree depth, Cost). This item measures proving time and memory on a desktop and a mid-range phone and records them here. If they're unacceptable, the answer is a new ballot version with a smaller protocol depth, decided by the owner, never a depth the client or a server chooses.
- **Protocol code**: the prover, its key handling and the path building are inside the `crypto-review` gate; `apps/ballot` needs the independent in-session subagent review (AGENTS.md, Before opening any PR, step 5).

## Plan

Each part is one PR on this branch's name.

1. **Choose the prover** (ADR amendment to [[0009-membership-proof]], and a prototype). Two candidates, decided by measurement against the rules above:
   - **snarkjs** (and its `ffjavascript`): the prover that made the pinned vectors; GPL-3.0, which sits under this repository's AGPL; a WebAssembly prover and a circom witness calculator (`semaphore.wasm`) that must be pinned too.
   - **An Abolish Groth16 prover over `@noble/curves`' BN254** with the witness computed in TypeScript: no third-party runtime code beyond what the allow-list already has, but a new primitive that the gate must review line by line, and slower in JavaScript. [[P1-17b]] already holds the field, curve and Poseidon pieces.

   The part ends with the choice, the exact versions and hashes, measured times on both devices, where the code lives (a new package if it isn't `apps/ballot`'s own), and the owner-reviewed asks: the allow-list entry, the CSP lines and the key's source. The key is pinned from `snark-artifacts.pse.dev`, which isn't a vendored or re-fetched source ([[P1-17b]], Known-weak), so the part also proposes how CI re-fetches and checks it.

2. **The prover core.** `prove(secret, leaves, definition, message)` returns the proof, built to part 1's choice and tested in Node against `docs/spec/vectors/membership-proof.json`'s Semaphore-made proofs: every proof it makes verifies under `packages/crypto`'s own verifier; its output for a fixed secret and path matches the vectors' public signals; a witness that doesn't satisfy the circuit, a wrong key hash, a path that doesn't climb to the definition's root, a depth other than 32 and a forbidden commitment are refused before any proving. fast-check properties over random trees and members; a mutation test that removes the self-verification fails.
3. **The tier path.** Rebuilding the 32-level path from the board's registration events (or the leaves the client fetches), the root check against the definition, and the cell tree for regional elections. The leaf source is part of the decision in part 1: reading the board's own entries through the API routes that exist is preferred, since each is checkable against the definition, and a new route for leaves is the fallback. Large tiers are streamed, not held twice.
4. **The worker and the key's delivery.** The prover in the existing Web Worker protocol (`apps/ballot/src/worker`): the key fetched once, hashed as it streams, kept in the browser's cache and re-checked on every use; progress messages; a proving screen in the style of the sending mockups (`everyday-sending.stories.tsx`, `sending.stories.tsx`) as a real screen with its messages, a story with axe at desktop width and 360px, and a plain refusal that names which check failed. Needs the `ci:` changes above.
5. **Wire it in.** [[P2-8]] part 3's sealing takes the proof; [[P1-20]] part 2b's casting stage uses the same prover (through Node, same code), and the reference election's membership-prover stub is deleted.

## Part 1 (#PR)

Decided ([[0009-membership-proof]], Amendment, `Accepted (agent) — owner may veto`): **snarkjs 0.7.5 with ffjavascript 0.3.1, single-threaded**, with its output verified under the pinned key and then re-randomised with CSPRNG scalars in `packages/crypto` (`(t⁻¹·A, t·B + t·u·δ₂, C + u·A)`, verified again), so zero knowledge rests on `@noble/*` and the platform CSPRNG, not on snarkjs's randomness (an ffjavascript ChaCha stream seeded once from `crypto.getRandomValues`, or from `Math.random` without `crypto`) or its correctness. [[membership]], Security notes, now requires that re-randomisation of any prover whose randomness the client doesn't control. An `@noble/curves` prover of our own was rejected: its MSMs and FFTs alone take 5.5× snarkjs's whole proof, and it needs a TypeScript witness generator for all 9,418 wires, a second implementation of Semaphore's circuit.

Measured (`packages/crypto/scripts/membership-prover-bench.mjs`, outside the workspace, 4-vCPU cloud host): one proof takes 3.7 s single-threaded in Node and in Chromium, 1.15 s with four threads in Node, 16.2 s and 24.1 s in Chromium at 4× and 6× CPU throttling; the `@noble/curves` lower bound is 20.6 s; re-randomising takes 34 ms. snarkjs's threaded mode starts `blob:` workers the CSP refuses, so the client proves single-threaded and never calls snarkjs's verifier or key export (which build the threaded curve).

Where the code lives: inputs, the key-hash check, self-verification and re-randomisation in `packages/crypto`; the snarkjs call in a new gated package, `packages/membership-prover` (runtime dependencies `@abolishus/crypto`, snarkjs and ffjavascript only; the verifier never imports it).

Owner asks, each a `ci:` change (rule B), listed in the Amendment: the new gated package and its dependency rule; the bundle allow-list entry for snarkjs's and ffjavascript's browser builds in the worker's chunk; `'wasm-unsafe-eval'` in `script-src` and `'self'` in `connect-src`; the zkey and witness calculator vendored in the package and re-fetched from `snark-artifacts.pse.dev` by CI; and, owner-only, GPL-3.0 code in the AGPL-3.0-only client.

Known-weak:

- No real phone was measured: the 4× and 6× rows are throttled Chromium. The phone measurement stays open for part 4, when the worker runs in the real client.
- snarkjs's prebuilt browser bundles and the witness calculator `semaphore-32.wasm` are trusted as published, not rebuilt from source.
- Single-threaded proving is about 3× slower than snarkjs's threaded mode.

Part 2 needs none of the `ci:` changes: the inputs, key check, self-verification and re-randomisation are `@noble/*` code in `packages/crypto`, tested in Node against `membership-proof.json`. Its snarkjs adapter waits on the gated-package `ci:` change; until it lands, part 2's tests drive snarkjs from a script outside the workspace, as the vector generators do.
