## Scope

Turn the page mockups in `apps/web/src/mockups/` (Storybook `Mockups/Web/…`) into the real `apps/web` routes, on the data that exists today. The mockups are the reference for layout, copy and motion; [[language]] is binding (two registers, everyday by default; square corners; motion only reveals real data; no motion that loops or counts). Nothing here waits on protocol work: every part uses routes the API already serves, and leaves out what it can't show yet instead of faking it.

Rules for every part:

- **No hard-coded strings.** The mockups hard-code English; the real components take translated text from `apps/web/src/messages.ts` (`useTranslate`), as the existing components do.
- **CSP-safe.** The page's CSP has `style-src 'self'`, which blocks inline `style` attributes. Kit components that set one (`TallyBars`' bar width; check `BoardMap`, `InclusionPath`, `QrCode`, share parts and the mockup helpers too) must draw the same thing another way before a real page uses them: SVG geometry attributes, `<meter>`/`<progress>`, or classes. Widening `style-src` is a `security.ts` change for the owner, not a fix.
- **Server-rendered.** Nothing reads `window` or `document` during render; scroll hooks and the motion utilities already render the final state on the server.
- **Analytics stay fixed.** Every new route gets a template in `src/analytics.ts` (`PAGES`) and its test; no path or poll ID is ever kept (T-67).
- **Tested like the kit.** Each new component has a story with a play function that passes axe at desktop width and 360px (`test:storybook` runs both); SSR and serve tests cover each route. A mockup stays in Storybook as the reference until its real page matches it; then its story is deleted in the same PR.

5. **The moderation log and the account page** (done in #244), from `moderation-page.tsx` and `account-page.tsx`, on the data their routes serve today. `/moderation` states what moderation can and can't reach, lists the log as the API serves it (oldest first, each row's poll with its fingerprint, the action and its ground, by the database's clock) and the policy's seven removal grounds, its never-grounds and its restore grounds. `/account` signed out offers sign-in and sign-up side by side and explains the separation between the account and the voting identity (T-10); signed in it lists the passkeys (synced or device-only, when added) and the sign-out, add, remove and delete actions. 6. **The board page** (done in #520). `/polls/:id/board?from=<entry>` from `board-page.tsx`'s ledger: the head as the server claims it (size, chain head with its fingerprint, tree root, and that it is the server's word until anchored), then 25 entries a page from `GET /board/entries` in `BoardLedger`, each with its number, anchoring period, kind and an entry hash this page computes from the entry's bytes (`src/board.ts`). Every entry is decoded with `@abolishus/crypto` under the board-entry version the definition pins, and must name this poll, sit at its asked-for position and never go back a period; a page with one that fails is refused whole (T-23, T-31, T-34). Pages start only at multiples of 25, filled up when the API cuts an answer short by bytes, and earlier, later and latest pages are plain links, so reading the board needs no script. There is no lookup by entry number: asking our server for a receipt's entry would tell it which entry is the visitor's, so the page says to check a receipt against a downloaded board instead, and a visit names only a window of 25 (T-10). A page past the end says so; anything but a canonical `u64` that starts a page starts at entry 0. The poll page's board facts link to it, and analytics counts it as the template `/polls/:id/board`, never the ID or the position (T-67).

7. **The board page's anchors** (done in #770). Section 02 of `/polls/:id/board`, from `board-page.tsx`'s Anchors: the latest 6 checkpoints our server has taken of the board, from `GET /board/checkpoints` (core's `readLatestCheckpoints`, the latest first, at most `limit`, below an optional `before` segment), each with its period, the entries by then, its hash as this page computes it (the value to anchor on L1), its chain head and Merkle root. `anchorRows` (`src/board.ts`) decodes each with `@abolishus/crypto` and refuses the whole list when one doesn't decode, names another poll, or doesn't go back from the one before it (an earlier period and at most as many entries), and the entries still show (T-23, T-24, T-31). The text says each is the server's word until the anchor holds it, which the page doesn't check.

8. **The board page's activity** (done in #772). Section 01 of `/polls/:id/board`, from `board-page.tsx`'s Activity: entries per anchoring period, worked out from the board's checkpoints rather than a new route. The page now asks `GET /board/checkpoints` for the latest 24 (`ACTIVITY_PAGE`) and its anchors still show the latest 6. `activityBars` (`src/board.ts`) takes each checkpoint's size less the one before it; every period that adds entries gets a checkpoint (docs/spec/board.md, Segments and checkpoints), so a period between two added none. The earliest checkpoint counts its whole size only when fewer came back than were asked for, which the contract says means there are none earlier; otherwise it is left out. The chart is a static SVG whose bar heights are attributes (no inline style, so `style-src 'self'` holds, and no motion), with its first and last period and the largest count as HTML text under and over it, and every count in a table behind "The count for each period", which needs no script. The counts are differences of the server's claims and say so; when the checkpoints are refused, the section says it can't count (T-23, T-24). With 24 checkpoints in hand, the anchors' note that earlier ones exist now shows only when there are more than 6.

9. **The board page's consistency checks** (done in #775). `/polls/:id/board` asks `GET /board/proofs/consistency` for the proofs between each pair of neighbouring checkpoints its anchors show, and between the head and the latest checkpoint (the smaller tree first, since either may be read first), all at once, at most 6 a page; equal sizes need no proof (the roots must be equal), and a head read empty beside a checkpoint fails without one, since a board that held entries never reads empty again. `oneHistory` (`src/board.ts`) checks each with `@abolishus/crypto`'s `verifyConsistency` over `BOARD_TREE`, and a proof the server refuses as out of range counts as failed: it claimed a tree its board doesn't hold. Each verdict is a line beside what it checked: under the head ("one history" or not) and under each checkpoint ("Extends the checkpoint after period N" or "Doesn't extend"), each saying it was checked by the server's proof or by the same root at the same size; a failure says our server couldn't prove it and to keep both, as evidence of tampering, and the page still shows everything else (T-24). The proofs name only checkpoint and head sizes every visitor is shown, so they tell our server nothing a visit didn't (T-10). The anchors' claim now says the page checks these proofs, and still leaves anchoring and the entries to the verifier. An entry's own page ("your place on the board") stays out of the website: asking our server for one entry's proof tells it which entry is the visitor's (T-10), so it belongs to the ballot client and the verifier, which hold the receipt.

## Independent review (part 7)

An in-session subagent review with the `crypto-review` checklist found one blocking point: the page's words called a taken checkpoint anchored ("the value anchored", "the anchor on Ethereum is unaffected"), while no anchor is deployed yet ([[P4-1]] part 2b-2b-2) and a checkpoint is taken before it is sent. Fixed: the hash is "the value to anchor", the lede says a checkpoint is our word until the anchor holds it, and the claim says the page checks no anchoring. Also fixed: the empty state no longer promises a checkpoint after the first hour (a deployment without an anchor takes none), "Latest" is no longer drawn in the recorded colour, and `ssr.test.ts` now covers the note on earlier checkpoints and the refusal of another poll's through the loader. Kept: a failed checkpoints call failing the page (Known-weak).
