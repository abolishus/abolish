# T-61: Release or publishing compromise

- Area: Development, supply chain and operations (G-14)
- Adversary: A-6, A-2
- Status: **Partial.** npm releases and the API image (built twice, signed and attested, deployed to staging only from `main`'s head); both unexercised. Residual: a re-run can briefly race a newer push (History, 2026-10-12); a branch can publish unless the `npm` env is main-only (owner); GitHub, Sigstore, npm trusted; no ballot client yet.

## Threat

A malicious npm release or ballot-client release is signed and published.

## Mitigation

Double build with hash comparison, Sigstore/cosign keyless signing, SLSA provenance, OIDC trusted publishing with no tokens, `next` tag only (P0-3).

Index: [[THREAT_MODEL]].

## History

- 2026-10-11 (P2-11 part 1): the API image is reproducible: a bundle `repro-build` already compares, on a Node base pinned by digest, with layer times clamped to the commit (`SOURCE_DATE_EPOCH`, `rewrite-timestamp`). Building it twice, signing and deploying by digest is part 2 ([[railway]]).
- 2026-10-12 (P2-11, #69 and #74): the deploy workflow builds the image twice, pushes it by digest, signs it and attests provenance, and deploys staging only from `main`'s head, so re-running an old run can't roll staging back. Residual: if `main` moves between that check and the Railway call, the older commit deploys and stays live until the queued newer run passes its checks and replaces it.
