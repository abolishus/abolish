# T-67: Analytics and error-tracking leakage

- Area: Development, supply chain and operations (G-14)
- Adversary: A-2, A-1
- Status: **Planned.** Residual: PostHog learns how often each page template is viewed, and when (to 10 seconds), but nothing that links two events (P2-9 part 2b); `apps/web` itself, and the proxy's logs, can still join a session to the polls its browser views (T-10, T-11).

## Threat

PostHog or logs capture poll participation, ballot data or identifiers.

## Mitigation

PostHog only in `apps/web`, proxied through our domain; never in `apps/ballot` (bundle test, P2-8); no secret, ballot or voting identity in logs (dev skill). In `apps/web`, PostHog is reached only from our server: page views as a template from a fixed list (never a poll ID or path), and errors as a name, a template and positions in our hashed bundles (never a message); each event carries a fresh random ID, no person profile and no GeoIP (P2-9 part 2b).

## History

- 2026-10-12 (P2-8 part 1): the ballot client's bundle test is built. It builds the client and fails on any analytics, tracking or error-reporting SDK's markers, on any npm package in the bundle but React's, and on any URL but a short list of inert strings; Until the `ci:` check in #82 merges, this is a package-local test that the PR it judges could weaken (T-59). The CSP's `connect-src 'none'` means the client can't make any subresource request yet (navigation isn't covered by CSP).
- 2026-10-12 (P2-8 follow-up): once #82 merges, the no-analytics check is owner-reviewed, but it judges the build of the client's own config, which could detect the check and emit clean output only then (T-59).
- 2026-10-12 (P2-8, after #82 merged): the ballot client's bundle and CSP policy is now an owner-reviewed `.github/tools/ci` check. Its residual is wider than `vite.config.ts`: any `apps/ballot/vite.config.*` (a `.js` or `.mjs` file takes precedence), any `postcss.config.*` from `apps/ballot` up to the workspace root, and Tailwind `@plugin`/`@config` directives in any CSS the build loads all run JS at build time, and any of them can detect the check and emit clean output only there.
- 2026-10-12 (P2-9 part 2a): `apps/web` now serves accounts on the same origin as the poll pages. Its request log never records a path, so it can't say which polls a signed-in visitor opened, and the pages never receive the session cookie. A compromised web server, or the proxy's logs, could still join the two. PostHog isn't added yet (P2-9 part 2b).
- 2026-10-12 (P2-9 part 2b): PostHog added to `apps/web` without its browser SDK. The front counts page views as templates (`/polls/:id`) and passes on a page's own error reports only if they are exactly a name, a template and bundle positions; every event gets a fresh random `distinct_id`, `$process_person_profile: false` and `$geoip_disable: true`, and goes in a shuffled 10-second batch from our server. So PostHog can't say which polls any visitor or account viewed. False reports can be sent by anyone (bounded per flush; T-52).
- 2026-10-13 (P2-18 part 3a): short links on `apps/web`, `/p/<code>`. Page views count the template `/p/:code` (either case), never the code, which names a poll as surely as its ID; the redirect and the 404 never quote it.
- 2026-10-18 (P2-19 part 6): a poll's board page, `/polls/<id>/board?from=<entry>`. Page views count the template `/polls/:id/board`; neither the ID nor the entry it opens at (which a voter may take from their receipt) is kept.
- 2026-10-22 (P2-24 part 2): a poll's flyer, `/p/<code>/flyer?paper=…&ink=…`. Page views count the template `/p/:code/flyer` (any case), never the code, paper or ink; the page prints only the short link, the same for everyone, so a printed flyer can't say who printed it (T-10). Its QR code is drawn on the server by our own encoder, with no third-party service.
- 2026-10-22 (P2-24 part 3): a poll's embed, `/embed/p/<code>?theme=…`, which other sites frame. Page views count the template `/embed/p/:code` (any case), never the code, the theme or the site it was on (the page asks for no referrer). The embed runs no script at all: its CSP has no `script-src`, so neither our analytics nor anyone else's can run in it, and it sandboxes itself with no scripts or forms whatever the host's iframe says.
