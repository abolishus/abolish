# T-54: Trustee unavailability

- Area: Availability and censorship resistance (G-10)
- Adversary: A-1, A-7
- Status: **Needs decision** (P1-7). A ranked-choice mixnet (P1-4) would add sequential mixer availability. Under P1-3 (option B), trustees must also be online during voting (otherwise their share is posted publicly for every ballot, with classical privacy only) and must process postings within the complaint window; a trustee that misses the window can't contribute to the tally, so the tally needs k trustees that did.

## Threat

Fewer than k trustees are available after close, so the tally can never be decrypted.

## Mitigation

k-of-n with k < n, chosen by the owner (P1-7; [[0006-trustees]] proposes 4-of-7, tolerating three unavailable trustees); the reference election and simulations run with trustees offline (P1-20, P1-21).

- 2026-10-12 (P1-12 part 3b, [[delivery]]): the delivery deadline (one day) and the complaint window (four days), counted from `closes_at + l1_inclusion_bound`, are constants of the delivery records' version 1 and terms of `W_S`, so the counted set is fixed before the tally. A trustee that misses the complaint window can't complain about an invalid posting, its summed shares then fail, and the tally needs `k` other trustees.

Index: [[THREAT_MODEL]].

## History

- 2026-10-12 (P1-14 part 2, [[ceremony]]): a ceremony qualifies a seat only if it took part in all four rounds and passed every check; the protocol's floor is `k` qualified seats. [[0006-trustees]]'s proposed rule 7 (`n − 1`) is the owner's; until then a definition can bind a ceremony with as few as `k` seats, leaving its tally no failure margin.
- 2026-10-11 (P1-15, part 1): a cell with no published opening fails the election (`tally-missing`, [[tally]]); any trustee holding `k` passing summed shares can combine and publish it, and any `k` give the same opening, so which trustees are online doesn't change the result.
- 2026-10-12 (P1-15, part 2a, [[tally]], Tally window): tally opening version 1 fixes a 7-day tally window, starting when the checkpoint anchoring the counted set is due (after every earlier window, each a constant of its pinned version or contract), as the tally's term in the seal, so no one can shorten it for one election and a longer earlier window never eats into it. The operator boards only attributed openings, so stripping a signature doesn't block the tally (the attributed original is boarded); the verifier still counts an unattributed opening that passes, as a defence against an operator that breaks that rule. A cell with no opening by the seal still fails the election permanently, and the board operator can cause that by refusing every opening, unattributed, since openings have no direct-submit path yet. [[tally]] requires one, as events under the event accumulator, before any election registry is deployed (P1-18).
- 2026-10-12 (P1-19 part 4a, [[verifier]], Key ceremony): the verifier applies [[0006-trustees]] rule 7, adopted by the owner: 3.2 fails `ceremony-participation` when a valid transcript has fewer than `max(k, n − 1)` qualified seats, so a coordinator that shrinks the qualified set to `k` (leaving the tally no margin) fails the election. `packages/crypto`'s `ceremony-quorum` still means fewer than `k`; the registry quorum `q = n − 1` is P1-18's follow-up.
