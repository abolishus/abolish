# Share delivery on the board

How a ballot's delivery to each trustee is shown on the board, and how anyone decides from the board which ballots were delivered and which a proven complaint excludes: the share-receipt record (`0x000c`), the share-posting record (`0x000d`) and the share-complaint record (`0x000e`), each version 1, the share-receipt batch (`0x0016`, version 1) and share-complaint batch (`0x0017`, version 1), which carry many of one seat's receipts or complaints under one signature on the contract path ([[P1-12d]], [[P1-12e]]), and the obligation root (`0x001a`, version 1), which commits to all of one seat's receipts or complaints as one Merkle root whose leaves are published by content address ([[0031-national-delivery-obligation]], [[P1-12f]]); the delivery deadline and the complaint window; the board operator's boarding rules; and the delivery check that the counted set of [[tally]] applies. This is the delivery and counting step of [[0002-everlasting-privacy]] (option B, accepted by the owner: Deadline, Complaints, Complaint window), with the owner's 2026-10-12 decision on its fallback: a client never posts a seat whose receipt passes, posting is the voter's explicit last resort, and only postings sent through the contract path deliver. What each record proves is in [[share-encryption]] (Intake and receipts, Public posting, Complaints); this page puts it on the board. Notation is from [[notation]], the ballot hash from [[ballot-validity]]. Threats: T-41, T-29, T-25, T-17, T-15, T-31, T-34, T-52, T-54.

## Versions

None of the six types is pinned in an election's profile. Versions 1, 2 and 3 of the ballot record (`0x0002`) fix all six at version 1, and versions 4 and 5 fix all six at version 2, which names the seat's panel (Version 2; the batches' and the obligation root's version 2 since [[P2-16]] part 5b), each together with the windows below ([[versioning]], Three levels), so delivery can't drift from the ballots it delivers: the ciphertexts' associated data name ballot version 1's share-ciphertext rules, which versions 2 and 3 keep, or version 4's own, with the seat's panel, which version 5 keeps, and the ballot hash names the ballot's own version ([[share-encryption]], Ciphertext, Ballot version 4; [[ballot-validity]], Ballot hash, Ballot record (version 2), Ballot record (version 3)).

Share receipts and complaints reach the board through the board path only under board-entry versions 3 to 7, which allow them ([[board]], Allowed payloads); no board-entry version allows a share posting, either batch or an obligation root, which reach the board only as contract events (Direct submit); version 2 is never assigned, since a frozen vector of `board.json` uses it as the version that doesn't exist. Under board-entry version 1 no receipt could be boarded through the board path, so a profile that pins any ballot version from 1 to 5 MUST pin one of them: [[verifier]] 2.3 fails a profile pinning one with any other board-entry version (`profile-combination`), the ballot client refuses to cast in such an election, and P1-18's election registry MUST refuse to register such a definition, so the mistake is caught before the election exists rather than after. A later board-entry version that also allows receipts and complaints adds itself to this rule, as versions 4 to 7 do; [[tally]], Destruction, narrows the choice to version 4, 5 or 7 for every profile that pins tally-opening version 1, to version 6 for every one that pins version 2, and to version 7 for every one that pins version 3 ([[tally]], Author panel).

## Records

### Share receipt (`0x000c`, version 1)

A trustee's share receipt ([[share-encryption]], Intake and receipts) as a record: its signed statement, then its signature.

| Field             | Type        | Meaning                                                                         |
| ----------------- | ----------- | ------------------------------------------------------------------------------- |
| `definition_hash` | `bytes[32]` | The election's definition hash                                                  |
| `ballot_hash`     | `bytes[32]` | The ballot hash of the public part the trustee checked ([[ballot-validity]])    |
| `seat`            | `u8`        | The trustee's seat, `i`                                                         |
| `share_hash`      | `bytes[32]` | `H(ct_i)`                                                                       |
| `signature`       | `p256-sig`  | The seat's signature under `abolish/v1/sig/share-receipt` over the first fields |

The fields before `signature` are exactly the 97-byte statement `m` the trustee signs ([[share-encryption]], Intake and receipts), so a node's receipt becomes a record with no new signature. 164 bytes with its header.

### Share posting (`0x000d`, version 1)

The client's public posting of one ciphertext with its ML-KEM message ([[share-encryption]], Public posting), made only by the voter's explicit choice (Client rules) and sent only through the contract path (Direct submit): a posting that reaches the board any other way delivers nothing.

| Field             | Type               | Meaning                                                                 |
| ----------------- | ------------------ | ----------------------------------------------------------------------- |
| `definition_hash` | `bytes[32]`        | The election's definition hash                                          |
| `ballot_hash`     | `bytes[32]`        | The ballot hash of the ballot the posting delivers                      |
| `seat`            | `u8`               | The seat the ciphertext is for, `i`                                     |
| `m`               | `bytes[32]`        | `m_i`, the ML-KEM message                                               |
| `ciphertext`      | `share_ciphertext` | `ct_i`, decoded strictly as [[share-encryption]] (Ciphertext) specifies |

A posting carries no signature: only a party that knows `m_i` can make one that passes, and a passing posting is the same whoever boards it ([[share-encryption]], Public posting). Since `ciphertext` decodes strictly, a ciphertext that doesn't decode makes the record fail to decode, so `posting-malformed` never arises for a record that decodes. Its check hashes `ct_i` as encoded in the record, which is `ct_i`'s one encoding. 1,308 + 64·`m` bytes with its header, for `m` options: 1,948 bytes at 10 options, 5,404 at `MAX_OPTIONS`.

### Share complaint (`0x000e`, version 1)

A trustee's complaint about a posting ([[share-encryption]], Complaints), signed so that an unfounded one is attributed.

| Field             | Type              | Meaning                                                     |
| ----------------- | ----------------- | ----------------------------------------------------------- |
| `definition_hash` | `bytes[32]`       | The election's definition hash                              |
| `ballot_hash`     | `bytes[32]`       | The ballot hash of the ballot whose posting it is about     |
| `seat`            | `u8`              | The complaining seat, `i`                                   |
| `proof`           | `complaint_proof` | `D` and its Chaum–Pedersen proof                            |
| `signature`       | `p256-sig`        | The seat's signature under `abolish/v1/sig/share-complaint` |

The signature is an ECDSA P-256 signature by seat `i`'s per-election signing key ([[trustee-identity]], Which key signs what), under `abolish/v1/sig/share-complaint`, over

```
m = definition_hash ‖ ballot_hash ‖ u8(seat) ‖ encode(proof)
```

161 bytes: the record's fields without its header and signature. It **attributes** the complaint to seat `seat` if and only if `seat` has registered keys ([[ceremony]], Transcript check) and the signature verifies under that seat's registered signing key, never its identity key; any other complaint is **unattributed**. 228 bytes with its header.

A proven complaint excludes its ballot whether or not it is attributed: its proof shows `D = ct_DH^x` for seat `i`'s registered `dh_i`, which needs `x`, and with it anyone sees the shares fail. The signature only decides whom an unfounded complaint is attributed to (T-29). `m` binds the definition, the ballot and the seat, so a complaint replayed against another election, ballot or seat is unattributed, never framing its signer; the proof itself binds the definition, the seat, the trustee's key and the ciphertext's hash ([[share-encryption]], Complaints).

### Share-receipt batch (`0x0016`, version 1)

Many of one seat's share receipts for one election under one signature, sent only through the contract path, so that a trustee node forcing what it owes through L1 pays for one signature verification, one storage key and one event per batch instead of per receipt (Capacity; T-25, T-52, T-54).

| Field             | Type                                    | Meaning                                                                               |
| ----------------- | --------------------------------------- | ------------------------------------------------------------------------------------- |
| `definition_hash` | `bytes[32]`                             | The election's definition hash                                                        |
| `seat`            | `u8`                                    | The trustee's seat, `i`                                                               |
| `receipts`        | `list<receipt_pair, RECEIPT_BATCH_MAX>` | 1 to `RECEIPT_BATCH_MAX` pairs, strictly ascending by `ballot_hash`                   |
| `signature`       | `p256-sig`                              | The seat's signature under `abolish/v1/sig/share-receipt-batch` over the first fields |

where `receipt_pair` is `ballot_hash` (`bytes[32]`, the ballot hash of the public part the trustee checked) then `share_hash` (`bytes[32]`, `H(ct_i)`), and `RECEIPT_BATCH_MAX` is 1,024. A batch of `c` pairs is `104 + 64·c` bytes with its header: 65,640 at `RECEIPT_BATCH_MAX`.

The signature is an ECDSA P-256 signature by seat `i`'s per-election signing key ([[trustee-identity]], Which key signs what), under `abolish/v1/sig/share-receipt-batch`, over

```
m = definition_hash ‖ u8(seat) ‖ u32(c) ‖ (ballot_hash ‖ share_hash) × c
```

the record's fields without its header and signature, `37 + 64·c` bytes. By signing it the seat states, for each pair, exactly what its share receipt `(definition_hash, ballot_hash, seat, share_hash)` would state ([[share-encryption]], Intake and receipts): that its shares of the ballot with that ballot hash, whose ciphertext hashes to `share_hash`, passed its intake. So each pair **reads as a share receipt** with those four fields, and passes `share-receipt` against a ballot `b` exactly when `share_hash` is `b`'s `share_hashes[seat]` and the batch's signature verifies under that seat's registered signing key; the batch's own tag keeps its statement from ever reading as a receipt's, or the reverse ([[domain-separation]]). A trustee node signs a batch only over receipts it issued: it MUST never put a pair in a batch whose shares it didn't receipt at intake, so a batch never states more than the receipts it carries.

Pairs are strictly ascending, so a set of receipts has one batch encoding per signature and no pair repeats (T-31). Different batches of one seat may carry the same pair, and a pair may also be carried by a share receipt: each is read on its own, as duplicates are (Delivery check).

### Share-complaint batch (`0x0017`, version 1)

Many of one seat's complaints for one election under one signature, sent only through the contract path, as the share-receipt batch carries receipts ([[P1-12e]]; Capacity; T-25, T-52, T-54).

| Field             | Type                                         | Meaning                                                                                 |
| ----------------- | -------------------------------------------- | --------------------------------------------------------------------------------------- |
| `definition_hash` | `bytes[32]`                                  | The election's definition hash                                                          |
| `seat`            | `u8`                                         | The complaining seat, `i`                                                               |
| `complaints`      | `list<complaint_entry, COMPLAINT_BATCH_MAX>` | 1 to `COMPLAINT_BATCH_MAX` entries, strictly ascending by `ballot_hash`                 |
| `signature`       | `p256-sig`                                   | The seat's signature under `abolish/v1/sig/share-complaint-batch` over the first fields |

where `complaint_entry` is `ballot_hash` (`bytes[32]`, the ballot whose posting it is about) then `proof` (`complaint_proof`, `D` and its Chaum–Pedersen proof, [[share-encryption]], Complaints), 128 bytes, and `COMPLAINT_BATCH_MAX` is 512. A batch of `c` entries is `104 + 128·c` bytes with its header: 65,640 at `COMPLAINT_BATCH_MAX`. The signature is by seat `i`'s per-election signing key under `abolish/v1/sig/share-complaint-batch`, over

```
m = definition_hash ‖ u8(seat) ‖ u32(c) ‖ (ballot_hash ‖ encode(proof)) × c
```

`37 + 128·c` bytes. Each entry **reads as the share complaint** `(definition_hash, ballot_hash, seat, proof)` it states: it is proven, unfounded or failing exactly as that complaint would be (Delivery check), and it is attributed to `seat` exactly when the batch's signature verifies under that seat's registered signing key. A proof binds its definition, seat, key and ciphertext by itself ([[share-encryption]], Complaints), so a batch adds only the signature's attribution. One complaint covers every passing posting of a ballot and seat (What a node owes in complaints), so entries are strictly ascending by ballot hash, one per ballot, and a set of complaints has one encoding per signature (T-31).

### Obligation root (`0x001a`, version 1)

All of one seat's receipts, or all of its complaints, for one election, committed to as one signed record: the root of a Merkle tree over them, their count, and the content address of the object that holds them, sent only through the contract path, so that a trustee node forcing what it owes through L1 pays for one deposit per kind whatever the electorate ([[0031-national-delivery-obligation]], option C; Capacity; T-25, T-52, T-54). Per-record batches stay the path for every election whose obligation they can carry (What a node owes, Elections that commit roots).

| Field             | Type          | Meaning                                                                                                            |
| ----------------- | ------------- | ------------------------------------------------------------------------------------------------------------------ |
| `definition_hash` | `bytes[32]`   | The election's definition hash                                                                                     |
| `seat`            | `u8`          | The trustee's seat, `i`                                                                                            |
| `kind`            | `enum8<1, 2>` | 1 for a **receipt root**, whose leaves are share receipts; 2 for a **complaint root**, whose leaves are complaints |
| `count`           | `u32`         | `c`, the number of leaves, at least 1                                                                              |
| `root`            | `bytes[32]`   | The root of the obligation tree over the leaves                                                                    |
| `leaves_cid`      | `bytes[36]`   | The binary CID ([[content-addressing]]) of the leaf object                                                         |
| `signature`       | `p256-sig`    | The seat's signature under `abolish/v1/sig/obligation-root` over the first fields                                  |

173 bytes with its header. The signature is an ECDSA P-256 signature by seat `i`'s per-election signing key ([[trustee-identity]], Which key signs what), under `abolish/v1/sig/obligation-root`, over

```
m = definition_hash ‖ u8(seat) ‖ u8(kind) ‖ u32(c) ‖ root ‖ leaves_cid
```

the record's fields without its header and signature, 106 bytes.

**Leaves.** A receipt root's leaves are `receipt_pair`s (64 bytes: `ballot_hash` then `share_hash`, Share-receipt batch), a complaint root's `complaint_entry`s (128 bytes: `ballot_hash` then `proof`, Share-complaint batch), strictly ascending by `ballot_hash`, so a set of receipts or complaints has one leaf list, and so one root, and no ballot hash repeats (T-31). The **leaf object** is the leaves concatenated in that order, `64·c` or `128·c` bytes, with no header of its own: `kind` and `count`, which the signature covers, fix its layout and length. `leaves_cid` is `objectCid` of exactly those bytes under [[content-addressing]]'s parameters (one raw block up to 1 MiB, which is 16,384 receipt leaves or 8,192 complaint leaves, and a balanced dag-pb tree above that), so it is canonical, as a checkpoint's CIDs are ([[board]], Checkpoints): no other CID of the same bytes is valid.

**Obligation tree.** The root is the Merkle tree of [RFC 9162](https://www.rfc-editor.org/rfc/rfc9162) §2.1.1 over the leaves `D[c] = (leaf_0, …, leaf_{c−1})`, each leaf the 64 or 128 bytes above, as the board tree is built ([[board]], Board tree) but under tags of its own:

```
MTH({d})  = H(DS("abolish/v1/obligation/leaf", d))
MTH(D[n]) = H(DS("abolish/v1/obligation/node", MTH(D[0:k]) ‖ MTH(D[k:n])))   for n > 1
root      = MTH(D[c])
```

with `k` the largest power of two smaller than `n`. Its own tags keep any node of an obligation tree from being a node of a board tree, or the reverse, so no inclusion proof of one verifies in the other (T-30). An inclusion proof that leaf `j` is in a root is RFC 9162's audit path `PATH(j, D[c])`, verified as [[board]] (Inclusion proofs) verifies one, with these two tags, `n = count` and the `root` the record signs: a size and root taken together from one signed record, never from two sources.

**What it states.** Signing a receipt root, the seat states, of each leaf, exactly what its share receipt `(definition_hash, ballot_hash, seat, share_hash)` would state, as a batch's signature does of each pair (Share-receipt batch): each leaf **reads as a share receipt** with those four fields, and passes `share-receipt` against a ballot `b` exactly when its `share_hash` is `b`'s `share_hashes[seat]` and the root's signature verifies under that seat's registered signing key. Each leaf of a complaint root **reads as the share complaint** it states, proven, unfounded or failing as that complaint would be, and attributed to `seat` exactly when the root's signature verifies (Share-complaint batch). A leaf counts only if its root's leaves are available and consistent with it (Leaf availability). The root's own tag keeps its statement from ever reading as a receipt's, a batch's or a complaint's, or the reverse ([[domain-separation]]). A trustee node puts in a root exactly the receipts or complaints it owes (What a node owes) and MUST never put in one a receipt it didn't issue at intake or a complaint whose proof it didn't make.

**One per seat and kind.** A seat sends at most one root of each kind for an election. The contract path accepts only the first root of each seat and kind whose signature verifies (Direct submit), and the delivery check reads only the first one in board order (`root-repeat`), so no seat can make a verifier fetch and read more than two leaf objects of it, and since only the seat's own signature fills its slot, no one else can take it, as with close statements ([[contracts]], Close statements; T-52, T-17). A seat whose root is wrong can't replace it; it can still send batches beside it (What a node owes).

### Leaf availability

The leaves are on neither L1 nor L2: that is what makes a root's cost constant. They are published as [[0029-board-data-availability]] publishes the board, by CID, on IPFS and in the archive, and whether they are available is judged by the trustees as the availability committee, from L1 and the L2's events alone, never by whether one verifier could fetch them, which would make a verdict depend on the verifier's network ([[0029-board-data-availability]], option A; T-53).

- **Publication.** A seat MUST serve its leaf object, by its CID, from the moment it submits its root: to every other seat of its panel first, and publicly, and keep it pinned through the archive's confirmation and the verification period after the seal, as a seat keeps what it attested ([[0029-board-data-availability]], Consequences).
- **Attestation.** Each seat that attests the counted extent ([[0029-board-data-availability]], option D, point 2, by `t_S + A'`) also names in that attestation, by the record's hash `H(DS("abolish/v1/obligation-root", record))` over the whole record, every obligation root in time for the election (Windows) whose leaf object it holds and has found consistent with the root (below). The roots in time are the contract's events, which the seat reads from its own L2 node, so every honest seat names the same set. The attestation record is [[availability]]'s (Availability attestation), whose `roots` bind the set of roots its seat names. A seat names a root only once it holds its leaf object and has checked it, and from then MUST serve it as its own.
- **Available.** A root's leaves are **available** if at least `q − k + 1` of the default panel's `q` qualified seats, `k` its threshold, name the root in counted-extent attestations that count ([[0029-board-data-availability]]: recorded by `t_A'`, and only through the contract path); otherwise they are **withheld**. With that count, withholding an honest seat's root takes `k` seats refusing to name it, a coalition that can already open ballots, and making a root available whose leaves no honest seat holds takes `q − k + 1` seats naming it falsely, which can already stall the tally by refusing summed shares, and here only stalls it (Summing, below; T-25, T-54). The default panel's, because a version-1 root, which only ballot versions 1 to 3 fix, is always a default seat's: they have no author panel. A version-2 root names its panel, and that panel's seats judge it (Leaf availability (version 2)). Until the attestation's contract path and check are built ([[availability]]; [[P4-3]] parts 2c-2 and 2c-3), no root is available, so a node never relies on a root before then (Capacity).
- **Withheld.** A withheld root delivers and excludes nothing: its ballots count only through their other records. It is reported `root-withheld` against its seat, with the seats that named it and, on each one's signed word, the seats that attested the counted extent without naming it, as a availability complaint is a seat's signed word ([[0029-board-data-availability]]). A seat that withholds its leaves drops only the ballots it alone would deliver, which it could already do by refusing intake, and here it is named (T-25, T-54).
- **Fetched.** The verifier fetches an available root's leaf object by `leaves_cid` from any source, block by block, each block checked against the CID that names it, and caps what it reads at `64·c` or `128·c` bytes for the record's `count`, walking only the canonical DAG of that length ([[content-addressing]], Reading by CID; T-49, T-52). Bytes that don't hash to their CID are a failed fetch from that source, never a verdict on the root: the verifier tries another source, and if none serves the object it reports the election unverifiable from its sources, never failed, since a threshold named the root and who claimed to hold it is on the record, as when a quorum attests and then withholds the board ([[0029-board-data-availability]], Attest, then withhold). So no source can change a root's verdict (T-53, T-24).
- **Summing.** The counted set is then a function of the counted extent, the counted-extent attestations recorded by `t_A'` and the leaf objects of the available roots ([[tally]], Context). A seat MUST NOT send any summed share until it has read those attestations from its own L2 node and finalized L1, never from the operator, and holds and has checked the leaf object of every available root; one it can't get it keeps fetching, from the seats that named the root, which MUST serve it, and it never sums over a set without that root's leaves. So every honest seat sums over the same set, and no recipient of summed shares holds `k` points for two counted sets, whose difference would open the ballots only one of them counts (T-14, T-29). [[availability]]'s rule that no summed share is sent before the counted extent's quorum is read (What a seat does) includes this. Fetching can start at `t_D` for receipt roots and at `t_K` for complaint roots, days before the fetch allowance `A'` after `t_S` that [[availability]] (Windows) leaves for the rest: up to `2M` leaves of 64 bytes and `2M` of 128 per seat (Residuals).

**Consistency.** An available root is **inconsistent** if its leaf object, fetched as above (so every source gives the same bytes), isn't `count` leaves of its kind's size, its leaves aren't strictly ascending by `ballot_hash`, a complaint leaf's proof doesn't decode as a complaint entry's does (Decoding), `MTH` over the leaves isn't `root`, or, for a dag-pb `leaves_cid`, the DAG its blocks form isn't the one `objectCid` gives for those bytes (another chunking or layout). Every one of these is a function of the signed record and of blocks that hash to its CID, so no source can bring it about. An inconsistent root delivers and excludes nothing, and is reported `root-inconsistent`, attributed to its seat: its signature binds a `root` and `leaves_cid` that no consistent object gives. An honest seat never names an inconsistent root, so a root is found inconsistent only where `q − k + 1` seats named one that isn't, which [[0029-board-data-availability]]'s collusion residual already covers.

**Bound.** A root whose `count` is above the obligation's bound, `2M` for the election's `M` members (What a node owes; the counts [[verifier]] 2.4 recomputes), is reported `root-count` against its seat and ignored, before anything is fetched, so no seat can make every verifier fetch and read more than it could owe (T-52, T-17).

### Decoding

Each record decodes strictly ([[notation]]): every `element` is canonical and not the identity where its table says so, every `scalar` is below `ℓ`, and nothing trails. Decoding doesn't compare `definition_hash`, `ballot_hash` or `seat` with the election; the delivery check does, so a record naming another election, ballot or seat is still read, and reported. A delivery record that fails to decode, including one under a version ballot version 1 doesn't fix (`profile-mismatch`), is a rejected entry ([[board]], Allowed payloads; [[verifier]] 2.3), listed in the report, never an election failure and never a receipt, posting or complaint. So is a posting, a batch of either kind or an obligation root that reached the board through the board path (`unexpected-record-type`, as the board entry carrying it is under every board-entry version). A batch with no entries is `non-canonical` at its count (offset 36), one whose count is above its maximum `length-over-max` there, before any entry is read, and one whose entries aren't strictly ascending by `ballot_hash` is `non-canonical` at the first entry's `ballot_hash` that isn't above the one before; a complaint entry's `D`, `c` and `z` decode as a single complaint's do. An obligation root whose `kind` is neither 1 nor 2 is `invalid-enum` at its `kind` (offset 36), and one whose `count` is 0 is `non-canonical` at its `count` (offset 37); `root` is read as bytes; `leaves_cid` (offset 73) must begin `0x01 0x55 0x12 0x20`, a raw block's CID, when the leaf object it names, `64·count` or `128·count` bytes, is at most 1,048,576 bytes, and `0x01 0x70 0x12 0x20`, a dag-pb root's, when it is larger ([[content-addressing]], Small objects), and is `non-canonical` there otherwise, so a root whose CID can never be canonical takes no seat's slot. Decoding never fetches or reads the leaves (Leaf availability). Under ballot versions 4 and 5, which fix both batches and the obligation root at version 2, a version-1 batch or root is a rejected entry (`profile-mismatch`), as a version-2 one is under ballot versions 1 to 3 (Records (version 2), Decoding).

## Windows

Version 1 of the three records fixes two windows, counted from `closes_at + l1_inclusion_bound` (the close rule's deadline, [[election-definition]]):

| Name               | Value   | Meaning                                                                                         |
| ------------------ | ------- | ----------------------------------------------------------------------------------------------- |
| `DELIVERY_WINDOW`  | 172,800 | Seconds by which a ballot's share receipts and postings must be sent: the **delivery deadline** |
| `COMPLAINT_WINDOW` | 432,000 | Seconds by which a complaint must be sent: the end of the **complaint window**                  |

A record's window is applied by its submission time ([[tally]], Tally window). A receipt or complaint that reached the board through the board path has its segment's anchoring period as its submission time, so it is **in time** if its entry's `segment` is at most

```
s_D = period(closes_at + l1_inclusion_bound + DELIVERY_WINDOW)    for receipts
s_K = period(closes_at + l1_inclusion_bound + COMPLAINT_WINDOW)   for complaints
```

where `period(t) = ⌊(t − epoch) / period⌋` under the anchoring clock ([[board]], Timing), so a record boarded in the deadline's own period is in time. That period can end moments after the deadline, so a client or trustee node MUST send its records by the deadline less the operator's boarding latency, and early enough that, if no board entry appears, it can still submit them through the contract path before the deadline, since a contract-path record is in time only by its submission time. A record sent through the contract path (Direct submit, below), and so every posting, is in time if its submission time is at or before the **deadline** `t_D = closes_at + l1_inclusion_bound + DELIVERY_WINDOW` (`t_K`, with `COMPLAINT_WINDOW`, for a complaint), whatever segment its contract event is boarded in. A record that is not in time is ignored: it delivers nothing and excludes nothing, wherever it is on the board.

Both windows, each followed by the contract-event window (a contract-path record sent at a window's end still has to reach the board), are in [[tally]]'s `W_S`, so `s_S ≥ s_K ≥ s_D` and every record that is in time, by either path, is in the counted extent, and the counted set is fixed before any summed share is sent ([[0002-everlasting-privacy]], Tally liveness). Receipts and complaints are the board-path records that can change a counted set, and contract-path receipts, postings and complaints the contract events that can: a receipt or a passing contract-path posting can complete a ballot's delivery, and a proven complaint excludes it ([[tally]], Tally window).

Why these values:

- **Two days for delivery.** A ballot cast at the close normally holds every receipt already (intake runs before the client shows "cast"). The window must first let trustee nodes see every counted ballot anchored, or recorded after forced inclusion, and still send its receipts through the contract path, even forced through L1 (Direct submit: about 40 hours with the deployed constants, [[availability]]'s fetch allowance for the ballot extent included); the rest covers a client that retries intake because a trustee or the relay is down at the close (intake stays open until the intake cutoff `c_I`, about 34 hours after `closes_at + l1_inclusion_bound` with the deployed constants, Direct submit), a voter who then chooses to post, and a receipt that reaches the board after its ballot. A longer window postpones the counted set and the tally (T-54).
- **Three more days for complaints.** A trustee that was offline during voting must process every posting addressed to it before the window closes, or it can't complain about an invalid one, and its summed shares then fail ([[tally]], Summed-share check), so it can't contribute to the tally. Every posting is a contract event, in L2 data every trustee's own L2 node reads, so the operator can't withhold one through the window. The time a trustee has is `COMPLAINT_WINDOW − DELIVERY_WINDOW` less the contract-event window (a posting submitted at `t_D` may become derivable from L1 only that much later) and less `F`, since a trustee node MUST send each complaint by `c_K = t_K − F`, so that, forced through L1 if the sequencer censors it, its submission time is still at or before `t_K` (Direct submit gives the bound). Three days after the last possible posting covers a weekend; more would postpone every election's seal ([[election-definition]], The seal).

## Boarding

The board operator never boards a share posting, a batch of either kind or an obligation root: each delivers only as a contract event (Direct submit), so it refuses every one sent through the board path, whoever sends it. It boards a share receipt or complaint only if all of the following hold, and refuses every other:

1. It names this election's definition, and `seat` is a seat of the registered key set.
2. A ballot whose ballot hash is the record's `ballot_hash` is already on the board, as a ballot entry or a contract event.
3. It is in time (Windows), boarded in a segment no later than `s_D`, or `s_K` for a complaint.
4. For a share receipt: its signature attributes it to `seat` (the `share-receipt` check against that ballot, with `share_hash` equal to the ballot's `share_hashes[seat]`). For a complaint: a contract-path posting for that ballot and seat, in time, is on the board and passes the public check (`posting-hash`, `posting-proof`, `posting-encapsulation`), the complaint is proven against it (`complaint-proof`, then decryption failing), and its signature attributes it to `seat`.
5. No passing record of the same type for the same ballot hash and seat is on the board yet (a receipt that passes `share-receipt`, a pair of a contract-path batch that passes it, a proven complaint or a proven entry of a contract-path complaint batch), by either path. A failing record, such as junk sent through the contract path, never blocks a passing one.

So a boarded receipt carries no chosen bytes beyond a registered trustee's choice of ECDSA nonce, and a boarded complaint none beyond that and its choice of the proof's nonce `w`, and there is at most one passing record of each type per seat per boarded ballot through the board path (T-17, T-52). Postings reach the board only as the contract's events, never through the board path, so their chosen bytes are bounded by what the contract accepts (Direct submit, Residuals). Without rule 2, a corrupt trustee could archive chosen bytes in receipts for ballot hashes of its choosing. Refusing an unfounded complaint also keeps a readable share out of the permanent archive through the board path (the contract path can't, Residuals): its `D` and the posted `m_i` open the share at once (T-15). An unfounded complaint can't change a counted set, so refusing it costs the result nothing; it only loses the evidence against its signer, which the trustee could have published elsewhere anyway.

The verifier still reads whatever the board holds, as the delivery check below says: a record the operator should have refused is read like any other and, where it fails, ignored, and a posting boarded through the board path is a rejected entry. Reporting such a record against the operator is [[verifier]]'s (P1-19).

### Direct submit

A voter who bypasses our servers delivers to the trustees' intake directly (T-25), and its ballot reaches the board as a contract event. Its receipts must reach the board too, or the ballot is never delivered; and for any ballot, cast through our API or not, an operator that withholds board-path receipts or complaints silently keeps it out of the counted set, or keeps an invalid one in it. Postings have no other path at all. A contract path for share receipts, postings and complaints, emitted as events under the event accumulator ([[contracts]]), MUST exist before any election registry is deployed (P1-18; T-25, T-54), for every ballot, not only those the contract recorded. It is the only path for postings: a contract event's data is on L2, which every trustee's own L2 node reads, so no operator can keep a posting from the trustees through the complaint window and then publish it, keeping an invalid ballot counted that no trustee could complain about ([[0002-everlasting-privacy]], Decision, 2026-10-12; T-54). Trustee nodes MUST send their receipts through the contract path too, so an operator that refuses receipts can't keep a receipted ballot undelivered (Client rules). What the operator serves is never enough to stand down: before its first anchor, an entry can be shown to some readers and dropped from the checkpoint ([[board]], Residuals). So a record or ballot counts as **anchored** for these rules only once the timely checkpoint for its segment, which the node or client reads from L1 itself, covers it with an inclusion proof ([[board]], Consistency proofs, client rule 2), and as **recorded by the contract** only once its contract event is derivable from finalized L1 data, read through sources the node or client chose itself, never our API, one server's claim or a sequencer's soft confirmation ([[revoting]], R5; [[0004-l2-choice]], Finality). Let `F` be the L2's forced-inclusion delay plus the missed-slot margin ([[0004-l2-choice]]), and `c_D = t_D − F` the last moment a contract-path receipt is sure to land in time, even forced through L1. For every receipt it **owes** (below), a node sends the receipt through the contract path, by `c_D` at the latest, unless by then a passing receipt for that ballot and seat is anchored. It sends them as share-receipt batches (Share-receipt batch), each of up to `RECEIPT_BATCH_MAX` of the receipts it owes, which is what Capacity sizes; a pair of a batch the contract recorded is a receipt the contract recorded for every rule here and in Client rules, and a single receipt through `submitReceipts` is still accepted. In an election that commits roots (What a node owes, below) it sends one receipt root instead, whose leaves are never a receipt the contract recorded for these rules: they count only once available, which is decided after the deadlines (Leaf availability). A ballot is **shown absent** when the node holds the published data of every timely checkpoint for the segments up to `period(closes_at) + 1`, matching the anchored roots, none of it carries the ballot, and the contract hasn't recorded it. A checkpoint is only a root, so an operator can anchor a ballot and withhold its entries from the nodes until after `c_D` ([[board]], Residuals, withheld tails); a node that lacks any of that data can't show any ballot absent.

**What a node owes** ([[0002-everlasting-privacy]], Decision, 2026-10-12). Every ballot a node receipts passed admission at intake, its membership proof included ([[share-encryption]], Intake and receipts), so each names a (`tier`, `ν`) of a registered member. A node decides what it owes at the **intake cutoff** `c_I = c_D − R = t_D − F − R`, with `F` and `R` the values the release pins and `deliveryWindowFits` checks (below), so every node and client computes the same `c_I`. By then L1 has finalized blocks after `closes_at`, so every L1 reference is decided ([[revoting]], Admission), and every counted ballot's anchoring or contract recording is confirmable (the windows' bound below). Its **view** is the ballots it receipted, less those it can show absent, together with every ballot it holds from the anchored board or the contract's records, each copy kept only if it passes the admission checks ([[ballot-validity]], Admission) and the entry that carries it is inside the poll's window ([[close]], Window: [[verifier]] 5.5, judged by its path, as the verifier judges it), whatever its L1 reference. A copy outside the window never counts or displaces another, so a ballot boarded after `s_A`, or recorded by the contract outside the window, can't take the place of the ballot the delivery check selects; and since a node shows a ballot absent from the timely checkpoints up to `s_A`, a receipted ballot that reached the board only late leaves the view too. For each (`tier`, `ν`) of a ballot it receipted, it applies [[revoting]]'s Selection (repeats, then the single newest block, a tie selecting nothing) to the view's ballots of that (`tier`, `ν`) whose L1 reference is admitted ([[revoting]], Admission), read from finalized L1 through sources the node chose; those whose reference isn't admitted stay in the view for the second rule below. If it holds a receipt for the selected ballot's `ballot_hash`, under any L1 reference and whether or not the copy it receipted is still in its view (a copy it showed absent keeps its receipt), it owes that receipt; otherwise, or on a tie, it owes nothing for that (`tier`, `ν`). A receipt is for a ballot hash, which leaves out the L1 reference ([[share-encryption]], Notes, One public part), and the delivery check reads it so: a ballot cast again with the same core after its block was reorganised away ([[revoting]], Client rule 4) keeps the receipts its first cast got, and the client treats those seats as receipted (Client rules), so a node owes them for the copy that is selected even if its own copy fails the L1 check. Its own copy failing the L1 check doesn't settle it either: when the operator withholds the board's data, the node may hold no copy of the ballot cast again, so for each (`tier`, `ν`) it also owes the receipt of the newest ballot in its view whose `ballot_hash` it holds a receipt for and whose L1 reference isn't admitted (the highest `l1_ref_number`, the smaller ballot hash on a tie, so every node agrees), whatever it selected. The node decides **once**, at `c_I`, over the view it then holds. It MUST keep intake open until `c_I`, so a client that retries because a trustee or the relay was down at the close still gets its receipt (Client rules), and from `c_I` it refuses intake for the election: a receipt it issued later would be one no decision covers, and with `R` left it could no longer send it in time. Deciding again as the view changed would make the obligation the union of every decision, which an operator releasing data at chosen times, or a member getting their own ballots recorded one at a time, could grow without bound. So a node gathers board data and contract records before `c_I`, and a ballot it learns of only afterwards changes nothing it owes. So a node owes at most two contract-path receipts per (`tier`, `ν`) of the election, and at most

```
2 · Σ over the definition's tiers t of group_size_t
```

in all: two per member of each tier, which 2.4 recomputes from the group registry (under definition version 3 or 4 the cells' `members`, whose sum per tier is the same), whatever the operator withholds and however many ballots anyone delivers. Under a rolling definition (definition version 7, `electorate_mode` 2; ballot version 5) the definition's `group_size_t` is only the opening count, and the sum is over each rolling tier's **members over the poll**: the distinct commitments live at some step the poll accepts for the tier, which the node computes from the same replay of the group registry as its intake ([[membership]], Rolling tier tree, Root clock and steps; [[share-encryption]], Ballot version 4, Ballot version 5). A secret has one nullifier per tier at every step ([[membership]], Rolling scope), so this is the same bound, over the poll's span instead of one block; it isn't known when the poll opens, so a node refuses every rolling definition (Capacity) until the forced path is sized for a rolling poll's growth, which MUST happen before any registry accepts one ([[P2-17]]). A member holds one nullifier per tier ([[membership]], Scope), and only a member's ballot passes intake, so no flood of ballots, ineligible or re-voted, adds to it (T-52, T-54, T-25). Receipting a ballot never obliges a node to send any other: a re-vote it receipted replaces the ballot it supersedes in the node's view, so a voter's re-votes cost a node at most two receipts, never one per ballot.

Why the view, and not every ballot receipted: the delivery check reads only the ballot [[revoting]] selects for each (`tier`, `ν`) from the board (Delivery check), so a receipt for any other ballot delivers nothing. The node's view differs from the board only by ballots it receipted that never reached the board but that it can't show absent, and by ballots on the board it doesn't hold; either way the node can be wrong only about a voter whose newest ballot isn't on the board (Residuals). A ballot the node holds from the board is in its view whoever receipted it, so a newer ballot this seat never receipted (its intake failed, say) correctly leaves the node owing nothing for the ballot it supersedes.

**What a node owes in complaints.** At the same decision, `c_I`, over the same view, the node fixes its **complaint scope**: for each (`tier`, `ν`) of any ballot in its view, receipted or not, the ballot hash of the ballot the same selection picks, if any, and that of the newest ballot of the view whose L1 reference isn't admitted (the highest `l1_ref_number`, the smaller ballot hash on a tie). It owes one complaint for each ballot hash in its scope for which a contract-path posting for its seat, in time for the delivery deadline, passes the public check and opens to shares that fail ([[share-encryption]], Complaints), and sends it through the contract path by `c_K = t_K − F` at the latest, unless by then a proven complaint for that ballot hash and seat is anchored or recorded by the contract. It sends them as share-complaint batches, each of up to `COMPLAINT_BATCH_MAX` of the complaints it owes, which is what Capacity sizes, or, in an election that commits roots, as one complaint root (below); a proven entry of a batch the contract recorded is a proven complaint the contract recorded for these rules, and a root's leaf never is. One complaint covers every passing posting for that ballot and seat, since they all carry the same `ct_i` and `m_i` (Delivery check). A complaint can change a counted set only for the ballot the delivery check selects, and a ballot cast again with the same core keeps its ballot hash, so the scope holds every ballot hash a complaint can matter for from what the node holds, and the node owes at most two complaints per (`tier`, `ν`), the bound its receipts have, however many postings anyone sends. The scope comes from the ballots the node holds, never from postings: a member can make up ballots that pass the contract's check and post against them without ever submitting them, which the contract can't stop ([[contracts]], Board, Known-weak), and none of those adds to what a node owes. A node SHOULD also complain, as its budget allows and only after every complaint it owes, about a failing posting outside its scope whose ballot it can't show absent: such a ballot can be counted only if the operator withheld it from the node (Residuals).

**Elections that commit roots** ([[0031-national-delivery-obligation]]). An election **commits roots** if, alone, with everything its seats may owe sent as batches, it doesn't fit the forced path (Capacity): its `M` members are more than `forcedPathMembersLimit` gives for its seats at the release's `R`, so every node and client decides it alike from the definition, the counts [[verifier]] 2.4 recomputes and the release's figures. In such an election a node sends what it owes as obligation roots instead of batches: one receipt root over every receipt it owes, through the contract path by `c_D`, and one complaint root over every complaint it owes by `c_K`, each only if it owes at least one, and each over exactly what it decided at `c_I` (the complaint root once the postings in time are recorded, by `t_D + W_C`), anchored or not, since a root is sent once and can't be added to. It publishes each root's leaf object from the moment it submits the root (Leaf availability). It MAY also send batches of what it owes beside a root, as its budget allows, and still sends its receipts through the board path at intake. An election that fits with batches never commits roots, so every election the batches can carry keeps its receipts and complaints in L2 data every reader holds, and never depends on the availability committee for them; only the elections they can't carry do ([[0031-national-delivery-obligation]], Recommendation).

A contract-path record costs the trustee gas, and the forced path through L1 carries only so much of it; these two bounds are what let a node check, before it lends its keys to an election, that it can send everything it may owe in time (Capacity). The windows MUST leave every counted ballot's anchoring, or its recording by the contract, confirmable on finalized L1 by `c_I`, with `R` left for the node to act by `c_D`, and the complaint window must leave a trustee time after the last posting:

```
DELIVERY_WINDOW                    ≥ max(2 · period + deadline + A, W_C) + R + F
COMPLAINT_WINDOW − DELIVERY_WINDOW ≥ W_C + F + R
```

where `period` and `deadline` are the anchoring clock's ([[board]], Timing; a ballot cast by the close is in a segment at most one period after it, anchored by that segment's end plus `deadline`), `A` is `BALLOT_FETCH_ALLOWANCE`, the least time the seats have after that to fetch the ballot extent before they attest it at `c_I` ([[availability]], Windows), `W_C` is the contract-event window (`CONTRACT_EVENT_WINDOW`, [[parameters]]; a ballot or posting submitted at a deadline, forced through L1 if need be, is on the board within it, and so recorded by the contract sooner), and `R` is a margin for L1 finality and for the node to act. P4-1 and P1-18 MUST keep their values within these bounds (`deliveryWindowFits` checks them); with hourly periods, a 12-hour anchoring deadline, `F` of 13 hours (Base's 12-hour forced-inclusion delay and an hour of missed slots), `W_C` of 14 hours and `R` of one hour, and `A` of 12 hours, they need 40 hours of the two days and 28 of the three that follow. The contract:

- accepts a receipt, complaint or batch of either only if it names this definition and is signed by the registered per-election key of the seat it names (P-256 verification on L2, once per batch), and accepts **any number** of them per seat and ballot hash, refusing only a byte-identical repeat. It can't tell a passing receipt from one whose `share_hash` isn't the ballot's, nor a proven complaint from a failing one, so no record ever occupies a slot: a seat that signs junk for a ballot it receipted, colluding with an operator that refuses the honest receipt, can't stop the voter sending that honest receipt through the contract afterwards. Extra records cost only the signing seat's gas;
- accepts an obligation root only if it names this definition and is signed by the registered per-election key of the seat it names, and only the first such root of each seat and kind for the definition: it fills that seat's slot, which only the seat's signature can, as with close statements ([[contracts]], Close statements), so no one else can take it and a verifier reads at most two leaf objects per seat (Obligation root). It can't fetch the leaves or judge them. The call (`submitObligationRoot`, `root-repeat` for a filled slot) and its event come in contract-event version 5 ([[contracts]], Board, Delivery records; Contract-event record, Event tables (version 5)); the registry has pinned a version that carries it since [[P1-12f]] part 1b-2, version 6 since [[P3-3]] part 3b-2a, but until the code that reads roots and the attestation that makes their leaves available exist no root can deliver, so a node refuses every election that commits roots (Capacity);
- accepts a posting only together with the record of the ballot it delivers, whatever path that ballot took, from whose tier (under ballot versions 2, 3 and 4, its cell, hashed under its own version, [[ballot-validity]], Ballot record (version 2), Ballot record (version 3), Ballot record (version 4)), nullifier and committed vote it recomputes the ballot hash itself ([[contracts]], Board, Delivery records). The client always holds that record, so one call serves a ballot cast through our API and a direct-submitted one alike, and the contract keeps no ballot's share hashes. It accepts the posting only if `H(DS("abolish/v1/share-ciphertext", ct))` equals that ballot's `share_hashes[seat]` (one SHA-256) and `sealed` is `4 + 64·m + 16` bytes for the definition's `m`, so only `m` is free in it, and it accepts **any number** of postings per seat and ballot hash, refusing only a byte-identical repeat. It can't run the public check (ML-KEM re-encapsulation and ristretto255 arithmetic), so it never lets a posting occupy a slot: a junk posting, made by anyone who saw `ct_i` in a pending transaction, fails the public check and is ignored, and the voter's own posting is still accepted beside it;
- never admits a ballot because of a delivery record: the ballot record in a posting call must pass the board's ballot check, so no one but a member can make one up to carry a ciphertext of their choosing, but it is carried only to bind the posting and is never emitted, and the ballot counts only if its own ballot entry or direct submission is admitted ([[verifier]] 5).

So, with the client rules below, no operator or third party can drop a receipted ballot that the delivery check selects without the trustee's node and every route the client has also failing, since neither stands down on anything short of an anchored receipt or one recorded by the contract in that sense, and the node's obligation is bounded by the electorate (What a node owes), except where the voter's newest ballot never reached the board (Residuals); and a trustee that receipts and never sends its receipt has signed a receipt the voter holds (Residuals). A seat, or an adversary that controls every route to it, can still refuse intake, and then the voter chooses between posting that seat, which the contract can't block, and leaving the ballot undelivered; nothing on the board attributes either (T-25, Residuals). A contract-path record names its ballot hash, or carries its tier (or cell) and nullifier, so the address that pays its gas is publicly linked to the ballot and, through the nullifier, to the voter's re-votes. The client MUST pay from a fresh, privately funded address, or through a relay that can't link it to the voter, as [[0004-l2-choice]] requires for direct submission (T-11, T-13); P1-18 and P2-8 carry this. A record it accepted is boarded as a contract event, late or not ([[verifier]] 4.4), and is in time by its submission time (Windows). P1-18 defines how the contract-event record carries it; the delivery check reads it as if it were the record itself, on the board where its contract event is.

### Capacity

A node's obligation is payable only if it can send all of it by the deadlines when the sequencer refuses its transactions, so that every record goes through L1 as a deposit ([[0004-l2-choice]], Forced inclusion). The portal meters deposits' gas per L1 block: at most `20,000,000` in one block, and above a target of a tenth of that, `2,000,000`, the metered price rises each block by up to an eighth of the excess over the target, relative to the target, as EIP-1559's base fee does; so depositing above the target for more than a few blocks costs an exponentially rising price, and the target is what depositors can sustain over hours. These are the OP Stack's metering parameters as Base's and Base Sepolia's `SystemConfig` set them (`resourceConfig()`: `maxResourceLimit` 20,000,000, `elasticityMultiplier` 10, `baseFeeMaxChangeDenominator` 8, read on L1 at mainnet block 26,199,382), which Base's multisig can change without delay ([[0004-l2-choice]], Upgrades). A deposit also carries at most 120,000 bytes of data.

The release pins the forced path's figures; the board's tests bind the three call figures to measured gas (`vectors/delivery-obligation.json`, `forcedPath`, and `vectors/delivery-root.json`, `rootCallGas`; [[contracts]], Board, Vectors):

| Name                  | Value     | Meaning                                                                                                                                                           |
| --------------------- | --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `DEPOSIT_GAS_TARGET`  | 2,000,000 | Deposit gas per L1 block that every seat of every election together may use: the portal's target                                                                  |
| `L1_BLOCK_SECONDS`    | 13        | Seconds per L1 block: 12-second slots with at most one in 13 missed, the margin `F` assumes ([[parameters]], `MAX_SEQUENCING_WINDOW`)                             |
| `RECEIPTS_PER_CALL`   | 1,024     | Receipts in one `submitReceiptBatch` call: one batch of `RECEIPT_BATCH_MAX` pairs, 65,640 bytes, 65,732 of calldata, within a deposit's 120,000                   |
| `RECEIPT_CALL_GAS`    | 4,500,000 | Gas of one batch call of up to `RECEIPTS_PER_CALL` receipts, its intrinsic gas included, within a deposit's 20,000,000 (measured cold: about 4,172,000 for 1,024) |
| `COMPLAINTS_PER_CALL` | 512       | Complaints in one `submitComplaintBatch` call: one batch of `COMPLAINT_BATCH_MAX` entries, 65,640 bytes, 65,732 of calldata                                       |
| `COMPLAINT_CALL_GAS`  | 5,000,000 | Gas of one complaint-batch call of up to `COMPLAINTS_PER_CALL` complaints, its intrinsic gas included (measured cold: about 4,566,000 for 512)                    |
| `ROOT_CALL_GAS`       | 200,000   | Gas of one `submitObligationRoot` call, its intrinsic gas included, whatever its count (measured cold: about 176,000 with dense calldata)                         |

The call figures assume that the board verifies P-256 through the `P256VERIFY` precompile at 0x100, as Base does (RIP-7212, at 3,450 gas; the measurement uses EIP-7951's 6,900, which a later upgrade of Base may bring); without it a receipt alone costs about 340,000 gas ([[contracts]], Board, Gas). The figures are measured cold, against real registries: a forced call is a deposit of its own, so every account and slot it reads (the board, both registries, the event accumulator) is cold. Each figure is also the safe gas limit for that call's deposit, which is what the portal meters: a node sets it as the deposit's `gasLimit`, and the board's tests run a further cold call of new records with exactly that limit and require it to be accepted. The measurement is taken from the caller, so it slightly overstates what the call itself needs.

For an election with `s` seats (the default panel's `n`, plus `n_A` with an author panel) and `M` members (the sum over its tiers of `group_size`, or under definition versions 3 to 6 of each tier's `regions`, the counts [[verifier]] 2.4 recomputes from the group registry), every seat may have to force:

- its receipts, at most `2M` (What a node owes): `G_R = s · ⌈2M / RECEIPTS_PER_CALL⌉ · RECEIPT_CALL_GAS` for all seats, from the intake cutoff `c_I` to `c_D = t_D − F`, which is `R` seconds;
- its complaints, at most `2M`: `G_K = s · ⌈2M / COMPLAINTS_PER_CALL⌉ · COMPLAINT_CALL_GAS`, from `t_D + W_C`, by when every posting in time is recorded, to `c_K = t_K − F`, which is `COMPLAINT_WINDOW − DELIVERY_WINDOW − W_C − F` seconds, at least `R` by the windows' bound above.

An election that commits roots (What a node owes) has the same two intervals, each carrying one root call per seat whatever `M` is: `G_R = G_K = s · ROOT_CALL_GAS`. Whether it commits roots is decided first, for the election alone with the batch figures above, so the batch figures and the root figure never mix within one election.

Each is spread evenly over its interval, half-open, as a rate in gas per second. A set of elections **fits** the forced path if at every moment the rates of the intervals containing it, over every election of the set, sum to at most `DEPOSIT_GAS_TARGET / L1_BLOCK_SECONDS`. The sum rises only where an interval starts, so it is enough to check it at each start. `forcedPathFits` (`packages/crypto`) is this check, `forcedPathElectionOf` reads `M` and `s` from a definition, and `forcedPathMembersLimit` gives the largest `M` one election alone fits with batches, above which it commits roots. Until the code that reads roots exists ([[P1-12f]] parts 2 and 3; the registry has pinned a contract-event version that carries the board's root call since part 1b-2, version 6 since [[P3-3]] part 3b-2a, version 7 since [[P3-2]] part 5b-2, version 8 since [[P4-3]] part 2c-3) and [[P4-3]] part 2c brings the attestation that makes leaves available, `forcedPathFits` counts every election with the batch figures, so a node refuses every election that would commit roots: refusing is the safe side, since a root that can't be sent, or whose leaves can't be available, would leave a seat unable to deliver what it owes.

Before it lends its keys to an election, a trustee node MUST check that the election fits together with every election its seat has already approved a ceremony for whose intervals can overlap the new one's, using the stub's member counts once [[verifier]] 2.4 has checked them against the chain, and refuse a stub that doesn't ([[ceremony]], Stub checks). An approved election stops counting only once finalized L2 shows it can never be registered: its `opens_at` has passed and the election registry holds no registration of its definition, which the registry would refuse from `opens_at` on ([[contracts]], Election registry, Registration, rule 6). Until then a node counts it, since its signature may still register it. A rolling definition's members over the poll aren't known when it opens (What a node owes), so a node refuses every rolling stub until [[P2-17]] sizes the forced path for a rolling poll's growth. An honest seat thus only serves elections whose receipts and complaints it can force through L1 in time at the portal's target, whatever the operator withholds and the sequencer refuses. A seat that refuses never becomes qualified, so it receives no shares and owes nothing; once more seats refuse than the ceremony's quorum `max(k, n − 1)` leaves room for, the election gets no ceremony registration and can't be registered ([[ceremony]], Approval and re-runs; T-25, T-52, T-54).

The figures make this a hard cap. With the deployed windows (hourly periods, a 12-hour anchoring deadline, `F` of 13 hours and `W_C` of 14) and `R` of one hour, one election alone fits at most 20,992 members with 3 seats, 12,288 with 5, 3,584 with 16 and 1,536 with 32, its receipts binding; `R` is the release's, and the windows allow up to 9 hours (`deliveryWindowFits`, with [[availability]]'s `A`), at 188,928 members with 3 seats, 113,152 with 5 and 35,328 with 16, at the price of an intake cutoff 26 hours after `closes_at + l1_inclusion_bound` instead of 34. Before `A` they allowed up to 21 hours, where the complaints bind, at 425,216 members with 3 seats, 254,976 with 5 and 79,616 with 16 (434,688, 260,864 and 81,408 while `W_C` was taken as 13 hours); `delivery-obligation.json` keeps those caps as computations of the forced path, which no release can now choose. A receipt costs about 4,100 gas on the forced path inside a full batch, against about 67,000 for a single receipt, which carries its own signature, storage key and event ([[P1-12d]]), and a complaint about 8,900 inside a full complaint batch, against about 157,000 alone ([[P1-12e]]). The cap still grows only linearly with what each record costs, and no record per receipt or complaint on L1 can carry a national electorate; an election above it commits roots instead ([[0031-national-delivery-obligation]]), whose forced path costs `s · ROOT_CALL_GAS` per interval at any `M`: at `R` of one hour, 16 seats, the most a default panel has, take about 0.58% of the target over the receipt interval, so the electorate no longer bounds the forced path, and only many overlapping elections with large panels do (Residuals).

### Client rules

A trustee that returns a valid receipt and never boards it would leave its seat undelivered, and an operator could do the same by refusing the client's copy. And a client that posted whenever its own boarding failed would let an operator that refuses receipts force every share onto the permanent board with `m_i`, readable by anyone who later breaks its classical encryption (T-15). So delivery never rests on one party boarding a receipt, and a client never posts a seat whose receipt passes ([[0002-everlasting-privacy]], Decision, 2026-10-12). The ballot client (P2-8) MUST, for every qualified seat `i`:

1. Treat seat `i` as receipted only if its receipt passes `share-receipt` against the exact ballot it casts (the receipt's statement rebuilt from that ballot, [[share-encryption]], Intake and receipts).
2. Never post a receipted seat, whatever happens to its receipt afterwards. It erases `m_i`, `e_i` and `w_i` for that seat at cast.
3. Keep every receipt and see one onto the board: submit it through the board path once its ballot entry is boarded, and check the operator's receipt for that entry ([[receipts]], Checks at cast), so a later drop is attributable; where the operator refuses the copy because a passing receipt is already boarded (Boarding, rule 5), obtain the operator's signed receipt and inclusion proof for that existing entry instead, and check it the same way. Until a passing receipt for its ballot hash and seat `i` is anchored (Direct submit) or recorded by the contract, whoever sent it, resubmit through every path it has, the contract path included, early enough to be in time even forced through L1; a receipt the operator only serves, unanchored, never stops it.
4. For a seat that isn't receipted, retry intake, and before treating private delivery as failed, try at least one route to seat `i`'s intake that doesn't pass through the operator: the trustee node's own intake endpoint, which the release lists with the pinned panel, reached through a network anonymiser so the trustee doesn't learn the voter's address (T-11): a delivery sealed to the seat's per-election KEM key and carried by an Oblivious HTTP relay ([[sealed-delivery]]). Only if every route fails, post `(i, ct_i, m_i)`, and only if the voter explicitly chooses to, after the client says that a posting lowers that seat's long-term privacy for this ballot: anyone who later breaks the share's classical encryption reads it, and a ballot with `k` or more seats posted is read whole ([[tally]], Residuals). The client asks as soon as delivery has failed, while the poll is open if it can, so a voter who declines can still re-vote, and keeps retrying intake until the intake cutoff `c_I` (Direct submit), after which every node refuses it; a posting the voter chooses then still has until `c_D = t_D − F` to be sent, so that, forced through L1, its submission time is at or before `t_D`. It posts only through the contract path. A client that sends a ballot only once every seat is receipted or posted, as the ballot client does ([[0002-everlasting-privacy]], Synchronous intake), never has its own ballot on the board undelivered, and no path admits a ballot after `closes_at` ([[close]], Window), so for its own casts these deadlines end at the close: it reads them as [[posting-relay]], The ballot's own deadline, says, and erases at the close. The later allowances, to `c_I` and `c_D`, serve a ballot already on the board. Until then it keeps only `ct_i` and `m_i` for that seat, never `e_i` or `w_i` (T-18), and it erases them once the voter declines or the deadline passes.

Trustee nodes board their receipts through the board path and, where that fails, send them through the contract path (Direct submit), so a receipted seat is delivered even when the client goes away; the client's own copies are a second route, never the only one.

In an election that commits roots, a client MAY ask a seat's node, once the node's receipt root is recorded by the contract, for the inclusion proof of its receipt's leaf, and check it against that root (Obligation root, Obligation tree): evidence, under the seat's own signature, that the seat counted the voter's receipt in what it owes, kept with the receipt. It never stands down on it: a leaf counts only if its root's leaves are available, which is decided only at the counted extent's attestation, long after the delivery deadline (Leaf availability), so rule 3 applies to a receipt that is a leaf as to any other. A seat that isn't receipted and that the voter doesn't post leaves the ballot undelivered: the voter is told so, and can re-vote while the poll is open.

## Delivery check

The verifier ([[verifier]] 5.9) takes the election's definition hash, its registered key set (each qualified seat's KEM key and signing key, [[ceremony]], Transcript check), `s_D`, `s_K`, `t_D` and `t_K`, the ballots [[revoting]] selects for each cell from the counted extent ([[tally]], Context), and every delivery record in the counted extent, in board order, each with its path: a board entry's payload with its segment, or a contract event's record with its submission time. A posting, a batch or an obligation root through the board path is a rejected entry (Decoding). Each pair of a contract-path share-receipt batch is read as the share receipt it states (Share-receipt batch), at the batch's place on the board and with its submission time, and passes `share-receipt` exactly when its `share_hash` is the ballot's for its seat and the batch's signature verifies; each entry of a contract-path share-complaint batch is read as the complaint it states, attributed by the batch's signature, the batch's submission time its own. It also takes, for each contract-path obligation root, whether its leaves are available (Leaf availability) and, for each available one, its leaf object, and the obligation's bound `2M`. Each contract-path obligation root is read once, as a record, and either set aside with the first of these codes that applies, in this order, or read leaf by leaf: `delivery-stray` (another definition), `delivery-seat` (a seat outside the registered key set), `root-signature` (its signature doesn't verify under its seat's registered signing key), `root-repeat` (an earlier root in board order of this definition, seat and kind whose signature verifies), `delivery-late` (a receipt root submitted after `t_D`, a complaint root after `t_K`), `root-count`, `root-withheld` and `root-inconsistent` (Leaf availability). Each of these is reported once for the root, whatever ballots its leaves name, since naming them would mean reading leaves that may not be held. A root that passes them all is read leaf by leaf, each leaf at the root's place on the board and with its submission time, as a batch's pairs or entries are: each leaf of a receipt root as the share receipt it states, passing `share-receipt` exactly when its `share_hash` is the ballot's for its seat (the root's signature has verified), and each leaf of a complaint root as the complaint it states, attributed to its seat. For each selected ballot `b`, with `bh = ballot_hash(b)` recomputed from the decoded ballot:

- **Seat `i` is delivered** if it isn't in the registered key set, or if some record in time names this definition, `bh` and seat `i`, and is either a share receipt, by either path, whose `share_hash` is `b`'s `share_hashes[i]` and which passes `share-receipt` against `b`, or a contract-path posting that passes the public check against `b` (`posting-hash`, `posting-proof`, `posting-encapsulation`).
- **The ballot is delivered** if every seat `1, …, n` is: every qualified seat has a receipt or a passing contract-path posting in time.
- **A complaint about seat `i` is proven** if it names this definition, `bh` and seat `i`, is in time for the complaint window (by either path), a contract-path posting for `b` and seat `i` that is in time for the delivery deadline passes the public check, wherever its contract event is on the board, and the complaint passes `complaint-proof` and doesn't fail `complaint-unfounded` against that posting ([[share-encryption]], Complaints). Every passing posting for `b` and seat `i` carries the same `ct_i` (its hash is `share_hashes[i]`) and the same `m_i` (unique for `ct_M`), so which one is used doesn't matter.
- **The ballot is excluded** if any complaint about any of its seats is proven, attributed or not.

`b` stays in the counted set exactly when it is delivered and not excluded; otherwise it counts nothing, with no fallback to an earlier ballot of its nullifier ([[revoting]], No fallback). Neither outcome depends on the order of the records, on duplicates or on records for other ballots, so the operator's ordering decides nothing ([[verifier]] 6.1, R3). The one exception is `root-repeat`, which keeps the first root of a seat and kind; roots reach the board only as the board contract's events, which accepts one per slot, so that first root is fixed by the contract's event sequence, never by an order the operator chooses.

The report lists, for each selected ballot, whether it was delivered, which seats were missing, and each proven complaint with its attribution; and, for the records:

A batch is one record: `delivery-stray` is reported once for a batch naming another definition, and every other code once for each of its pairs or entries that names a selected ballot, with its index in the batch from 0 as `pair`; a batch whose signature doesn't verify under its seat's registered signing key is `share-receipt` for each such pair, attributed to no one, and one that verifies is attributed to its seat for each pair whose `share_hash` isn't the ballot's. Each record, and each such pair, is reported with the first of these codes that applies, in table order, so a late record for this definition, a selected ballot and a registered seat is reported late, whatever else is wrong with it. An obligation root's own codes (`delivery-stray`, `delivery-seat`, `delivery-late` and the five `root-*`) are reported once for the root, in the order Delivery check gives; every code for a leaf of a root that is read is reported once for each leaf that names a selected ballot, with its index in the leaf list from 0 as `leaf`, a leaf of a receipt root that fails `share-receipt` attributed to the root's seat, whose signature has verified. Records naming a ballot that isn't selected (an earlier ballot of a re-voting nullifier, a ballot outside the counted extent) are read and set aside: they decide nothing, and nothing is reported for them. A record that doesn't decode is a rejected entry (Decoding).

Notes:

- **Seats that aren't qualified.** A ceremony can end with fewer than `n` qualified seats ([[ceremony]], Transcript check), and shares are encrypted only to qualified seats' keys. For a seat outside the registered key set the client encrypts nothing and sets the ballot's `share_hashes[i]` to 32 zero bytes; that seat needs no delivery and is never summed, and its share of the vote is simply never sent, so the tally needs `k` of the qualified seats. The ballot record's admission checks reject any other value there (`share-hash-unqualified`, [[ballot-validity]], Ballot record), so a ballot can't carry chosen bytes in the share hashes of the `n − q` seats that aren't qualified (T-17).
- **A receipt and a proven complaint for one seat.** A trustee receipts only shares that pass its own intake, and a proven complaint shows publicly that the same ciphertext's shares don't, so both can't be honest. The ballot is excluded, since the proof is public and the trustee can't sum it correctly either, and the receipt is reported against its seat (T-29).
- **Postings next to receipts.** A passing posting for a seat that also has a receipt is redundant, and the client never makes one (Client rules); but the contract can't tell, so one found among the contract events still delivers, and [[verifier]] 8.2 counts it as readable ([[tally]], Residuals). Only the client and the seat's own trustee know `m_i`, and the trustee could publish the share anyway (T-14).

## Version 2

Ballot version 4 ([[ballot-validity]], Ballot record (version 4)) shares each vote to two panels, so its delivery records name the seat's panel as well as its index: the share receipt, posting and complaint, both batches and the obligation root at version 2, which ballot version 4 fixes with the same windows (Versions). Everything not stated here is version 1's: the windows, the boarding rules, the contract path, what a node owes, the client rules and the delivery check, each applied per seat of either panel. `panel` is an `enum8<1, 2>`, 1 the default panel and 2 the author panel ([[ballot-validity]], Context (version 4)); a seat's **panel key set** is the registered key set of its own panel ([[share-encryption]], Ballot version 4, Keys).

### Records (version 2)

**Share receipt (`0x000c`, version 2):**

| Field             | Type          | Meaning                                                                           |
| ----------------- | ------------- | --------------------------------------------------------------------------------- |
| `definition_hash` | `bytes[32]`   | The election's definition hash                                                    |
| `ballot_hash`     | `bytes[32]`   | The ballot hash of the public part the trustee checked                            |
| `panel`           | `enum8<1, 2>` | The seat's panel                                                                  |
| `seat`            | `u8`          | The seat's index in its panel, `i`                                                |
| `share_hash`      | `bytes[32]`   | `H(ct_i)`                                                                         |
| `signature`       | `p256-sig`    | The seat's signature under `abolish/v1/sig/share-receipt-2` over the first fields |

The fields before `signature` are the 98-byte statement of [[share-encryption]] (Share receipt (ballot version 4)). 165 bytes with its header.

**Share posting (`0x000d`, version 2):** version 1's fields with `panel` (`enum8<1, 2>`) between `ballot_hash` and `seat`; `ciphertext` is checked against the seat's own panel ([[share-encryption]], Public posting (ballot version 4)). 1,309 + 64·`T` bytes with its header, for `T` flat options.

**Share complaint (`0x000e`, version 2):** version 1's fields with `panel` (`enum8<1, 2>`) between `ballot_hash` and `seat`, and its proof under [[share-encryption]]'s Complaints (ballot version 4). The signature is by the seat's per-election signing key, registered in its panel key set, under `abolish/v1/sig/share-complaint-2`, over

```
m = definition_hash ‖ ballot_hash ‖ u8(panel) ‖ u8(seat) ‖ encode(proof)
```

162 bytes, and attributes the complaint to seat `seat` of panel `panel` if and only if that seat has registered keys in its panel key set and the signature verifies under its registered signing key; any other complaint is unattributed. 229 bytes with its header. The signed tags are new for the reason [[share-encryption]] gives: version 1's statements name no version, so one tag over both would have two layouts.

**Share-receipt batch (`0x0016`, version 2):**

| Field             | Type                                    | Meaning                                                                                 |
| ----------------- | --------------------------------------- | --------------------------------------------------------------------------------------- |
| `definition_hash` | `bytes[32]`                             | The election's definition hash                                                          |
| `panel`           | `enum8<1, 2>`                           | The seat's panel                                                                        |
| `seat`            | `u8`                                    | The seat's index in its panel, `i`                                                      |
| `receipts`        | `list<receipt_pair, RECEIPT_BATCH_MAX>` | 1 to `RECEIPT_BATCH_MAX` pairs, strictly ascending by `ballot_hash`, as in version 1    |
| `signature`       | `p256-sig`                              | The seat's signature under `abolish/v1/sig/share-receipt-batch-2` over the first fields |

The signature is an ECDSA P-256 signature by the seat's per-election signing key, registered in its panel key set, under `abolish/v1/sig/share-receipt-batch-2`, over

```
m = definition_hash ‖ u8(panel) ‖ u8(seat) ‖ u32(c) ‖ (ballot_hash ‖ share_hash) × c
```

the record's fields without its header and signature, `38 + 64·c` bytes. A batch of `c` pairs is `105 + 64·c` bytes with its header: 65,641 at `RECEIPT_BATCH_MAX`. Each pair **reads as the version-2 share receipt** `(definition_hash, ballot_hash, panel, seat, share_hash)` it states, and passes `share-receipt` against a ballot `b` exactly when `share_hash` is `b`'s share hash for that seat in that panel (`share_hashes[seat]` for panel 1, `author_share_hashes[seat]` for panel 2) and the batch's signature verifies under that seat's registered signing key in its panel key set. Everything else is version 1's: what signing states, that a node batches only receipts it issued, and the pairs' order.

**Share-complaint batch (`0x0017`, version 2):** version 1's fields with `panel` (`enum8<1, 2>`) between `definition_hash` and `seat`, each entry's `proof` under [[share-encryption]]'s Complaints (ballot version 4). The signature is by the seat's per-election signing key, registered in its panel key set, under `abolish/v1/sig/share-complaint-batch-2`, over

```
m = definition_hash ‖ u8(panel) ‖ u8(seat) ‖ u32(c) ‖ (ballot_hash ‖ encode(proof)) × c
```

`38 + 128·c` bytes. A batch of `c` entries is `105 + 128·c` bytes with its header: 65,641 at `COMPLAINT_BATCH_MAX`. Each entry **reads as the version-2 share complaint** `(definition_hash, ballot_hash, panel, seat, proof)` it states: proven, unfounded or failing exactly as that complaint would be, and attributed to seat `seat` of panel `panel` exactly when the batch's signature verifies under that seat's registered signing key in its panel key set. Entries are strictly ascending by ballot hash, one per ballot, as in version 1.

**Obligation root (`0x001a`, version 2):**

| Field             | Type          | Meaning                                                                             |
| ----------------- | ------------- | ----------------------------------------------------------------------------------- |
| `definition_hash` | `bytes[32]`   | The election's definition hash                                                      |
| `panel`           | `enum8<1, 2>` | The seat's panel                                                                    |
| `seat`            | `u8`          | The seat's index in its panel, `i`                                                  |
| `kind`            | `enum8<1, 2>` | 1 for a receipt root, 2 for a complaint root, as in version 1                       |
| `count`           | `u32`         | `c`, the number of leaves, at least 1                                               |
| `root`            | `bytes[32]`   | The root of the obligation tree over the leaves                                     |
| `leaves_cid`      | `bytes[36]`   | The binary CID ([[content-addressing]]) of the leaf object                          |
| `signature`       | `p256-sig`    | The seat's signature under `abolish/v1/sig/obligation-root-2` over the first fields |

174 bytes with its header. The signature is by the seat's per-election signing key, registered in its panel key set, under `abolish/v1/sig/obligation-root-2`, over

```
m = definition_hash ‖ u8(panel) ‖ u8(seat) ‖ u8(kind) ‖ u32(c) ‖ root ‖ leaves_cid
```

the record's fields without its header and signature, 107 bytes. The leaves, the leaf object and its CID, the obligation tree under `abolish/v1/obligation/leaf` and `/node`, and its inclusion proofs are version 1's (Obligation root): a leaf is a receipt pair or a complaint entry, which names no panel, and the record that signs the root names it. So each leaf of a receipt root **reads as the version-2 share receipt** `(definition_hash, ballot_hash, panel, seat, share_hash)`, and each leaf of a complaint root as the version-2 complaint `(definition_hash, ballot_hash, panel, seat, proof)`, its proof under Complaints (ballot version 4), each passing or attributed exactly as a batch's pair or entry is, under the root's signature. An attestation names it by `H(DS("abolish/v1/obligation-root", record))` over its whole record, as a version-1 root's; the record begins with its version, so no root of one version has another's record hash. **One per panel, seat and kind**: a seat sends at most one root of each kind for an election, and since seat `i` of the author panel is a different seat from seat `i` of the default panel, the contract path's slot and the delivery check's `root-repeat` are kept per panel, seat and kind, so no seat makes a verifier fetch and read more than two leaf objects of it, whichever panel it is in (T-52, T-17). The bound `2M` (`root-count`) is a seat's, of either panel (What a node owes below).

The three signed tags are new, as the complaint's is: version 1's statements name no version, and each tag has one layout ([[domain-separation]], Rules), so no signature over one version's statement is ever checked as the other's (T-31).

**Decoding.** As version 1's, with `panel` an `enum8<1, 2>`: any other value is `invalid-enum`. Decoding doesn't compare `panel` with the election, so a record naming the author panel in a poll without one is still read, and reported `delivery-seat` (that panel's key set is empty). In both batches and the obligation root `panel` is at offset 35 and every later field is one byte further on than in version 1: `seat` at 36; a batch's count at 37 (`non-canonical` there for no entries and `length-over-max` above its maximum, before any entry is read) and its first entry at 41, its entries' order and fields decoded as version 1's; a root's `kind` at 37 (`invalid-enum` unless 1 or 2), its `count` at 38 (`non-canonical` if 0), `root` at 42, `leaves_cid` at 74 (`non-canonical` unless its first four bytes are the ones its kind and count give, as in version 1) and its signature at 110.

### Boarding, direct submit and client rules (version 2)

Version 1's rules, per seat of either panel, with each rule's "seat of the registered key set" read as a seat of the panel key set of the panel the record names, its signature checked against that key set, and rule 5 per ballot hash, panel and seat. So at most one passing record of each type per seat of each panel per boarded ballot reaches the board through the board path (T-17, T-52).

**What a node owes** is version 1's, for each seat of either panel: an author seat runs membership-checked intake and decides at `c_I` over its own view exactly as a default seat does, so it owes at most two contract-path receipts per (`tier`, `ν`), and the bound holds per seat whatever panel it is in (T-52, T-54). It sends them in version-2 batches, or, in an election that commits roots, in one version-2 root of each kind, as a default seat does. Capacity counts every seat of both panels, at most `2 · MAX_TRUSTEES`; a version-2 batch or root is one byte longer than version 1's, and its calls stay within version 1's figures, an author seat's as a default seat's: a full version-2 receipt batch, complaint batch and root cost, cold, at most `RECEIPT_CALL_GAS`, `COMPLAINT_CALL_GAS` and `ROOT_CALL_GAS` with room left for real registries' reads ([[contracts]], Board, Vectors), so Capacity sizes them with the same figures, with `s` the definition's `panel_size` plus the length of its `author_keys` (`forcedPathElectionOf`).

**The contract path** MUST accept an author seat's receipts and complaints as it does a default seat's: signed by that seat's registered per-election key, checked on L2. The trustee registry records only the key sets of the panels its deployment pins ([[contracts]], Trustee registry), and an author panel is never pinned, so the board contract can't find an author key set there. Giving it one (an author panel's key set, registered under a quorum of approvals by the definition's `author_keys`, as [[ceremony]] for the author panel has them sign) is [[P2-16]] part 5's: the election registry records it with the definition ([[contracts]], Election registry, Author panel registration; [[0035-author-key-set-on-l2]]), and the board checks version-2 records against it ([[contracts]], Board, Delivery records (version 2)). Until a deployment serves it, an author seat can't be delivered through the contract path, so the election registry MUST refuse to register a definition with an author panel, and P2-16 part 5 MUST give the contract that path before any registry accepts one (T-25, T-54). **Version-4 ballots and version-2 records on the contract path.** The board contract MUST take ballot version 4 (its framing, `validity-shape` and `share-hash-unqualified` over both halves, and its ballot hash for the posting path) and the version-2 records under their new tags with the panel byte, both batches and the obligation root among them, with one root slot per panel, seat and kind, before the election registry registers any definition pinning ballot version 4, with or without an author panel; until then the registry MUST refuse such a definition, as it must every profile [[verifier]] 2.3 refuses ([[contracts]], Election registry; P2-16 part 5; T-25, T-54). A posting names its panel, and the contract compares `H(ct)` with that panel's list (`share_hashes` or `author_share_hashes`) and `sealed`'s length with `4 + 64·T + 16`. **Ballot version 5 on the contract path.** A rolling poll's delivery records are these same version-2 records, and the board MUST take them under ballot version 5 as under version 4 before the election registry registers any definition pinning ballot version 5, with a posting's ballot checked against a root its sender supplies, since no rolling root is registered anywhere: `submitRollingPosting(root, posting, ballot)` ([[contracts]], Board, Delivery records (ballot version 5); [[P2-17]]). A client posting in a rolling poll sends the root its ballot was proved against. The root is never emitted: the delivery check reads the posting alone, as under version 4, and it delivers only for a ballot the verifier admits, whose root is the step's own (T-25, T-54).

**Client rules** apply to every qualified seat of both panels. Rule 4's route that bypasses the operator is, for an author seat, the author node's own intake endpoint; the release lists only pinned panels' endpoints, so where an author panel publishes its seats' endpoints is [[P2-16]] part 7's, with the author trustees' names in the display text: an endpoint is free text, which never goes on the board ([[display-text]]; T-17). The client needs no authentication of an endpoint beyond what delivery already checks: each ciphertext is sealed to the seat's registered KEM key with the seat bound in its associated data, and only that seat's registered signing key makes its receipt, so a false endpoint can only drop the delivery, which the client then posts, and see the voter's network address beside the ballot record it receives, a party outside the operator and the registered trustees (T-11). So a client MUST NOT send to an author endpoint without the voter's explicit choice and a path that hides the voter's address; part 7 specifies both. Until then an author seat's only route is the operator's relay, and the client says so before casting (T-25, T-11).

### Leaf availability (version 2)

Version 1's rules (Leaf availability), per panel. A version-2 root is published, fetched, checked for consistency and bounded as a version-1 root is, and a root of panel `P` is **available** if at least `q_P − k_P + 1` of panel `P`'s `q_P` qualified seats, `k_P` its threshold, name it in counted-extent attestations that count ([[availability]], Availability check); otherwise it is **withheld**, reported `root-withheld` against its seat with the seats of panel `P` that named it and those of panel `P` that attested the counted extent without naming it. A seat names, in its counted-extent attestation, only roots of its own panel whose leaf object it holds and has checked, at most two for each seat of its panel, so `2 · MAX_TRUSTEES` still bounds the list ([[availability]], The roots), and the board refuses an attestation naming a root of the other panel ([[contracts]], Board, Availability records). Every seat of either panel MUST still hold, and have checked, the leaf object of every available root of both panels before it sends any summed share, so every honest seat of both panels sums over the same counted set (Summing; T-14, T-29).

Each panel judges its own seats' roots so that neither can withhold the other's: the default panel is the operator alone during launch ([[0027-trustee-panels-and-live-results]], the transitional panel), and an author panel is the voters' protection from it, so a rule letting the default panel's threshold drop an honest author seat's root would hand the operator the ballots that only that root delivers (T-25, T-54). The cost is each panel's own threshold: withholding an honest author seat's root takes `k_A` author seats refusing to name it, and an honest default seat's root `k` default seats. Without an author panel those `k` seats can already open ballots; beside an author panel neither coalition can, since every ballot opens only with both thresholds ([[ballot-validity]], Residuals (version 4)), so each can drop ballots it can't read (Residuals). A root available if either panel's `q_P − k_P + 1` names it would make withholding any honest seat's root take `k` default and `k_A` author seats together, exactly the coalition that can read ballots, as in version 1, while naming a root falsely would still only stall; it needs every seat to name both panels' roots, so an attestation's list grows to `4 · MAX_TRUSTEES` under a new attestation version. [[0037-version-2-root-availability]] chooses the per-panel rule for now and records that one as the stronger alternative. Making a root available whose leaves no honest seat holds takes `q_A − k_A + 1` author seats naming it falsely, which can already stall the tally by refusing their partial openings (`tally-missing`, [[tally]], Author panel), and here only stalls it, as in version 1.

### Delivery check (version 2)

The delivery check of version 1, over the seats of both panels. For each selected ballot `b`, with `bh` recomputed:

- **Seat `i` of panel `P` is delivered** if it isn't in `P`'s panel key set, or if some record in time names this definition, `bh`, panel `P` and seat `i`, and is either a share receipt, by either path, whose `share_hash` is `b`'s share hash for that seat (`share_hashes[i]` for the default panel, `author_share_hashes[i]` for the author panel) and which passes `share-receipt` against `b`, or a contract-path posting that passes the public check against `b` for that seat.
- **The ballot is delivered** if every seat of both panels is.
- **A complaint about seat `i` of panel `P` is proven** as in version 1, against a passing contract-path posting for `b`, panel `P` and seat `i`.
- **Batches and roots** are read as version 1 reads them (Delivery check), each pair of a contract-path version-2 share-receipt batch and each leaf of an available, consistent version-2 receipt root as the version-2 share receipt it states, and each entry of a version-2 complaint batch and each leaf of a version-2 complaint root as the version-2 complaint it states, for the record's panel and seat, against that panel's share hashes and key set. A root's own codes are version 1's, in the same order: `delivery-seat` for a seat outside the panel key set of the panel it names, `root-signature` under that seat's key in it, `root-repeat` per panel, seat and kind, and `root-withheld` from its own panel's attestations (Leaf availability (version 2)).
- **The ballot is excluded** if any complaint about any seat of either panel is proven, attributed or not.

The report codes are version 1's, each reported with the record's panel and seat: `delivery-seat` for a seat outside the panel key set of the panel it names, and `receipt-contradicted` for a passing receipt of a seat whose complaint, about the same ballot and in the same panel, is proven, a batch's pair or a root's leaf with its `pair` or `leaf` index as in version 1. A record for one panel never delivers, excludes or contradicts a seat of the other.

## Residuals

- **Until the contract path exists, nothing can post and the operator can withhold receipts and complaints** (Direct submit, P1-18), for ballots cast through our API as well as direct-submitted ones: a seat that isn't receipted can't be delivered at all, a ballot whose receipts the operator refuses is silently left undelivered, and a complaint it refuses keeps an invalid ballot counted, so the complaining trustee's summed shares fail and the tally needs `k` other trustees (T-25, T-54). Nothing on the board attributes either.
- **A posting is the voter's chosen loss of everlasting privacy for that seat.** A posted share is protected only by the discrete logarithm in ristretto255, so a future adversary who breaks it reads the share, and a ballot with `k` or more seats posted whole ([[tally]], Residuals). The client posts only a seat that isn't receipted, only at the voter's explicit choice after saying so (Client rules); the owner accepted this as an extension of [[0002-everlasting-privacy]]'s fallback on 2026-10-12 (T-15).
- **A seat's `m_i` stays on the device until the voter decides.** For a seat that isn't receipted, the client keeps `ct_i` and `m_i` after cast, up to the delivery deadline, though never `e_i` or `w_i` (Client rules). That proves nothing about the vote to a coercer, but a device thief in that window could post the seat against the voter's wishes, dropping it to classical privacy (T-18, T-45, T-15).
- **The forced path caps an election's electorate.** A node owes at most two receipts and two complaints per (`tier`, `ν`) (What a node owes) and serves only elections whose obligation fits the forced path at the portal's target (Capacity), which closes the unbounded obligation [[0002-everlasting-privacy]] (Decision, 2026-10-12) accepted until [[P1-12c]]. With receipts and complaints batched ([[P1-12d]], [[P1-12e]]), at about 4,100 gas a receipt and 8,900 a complaint, the forced path carries an election of at most 20,992 members with 3 seats and `R` of one hour, or 188,928 with `R` of 9 hours, the most the windows allow ([[availability]], Windows), so honest seats refuse larger elections, which with more than one honest seat refusing can't be registered: a liveness cap, never a silent drop. A national electorate needs more than any record per receipt on L1: an election above the cap commits roots ([[0031-national-delivery-obligation]], accepted by the owner), one signed root per seat and kind whose leaves are available only through [[0029-board-data-availability]]'s counted-extent attestation. The root's call is built and the code that reads roots is in part ([[P1-12f]]), but not that attestation's contract path and check ([[availability]]; [[P4-3]] part 2c), so until all are, nodes refuse every election that would commit roots (Capacity) and the cap stands. The trustee node runs the check (stub check 4) for the definitions it reads, version 1 so far; a release that reads later versions MUST count their seats and members the same way, an author panel's seats included. The target is shared with every other depositor, voters' forced ballots and postings included, and with anyone who pays the rising price to fill it, and Base's multisig can lower it without delay; the check reserves nothing for them, so a seat that must force everything competes for the portal on price. A node counts only the elections its own seat approved, so elections of panels that share no seat with it (another pinned panel, or author panels once [[P2-16]] brings them) share the portal unseen, and the target can be oversubscribed by as many times as such panels have elections whose intervals overlap. A full batch call takes 22.5% of an L1 block's deposit limit, so a depositor who puts more than 15,500,000 gas in the same block keeps it out of that block; a node under contention sends smaller batches, at slightly more gas per receipt, which the figures' margin covers only in part. Its close statements (at most two per election, about 128,000 gas each with `P256VERIFY`, [[close]]), its availability records (at most four per election, [[availability]]) and the complaints it SHOULD make outside its scope aren't counted either: the statements and records are a few hundred thousand gas each against hundreds of millions an interval carries (T-25, T-52, T-54, T-71).
- **A root's leaves rest on the availability committee.** In an election that commits roots, a seat's receipts and complaints reach L1 only as one root, and its leaves count only if the default panel's threshold names the root in its counted-extent attestations (Leaf availability). A seat that withholds its leaves drops every ballot whose only delivery to it was a leaf, before any result, named by `root-withheld`; and `k` seats that refuse to name an honest seat's root drop the same ballots, on the refusing seats' signed word, a coalition that can already open ballots ([[0029-board-data-availability]], Recommendation). Under batches an honest seat's receipts are L2 data and no coalition can do this, so roots add it. Combined with an operator that refuses the chosen ballots' board-path receipts, those `k` seats can choose which ballots they drop; the voter's client, which keeps sending its own receipts through every path until one is anchored or recorded by the contract and never stands down on a leaf (Client rules), is what still delivers them. Under the transitional panel every seat is ours ([[0031-national-delivery-obligation]], Consequences), so the availability of every root is the operator's word, as the board's is; an election that commits roots adds nothing a voter can check against us until independent trustees hold seats, which every civic poll requires before it opens (T-25, T-54, T-24).
- **Each panel's threshold can drop an honest root of its own panel.** Under ballot version 4 each panel judges its own seats' roots (Leaf availability (version 2)), so `k_A` author seats that refuse to name an honest author seat's root, or `k` default seats that refuse to name an honest default seat's, drop every ballot whose only delivery to that seat was a leaf, before any result, on the refusing seats' signed word (`root-withheld` names who named it and who attested without). Beside an author panel neither coalition can open ballots, since every ballot opens only with both thresholds, so unlike version 1's `k` (above) it drops ballots it can't read; combined with an operator that refuses the chosen ballots' board-path receipts, it can choose which ballots it drops. The voter's client, which never stands down on a leaf (Client rules), is what still delivers them. The author chose the panel and its threshold, and the default panel, which during launch is the operator alone, can't do it in their place. A root available if either panel's threshold names it would need both coalitions together, at the cost of a new attestation version ([[0037-version-2-root-availability]]). An election whose obligation fits batches commits no root, and none of this applies to it (Capacity; T-25, T-54).
- **Leaves cost every seat and verifier their fetch.** Each seat fetches every other seat's leaf objects before it attests the counted extent, and every verifier fetches every available root's: at most `2M` leaves of 64 bytes and `2M` of 128 per seat: for a national referendum of 150 million members with 7 seats, about 134 GB of receipt leaves, and complaint leaves bounded at twice that, though a seat owes a complaint only about a failing posting, against a board of ballots tens of kilobytes each. A root's own record carries 72 bytes its seat chooses (`root`, `leaves_cid` and `count` within its bound) on L2, at most two per seat and election, and its leaves the pairs' and entries' chosen bytes, as batches do, in the archive only if available (T-17, T-52).
- **A seat's root binds its view at `c_I`.** A root holds exactly what the seat decided it owes (What a node owes), which no verifier can recompute from the board where the operator withheld data, as for batches; a root that leaves out a receipt the seat owed drops that seat for that ballot unless the receipt reached the board some other way, and the client holding the receipt can show it, with the root's signed count and the missing leaf's absence from the available leaf object (T-25).
- **A newest ballot that never reached the board can cost an older one its fallback receipts.** A node's view keeps a ballot it receipted unless it can show it absent, so when a voter's newest ballot reached the trustees but not the board (the client went away mid-cast, or every route refused it), and an operator withholds board data so that no node can show it absent, every node owes only that newest ballot's receipt, and the older ballot the delivery check selects is delivered only if its receipts reached the board some other way: the nodes' board-path copies at intake, or the client, which keeps seeing every ballot's receipts onto the board (Client rules). An operator that refuses those copies and withholds its data can then drop the older ballot unattributed. A newest ballot boarded only after `s_A` doesn't do this: the node judges each copy by the close rule and shows the ballot absent from the timely checkpoints (What a node owes). It needs the voter's newest ballot to be missing from the counted board, and it costs the voter a ballot they had already replaced. It is a trade: before P1-12c a node owed the older ballot's receipt too, at the price of the unbounded obligation the owner accepted only until P1-12c ([[0002-everlasting-privacy]], Decision), which rejected permanent operator drops of chosen ballots. So it MUST be closed, by making withheld board data attributable (P4-3; [[availability]], specified, closed once built), or accepted by the owner, before any election registry is deployed, and it is listed in STATUS (Known-weak) for the owner (T-25, T-54).
- **Approved stubs nobody registers hold capacity until they open.** A seat counts every election it approved until finalized L2 shows it can't be registered (Capacity), so whoever can get ceremonies run (the coordinator, which is the operator, and the creators it accepts) can take a seat's capacity for closing times of its choosing without registering anything, until each such stub's `opens_at`, with stubs that open just before they close, and honest seats then refuse real elections closing then: registration censorship, by every seat at once (T-25). The coordinator can already refuse to run any ceremony; what this adds is that creators it accepts can do it too. Bounding it needs an admission rule for stubs, a quota per creator or the brief's moderation, which [[P2-13]] owns; until a node reads registrations from finalized L2 (P2-13 part 3), it releases nothing. It MUST be closed, or accepted by the owner, before any election registry is deployed.
- **Withheld board data can keep a failing posting's ballot out of a node's complaint scope.** The scope comes from the ballots a node holds at `c_I` (What a node owes). A counted ballot whose data the operator withholds from the node, and that this seat never receipted (its voter posted the seat instead), isn't in it, so the node owes no complaint about its posting; a cheating client and that operator can then keep an invalid ballot counted, and this seat's summed shares fail ([[tally]], Summed-share check), so the tally needs `k` other seats, and a ballot posted invalid to every seat can stall it (T-54, T-41). A member who also posts against ballots it made up, newer than the counted one, can steer the scope of a node that can't show them absent, as the newest-ballot residual above steers its receipts. The node still SHOULD complain about failing postings outside its scope whose ballots it can't show absent, as its budget allows, so this needs both withheld data and more postings than the node pays for. It replaces an obligation to complain about every failing posting, which anyone with a member's proof could grow without bound. It MUST be closed by P4-3's data availability ([[availability]]: a seat that attests holding the ballot extent at `c_I` holds every counted ballot that reached the board through the operator, and without a threshold of such seats the election fails `unavailable`; specified, closed once built) or accepted by the owner before any election registry is deployed (T-25, T-54).
- **Refused intake still forces a choice.** A trustee that refuses intake, or an adversary that controls every route to it (the operator's relay and the voter's network), leaves the voter to choose between posting that seat, with its loss of everlasting privacy, and an undelivered ballot. Neither is attributed on the board: a refusal at intake leaves nothing signed (T-25, T-11).
- **A receipted seat can still go undelivered.** A trustee that returns a valid receipt and never sends it, with an operator that refuses the client's copy and every contract-path route the client has refused too (a relay the operator runs or a state actor compels), leaves the ballot undelivered, and the client may not post instead (Client rules). The voter holds the trustee's signed receipt, which shows off the board that the seat receipted, but nothing on the board attributes the drop; the client says so, so the voter can re-vote through another route while the poll is open (T-25, T-41).
- **A cheating client can still exclude its own voter's ballot** by posting an invalid share: a proven complaint excludes it after the close, too late to re-vote ([[0002-everlasting-privacy]], Re-voting; T-41, T-42).
- **A trustee that misses the complaint window** can't complain about an invalid posted share, so its summed shares fail and it can't contribute to the tally ([[0002-everlasting-privacy]], Tally liveness; T-54).
- **A voter can archive chosen bytes in postings**, about `n · (64·m + 36)` per ballot and re-vote, through the contract path, since neither the contract nor the public check opens `sealed` (Direct submit; T-17). Through the contract path anyone can also post, for the price of gas, postings naming a made-up ballot (a committed vote of their choosing), which the delivery check sets aside but the archive keeps, like any contract event's inclusion evidence (T-17).
- **The contract path archives what the board path refuses.** The contract can't check a receipt's ballot hash or a complaint's decryption, so a registered seat can archive, for gas, about 130 to 190 chosen bytes per made-up ballot hash in receipts and complaints, and an unfounded complaint next to a passing posting puts `D` and `m_i` on the permanent archive, opening that share with no cryptanalysis. Both are within what the seat could disclose itself (T-14), and both are attributed to it: the first is set aside, the second reported `complaint-unfounded` (T-17, T-15).
- **Failing postings for real ballots cost verifier work.** Anyone who has seen `ct_i` can send, for gas, any number of contract-path postings with a wrong `m`; each names a selected ballot, so every verifier runs the public check (ML-KEM re-encapsulation and ristretto255 arithmetic) on it, and the archive keeps its 32 chosen bytes. Bounded only by gas; P1-18 may price or cap postings per seat (T-52, T-17).
- **Receipts don't admit ballots.** A receipt says that the trustee's shares pass for this public part and that a record carrying it passed admission at intake ([[share-encryption]], Intake and receipts), but it never stands in for the ballot's own checks: the verifier admits each ballot entry from its own record (5.1 to 5.4) and its L1 reference (5.8), and a receipt adds nothing to them.
