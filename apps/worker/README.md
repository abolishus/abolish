# @abolishus/worker

Background jobs on BullMQ, over Redis in development and CI and Dragonfly in deployment. Internal and source-only; AGPL-3.0-only. Handlers parse, call `@abolishus/core` and log; no protocol logic lives here.

## No joins (T-10)

- **Sides.** Every queue in `src/queues.ts` is a board queue, an account queue or an operational one. A board queue's data names no account, session or person; an account queue's names no ballot, nullifier, poll or election; an operational queue (upkeep such as the identity-backup prune) names neither. No job crosses sides. `tests/no-join.test.ts` checks every queue's fields against both deny-lists, so a renamed field would pass; review of each new queue still has to catch that.
- **Strict data.** Job data is a `z.strictObject`, parsed again by the worker before a handler sees it; data with a field the schema doesn't name, or a job named other than its queue's key, fails as `invalid-job-data` without being handled. Job IDs are BullMQ's counters, or for `{ballot-submit}`, `{receipt-submit}`, `{opening-submit}` and `{destruction-submit}` a random UUID `BallotQueue`, `ReceiptQueue`, `OpeningQueue` or `DestructionQueue` draws, never derived from data.
- **Nothing kept.** A job's data, error and stack trace leave Redis as soon as it finishes (`removeOnComplete` and `removeOnFail` on the worker, so a producer can't opt out by omission). BullMQ also writes every failure's message, and every completed job's return value, to the queue's events stream, which those options don't clear and which keeps each job's ID, name and timestamps (up to about 10,000 events); the only return value is `{ballot-submit}`'s outcome, a board index or a refusal's code, never the ballot, so names are fixed to the queue's key and the worker turns any error into a `JobError` whose message is its fixed kind. Two tests fail if anything reaches a log line or any Redis key, the events stream included: one queues an account field on a board queue, the other makes a handler throw a message that quotes data.
- **Producers.** Four: `BallotQueue`, `ReceiptQueue`, `OpeningQueue` and `DestructionQueue` (`src/ballot-queue.ts`, exported as `@abolishus/worker/ballot-queue` for the API), each of which parses the data, forces `JOB_OPTIONS` and the job name, takes no job ID, deduplication ID or option from its caller, and draws a random job ID itself so it can listen for the outcome before the job is queued. `tests/ballots.test.ts`, `tests/receipts.test.ts`, `tests/openings.test.ts` and `tests/destructions.test.ts` fail if a ballot, a receipt, an opening, a statement or its election stays in any Redis key, the events stream included, once judged.
- **Log.** One line per job: queue, outcome, error kind from a fixed list, duration. Never the data, the job ID or an error message, since messages can quote data. An audit finding adds the election ID and entry index, and an anchoring finding the election ID and segment, all public on the board, and no person's request leads to either.

## Keys (Dragonfly)

Every key is `abolish:{<queue>}:…`. The braces are a hash tag: BullMQ's Lua scripts touch several keys of one queue, which Dragonfly (with `--cluster_mode=emulated --lock_on_hashtags`) and Redis Cluster need in one slot, while separate queues can live on separate threads or shards. A test checks every key the worker creates.

## Tier 0 batch job

`src/tier0-chain.ts` is the batch job's chain adapter (docs/spec/registration.md, The batch): `ViemTier0Chain` reads the group registry from one L2 node at a pinned pair of finalized and latest blocks, and `checkTier0Deployment` refuses to start a job whose chain, registrars, threshold or keys aren't the registry's. Submission is passed in: `src/tier0-bundler.ts`'s `connectTier0Bundler` checks the registration account and paymaster against the configured EntryPoint, registry and owner key, and the bundler against the chain and EntryPoint, then returns the submitter, which sends each record as an ERC-4337 operation from the account, paid by the paymaster (docs/spec/contracts.md, Registration paymaster and Registration account): it builds exactly the call the paymaster sponsors under a nonce key named by the record's group, lowers the fee (estimating again, since an L2 bundler's `preVerificationGas` grows as the fee falls) so the operation's most-it-can-cost stays within the paymaster's cap or sends nothing, signs EntryPoint v0.8's hash with the account's key and requires the bundler to answer that hash. Every failure is a fixed message, never the record or the bundler's error (T-10, T-13). `tests/tier0.test.ts` runs the job against the group registry on Anvil, and `tests/tier0-bundler.test.ts` the submitter against EntryPoint v0.8 itself with the account and paymaster, through a stand-in bundler that lands each operation with `handleOps` (no bundler's ERC-7562 simulation runs; Known-weak in P3-2's status). Both need the toolchain (`.github/scripts/install-toolchain.sh`).

`src/anchor-chain.ts` is the anchoring job's chain adapter (docs/spec/contracts.md, Board anchor): `ViemAnchorChain` reads the board anchor from one L1 node at the block its `now()` pinned, refusing a node behind a block or time already read; it simulates each `anchor` call from the authority before sending it, and fails a call whose sender resolved while the anchor doesn't hold its checkpoints. `checkAnchorDeployment` refuses to start a job whose chain, clock or authority aren't the anchor's finalized ones, or whose authority is a single key. Sending is passed in. `tests/anchor-chain.test.ts` runs core's `anchorBoards` through it against the anchor on Anvil.

`src/anchor-safe.ts` is the authority's side (P4-1 part 2b-2a): `checkAnchorSafe` refuses a Safe that isn't exactly the deployment record's at a given block: its history (`checkAnchorSafeHistory`: a SafeL2 set up in the recorded block with no setup delegatecall, never a delegatecall since and never a module's execution, read `LOG_RANGE` blocks at a time) and, which that history makes sound, its state (`checkAnchorSafeState`: the proxy's and singleton's code hashes, the singleton in the proxy's slot 0, the owners as a set, the threshold, which must be at least 2, no module, no guard and the named fallback handler). `safeSender` is `ViemAnchorChain`'s sender: it signs only `anchor` calls, refuses a node behind a block already read, checks the Safe again at the latest block (remembering the history up to the finalized one), signs the anchor call as a Safe transaction (a `CALL`, no `safeTxGas`, base gas, gas price or refund) with the first `threshold` owners whose signature recovers to their own address, executes it from an executor key after the node's estimate has run it, and requires the receipt's `ExecutionSuccess` for the hash signed. Nothing is sent for a changed Safe, too few honest signatures or an execution that would revert. Owner keys (`keySigner`) and the executor key must be secp256k1 keys, are used only to sign and are never logged or quoted; a failed estimate or send throws fixed text, never the node's error, which would quote the signatures. `tests/anchor-safe.test.ts` runs Safe v1.4.1 (vendored in `packages/contracts`) on Anvil: each change a quorum could make to the Safe is refused, among them a delegatecall that writes a module the getters don't list and that then acts as the Safe, and the anchor holds each checkpoint sent.

## Tier 1 relay

`src/tier1-chain.ts` is the relay job's chain adapter (docs/spec/tier1-relay.md, The batch; P3-3 part 3c-2b-2b): `ViemTier1Chain` reads the group registry's logs from one L2 node as contract-event records, numbered by the registry's own count and replayed from the accumulator at the block the last read ended at to the accumulator the registry holds at the block read to, so a node that drops, adds, alters, reorders or re-times a log is refused (T-53, T-71). It signs `addTier1Member(record)` itself with the relay account's key, at the nonce core gives, with gas limit `TIER1_RELAY_GAS_LIMIT` and the node's EIP-1559 fees; a replacement raises both fees by an eighth over the transaction it replaces, and no fee is ever signed above `TIER1_MAX_FEE_PER_GAS`, so a node's fee answer can't spend more than the cap (T-52). A broadcast the node answers with an error is refused (one it already holds is sent), and a simulation it answers with an error is a revert; a node that can't be reached throws. Every failure is `Tier1ChainError`, naming a step only: viem's errors quote the URL and the request, which can carry a record or a signed transaction (T-10, T-13). `checkTier1Deployment` refuses to start a relay whose chain, registrars, threshold or deployment block aren't the registry's (as Tier 0's check) or whose published group isn't a final Tier 1 group. `tests/tier1.test.ts` runs the adapter and the scheduled jobs against the registry on Anvil with a fresh funded key; nothing can count there (no Tier 2 group exists on it), so sending is checked against a stand-in registry, and what counts is core's `tests/tier1-batch.test.ts`'s. It needs the toolchain.

## Posting relay

`src/posting-chain.ts` is the posting relay's chain adapter (docs/spec/posting-relay.md, Sending, In flight and Pruning; ADR 0042; P2-8 part 2b-2b-2b-2b-1): `ViemPostingChain` is both core's `PostingChain` for the posting worker and its `PostingKeyChain` for the ledger, over one L2 node with the posting key. It simulates `submitPosting(posting, ballot)` from the key within `POSTING_GAS_LIMIT_MAX` (a revert is a revert; a call past the cap reads as more gas than it, which the worker refuses `too-costly`), signs it at the nonce and gas limit core gives with fees never above core's fee cap (T-52), broadcasts it, prices its L1 data from the OP Stack fee oracle, and reads receipts as the node sends them, `l1Fee` included. A posting is found on the board only as a `SharePosted` log of the board with the posting's own topics and exactly its bytes, at the latest or the finalized head; each posting's search is kept up to the finalized block it reached, starting `POSTING_LOOKBACK` blocks behind the head it was first asked at, and a node whose logs stray from the filter is refused (T-25). Every failure is `PostingChainError`, naming a step only, since viem's errors quote the URL and the request, which can carry `m_i` or a signed transaction (T-10, T-18). `checkPostingDeployment` is the worker's startup check: the node is on the configured chain, the finalized head is at or past the board's deployment block, the address is a board whose election registry names it back at the finalized block, and the posting key's account holds no code (an EIP-7702 delegation would let other code spend from it; T-50, T-52); it returns the registry and the L1 chain and relay it names. The adapter also reads the L2's safe head for the forced path (`includedSafe`, `postedSafe`; T-50) and, given `ViemPostingL1` as its `deposits`, counts a deposit's reserve in each first send's costs.

`src/posting-l1.ts` is the forced path's L1 side (docs/spec/posting-relay.md, Forced through L1 and Depositing; P2-8 part 2b-2b-2b-2b-3b-2): `ViemPostingL1` estimates `depositTransaction(board, 0, g, false, calldata)` on the portal from the posting key, prices its reserve, signs deposits within the L1 fee cap and cancellations (0-wei transfers to the key itself) within twice it, broadcasts them and reads L1 receipts and heads; `postingDepositChain` joins it with the L2 adapter's safe-head reads into core's `PostingDepositChain`. `checkPostingL1` is the forced path's startup check and gives the portal: the L1 node is on the chain the registry names, the registry's L1 relay names the board, the portal it names holds code, and the key's L1 account holds none, since a contract's deposit is aliased on L2. `ViemPostingRegistry` reads the election registry's `DefinitionRegistered` events from finalized L2 blocks, kept in memory so each ask reads only the blocks since, for core's `PostgresPostingElections` to check the index's progress against (T-54).

`src/posting-runner.ts` is the worker's loop (P2-8 part 2b-2b-2b-2b-2): every `POSTING_TICK_MS` (2 s) core's `PostingWorker.tick`, then `PostgresPostingLedger.tend` with the latest block, every `POSTING_DEPOSIT_EVERY_MS` (an L1 slot) `PostgresPostingDeposits.tend` with the L1's latest and finalized blocks, and every `POSTING_PRUNE_EVERY_MS` (a minute) `prune` with the L2's finalized one, one round at a time, the next timed from the end of the last. It isn't BullMQ: a scheduled job's ID and times stay in its events stream, and the queue is drained in place (docs/spec/posting-relay.md, Queue; T-11, T-13). Each step's failure is its own, and the log holds counts and steps only: a round's counts when something moved, and a step's `failing` and `recovered` as it starts failing and recovers, never its error (T-10, T-18). `src/posting-main.ts` (`posting.mjs`) composes them for the deployment of its own (Running, below).

`tests/posting-chain.test.ts` runs the adapter, the startup check and the composed worker (the queue, the ledger, the deposits and the loop against Postgres and Redis) against stand-in contracts on Anvil with a fresh funded key, and needs the toolchain; `tests/posting-l1.test.ts` runs the L1 side, the registry's events and a posting the L2 keeps out forced through L1 end to end, on two Anvils; `tests/posting-runner.test.ts` runs the loop over fakes.

## Creation step

`src/poll-create-chain.ts` is the creation step's chain adapter (ADR 0032; P2-22 part 3a): `ViemPollCreationChain` signs `createElection()` with the creation key (the node's gas estimate with 20% headroom, a fee cap of three latest base fees plus the tip), sends the signed bytes to one L2 node, treating a node that already holds them as a send that took, reports a transaction the node holds without a receipt as included rather than unknown, and reads a creation only from finalized history: the receipt must be the key's own call to the configured registry, in the node's block at that height, with one `ElectionCreated` naming the key and the identifier the registry's counter gives (`@abolishus/crypto`'s `electionId`), or the node is refused rather than read. `checkPollCreationDeployment` refuses to start on another chain, or at an address that isn't an election registry numbering its elections for that chain and address. `tests/poll-create-chain.test.ts` runs core's step through the adapter against the registry on Anvil with a fresh funded key, and needs the toolchain.

### The creation key's commands

`src/creation-key-cli.ts` (`vp run --filter @abolishus/worker creation-key status`, or `… creation-key sweep <funding address>`) is what the poll-creation runbook's Funding, Rotation and Compromise sections run in the `worker-create` service, with its variables (P2-22 part 3b-3; T-72). Each starts with `checkPollCreationDeployment`, also needs `DATABASE_URL` for the creation step's ledger, and prints one JSON object; neither the key, the node's URL nor a malformed argument is ever printed. `status` reads only: the key's address, balance, nonce counts and one creation's cost at the latest fees (with the L1 and operator fees from the OP Stack's `GasPriceOracle`), whether the balance is below a day's ceiling of creations, the ledger's counts (recorded, not yet included, not yet final, the last 24 hours), `unrecorded` (included nonces with no ledger row: transactions the worker didn't send, the runbook's sign of compromise, which a sweep also shows as one), and the polls the key still has to finish (`submitted` with its creation, `created`, `rooted`, `ceremony`; core's `creationKeyRecords`). `sweep` refuses while the node holds a pending transaction of the key or the ledger a creation at a nonce the node hasn't included (the sweep would take its nonce and fail its poll as `creation-replaced`), then sends the balance at the latest block, less the transfer's gas at the fee cap and twice the oracle's L1 and operator fees, to the funding address (a full address, checksummed if mixed-case, never the key or zero), and waits up to five minutes for its receipt, saying so if the transaction is still pending. `tests/creation-key.test.ts` runs both on Anvil with the election registry and a stand-in oracle, and needs the toolchain.

## Running

`vp run --filter @abolishus/worker start` (plain Node, as `apps/api`; `erasableSyntaxOnly` keeps it that way), or in the image (`Dockerfile`: the bundle `vp pack` builds into `dist/`, `main.mjs` and `creation-key.mjs`, with every dependency inlined) `node main.mjs`, with `DATABASE_URL` (a user granted `abolish_app`, never the owner), `REDIS_URL` and optionally `AUDIT_EVERY_MS` (at least 60000).

Ballot admission (`{ballot-submit}`) runs only with all three of `BALLOT_PINNED_PANELS` (the trustee panels the release pins, as JSON: `[{"threshold": k, "keys": ["<hex>", …]}]`, each key a seat's identity key in seat order), `BALLOT_ANCHOR_EPOCH` and `BALLOT_ANCHOR_PERIOD` (the anchoring clock of the anchor contract our definitions name, docs/spec/board.md, Timing); the worker refuses to start with only some. They were the API's `API_PINNED_PANELS`, `API_ANCHOR_EPOCH` and `API_ANCHOR_PERIOD` before admission moved here. With them, `BALLOT_L1_RPC_URL` (an L1 node, `https:` or `http:`) and `BALLOT_L1_CHAIN_ID` (the `l1_chain_id` our definitions name), both or neither, turn on the L1 reference check (verifier 5.8): the worker refuses to start if the node is on another chain, then refuses a ballot whose reference the finalized chain already rejects (`l1-ref-before-open`, `l1-ref-after-close`, `l1-ref-unknown`), boards one naming a block L1 hasn't finalized yet, and boards one unchecked, with an `l1-unchecked` log line naming neither ballot nor election, when the node can't be read within 2 s or the definition names another chain.

Tally openings (`{opening-submit}`) are boarded only with all of those and `BALLOT_ANCHOR_ADDRESS` (the anchor contract our definitions name as `l1_anchor`) and `BALLOT_ANCHOR_DEADLINE` (the anchoring deadline it fixes), both or neither: the worker refuses to start unless the L1 node is on `BALLOT_L1_CHAIN_ID` and the anchor's finalized code fixes exactly `BALLOT_ANCHOR_EPOCH`, `BALLOT_ANCHOR_PERIOD` and the deadline (`checkAnchorClock`). It then reads the anchor without sending (`ViemAnchorReader`) and finalized L1 headers (`RpcL1HeaderRun`, apps/node's `headerRun`, at most `MAX_RUN_BYTES` of headers per run) from that node, for core's `anchoredCountedTally`: an election's counted tally is decided once `t_S` has passed by the anchor's time and the anchor holds the counted checkpoint, kept for good once decided, asked again after a minute while waiting and after ten minutes when the anchor didn't hold the checkpoint. An opening is first checked against its election's target (`openingTargets`: decoding under the stored definition's pin, naming its definition, and the registered key set from its transcript), an opening already boarded in the same bytes is answered from the board, only one a registered seat signed starts a computation, a computation that throws is tried again only after a minute, and an opening of another election while one is computed is answered `not-ready` (T-52).

Destruction statements (`{destruction-submit}`) are boarded whenever ballot admission is configured, by its pinned panels and clock, and need nothing more: the Boarding rule reads only the stored definition, the transcript it names and the statements already boarded, never the anchor or L1, since timing is the verifier's to report (8.5). Each election's target is read once and kept, for 4,096 elections.

The archive (`{archive}`, P4-3 part 4b-2b-2b-1) runs only when every one of these is set, and only beside the anchoring runner, whose anchor every manifest names and whose calls carry the locator; the worker refuses to start with some of them, or without the runner (`src/archive-env.ts`). It posts through one Arweave node with `HttpArweaveClient` (`src/arweave-client.ts`). The wallet can only add data under its own address, which no reader trusts, so seizing it costs what it holds (docs/adr/0005-permanent-archive.md, Keys; T-52): fund it only with what a period's uploads need. Funding it on Arweave's mainnet spends real money, so it waits for the owner (ADR 0005, Default).

| Variable              | Value                                                                                                                                             |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ARCHIVE_ARWEAVE_URL` | The Arweave node (HTTP), taken as the verifier takes a gateway: no credentials, query or fragment. A provider's key may be in its path.           |
| `ARCHIVE_WALLET`      | Secret: the wallet's JWK, as Arweave's wallets export it: a 4096-bit RSA private key with exponent 65537. Removed from the environment once read. |
| `ARCHIVE_MAX_REWARD`  | The most winston one upload's reward may be: a higher quote is refused before anything is signed, since the node quotes the price (T-52).         |

`ARCHIVE_EVERY_MS` (optional, only with them) sets the schedule: 600,000 (ten minutes) by default, at least 60,000. Neither the URL nor the wallet is ever quoted in an error. An object counts as archived only once a node serves data for its upload that reads as its CID, 25 blocks deep (core's `ARCHIVE_DEPTH`), and an upload in no block is posted again after two hours (`ARCHIVE_REPOST_AFTER`). After a wipe of Postgres a run that finds the anchor naming a chain reads it back from Arweave before anything else (P4-3 part 4b-2b-2b-2): every manifest from 0 to the named one, through the links, each from a transaction 25 blocks deep whose data reads as its CID, with the transactions its objects are listed under, so nothing listed is posted again and the chain carries on from the anchor's sequence. Until the whole chain reads, nothing is written or posted, the run logs `archive-resume` with why (`locator`, `foreign`, `malformed`, `conflict` or `unavailable`) and fails with `archive-findings`, and the next run tries again; the line of counts then carries `resumed`. Let any anchoring call in flight land before a wipe: the run resumes from the locator the anchor holds, and one landing after that names a manifest the new chain writes over.

One image serves every deployment, told apart by their variables only (and the posting worker by its entry point): the creation worker gets the creation step's and nothing else, the setup worker every other job's but the anchoring runner's, which refuses to share a process with Tier 0's or Tier 1's keys (`docs/runbooks/railway.md`, Services).

The creation step (`{poll-create}`) runs only when every one of `CREATE_L2_RPC_URL` (the L2 node, HTTP), `CREATE_CHAIN_ID`, `CREATE_REGISTRY` (the election registry our definitions name), `CREATE_KEY` (secret: the creation key, 64 hex digits, `0x` optional), `CREATE_L1_RPC_URL`, `CREATE_L1_CHAIN_ID`, `CREATE_ANCHOR` and `CREATE_PANEL_THRESHOLD` and `CREATE_PANEL_KEYS` (the default panel, as `POLL_STUB_PANEL_*` give it) is set, with `CREATE_DAILY_CEILING` optional (creations sent in any 24 hours, 200 by default); the worker refuses to start with some of them, with the ceiling alone, or with any ballot, Tier 0, Tier 1, registry-sync or anchoring variable beside them, since the key runs alone (ADR 0032, rule 2; `docs/runbooks/poll-creation.md`). At startup (`checkPollCreationDeployment`) the registry's trustee registry must pin the panel at its threshold and rule 7's quorum `max(k, n − 1)`, and is the one ceremonies are registered with. Neither the key nor the URL is ever quoted in an error.

The roots step (`{poll-root}`) runs only when every one of `POLL_ROOT_GROUPS` (the deployment record's published groups, `<tier>:<group_id>` pairs separated by commas, each group once, each in region 0 until the registry records regions), `POLL_ROOT_REGISTRARS` (the group registry's registrars in seat order, comma-separated) and `POLL_ROOT_THRESHOLD` is set, and only beside the registry sync's variables, whose index, nodes, group registry and event version it reads with; the worker refuses to start with some of them or without the sync. All three are public.

The stub step (`{poll-stub}`) runs only when every one of `POLL_STUB_PANEL_THRESHOLD` and `POLL_STUB_PANEL_KEYS` (the default panel the trustee registry pins: its threshold and the seats' compressed P-256 keys in seat order, hex, comma-separated), `POLL_STUB_RECEIPT_KEYS` (the board operator's receipt keys, the same form, in ascending byte order), `POLL_STUB_INCLUSION_BOUND` (the release's `δ`, seconds), `POLL_STUB_SEQUENCING_WINDOW` and `POLL_STUB_MAX_SEQUENCER_DRIFT` (the L2's, seconds) is set, and only beside the registry sync's variables, whose chain and contracts every stub pins. At startup (`pollStubDeployment`) the election registry at `REGISTRY_SYNC_ELECTION_REGISTRY` must hold the sync's board, trustee and group registries and L1 chain, and its own `l1Anchor` and `l1Relay` are the stubs'; the trustee registry must pin the panel at its threshold; `REGISTRY_SYNC_EVENT_VERSION` must be the contract-event version stubs pin (8); and core's `pollStubDeploymentRule` must accept the whole; and the anchor the registry names must hold a board anchor on `REGISTRY_SYNC_L1_CHAIN_ID` in finalized state, whose epoch and period the opening step (`{poll-open}`) boards transcripts by. Otherwise the worker refuses to start, naming the mismatch. All six are public. The creation step's startup check, in turn, requires the registry to name `CREATE_L1_CHAIN_ID` and `CREATE_ANCHOR`, so the per-slot check reads the anchor every stub pins.

## Tests

`vp run --filter @abolishus/worker test` needs `TEST_DATABASE_URL` and `REDIS_URL`, and runs uncached. Each run uses its own key prefix and removes its keys afterwards. `tests/image.test.ts` packs the bundle outside the repository and runs it with plain Node: it refuses to start without its database and Redis, refuses the creation key beside another job's variable and the posting worker's variables in `main.mjs`, and `posting.mjs` refuses to start without its variables, beside another job's or with an unreachable node, without quoting a key or a URL.

## Decisions

- **ioredis as BullMQ's client.** BullMQ 6 takes ioredis or node-redis; ioredis is the one BullMQ's own tests pin and the one its Dragonfly guidance uses.
- **`msgpackr-extract` isn't installed** (`ignoredOptionalDependencies`). msgpackr, which BullMQ uses, loads this optional prebuilt native binary whenever it is present, install scripts or not; without it msgpackr uses its pure-JS codec. A test checks it doesn't resolve and that msgpackr's native acceleration is off.
