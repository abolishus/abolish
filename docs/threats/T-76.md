# T-76: Web push services and endpoints

- Area: Ballot secrecy, unlinkability and privacy (G-3, G-4, G-5, G-12)
- Adversary: A-1, A-2, A-5
- Status: **Planned.** Built by [[P2-27]] part 4 (4a, subscriptions and sending in `packages/core`, done; the website's routes, service worker and account page next). Residual: each push service learns that a browser it serves uses Abolish, and when an account it serves was moderated, to the day.

## Threat

Web push ([[P2-27]], Notifications) has a browser subscribe with its vendor's push service and hand us the endpoint, a URL our server then calls to wake it. So:

- **Server-side request forgery.** The endpoint is whatever the page sends. An account (A-5) or a script on a compromised page could hand us any URL: our cloud provider's metadata service, an internal host, or a third party to flood, and our server would call it with our credentials' signature attached.
- **The push service learns about the account.** Google (Chrome and other Chromium browsers), Mozilla (Firefox), Apple (Safari) and Microsoft (Edge) each tie an endpoint to a browser install, often to a signed-in vendor account, so whatever we push, and when, they learn about that person. With a payload they would also learn its words, unless it were encrypted; with a send time close to a public moderation decision, they would learn which poll or profile was the account's ([[T-73]]'s same matching).
- **Compulsion and breach.** A state (A-1) can ask a push service which browsers we pushed to and when; an insider (A-2) with the database reads which endpoints belong to which account.
- **Fan-out.** One notice pushed to many endpoints, or many notices, makes our server a source of traffic toward the push services (T-52).

## Mitigation

- **Only the push services' own hosts.** `parsePushEndpoint` takes an https URL in the URL parser's canonical form, at most 1024 characters, on `fcm.googleapis.com`, `updates.push.services.mozilla.com`, `web.push.apple.com` or a host under `notify.windows.com`, with no port, user or fragment; anything else is refused before it is stored, the sender checks again before every request and follows no redirect, and the table refuses an endpoint that isn't https or is too long. Our server calls no host but these.
- **No payload.** A push is an empty message that wakes our service worker, which shows a fixed notice of its own; there is nothing to encrypt (RFC 8291 isn't needed), so the browser's `p256dh` and `auth` keys are never asked for or kept, and the push service never sees words. The request carries the VAPID token (our public key, the service's origin, a 12-hour expiry and our contact `subject`), a week's TTL, normal urgency and a fixed topic; never an account, a poll or what was decided.
- **Sent when the e-mail is.** A push goes with a notice's first try, after the UTC midnight following the decision ([[T-73]], [[0038-verified-accounts]], Amendment (P2-27 part 3a)), so its time narrows nothing past the day. It is pushed once per notice: a refused e-mail's later tries don't push again.
- **Opt-in, bounded and forgettable.** A browser is subscribed only when its user asks on the account page; an account keeps its newest 5; a push service's 404 or 410 deletes the subscription; the rows are account class (T-10), deleted with the account and lost in a wipe, and the endpoint is not in the account's export, since it is a standing way to wake that browser.
- **Only moderation pushes.** Only a moderator's decision queues a notice, at most one a day per account, so no one outside can make us push (T-52).

Not mitigated: the push service's own records of which browsers we woke and when; whatever a vendor learns by tying an install to its own account; an insider reading which endpoints belong to which account. The VAPID secret key lives in the website's environment, so a compromise of it lets an attacker wake our subscribers' browsers, though only to show our own fixed notice, since our service worker shows nothing else.
