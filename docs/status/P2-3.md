## Scope

`apps/api` (Hono + oRPC): board read, ballot submit, election definitions.

Must include the T-10 no-join test for this app: no request log line, metric label or cache key carries both an account or session identifier and a ballot, nullifier or poll-participation value.

## Plan

1. **Read side and request log** (this part): every procedure of the contract, with `ballots.submit` failing closed; election definitions stored in core; the T-10 request-log test.
2. **Ballot admission**: `ballots.submit` decodes the record strictly and runs the admission checks (verifier 5.1 to 5.5, 5.7, 5.8) before `appendEntry`, with the segment taken from the anchoring clock. Needs P1-17b (membership proof verification) and the ballot record's decoder; until then the server boards nothing, and nothing is lost: a voter can submit directly once P1-18's direct submit exists (T-25).

## Built (part 1)

- `packages/core`:
  - migration `0001_election_definitions.sql`: one write-once row per election (`SELECT`, `INSERT` for `abolish_app`; triggers reject every change for every role);
  - `storeDefinition` (strict decoding and well-formedness through `@abolishus/crypto`, idempotent, `conflict` on different bytes) `readDefinition` and `hasDefinition` (an existence check that doesn't read the bytes);
  - `readHead`, `readEntries` (count and byte bounded, lengths read before payloads), `readInclusionProof` and `readConsistencyProof`, all over `@abolishus/crypto`'s `BOARD_TREE`;
  - `@abolishus/core/test-db`, the per-file test schema helper, for other packages.
- `apps/api` (new, private, AGPL-3.0-only): the contract's router and a `node:http` server with oRPC's OpenAPI handler. JSON bodies only, bounded and cut off at `MAX_REQUEST_BODY`; a GET with a body is refused; board procedures answer only for elections with a stored definition; `ballots.submit` answers `ELECTION_NOT_OPEN`.
- Transport limits: a POST with a query string is refused; at most 32 requests in flight, the rest get 503 before anything is read; idle connections are destroyed after 15 s, a request must arrive within 30 s and none holds a slot past 60 s, so stalled or slow clients can't hold the slots; an oversize body is cut off without destroying the socket, so the 413 reaches the client.
- `erasableSyntaxOnly` in both packages' `tsconfig.json`: Node runs the app with type stripping only, which rejects parameter properties (core's `AppendError` had one) and enums.
- Request log (T-10, T-11): method, matched contract route, status and duration only; errors by kind only. The handler context is the database alone.
- Decision: no Hono yet (see the app's README). Adding it changes the owner-reviewed catalog, and nothing needs it until accounts (P2-5).
- Threats: T-10, T-11 (no addresses logged), T-23, T-24, T-31, T-34, T-52, T-53.

## Tested

- Core (against Postgres, `FC_NUM_RUNS=1000`): the definitions table's schema, grants and write-once triggers (app and owner); every decoding and well-formedness vector of `election-definition.json` refused, with nothing stored; the published hash; conflicts; byte flips either refused or stored exactly as given. Board reads: heads equal what `checkBoard` and `merkleRoot` recompute; pages concatenate to `readBoard`; the byte budget (examples and a property that each page is within budget and maximal); every inclusion and consistency proof of an 11-entry board verifies with `verifyInclusion` and `verifyConsistency`; `invalid-range` and `beyond-board`, including sizes above Postgres's `bigint`.
- API, over HTTP: every procedure checked with `@abolishus/crypto`; error statuses; a 9 MB board page cut at 8 entries; non-JSON, multipart, oversize and chunked oversize bodies refused; `ballots.submit` boards nothing.
- T-10: requests carrying cookies, bearer tokens, forwarding headers, query values and ballots leave none of them in the log, and every line has exactly the four allowed fields; an internal error's message never reaches the log or the response.
- `src/main.ts` starts under plain Node and answers a request.
- Mutation checks, by hand: logging the raw URL, removing the streaming body bound, boarding on submit, removing the in-flight cap, accepting a POST's query string and reintroducing a parameter property each fail a test.

## Independent review

A fresh in-session subagent reviewed the diff against `.github/review/crypto-review.md`, the crypto-review and migrations skills, and ran the tests and a live server. Nothing blocking. Its findings:

- **Fixed:** `src/main.ts` crashed under plain Node on parameter properties, in the app and in core (now `erasableSyntaxOnly` plus a startup test); the existence check read the whole definition (now `hasDefinition`); a POST's query string was ignored rather than refused; 500s from output validation weren't logged; an oversize streamed body could reset the connection before the 413 arrived; per-request memory was unbounded across concurrent requests (now an in-flight cap); the empty-board head is now stated in the contract; the unused `definition_hash` column is dropped; storing a definition now says it must come from a finalized L2 block.
- **Known-weak, below:** O(n) heads and proofs; the API's role can insert; duplicate JSON keys.
- **Second pass**, over the fixes: one blocking finding, fixed. The in-flight cap let a few idle connections (a stalled upload, an unread answer) hold every slot, with Node's default timeouts never freeing them; now idle connections are destroyed after 15 s and requests must arrive within 30 s, tested for both kinds of stall. Its nits: `retry-after` on 503 and the startup test waiting for its child, done; a test that a 500-class `ORPCError` is logged, not added (the router has no seam to make an answer fail its output schema without test-only code).
- **Third pass**, over the timeout fix: nothing blocking. Its slow-reader finding (a client trickling reads, never idle) is fixed with a 60 s deadline per slot, tested; the 500-class log test stays as above.
- Not changed: `@abolishus/core/test-db` stays an export of the source-only, private package, for other packages' database tests. The migrations skill's rebuild-job rule has nothing to update until P3-5 builds the job; the definitions table is rebuilt from `DefinitionRegistered` events there.

## Known-weak

- **No ballots are taken yet** (part 2).
- **Heads and proofs read every entry hash** of the tree they cover, O(n) per request, with no cache, and `count(*)` scans the board's index. The in-flight cap bounds memory, not CPU. Fine for the reference election; a stored size and tree frontier per election must come before part 2 boards ballots (T-52).
- **The API connects as `abolish_app`, which may insert** board entries and definitions, though part 1 never writes. A compromised API could store a wrong definition for an election not yet stored, permanently (clients still catch it against the registry hash). A read-only role for the API's reads comes with part 2, which needs to write only through `appendEntry`.
- **A few connections can still take every in-flight slot** for up to the 60 s deadline at a time, and reconnect; per-address connection limits belong to the proxy (P2-11, T-52).
- **Duplicate JSON keys** in a POST body are accepted, last one wins (`JSON.parse`). Harmless while `submit` boards nothing; part 2 must refuse them before admission (T-31).
- **No rate limiting** (`RATE_LIMITED` is never returned) and no CORS, which the ballot client will need from its own origin (P2-8).
- **The proxy's own access log** is outside this test; P2-11 must configure it (T-11).
- Stored entry hashes are served as stored; a client that checks what it is served catches a column that disagrees with the bytes.
