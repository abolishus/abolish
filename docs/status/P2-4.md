# P2-4: `apps/worker`

- State: in progress (part 1, worker scaffold, hashtagged queues and the T-10 no-join test, merged in #64; part 2a, batched membership proofs in ballot admission (`finishBallotSteps` in `packages/crypto`, `admitAll` in `packages/verifier`), merged in #322; part 2b, the worker's admission queue, merged in #335; part 3, IPFS pinning and tally coordination, with P4-3 and P1-15)
- Branch: `claude/p2-4`
- Phase: Phase 2: Open polls end to end at Tier 0

## Scope

`apps/worker` (BullMQ, hashtagged queues): proof batch verification, IPFS pinning, tally coordination.

Must include the T-10 no-join test for this app: no queue job payload, job ID or worker log line carries both an account or session identifier and a ballot, nullifier or poll-participation value.

## Plan

1. **Worker scaffold** (this part): `apps/worker` on BullMQ with ioredis, one hash tag per queue, the T-10 no-join tests for job data, Redis and the worker's log, and a first job: the scheduled board audit (`auditBoard` and `listBoards` in core; T-23, T-66).
2. Proof batch verification, with ballot admission (P2-3 part 2) and the membership verifier (P1-17b), in two parts:
   - **2a, batched admission** (this part): each ballot's admission checks stopped at its membership proof, many ballots' proofs verified together, every verdict the one checking the ballot alone gives ([[ballot-validity]], Batched admission).
   - **2b, the worker's admission queue** (this part): the API hands each submission to a hashtagged BullMQ queue and answers once its job completes; the worker takes the jobs waiting together, admits them with `admitAll` and boards the admitted ones in order, so the API process no longer verifies proofs (T-52). The job carries the election and the ballot only (T-10).
3. IPFS pinning, with the archive (P4-3); tally coordination, with the tally (P1-15).

## Part 2a

- Built: `packages/crypto` `stepBallot`, `stepBallotV2`, `stepBallotV3` and `stepBallotV4` (each version's admission checks up to the membership proof, as opaque steps only this module makes) with `finishBallotStep` and `finishBallotSteps` (many steps' proofs by `verifyDecodedMembershipProofs`, then each passing ballot's validity proofs); `checkBallot` to `checkBallotV4` and trustee intake are now the step finished alone, unchanged in result. `packages/verifier` `steppedJudgeFor` (what `judgeFor` now wraps) and `electionAdmission`'s `admitAll`, which `admit` now calls with one payload. [[ballot-validity]] (Batched admission), T-52's history.
- Tested: in each ballot version's vector suite (ballot.json, ballot-v2.json, ballot-v3-records.json, ballot-v4-records.json, from independent implementations with snarkjs's verdicts), every vector batched together, across elections, gets the vector's result and exactly `checkBallot`'s; a property over any multiset of version-1 vectors in any order, past a batch of 64 (runs capped at 3, each up to 80 Groth16 proofs); forged steps, a copied step and a non-array refused. In `packages/verifier`, `admitAll` over each verifier-ballots.json case gives the verifier report's 5.1 to 5.4 verdicts, and over any multiset of a copy's payloads (non-ballots, an empty and a truncated payload among them) exactly `admit`'s; the whole crypto and verifier suites pass unchanged.
- Independent review (`crypto-review` checklist): nothing blocking. Applied: the step's docs say the record must not change before it is finished (the validity proofs are read then); `finishBallotSteps` refuses a hole in its array; a test of a passing batch of 64 and a split failing one; a comment that finishing can't throw on any payload's bytes, so one payload never loses the others' verdicts.
- Known-weak: nothing calls `admitAll` yet, so the API still verifies each submission's proofs alone, on its own process (part 2b). The verifier's own board walk still checks proofs one at a time; batching it is the same change to `ballotChecks`, not planned yet. Batching doesn't bound flooding: a junk ballot that reaches the membership proof costs at most its own batch of 64 the gain (T-52).

## Part 2b

- Built: `packages/core` `BallotAdmissions.submitAll` (many ballots of one election: `admitAll`'s verdicts, then the admitted ones appended in the order given, so each gets what `submit` would give it called in that order; `submit` is now its one-ballot case) and `readBoardedEntry` (the entry at an index and its link, only if it carries the given payload). `apps/worker`: the board-side `{ballot-submit}` queue (data: the election and the ballot, hex, strict), `BallotBatches` (`src/ballots.ts`: the jobs handled at once, up to 64, gathered into one `submitAll` per election, the first waiting 10 ms for others, one batch at a time), its handler returning the outcome (a board index or the refusal's code, `BALLOT_OUTCOME`), and `BallotQueue` (`src/ballot-queue.ts`, exported as `@abolishus/worker/ballot-queue`), the only producer: it parses the data, forces the options and name, draws a random job ID so it hears the outcome however fast it comes, answers `unavailable` after 20 s or while 4,096 wait, and removes a job no worker took. `apps/api`: `ballots.submit` checks the election is held, queues the ballot and answers from the board at the worker's index, only if that entry carries the submitted bytes; a new contract error `BALLOTS_UNAVAILABLE` (503). Configuration moved: the worker's `BALLOT_PINNED_PANELS`, `BALLOT_ANCHOR_EPOCH` and `BALLOT_ANCHOR_PERIOD` replace the API's `API_PINNED_PANELS`, `API_ANCHOR_EPOCH` and `API_ANCHOR_PERIOD`; the API's `REDIS_URL` alone turns ballots on, and Tier 0's three settings now need it. T-52 and T-10 history.
- Tested: core `tests/admission.test.ts`: for the mixed, repeats and admitted cases of `verifier-ballots.json`, one `submitAll` gives each ballot `submit`'s verdict in order, the same board byte for byte, and entries carrying their own ballots; refusals for a whole batch outside the window or for an unknown election; bad inputs; `readBoardedEntry` against another payload, index, election and position past the board. Worker `tests/ballots.test.ts` against live Redis and Postgres: each mixed-case ballot through the queue gets its vector verdict; ballots sent together are judged in fewer `submitAll` calls than ballots (checked by mutation: with the queue's concurrency at 1 it fails) and each outcome names its own entry; the worker's clock decides the window; no ballot or election stays in any Redis key, events stream included, and no log line names one; with no worker pinning panels a ballot times out as `unavailable` and leaves the queue; past the waiting bound a ballot is refused without being queued; a batch whose database is gone fails as `internal` and the API hears `unavailable`. API `tests/submit.test.ts` runs every earlier case through a real worker and queue, plus `BALLOTS_UNAVAILABLE` and a worker naming a wrong or missing index answered 500, never as the entry. The API bundle builds and starts against Redis.
- Known-weak: one worker judges one batch at a time, so junk reaching the membership proof delays honest ballots behind it, up to the API's 20 s timeout (T-52); the route has no rate limit of its own. A ballot answered `unavailable` may still be boarded: the client's retry with the same bytes gets its entry, and nothing tells it otherwise. A stalled batch (one whose verification holds the event loop past BullMQ's 30 s lock) is run again, which boards nothing twice since appends are idempotent for the same bytes. Deploying needs the worker given the `BALLOT_*` settings and the API `REDIS_URL`; until then the API boards no ballot.
