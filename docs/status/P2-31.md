- State: in progress (part 1, [[0038-verified-accounts]] with T-73, merged in #526; part 2a, email verification in `packages/core`, merged in #534; part 2b, the website's routes and the sending adapter, merged in #540; part 3a, phone verification in `packages/core`, merged in #545; part 3b, the Twilio adapter and the website's routes, merged in #548; part 3c, the phone-hash rotation and the [[account-keys]] runbook, merged in #552; part 3d, the e-mail keyrings' rotation, in progress)
- Branch: `claude/p2-31`
- Phase: Phase 2: Open polls end to end at Tier 0

## Scope

The owner's decision of 2026-10-21 ([[PROJECT_BRIEF]], Identity; [[0024-tier0-registration]], Owner decision): every account is verified by email and by phone, one account per phone number, so a second account, and with [[P2-30]] a second Tier 0 identity in a group, costs a second phone number. Accounts today are passkey-only ([[P2-5]]).

## Rules

- **Email** is kept, since notifications and account recovery need it ([[P2-27]]); verified by a one-time code or link; one account per normalised address.
- **The phone number is never kept in the clear.** It is verified by a one-time code sent through an SMS provider, then stored only as a keyed hash (HMAC under a server secret, rotated by re-keying) for the one-account-per-number check, and dropped. Changing it re-verifies; a number freed by account deletion stays held for a cooling-off period, so a number can't be cycled through accounts.
- **Virtual and VoIP numbers are refused** where the provider's line-type lookup says so; the refusal says plainly why.
- **The provider sees each number and when it was verified.** That is a new party that learns who uses Abolish (beside T-11's), and gets a threat entry; nothing about polls, answers or ballots ever reaches it.
- **Nothing joins accounts to ballots** (T-10): the verification tables are account-side, and the no-join tests cover them. Verification happens before the account takes a Tier 0 token ([[P2-30]]), never at the moment of voting, so its timing joins nothing.
- Turnstile stays on sign-up and on sending codes; codes are rate-limited per account, per number and per address.
- The owner signs up for the SMS provider and holds its keys (Twilio Verify recommended: it sends and checks the codes and offers the line-type lookup). Staging uses the provider's test credentials.

## Plan

1. ADR: the provider, the number's keyed hash and its key's rotation, the cooling-off period, the countries served at launch, and the threat entry.
2. Email verification in `packages/core` and `apps/web` (codes, rate limits, the account's state), with the sending service shared with [[P2-27]].
3. Phone verification: the provider's adapter, the keyed hash, one account per number, line-type refusal, cooling-off.
4. The sign-up and account screens: verify email, verify phone, change either; existing accounts verify at their next sign-in.
5. Gate voting: an account takes a Tier 0 token ([[P2-30]]) only once both are verified.

## Built (part 2a)

- `packages/core`: `requestEmailCode`, `verifyEmailCode`, `readAccountEmail` and `pruneAccountEmails` (`src/account-emails.ts`), with migration `0025_account_emails.sql` (`account_emails`, `account_email_codes`, `account_email_sends`, `account_email_recipients`, all in the account class) and server keyrings (`src/keyring.ts`, `id:hex,…`, last key current).
- The address kept only as AES-256-GCM ciphertext bound to its account and an HMAC of its folded form (local part lowercased, domain in ASCII); lookups match under every hash key, so rotation (part 3's job) never frees an address.
- Codes of 8 digits, single use, 15 minutes, 5 tries, kept as a hash bound to the account. A request for another account's address sends that address a notice instead of a code and answers the requester the same way (T-11). Two accounts verifying one address are serialised on it; the first keeps it.
- Turnstile `email-code` on every request, after the cheaper checks; 5 sends an hour and 10 a day per account; 5 messages a day per address whoever asks, past which nothing is sent and the requester can't tell. Recorded in [[0038-verified-accounts]]'s Amendment: the counts are Postgres rows rather than Redis counters, the per-address cap, IDN folding, and the two-deploy rollout of a new key (the keyring marks the current key with `*`).
- `EmailSender` is the interface the provider adapter (part 2b) and notifications ([[P2-27]]) implement; `renderEmail` gives them a plain-text message with no link or image (T-67).
- Tested: the Drizzle view against the migration, the grants, no address in any stored row, the address parser (examples and properties), limits and their race, expiry, tries, single use, the code and box bound to their account, change of address, deletion, a held address answered like any other, the per-address cap, the verify race (also between instances while a new key is staged), an address held under an older key, a sender that throws, a code whose key is gone (fails without spending a try), and keyring parsing.

## Built (part 2b)

- Tested: the routes end to end through the front with the real core as `abolish_app` (the whole flow, a held address and a capped one answered like any other, an outage answered like a send and logged by kind, an answer that doesn't wait for the provider, refusals, session, origin, media type and routes, 503 without the service, nothing of the address or code in the log); the adapter against a stand-in Postmark (the exact fields, every failure shape, recipients that aren't one bare address, bad options); the prune against Postgres; and the built bundle starting with the configuration and refusing part of it or a malformed one without quoting it.

## Built (part 3a)

- `packages/core`: `requestPhoneCode`, `verifyPhoneCode`, `readAccountPhone` and `pruneAccountPhones` (`src/account-phones.ts`), with migration `0026_account_phones.sql` (`account_phones`, `account_phone_holds`, `account_phone_codes`, `account_phone_sends`, `account_phone_recipients`, all in the account class) and `PhoneVerifier`, the interface the Twilio adapter (part 3b) implements: `lookup`, `start` and `check`.
- The number is never stored, not even sealed: only its nested HMAC chain (`abolish/phone/v1` over E.164, then one HMAC per later key), matched on every prefix of the chain, so a value made under an older key still matches and the rotation job extends a stored chain with the hash alone. The page sends the number again with the code, since nothing stored can give it back. Verify holds the codes.
- Numbers typed with separators, and ten-digit or `1`-prefixed North American numbers, are read as E.164, and refused unless the lookup gives back the same E.164 form, so one line has one chain; the lookup's country (US, CA) and line type decide the rest: a mobile gets an SMS, a landline or fixed VoIP line a call, and every other type, an unknown one included, is refused as virtual.
- A number another account holds, or one held after an account let it go, is refused (`number-held`) only once its right code is entered, never when a code is asked for, so only whoever has the phone learns it is someone's (T-11). One verified or moved to its account 90 days ago or more moves to the account entering its code, which takes it for a new 90 days; the old account loses its verified phone only. A changed number is held 90 days; a deleted account's number too, by a trigger on `account_phones`, so every deletion path holds it. Days are kept to the day, as the ADR says.
- Turnstile `phone-code` on every request; 5 requests an hour and 10 a day per account, and a daily ceiling across every account (`dailyCeiling`, the deployment's to set), counted under the account's lock before the lookup, which costs too, and kept whatever the lookup or the send says; 5 codes a day per number whoever asks, past which nothing is sent and the requester can't tell. Recorded in [[0038-verified-accounts]]'s second Amendment.
- Tested: the Drizzle view against the migration; no number in any stored row; the checks (hash lengths, days and hours only); the parser (examples and properties); the chain against an independent HMAC computation, a value under an older key matched after a new one is staged or made current, and a chain extended as the rotation job will; the line types (each refused one, a prototype key among them) and channels; a country not served though it dials `+1`; a failed lookup refusing and counting; the Turnstile action and the order of checks; the limits, their race and the ceiling; the per-number cap; a failed send; a held number sent a code all the same; wrong, malformed, expired, spent and other-number answers, an unanswered check spending no try; refusal within 90 days, moves after, the move's new 90 days, re-verification; holds on change and on deletion and their end; two accounts entering codes for one number at once, also on instances with different keyrings; a hold under an older key; a number the provider writes differently; a move racing its old account's change of number (the in-session review's one blocking finding, fixed by locking the account's own number with the new one and deleting a moved row by its hash too); and the prune.

## Built (part 3b)

- `packages/core`: `createTwilioVerifier` (`src/twilio.ts`), the `PhoneVerifier` over Twilio Lookup v2 (`Fields=line_type_intelligence`) and Verify v2 (`Verifications`, `VerificationCheck`), with an API key's SID and secret (or the account's SID and auth token) in Basic auth. Twilio is sent the number, the channel and the code typed, as form fields, and nothing else: no custom code, friendly name or locale. Anything but Twilio's clear answer is `unavailable`, never a pass; `approved` needs both `status: approved` and `valid: true`.
- Lookup: a number Lookup calls not valid is the new `invalid` outcome, which core refuses as `invalid-number` (the request still counts); a line type Lookup couldn't give is `unknown`, refused as virtual, as the ADR says.
- Verify: a wrong code, one gone (`expired`, `canceled`, …), no verification waiting (404 with Twilio's error 20404) and Verify's cap on checks (429 with error 60202) are all `wrong`, so the many accounts that may ask for a code to one number share Verify's one bound of 5 checks (the part 3a known-weak, closed); any other failure is `unavailable` and spends no try. Only codes of 6 to 10 digits are sent to be checked, so a Verify service set to shorter codes verifies nothing rather than allowing 25 guesses in 10^4 a day (T-01). The check, which runs inside core's transaction on the account, waits 5 seconds at most (the part 3a known-weak, closed); a lookup or a send 10.
- `apps/web`: `GET /phone` (the day the account's number was verified, as `verifiedOn`, `YYYY-MM-DD`), `POST /phone/request` (`{ number }`, with the `phone-code` Turnstile token in `x-turnstile-token`) and `POST /phone/verify` (`{ number, code }`) (`src/node/phone.ts`), behind the session, our `Origin` and JSON as `/email` is; core's refusals as codes (`VIRTUAL_NUMBER`, `UNSUPPORTED_COUNTRY`, `NUMBER_HELD`, `WRONG_CODE` with `triesLeft`, `LOOKUP_UNAVAILABLE`, `CHECK_UNAVAILABLE`, `SERVICE_BUSY`, …). The front passes the account cookie to `/phone` and logs it as route class `phone`.
- The provider's send is called after the answer, never before it, so a capped number (sent nothing) answers as fast as any other, and a send Twilio didn't take is logged as `PhoneSendUnavailable` rather than answered (the part 3a known-weak, closed). The lookup is awaited: it is made for every number, capped or not, and its refusals are the ADR's to show.
- `PHONE_HASH_KEYS`, `TWILIO_KEY_SID`, `TWILIO_KEY_SECRET`, `TWILIO_VERIFY_SERVICE_SID`, `PHONE_DAILY_CEILING`: all five or none; without them `/phone` answers 503. The phone keyring must share no key with the e-mail keyrings. Malformed values are refused at start, naming the variable or option only.
- The account prune now also runs `pruneAccountPhones` on its 10-minute timer.
- Tested: the adapter against a stand-in Twilio (the exact URLs, method, headers and form fields; every answer shape that is `approved`, `wrong`, `invalid` or `unavailable`; numbers and codes in the wrong shape never sent; the check's own timeout; bad options refused by name); the routes end to end through the front with the real core as `abolish_app` (the whole flow with a number as typed, landlines called, a held number asked for as any other and refused only with its code, a capped number answered like any other, a send outage answered as sent and logged by kind, an answer that doesn't wait for the send, every refusal, a check outage spending no try, session, origin, media type and routes, 503 without the service, nothing of the number or code in the log); the prune against Postgres; and the built bundle starting with the configuration and refusing part of it, a shared key or a malformed one without quoting it.

## Built (part 3c)

- `packages/core`: `rotatePhoneHashes` (`src/account-phones.ts`) extends every stored chain under a key older than the keyring's current one to it, one HMAC per later key, without the number: `account_phones`, `account_phone_holds`, `account_phone_codes` and `account_phone_recipients`, whose rows now record their key (migration `0030_account_phone_rotation.sql`, with `hash_key` indexes and `UPDATE` of the recipients' hash columns for the rotation). Chains under the current key or a staged later one are left; rows under a key the keyring lacks are left and counted; nothing is rotated while a key fails the check value stored for its ID (`account_phone_key_checks`, written by the first instance to hold the key), since a rotation under wrong bytes would match no number again; and a verified number whose extended value another account's row already holds (two accounts on one number) is left and counted. Each row is rewritten only if it still holds the chain read, and a verified number's row only under its number's locks, which `verifyPhoneCode` holds over every value of the chain while it reads and moves a row by its hash.
- `apps/web`: the account timer (`src/node/prune.ts`) runs it every 10 minutes and at start where the phone service is configured, logging `PhoneHashRotationFailed`, `PhoneHashKeyMismatch`, `PhoneHashKeyMissing` or `PhoneHashConflict` by kind only.
- [[account-keys]] runbook: the three keyrings, the rules (never drop, reorder or insert a phone-hash key; two deploys for every new key), the rotation's steps, the check that it is done and what each log line asks of the operator, what it can't reach (older backups, dead rows until `VACUUM FULL`, the provider's recovery log), and the Verify service settings the guess bound rests on. [[0038-verified-accounts]]'s third Amendment; T-73's history.
- Tested: every table's chains extended to the value an independent HMAC computation gives, and still working after (a verified number, a hold and a waiting code under the rotated chain; a code's tries and a number's cap carried over); several keys at once from wherever a chain stands; chains under the current or a staged key left alone, and a second run doing nothing; rows under an unknown key left and counted; a key with changed bytes stopping the rotation; two accounts on one number left and counted while the rest rotate; a per-number count from before the migration left alone and still counted; rotation racing a move and a change of number (no failure, no number freed unheld or verified twice); the Drizzle view and the grants against the migrations; and the timer rotating only where configured and logging an unknown key.

## Known-weak

- A phone number costs cents to a dollar at SMS-activation markets, and a state makes numbers at will: Tier 0 stays not Sybil-resistant (T-01).
- Whoever holds the account table and every phone-hash key recovers every verified number; each provider keeps its own record of who verified and when (T-73).
- A dump can narrow an address that was sent a message to the accounts that asked for a code in that hour: the per-address rows are timed to the hour, the per-account ones to the second (T-73).
- Accounts made in bulk can spend an address's 5 daily messages and keep its owner from verifying it that day (T-52).
- During a provider outage the page is told a code went when none did; the person asks again, spending their hourly limit, and only the operator's log shows the outage.
- A send still in flight when an instance shuts down may be lost; the person asks again.
- Postmark may refuse an address whose local part isn't ASCII (SMTPUTF8); that person is told a code went and never gets one. Not confirmed against Postmark either way.
- No screen calls `/email` yet: the account page's e-mail steps are part 4.
- No screen calls `/phone` yet: the account page's phone steps are part 4.
- Twilio may answer 20404 both for a verification that isn't waiting and for a Verify service SID that doesn't exist, so a misconfigured service could read every check as wrong; its sends would fail first (logged as `PhoneSendUnavailable`), so no code would reach anyone to check.
- The guess bound (5 codes a number a day, 5 checks a code) assumes the Verify service keeps its defaults: 6-digit codes or longer (the adapter refuses shorter), a 10-minute lifetime (`PHONE_CODE_SECONDS`) and 5 checks per verification. Nothing reads the service's settings; the [[account-keys]] runbook says to check them.
- A check Twilio approves but answers after the 5-second timeout is told `CHECK_UNAVAILABLE`; the code is spent at Twilio, so the retry is wrong and the person asks for a new code.
- Not tried against Twilio itself (no account yet): the field names and status codes are Twilio's documented ones, and the adapter treats anything else as `unavailable`.
- During a provider outage the page is told a phone code went when none did, as with e-mail; only the operator's log shows it.
- An account that changes its number and changes back within 90 days is refused its own old number: a hold doesn't record who freed it, by design.
- A phone-hash keyring that dropped, reordered or inserted a key anywhere but at the end would stop matching the values made under it, letting a number verify a second account; every key is kept for good, in order, a rule of the [[account-keys]] runbook, not enforced by code. A dropped key shows as `PhoneHashKeyMissing` in the log only once rows under it exist; an inserted or reordered one shows nothing.
- A rotation reaches only the live tables: dumps and backups taken before it, dead row versions until `VACUUM FULL`, and the provider's recovery log and replicas still hold chains under the older keys (T-73); the runbook says to delete those backups and shorten or wait out the recovery window after an exposure.
- Each instance counts the rows of all four phone tables under a key it lacks every 10 minutes, scans the `hash_key` indexes don't serve; cheap at today's size, worth an index-only path if the tables grow large.
- An instance with a phone-hash key's bytes changed under its ID stops rotating (`PhoneHashKeyMismatch`) but still verifies new numbers under the wrong key until fixed; only requests and answers made under it are affected.
- A rotation is one transaction per verified number, so a shutdown mid-rotation waits for the run (each row commits alone, and the next tick resumes).
- Not tested: rotation racing an account's deletion, a staged instance's answer during a rotation, or a request at the per-number cap during one; the review's reading is that each holds.
- The e-mail keyrings can take a new key, but rows under older ones are never rewritten until part 3d, so an exposed e-mail key can't be retired yet.
- Each account asking for a code for a number gets its own 5 tries, while the provider keeps one code per number: the bound on guesses is Verify's own cap of 5 checks per verification, which the adapter reads as `wrong` (part 3b). That holds only while the Verify service keeps its default cap.
- The provider's check runs inside the account's transaction, holding a connection for up to the adapter's 5 seconds.
- Accounts made in bulk can spend a number's 5 daily codes and keep its owner from verifying it that day (T-52), as with e-mail.
- Holds and moves count whole UTC days: a number verified at 23:59 can move 89 days and a minute later.
- Whoever has the phone learns, from `number-held`, that the number is some account's: the ADR's refusal "in plain words".
- The holds' trigger stamps the database's own day, not the injected clock; only tests notice.
- Postmark refuses a recipient on its suppression list (an earlier bounce or complaint) as it would any failure, so that person is told a code went and never gets one.
- Making a new hash key current before every instance holds it could let two accounts verify one address or one number; the two-deploy order is a rule of the [[account-keys]] runbook, not enforced by code.
- Anyone without a US or Canadian number can't verify an account, so can't vote at Tier 0, until the country list widens.
