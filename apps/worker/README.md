# @abolishus/worker

Background jobs on BullMQ, over Redis in development and CI and Dragonfly in deployment. Internal and source-only; AGPL-3.0-only. Handlers parse, call `@abolishus/core` and log; no protocol logic lives here.

## Queues

| ------------------------- | ----------- | ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `{board-audit}`           | board       | `{}` | Every `AUDIT_EVERY_MS` (10 minutes by default, and once at start): core's `auditBoard` over every stored board. Each bad board, and each board whose audit failed for another reason (`audit-error`), is a finding line; the job then fails with `board-audit-findings`.                                                                                                                                                                                                                                                                                                                                                                                                                                 |

| `{ballot-submit}` | board | `{electionId, ballot}` (hex) | Only with pinned panels (`startWorker`'s `ballots`): the ballots the API's `ballots.submit` queued through `BallotQueue`. ## No joins (T-10)

- **Sides.** Every queue in `src/queues.ts` is a board queue, an account queue or an operational one. A board queue's data names no account, session or person; an account queue's names no ballot, nullifier, poll or election; an operational queue (upkeep such as the identity-backup prune) names neither. No job crosses sides. `tests/no-join.test.ts` checks every queue's fields against both deny-lists, so a renamed field would pass; review of each new queue still has to catch that.
- **Strict data.** Job data is a `z.strictObject`, parsed again by the worker before a handler sees it; data with a field the schema doesn't name, or a job named other than its queue's key, fails as `invalid-job-data` without being handled. Job IDs are BullMQ's counters, or for `{ballot-submit}` a random UUID `BallotQueue` draws, never derived from data.
- **Nothing kept.** A job's data, error and stack trace leave Redis as soon as it finishes (`removeOnComplete` and `removeOnFail` on the worker, so a producer can't opt out by omission). BullMQ also writes every failure's message, and every completed job's return value, to the queue's events stream, which those options don't clear and which keeps each job's ID, name and timestamps (up to about 10,000 events); the only return value is `{ballot-submit}`'s outcome, a board index or a refusal's code, never the ballot, so names are fixed to the queue's key and the worker turns any error into a `JobError` whose message is its fixed kind. Two tests fail if anything reaches a log line or any Redis key, the events stream included: one queues an account field on a board queue, the other makes a handler throw a message that quotes data.
- **Producers.** One: `BallotQueue` (`src/ballot-queue.ts`, exported as `@abolishus/worker/ballot-queue` for the API), which parses the data, forces `JOB_OPTIONS` and the job name, takes no job ID, deduplication ID or option from its caller, and draws a random job ID itself so it can listen for the outcome before the job is queued. `tests/ballots.test.ts` fails if a ballot or its election stays in any Redis key, the events stream included, once judged.
- **Log.** One line per job: queue, outcome, error kind from a fixed list, duration. Never the data, the job ID or an error message, since messages can quote data. An audit finding adds the election ID and entry index, and an anchoring finding the election ID and segment, all public on the board, and no person's request leads to either.

## Keys (Dragonfly)

Every key is `abolish:{<queue>}:…`. The braces are a hash tag: BullMQ's Lua scripts touch several keys of one queue, which Dragonfly (with `--cluster_mode=emulated --lock_on_hashtags`) and Redis Cluster need in one slot, while separate queues can live on separate threads or shards. A test checks every key the worker creates.

## Tier 0 batch job

`src/tier0-chain.ts` is the batch job's chain adapter (docs/spec/registration.md, The batch): `ViemTier0Chain` reads the group registry from one L2 node at a pinned pair of finalized and latest blocks, and `checkTier0Deployment` refuses to start a job whose chain, registrars, threshold or keys aren't the registry's. Submission is passed in: `src/tier0-bundler.ts`'s `connectTier0Bundler` checks the registration account and paymaster against the configured EntryPoint, registry and owner key, and the bundler against the chain and EntryPoint, then returns the submitter, which sends each record as an ERC-4337 operation from the account, paid by the paymaster (docs/spec/contracts.md, Registration paymaster and Registration account): it builds exactly the call the paymaster sponsors under a nonce key named by the record's group, lowers the fee (estimating again, since an L2 bundler's `preVerificationGas` grows as the fee falls) so the operation's most-it-can-cost stays within the paymaster's cap or sends nothing, signs EntryPoint v0.8's hash with the account's key and requires the bundler to answer that hash. Every failure is a fixed message, never the record or the bundler's error (T-10, T-13). `tests/tier0.test.ts` runs the job against the group registry on Anvil, and `tests/tier0-bundler.test.ts` the submitter against EntryPoint v0.8 itself with the account and paymaster, through a stand-in bundler that lands each operation with `handleOps` (no bundler's ERC-7562 simulation runs; Known-weak in P3-2's status). Both need the toolchain (`.github/scripts/install-toolchain.sh`).

`src/anchor-chain.ts` is the anchoring job's chain adapter (docs/spec/contracts.md, Board anchor): `ViemAnchorChain` reads the board anchor from one L1 node at the block its `now()` pinned, refusing a node behind a block or time already read; it simulates each `anchor` call from the authority before sending it, and fails a call whose sender resolved while the anchor doesn't hold its checkpoints. `checkAnchorDeployment` refuses to start a job whose chain, clock or authority aren't the anchor's finalized ones, or whose authority is a single key. Sending is passed in; through the Safe it is P4-1 part 2b-2's. `tests/anchor-chain.test.ts` runs core's `anchorBoards` through it against the anchor on Anvil.

## Running

`vp run --filter @abolishus/worker start` (plain Node, as `apps/api`; `erasableSyntaxOnly` keeps it that way) with `DATABASE_URL` (a user granted `abolish_app`, never the owner), `REDIS_URL` and optionally `AUDIT_EVERY_MS` (at least 60000).

Ballot admission (`{ballot-submit}`) runs only with all three of `BALLOT_PINNED_PANELS` (the trustee panels the release pins, as JSON: `[{"threshold": k, "keys": ["<hex>", …]}]`, each key a seat's identity key in seat order), `BALLOT_ANCHOR_EPOCH` and `BALLOT_ANCHOR_PERIOD` (the anchoring clock of the anchor contract our definitions name, docs/spec/board.md, Timing); the worker refuses to start with only some. They were the API's `API_PINNED_PANELS`, `API_ANCHOR_EPOCH` and `API_ANCHOR_PERIOD` before admission moved here.

The Tier 0 batch job runs only when every one of these is set, and the worker refuses to start with some of them (`src/tier0-env.ts`), or when `checkTier0Deployment` or `connectTier0Bundler` find the chain other than configured:

| Variable               | Value                                                                                       |
| ---------------------- | ------------------------------------------------------------------------------------------- |
| `TIER0_L2_RPC_URL`     | The L2 node the job reads (HTTP).                                                           |
| `TIER0_BUNDLER_URL`    | The ERC-4337 bundler it submits through (HTTP).                                             |
| `TIER0_CHAIN_ID`       | The L2's chain ID.                                                                          |
| `TIER0_GROUP`          | Region 0's published group, the API's `API_TIER0_GROUP`.                                    |
| `TIER0_REGISTRY`       | The group registry's address.                                                               |
| `TIER0_REGISTRY_BLOCK` | Its deployment block.                                                                       |
| `TIER0_REGISTRARS`     | The registry's pinned registrars, comma-separated, in seat order.                           |
| `TIER0_THRESHOLD`      | Its threshold.                                                                              |
| `TIER0_SIGNER_KEYS`    | Secret: `seat:key` pairs, comma-separated, exactly `TIER0_THRESHOLD` of them, seats rising. |
| `TIER0_ENTRY_POINT`    | EntryPoint v0.8's address.                                                                  |
| `TIER0_ACCOUNT`        | The registration account's address.                                                         |
| `TIER0_ACCOUNT_KEY`    | Secret: the account's owner key.                                                            |
| `TIER0_PAYMASTER`      | The registration paymaster's address.                                                       |

Keys are 64 hex digits, `0x` optional, and are never quoted in an error. Treat both URLs as secrets too: a provider's API key often sits in their path or query, so a malformed URL is named, not quoted, and a startup that can't reach the node or bundler reports only which check failed. The registrars' keys and the account's key are online in the job (T-69).

## Tests

`vp run --filter @abolishus/worker test` needs `TEST_DATABASE_URL` and `REDIS_URL`, and runs uncached. Each run uses its own key prefix and removes its keys afterwards.

## Decisions

- **ioredis as BullMQ's client.** BullMQ 6 takes ioredis or node-redis; ioredis is the one BullMQ's own tests pin and the one its Dragonfly guidance uses.
- **`msgpackr-extract` isn't installed** (`ignoredOptionalDependencies`). msgpackr, which BullMQ uses, loads this optional prebuilt native binary whenever it is present, install scripts or not; without it msgpackr uses its pure-JS codec. A test checks it doesn't resolve and that msgpackr's native acceleration is off.
