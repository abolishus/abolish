# T-24: Equivocation (split view)

- Area: Integrity and verifiability (G-7, G-8, G-9)
- Adversary: A-2, A-1
- Status: **Planned.** Residual: before its segment's anchoring deadline, a voter checking via our API alone can be shown a fork. Receipts must be re-checked against L1 after the deadline, and the client must refuse an envelope labelled with a segment other than the current period ([[board]]). Whoever holds the election's anchoring key can fail a running election, publicly and attributably, by anchoring checkpoints for different segments that no single board matches (equivocating within one segment is refused by the L1 board anchor, [[contracts]]) (`checkpoint-inconsistent`, attributable from L1 and any copy that matches a checkpoint). Not mitigated yet: a checkpoint that extends every receipt with entries never published, or forks only after the last receipt, leaves the election unverifiable for good, and no voter's receipt attributes it ([[board]], Residuals; P4-1, P4-3).

## Threat

The server shows different boards to different viewers, for example omitting one voter's ballot only from the copy that voter sees.

## Mitigation

Receipts are checked against L1-anchored checkpoints, which everyone sees identically: each anchor names its election and segment, the verifier checks every checkpoint anchored for the election, and two different ones for a segment fail as equivocation; an inclusion proof shows the entry is in the anchored tree, and a consistency proof shows the anchored tree extends the one the voter was shown when casting (RFC 9162; [[board]]; P1-13, P1-16, P4-1); community nodes (P4-5) and the verifier read from chain + IPFS, not our API.

- 2026-10-17 (P4-3 part 2b-2b-2, [[verifier]], Board by CID, Gateways): a gateway the verifier asks for a block can withhold it but never change it: an answer counts only if its SHA-256 is the CID's digest, redirects are never followed, and the copy is authenticated against L1's anchors, so a gateway serving different viewers different data can only leave a copy short, unverifiable from it, never failed.

Index: [[THREAT_MODEL]].

## History

- 2026-10-10 (P1-16): board tree, inclusion and consistency proofs and checkpoints specified and built in `packages/crypto`; receipts that carry them are P1-13's.
- 2026-10-11 (P1-16 follow-up, #37): checkpoints no board can match fail the election as `checkpoint-inconsistent` instead of reading as a bad copy; client rule 2 checks every timely checkpoint against the receipt, earlier ones included.
- 2026-10-11 (P1-13, receipts): the receipt carries the operator's signature on the size, root and head of the board it showed the voter, with the voter's entry last ([[receipts]]); checking it against the anchored checkpoints is [[P1-13b]].
- 2026-10-12 (P4-1 part 1): the L1 board anchor stores one checkpoint per election and segment, refusing a second even if equal, so L1 never holds an equivocation, and a verifier reads every anchor of an election from per-segment storage slots with storage proofs, from the election's lowest anchored segment to the seal, never from a log list an RPC node could shorten ([[contracts]], Board anchor). Not deployed yet.
- 2026-10-12 (P1-19 part 3a): `packages/verifier` reads an election's anchors from the board anchor's storage, proven against one L1 header's state root (strict RLP, Merkle–Patricia proofs), from `max(lowest, f)` to the last ended period, and matches each word against the copy or a checkpoint whose hash is the word; a word nothing matches is unverifiable, never failed ([[verifier]], Anchors from L1). The header itself is still a local input, so no run is verified yet.
- 2026-10-12 (P1-13b part 2a): client rule 2 is replaced by [[receipts]], Later checks: the client rebuilds the board tree from every segment's entry-hash list and compares every counted checkpoint's root, and an anchored board its receipt's root isn't a prefix of is a `forked` verdict a third party can check with a consistency proof.
- 2026-10-13 (P4-3 part 2a, [[0029-board-data-availability]]): decided, not built. Checkpoint version 2 names each segment's CIDs on L1, and before any result each trustee panel's threshold of seats must attest through the L2 contract path that it held the ballot extent by `c_I` and the counted extent before any summed share, or the election fails `unavailable`, listing who attested, complained or did nothing. A withheld or forked extent through the counted set then fails the election instead of leaving it unverifiable, unless a panel threshold colludes; the tail after it (openings, tally, destruction statements) stays unverifiable, and under the transitional panel the attestation is the operator's own.
- 2026-10-13 (P4-3 part 2b-1): checkpoint version 2 built: each checkpoint names the CIDs of its last segment's object and entry-hash list (`abolish/v1/board-checkpoint-2`; version 1, never anchored, retired), `BoardAnchor` takes 180-byte checkpoints and refuses misframed CIDs, and a checkpoint whose CIDs don't name the anchored bytes fails the election as `checkpoint-cid`, attributably to the anchoring authority. Withholding is named on L1 but fails nothing until part 2c's attestations. Not deployed yet.
- 2026-10-16 (P1-12f part 1a, [[delivery]], Leaf availability): specified, not built. A root's leaf object is named by its canonical CID in the signed root, and a counted-extent attestation names each root it holds by its record hash, so a seat can't show one leaf set to some seats and another to others without an inconsistent root, attributed to it.
- 2026-10-17 (P1-12f part 3a, `packages/crypto`): a root's leaf object is read from its blocks, each checked against its CID, and blocks that hash but don't form the canonical DAG of the signed length (another chunking or layout, a non-canonical node) make the root `root-inconsistent` against its seat, as the spec says, rather than unverifiable: no source can bring that about or hide it, only fail to serve a block.
- 2026-10-17 (P4-1 part 2a): the anchoring run (core's `anchorBoards`, `apps/worker`'s `{board-anchor}`) takes each ended period's checkpoint with the verifier's `copyCheckpoints` under the board lock and fences its segment, in `appendEntry` and a trigger, so no entry lands behind a checkpoint once taken; it sends each checkpoint only while the anchor's slot is empty, and reports a slot holding another checkpoint (`anchor-conflict`) instead of sending a second. Not run against a chain yet: the Safe's adapter is part 2b.
- 2026-10-17 (P4-3 part 2b-2a, [[board]], A copy from L1's CIDs): `packages/crypto` reads a board copy from the CIDs the counted checkpoints name, each run's segment object within the most its entries encode, and the board checks authenticate every byte of it, so a source serving other bytes only leaves the copy short (unverifiable), never a second view that passes.
- 2026-10-17 (P4-5 part 2): `apps/node` pins only checkpoints whose hash the anchor holds at the finalized L1 block, proven with the verifier's own state reader; logs only say what to prove, and a withheld log, below the lowest logged segment as much as between, leaves that election unpinned and reported (`l1-checkpoint-unknown`), never pinned short without a word.
- 2026-10-17 (P4-3 part 2c-1, [[availability]]): specified, not built. The availability attestation (`0x001b`) and availability complaint (`0x001c`) records, signed by each seat's per-election key and counted only through the L2 contract path; the fetch allowances `A` and `A'` (12 hours each) with `A` in `deliveryWindowFits`'s bound (built in `packages/crypto`, which caps the release's `R` at 9 hours); and verifier 4.6, which reads L1 and the L2's events alone and fails the election `unavailable` unless every panel's threshold attested both the ballot extent (`C_A`, by `t_A = c_I + F`) and the counted extent (`C_S`, by `t_A' = t_S + A' + F`). The records' codec and the check are in `packages/crypto` with vectors; the contract call, the verifier's inputs and the seats' job are parts 2c-2 to 2c-4, so nothing fails an election for withholding yet.
