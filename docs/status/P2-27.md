## Scope

The rest of the account side ([[P2-5]]): who you are to the app, never how you voted.

- A creator's public profile: the polls they asked, nothing else.
- Settings: name, sign-in passkeys, notification choices, data export and account deletion.
- Notifications by email, and by web push where the browser allows: results ready, live batches on followed polls ([[P2-25]]), moderation decisions on your polls ([[P2-10]]).
- The account is also what voting needs at Tier 0 ([[P2-30]]); the account page shows that the device holds a voting identity and offers its backup, never anything about answers.

Rules for every part, as [[P2-19]]'s: everyday register by default ([[language]]); no hard-coded strings (`messages.ts`); CSP-safe (no inline `style`); server-rendered where the page is the website's; a fixed analytics template per route, never a path or poll ID (T-67); each component a story with a play function passing axe at desktop width and 360px; SSR and serve tests per route; the mockup's story deleted in the PR whose page matches it. Privacy holds everywhere: nothing an account does on the website (following, reacting, sharing, notifications) is ever stored, logged or keyed with a ballot, nullifier, receipt or the fact of having answered, and the T-10 no-join tests cover every new table, queue and log line ([[PROJECT_BRIEF]], Identity).

## Notes

- **Part 1a**: [[0040-creator-profiles]] (`Accepted (agent) — owner may veto`, under Decisions to review in [[STATUS]]): a profile is opt-in and per poll, an author-chosen name (NFC, 1 to 60 code points, no control, format or invisible characters, one rename a day, not unique and not verified) and a random 80-bit base32 handle at `/by/<handle>`, never reissued; it shows the name and the linked polls that are registered and listed, nothing else. The link lives only in account-class rows (never on chain, IPFS, the board or the archive), deleted with the profile or account and lost in a wipe; profile pages are `noindex` and counted as `/by/$handle`; public reads come from `apps/web`'s server, so the API still reads no account table; names are moderated under [[moderation-policy]]'s grounds before any is shown. New threat [[T-75]]; history lines in T-10, T-17, T-67 and T-68.
- **Part 1a known-weak**: "Asked by" is our database's word, which an insider can change; a rename changes the name on every linked poll; look-alike names are answered only by `impersonation` moderation; copies of a poll page made while it was linked outlive unlinking (T-75).
- **Part 1b**: `packages/core` (`src/profiles.ts`, migration 0033): `profile_handles` (every handle ever issued; the app role may add one, never change or remove it), `account_profiles` (one per account: handle and name; the name may be updated, never the handle), `account_profile_namings` (the UTC day an account last set a name, kept when the profile is deleted) and `account_profile_polls` (which of an account's own polls it shows, keyed on `account_polls (id, user_id)`), all account class in the no-join tests. `makeProfile` needs a verified phone; `profileName` collapses spaces, trims, composes to NFC and refuses control, format, private-use, unassigned, surrogate, default-ignorable and separator characters but the space, the blank Braille pattern and names with nothing visible, 1 to 60 code points, checked again by the table; a name is set at most once a UTC day, making included; `showOnProfile` makes or takes back a poll's choice at any state; `readProfile` returns the name and the newest 100 chosen polls with a stored definition and no delist or hide standing; `askedBy` gives a poll's profile, none for a hidden poll. Tested in `tests/profiles.test.ts` (schema and grants, the name rules as properties against the table, handles, limits, races, cascades and what the public reads leave out).
- **Part 1b known-weak**: the phone is checked only when a profile is made, so a number moved on after 90 days leaves the old profile standing (one new profile per number per 90 days, as accounts); the app role can point a new profile row at a retired handle by hand, which core never does (the insider case of T-75); look-alike letters pass (`impersonation` moderation only).
- **Part 1c-1**: `packages/core` (`src/profile-moderation.ts`, migration 0034). `profile_moderation_actions` is the profiles' half of the moderation log: append-only for the app role and the owner (grants and triggers, as `moderation_actions`), each row a `hide` under a removal ground or a `restore` under a restore ground, naming the profile by its handle and never its account. An insert trigger numbers every row from the poll log's own sequence whatever the insert says, and every decision takes `lockModeration`, so the two tables read as one log in commit order and no number names two decisions (`readModerationLog` and `readProfileModerationLog` merge by `seq`). `moderateProfile` refuses a malformed decision, `appeal-upheld` outside a review (`appeal-only`), a handle no profile has now (`unknown-profile`, so deleted profiles' retired handles too), an inactive moderator, the moderator's own profile (`own-profile`) and a no-op (`no-change`: a restore of a visible profile, or a hide re-citing a ground cited since it was hidden). While the newest decision hides a profile, `readProfile` returns only its handle and the ground (`state: "hidden"`), and `askedBy` names it on none of its polls; the polls themselves stay listed, moderated as polls; a rename doesn't lift a hide. `profile_reports` counts reports per handle and ground as `moderation_reports` does (`reportProfile`, `readProfileReportQueue`, `reviewProfileReports`), nothing about the reporter. `account_profile_appeals` (account class, deleted with the profile or account) holds the author's one appeal per hide (`fileProfileAppeal`), reviewed under `decideAppeal`'s rules (`decideProfileAppeal`: not the decider or a re-citer, not the profile's own account, `superseded` after a restore), and the author's view (`readProfileModeration`) names no moderator or reviewer. Tested in `tests/profile-moderation.test.ts` (schema, grants, append-only for both roles, the shared numbering against an explicit `seq`, the check constraints; hides, restores and every refusal; a fast-check model of the no-change rule; merging the two logs; reports and the queue's cursor; appeals filed, upheld, rejected and superseded, the queue naming no account, cascades) and the updated `tests/profiles.test.ts`, `tests/accounts.test.ts` and `tests/no-join.test.ts` (the new tables classified).
- **Part 1c-1 known-weak**: a hidden profile's author can delete it and make a new one, under a new handle and at most one name a day, shedding the hide; the new profile links no poll until its author chooses each again, and `impersonation` reports start over. A decision judges the name it saw: a rename after a restore isn't reviewed again unless it is reported. The app role can still insert log rows directly, bypassing the tooling's rules, as for polls (T-68). The API, the operator's commands and the author's route come in part 1c-2, so nothing is reportable or appealable from outside yet.
- **For part 1c-2**: the API's `GET /moderation/log` should carry both targets in one sequence (merge by `seq`); `POST /moderation/reports` takes a profile handle beside an election ID; the author's appeal and view go on `apps/web`'s origin as `POST /drafts/appeal` does, never the API (T-10).
- **For part 1d**: render every name isolated (`<bdi>` or `dir="auto"`), so a right-to-left name can't reorder the text around it; profile pages `noindex`, counted as `/by/$handle`; nothing shown before 1c merges.
