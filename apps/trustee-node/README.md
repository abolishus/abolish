# @abolishus/trustee-node

The node each trustee runs on infrastructure it controls ([[0006-trustees]], Consequences; `docs/status/P2-13.md`). Internal and source-only; AGPL-3.0-only. It runs only what `docs/spec/` defines, calling `@abolishus/crypto` for every message and check and never reimplementing one.

So far it holds the seat's part in the key ceremony (`docs/spec/ceremony.md`), the transport that carries it to and from the coordinator, the seat's availability attestation of the ballot extent (`docs/spec/availability.md`), its intake of delivered ballots with share receipts (`docs/spec/share-encryption.md`, Intake and receipts), and the decision at the intake cutoff of what it owes through the contract path (`docs/spec/delivery.md`, What a node owes). It listens for deliveries at its intake endpoint, and, with the availability duty, serves what it attests as a trustless gateway. It sends the receipts it owes, and decides and sends the complaints it owes about postings whose shares fail (not yet stepped in `run`). Its tally duty reads the counted set from the counted extent it attested, sums its shares over it, exchanges summed shares with the other seats over the summed-share channel and signs each cell's opening, stepped in `run` with the channel served when the configuration names the other seats' endpoints. It sends each opening to the board operator, and once the anchored board carries a passing opening of every cell, or finalized L1 shows `t_D`, it destroys the election's secrets and shares, signs its destruction statement and sends it to the operator until the destruction window ends. Operating a node: [[trustee-node]] (`docs/runbooks/trustee-node.md`).

## Electorate check

`l2ElectorateCheck` (`src/electorate.ts`) is `run`'s `ElectorateCheck` where the configuration names `availability.groupRegistry` ([[ceremony]], Stub checks, step 3; [[verifier]], Electorate). On the L2 the configuration pins (the node's `eth_chainId`), once the stub's latest `root_l2_block` is in the seat's own L2 node's finalized history, and not before the registry's deployment block, it takes the registry's event accumulator and count proven under an output root on L1 (`l1OutputRootAccumulators`, `src/output-root.ts`: of the newest 64 dispute games at the seat's L1 node's finalized head, those of the type the portal (`availability.portal`) respects that aren't shown false, highest claimed L2 block first, the first whose block's header, the message passer's storage root and the registry's account and storage proofs from the seat's L2 node prove under its root, by `packages/verifier`'s `accumulatorAtOutputRoot`), at a block at or after the stub's. It then reads every log of the registry from its deployment block to the proven block, each with its block's time, and requires them to replay to the proven accumulator (`checkEventAccumulatorProof`), so the L2 node can't hide, invent, alter, reorder or move a log. Of those, the group events (creations, additions, removals and `RegistrarsPinned`) go, in that order, to `packages/verifier`'s `electorateCheck` under the registry and registrars the configuration pins, which passes the stub only if it names that L2 and that registry, and every tier's groups, regions and cells (version 1: `group_id`, `root` and `group_size`) are what the registry's strict replay and the first-occurrence rule make of the log at the tier's block. A Tier 1 or Tier 2 tier, a block not final yet or past the newest posted root, a log that doesn't replay, answers that don't prove and a node that can't be read are refusals (`stub-electorate`), never passes; any other error stops the node.

## Transport

For the ceremony the node only calls out: it polls the coordinator for what it asks of the seat and posts its answers, so no ceremony request reaches the host that holds the seat's keys unasked (`TrusteeNode` over a `Coordinator`; `HttpCoordinator` over HTTPS). It listens only for intake deliveries and, with the availability duty, gateway requests for what it attests. The coordinator is trusted for liveness only ([[ceremony]], Parties and keys): everything it returns goes through the seat's checks, and everything the node posts is signed or public.

| Request                                | Body                                                                                                       |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `GET  v1/ceremony/seats/{i}/requests`  | 200: `list<{stub: bytes, transcript: bytes}, 16>`                                                          |
| `POST v1/ceremony/seats/{i}/messages`  | `{stub_hash: bytes32, transcript: bytes}`: a transcript holding only the seat's message, in its round; 204 |
| `POST v1/ceremony/seats/{i}/approvals` | `{stub_hash, ceremony_transcript_hash, key_set_hash: bytes32, signature: p256-sig}`; 204                   |

Bodies use [[notation]]'s encoding (`bytes` is `bytes<2^20>`), as `application/octet-stream`; they are this transport's envelopes, not protocol records: nothing hashes, signs or archives them whole. Inside them the stub is an election-definition record and the rounds a ceremony transcript record (version 1). A request's `transcript` holds the rounds the coordinator has closed, and asks for the first empty one; all four rounds ask for approval; a non-empty round after an empty one asks for nothing and is refused. The node recomputes `stub_hash` from the stub rather than taking it from the coordinator, and names a run by it and `run_id`.

A lost poll, post or response costs nothing: the next poll asks again and the seat answers with the message it recorded. The node settles each request once (answered, or refused for a reason a later poll can't change) and asks the seat again only for `stub-electorate`, which can change as L2 finalizes, and `no-run`, which can change once it answers an earlier round listed after it. `HttpCoordinator` takes HTTPS only (HTTP only to loopback), follows no redirect, times requests out and stops reading a body past its bound.

## Availability duty

`AvailabilitySeat` is a default-panel seat's duty at the ballot extent for one election it approved ([[availability]], What a seat does; [[0029-board-data-availability]]; T-24, T-25, T-53, T-54). `CeremonySeat.approvedElection(stubHash)` gives it the election and the per-election signing secret of the approved run, from an `approved-runs/` record written before the approval. Each `step()`:

1. Resends a stored attestation unless the board contract has recorded it (`recorded`); a stored record is resent past `c_I` too, since one forced through L1 by `t_A` counts, but never past `t_A`, when it can't (`unrecorded`, an alarm).
2. Past `c_I` with no attestation it signs nothing new, and resends a stored complaint (`past-cutoff`).
3. Reads the election's anchors from finalized L1 (`FinalizedBoardAnchors`) and waits until `s_A`'s anchoring deadline has passed there (`waiting`), so `C_A`, the counted checkpoint with the largest segment at or before `s_A = period(closes_at) + 1`, is fixed. A failure of the board checks' steps 1 and 2 is `board-failed`, reported before anything else; no counted checkpoint at or before `s_A` is `no-checkpoint`.
4. Reads the board through `C_A` by the anchored CIDs from any sources (`readBoardCopy` over the anchors at or before `C_A`'s segment) and runs `verifyBoard` over them. A copy that passes, or fails only `unanchored` or `unsealed` (which judge segments past the extent), is held: the seat first pins every segment object and entry-hash list the counted checkpoints through `C_A` name (each run's entries and their entry hashes, each compared with its CID on L1) through the deployment's `pin`, then signs an attestation naming `C_A`'s `checkpoint_hash` with no roots, stores it, then sends it. A pin that fails throws, and nothing is signed: the seat never attests what it can't serve ([[availability]], What a seat does, 4).
5. A copy that stops, or fails `checkpoint-missing` or `copy-mismatch`, isn't held from these sources: before `c_I − sendMargin` it is `fetching`; from then it signs a complaint naming that run's `object_cid`, stores and sends it, and keeps trying to attest by `c_I`. Any other board failure is the operator's or the anchoring authority's (`board-failed`): no record, and 4.2 fails the election.

Records live under `availability/<definition hash>/ballot/` and are written once, so the seat signs at most one attestation and one complaint of the point.

**The counted extent.** The same `AvailabilitySeat`, given `counted` (the deployment's pinned anchoring clock), is the seat's duty at point 2: `C_S` is the counted checkpoint with the largest segment at or before `s_S`, fixed at `t_S`, both from `countedExtent` over the definition's close and bound and that clock ([[tally]], Tally window), so the duty's cutoff `c_A' = t_S + A'` and deadline `t_A' = c_A' + F` are known before any read. Its reader is `l1BoardAnchors(options, election, AVAILABILITY_POINTS.countedExtent)`, which proves the anchor's words from `f` through `s_S` rather than `s_A`; the seat refuses a read under another clock than its own (`L1AnchorError` `clock`) and an election closing before the clock's epoch (`outside-clock`). Every step above holds with `C_S`, `c_A'` and `t_A'` for `C_A`, `c_I` and `t_A`; the records live under `availability/<definition hash>/counted/`, apart from the ballot extent's, and name point 2. An attestation names no roots ([[availability]], Attestation, The roots): a seat names only roots whose leaf objects it holds and has checked, and the node fetches none yet ([[P1-12f]] part 3c); honest seats send roots only in elections that commit them, which the stub's capacity check refuses until then. A reader whose clock stops before `s_S` is refused as `clock` too, so a ballot-extent reader wired to the counted duty can't make it attest `C_A` as point 2. `heldExtent` gives the counted extent the seat attested, for the tally's counted set (part 5b-2b-2b). A recorded record that differs from the stored one is `foreign-record`, an alarm: the seat's per-election key signed bytes this node never stored. The deployment supplies the L1 reader, the block sources, `pin` and the contract path (`ContractPath`: `send`, forced through L1 when the sequencer refuses, and `recorded`, read from the seat's own L2 node as finalized L1 derives it).

`l1BoardAnchors(options, election)` is the L1 reader (`src/l1.ts`). Set up once per approved election, it checks both nodes' chain IDs, reads the election's `ElectionCreated` and `DefinitionRegistered` from the registry in finalized L2 history (`registration`, from `@abolishus/node`), requires the registered definition to hash to the approved `definitionHash` and to name the deployment's anchor, registry and chains, requires the anchor's `epoch`, `period` and `deadline` getters to give the deployment's pinned clock (`timing`; a wrong clock would fix `C_A` at another moment, and the seat's one attestation would never count) and the creation's L1 origin to be the finalized L1 block of its number (its hash and timestamp), and fixes `f` from that origin. Each read takes the finalized L1 header, the election's `CheckpointAnchored` logs as candidates, and `eth_getProof` for the lowest-segment word and segments `f` to the last ended one at or before `s_A`, then proves them with the verifier's `anchorsFromState`: a checkpoint counts only as the proven word's preimage, so a node can make a read fail (`l1-checkpoint-unknown`, `l1-proof-missing`) but never hand the seat an anchor L1 doesn't hold (T-24, T-51, T-53). The clock's `lastSegment` is `s_A` rather than the seal, which no definition derives yet: every seal is at or after `s_A`, and the duty reads nothing past `C_A`. Refusals are typed (`L1AnchorError`: `chain`, `definition-version`, `definition-hash`, `definition-deployment`, `clock`, `origin`, `outside-clock`).

`l2RecordedAvailability(options)` is `ContractPath.recorded` over the seat's own L2 node (`src/recorded.ts`). Set up once, it checks the node's chain ID (`RecordedError`: `chain`). Each read asks for the board's `AvailabilityAttestationSubmitted` or `AvailabilityComplaintSubmitted` logs with the slot's definition hash and seat as topics, from the board's deployment block to the node's finalized block, which the node derives from finalized L1, so a sequencer's soft confirmation never stops the seat resending (T-71). A log must pass the event check under the newest contract-event version (`checkContractEvent`), name the slot's definition and seat and carry a record of the slot's panel and point; any other log is passed over, as a withheld one would be. Two records in one slot, which the board never emits, are refused (`L2Error`: `l2-repeated`). The node is trusted for which logs exist, as for the registration: hiding the seat's record makes it resend bytes the contract takes as a no-op, and showing one it never recorded either stops the resending early or raises `foreign-record`; what the seat signs is its store's, never this read's (T-24, T-53).

`availabilitySender(options)` is `ContractPath.send` (`src/send.ts`). Set up once, it checks both nodes' chain IDs and that the board (on L2) and the deployment's pinned `OptimismPortal` (on L1) have code (`SendError`: `chain`, `no-code`). One account, whose key the deployment supplies, pays on both chains; it grants no authority, since the board accepts a record for its seat's P-256 signature whoever sends it. Each send, one at a time so two never take one nonce:

1. Offers the record's `submitAvailabilityRecord` call to the seat's L2 node, which passes it to the sequencer: one EIP-1559 transaction at the account's pending nonce, with a fixed gas limit (`AVAILABILITY_CALL_GAS`, 600,000: the board's figure is at most about 172,000 for a record with no roots and 422,000 for one naming 32, so no node's estimate can starve it), the deployment's fee cap as its fee and the node's tip up to the cap. The same signed bytes are resent until a block holds them; one whose nonce went to another transaction is signed again at the next. A call the board reverted is `reverted`, an alarm: it refuses the record, so no resend fills the slot.
2. Deposits the same call through the portal (`depositTransaction(board, 0, AVAILABILITY_CALL_GAS, false, call)`) when the L2 node refuses it or can't be reached, when it has waited `forceAfter` outside any block, and from `cutoff − forceLead` whatever the sequencer did, since a record in an unsafe block whose batch isn't on L1 by `c_I` must be forced all the same. A deposit on L1 by `c_I` reaches L2 by `t_A = c_I + F`, and the record counts by that block's time ([[availability]], Windows; T-25, T-50, T-71). Its L1 gas is the L1 node's estimate and a quarter, at least `DEPOSIT_GAS_FLOOR` and at most 2²⁴ (`deposit-gas` past it); one that reverted on L1 is signed again.
3. Throws `unsent` when neither path took the record now; the seat's next step tries both again. A call the board reverted is still deposited once from `cutoff − forceLead`, since only the node says it reverted, and at most `MAX_SIGNED_PER_RECORD` (3) transactions are signed per record and chain, so a node lying about nonces or reverts can't collect signed deposits to spend the account (T-52). A nonce past 2⁵³, which no account reaches, is the node's refusal.

`AvailabilityDuties` (`src/duties.ts`) runs the ballot extent's duty in a deployment, and `CountedAvailabilityDuties` the counted extent's, over the same sender, sources and store, settled the same way by `t_A'` (logged as `counted-availability`); `run` gives both `boardSender`'s availability call, the receipt duty taking the same sender's receipt-batch call. Each poll it lists the stubs the seat approved (`CeremonySeat.approvedStubs`), builds each one's `AvailabilitySeat` once its L1 reader can be set up (the board-entry version it checks under is the registered definition's pin, which `l1BoardAnchors` gives), and steps them side by side until each is `recorded`, `unrecorded` or `foreign-record`, or `past-cutoff` at a step begun after `t_A` (so a record never recorded is still reported `unrecorded`). A node's failure (`RpcError`, `L1Error`, `L2Error`, `SendError`) is retried at the next poll; an `L1AnchorError` gives the election up for good, and so does `t_A` passing before its duty could be set up (`availability-abandoned`: never registered, or never final at the seat's nodes); an L1 node whose finalized block is behind the creation's origin is a lag, retried; anything else ends the loop, as it ends the ceremony's. Each election's status and failure is logged when it changes, never a secret.

The board takes a byte-identical repeat as a no-op, so a record that arrives both ways, or again after a restart (the signed transactions are held in memory only), costs gas and nothing else. Nothing the nodes answer here decides whether the record is recorded (`recorded` does): a node that lies about a receipt delays the deposit to `cutoff − forceLead`, never past it.

## Intake

`IntakeSeat` takes one delivered ballot at a time: the stub and the approved transcript that register the election, the whole ballot record and the seat's `ct_i` (`docs/spec/share-encryption.md`, Intake and receipts). Before it takes any ballot of an election, it checks the election as a verifier does before admitting ballots, and keeps only a pass, since a check that couldn't decide may pass later:

- the seat approved the stub, and the transcript is the one it approved; the transcript's check still returns the key set its approval signed, with its own seat in it (3.2; `intake-unapproved`, `intake-transcript`; T-37);
- the stub checks again: the pinned panel, chain and trustee registry (2.5), the profile (2.3), the membership key (1.3) and the electorate through the deployment's `ElectorateCheck` (2.4), against the roots ballots are checked under, since those member counts bound what the seat owes (`intake-definition`; T-52, T-13). A pass is kept per stub, in memory, so an election waiting on its registration doesn't recount the registry's log on every delivery (T-52);
- finalized L2 shows the definition registered over the ceremony the seat approved, with that key set, through the deployment's `RegistrationCheck` (2.1, 3.1's registration part, 3.2; `intake-unregistered`), which must resolve `false` when it can't decide.

`l2RegistrationCheck(options)` is that check over the seat's own L2 node (`src/registration.ts`; [[verifier]], Registration). On the pinned chain (`eth_chainId`), it takes both registries' accumulators and counts proven under one output root at or after both deployment blocks (`l1OutputRootAccumulators`, as the electorate check does), reads each registry's whole log from its own deployment block to the proven block, and requires each to replay to its proven accumulator (`provenLog`), so the L2 node can't hide, invent, alter, reorder or move a log. Of those, the election registry's `DefinitionRegistered` for the election and the trustee registry's `CeremonyRegistered` for the stub and panel, by their leading topics, go to `@abolishus/verifier`'s `registrationCheck` with the key set hash the seat's own transcript check returned: exactly one registration, of the definition the seat checked (its hash recomputed from the logged bytes), and exactly one ceremony record, of the definition's transcript, whose header is that ceremony's and whose key set (from contract-event version 2 on) hashes to the seat's. A registration or ceremony record past the L2 node's finalized block is refused too, since a game may claim an unsafe block. Anything else, no proven root yet, a log that doesn't replay, answers that don't prove, an unreadable node or a node of another chain is a refusal. `run` uses it whenever `availability` is configured, reading `availability.registry` from `availability.registryFromBlock` and the trustee registry the configuration pins from `availability.trusteeRegistryFromBlock`; without `availability` every delivery is refused.

Then crypto's `intakeBallot` runs the admission checks of [[verifier]] 5.1 to 5.4, the membership proof included, and opens the shares, under the ballot version the election pins: version 1 under definition version 1 (`ballotElection`), version 3 under definition version 5 (`questionBallotElection`: the cell the ballot names and each question's range proof); the first failure is the result and nothing is signed or stored. On a pass, the ciphertext, the shares, the tier and the nullifier are written once under `intake/<stub_hash>/<ballot_hash>`, and the L1 reference of each copy delivered under `copies/<stub_hash>/<ballot_hash>/`, before the share receipt record (`0x000b`) is returned, so no receipt names a share the seat doesn't hold, and the decision at `c_I` can rank the copies it receipted even when the operator withholds every other copy (T-25). The same delivery again gets the same receipt (RFC 6979). From the intake cutoff `c_I` by the node's clock (`intakeCutoff` at the release's windows), every intake for the election is refused, a delivery whose checks finish at or after it included (`intake-closed`; [[delivery]], What a node owes; T-54). The clock is read again once the records are durable, and a delivery past `c_I` by then gets no receipt, so every receipt the seat gives was written before the decision reads the store.

## Obligation

`decideObligation` decides what the seat owes for an election once, from `c_I` on by the node's clock ([[delivery]], What a node owes). Its view is every copy the seat receipted (from `intake/` and `copies/`, with `M` recomputed from the ballot hash, tier and the copy's L1 reference), less the ballots it shows absent, together with every copy it holds from the anchored board or the contract's records, which the deployment's `ObligationView` supplies already admission-checked with their entries, along with finalized L1 read through sources the node chose. crypto's `owedReceipts` gives the ballot hashes whose receipts the seat sends through the contract path by `c_D`, and `complaintScope` the ballot hashes it owes complaints about by `c_K`. The decision waits while finalized L1 doesn't reach past `closes_at`, is checked against `2M` (two per member of each tier: anything over it means a copy that skipped admission, and throws rather than being written), and is written once under `obligations/<stub_hash>` before anything is sent from it; every later call returns the written decision, whatever the view says by then, so an operator releasing board data at chosen times can't grow the obligation into the union of several decisions (T-52, T-54, T-25). A view that holds a board copy of a ballot it also shows absent throws: no honest source gives both.

## View

`obligationView(options)` is the `ObligationView` a deployment gives `decideObligation`, read from the seat's own nodes when the seat decides ([[delivery]], What a node owes). Each read checks both nodes' chains and requires the definition the election registry registered in finalized L2 history to be the one the seat approved, of version 1 or 5 and hashed under its own layout (`ViewError`). Its finalized L1 is the header run the verifier reads for 5.8 (`headerRun`): from the last block before `opens_at − L1_REF_MARGIN` to the first after `closes_at`, each block naming the one before it as its parent, so the L1 node is trusted only for which block is finalized, and a run cut by `maxRunBytes` is refused (`l1-run-short`) rather than searched for `l1_ref_min` from inside the window. Its copies come from the ballot extent the seat attested (`AvailabilitySeat.heldExtent`: read again through the same anchors from the blocks the seat pinned before attesting, refused while the L1 node shows another `C_A`, and for good when the pinned blocks no longer hold it, `extent-lost`), each board-path ballot with its segment, and from the board contract's `BallotSubmitted` and `RelayedBallotSubmitted` logs for the definition in the seat's L2 node's finalized history, an ordinary ballot with its L2 block's timestamp and a relayed one with its relay call's stamp; every copy is kept only if the verifier's own admission (`electionAdmission`, 5.1 to 5.4, membership proofs batched) passes it, which needs the ceremony transcript the extent carries. Logs and archived events are read under the contract-event version the definition pins, as the verifier's 4.4 reads them. A receipted ballot is shown absent only when the seat attested the extent, no admitted copy carries it, and no ballot log of the board names it (whether or not it passes the event check; a contract event the board archives is the operator's claim, not the contract's record, so it never counts); and only once the L2 node's finalized history is past the contract-event window's end (`closes_at + W_C`), by when every in-window ballot the contract records is in a block, so a lagging node delays the decision (`RpcError`) rather than hiding a recorded ballot (T-25, T-52, T-54). A seat that didn't attest decides over its own intake alone.

## Receipt duty

`ReceiptDuty` sends what the decision owes ([[delivery]], Direct submit). Once `decideObligation` has decided, it signs the owed receipts as share-receipt batches (crypto's `batchShareReceipts`: sorted by ballot hash, at most `RECEIPT_BATCH_MAX` pairs each), every pair's `share_hash` read from the intake record written before that receipt was given, so a batch states only receipts the seat issued. The batches are written once under `deliveries/<stub_hash>/receipts` before any is sent; a restart, a later view or a later step resends the stored bytes and never signs another set (T-52, T-54). Each step reads, through `ReceiptPath.recorded`, every batch the board recorded for the definition and seat in the seat's own L2 node's finalized history, and sends each stored batch not among them byte for byte through `ReceiptPath.send`, by `c_D = t_D − F`, so a deposit through the portal lands by the delivery deadline `t_D` (T-25). It returns `recorded` once every stored batch is (or when nothing is owed), and from `t_D` on stops sending and reports `unrecorded`, since nothing submitted then delivers. The board takes any number of batches per seat, so another batch of the seat's never counts as one of the stored ones. `boardSender` gives the availability call and the receipt-batch call (`submitReceiptBatch`, with `RECEIPT_CALL_GAS`, the release's figure, as the call's and the deposit's gas limit) over one account and one queue, so the two never take one nonce; `l2RecordedReceiptBatches` reads the board's `ShareReceiptBatchSubmitted` logs for the definition and seat up to the L2 node's finalized block, each through the event check.

`ReceiptDuties` (`src/duties.ts`) runs the duty in a deployment on the availability duty's schedule: each poll it lists the stubs the seat approved, builds each one's `ReceiptDuty` over the deployment's `obligationView` and the board's receipt-batch call, and steps them side by side, from before `c_I` (`open`: nothing is decided until intake closes), until each is `recorded` or `unrecorded`. A node's failure (`RpcError`, `L1Error`, `L2Error`, `SendError`) is retried at the next poll, so a view its nodes can't give yet delays the decision rather than shrinking it; a refusal no retry changes (`ViewError`, `L1AnchorError`) is reported and gives the election up; anything else, a view breaking a rule no honest source breaks among it, ends the loop, as it ends the ceremony's. Each election's status and failure is logged once when it changes (`receipts`, `receipts-error`), never a secret. `run`'s view (`dutyWiring`) reads the attested extent through an `AvailabilitySeat` set up as the availability duty's is, over the same store, reader and blocks, and only for a seat that stored its attestation (`attested`), so a seat that didn't decides over its own intake whatever its L1 reader says.

## Complaint duty

`ComplaintDuty` (`src/complaint.ts`) sends the complaints the decision's scope owes ([[delivery]], What a node owes in complaints). From `t_D + W_C`, by the node's clock and with the seat's own L2 node's finalized history past it (`ComplaintPath.postings` returns that history's last timestamp), every posting submitted by `t_D` is recorded, so the duty decides once: of the postings the board recorded for the definition and seat, it keeps those submitted by `t_D` for a scope ballot the seat didn't receipt (a receipted ballot's shares passed this seat's intake, so a passing posting of it opens again). It reads each such ballot's committed vote from the deployment's ballot source, matched by the ballot hash recomputed from the record, so a source can withhold a ballot but never swap one (T-38), and waits (`waiting-ballots`) rather than decide without one, until `c_K − R`: then it decides without the ballots still withheld, giving up only their complaints, so anyone posting against a ballot a source withholds can't cost the seat every complaint it owes (T-29, T-54). For the first posting of a ballot that passes the public check it opens the shares, and owes a complaint only when they fail decryption or the share check: crypto's `proveComplaint`, which reveals the DH value for nothing else (T-15, T-29). The complaints are signed as share-complaint batches (`batchShareComplaints`, at most `COMPLAINT_BATCH_MAX` each) and written once under `deliveries/<stub_hash>/complaints` before any is sent; a restart or a later posting resends the stored bytes and never signs another set (T-52). Each step sends every stored batch not among `ComplaintPath.recorded` by `c_K = t_K − F`, returns `recorded` once all are (or when nothing is owed), and from `t_K` on stops and reports `unrecorded`. The scope comes from the ballots the seat held at `c_I`, never from postings, so postings against ballots never cast cost the seat only their decoding. `run` gives it the board's paths over the seat's own L2 node: `l2Postings` reads the board's `SharePosted` logs for the definition up to the node's finalized block (the event has no seat topic, so each record's own seat is matched), each through the event check and with its L2 block's timestamp, by which the delivery deadline judges it, and gives that finalized block's timestamp; `l2RecordedComplaintBatches` reads `ShareComplaintBatchSubmitted` for the definition and seat as the receipt batches are read; and `boardSender`'s complaint-batch call (`submitComplaintBatch`, with `COMPLAINT_CALL_GAS`, the release's figure, as the call's and the deposit's gas limit) shares the one account and queue with the other calls. Its ballots come from `complaintBallots`, over the view's own nodes and checks: the ballot records of the extent the seat attested and the board contract's `BallotSubmitted` and `RelayedBallotSubmitted` records that pass the event check, nothing admitted, since the duty matches each by the hash it recomputes; an extent the pinned blocks no longer hold costs only its own ballots, so the duty still decides over the contract's and waits for the rest until `c_K − R`. `ComplaintDuties` steps it on the same schedule as the receipt duty, over the same decision (so the scope is the one stored at `c_I`), until `recorded` or `unrecorded`, logging `complaints` and `complaints-error`, and gives up an election set up past `t_K` only.

## Tally duty

`TallyDuty` (`src/tally.ts`) is the seat's part in [[tally]] (Summed shares, Summed-share message, Combination, Opening record). Before it reads anything of the counted set it asks `TallyDutyOptions.summing`, the summed-share rule (below), and only once that finds both points available does `TallyDutyOptions.counted` give the counted set, cell by cell, once it is fixed (`waiting` until then). `countedSet` (`packages/verifier`; [[verifier]], Counted set from the counted extent) computes it from the counted extent the seat attested, exactly as the verifier later recomputes it, or says which row leaves it undecided. `countedSource` (`src/view.ts`) is the deployment's source over it: the counted extent from the seat's point-2 `AvailabilitySeat.heldExtent` (refused if the seat holds none, or one ending elsewhere than `s_S`), the registered definition from the seat's own L2 node (checked as `obligationView` checks it), the L1 run 5.8 needs from its own L1 node, and the anchoring clock the deployment pins. Before calling `countedSet` it waits for the L2 node's finalized history to pass `t_A'`, then requires every contract-event record of the extent to be one of its contract's logs in the block the record names, with the same topics and data, each log carrying at most one record, under that block's own timestamp; any record failing that is the operator's, never the contract's, and the source refuses (T-35, T-71). An undecided row waits while finalized L1 doesn't yet reach a ballot's reference (5.8 `l1-ref-pending` or `l1-blocks-short`, or `not-reached`) and is refused otherwise (relayed ballots, obligation roots, version-2 batches, an election admitting no ballot), so the seat never sums over a set the verifier wouldn't give. The duty passes a refusal through as its own `refused`. The duty never chooses a set:

- **No summed share before the quorum** ([[availability]], What a seat does; T-54, T-14, T-24). `summingRule` (`src/summing.ts`) waits for `t_A' + R` on the node's clock (`waiting` `wall`), for `C_S` to be fixed on finalized L1 through the counted extent's own reader, which must run under the pinned clock and reach `s_S` (`l1`; `L1AnchorError` `clock` otherwise), and for the seat's own L2 node to have derived a block after `t_A'` (`l2`), so it reads every record that can count and no seat reads more. Then it runs crypto's availability check (verifier 4.6's) over every attestation and complaint the board emitted for the definition, as `l2AvailabilityRecords` reads them from that node's finalized history with each block's timestamp, against `C_A` and `C_S` from that reader (none where the board fails its checks or no counted checkpoint is at or before the point, so nothing counts there), `t_A` and `t_A'`, and the default panel the duty gives it: `k` and every seat's per-election signing key from the transcript it checked against its approval. Fewer than `k` attestations that count at either point is `unavailable`, and the duty never sums: past `t_A'` on the derived head no read shows another record that counts, so the verdict is final, and the duty writes it once (`tally/<stub hash>/unavailable`) so no later read, from a node that lags or lies, makes it sum. A root that is available, named by `q − k + 1` of the panel's `q` seats in counted-extent attestations that count ([[delivery]], Leaf availability), is `unheld-roots`, which the duty reports as `refused`: the seat holds no leaf object, since it fetches none ([[P1-12f]] part 3c), and the rule lets it sum only holding every available root's. A root fewer seats name is withheld and needs no leaves, so one seat naming a root can't stop the others summing. Definition versions 1 and 5, the only ones the node approves, have no author panel.

- **The election is the approved one.** The definition (version 1, or version 5 tagged with its version, `TallyDefinition`) and transcript the deployment gives must hash, each version under its own layout, to the definition the seat approved and the transcript it signed for, and the transcript's check under the pinned panel must return the approved key set with the seat's own keys in it; only that key set's KEM keys get summed shares and only its signing keys open a message (T-37).
- **The counted set is checked before any sum.** One list per cell of the registered partition (under definition version 1 one cell per tier; under version 5 every tier's regional cells, numbered across the definition, [[verifier]] 2.8), each ballot of the election and of that cell, decoding under the ballot version the definition pins (version 1, of the cell's tier; version 3, naming the cell) and matching the election's shape (every question's options, in flat order), with no voter twice: a nullifier is its tier's, so under version 5 one voter in two cells of a tier is refused as in one; the set's aggregate is then written once per cell, so a source that later gives another set is refused for good (`refused`), and nothing is sent for the election (T-14, T-16, T-29).
- **Sums from intake, or from a posting.** Each counted ballot's shares are the ones intake checked and stored under the ballot hash recomputed from the record (T-38). A counted ballot the seat didn't take in at intake (its delivery never came, and the voter posted the seat's ciphertext through the contract path instead) gets its shares from the postings `CountedSet` carries: `countedSource` gives every share posting the counted extent's authenticated `SharePosted` events carry for the definition, and the duty reads only version-1 postings naming its own seat, opens a posted ciphertext only if it hashes to the ballot's share hash for the seat, with the seat's own KEM key, and keeps the shares only if they pass the share check against that ballot's commitments ([[tally]], Destruction, What). The hash fixes the ciphertext, so the posting's `m_i` isn't needed and only the first matching copy is opened: copies posted under other `m_i` and postings that can't match cost no decapsulation (T-52). The hash and the associated data binding the ballot's commitments keep another ballot's ciphertext out (T-38); the share check refuses a dishonest client's bad shares behind a matching hash. Shares opened from a posting are held in memory only, never stored, and opened again whenever the counted set is fixed after a restart, so destruction leaves none on disk (T-14, T-15); shares that fail open are the complaint duty's to prove, never revealed here. The seat's sums must pass its own summed-share check before they are sealed. A seat lacking shares of a counted ballot from both sources sends nothing for that cell (`missing-shares`) but still combines the others' sums.
- **Messages.** Each step seals the seat's sums, with fresh randomness, to every other registered seat through `SummedSharePeers`, the node-to-node channel (hybrid post-quantum TLS, never the board, IPFS or a store that keeps them; T-15), until the seat has signed the cell's opening. `receive` runs crypto's checks on every message (`openSummedShares`, context and signature before decapsulation, T-39) and keeps the sums that pass, in memory; a failing message is ignored and nothing about it goes back to its sender: the receiving node acknowledges every message on arrival, before and whatever `receive` makes of it, so neither its answer nor its timing tells `summed-decrypt` from `summed-check` (T-39). Only `step` reads the counted set; a message that arrives before it has is dropped, and its sender resends.
- **One opening per cell.** Holding passing sums from `k` seats, its own included, the duty combines the `k` lowest (`openCell`, which runs the opening checks on the result), signs the opening as `signer` and writes it once before `openings()` hands it out, so a later step, a restart or another message never signs a second (T-29).
- **The board's openings read back** ([[tally]], Destruction, When; T-53, T-24, T-49). Once the counted set is fixed, each step asks `TallyDutyOptions.board` for the board's tally openings and judges them itself: crypto's opening checks (`checkTally`) against the seat's own aggregate of each cell over the set it fixed, never the board's or a server's word. A cell with a passing opening (one of `m` entries over that aggregate that opens every option, attributed or not, since a passing opening is correct whoever combined it) is `published`, with the segment of the first one in board order; the seat sends and signs nothing more for it, and keeps it published whatever a later read says, since an anchored entry never leaves the board. An opening over another set, one that doesn't open an option, a stray or an undecodable one publishes nothing. `boardOpenings` (`src/openings.ts`) is the deployment's reader: through the election's L1 reader up to `s_T` (`l1BoardAnchors` with `tally`), it reads the board through the latest counted checkpoint finalized L1 shows, by the CIDs the checkpoints name, from the seat's directory and then the gateways, checks the copy against the anchors (`verifyBoard`), and gives every tally-opening payload with its segment, in board order: each is included under a checkpoint the seat read anchored on its own finalized L1. A copy that can't be read from those sources yet (or nothing anchored) is `unread`; a board failing a check no later read settles is reported by its code, and none of its openings count. It reads the board again only when the counted checkpoints change (a later one, or a late timely one for an earlier segment). A read that fails (a node down, a reader that can't be set up) is `unread`: the seat still sends its sums and combines that step, so the read never holds up the tally (T-54). The step's status carries the read (`board`: `read`, `unread`, or the failing check's code).

`TallyDuties` (`src/duties.ts`) runs the duty in a deployment on the other duties' schedule: each poll it lists the stubs the seat approved and builds each one's `TallyDuty` over the definition registered on the seat's own L2 node (`tallyDefinition`, `src/view.ts`, read and checked as the view's is), the transcript the seat's approval signed for (`CeremonySeat.approvedTranscript`: the seat writes its own copy at approval, before it signs, so the tally never takes the transcript from the operator's board), `summingRule` over the counted extent's L1 reader and the board's availability records (`l2AvailabilityRecords`), and `countedSource` over the counted extent the seat attested at point 2 (`dutyWiring`'s `counted`: none for a seat that stored no point-2 attestation, without asking its nodes). It steps each one until every cell is `published`, the election is `unavailable`, the seat refuses its counted set, or `t_D` (`tallyDeadline`: the later of `t_S + TALLY_WINDOW` and the anchoring deadline of segment `s_T − 1`, under the pinned clock) is behind the node's clock, past which the seat may combine nothing more ([[tally]], Destruction): no step begins past it and no duty is set up, so a node restarted then signs and sends nothing. A refusal settles the election for good until the node restarts: it is the operator's to look into, and stepping on could only sum over a set the seat already refused (T-54). An approval from before the seat kept its transcript gives its election up (`tally-error`, `ViewError` `transcript`). A node's failure is retried each poll and a refusal for good gives the election up, as for the other duties; events are `tally` (each election's status when it changes, cells included) and `tally-error`. `TallyDuties.receive` hands each summed-share message to every election's duty built and not settled, in turn: each runs crypto's checks, and a message of another election fails at its context, so no step reads a message's bytes to route it (T-39). `run` serves the channel (`serveSummedShares`) with `TallyDuties.receive` behind it and sends through `httpPeers` over the configured endpoints.

**Sending the openings** ([[tally]], Opening record, Boarding; Destruction, When; T-54, T-53). `OpeningSender` (`src/opening-sender.ts`) sends each opening the duty signed and stored (`signedOpenings`) to the operator's `POST /openings` through `HttpOperator` (`src/operator.ts`), and sends it again until the seat's own read of the anchored board (the tally duty's `published` cells, `publishedOf`) shows a passing opening of its cell, or the seal's tally term: a trustee keeps every opening it signed and resends it until the seal, so an operator that withholds openings until the tally window ends can't make the seats destroy what would combine new ones while a cell is still off the board. `OpeningSends` (`src/duties.ts`) steps each election's sender on the other duties' schedule until every cell is published or `openingsDeadline` (`t_D + DESTRUCTION_WINDOW`, the seal's tally term: no seal is derived from a definition yet, and every seal is at or after it) has passed; no step begins past it, and no sender is set up, so openings are still sent past `t_D`, when the tally duty itself has stopped. The operator's answer is a claim and only paces the sending: a `201` whose entry, decoded under the pinned board-entry version, carries the opening's bytes (or, with `earlier`, a version-1 tally opening over the same signed message) is `boarded`, and a `422` refusal `rejected` with the Boarding rule's code; either waits `RESEND_AFTER` (600 s, the operator's own lapse for a refusal resting on one anchor read) before the cell is sent again. An entry that doesn't carry it is `misanswered` and sent again the next step. `not-ready`, `not-open` (`409`/`404`) and `unavailable` (anything else, a timeout or an unreachable operator included) end the step's sending after that one request, so a stalled operator costs one request per election and step (T-52); each step starts one cell further on, so a cell the operator keeps failing on its own holds no other back. `PublishedReads` keeps what each election's tally step last read published, which the sender reads. So an operator that lies can delay the next send to `RESEND_AFTER`, never stop it. The request carries the election's id and the opening, both public once boarded, and no credential; a redirect is refused, and an answer past `MAX_ANSWER` (64 KiB) is read as `unavailable` (T-10). Events are `openings` (`none`, `complete`, or `sending` with each cell's state) and `openings-error`.

Summed shares and received messages are never written to the store: they are recomputed, or resent by their senders, after a restart, and are among what destruction removes. They live only in the `TallyDuty` instance, so destruction drops the instance, and the transport's buffers, rather than zeroing values the runtime can't zero.

## Destruction

([[tally]], Destruction; T-14, T-40, T-69.) `DestructionDuty` (`src/destruction.ts`) destroys an election's material at the earlier of two moments, both read as the spec reads them and never on the node's clock: every cell `published` by the tally duty's own read of the anchored board (`PublishedReads`, each opening checked against the seat's own aggregate under a counted checkpoint its own finalized L1 node shows anchored), or the time of the finalized L1 block its own L1 node gives at or past `t_D` (`tallyDeadline`). A clock running fast destroys nothing early; an L1 node that lags or is down destroys late, never early, and the duty keeps stepping past `t_D` until it has destroyed. Without `availability.tally` there is no board read, and the seat destroys at `t_D`.

`CeremonySeat.destroy` (`src/ceremony.ts`) does the destroying, in an order a crash can't break: first a write-once `destroying/<stub hash>` record, after which `approvedElection`, `intakeSecrets` and `withSecrets` hand out nothing and the schedule drops, unstepped, every duty of the election that reads a secret (the tally duty with its summed shares and received messages among them, and any duty whose step destruction overtook); then a wait for every use of the secrets already begun (`withSecrets`: intake reads them per delivery inside one, opening, storing and signing there, and keeps none in its cache), so nothing is written or signed with them once anything is removed and no removed intake record is written again; then every ballot's record from intake (its share ciphertext and the shares opened from it); then the statement (`0x000f`, version 1, the version tally-opening version 1 fixes, which the seat signs), signed once and recorded under `destruction/<stub hash>`; then the approved run's secrets record, which holds the KEM secret and the signing key together, so the statement is the signing key's last use. The KEM secret goes after the signing rather than before it, which nothing outside the node can tell, since `destroy` returns the statement only once both are gone: whatever sends it must take it from `destroy`, or from `destructionStatement`, which reads it only once the secrets record is gone, never from its record alone, which a crash can leave beside the secrets until the next call. The secrets record is read with a plain `get`, never the `putOnce` that makes other records durable on read, so a read in flight can't put it back. A later call repeats whichever step a crash cut short and returns the same statement bytes. The signed openings, the transcript, the approval and every other public record are kept, and `OpeningSends` and `DestructionDuties` read the election without its secrets (`approvedElectionInfo`), so openings are still sent until the seal's tally term. `SeatStore.remove` is the store's only removal, used only here, and only on records no duty writes again once `destroying` exists.

`DestructionDuties` (`src/duties.ts`), built by `destructionDuties` (`src/destruction.ts`) over the seat without secrets, so the `destroying` record never drops it and a destruction a crash cut short is finished on the next step, steps each approved election's duty until it reports `destroyed`; `run` steps it in turn with `TallyDuties` (`runInTurn`), destruction first, so no tally step is reading the secrets as they go and the tally duty destruction ends is dropped in the same round. The receipt, complaint and availability duties run in their own loops: their deadlines (`t_D` of delivery, `t_K`, `t_A'`) all come before the counted set the first moment rests on and before `t_D`, and each drops an election as soon as `destroying` holds.

**Sending the statement** ([[tally]], Destruction, What; Destruction window; T-14, T-54). `StatementSender` (`src/statement-sender.ts`) sends the statement `CeremonySeat.destructionStatement` holds, once destruction has finished, to the operator's `POST /destructions` through `HttpOperator.submitDestruction` (the same `availability.tally.operator`), and sends it again until `t_D + DESTRUCTION_WINDOW` (`openingsDeadline`), by when a statement must be on the board. The tally duty that reads the board is gone by then, so the seat can't read its statement boarded: the operator's answer only paces the sending, as for openings. An entry that, decoded under the pinned board-entry version, carries the statement's bytes (or, `earlier`, a version-1 statement over the same signed message) is `boarded`, a refusal `rejected` with the Boarding rule's code, and either waits `RESEND_AFTER` (600 s); an entry that doesn't carry it is `misanswered`, and `not-ready`, `not-open` and `unavailable` are sent again next step. Resending after `boarded` covers an operator that answered an entry it never anchored, at one request per 10 minutes for a day. Under a board-entry version that doesn't allow `0x000f` the sender reports `unboardable` and settles. `StatementSends` (`src/duties.ts`) steps each approved election's sender over the seat without secrets (`afterDestruction`), with no step begun nor sender set up past the window's end; `run` runs it in its own loop beside destruction, since `destructionStatement` only reads (T-52, T-53, T-10).

## Intake endpoint

`serveIntake(intake, options)` serves an `IntakeSeat` at `POST /v1/intake`: what clients reach through a network anonymiser when the operator's route fails, and what the operator's relay delivers through ([[delivery]], Client rules 4; T-11).

| Request          | Body                                                                                                                                                               | Answers                                                                                                                                                                         |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST v1/intake` | `{stub: bytes, transcript: bytes, record: bytes, ciphertext: bytes}` (`application/octet-stream`): the stub, the approved transcript, the ballot record and `ct_i` | 200: the share receipt record (`0x000b`); 422: the refusal's code as text; 400 an envelope with no decoding; 413 past `MAX_DELIVERY`; 503 the queue is full, with `Retry-After` |

The body is this transport's envelope in [[notation]]'s encoding (each `bytes` is `bytes<2^20>`, so `MAX_DELIVERY` is 4 MiB and 16 bytes), not a protocol record. Every answer allows any origin (`access-control-allow-origin: *`, and a preflight for `content-type`): the delivery carries no credential and the receipt is public, so a browser's ballot client may post from wherever it is served. What the endpoint bounds (T-39, T-52):

- **The body**: a declared length past `MAX_DELIVERY` is refused before any of it is read, and a streamed one once it passes it.
- **The deliveries held at once** (`queue`): each is counted from its headers to its answer, so at most `queue` bodies are in memory; past it the endpoint answers 503 without reading the body. `intakeBallot` is synchronous work, so the seat checks one delivery at a time.
- **The connections**: 10 seconds for the headers and 30 for the whole request, enforced each second, and at most `CONNECTIONS_PER_PLACE` (4) open connections per queue place. A peer that sends slowly still holds a place for up to about 31 seconds, so a few such peers can keep members' deliveries at 503 while they keep reconnecting (liveness only, T-54). An upload its peer abandons frees its place and logs nothing.

With `tls` it serves HTTPS, TLS 1.3 only, with the hybrid post-quantum group `X25519MLKEM768` and nothing else ([[0002-everlasting-privacy]], Consequences: every intake endpoint negotiates it, since a share ciphertext recorded in transit is exposed to a later quantum break of the KEM). Without it the endpoint takes plain HTTP only on a loopback address, for a TLS proxy on the same host that must hold to the same group. A seat that throws is answered 500 and logged by the error's name only, never a body, a ballot or an address.

## Summed-share channel

`serveSummedShares(receive, options)` (`src/channel.ts`) is where a seat's node takes the other seats' summed-share messages ([[tally]], Summed-share message), and `httpPeers(options)` the `SummedSharePeers` it sends its own through. Neither keeps a message: the endpoint hands it to `receive` (the elections' `TallyDuty.receive`) and drops it, and a send holds it only until it is answered ([[0015-tally-publication]]; T-15).

| Request                 | Body                                                                            | Answers                                                                                                                                  |
| ----------------------- | ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `POST v1/summed-shares` | one summed-share message (`0x000b`, version 1 or 2), `application/octet-stream` | 202 once the body is read in full, whatever the seat makes of it; 413 past `MAX_SUMMED_SHARE`; 503 the queue is full, with `Retry-After` |

The body is the spec's record itself, with no envelope; every check on it is the seat's. The endpoint answers 202 as soon as it holds the whole body, before `receive` runs, so the answer is the same for a message that passes and one that fails any check (Receiving, Notes; T-39); how long the check takes is not hidden (Known-weak). It bounds what a message costs as the intake endpoint does (T-52): a body past `MAX_SUMMED_SHARE` (version 2's fields at `MAX_OPTIONS`, 5,375 bytes) declared or streamed, `queue` messages held from their headers until `receive` has finished with them, checked one at a time, 10 seconds for the headers and 30 for the request, and `CONNECTIONS_PER_PLACE` open connections per place. A `receive` that throws is logged by the error's name only. It answers no browser: no CORS header, and every answer `cache-control: no-store`.

With `tls` it serves HTTPS, TLS 1.3 only, with the hybrid post-quantum group `X25519MLKEM768` and nothing else, as the spec requires of this channel; without it, plain HTTP only on a loopback address, for a TLS proxy on the same host that holds to the same group. `httpPeers` holds the sending side to the same: each other seat's endpoint by seat index, `https:` (or `http:` only on loopback), TLS 1.3 offering only `X25519MLKEM768`, the peers' certificates checked against `ca` when given and the system's roots otherwise. A send resolves on 202, which says only that the message arrived; any other answer, a refused connection or TLS handshake, no answer within `timeoutMs`, or a seat with no endpoint throws `PeerError`, naming the seat and a status or error code, never an address, and the tally duty sends again at its next step.

The channel authenticates no sender: a summed-share message is signed by its sender's per-election key and checked by the seat before it decapsulates anything, so anyone may post one and only a registered seat's makes the seat do more than verify a signature (T-39).

## Configuration and commands

`vp run --filter @abolishus/trustee-node start -- <command>`:

- `keygen --out <file>`: a fresh identity key in a new owner-only file (never over an existing one); it prints only the public key, for the panel's registration.
- `run --config <file>`: one seat's node. The JSON file pins `panel` (`threshold` and the identity keys as hex), its `panelId` (compared with the panel's computed identifier, so a mistyped key fails), `l2ChainId`, `trusteeRegistry`, `seat`, `identityKeyFile` (64 hex digits in a file only its owner can reach, never read through a symbolic link, and refused unless its key is the seat's), `store` (the `FileStore` root), `coordinator` and `pollSeconds`. It logs one JSON event per line, never a secret.
- With an `availability` object, `run` also runs the availability duty and the receipt duty, polling at `pollSeconds`: `l1` and `l2` (the nodes' URLs, never printed), `l1ChainId`, `anchor`, `anchorFromBlock` and `anchorClock` (`epoch`, `period` and `deadline` as decimal strings), `registry` and `registryFromBlock`, `trusteeRegistryFromBlock` (the pinned trustee registry's deployment block), `board` and `boardFromBlock`, `portal`, `accountKeyFile` (the paying account's secp256k1 key, held as the identity key is), `l1MaxFeePerGas` and `l2MaxFeePerGas` (wei, as decimal strings), `forceAfterSeconds`, `forceLeadSeconds` and `sendMarginSeconds`, `maxBoardBytes` (default 2³⁰), `gateways` (up to 16 trustless gateways, optional), `blocks` (a directory of CAR files, read at start and asked first, where the seat pins what it attests as `<cid>.car`) and `serve` (`port`, and `host`, loopback by default), where the node serves that directory, with everything pinned since, as an IPFS trustless gateway (`apps/node`'s `gateway`: raw blocks only, no request logged). `servedBlocks` (`src/served.ts`) is that directory: `apps/node`'s mirror, and each object pinned, written by `pinObject` and served at once. The account key must not be the identity key. At start it checks both nodes' chains and the contracts' code: a mismatch, or an address it can't listen on, exits 2, a node that can't be read exits 1. One sender serves every election and both duties, since the account is one.
- With `availability.groupRegistry`, `run` checks each stub's electorate (Electorate check): `address` and `fromBlock` (the registry's deployment block, a decimal string), `registrars` (2 to 16 addresses as hex, in strictly ascending order, as the deployment record and the registry's `RegistrarsPinned` list them) and `threshold` (2 to the number of registrars). Without it the node refuses every stub with `stub-electorate`.
- With `availability.tally`, `run` also runs the tally duty and serves the summed-share channel: `host`, `port`, `queue` (default 16) and, for HTTPS, `tlsCertFile` and `tlsKeyFile`, as the intake endpoint's (plain HTTP on loopback only); `peers`, each other seat's channel URL (`https://…/v1/summed-shares`, or `http:` on loopback) by its seat index as a decimal string, never the seat's own; `caFile`, the CA (PEM) the peers' certificates chain to, in place of the system's roots; `timeoutSeconds` (default 30) for one send, to a peer or the operator; and `operator`, the board operator's API base URL (`https:`, or `http:` on loopback, no credentials, query or fragment), which the seat's openings and destruction statements are sent to (Tally duty, Sending the openings; Destruction, Sending the statement). A peer URL that isn't a URL or isn't `https:` off loopback, or a CA file that can't be read, exits 2. The `summed-shares` event carries the channel's URL. A seat the configuration names no endpoint for is counted unsent at every step.
- With an `intake` object, `run` also serves the intake endpoint: `host`, `port`, `queue` (default 16) and, for HTTPS, `tlsCertFile` and `tlsKeyFile` (PEM; the key held as the identity key is). Without the TLS files `host` must be a loopback address. The `started` event carries the endpoint's URL. It refuses every delivery of a stub the seat didn't approve (`intake-unapproved`), and, without `availability` or until the seat's L2 node shows the definition registered, every delivery of one it did (`intake-unregistered`).
- `run-env --data <dir>`: `run` for a host that gives the seat only variables and a persistent volume at `<dir>` (`src/env-seat.ts`; staging's seats on Railway, [[trustee-node]], Staging on Railway). `TRUSTEE_CONFIG` is `run`'s JSON without `identityKeyFile` or `store`, which become `<dir>/identity.key` and `<dir>/store`; `TRUSTEE_IDENTITY_KEY` is the key file's contents as `keygen` writes them, optional once a key is on the volume. The configuration and the key are checked as `run` checks them before anything is written; the key is then written owner-only (a synced pending file linked to its name) only if no key is there, and a different key than the one there, a key whose store is gone (the store's directory is made before the key) or a `<dir>` that doesn't exist is refused (exit 2). Both variables are unset once read and never printed. The image (`Dockerfile`, the bundle `vp pack` builds into `dist/main.mjs`) runs `run-env --data /data` by default.
- `local-ceremony [--seats n] [--threshold k] [--dir path]`: a whole ceremony between `n` local nodes and a local coordinator (`LocalCoordinator`, on loopback HTTP), with a panel and a stub made up for the run and no chain: the electorate check passes.

## Known-weak

- **The electorate check is worth the output root it is proven under.** The seat's L2 node is trusted for nothing but availability, but the L1 node's `eth_call` answers about the portal, the factory and the games are taken as given, as for the worker's registry sync ([[P3-5]] part 3b): not yet proven against the finalized state (a game's root claim and block are immutables in its code, which an account proof reaches through the code hash). An unresolved game is its proposer's word until it resolves, and a game the guardian has blacklisted or retired in the anchor state registry is still taken, as the worker takes it: a false root a colluding L2 node proves could pass an overstated stub (T-71). A claim the seat's L2 node doesn't prove (a false root, a block far ahead) is passed over for the next highest, so it can't stop the check. The L2 node must serve proofs at the game's block, usually thousands of blocks behind its head, so it must keep historical state (an archive node); one that keeps only recent state refuses every stub. The game read and proof are repeated for every stub check, about 70 `eth_call`s (T-52). Intake keeps a stub's pass in memory, so a restarted node recounts once per stub, and a stub refused at intake (a node that couldn't be read, or no root posted past its block yet, which takes the L2's proposal interval) is recounted at its next delivery, bounded only by the intake queue (T-52, T-54). It reads every log of the registry from its deployment block in one request for every stub check, and the time of each block whose logs the node gives without one, a log anyone can grow with self-paid additions, so a provider may refuse it past its range or answer-size limits (64 MiB): a refusal, not a pass, which would refuse every stub until the read is paged (T-52). The registration check (Intake) still trusts the L2 node for which registry logs exist. Tier 1 and Tier 2 tiers are refused, since the node doesn't run [[vouching]]'s count.
- **The registration check trusts the seat's L2 node for which logs exist.** Hiding the registration or the ceremony record only makes the seat refuse, and the registries never log a second of either. Until the logs are proven under an output root (part 3c), a node that invents both records for the definition and key set the seat approved can make it take that election's ballots before, or without, its registration, never those of a substituted definition or key set (T-71). Both logs are read in one request each from the election registry's deployment block, unpaged but filtered by their indexed topics, so each answers at most the election's one log and its stub's; a provider capping `eth_getLogs`' block range would refuse every delivery once the chain outgrows it, until the read is paged (T-52). Definition versions 1 and 5 (ballot versions 1 and 3) are taken in; every poll the website creates is version 5. A definition with an author panel is never one the node approves (`stub-version`), and the check leaves one unverifiable (`author-panel`).
- **Intake storage isn't bounded per member.** The receipt obligation is (two per tier and nullifier), but every distinct ballot a member delivers (each re-vote, or a core sealed again) is stored, so one member can grow a seat's store. A per-member cap was built and dropped before merging: intake doesn't check the L1 reference, so a coercer who once holds a member's device can make ballots ahead and spend any allowance just as it opens, and then the member's own later re-vote, which selection would pick, gets no receipt anywhere and counts nothing unless posted (T-45). A bound that keeps re-voting open needs the node's view of the L1 head, so it waits on part 4b-2, where the node reads L1. Each repeated delivery of a held ballot runs every check again, decapsulation included.
- **No limit per network address.** The endpoint is reached through anonymisers and the operator's relay, so an address says nothing; non-members cost the seat only the checks before the membership proof and the proof itself, bounded by the queue. A flood of them fills the queue and delays members' deliveries (503 and a retry), which costs liveness only (T-54). The queue is one process's: a seat that needs more runs more CPU, not more processes over one store.
- **TLS is the node's or the proxy's.** The endpoint refuses classical key exchange, so a client without `X25519MLKEM768` (older browsers) can't reach it directly and falls back to the operator's route; the proxy case relies on the trustee configuring it the same way. Nothing pins the endpoint's certificate beyond the Web PKI: an endpoint that isn't the seat's gets the ballot record and the voter's address, never a usable share or a receipt that verifies (T-11).
- **The node's own clock closes intake.** A clock running fast closes it early (clients retry another route, [[delivery]], Client rules); one running slow keeps it open past `c_I`, whose deliveries the single decision then counts: the decision runs by the same clock, so it can't miss a receipt the node gave, but a seat whose clock is slow owes receipts other seats' views may not hold. A clock stepped backwards across `c_I` while the decision runs could let a receipt leave after the store was read.
- **Identity key from a file only.** The key sits unencrypted in an owner-only file; a hardware token needs `@abolishus/crypto`'s ceremony functions to take a signer instead of a secret key.
- **The coordinator's side is local only.** `LocalCoordinator` relays one ceremony for `local-ceremony` and the tests; the creator's coordinator, and starting a new run after a failed one, come with the services that run elections. The node doesn't tell the coordinator why it refused a request; the reason is in its own log.
- **The transport isn't in `docs/spec/`.** The envelopes above are fixed only by this README and the code; a second node implementation (rule 6) needs them specified. Nothing in them is permanent, so changing them later costs a coordinator and node release, not a protocol version.
- **The availability duty serves what it attested over HTTP only.** Announcing the blocks on IPFS's DHT is for an IPFS node the operator points at the directory, and it serves every reader alike, other seats not first. It doesn't follow the board while the poll runs: it reads the whole extent once `C_A` is fixed, from the gateways and the directory. Everything served is held in memory, as `apps/node`'s mirror holds it. Elections are stepped side by side, but each poll waits for its slowest step, so an election whose sources are slow (each gateway request may take its timeout) delays the others' next step by as long.
- **The L1 reader trusts its nodes for some inputs.** The L1 node for which block is finalized (no light client yet, as for the verifier, P1-19); the seat's L2 node for the drift between the creation and its L1 origin, which the verifier's 4.4 bounds from the archived event's L2 time and a log read doesn't carry: within the drift a sequencer can name an earlier real block, lowering `f` by at most a period, which lets an anchor made before the election existed count and fails the board checks (no attestation), never makes the seat attest another board. Each read asks for the election's anchor logs from the anchor's deployment block and a proof of every segment from `f` to `s_A`, one slot per period the poll runs (168 for a week of hourly periods); the counted extent's reader proves through `s_S`, about 134 slots more with hourly periods and the deployed windows.
- **The sender's fees are capped, not raised.** A transaction pays the deployment's cap at most, so a base fee above it leaves the L2 call waiting (then deposited) and the deposit waiting on L1, past `c_I` if the spike lasts; the cap is the operator's trade-off between that and what the account may spend. The signed transactions are held in memory, so a restart signs them again at new nonces, and a record already in a block is sent once more, at the account's cost. The portal is the deployment's pin: the node can't check from L1 that it is the L2's portal. A pending transaction's tip isn't raised, and two senders sharing one account would take one nonce, so a deployment builds one per account.
- **No roots at the counted extent.** A counted-extent attestation names no roots, so elections that commit roots stay refused until the node fetches leaf objects ([[P1-12f]] part 3c), and the tally refuses to sum (`unheld-roots`) where an attestation that counts names one. The counted duty reads the whole extent once `C_S` is fixed, as the ballot extent's does, though most of it is the ballot extent the seat already pinned; it doesn't reuse that copy.
- **Stricter than the spec on a broken board.** The spec has a seat attest a copy that passes the board checks' steps 1 to 3 and `checkpoint-cid`; `verifyBoard` checks the entries (step 4) and boundaries before the CIDs, so a board failing those gets no attestation. 4.2 fails such an election anyway.
- **The decision trusts its view's source.** `obligationView` reads the board through the extent the seat attested, which closes before `c_I`, but the contract's records as the seat's L2 node shows them when the seat decides, so a relayed ballot whose deposit lands after `c_I` but before the decision is in the view, and one landing after the decision isn't; the decision can't tell when a copy was learned. The `2M` check catches copies of non-members, not an honest member's ballot passed in late. A node that is down at `c_I` decides when it comes back, over the view it holds then.
- **Some failures stop the decision rather than narrow it.** A poll whose L1 window takes more than `maxRunBytes` of headers (64 MiB, about two weeks) is refused for good (`l1-run-short`), and so is an attested extent the pinned blocks no longer hold (`extent-lost`); an L1 node that keeps showing another `C_A` fails every attempt. `ReceiptDuties` reports the refusal (`receipts-error`) and gives the election up, or keeps reporting the failing read: the seat then never decides or sends a receipt through the contract path, where deciding over its own intake alone would at least send some. The stub check doesn't yet refuse polls longer than the run's budget. One schedule reports each election's failures, but nothing pages the operator: watching the log is the deployment's.
- **A seat that didn't attest the extent sees only its own intake.** Admission needs the ceremony transcript, which only the board carries, so without the attested extent the view holds no board or contract copy and shows nothing absent: the seat owes its newest receipted ballot of each (`tier`, `ν`), and if the operator withheld a newer one from the board, the older counted ballot lacks this seat's receipt, the residual of [[delivery]] (Residuals).
- **The contract's ballots are the L2 node's word.** The seat's own L2 node is trusted for which ballot logs exist, as for the recorded batches; a relayed ballot's window is judged by the stamp its event carries, which the contract checked against the window, not matched against the L1 relay's record as the verifier's 4.5 does (T-53).
- **The complaint duty decides from what its sources show at `t_D + W_C`.** A node down then decides when it comes back, over the postings its L2 node shows by then, which still hold every posting in time. Every posting read is held in memory, and each scope ballot's postings are checked until one passes, so a flood of failing postings against a scope ballot costs an ML-KEM encapsulation and a proof check each (liveness only, bounded by the poster's gas, T-54). It complains only within its scope, not yet, as the spec says it SHOULD as its budget allows, about failing postings of ballots outside it that it can't show absent. Every owed complaint is sent, including one whose proven complaint is anchored already (gas only). The seat's own L2 node is trusted for which postings exist: one that hides a posting in time keeps the seat from complaining about it (T-53), and one that hides a contract ballot leaves its postings waiting until `c_K − R`.
- **Every owed receipt is sent.** The spec lets a seat skip a receipt whose passing receipt is anchored by `c_D`; the duty sends it anyway, since the node doesn't read the board's receipts yet. The board takes the batch beside it, so this costs the account gas, never a wrong verdict. A batch the seat's L2 node hides is resent, a no-op for the board; one it shows that the board never recorded stops the seat resending it, which only the seat's own L2 node can do (T-53). Elections that commit roots aren't sent as roots: the capacity check refuses them until roots can be read ([[P1-12f]]).
- **The tally's openings reach the board only through the operator.** `run` sends each opening the seat signs to the operator's route until it reads the cell published or the seal's tally term; an operator that never boards them keeps the result off the board, and the election fails `tally-missing` at the seal (T-54): no contract path takes a tally opening yet. Which cells are published is kept in memory, so after a restart past `t_D`, when the tally duty no longer reads the board, the seat resends every opening it signed until the seal's tally term. `openingsDeadline` stands in for the seal, which no code derives from a definition yet: the seal is the end of the period containing the latest window's end, so the seat stops at the tally term itself, by when an opening must be on the board, and if a later window ever ended past it the seat would stop sending before the seal; under a board-entry version without destruction statements the tally term is the tally window's end, and the seat sends a day longer than it needs. Like `t_D`, it is read on the node's clock, so a clock running fast stops the sending early (liveness only, T-54). The sender is set up only once the seat's own L1 and L2 nodes give the definition's pinned board-entry version (`l1BoardAnchors`), so while they are down no opening is sent. Each changed checkpoint makes the seat read the whole board through it again, its ballots included, within `maxBoardBytes`; a board larger than that is `unread` for good, so the seat steps until `t_D`. The reader proves every segment from `f` to `s_T`, a week of periods more than the counted extent's. Published cells are kept in memory, so a restart reads the board again before it stops sending. No seat sums in practice either, since none approves a stub until the electorate check (part 3). A seat that didn't attest the counted extent never sums, though `k` others can. `t_D` is computed here (`tallyDeadline`), outside the `crypto-review` gate and with no vector, and read on the node's clock, while destruction must act on it only once finalized L1 shows it: part 5c-2 moves it into `packages/crypto` with `s_T` and `t_D` in `tally-window.json`; destruction reads it against finalized L1 (part 5c-1), but the tally duty still stops by the node's clock, so a clock running fast stops the seat combining early (liveness only, T-54). Messages are handed to every unsettled election's duty in turn, so each costs a context check per election the seat tallies at once (T-52). The rule trusts the seat's own L2 node for which availability records exist, as every L2 read here does: one hiding attestations makes the seat find the election unavailable and never sum (liveness), and one showing attestations the board never recorded, or recorded after `t_A'` under an earlier block's time, could make it sum over an election that failed, given `k` seats' signed attestations (T-53, T-14). The channel authenticates nodes only by the peers' certificates on the sending side: the endpoint takes a message from anyone, so an unregistered sender can fill its queue and delay the seats' messages, which they resend each step (liveness only, T-52). The check of a summed-share message is synchronous, and its cost depends on where it stops: a failed context or signature costs a signature check, and any message that reaches decapsulation (only a registered seat's signed one does) costs the decapsulation and the whole summed-share check, over every option with its scalars blinded and over placeholder shares when it doesn't decrypt, so a registered seat timing one message from the next one's acknowledgement (or from 503s at a full queue) can't tell `summed-decrypt` from `summed-check` (T-39). It can still tell those from a pass, which stores the sums: the accept or reject bit the spec allows. The costs are equal in curve work, up to the AEAD body and the decode of a message that opens, which only a sender knowing its key can make; they aren't measured, and JavaScript gives no hard constant-time guarantee. A counted ballot neither taken in nor posted for the seat on the counted extent leaves the seat `missing-shares` (the others' sums still let it combine): it can't arise with the seat honest, since the delivery check counts a ballot only with this seat's receipt or a posting for it that passes, and the seat's receipts all come from its intake, unless the store lost a record; a posting that passes but whose shares fail is the complaint the seat owes, which excludes the ballot once it lands in time. Messages received are kept in memory, so a restart waits for the senders' next resend, and a seat resends to every other seat each step until it has signed the opening, with no acknowledgement. A source that gives a well-formed but wrong counted set first fixes that set for the seat: the duty can check the set's form, not that it is the anchored extent's. That breaks privacy as well as the count: sums over a set that differs from the anchored one by a ballot, beside the published opening, let `k − 1` other trustees recover this seat's share of that ballot and open it, so part 5b must derive the set only from the seat's own finalized L1 and L2 nodes through `packages/verifier` (with 2.8), never a served value (T-14, T-16, T-29). A seat stops resending its sums once it has signed its own opening; if every seat that opened a cell then fails before its opening is boarded, the others wait for those seats to come back.
- **Definition versions 1 and 5 at the ceremony, intake, the contract-path duties and the tally.** A version-5 stub (questions over regional cells, the one the website creates) is checked, approved and its version-3 ballots taken in and receipted; versions 3, 4, 6 and 7 are refused (`stub-version`), version 6 until the node reads the author panel's ceremony and version 7 until check 4 can count a rolling electorate. The availability duty's L1 reader, the obligation's view and the complaint duty's ballot source read a registered version-5 definition under its own hash (`electionDefinitionV5Hash`), the view's copies are admitted by the verifier's own admission under ballot version 3, and the complaint duty matches a version-3 record by the ballot hash its cell gives (`ballotHashV3`); version 3's shares, ciphertexts, receipts, postings and complaints are version 1's, so the receipt and complaint duties send the same records. The tally duty takes a version-5 definition (`TallyDefinition`): it sums and opens each regional cell over its version-3 ballots, looked up by `ballotHashV3`, and `openCell` checks each question's range on the result (`tally-question-range`). Every duty a seat has for an election now reads version 5, so nothing on the node's side still stops part 3 giving deployments an electorate check that passes a version-5 stub. The `ElectorateCheck` gets the stub with its version (`Stub`): under version 5 it must check every tier's cells against the group registry's regions ([[verifier]] 2.4), which no deployment supplies yet (part 3).
- **The store must never be rolled back or shared.** Every duty rests on records written once. Restoring the store from a backup or snapshot, or running one seat from two hosts with their own stores, lets a coordinator get a second round-4 message, a rejoined run or a second approval. The node can't detect either; the deployment must prevent both ([[trustee-node]] says how).
- **Secrets at rest.** `FileStore` keeps the run's KEM secret, signing key and challenge secrets, and every ballot's shares from intake, in files readable only by their owner, unencrypted, until destruction removes them. Removing a file doesn't overwrite its blocks, so a removed record can still be read from the device by whoever reaches it: an encrypted disk, and a store never backed up, are the deployment's ([[trustee-node]], Store). JavaScript can't zero memory, so the copies a dropped duty held stay until the runtime reuses them. The secrets of runs the seat began but didn't approve are never removed: no ballot's share is encrypted to their KEM keys, and their signing keys signed only those runs' messages. Summed-share messages already queued on the channel when destruction begins stay in memory until dispatched to no duty (ciphertexts under the KEM key just removed). An election whose `t_D` can't be computed (a close before the anchoring clock's epoch, `L1AnchorError`) gives its destruction up, reported once as `destruction-error`, and keeps its material: no duty of it runs either, but its intake may hold shares, so the operator must destroy them by hand.
- **The destruction statement reaches the board only through the operator.** An operator that refuses or withholds it makes the seat `destruction-missing` in 8.5, which fails nothing and can't be told from the seat's silence (T-54). The statement is sent only with `availability.tally`, whose `operator` it goes to: a seat without it destroys at `t_D` and sends nothing. The window's end is read on the node's clock, so a clock running fast stops the sending early (liveness only). The sender is set up only once the seat's own L1 and L2 nodes give the pinned board-entry version, as the openings' is. Version-2 statements (author panels) aren't signed or sent. `t_D` comes from crypto's `destructionMoment`; destruction reads it against finalized L1, the tally duty and both senders against the node's clock.
- **A corrupt record throws.** A record that doesn't decode (a damaged disk, a partial restore) makes the request throw rather than return a typed refusal; the node still acts on nothing.
- **Equivocation evidence.** The node refuses a transcript holding another message of its seat, or another view of a round it signed over, but doesn't yet publish the two messages, which the spec says it SHOULD.
- **Stricter than the spec on approval.** It approves only after sending all four rounds and only when its own seat qualified. The spec requires the transcript to hold every message the node sent and the rounds it signed over; a node that never revealed could otherwise approve a transcript it can't vouch for.
