# T-41: Targeted malicious client

- Area: Client integrity and cast as intended (G-6, G-13)
- Adversary: A-2, A-1, A-7
- Status: **Planned.** Residual: a voter who loads the client from abolish.us without checking its hash trusts whoever serves that domain. Hash-checking in a browser has no good UX; the native app (P5-2) closes this for its users, except that a voter with a recovery backup can still be lured into authenticating with the backup passkey on a malicious web client on the ballot RP ID, which exposes the secret however they vote ([[0017-identity-recovery-backup]]). Under P1-3 (option B), a malicious client can also post an invalid share on the voter's last ballot; the proven complaint can arrive after close, too late to re-vote, so that vote is nullified.

## Threat

Whoever serves the JavaScript serves a modified ballot client to one voter.

## Mitigation

The ballot client is a reproducible, signed, hash-addressed static build pinned to IPFS (P2-8, P0-3); the verifier checks a served client against a signed release (P1-19); `abolishus.eth` and a second domain serve the same hash (P4-4).

## History

- 2026-10-11 (P1-13): a ballot's L1 reference and membership message are made after the cast-or-challenge choice, so Benaloh doesn't audit them; the voter's receipt check must show the ballot's admission verdict and whether it is selected ([[revoting]], Owned elsewhere).
- 2026-10-11 (P2-6 part 1): [[0017-identity-recovery-backup]] widens this threat's reach. Whoever serves the ballot client's RP ID can read a voter's secret from the recovery backup on any device the backup passkey syncs to, including one where the voter never ran the ballot client, once the voter authenticates there; and a served `/.well-known/webauthn` that differs from the signed release could let another origin ask for the PRF. The RP ID's well-known and associated-domain files are part of the signed release and P1-19's served-client check covers them.
- 2026-10-11 (P1-12, part 2): a client that posts an invalid share is caught by a trustee's complaint, a Chaum–Pedersen proof of the DH value anyone checks. Only the client that made a ciphertext, or the trustee it is for, knows the `m` that makes its posting pass ([[share-encryption]], Public posting), a failing posting is ignored, and a trustee can't exclude a ballot without a proof ([[share-encryption]], Complaints).
- 2026-10-12 (P2-8 part 1): the ballot client is a reproducible static build with relative URLs, so one set of bytes serves at any path. It refuses to run on an IPFS path gateway (`/ipfs/<cid>/`), where every CID shares one origin and another CID's page could read the client and its randomness; entry points must be origins dedicated to the client (P4-4). Signing and publishing the release hash are still to come.
- 2026-10-12 (P2-8 part 2a): `checkElectionToShow` refuses display text that doesn't match the commitment of a definition whose hash the caller read from the L2 registry, so whoever serves the records can't relabel the options for one voter, not even by serving a forged definition with them (shown in Chromium with two labels swapped, and with a definition the registry doesn't hold). The ballot page doesn't read the registry yet (P2-8 part 2b), and until it does, nothing in it calls the check. Confusable or bidirectional characters in labels aren't screened.
- 2026-10-12 (P1-12 part 3a): a trustee signs a share receipt only after the ballot's validity checks, a check that the ciphertext is the one the ballot names for its seat, and its own decryption and share check, and the receipt signs the ballot hash, so a client can't collect receipts for one public part and publish another ([[share-encryption]], Intake and receipts). A receipt says nothing about eligibility. Which record carries receipts to the board, and the delivery deadline, are part 3b's.
- 2026-10-12 (P1-12 part 3b, [[delivery]]): receipts and complaints reach the board as their own records (`0x000c` and `0x000e`, under board-entry version 3) or as contract events, and postings (`0x000d`) only as contract events, each keyed by the ballot hash and seat. A selected ballot counts only if every qualified seat has a passing receipt or contract-path posting sent by the delivery deadline (two days after `closes_at + l1_inclusion_bound`) and no complaint about it, sent within the complaint window (five days), is proven; the verdict doesn't depend on the records' order. A receipt that passes for a seat whose complaint is proven is reported against that seat. `checkDelivery` implements it, with vectors from an independent implementation. The cheating-client residual stands: a proven complaint after the close can't be answered by a re-vote. The ballot client (P2-8) must check every receipt against the ballot it casts, never post a seat whose receipt passes, and keep resubmitting its receipts through every path until one is anchored or recorded by the contract (derivable from finalized L1), while trustee nodes send theirs through the contract path, so a trustee that receipts and never boards, or an operator that refuses the client's copy, can't drop the ballot alone; a seat that isn't receipted is posted only at the voter's explicit choice ([[delivery]], Client rules).
- 2026-10-12 (P4-4 part 1, [[0020-entry-points]]): the client runs only at origins dedicated to it: the second domain (also the ballot RP ID), `abolishus.eth` through a gateway that gives the name its own origin, and `apps/node`'s local origin; abolish.us only links to it. The ENS gateway's operator is trusted for the bytes it serves, like any host, and is never listed as a related origin of the RP ID, so it can't ask for a backup's PRF. The `contenthash` is set only to signed releases' CIDs, by a release Safe separate from the anchoring Safe. An expired name re-registered by someone else would serve their client under our listing, so both names are kept at least 5 years from expiry.
- 2026-10-13 (P2-14 part 1a, [[election-definition]], Layout (version 5); [[display-text]], Layout (version 2)): a multi-question poll's definition carries each question's limits and no method label, so the instruction a voter reads is rendered from the values the validity proof checks. Its display text must name exactly the definition's questions, each with exactly its options, with labels distinct within a question and question texts distinct within a translation; the cast-confirmation screen and any challenge checker show every question's chosen labels in every translation, so a swapped label on any question shows up beside the others.
- 2026-10-13 (P2-14 part 2, `packages/crypto`): `checkElectionRecordToShow` shows a version-5 poll only if its version-2 display text matches the definition's commitment and has exactly its questions, each with exactly its options, no repeated label within a question and no repeated question text, so the per-question labels a client shows are the ones the commitment fixes. The released profile check now fails a definition of version 1, 3 or 4 that pins a display-text version other than 1.
- 2026-10-13 (P3-2 part 4b, [[registration]]): the Turnstile challenge page, which runs Cloudflare's script, is on a host that is neither the ballot RP ID nor under it nor under abolish.us, since a page may use any registrable suffix of its host as its RP ID and could otherwise request the backup passkey's PRF output. The ballot client frames it, with only the challenge origin in its `frame-src`, and accepts from it only a token-shaped message from that origin and frame.
- 2026-10-18 (P4-4 part 2a, [[0036-release-record]]): what signs a release is an append-only L1 release registry written only by the release Safe, so every release, a release made for one voter included, is public on L1 in one chain before the verifier's 1.1 or `apps/node` can pass it, and a served client that isn't on the chain, or is revoked, fails 1.1. Sigstore keyless signing stays as CI evidence, not the trust root. A Safe quorum can still publish a bad release, but only in public; an entry point behind an ENS gateway is served without the record's headers.
