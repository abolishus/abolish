# @abolishus/ballot

The ballot client: a static single-page app, the only place a vote is cast. Built reproducibly into `dist/`, which is hash-addressed and served unchanged from `abolishus.eth`, subdomain IPFS gateways, our domains and the Capacitor shell. Internal (AGPL-3.0-only).

## What it holds to

- **No third-party runtime code beyond React, the shadcn/ui runtime and `@abolishus/crypto`'s `@noble/*` libraries**, except snarkjs's and ffjavascript's browser builds in the prover worker alone (owner decisions 2026-10-12 and 2026-10-17, [[0009-membership-proof]] Amendment; T-43, T-55). `tests/bundle.test.ts` builds the app, Web Workers included, and fails if any module in the bundle comes from an npm package outside its allowlist (React, Base UI and its dependencies, `class-variance-authority`, `cn`, `lucide-react`, `@noble/*`), or from workspace code other than this app, `@abolishus/ui` and `@abolishus/crypto`'s build (and `packages/membership-prover/src`, in the prover worker only). The fonts (Oxanium, JetBrains Mono) are bundled, never fetched from a CDN.
- **No analytics** (T-67). The same test fails on any analytics, tracking or error-reporting SDK's markers (PostHog, Google Analytics, Segment, Sentry and others) and on any URL other than a short list of inert strings (XML namespace names, React's error-decoder link, Tailwind's licence comment).
- **A strict CSP** (T-43), in a `<meta>` tag ahead of everything that loads, so it travels with the bytes whoever serves them: scripts, styles, fonts and images from the client's own origin only; no inline code or `eval`, but WebAssembly may compile (`'wasm-unsafe-eval'`, for the prover); `connect-src` listing only the client's own origin (for the prover's key and witness calculator, served from the release), the API's origin and one L2 JSON-RPC origin (staging's today; a release names its own), the last two untrusted and checked against the registry; workers from its own origin only; Trusted Types, so no string becomes markup or script, with one named policy (`ballot-worker`) reserved for the workers' own script URLs (the ballot worker's and the prover worker's); no `<base>` and no form posts. `tests/csp.ts` pins the policy directive by directive. A `<meta>` policy can't set `frame-ancestors`, so framing protection needs a header from the host.
- **Protocol work in a Web Worker** (`src/worker/`). The worker checks an election before the client shows it, with `@abolishus/crypto`'s `checkElectionRecordToShow`, for definition versions 1 and 5 (a poll of questions, each with its own limits): it refuses a definition that doesn't decode, names another election, isn't the one the L2 election registry holds (the page supplies the registered hash) or is ill-formed, and text that doesn't decode, doesn't match the definition's commitment or is ill-formed, every question with exactly its options (T-34, T-41); `src/election.ts` only turns a passed election into what the screens show. Encryption joins it later. The page spawns it through the one Trusted Types policy the CSP allows, `ballot-worker`, which `src/worker-policy.ts` creates when it is evaluated; `main.tsx` imports it first, so it exists before any other module's code runs, and it mints a URL for the worker's own script only. A worker takes no CSP from the page, so on a host that sends no CSP header it would run unrestricted: the page does all I/O, and the build check finds none of a listed set of network and code-loading APIs in the worker's script, a heuristic over its bytes (T-43).
- **Opening a poll from its link** (`src/link.ts`, `src/load.ts`, `src/open.tsx`). A ballot link carries the election in its fragment (`#election=<64 hex digits>`), which the host serving the client and any gateway never see; the API and the RPC do learn which election an address opened, since the page asks them about it. The page reads the definition hash the election registry holds for it with `eth_call` (`definitionHashOf`) at the registry address and chain this build pins (`src/deployment.ts`), at the L2's finalized head, never at the registry a served definition names; then it fetches the definition and display text from the API with no credentials, referrer or redirect, reading each answer only up to the largest record it can carry. The worker checks the four together, and only an election that passed is shown; every other end (no registry pinned, not registered, withheld under moderation, unreachable, a malformed answer, a refused check) is a screen that shows no poll text (T-34, T-41, T-10, T-52). Staging pins no registry until one is deployed, so a staging build opens no poll. Sealing and sending come later: "Send" says that nothing was sent.
- **Membership proofs on the device** (`src/worker/prove.ts`, `src/prover/`, `src/prover-client.ts`, `src/prover-artifacts.ts`; [[membership]], Security notes). The ballot worker builds the witness from the identity secret and the tier's leaves (`membershipProverInput`: the path is built here and checked against the definition's root; the secret's copy is zeroed after), and sends it to a prover worker the page starts for that one proof and terminates after, over a `MessageChannel` the page only hands out, so the page, which supplies the secret, never sees the witness, and snarkjs never shares a realm with the page or the ballot worker. The prover worker runs `@abolishus/membership-prover` (snarkjs, single-threaded) and answers the ballot worker alone; the page hears only its progress, steps done of steps in all, never time. The ballot worker verifies the answer against the signals it computed, re-randomises it from its own CSPRNG and verifies it again (`finishMembershipProof`); a refusal names the check (T-07, T-10, T-12, T-55). The proving key and witness calculator are emitted beside the scripts under names carrying their sha256 (`vite.config.ts`), fetched by the page from its own origin, checked against the pins on every load and kept in Cache Storage, where a copy that fails the check is dropped and fetched again. The prover worker is held to the ballot worker's API ban: the build cuts out fastfile's URL read and ffjavascript's thread pool at their exact text in the pinned versions, and fails if that text changes or the prover worker bundles either file uncut; it also drops the scheme from the link in js-sha3's licence comment, which the URL scan would read as a request (the full notice ships in `third-party-licenses.md`). The proving screen (`src/proving.tsx`) shows the steps the prover reports on a still bar, with no time and no value before the first report, and each refusal in words with the check's name and a retry only where another fetch or another prover could help; nothing in the client asks for a proof yet ([[P2-8]] part 3 wires it into sealing).
- **Relative URLs only** (`base: "./"`), so one build works at any path (T-41, T-49).
- **An origin of its own.** A path gateway (`/ipfs/<cid>/`, `/ipns/<name>/`) puts every CID on one origin, where `'self'` and the same-origin policy admit any other content on the gateway: a page under another CID could open or frame the client, read its document and replace `crypto.getRandomValues`. So the client shows a refusal instead of running on such a path (`src/origin.ts`; T-43, T-41). It is served from origins dedicated to it: our domains, `abolishus.eth`, or a subdomain gateway (`<cid>.ipfs.<gateway>`).
- **Third-party licences** ship as `third-party-licenses.md` beside the bundle, since minification strips React's notice. Vite's licence output sees only the page's build, so `vite.config.ts` appends the notices of snarkjs, ffjavascript and every package their prebuilt bundles inline, at the pinned versions (GPL-3.0, Apache-2.0 and MIT; combined under GPL-3.0 §13, owner-approved).
- **Reproducible**: `dist/` is declared as the build output, and `repro-build` builds it twice and compares every byte.

## Test

- `vp run --filter @abolishus/ballot test`: builds the app and checks the bundle (the worker's script included: its own file, with no network, worker or code-loading API), the CSP and `index.html`, and the path-gateway rule; checks that the entry script creates `ballot-worker` before React's code; checks what the client shows of a checked election (the checks themselves are tested against every vector in `packages/crypto`); checks the page–worker and prover messages and the worker-URL rule; checks the ballot worker's proving against a stand-in prover answering with Semaphore's proofs (`tests/prove.test.ts`) and the artifacts' loading against an in-memory release and cache (`tests/prover-artifacts.test.ts`); and checks the registry read and record fetching against a fake network (`tests/load.test.ts`).
- `vp run --filter @abolishus/ballot test:e2e`: serves the production build and loads it in headless Chromium: it renders with its styles and fonts, with no CSP violation, console error or request to another origin, and the browser refuses an injected script, markup written into an HTML sink, an event-handler attribute, a request to any origin but its own, an image from another origin and a string evaluated as script, and compiles WebAssembly; served under `/ipfs/<cid>/`, it refuses to run; the page already holds `ballot-worker`, so no later code can create it. `tests/worker.e2e.ts` builds a test-only page (`tests/harness/`) under the same CSP that drives the real worker: it checks an election and refuses relabelled text, nothing but the client's own files is requested while it runs, and it opens an election through the real fetch path, with the RPC and API stood in for at their own origins (the worker's script is served with no CSP header, as a gateway would), and no worker can be spawned from a plain string URL. It also proves membership for `membership-prover.json`'s first case through a real prover worker: the proof verifies, progress runs from 0 to 10 of 10 in order, the key and calculator are fetched once and served from the cache after (and fetched again when the cached key is swapped), two proofs differ, and a secret whose leaf is missing is refused before any step. Needs Playwright's Chromium (`vp exec playwright install chromium`).
- `vp run --filter @abolishus/ballot test:storybook`: every screen's story in headless Chromium, its play function, then axe (WCAG 2.2 AA), in both themes.
- `vp run --filter @abolishus/ballot preview`: builds and serves the production client. There is no dev-server script: Vite's development client injects inline styles and a WebSocket that the CSP refuses, and a relaxed development policy would be a second policy to keep from leaking into a release. Use Storybook for working on screens.
