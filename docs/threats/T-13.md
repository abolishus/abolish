# T-13: Anonymity-set narrowing

- Area: Ballot secrecy, unlinkability and privacy (G-3, G-4, G-5, G-12)
- Adversary: A-10, A-2
- Status: **Partial by design.** Residual: the paymaster links an account (or IP) to an identity commitment at registration; with T-20 and T-11 that is a path to linkage, so sponsorship must not require an account where avoidable (P2-6, P3-2).

## Threat

A membership proof against a Merkle root that was current only briefly (say, right after the voter's own registration), a small group, or registration-then-vote timing narrows who the voter can be. The paymaster sponsoring registrations sees which account sponsored which identity commitment.

## Mitigation

Ballots are proven against the group root fixed in the election definition (T-08), never a later root; anonymity-set size per tier is published with results (P1-18, P3-2, P3-6).

## History

- 2026-10-11 (P1-17): per-tier-group scope adopted ([[membership]], Scope): one secret in two tier groups yields unrelated nullifiers, so a person's ballots in different tiers aren't linked by the nullifier. The scope binds the tier as well as its root, so this holds even when two tiers have the same root. Every proof uses one protocol-wide depth (32), so the verification key reveals nothing about the voter's leaf position and no server can serve a voter a depth that singles out their ballot.
- 2026-10-11 (P3-1): If [[0010-tier2-identity-provider]] uses zkPassport's non-salted nullifier (the mode waits on the owner's PII answer), an issuing state holding a document's chip data can tell that the document registered at Tier 2 and which identity commitment it registered. That reveals registration, not votes (membership proofs are perfectly zero-knowledge, [[0009-membership-proof]]). Anyone else holding the chip data can too (a malicious proof-app build, leaked chip dumps). Whether that nullifier on the board counts as PII on-chain is an owner question; no real document is registered on a public chain until it is answered. The alternatives (zkPassport's salted mode, a trustee-run threshold VOPRF, nullifiers kept with attesters) each add a trust cost.
- 2026-10-11 (P1-13): each ballot's L1 block fixes when it was made to about 12 seconds, so a voter casting in two tiers at the same moments links their two nullifiers by timing; the client casts in each tier independently ([[revoting]], Client rule 7).
- 2026-10-11 (P1-18, part 2): the election registry refuses a definition with any tier root at or after the registering L2 block ([[contracts]], Election registry), so every addition behind a root is public on L2 before voting.
- 2026-10-12 (P3-2 part 1): when a commitment joins a group is public on L2. Group additions are signed batches at fixed positions, so a group's sequence is the registrars' and can't be inflated by replays: the verifier replays each group with its own count and fails a definition whose group history breaks the signed sequence, even one rewritten by L2 governance, though a rewrite that drops the latest additions or any removal still checks (T-71) ([[contracts]], Group registry); batching registrations hides some timing, which the signing service (P2-6, P3-2) decides.
- 2026-10-12 (owner, [[0010-tier2-identity-provider]]): a chip-recomputable Tier 2 nullifier is PII and never boarded; additions are trustee-attested, so attesters see each nullifier with its commitment, until a trustee-run VOPRF nullifier exists.
- 2026-10-12 (P1-15 part 4a, [[0019-regional-cells]]): with regional groups, the group registry's events show each commitment's declared region, permanently, and a region move links old and new region by timing. Per-cell turnout is public, as per-tier turnout is; the remainder cell hides the turnout of the regions folded into it.
- 2026-10-12 (P3-4 part 1, [[0022-tier2-keyed-nullifier]]): the attesters hold a nullifier keyed by the panel's threshold OPRF key instead of zkPassport's, and never see the latter; a stolen or compelled attester list then needs `k` shares to map offline with chip data. The keyed nullifier stays off the board. Residual: anyone holding a document's chip data (the issuing state first) can query for it as its holder would, one valid proof per document, and learn its nullifier and whether it registered, which also maps a stolen list online; the panel publishes query and duplicate counts.
- 2026-10-12 (P3-2 part 4a, [[0024-tier0-registration]]): Tier 0 commitments join their group in CSPRNG-shuffled batches on a fixed period (at most 10 minutes), so a batch's order and timing reveal only the period a commitment registered in, among that period's registrations in that group, which at low volume can be one.
- 2026-10-13 (P3-2 part 4b, [[registration]]): batches form only at fixed 10-minute boundaries in UNIX time, sorted by commitment value, so a batch's order is a public function of its contents that anyone can check (an unsorted batch shows the service leaked an order), refining the ADR's shuffle. A quiet group's queue is held for up to six boundaries until it has eight commitments, so a registration's time is shared with that many others unless the group stays quiet for an hour. The route answers alike whether a commitment is queued, already live or newly accepted, so it can't be used to time a registration more finely than its batch, except through the busy answer: someone who already knows a commitment can learn whether it is newly queued by filling the group's queue, at about a thousand solves per probe. Residual: a Sybil can fill a batch with its own commitments (T-01).
- 2026-10-13 (P2-17 part 1, [[membership]], Root clock and steps): a rolling ballot names a step of a public UNIX-time root clock (`ROOT_PERIOD` 600 s, offset 300 s), and only one within `ROOT_WINDOW` (2 h) before its L1 reference; a conforming client names the newest settled step, so the step says no more than the reference does. A non-conforming client's step can reveal that its voter joined within the window (residual). Every step root is recomputed from public additions at its boundary, never committed in advance, and an honest client proves only against a step settled on L1.
- 2026-10-13 (P2-17 part 2a, [[ballot-validity]], Ballot record (version 5); [[revoting]], Admission): ballot version 5 carries the step, chosen at cast after the L1 reference, and the verifier enforces the window against the named block's timestamp (`root-step-stale`, `root-step-future`) and the poll's accepted steps (`root-step-range`), so a step reveals no more than `ROOT_WINDOW` beside the reference. A non-conforming client's choice of an older step within the window remains the residual.
- 2026-10-14 (P2-17 part 2b-1, [[membership]], Reported counts): the smallest step any admitted ballot named, re-voted ones included, is reported and flagged when small, since the board shows that one of that step's members cast it: the anonymity set of the worst-placed ballot, which a non-conforming client's old step would shrink, is now visible rather than implicit.
- 2026-10-16 (P3-2 part 4c, [[contracts]], Registration paymaster): the paymaster sponsors only the signing service's own account, so no registrant's account or address is ever a sponsored sender; the paymaster, its bundler and the chain see the service next to each batch, whose commitments the registry's event publishes anyway. The residual in this file's status (an account or address joined to a commitment through sponsorship) doesn't arise on this path; the join by address at the registration request (T-11) remains.
- 2026-10-16 (P3-3 part 2b-1, [[vouching]], The root a vouch names): a vouch's Tier 2 root is taken only at a block on a grid of 1,800 L2 blocks (an hour, as coarse as the anchoring periods [[0014-tier1-vouching]] first chose), so every voucher who syncs within the same hour names the same root.
- 2026-10-16 (P3-2 part 4d-1, [[registration]]): every accepted registration request answers 200 with an empty object, whether its commitment is new, already queued, in flight or live, and a property test checks that across all four states. The queue keeps no arrival time or order. The small timing difference between a queued and an ignored commitment (one hash write inside the same Redis script) is left unpadded, as stated in [[registration]], Known-weak.
- 2026-10-16 (P3-2 part 4d-2a, [[registration]], The batch): a group's short queue is held up to six boundaries, more than 256 queued are chosen by a Fisher–Yates shuffle drawing from `crypto.getRandomValues` by rejection sampling, and every batch is sorted by commitment value, so a batch's order is a public function of its contents; tests check the order, the choice's size and spread, and that Redis keeps nothing but the queue, the counts, the index, the in-flight records (public once sent), a hold count and a position floor per group, the last boundary's number, the index being rebuilt (public) and the job's lock token. Each boundary runs once, so a retry can't shorten the hold or put a batch between boundaries.
- 2026-10-17 (P3-2 part 4d-2b-1, [[registration]], The batch): the worker's Tier 0 jobs take no data, the boundary job logs per group only its ID, step and two flags, and a test against Anvil checks that no log line holds a queued commitment or the signed record and that every Redis key is under a queue's or the registration's hash tag. The boundary is tried every 30 s and runs once per period, so batches stay on the boundaries.
