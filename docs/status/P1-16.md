# P1-16: Bulletin board model

- State: in progress (in review; done when #31 merges)
- PR: #31
- Branch: `claude/p1-16`
- Phase: Phase 1: Threat model, spec, crypto core, circuits, verifier, reference election (CLI only)

## Scope

Bulletin board model: append-only hash-chained entries, inclusion proofs, and Merkle roots for anchoring.

## What was built

- [[board]]: the board-entry envelope (record type `0x0007`, version 1: election, index, segment, payload), the allowed payload types, the entry hash, the hash chain, the board tree (RFC 9162 §2.1 with tagged `H`), inclusion and consistency proofs, segments, checkpoints and their hash, segment objects for [[content-addressing]], the canonical order of spoiled-ballot openings, and the board checks behind [[verifier]] 4.1 and 4.2.
- Both a hash chain (the brief requires one) and an RFC 9162 tree. Checkpoints carry the size, chain head and root, and every period that adds entries must be anchored. `abolish/v1/board-chain`, `board-entry`, `merkle/leaf` and `merkle/node` are specified, and `abolish/v1/board-checkpoint` is new. `MAX_BOARD_PAYLOAD` = 1 MiB is in [[parameters]].
- `packages/crypto`: `src/board.ts` and `src/merkle.ts`.

## Tested

- `docs/spec/vectors/board.json`, from an independent Python implementation (`scripts/board-vectors.py`):
  - 25 envelope vectors;
  - every root, inclusion proof and consistency proof of a 13-leaf tree (91 + 91 proofs);
  - 14 rejected proofs;
  - 33 board-check vectors, one or more for every error code.
- transparency-dev/merkle v0.0.2's RFC 6962 vectors, vendored and run with RFC 6962 hashing:
  - every root and node hash;
  - inclusion and consistency proofs, both generated and verified.
- fast-check properties (passing at `FC_NUM_RUNS=1000`):
  - envelope round-trip and canonicity;
  - prefix roots computed in one pass agree with each root computed separately;
  - proofs are complete, and tampered proofs fail;
  - any byte changed, or any entry dropped, duplicated or swapped, on an anchored board fails a check;
  - unanchored entries are caught;
  - hostile and malformed arguments are rejected.

## Known-weak

- The second implementation behind `board.json` is also ours, though it shares no code with `packages/crypto`. Its tree shape and proof algorithms are checked against transparency-dev's published vectors.
- **Openings and challenged ballots (for P1-13).** The canonical opening order hides when an opening was sent. It doesn't unlink the opening from the challenged ballot it opens, and that challenged ballot is a board entry posted in the casting session. P1-13 must keep that entry from being tied to the cast ballot, or record the link as a residual in T-47.
- **Undecodable payloads.** The operator must board only payloads that decode strictly. If one breaks this, the verifier reports the entry as rejected rather than failing the election, and its bytes stay in the archive (T-17).
- An inclusion proof binds a root, not a size on its own, so sizes must always be taken from a checked checkpoint ([[board]]).
- Until P4-1 fixes the period length and epoch, segment numbers are any non-decreasing `u32`.
- The opening order applies only to openings carried directly. If P1-13 or P1-18 lets an opening arrive inside a contract event, they must extend the rule.
