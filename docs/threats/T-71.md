# T-71: L2 governance rewrites state or forges transactions

- Area: Availability and censorship resistance (G-10)
- Adversary: A-1 (and third-party L2 governance, not yet an adversary class)
- Status: **Planned.** Detection only. Residual: tampering can be detected, not prevented; Base upgrades have no delay. Governance changes elsewhere on the L2 (gas, deposit limits, sequencing bounds) can still censor or delay us.

## Threat

A Stage 1 L2's Security Council (with Coinbase, on Base) changes the rollup's rules and so its state, or forges a transaction from any address, by choice or under compulsion; on Base, Coinbase alone also sets the chain's configuration and allowlists state proposers. In April 2026 Arbitrum's Security Council, acting alone and instantly, spoofed a transfer from an exploiter's address.

## Mitigation

No contract trusts `msg.sender` alone for anything that affects a result: ballots carry membership proofs, trustee keys their DKG transcript hash, Tier 2 additions their document proof, Tier 0 additions a threshold of dedicated registrar keys pinned in the group registry and the verifier's release ([[contracts]], Group registry, departing from [[0004-l2-choice]]'s Safe owners; see STATUS, Decisions to review), Tier 1 additions their vouches ([[0014-tier1-vouching]]). Deposits and forced ballots reaching our contracts are checked against their L1 source; the verifier recomputes our contracts' state from their events and calldata, and anchored group roots come from the board's signed additions, never from L2 state (P1-19, P4-1). Each contract keeps an event accumulator ([[contracts]]): a running hash and count over every log it emits, at a fixed storage slot, so the archived event sequence can be checked against L2 state at an output root ([[verifier]] 4.4).

## History

- 2026-10-12 (P1-13b part 1, [[0023-receipt-evidence]]): receipt keys, whose signatures are attributed to the anchoring authority, are registered on L1 by that authority, never on L2, where governance could forge a registration from the authority's address and frame it with receipts under a key of its own. Verifiers and clients prove the registrations from L1 state.
- 2026-10-11 (P1-18): the event accumulator is specified ([[contracts]]), implemented in `packages/contracts` (`EventAccumulator`) and `packages/crypto` (replay), and vectored. Status stays Planned: no contract that emits result-affecting events exists yet.
- 2026-10-12 (P1-18 part 3): the trustee registry records a ceremony transcript only with signatures from a quorum of distinct seats of a pinned panel, checked on chain against the pinned keys; anyone may submit, and the sender is never checked or recorded ([[contracts]], Trustee registry). Its events go through the event accumulator.
- 2026-10-12 (P3-2 part 1): group additions and removals carry their registrars' signatures over their position (a removal, over the member count it saw), and the verifier replays each group with its own count, so a history rewritten to replay, reorder or drop a batch before a later one fails as `group-history` ([[contracts]], Group registry, Verification). Dropping the latest additions before a root's block, or any removal, leaves a history that still checks; only an honest accumulator storage proof catches it.
- 2026-10-12 (P1-18 part 4a, [[0025-contract-event-evidence]]): each event's L2 block number and timestamp are bound into its contract's event accumulator, so position, like completeness, rests on the accumulator's storage proof under an L1 output root, and no event is evidenced by a transaction proof. A contract that accepts anything because of its caller (the forced-ballot relay) records it in its event, so the verifier still traces it to its L1 call (verifier 4.5). Status unchanged.
- 2026-10-12 (P1-18 part 4b-1): the event accumulator binds each log's L2 block number and timestamp (`abolish/v1/event-accumulator-2`), implemented in `packages/contracts` and `packages/crypto` (`checkEventAccumulatorProof`) and vectored, so an archive that moves an event to another block, or across a storage proof's block, fails the check. Status unchanged: no contract is deployed.
- 2026-10-13 (P1-18 part 4b-2a): `ElectionCreated` and `DefinitionRegistered` carry their block's L1 origin, authenticated by the registry's event accumulator, so no L1-attributes transaction is archived for `f` or a version cutoff; the verifier checks the origin against finalized L1, the event's L2 timestamp and the release's pinned drift, and checks that a registration's origin is no earlier than its own election's creation's ([[contracts]], Election registry, Events, The L1 origin). Status unchanged: nothing is deployed and the verifier's check is P1-19's.
- 2026-10-13 (P1-18 part 4c-1, [[0030-close-rule]]): decided, not built. A forced ballot comes through our L1 relay, whose accumulator in L1 state binds each call's index, L1 block and ballot hash, so a relayed ballot forged from the relay's aliased address by L2 governance matches no call and fails 4.5. Dispute games count, for attributing late contract events and as the floor of the panel's close statements, only once resolved in the claim's favour; an attribution resting on a TEE-only game is reported as such.
- 2026-10-13 (P1-19 part 4k, [[verifier]], Contract events): built, in part. The verifier decodes every contract-event record of the election on the board under the pinned contract-event version and runs the event check against the definition's L2 contracts, so a boarded record from a contract the definition doesn't name, or one that isn't an event of its contract's table, fails 4.4 inside the anchored extent. 4.4 still can't pass: the required entries need L2 reads and the archive, and the accumulator replay that shows each record is its contract's own needs storage proofs at output roots settled on L1 (P4-3, P1-19 part 3b). No ordering rule is applied to the board's subset of a shared sequence; that is open (P1-18).
- 2026-10-13 (P1-18 part 4c-2b-2a): L2 governance raising the drift or sequencing window during a poll now fails it at [[verifier]] 2.6 for every definition the registry admits, since the registry caps both assumptions at Base's current values ([[parameters]]).
- 2026-10-13 (P1-18 part 4c-2b-2b-2a): specified, not built. The L1 relay stores one call hash per call over the whole record, its index, L1 block and stamp, so a relayed ballot forged by L2 governance from the relay's alias matches no recorded call and fails [[verifier]] 4.5 (`relay-unmatched`, or `relay-duplicate` for a second event naming one call), proven from L1 state at the verifier's finalized block ([[contracts]], L1 relay, Verification).
- 2026-10-14 (P3-5 part 2a): `apps/indexer` keeps every group-registry log in the shape the accumulator hashes, and its tests check the indexed sequence against the registry's stored accumulator and count on Anvil, the backfill's and the live path's, and show a dropped, altered or moved log failing. The tests read the storage slots from the node; a reader that relies on the index must prove them under an output root instead (verifier 4.4). Status unchanged.
- 2026-10-14 (P1-19 part 4n): until 4.4 replays the event accumulators, an ordinary-path ballot anywhere in the anchored extent, admitted or not, leaves selection (6.1) unverifiable, so an `l2_timestamp` no one has proven never decides which ballot counts.
- 2026-10-15 (P1-18 part 4c-3): the board's relayed-ballot call accepts only the relay's alias, so only a deposit the relay made, or one L2 governance forges from that alias, reaches it; until verifier 4.5 matches each such event with the call the relay stored, a relayed ballot's stamp is the event's word, so the verifier sets relayed ballots aside after 5.1 to 5.4 and decides neither the window nor selection with one present.
- 2026-10-15 (P1-18 part 4c-3 follow-up): a residual stated. The board remembers a relayed record, so a deposit L2 governance forges from the relay's alias, carrying a voter's ballot bytes with a stamp inside the window, turns that voter's later direct submission of the same bytes into a silent no-op. Verifier 4.5 rejects the forged event (`relay-unmatched`), so the ballot is lost with no failed call to warn the voter; this needs L2 governance, which can already censor (T-50).
- 2026-10-15 (P1-19 part 4o, [[verifier]], Contract events): 4.4 checks the L1 origin of the election's own `ElectionCreated` and `DefinitionRegistered` as [[contracts]] (The L1 origin) says: against the release's pinned drift (1,800 seconds, never the definition's), the registration's against the creation's, and, where the bundle's run of finalized headers holds the origin's number, against that block. A rewritten `L1Block` predeploy or a sequencer naming another origin fails 4.4 inside the anchored extent; the `l2_timestamp` it compares with stays unauthenticated until the accumulator replay.
- 2026-10-16 (P3-3 part 2b-1, [[vouching]], Counting across the deployment): Tier 1 additions are authorised by vouches checked from the board, never by who sent them. Whoever orders the chain can only choose which of one voucher's own double-spent vouches counts, and a rewritten Tier 2 history, shown by the earliest Tier 2 record that breaks the strict replay, fails every definition whose Tier 1 replay reaches it as `group-history`, the same for every verifier.
- 2026-10-16 (P3-3 part 2b-2, [[vouching]], The root a vouch names): besides a Tier 2 record its group's strict replay refuses, a members record naming a group with no earlier `GroupCreated` and a repeated `GroupCreated` also stop Tier 1 counting at their block, each judged from earlier events alone so that replays of different lengths agree; the release's registry can emit neither. `countTier1Additions` implements the rule with vectors for all three.
- 2026-10-18 (P3-4 part 2b-4b-1, [[contracts]], Group registry, Nullifier keys): the group registry's records of the Tier 2 keys inherit this residual: a rewritten L2 history can show a different initial key or successor recorded from any quorum's still-valid approvals placed before their deadline; the verifier's replay catches only histories the registry couldn't have logged, and the accumulator's storage proofs the rest.

- 2026-10-17 (P3-5 part 3b, [[contracts]] Event accumulator, Output root; `packages/verifier` `accumulatorAtOutputRoot`; `apps/worker` registry sync): the registry sync no longer trusts the L2 node for the accumulator. The L1 node names the newest dispute game of the type the L2's portal respects at its finalized head (never a configured type, since a type anyone can create without a proof would let anyone post a root); the L2 node's header, message-passer root and account and storage proofs must hash to that game's root claim, and the game's block must be the header's, else the run records nothing and logs `output-root`. Checked on a real Base Sepolia game and its block (`output-root.json`) and on Anvil. Residuals: the root is the game's proposer's word until the game resolves (a TEE-only root is Coinbase's allowlisted proposer's), a game shown false after a run doesn't undo what the run recorded, and blacklisted or retired games aren't refused, since the sync reads only the game's own status; one L1 node is trusted for its finalized head. Status unchanged.
