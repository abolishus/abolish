- State: in progress (part 1, the code functions in `packages/core`, merged in #199; part 2, the lookup in Postgres and the API route, merged in #205; part 3a, the website's `/p/<code>` redirect, merged in #NN; part 3b, each poll's canonical code on its page and link preview, next)

## Scope

Short links for polls, as [[sharing]] (Short links and entry points) designs them: `abolish.us/p/<code>`, where the code is the first 35 bits of the poll's definition hash (its seal) as 7 characters of lower-case Crockford base32 (`0-9a-z` without `i l o u`). The link-preview renderer already computes the 7-character form (`shortCode` in `apps/web/src/og/model.ts`, P2-9); nothing resolves a code yet, so the link printed on previews doesn't open anything.

The rules every part keeps:

- **Ownership is a pure function of public data.** Among registered polls in registration order, the earliest whose definition hash has a 7-character prefix owns that code; a later poll whose prefix is taken gets 8 characters, then 9, and so on. An earlier poll's code never changes when later polls arrive, so a poll ground to collide can't take an existing code, and mirrors, `apps/node` and the verifier can resolve codes without us.
- **Forgiving input.** Codes are case-insensitive; on input `o` reads as `0` and `i`/`l` as `1`; `u` and anything else outside the alphabet is refused. QR codes carry the upper-case form (`HTTPS://ABOLISH.US/P/3J55DW1`), so `/P/<CODE>` must resolve too.
- **No code is kept.** Page analytics record the template `/p/:code`, never the code (T-67). A refusal never echoes the input.

## Plan

Each part is one PR on this branch's name. None is protocol code, so none is inside the `crypto-review` gate.

1. **The code functions** in `packages/core` (shared by `apps/api` and `apps/web`; `packages/crypto` stays protocol-only): `shortCode(hash, length)`, input normalisation, and the ownership rule over definition hashes in registration order. `apps/web`'s `shortCode` moves here. Fast-check properties (honouring `FC_NUM_RUNS`, printing the seed): codes round-trip; normalisation accepts every forgiving variant and refuses the rest; every poll gets a unique code; an earlier poll's code never changes as later polls arrive, adversarially colliding prefixes included; a code grows past 7 characters only on a collision.
2. **Lookup in Postgres and the API route.** A Drizzle migration (the migrations skill's workflow) adding what an indexed lookup by definition-hash prefix needs, and a contract route in `packages/api-contract` (`zod/mini`, strict) that resolves a code to its election id and canonical code, for example `GET /elections/by-code/{code}`. It applies the ownership rule at the code's length, resolves a delisted or hidden poll exactly as the election routes resolve it by id today, and is rate-limited like comparable routes. The OpenAPI spec is regenerated. Tests: resolution, collisions resolved by the rule, unknown and malformed codes answering 404 without echoing input.
3. **The website's `/p/<code>`.** In two parts: 3a (#NN), the redirect, its checks and its analytics template; 3b, the canonical code on the poll page and the link preview, which needs an API route answering a poll's canonical code by its ID (part 2 resolves only codes to polls). It resolves the code through the API and redirects to `/polls/<electionId>`, with long caching only for a code that resolved. An unknown code gets the site's NotFound page with a 404. The router also matches `/P/<CODE>`. The poll page and the link preview show each poll's canonical code, so a collided poll shows its 8-character one. The analytics template `/p/:code` is added to `src/analytics.ts`. Tests in the style of `ssr.test.ts` and `serve.test.ts`: redirect, upper-case and forgiving forms, not found, the analytics template, and security headers on the redirect.

Later, with the sharing surfaces: `/p/<code>/flyer`, `/p/<code>/embed`, `/embed/p/<code>` (the script-free embed, which needs `frame-ancestors` relaxed on `/embed/*` only), and code entry in the ballot client's other entry points ([[0020-entry-points]]).

## Part 1 (#199)

`packages/core/src/short-codes.ts` (also `@abolishus/core/short-codes`): `shortCode`, `parseShortCode`, `assignShortCodes` and `resolveShortCode`; `apps/web`'s link previews call it.

- The rule as built: in registration order, a poll's code is the shortest prefix of at least 7 characters that no earlier poll's **hash** shares (not merely no earlier poll's code). So a code's owner is always the earliest poll with that prefix, and part 2's lookup is: the earliest registered poll whose hash starts with the code, which owns it if the code is 7 characters or some earlier poll shares its prefix one character shorter. Any other prefix answers 404.
- Codes run to 52 characters: the 52nd holds the hash's last bit and four zero padding bits, which `parseShortCode` requires, so distinct hashes always get distinct codes.
- Case is folded in ASCII only (the Kelvin sign is refused, not read as `k`).
- Tested: fast-check properties against an independent bit oracle and a naive statement of the rule over adversarially colliding prefixes (uniqueness, stability as polls arrive, growth only on collision, resolution), plus fixed examples.
- Known-weak: a 7-character collision costs seconds to grind, and it only ever lengthens the grinder's own code; someone who learns a definition hash before it's registered can register a colliding poll first and push the victim to 8 characters. `assignShortCodes` holds every hash in memory: it is the reference, and part 2 resolves in Postgres.

## Part 2 (#205)

Migration `0007_election_registrations.sql`, `packages/core/src/registrations.ts` and `GET /elections/by-code?code=` (`elections.resolveCode` in `packages/api-contract`).

- `election_registrations` records every `DefinitionRegistered` event (election, definition hash, L2 block and log index), whether or not its definition is stored: a definition the registry accepts but `storeDefinition` refuses still owns its codes, so ours match a mirror's. If the definition is stored, the event's hash must be its hash. Write-once, and rows arrive in chain order (a trigger, under READ COMMITTED only), so a code that resolves never moves.
- `lookupShortCode` is two index-range reads: the earliest registration with the code's prefix, and, for a code longer than 7 characters, the earliest with the prefix one shorter, which must be an earlier poll. The hash range is materialized before ordering, so an unknown code never walks the table.
- The route answers `{ electionId, code }` (the canonical code), and `CODE_NOT_FOUND` (404) for a code no poll owns and for anything that isn't a code within 64 characters, without quoting the input; longer input is a 400 that doesn't quote it either. Delisted and hidden polls resolve as they do by ID. The request log keeps only the route (T-11, T-67). No route-specific rate limit: like the other public reads, it is under the proxy's whole-host rule (`docs/runbooks/railway.md`).
- Tested: the lookup agrees with `resolveShortCode` over adversarially colliding hashes at every neighbouring prefix length (fast-check, capped at 50 runs like the other database-backed properties); the 51-shared-character case; `shortCodeRange` against `shortCode` and at its edges; the table's grants, triggers (owner included), chain order and isolation check; `recordRegistration`'s refusals; the route end to end (forgiving forms, collisions, moderation, not found, the 400, the log).
- Known-weak: nothing records registrations yet, so no code resolves on staging until the indexer (P3-5) calls `recordRegistration` for each finalized event. The database can't check that `definition_hash` is the definition's hash for an event whose definition isn't stored, so an insider or a compromised indexer can point a code at any election; part 3 should at least check, before redirecting, that the code is a prefix of the registry's hash for the returned election, and earliest ownership stays unchecked by the client.

## Part 3a (#NN)

`apps/web/src/routes/p.$code.tsx`, `resolveShortLink` in `src/server/load.ts` and the `fetchShortLink` server function.

- `/p/<code>` reads the code with `@abolishus/core`'s `parseShortCode`, so case and `o`/`i`/`l` are forgiven, and `/P/<CODE>` matches because the router's routes aren't case-sensitive. Anything that isn't a code is the site's 404 without asking the API, so input over the API's 64 characters never becomes its 400.
- The API's answer is checked before anyone is sent on, as part 2's known-weak asked: the poll's definition is fetched, decoded and checked to name that election (as its page does, T-34), and the code must be a prefix of that definition's hash at the code's length. A code no poll owns, one the API claims for a poll whose hash doesn't start with it, and one whose poll's served definition names another election are all the 404, which never quotes the input.
- The redirect is a **301** to `/polls/<electionId>` with `Cache-Control: public, max-age=86400`. 301 rather than 308: the same for a GET, and the permanent redirect every link-preview crawler follows. A day rather than for good: a code that resolves never moves to another poll, but a database that pointed one at the wrong poll (part 2's insider case, now limited to polls sharing the prefix) should stop sending visitors there within a day of being fixed. `src/start.ts` keeps a redirect's own `Cache-Control`, since a redirect carries no document and no nonce; every other redirect sets none and stays `no-store`, and 404s and failures are `no-store`.
- Analytics: the template `/p/:code`, in either case, never the code (T-67).
- Threats: T-31, T-34, T-67 (a history entry), T-10 (nothing of the visitor's reaches the API).

Tested (part 3a): in `tests/ssr.test.ts` against the built server and a stub API: the 301, its location, caching and security headers, and the poll page it leads to; upper-case, forgiving and mixed-case spellings; an 8-character code; the three not-found cases (uncached, quoting nothing); malformed codes (a `u`, too short, too long, punctuation, the Kelvin sign, padding bits) refused without an API call; nothing of the visitor's forwarded; the lookup form's redirect still `no-store`; an unreachable API giving the uncached error page; the server-function CSRF check covering the new function. `isShortCode` and the analytics template by property. Mutation by hand: dropping the prefix check fails the claimed-code test.

Known-weak (part 3a): which of several polls sharing a prefix owns a code is still the API's word: the page checks the prefix, not the registry's order (the verifier and mirrors can). The poll page and its link preview still print the 7-character form, which for a collided poll is another poll's code (3b). Nothing records registrations on staging yet, so no code resolves there until P3-5's indexer.
