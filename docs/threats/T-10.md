# T-10: Account-to-ballot linkage on the server

- Area: Ballot secrecy, unlinkability and privacy (G-3, G-4, G-5, G-12)
- Adversary: A-2, A-1
- Status: **Planned.** Residual: network metadata, T-11.

## Threat

A table, log line, cache key, queue job or metric joins an account (or a session, cookie or IP) to a ballot or poll participation.

## Mitigation

Accounts and voting identities are separate systems, including the recovery backup (T-20); the ballot path carries no account credential. A test asserts that no table can join them (P2-1, built): every table is classed as board or operational, no foreign key starts or ends at a board table, and no board column has an account-like name. The API's request log has one (P2-3, built): a line holds only the method, the contract route matched, the status and the duration, never an address, a header, a query string or a body, and the handlers' context holds the database alone, so no procedure can read a cookie, token or address. Accounts (P2-5 part 1, built) live in their own tables, which the no-join test classes separately: foreign keys from or to them stay among them, no column of theirs has a ballot-like name, and no view or function reads both classes. Account cookies are host-only on `apps/web`'s origin, and the API refuses (with 400, before reading anything) any request carrying an account cookie or an `Authorization` header, so no ballot or board request is ever handled next to an account. Queues and the worker's log have one (P2-4, built): each queue is on one side, its job data is strict and can't name the other side, nothing of a job stays in Redis once it finishes, and a log line holds only the queue, outcome, error kind and duration. The API has no cache or metrics yet, and whichever part adds one extends the test. Migrations rules (`.claude/skills/migrations`).

## History

- 2026-10-11 (P2-1): the schema no-join test is built. It covers tables only, and the column deny-list matches by name, so a renamed linking column would pass; review of each migration still has to catch that.
- 2026-10-11 (P2-3 part 1): the API's request-log test is built. It sends cookies, bearer tokens, forwarding headers, query values and ballot bodies, and fails if any reaches a log line or if a line has any field beyond method, route, status and duration. Internal errors are logged by kind only, since error messages can quote input. It doesn't cover the reverse proxy or hosting platform in front of the API, whose access logs P2-11 must configure (T-11).
- 2026-10-11 (P2-6 part 1): [[0017-identity-recovery-backup]] stores recovery envelopes through the ballot path with no account session, in an operational table with no account column; P2-6 part 3 classes it in the no-join test and refuses, rather than ignores, an account cookie or token on its routes.
- 2026-10-11 (P2-5 part 1): accounts (better-auth, passkeys only) in `account_*` tables, classed as their own kind in the no-join test, which now also fails on a foreign key leaving the account tables, an account column with a ballot-like name, a view, or a function that names tables of both classes. The account handler is for `apps/web`'s origin; the API refuses requests carrying an account cookie (any name under the account prefix, with or without `__Secure-`/`__Host-`) or an `Authorization` header. The name-based checks share the P2-1 caveat: a renamed linking column or a join written in application code isn't caught by them.
- 2026-10-11 (P2-4 part 1): the queue and worker-log no-join tests are built. Every queue is on the board or the account side and its strict job data can't name the other side (field names matched by a deny-list, as for columns); the worker re-parses data before handling it; a job's data, error and stack trace leave Redis when it finishes, even if its producer didn't ask, and the failure message BullMQ keeps in its events stream is only the error's fixed kind; a log line holds the queue, outcome, error kind and duration, plus public election IDs for audit findings. Tests queue an account field on a board queue, and make a handler throw a message quoting data, and fail if either reaches a log line or any Redis key, the events stream included.
