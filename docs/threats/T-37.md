# T-37: Trustee key substitution

- Area: Integrity and verifiability (G-7, G-8, G-9)
- Adversary: A-2
- Status: **Planned.** Residual: voters trust that the registered key belongs to the named trustee; trustees must check their own key on L2.

## Threat

A trustee's public key, or the joint key, is replaced so a party we control can decrypt.

## Mitigation

Trustee key registration is a public, anchored transcript: each trustee's per-election KEM key and signing key, with proofs of possession, registered on L2 and bound into the election definition (P1-14, P1-18, [[0002-everlasting-privacy]]). Replacing k trustees' KEM keys would let the holder read every ballot.

## History

- 2026-10-11 (P1-14, [[0012-trustee-identity-signatures]]): every trustee statement is signed by the seat's pinned identity key (ECDSA P-256, low-s, under a registered signature tag), and the trustee registry records a ceremony only with signatures by the pinned panel, never on `msg.sender` alone ([[trustee-identity]]). The panel identifier binds `k`, `n` and every key in its seat, so a definition can't name a known panel with a substituted key or a lower threshold. Residual: a stolen identity key speaks for its seat in every election until a release unpins it, so it belongs in hardware ([[0006-trustees]], rule 6); identity signatures are not post-quantum.
- 2026-10-11 (P1-14 follow-up): the entry above overstates the identity key's role. As [[trustee-identity]] (Which key signs what) and [[verifier]] 3.1 state, every ceremony-phase statement is signed by the seat's pinned identity key, and every later statement (receipts, tally shares, destruction) by the per-election signing key registered in its identity-signed ceremony entry. A further residual, stated in [[0012-trustee-identity-signatures]] and [[trustee-identity]]: P-256's parameters come from an unexplained seed, so an adversary holding an undisclosed break of P-256 could forge `k` seats' ceremony entries and register KEM keys it holds (also T-14).
- 2026-10-11 (P1-18, part 2): the election registry admits a definition only if the trustee registry recorded its stub hash with its ceremony transcript hash, approved by a quorum of the panel the definition names at its threshold and size; the check compares hashes, never the sender ([[contracts]], Election registry). The trustee registry itself is P1-18's next part.
- 2026-10-12 (P1-14 part 2, [[0018-ceremony-possession]], [[ceremony]]): the ceremony transcript registers each qualified seat's per-election KEM and signing keys. Every message is signed by the seat's pinned identity key over the ceremony context (chain, registry, election, stub, panel, run) and the hash of every earlier round, so no one can add, swap or replay a key, or move a transcript to another election; the DH key carries a Schnorr proof of knowledge bound to its seat, the signing key its own signature, and the ML-KEM key is shown openable by answering every other qualified seat's encapsulated challenge before the challenges are revealed. The verifier recomputes the qualified set and the key set from the transcript alone. Residual: a coordinator can withhold a seat's messages and so exclude it (down to `k` approving seats); it can't register a key no qualified seat proved it holds.
- 2026-10-12 (P1-18 part 3): the trustee registry is built ([[contracts]], Trustee registry). It pins each panel's keys at deployment, checked against their encodings exactly as `p256Key` decodes them, and records a transcript for a stub and panel, write-once, only with at least the panel's quorum `q` (`k ≤ q ≤ n`, `q = k` until [[0006-trustees]] rule 7 is decided) of valid ceremony registration signatures bound to this chain and registry. Recording per stub and panel keeps another pinned panel from blocking a stub's own. A stolen identity key still signs for its seat.
- 2026-10-12 (P1-15 part 2b, [[tally]], Summed-share message): a trustee seals its summed shares only to a KEM key looked up by seat in the key set `checkCeremonyTranscript` returned for the transcript the election's definition names (`ceremony_transcript_hash`); `packages/crypto` records each checked set with its transcript hash, and `sealSummedShares` and `openSummedShares` refuse any other set (a plain array from an API, a cache or a file, or another run's or another election's checked set), so whoever serves keys to a node can't substitute a recipient's key and read the sums, or a sender's key and reach decapsulation (`crypto-review` on #93). Both functions take the registered definition and derive its hash, its `ceremony_transcript_hash` and the tally rules from it, so a caller can't pair one election with another run's transcript. Residual: the node must pass the definition registered on L2, and the transcript check still rests on its identity signatures and the pinned panel, as above.
