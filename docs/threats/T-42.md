# T-42: Compromised voter device changes the vote

- Area: Client integrity and cast as intended (G-6, G-13)
- Adversary: A-3
- Status: **Partial.** Malware that controls the device can also fake the challenge check. Checking must be possible on a second device or by an independent verifier the voter chooses: [[challenge]] specifies that flow (the tracking code recorded before the choice, the opening and its checks), and its client and checker are P2-8's and P5-4's. Under P1-3 (option B), malware can also post an invalid share on an honest voter's last ballot; the complaint can arrive after close, so the voter can't re-vote, and the vote is nullified.

## Threat

Malware alters the plaintext before encryption.

## Mitigation

Benaloh challenge/spoil: the voter can challenge any ballot, and a checker they choose rebuilds the core from its opening and compares its tracking code with the one recorded before the choice ([[challenge]]; [[0021-challenged-ballots]]).

## History

- 2026-10-11 (P1-13): a ballot's L1 block publishes when it was made, so P1-13's challenge part must keep challenged entries from being matched to the cast ballot by time ([[revoting]], Residuals); the receipt check must show admission and selection, since the ranking fields escape Benaloh's audit.
- 2026-10-12 (P1-13 part 3a, [[0021-challenged-ballots]]): a challenged ballot is never boarded on its own. The casting device commits to the core by its tracking code (the full core hash, as a QR code) before the cast-or-challenge choice; a second device records it, checks a challenge's opening against it, and later finds the cast ballot by it. So challenging leaves no board entry near the cast ballot to match by time. The check resists malware only on a second device or checker the voter chooses.
- 2026-10-12 (P1-13 part 3b): [[challenge]] specifies the core hash, the opening record (`0x0003`, version 1) and its checks, which rebuild every VSS commitment and registered seat's ciphertext from the opening; `packages/crypto` refuses to cast a core it opened or open one it cast. A passing opening of a vote outside the rules is evidence against the client (`opening-vote-outside`).
- 2026-10-13 (P1-19 part 4g): `packages/verifier` runs [[challenge]]'s checks over every opening on a board copy (6.2) and reports each one's tracking code and vote, flagging `opening-vote-outside` as evidence against the client that made the core ([[verifier]], Spoiled-ballot openings).
- 2026-10-13 (P2-14 part 1b, [[challenge]], Opening version 2): spoiled-ballot opening version 2 opens the cores of ballot versions 2 and 3 (a cell in place of the tier, the poll's flat options), with `opening-vote-outside` naming the first question outside the rules, so regional-cell and multi-question elections can be challenged; [[verifier]] 2.3 pairs ballot versions 2 and 3 with it and ballot version 1 with opening version 1.
- 2026-10-13 (P2-14 part 3b, `packages/crypto`): `profileCombinationRule` (2.3) now refuses a profile pinning ballot version 1 beside any opening version but 1, or ballot version 2 or 3 beside opening version 1, so no election whose ballots couldn't be challenged passes; a version-5 profile with opening version 2 stays unverifiable here until the package reads that opening (part 3c).
- 2026-10-13 (P2-14 part 3c, `packages/crypto`): spoiled-ballot opening version 2 is read and checked: `openChallengeV2` opens the core `cellBallotCore` gives (the tracking code `cellTrackingCode` shows before the choice) for a cell of a version-4 or version-5 election, from a sharing of the ballot version's own kind, only if it was never proved; `checkChallengeOpeningV2` runs version 1's checks with `opening-cell` and the core hash under the profile's ballot version, and reports the first question outside the rules. `profileCombinationRule` now passes ballot versions 2 and 3 beside opening version 2, so a regional-cell or multi-question profile no longer stays unverifiable at 2.3 for want of a challenge. The verifier's 6.2 still leaves those openings unverifiable until it reads them (part 5).
- 2026-10-13 (P2-14 part 5b, `packages/verifier`): 6.2 reads spoiled-ballot opening version 2 under definition versions 3 to 5: each opening is checked by `checkChallengeOpeningV2` against the definition's cells and questions and the registered key set, reports its tracking code under the ballot version the profile pins and, when its vote is outside the rules, the first question outside, and is judged against the Publication rules (`opening-early`, `opening-cast` against the admitted version-2 or version-3 ballots at or below the floor of `s_S`, `opening-repeat` by that tracking code) as under definition version 1. `verifier-openings-v2.json` comes from an independent Python implementation.
- 2026-10-13 (P2-16 part 2b-4, `packages/crypto`): spoiled-ballot opening version 3 is read and checked for ballot version 4's cores: `openChallengeV3` opens the core `panelBallotCore` gives (both halves, an unregistered seat's share hash zero in either panel) only if its sharing was never proved, and `checkChallengeOpeningV3` runs version 2's checks over both halves, default half first, rebuilding each seat's ciphertext under its own panel's binding, and gives each `v_j` and `r_j` as the sums of the halves' constant terms. `profileCombinationRule` now reads opening version 3, so a profile pinning it beside ballot version 2 or 3 fails 2.3 rather than staying unverifiable. With an author panel the exported paths refuse the poll until its key set has a checked source (part 3); the verifier's 6.2 doesn't read version 3 yet (part 4). `spoiled-opening-v3.json` comes from an independent Python implementation.
- 2026-10-17 (P2-8 part 3b-2c-1, `apps/ballot`): the screens seal in the worker and show the tracking code before the choice, as a QR code of all 32 bytes with the election id (the layout now in [[challenge]], Client rule 1), its fingerprint and its hex, whether or not anyone scans it. A challenge hands the opening's record bytes to the voter's other device as a file, and the casting device never says what the opening holds or that it checks: only a checker that recorded the code before the choice can. An opening whose code isn't the one shown is never handed over. Open: no checker exists yet, so a voter can record a code and save an opening but nothing compares them (P5-4).
- 2026-10-30 (P2-17 part 4d-2b-2b-1, `packages/crypto`, `packages/verifier`): a version-3 opening's tracking code is the core hash of the ballot version its context checks, ballot version 5's under a rolling definition (`checkChallengeOpeningV3`, `openingV3CoreHash(…, 5)`), never version 4's, so one code never names cores of two ballot versions. The ballot client's rolling path, which shows the code before the choice, isn't built yet (part 8).
