## Scope

`ci: deploy`: signed images to Railway (PR environments + staging), and Cloudflare in front.

Deployment design set by the owner (2026-10-11). The GitHub environments already exist; use them as they are:

- **`staging`** (GitHub environment, `main` only, no reviewer) holds `RAILWAY_TOKEN`, a Railway project token scoped to the Railway `staging` environment. Every merge to `main` builds the image twice, checks the hashes match, signs it, and deploys it to staging. The reference election then runs against staging.
- **`production`** (GitHub environment, `prod` branch only, owner approval required) holds a separate `RAILWAY_TOKEN` scoped to the Railway `production` environment. A production deploy runs when the `prod` branch moves. It never rebuilds: it finds the signed image already built from that commit on `main`, verifies its signature and provenance, checks that the reference election passed on staging for that digest, and deploys that digest. The job waits for the owner's approval.
- Only the owner moves `prod`, by fast-forwarding it to a commit on `main`. Agents never push to it; they list release candidates (commit, digest, reference-election result) in STATUS.
- Deploy jobs use secrets only through these environments, never repository secrets, so workflows run for PR branches can't reach them.
- PR environments, if any, get no Railway token with access to staging or production data.
- Write `docs/runbooks/railway.md`: every Railway service, variable and setting the owner must create by hand (Postgres, Dragonfly, one service per app), and how to roll back to a previous digest.

## Part 2: `ci: deploy` (#69)

`.github/workflows/deploy.yml` (owner-reviewed, no auto-merge): on every push to `main`, once `ci`, `repro-build` and `reference-election` pass, build the image twice in fresh checkouts that differ in path, locale, timezone and umask, and compare digests; push to GHCR by digest, sign with cosign keyless and attest SLSA provenance; then in the `staging` environment verify both, run the digest's migrations from the runner, and deploy the digest to the Railway `api` service.

- Migrations run from the workflow rather than as a Railway service: Railway's deployment status can't say when a one-shot process exited, and its pre-deploy command would give the API the migrator's credential. The cost: `MIGRATE_DATABASE_URL` in the `staging` environment, and Postgres reachable over Railway's TCP proxy ([[railway]]).
- Production isn't built: it must check that the reference election passed on staging for the digest, which waits on P1-20. Until then nothing can deploy to production. Release candidates go into STATUS once staging deploys.
- Known-weak: unexercised until it first runs on `main` (GHCR package creation, `gh attestation verify`, Railway's token header and statuses). Tested in session: the OCI archive's digest, a digest-preserving push to a local registry, and the Railway GraphQL calls against Railway's live schema.
