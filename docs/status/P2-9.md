## Scope

`apps/web`: TanStack Start SSR (discovery, results, poll creation), and PostHog proxied via our domain.

## Plan

1. **Scaffold, poll pages and the moderation log** (this part): TanStack Start rendered on the server; a poll page from the API's definition, board head and moderation state; the public moderation log; a lookup by poll ID; the security headers.
2. **Accounts and PostHog**, in two PRs:
   - 2a (this part): the account handler from `@abolishus/core` (P2-5 part 1) under `/auth` on this origin, an account page, and a Node server entry for P2-11's image. Turnstile joins once P2-5 part 2 lands.
   - 2b: PostHog proxied through our domain, capturing no poll IDs from pages a signed-in account views beyond what T-67 accepts.
3. **Discovery and poll creation**: the API has no listing route yet (P2-3 part 2 or a follow-up adds one, honouring delisting); poll creation needs the election registry write path.
4. **Results**: per-cell tallies once P1-15 publishes them, with the display text checked against the definition's commitment before it is shown (T-34).

## Built (part 2a)

- `src/node/serve.ts`, the Node front: the built Start handler for pages and server functions, the account handler under `/auth`, and `dist/client/assets` (content-hashed `.js`, `.css`, `.woff2` names only, immutable caching). Every request's URL is built on `WEB_ORIGIN`, never on `Host`, and an absolute-form target is refused. Bodies are bounded at 64 KiB, a GET with a body is refused, at most 64 requests run at once (503 past that) and idle or overlong connections are destroyed, as in the API (T-52). The log line is the method, a route class (`page`, `server-fn`, `auth`, `asset`, `refused`), the status and the duration: never a path (a poll page's path names the poll), query, header or address (T-10, T-11, T-67). Account answers get `no-store`, `nosniff`, `no-referrer` and same-origin CORP; every `Set-Cookie` is kept apart.
- `src/node/main.ts`, packed into `dist/node/main.mjs` with every dependency inlined; the Start server build now inlines its dependencies too, so `dist/` runs with no `node_modules`. Configuration: `API_URL`, `WEB_ORIGIN`, `ACCOUNT_RP_ID` (the origin's host by default), `ACCOUNT_SECRET`, `DATABASE_URL` (a login granted `abolish_app`), `WEB_HOST`, `WEB_PORT`, checked at start.
- `/account`: create an account with a passkey, sign in and out, sign out every other session, list, add and remove passkeys (never the last one), and delete the account after a second confirmation. The page talks to `/auth` on its own origin; WebAuthn's JSON forms are converted by hand (`src/account/webauthn.ts`, strict unpadded base64url, no extensions asked for or sent), so the page adds no third-party browser code (T-55). No passkey name is sent. The page is `noindex`, and the server renders it without reading the session.
- The route generator formats `src/routeTree.gen.ts` at 80 columns; a build plugin reformats it in the repo's style, so a build leaves the committed file unchanged.
- `packages/core`: exports its software authenticator for tests (`@abolishus/core/test-authenticator`); `boundedBody` is typed so it type-checks under a DOM `lib` too.
- Threats: T-10, T-11, T-52, T-55, T-67.

## Known-weak (part 2a)

- **One process holds account sessions and serves poll pages.** Nothing joins them (the pages never read the session, the log has no paths), but a compromised `apps/web`, or the proxy's logs, could join a session to the polls its browser views (T-67, T-11). It never sees a ballot (T-10).
- **Sign-ups and ceremony starts are unbounded** until Turnstile (P2-5 part 2) and the proxy's per-address limits (P2-11) (T-52, T-01).
- **Adding a passkey or deleting the account needs a session under a day old.** The page says so on any failure but doesn't tell that case apart from others.
- **The route-tree formatting plugin runs `vp fmt`** during the build, so building needs Vite+ on the path (it always does here).
- **No image yet**: P2-11 adds the Dockerfile; `dist/` already runs on its own.

## Built (part 1)

- `apps/web`: TanStack Start 1.168 (React 19) on Vite+, SSR, file routes (`src/routes/`; `src/routeTree.gen.ts` is generated by the build, in the repo's style).
  - `/`: what the site is and a lookup form (a plain GET form, so it works without script). `/polls?id=…` forgives `0x`, capitals and spaces and redirects to the poll's one address; anything else returns to the form, marked invalid.
  - `/polls/<id>`: only canonical lowercase hex is a poll page (T-31). The definition is decoded with `@abolishus/crypto`; one that doesn't decode, or names another election, is refused rather than shown (T-34). Shown: counting rule, options, selections, electorate tiers and group sizes, trustee threshold, opening and closing times in UTC, the definition hash to compare with the registry, a broken well-formedness rule if any, the board's size, chain head and root, marked as the server's word until anchored (T-24), and the moderation state with its reason; delisted or hidden polls get `noindex`.
  - `/moderation`: the public log, paged by sequence number (T-68).
- Data comes only through server functions, which call the API from our server with an oRPC client over the contract, checking every answer against it (`ResponseValidationPlugin`), with no redirects followed and a 5-second timeout. No request to the API carries anything of the visitor's (T-10).
- Every response carries a CSP with a fresh 128-bit nonce, which the router stamps on the inline scripts it renders, plus `no-store` (a cached page would share its nonce), HSTS, `no-referrer`, `nosniff`, same-origin opener and resource policies and a restrictive `Permissions-Policy` (T-43, T-11, T-67). Search parameters are read as text and every route's validator sets each key it reads, so a repeated or malformed one (`?id=a&id=b`, `?after=abc`) is dropped rather than reaching a loader. Server functions refuse cross-site calls (TanStack's CSRF middleware) before any handler runs. A failed API call reaches the page as one fixed error; the log gets the error's kind only.
- Every string is in the i18n catalog (`src/messages.ts`), including each well-formedness rule's name; every component has stories. Dates are formatted in UTC for the page's locale; the browser's ICU may word them slightly differently from Node's, so they hydrate with `suppressHydrationWarning` and keep the server's text.
- Reproducible: TanStack Start's server manifest records each route's source as an absolute path, which nothing reads at run time; a build plugin rewrites it relative to the package before the chunk is hashed, so two checkouts build identical `dist/` trees.
- New dependencies: `@tanstack/react-start` and `@tanstack/react-router` (the brief's frontend stack), `@orpc/client` and `@orpc/openapi-client` (the contract's own client; `@orpc/client` was already in the tree).
- Threats: T-10, T-11, T-24, T-31, T-34, T-43, T-67, T-68.

## Known-weak (part 1)

- **The page doesn't check the registry or the anchor.** It decodes the definition and shows its hash, but doesn't compare it with the election registry on L2, nor the board head with an L1 checkpoint; it says these are the server's word. The verifier is where they are checked (T-34, T-24).
- **No question or option text yet.** The display text lives off the board; showing it needs fetching it and checking its commitment (P1-10b), which comes with results (part 4).
- **The CSP is weaker than the ballot client's**: `'self'` scripts beside the nonce (route chunks load by dynamic import) and no Trusted Types, since the framework renders inline scripts. Nothing on this site casts a vote or holds a voting secret (T-43).
- **The server sees which polls a visitor views** (T-11, T-67), as any web server does. Its own request log and the proxy in front of it must keep no addresses or query strings (P2-11, as for the API).
- **No production server entry or image yet**: the build is a fetch handler (`dist/server/server.js`); part 2 adds the Node entry and P2-11 the image.
