# T-11: Network-level linkage

- Area: Ballot secrecy, unlinkability and privacy (G-3, G-4, G-5, G-12)
- Adversary: A-2, A-1, A-10
- Status: **Not mitigated.** Anyone seeing network traffic (us, Cloudflare, an ISP, A-1) can correlate an IP across registration and voting. Voters who need protection must use Tor or another anonymity network; the client must not break under it. Under P1-3 (option B), each trustee's intake also sees submission metadata, so up to n more parties can correlate IPs.

## Threat

Our servers, CDN or an RPC provider see the same IP or browser fingerprint at registration and at ballot submission, or time-correlate them.

## Mitigation

Ballot submission uses no account session and no cookies; the API's own request log drops IPs on the ballot path (P2-3); the proxy's and the platform's logs are residuals (History, P2-11). Direct submit (T-25) bypasses us entirely. Under [[0002-everlasting-privacy]] (P1-3, option B): a direct submit still delivers its shares to the n trustees' intakes, or posts them publicly, so it bypasses us but not the trustees.

## History

- 2026-10-11 (P2-5 part 1): accounts keep no network address or user agent: better-auth's IP tracking is off, a hook clears both fields on every new session, and the migration's checks refuse any non-null value, so a session row can't be joined to an address later. better-auth's rate limiter, which keys on addresses, is off; per-address limits are the proxy's (P2-11).
- 2026-10-11 (P1-13): a client's check of its ballot's L1 block after finality must not be a targeted request for that one block, which would link its network address to the ballot ([[revoting]], Client rule 4).
- 2026-10-11 (P2-11 part 1): [[railway]] turns off Cloudflare's log exports (no Logpush, no Log Explorer), but Cloudflare still keeps WAF and rate-limit matches as security events with the client address and query string, so a rate-limit match on ballot submission records an address with its time. Railway's own HTTP logs can't be turned off and may record client addresses. Both are more parties that see addresses, never with an account session on the ballot path (T-10).
- 2026-10-11 (P2-10 part 2): a poll report keeps no address and no time of its own (only the hour its ground's oldest unreviewed report arrived). An insider reading the counters repeatedly, or holding the write-ahead log or backups, can still time a report, and Railway's HTTP logs may hold the address with that time. A rate-limit match on `POST /moderation/reports` is a Cloudflare security event like any other, with the reporter's address.
- 2026-10-12 (P2-5 part 2): server-side Turnstile verification sends Cloudflare only the secret key and the token, never the visitor's address (`remoteip` is optional and omitted). Cloudflare already sees the address in transit, and its widget sees the browser; from us it learns when a token was redeemed and for which action (`passkey-register` is a sign-up or a new passkey), never an account ID or an address.
- 2026-10-12 (P3-2 part 4a, [[0024-tier0-registration]]): Cloudflare, terminating TLS in front of the API, sees each Tier 0 registration request whole (the address, the Turnstile token and through it the solve's browser signals, and the commitment) and keeps a rate-limit match with the address and time; Railway may log the address. Registration carries no account, but a join by address remains, mitigated only by an anonymity network, over which the challenge page and the route must work.
- 2026-10-13 (P3-2 part 4b, [[registration]]): the challenge page runs on an origin of its own and sees no commitment; Cloudflare, whose script runs there, sees the solve's address and time, which it can join to the registration request it also proxies. The client never asks the service about its commitment: it reads the outcome from each Tier 0 group's records in full. Both the page and the route must work over Tor.
- 2026-10-13 (P2-16 part 2a, [[ballot-validity]] Residuals (version 4)): under ballot version 4 every author seat runs membership-checked intake, so the author's trustees see each ballot record with the address that delivered it; where an author panel publishes its seats' own intake endpoints is part 3's, and until then an author seat's only route is the operator's relay. Not mitigated.
- 2026-10-16 (P2-16 part 3a, [[delivery]], Version 2): where author seats publish intake endpoints moves to part 7, in the display text, and the client doesn't authenticate an endpoint beyond delivery's own checks (the seat's registered KEM and signing keys). So an endpoint the creator names that isn't the seat's own receives each ballot record it is sent (nullifier and ballot hash) with the voter's network address: a party beyond the operator and the registered trustees. Not mitigated; part 7 should use an author endpoint only with the voter's consent and over a path that hides the address.
