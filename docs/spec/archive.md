# Permanent archive

How board data is archived on Arweave and found again from L1 alone: what an archived object's Arweave transaction holds, the archive manifest (record type `0x0021`) that lists a run of archived objects and links the manifests before it, the contract-event evidence (record type `0x0025`) that a version-2 manifest lists, the contract-event runs (record type `0x0026`) that a version-3 manifest lists, and the body of the board anchor's `archiveLocator` ([[contracts]], Archive locator) that names the latest confirmed manifest. Threats: T-51 (data loss once our pinning stops), T-49 (verification with our servers and domain gone), T-17 (chosen bytes in the permanent record), T-52 (input that costs a reader work), T-24 (a source serving different bytes to different readers), T-69 (a seized authority overwriting the locator). Decided by [[0005-permanent-archive]] (option A), Consequences, "Archive objects and how they are found".

Integrity never rests on the archive. Every object found through it is checked against the L1-anchored checkpoints ([[board]], Board checks) as a copy from any other source is, so a manifest or a transaction can only send a reader to bytes that fail those checks or to nothing: the election is then unverifiable from the archive, never failed by it (T-53). Arweave is one more source next to IPFS, never a required one ([[0005-permanent-archive]], Verifier and node).

## Archived objects

An archived object is a board segment object or an entry-hash list that a checkpoint names ([[board]], Segments and checkpoints), a contract-event evidence record (Contract-event evidence, below), a contract-event run (Contract-event run, below), or an archive manifest. Display text is never archived ([[display-text]]; T-17). Our contracts' event-accumulator evidence ([[contracts]], Evidence) is listed only by manifest versions 2 and 3, and their events only by version 3, which adds them.

Each archived object is the data of exactly one Arweave base-layer transaction, and that data is exactly `objectCar(object)`: the object's CAR under [[content-addressing]]'s parameters, with its CID as the one root. Nothing else is in the data, so the same bytes are a CAR any IPFS node imports (`ipfs dag import`), and the CID is the same whether the object is fetched from IPFS or from Arweave. A transaction is named by its 32-byte ID, the SHA-256 of its signature, which Arweave writes as 43 characters of unpadded base64url ([RFC 4648, section 5](https://www.rfc-editor.org/rfc/rfc4648#section-5)); every Arweave node and gateway serves the data by that ID. Transaction tags (`Content-Type: application/vnd.ipld.car` and the root's CID text, say) are an index for gateways, never read by a verifier and never trusted.

A transaction ID says only who posted the data, which a verifier doesn't trust: the bytes are judged by their CID. Reading an object from a transaction's data, with the object's CID `c` and a bound `M` on its length:

1. the data MUST start with the CAR header [[content-addressing]] gives for `c` (CAR), byte for byte; then
2. each block follows as a varint length, a CID and the block, as the CAR encodes it; a varint that isn't minimal or is longer than 8 bytes, a block whose CID isn't 36 bytes framed as [[content-addressing]] frames them, or a length running past the data is **inconsistent**;
3. the object is read within `M` ([[content-addressing]], Reading within a bound) from the blocks the data carries, each served only under its own CID. If its length is over `M` it is **over-bound**; any other failure of the read (an inconsistent DAG, or a block the walk reaches that the data doesn't carry) is **inconsistent**;
4. the data MUST then be exactly `objectCar` of the object read, or it is **inconsistent**: no other block, order or repetition is accepted, so one transaction's data has one reading.

Otherwise it is the object. Every outcome is a function of the data, `c` and `M` alone; a source that serves other data for a transaction ID is a source that failed, and the reader tries another, as for IPFS (T-24). `packages/crypto`'s `readArchivedObject` is this reader, over data its caller fetched within its own limit.

## Archive manifest (record type `0x0021`)

A manifest lists archived objects with the transactions that hold them, and links the manifests that confirmed before it, so every confirmed manifest is reachable from the latest one ([[0005-permanent-archive]], Archive objects and how they are found). It is a record ([[notation]], Records) and itself an archived object; its CID is `objectCid` of its encoding, which is at most 1 MiB, so it is always one raw block (`0x01 ‖ 0x55 ‖ 0x12 ‖ 0x20 ‖ SHA-256`). No profile pins its version: a manifest belongs to a deployment, not to an election, and each locator version fixes the manifest version it names (Locator). Since a version-3 manifest is at most 835,639 bytes (Layout (version 3)), every version is one raw block.

### Layout (version 1)

| Field         | Type                 | Meaning                                                                               |
| ------------- | -------------------- | ------------------------------------------------------------------------------------- |
| `l1_chain_id` | `u64`                | The chain ID of the L1 the deployment's board anchor is on.                           |
| `anchor`      | `bytes[20]`          | The board anchor's address: the contract whose locators name this manifest's chain.   |
| `sequence`    | `u64`                | This manifest's place in the deployment's chain: 0 for the first, then one more each. |
| `objects`     | `list<object, 8192>` | The archived objects it lists.                                                        |
| `links`       | `list<link, 1024>`   | The earlier manifests it names.                                                       |

`object` is a structure of `cid` (`bytes[36]`), the object's CID, and `transaction` (`bytes[32]`), the ID of the transaction whose data is its CAR. `link` is a structure of `sequence` (`u64`), the linked manifest's `sequence`, `cid` (`bytes[36]`), its CID, and `transaction` (`bytes[32]`), the transaction holding it.

`MAX_MANIFEST_OBJECTS = 8192` and `MAX_MANIFEST_LINKS = 1024`, so a manifest is at most `43 + 8192·68 + 4 + 1024·76 = 634,927` bytes, under one chunk. A period with more objects than one manifest lists gets more than one manifest.

A decoder rejects, as `non-canonical` at the field's offset, after the framing of [[notation]]:

- an object's `cid` that isn't `0x01 ‖ codec ‖ 0x12 ‖ 0x20 ‖ digest` with `codec` raw (`0x55`) or dag-pb (`0x70`), the only CIDs [[content-addressing]] makes;
- objects not in strictly ascending byte order of `cid`, so no object is listed twice and a manifest's objects have one order;
- a link's `cid` that isn't raw (`0x01 ‖ 0x55 ‖ 0x12 ‖ 0x20 ‖ digest`), since every manifest is one raw block;
- links not in strictly ascending order of `sequence`, or a link whose `sequence` isn't below the manifest's own;
- a manifest with no objects and no links, which names nothing.

### Layout (version 2)

Version 2 is version 1 with one more field, the contract-event evidence it lists ([[contracts]], Evidence; [[0025-contract-event-evidence]], Consequences):

| Field         | Type                       | Meaning                                                    |
| ------------- | -------------------------- | ---------------------------------------------------------- |
| `l1_chain_id` | `u64`                      | As in version 1.                                           |
| `anchor`      | `bytes[20]`                | As in version 1.                                           |
| `sequence`    | `u64`                      | As in version 1.                                           |
| `objects`     | `list<object, 8192>`       | As in version 1.                                           |
| `links`       | `list<link, 1024>`         | As in version 1: the earlier manifests, of either version. |
| `evidence`    | `list<evidence_ref, 1024>` | The contract-event evidence records it lists.              |

`evidence_ref` is a structure of `contract` (`bytes[20]`), the L2 contract whose event accumulator the record proves, `l2_block` (`u64`), the L2 block it proves it at, `cid` (`bytes[36]`), the record's CID, and `transaction` (`bytes[32]`), the ID of the transaction whose data is its CAR. A record is at most 35,459 bytes (Contract-event evidence), so it is always one raw block. The reference's `contract` and `l2_block` let a reader pick the records it needs without fetching the rest; they are the record's own claim, and the evidence check holds the record to them.

`MAX_MANIFEST_EVIDENCE = 1024`, so a version-2 manifest is at most `634,927 + 4 + 1024·96 = 733,235` bytes, still one chunk. A decoder rejects everything version 1 rejects, each at the same offset, and, as `non-canonical` at the field's offset:

- a reference's `cid` that isn't raw (`0x01 ‖ 0x55 ‖ 0x12 ‖ 0x20 ‖ digest`), since every evidence record is one raw block;
- references not in strictly ascending order of `contract` (as bytes), then `l2_block`, then `cid` (as bytes), so no reference is listed twice and a manifest's references have one order, reported at the reference's offset once the whole reference is read ([[notation]], Strict decoding), so a reference cut short is `truncated` first; two records for one contract and block (two games claiming the block, say) are both listed, ordered by CID;
- a manifest with no objects, no links and no evidence, at the offset of `objects`' count, as in version 1, which names nothing. A manifest that lists evidence alone is well formed.

A version-2 manifest links manifests of version 1 or 2, since a deployment's chain may span the change: a reader decodes a linked manifest under the version its header names, if that is at most the version its locator fixes (The chain from a locator).

**Who writes them.** The worker that archives (P4-3 part 4) writes version 3 from its first manifest, since version 1 can't list the evidence its contracts need and version 2 not their events (Layout (version 3)); nothing has been archived under version 1 or 2. It writes manifest `k` once manifests `0` to `k − 1` exist, listing the objects of the periods it covers and linking exactly the manifests below `k` that have confirmed on Arweave and that no other confirmed manifest below `k` reaches through links: the roots of the confirmed manifests' links, and only confirmed ones (at most 1,024 per manifest; the next manifest links the rest). A manifest whose upload fails is posted again with the same bytes under a new transaction, so its CID and sequence don't change. A manifest that confirms after a later one was written is a root again when the next is written, and is linked then, so a manifest may be linked more than once (once by a manifest that never confirmed, say) but every confirmed manifest is reachable from every confirmed manifest written after it confirmed. The worker names a manifest `m` in a locator only once `m` has confirmed and every manifest `0` to `m − 1` is reachable from it through links; until then the locator keeps naming the last manifest that met that rule, and the worker writes a further manifest, which links the stragglers, when they confirm. So the manifest a locator names reaches every manifest before it, out-of-order and failed uploads included ([[0005-permanent-archive]]). Listing an object again in a later manifest (a second transaction, after the first was lost) is allowed: a reader takes any listing that reads.

### Layout (version 3)

Version 3 is version 2 with one more field, the contract-event runs it lists: the events themselves, which the evidence proves ([[contracts]], Evidence; [[0025-contract-event-evidence]], Amendment of P4-3 part 3b-3c-2a):

| Field         | Type                       | Meaning                                                |
| ------------- | -------------------------- | ------------------------------------------------------ |
| `l1_chain_id` | `u64`                      | As in version 1.                                       |
| `anchor`      | `bytes[20]`                | As in version 1.                                       |
| `sequence`    | `u64`                      | As in version 1.                                       |
| `objects`     | `list<object, 8192>`       | As in version 1.                                       |
| `links`       | `list<link, 1024>`         | The earlier manifests, of versions 1 to 3.             |
| `evidence`    | `list<evidence_ref, 1024>` | As in version 2.                                       |
| `runs`        | `list<run_ref, 1024>`      | The contract-event runs it lists (Contract-event run). |

`run_ref` is a structure of `contract` (`bytes[20]`), the L2 contract whose events the run holds, `first` (`u64`), the index `n` of its first event in that contract's sequence, `count` (`u32`), the number of events it holds, `cid` (`bytes[36]`), the run's CID, raw or dag-pb since a run may be longer than one chunk, and `transaction` (`bytes[32]`), the ID of the transaction whose data is its CAR. The reference's `contract`, `first` and `count` let a reader pick the runs it needs without fetching the rest; they are the run's own claim, and a reader holds the run to them (The event replay).

`MAX_MANIFEST_RUNS = 1024`, so a version-3 manifest is at most `733,235 + 4 + 1024·100 = 835,639` bytes, still one chunk. A decoder rejects everything version 2 rejects, each at the same offset, and, as `non-canonical` at the field's offset:

- a reference's `count` that is 0 or over `MAX_RUN_EVENTS` (65,536), or with `first + count` over `2^64`, at the offset of `count`, since a run holds at least one event, at most `MAX_RUN_EVENTS`, and only indices a `u64` holds;
- a reference's `cid` that isn't `0x01 ‖ codec ‖ 0x12 ‖ 0x20 ‖ digest` with `codec` raw or dag-pb;
- references not in strictly ascending order of `contract` (as bytes), then `first`, then `cid` (as bytes), so no reference is listed twice and a manifest's references have one order, reported at the reference's offset once the whole reference is read, as version 2's evidence is;
- a manifest with no objects, no links, no evidence and no runs, at the offset of `objects`' count, which names nothing. A manifest that lists runs alone is well formed.

A version-3 manifest links manifests of versions 1 to 3, read as version 2's links are (The chain from a locator).

### The chain from a locator (verifier 4.3)

From the latest locator proven in the anchor's state at `B` ([[contracts]], Archive locator) a reader:

1. decodes it (Locator). A version it doesn't know is reported (`locator-version`) and the walk stops; a known version of the wrong length (`locator-length`), a version-1 or version-2 locator naming a CID that isn't raw (`locator-cid`) and anything the anchor's framing refuses (`locator-framing`, which also covers a length word in the anchor's state that no Solidity `bytes` of at most `MAX_LOCATOR_LENGTH` bytes has, so the reader never reads more than 128 bytes' slots) are reported the same way. None of them fails anything;
2. reads the manifest it names from the named transaction, within 1 MiB, and decodes it under the version the locator fixes (a version-1 locator fixes version 1, a version-2 locator version 2, a version-3 locator version 3). It MUST have the CID the locator names (the read ensures it), the reader's `l1_chain_id` and `anchor` (`manifest-foreign` otherwise, and the walk doesn't follow it). Data that reads as the CID but doesn't decode is `manifest-malformed`: the CID fixes the bytes, so no other source can serve better. A transaction no source serves data for that reads as the CID is `unavailable`, and the walk stops;
3. reads each link's manifest the same way, decoding it under the version its header names where that is at most the version the locator fixes, and as `manifest-malformed` otherwise (a version-1 chain links only version 1; a version-2 chain may link versions 1 and 2, and a version-3 chain any of the three), requiring its `sequence` to be the link's (`link-sequence` otherwise, and the walk doesn't follow it), and continues from it, breadth first in each manifest's link order. Each sequence is read once: the first link to a sequence fixes its CID, and a later link to it naming another CID is `link-conflict`, with both (once per sequence, however many links conflict), and is never read. A later link naming the same CID under another transaction is tried while the sequence is still unreached, since a manifest whose upload failed is posted again with the same bytes (Who writes them). The reader stops after a budget of manifest reads of its own choosing (`over-budget`, unverifiable for this reader, never a verdict), since the authority chooses how many there are (T-52). A link that needs a read counts against the budget as soon as its manifest is reached, so the links waiting never outnumber the reads left, and a walk stops as soon as they would; a walk that stops there reports no gap and no unavailable link, since what it didn't read isn't missing;
4. reports the sequences from 0 to the latest's that no manifest reached, as ranges (`archive-gap`, each range's first and last); every link transaction no source served data for that reads as its CID (`unavailable`, with where the reader was sent from, the CID and the transaction), even where another transaction reached that sequence, since an honest link names a confirmed upload; and every sequence reached only through earlier locators (below), not from the latest locator's chain alone, as ranges (`earlier-only`): what a reader without those logs would lose. Ranges keep the report bounded however large the latest `sequence` is (T-52). None of these says who failed: a source that withheld a transaction and an authority that named one that never held the manifest look alike to a reader.

An earlier locator from an `ArchiveLocated` log at or before `B`, while L1 history serves it, names a manifest the reader checks against the CID the chain's links name at that sequence, so a locator overwritten by a seized authority is detected while the logs last (T-69; [[contracts]], Known-weak). A repeated locator is judged once. First the chain alone: a locator naming a CID the chain's links name is the chain's own manifest and never a mismatch, and if that sequence is still unreached and the locator names a transaction not yet read for it, the manifest is read from it (step 3's rules, from the same budget) and the walk goes on from it; this repeats over the locators until a pass reaches nothing more, so a source's lapse on a link is not taken for an overwrite, whatever the locators' order. Then the rest, each read as step 2 reads the latest's, from the same budget, and judged against the chain as it then stands. A manifest of this deployment at a sequence the chain names (another manifest there) or above the latest's (where the locator was rolled back) is `locator-mismatch`, with its sequence, its CID and the CID the chain names there if any. One at a sequence below the latest's that the chain doesn't name is followed (step 3's rules, the same budget) and is no mismatch, since a reader can't tell a link a source withheld from one the authority cut off; what it reaches is reported as `earlier-only` (step 4), a fact either way. Earlier locators are judged only once the latest's manifest is reached, since otherwise there is no chain to judge them against. Every listed object that a counted checkpoint of an election names is read by its transaction within the checkpoint's bound ([[board]], A copy from L1's CIDs) and must be the object the checkpoint names; a CID a counted checkpoint names that no reached manifest lists is reported (`not-archived`; The listed objects, below). All of these are reports on the archive path, never verdicts on an election: the board checks judge the bytes, wherever they came from. `packages/verifier`'s `latestLocatorFromState` and `walkArchive` are steps 1 to 4 and the earlier locators' check (P4-3 part 3b-1), over chains of versions 1 and 2 since part 3b-3b and of version 3 since part 3b-3c-2b-1, and `listedTargets` and `readListedObjects` the listed objects (part 3b-2a); `readArchive` runs them for a bundle and the report gives 4.3 from them ([[verifier]], Archive; part 3b-2b-1), with the earlier locators read from the anchor's logs a bundle carries, proven against its event accumulator in L1 state (`earlierLocators`, part 3b-2b-2a); the command line's Arweave gateways are part 3b-2b-2b.

### The listed objects

The objects a counted checkpoint names are each run's segment object, which a board copy reads ([[board]], A copy from L1's CIDs), and its entry-hash list, which a copy doesn't need but the archive must hold. Take the checkpoints that count after the board checks' steps 1 and 2, and their distinct sizes `n_1 < n_2 < …`, with `n_0 = 0`. For each size `n_i` with `n_i > n_{i−1}` its checkpoints' `object_cid` names the run's segment object, at most `(n_i − n_{i−1}) · (51 + MAX_BOARD_PAYLOAD)` bytes, and its `hashes_cid` the run's entry-hash list, at most `32 · (n_i − n_{i−1})` bytes. Step 2 makes counted checkpoints of one size name the same CIDs, so the first of each size stands for all. The targets are every segment object by ascending size, then every entry-hash list by ascending size, so a budget that runs out spends itself on what a copy reads first. A reader has two budgets of its own (T-52): `maxBytes`, against which every answer a source gives is charged, read or not, and an object read is charged its own length where that is more than its answer's (an object of identical chunks is far longer than its CAR, [[content-addressing]], Reading within a bound), and `maxReads`, against which every transaction it asks for is charged (1,024 by default). It takes each target in order:

1. a CID no reached manifest lists is `not-archived`, with the size and the CID. This needs no read, so it is reported for every target, before or after a budget runs out. A CID that is a target twice is tried once, whatever came of it;
2. otherwise, while the budgets last, the distinct transactions it is listed under are tried in walk order (the order the manifests were reached, then each manifest's), each transaction's answers in the order its sources give them, until one reads as the CID (Archived objects) within `M`, the target's bound or what is left of `maxBytes`, whichever is less. An answer longer than `objectCar` of an object of `M` bytes can be (at most `M + 59 + 256 · max(1, ⌈M / 2^20⌉)` bytes: the header, and a varint, a CID and a parent's link fields for each block, at most two blocks a chunk) is that source's failure and is never held or charged; any other answer is charged, and one that doesn't read as the CID is that source's failure, and the next is tried. A listing in a later manifest is how a lost upload is found again (Who writes them);
3. data that reads as the CID's header and DAG but whose object is over the target's bound is `object-over-bound`, once: the CID fixes the object's length, so no other listing is tried, and the board checks find the same run `inconsistent`. (An object over its bound whose CAR is past the data limit is never parsed, so it is reported `object-unavailable` instead; either is a report, and the board checks judge the run the same.) The reads stop (`objects-over-budget`, with the size, the CID, `maxBytes` and `maxReads`) at a target read as over what is left of `maxBytes` but within its bound, at one still unread when either budget is spent, and at one with no answer that reads while what is left of `maxBytes` is short of its bound, since an honest answer may have been too long to hold. That is unverifiable for this reader, never a verdict, and no target after it is read;
4. a target whose every listed transaction was tried without an answer that reads is `object-unavailable`, with the transactions tried.

So the objects a reader keeps total at most `maxBytes`, and the bytes it fetches are at most `maxBytes` of answers it held, plus, per transaction asked, up to the data limit from each gateway whose answer was cut off there (Reading from gateways); and it holds a few times `maxBytes` at most: an answer, its copy and the CAR it is compared with while it is read, and each object read with its blocks. An object read is the bytes its CID names, so its blocks (`contentDag` of it, [[content-addressing]]) serve a board copy by CID beside IPFS ([[board]], A copy from L1's CIDs), and the board checks then judge it as any other copy. A run the archive doesn't hold leaves a copy short, never failed (T-53).

### Reading from gateways

A reader fetches a transaction's data from an Arweave node or an ar.io gateway as `GET {base}/raw/{id}`, `id` the transaction's 43-character base64url ID: the raw-data route, which resolves no path manifest and sends no sandbox redirect, so a 200 answer's body is the data as posted. The verifier asks the gateways its user names in order, at most 16, and asks the next only when an answer doesn't read (above): a status other than 200, a redirect (never followed, since it could reach a host the user never named), a timeout, a body past the reader's limit, or data that doesn't read as the CID, so a gateway can withhold an object but never change one (T-24, T-49). The body is read only up to the limit, whatever its declared length, as for IPFS gateways ([[verifier]], Board by CID). What it asks for is visible to every gateway it names: a transaction ID says which manifest or segment is being read (T-11). `packages/verifier`'s `arweaveSource` is this source.

## Contract-event evidence (record type `0x0025`)

One contract's event accumulator proven at one L2 block under an output root an L1 dispute game claims: the account proof and the storage proofs of `S` and `S + 1`, with the output root's preimage ([[contracts]], Event accumulator, Verification and Output root; [[0025-contract-event-evidence]], Consequences, The evidence). It is a record ([[notation]], Records) and an archived object, listed by a version-2 manifest's `evidence`; never on the board or the chain, and never pinned by a profile: the manifest version that lists it fixes its version (version 2 lists version 1).

### Layout (version 1)

| Field                         | Type                   | Meaning                                                                                                                                                      |
| ----------------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `l2_chain_id`                 | `u64`                  | The L2's chain ID, the definition's `l2_chain_id`.                                                                                                           |
| `contract`                    | `bytes[20]`            | The contract whose accumulator is proven: one of the definition's L2 contracts.                                                                              |
| `game_index`                  | `u64`                  | The index, in the L1 dispute game factory that the L2's portal names (`disputeGameFactory()`), of the game whose root claim is `output_root`.                |
| `game`                        | `bytes[20]`            | That game's address, as the factory's `gameAtIndex(game_index)` gives it.                                                                                    |
| `output_root`                 | `bytes[32]`            | The game's root claim: the version-0 output root of the L2 block proven at.                                                                                  |
| `message_passer_storage_root` | `bytes[32]`            | The storage root of the L2ToL1MessagePasser after that block.                                                                                                |
| `header`                      | `bytes<1024>`          | The RLP encoding of that block's header.                                                                                                                     |
| `nodes`                       | `list<bytes<532>, 64>` | The trie nodes the proof walks: the contract's account proof under the header's state root and the storage proofs of `S` and `S + 1` under its storage root. |

`MAX_EVIDENCE_HEADER = 1024` (an OP Stack header is about 640 bytes today, and a fork adds a few words), `MAX_TRIE_NODE = 532` (a branch node of sixteen 32-byte references, the largest node a Merkle–Patricia trie with 32-byte keys has) and `MAX_EVIDENCE_NODES = 64` (an account proof on Base is about ten nodes, and two slots of one of our contracts a few more), so a record is at most `3 + 8 + 20 + 8 + 20 + 32 + 32 + 4 + 1024 + 4 + 64·(4 + 532) = 35,459` bytes, one raw block.

A decoder rejects, as `non-canonical` at the field's offset, after the framing of [[notation]]:

- an empty `header`;
- an empty node;
- nodes not in strictly ascending byte order (a node that is a prefix of another first), so no node is listed twice and a record's nodes have one order, whatever order a node served them in;
- a record with no nodes, at the offset of `nodes`' count, since no account is proven without one.

Every other property (that the header is one RLP header, that each node is a trie node, that the proof holds) is the evidence check's, below, so a record that decodes may still prove nothing.

### The evidence check

A reader keeps, from every manifest its walk reaches, the references to the contracts it needs: each reference (its `contract`, `l2_block` and `cid`) once, with every distinct transaction listing it, in the order the walk reached them, up to a budget of (reference, transaction) pairs of its own choosing (65,536 by default), since every manifest may list 1,024 and the authority chooses how many there are (T-52). A walk that would keep more keeps none beyond the budget and reports `evidence-over-budget`, unverifiable for this reader, never a verdict.

It reads a reference's record from its transactions in that order, each answer within the CAR of a 35,459-byte raw block, until one reads as the reference's CID within 35,459 bytes (Archived objects); an answer that doesn't read is that source's failure, and one that does settles the reference, since its CID fixes the bytes. Bytes that don't decode under version 1 are `evidence-malformed`; a reference no transaction serves is `evidence-unavailable`, with the transactions tried. Otherwise the record is judged against the definition it is checking ([[verifier]] 4.4 and 4.6 take the accumulator it proves). In order, the first that fails is the result:

1. `l2_chain_id` MUST be the definition's `l2_chain_id`, and `contract` the reference's (`evidence-foreign`);
2. the account and slots `S` and `S + 1` are read as [[contracts]] (Event accumulator, Output root) says, from `output_root`, `message_passer_storage_root`, `header` and `nodes`, with its codes (`output-root`, `l2-header`, `l2-proof-missing`, `l2-proof-malformed`, `l2-contract-absent`, `l2-count`);
3. the header's number MUST be the reference's `l2_block` (`evidence-block`);
4. every node MUST be one the walks of step 2 use (`evidence-node-unused`), so a record carries no bytes its proof doesn't need (T-17).

A record that passes proves the contract's accumulator and count at `l2_block`, against which its contract-event records are replayed ([[contracts]], Event accumulator, Verification), worth exactly what `output_root` is: the reader checks on L1 that the factory's `gameAtIndex(game_index)` is `game`, of the game type the portal respects, and that its root claim is `output_root` and its L2 block `l2_block`, and reports what the game's state makes the root worth ([[contracts]], Output root; [[verifier]] 4.4; T-71). Until the verifier reads dispute games from L1 (P1-19), the root is the record's word, and the evidence is worth what a bundle's `outputRoot` is. None of these fails an election: evidence that doesn't hold up, or no evidence, leaves what needs it unverifiable (T-53).

**Who writes them.** The worker that archives (P4-3 part 4), as [[contracts]] (Evidence) says: for each of the definition's L2 contracts whose count changed in an anchored period, and at close, the record at the first L2 block at or after the period's end that a game of the respected type claims, with the game's index and address from the factory, `eth_getProof`'s account and storage proof nodes for `S` and `S + 1` (each node once, sorted) and the block's header, each checked by the worker as the evidence check checks it before upload. A period `s` ends at the anchor's `epoch + (s + 1) · period` ([[board]], Timing), and the record's block is the first whose L2 timestamp is at or after it. The worker examines each contract's anchored periods in order, from the one after the last it examined: a record proving the count the last one did writes nothing, and one whose game doesn't exist yet stops that contract until a later run. It judges the record as decoded from the bytes it posts. Beyond the evidence check, it refuses a record that isn't canonical, is dated before the period's end, or proves a lower block or count than the contract's last record, or another accumulator at its count. A record showing the contract had no code at the block, while the worker has counted none of its events, moves its place on and writes nothing, so a contract deployed after the first anchored period starts at genesis with its first record. `packages/core`'s `archiveBoards` writes them over the records and events a deployment's `ContractEventSource` gives (P4-3 part 4b-3a); the source over the L1 games, the L2 node and the index is part 4b-3b.

## Contract-event run (record type `0x0026`)

A run of one contract's events, consecutive in its sequence, as its event accumulator hashes them: each event's contract-event record (`0x0008`, [[contracts]], Contract-event record) less the two fields every event of the run shares or implies, the contract and the index. It is how the archive keeps every event of each of our L2 contracts, the shared ones' events of every election included, independent of any election's board ([[contracts]], Election registry, The shared event sequence; [[0025-contract-event-evidence]], Amendment of P4-3 part 3b-3c-2a). It is a record ([[notation]], Records) and an archived object, listed by a version-3 manifest's `runs`; never on the board or the chain, and never pinned by a profile: the manifest version that lists it fixes its version (version 3 lists version 1).

### Layout (version 1)

| Field         | Type                 | Meaning                                                                                       |
| ------------- | -------------------- | --------------------------------------------------------------------------------------------- |
| `l2_chain_id` | `u64`                | The L2's chain ID, the definition's `l2_chain_id`.                                            |
| `contract`    | `bytes[20]`          | The contract that emitted every event of the run: one of the definition's L2 contracts.       |
| `first`       | `u64`                | The index `n` of the run's first event in the contract's sequence; event `i` has `first + i`. |
| `events`      | `list<event, 65536>` | The events, in order of `n`.                                                                  |

`event` is a structure of `l2_block` (`u64`), `l2_timestamp` (`u64`), `topics` (`list<bytes[32], 4>`) and `data` (`bytes<MAX_EVENT_DATA>`), exactly the fields of the same names of the contract-event record, which versions 1 to 9 share ([[contracts]], Layout (versions 1 to 9)). So event `i` is the record `contract ‖ u64(first + i) ‖ l2_block ‖ l2_timestamp ‖ topics ‖ data`, field for field, which a reader frames under the contract-event version its election's profile pins and judges as a boarded record is judged ([[contracts]], Event check): the run carries no version of its own records, since one contract's sequence serves elections pinning different versions.

`MAX_RUN_EVENTS = 65,536`, and a run's encoding is at most `MAX_CONTRACT_EVENT_RUN = 2^24` (16,777,216) bytes, the bound a reader reads it within (Archived objects), so even one event of the largest `data` a record frames fits in a run, and the writer splits a period's events into as many runs as these bounds need. The length is the reader's bound and a writer's rule, never a decoding one: a decoder judges the bytes it is handed, and a writer never makes a run past it. A decoder rejects, as `non-canonical` at the offset of `events`' count, after the framing of [[notation]]:

- a run with no events, which says nothing;
- a run whose last index, `first + count − 1`, is over `2^64 − 1`, since no `u64` holds it.

Every other property (that the blocks and timestamps never decrease, that each event is one of its contract's, that the run is the contract's own history) is the replay's and the event check's, below, so a run that decodes may still be false.

### The event replay

A reader replaying a contract's accumulator from the archive ([[verifier]] 4.4; [[contracts]], Event accumulator, Verification) keeps, from every manifest its walk reaches, the run references to that contract: each reference (its `contract`, `first`, `count` and `cid`) once, with every distinct transaction listing it, in the order the walk reached them, under the walk's budget of (reference, transaction) pairs, which evidence and run references share (The evidence check; a manifest's evidence is kept before its runs). To replay up to the count `c` an evidence record proves, it takes, from `n = 0`, the references whose `first` is `n`, in ascending order of `cid` (then of `count`), and reads each from its distinct transactions in walk order, each within the most a run of its `count` events encodes (the record's 43 bytes of framing and fixed fields and `count` events of four topics and `MAX_EVENT_DATA` bytes each, never more than `MAX_CONTRACT_EVENT_RUN`) and what is left of a byte budget of its own (1 GiB by default), every answer charged against it as the listed objects' are (The listed objects) and each event of a run taken charged 512 bytes more for its record held, since a run of empty events takes many times its encoding once decoded, and a run not taken kept only as its bytes, so the budget bounds what the reads hold, until one reads as its CID (Archived objects); a CID that read once is judged from those bytes against every later reference naming it, never read again, unless it named an object over the bound of a smaller `count` and a later reference's bound is larger. The first that reads and whose run has the definition's `l2_chain_id`, the reference's `contract` and `first`, and exactly `count` events is taken, and the reader goes on from `n + count`, until `n ≥ c`. A reference whose data reads as its CID but doesn't decode is `run-malformed`, one whose data names an object longer than a run of its `count` can be is `run-over-bound` (an object over the bound whose CAR is past the data limit is never parsed, so is `run-unavailable` instead), one whose run disagrees with the definition or the reference is `run-foreign`, one no transaction serves is `run-unavailable` with the transactions tried, and an `n` below `c` where no reference starts, or where none of those starting there is taken, stops the replay with `run-gap` and `n`. The reads stop with `runs-over-budget` and `n` when the byte budget or a budget of transactions (1,024 by default) runs out, or where no answer read while what is left of the byte budget was short of the reference's bound, since an honest answer may have been too long to hold. None of these says who failed: each leaves the replay, and so whatever needs it, unverifiable, never failed (T-53). The events of the runs taken, event `i` of a run numbered `first + i`, are then the contract's archived sequence, replayed against each evidence record of the contract as [[contracts]] (Event accumulator, Verification) says. An archived event's event check counts only once the replay has authenticated it against evidence whose root is settled on L1 (P1-19): until then the archive's authority writes evidence and runs whole, so an event of a run that fails the check leaves what needs it unverifiable, never failed, as 4.6's `evidence-unchecked` does (T-53, T-71).

Two runs that read at one `n` are both the authority's, since only it writes manifests: the first in `cid` order is taken, and a replay it breaks is unverifiable, never repaired by trying the other, so a reader's work stays linear in the runs it needs. `packages/crypto`'s `contractEventRunRecords` gives a run's events as contract-event records; `packages/verifier`'s `walkArchive` keeps the references (its `runs`) and `readRuns` is these reads (P4-3 part 3b-3c-2b-1); `replayArchive` replays each contract's sequence against every evidence record of it for 4.4 ([[verifier]], Contract events, step 6; P4-3 part 3b-3c-2b-2), with `packages/crypto`'s `checkEventAccumulatorProofs`, which judges every record over one replay of the sequence, as `checkEventAccumulatorProof` judges each alone.

**Who writes them.** The worker that archives (P4-3 part 4): for each of the definition's L2 contracts whose count changed in an anchored period, and at close, the events from the count its previous evidence record proved (0 for the first) to the count of the record it writes for the period (Contract-event evidence, Who writes them), as one run, or consecutive runs under `MAX_RUN_EVENTS` and `MAX_CONTRACT_EVENT_RUN`, listed in the manifest that lists that evidence. Each run's events are the logs it indexed ([[P3-5]]), each checked by the worker against the evidence by the replay above before upload, so a run it uploads always replays: from the accumulator, count, block and last event the contract's previous record proved, exactly the events the new record counts, in order of block and timestamp, each after the previous record's block and none past the new one's, reproducing its accumulator, which is the whole sequence's replay against both records (`packages/crypto`'s `checkEventAccumulatorContinuation`). A span needing more runs than a manifest lists is refused before its events are fetched. Runs are cut as long as both bounds allow, so the same events always make the same runs, and a record and its runs are listed only together, once every one of them and every earlier record of the contract has confirmed, so a contract's records are listed in count order (at most `MAX_MANIFEST_RUNS` runs a record, which a period's events never approach). A source that fails, or gives a record or events that don't check, holds up only that contract, never the board's objects (`packages/core`'s `archiveBoards`, P4-3 part 4b-3a).

## Locator

The board anchor frames a locator as `u16(version) ‖ body` ([[contracts]], Archive locator). Version 1's body is 68 bytes:

| Field         | Type        | Meaning                                                  |
| ------------- | ----------- | -------------------------------------------------------- |
| `manifest`    | `bytes[36]` | The CID of the latest confirmed manifest, raw as above.  |
| `transaction` | `bytes[32]` | The ID of the Arweave transaction whose data is its CAR. |

A version-1 locator is 70 bytes in all, under `MAX_LOCATOR_LENGTH`, and names a version-1 manifest. Version 2's body is version 1's, 70 bytes in all, and names a version-2 manifest, and version 3's is the same and names a version-3 manifest. A body of any of the three of any other length is `locator-length`, and one whose `manifest` isn't a raw CID is `locator-cid`, each reported as step 1 reports. Version 0 never occurs (the anchor refuses it), and every other version is reserved for a later scheme (ANS-104 bundles, or another store), each with its own fixed length. A reader that knows only version 1 reports a version-2 locator as `locator-version`, as it would any version it doesn't know; `packages/verifier` reads versions 1 and 2 since P4-3 part 3b-3b and version 3 since part 3b-3c-2b-1.

The worker sends the latest confirmed manifest's locator with every anchoring call once one exists ([[contracts]], Archive locator), and after an election closes, a locator-only call once a manifest that meets the locator rule (Who writes them) reaches every manifest listing that election's objects, posting a closing manifest that only links stragglers if needed ([[0005-permanent-archive]], the final anchor). `packages/core`'s `anchorBoards` does both (P4-3 part 4b-2a). Once per run, before any call, it reads the archive's locator and the one the anchor holds. It carries the archive's in every call with checkpoints if the anchor holds none, the same, or one naming a manifest of the archive's own chain at or below the archive's latest; otherwise it carries none and reports it, so the worker never overwrites another chain's locator and a run's own never fall below the one it read. Runs are serialised across processes by a session lock on the worker's database, and a run that meets it does nothing (`anchor-busy`), since a run whose call landed after a later run's would set the locator back one step until the next run, which a verifier reading in between reports as `locator-mismatch` (T-69). The lock is lost silently if its connection drops, so every worker must reach Postgres directly, never through a transaction-mode pooler, and with the same search path, since the lock is keyed by the schema it resolves first. A run that sent no checkpoint call sends the locator alone unless the anchor holds it, so the locator-only call follows each newly confirmed manifest, the final anchor's included, within one run; a run whose checkpoint call failed leaves it to the next run's, since a second call from the authority could replace the pending one and miss its window (T-49). It sends only a version-3 locator naming the highest manifest that meets the locator rule, and none from a database that holds no chain. A database that holds no chain while the anchor names one (after a wipe) never starts a new manifest 0, which would read as an overwritten locator: the archive run first reads the anchor's chain back, from the manifest its locator names down through the links to manifest 0 as The chain from a locator walks it, each manifest from a transaction the worker counts confirmed whose data reads as its CID, and records it with the transactions its objects are listed under, then carries on from that sequence (`packages/core`'s `archiveBoards`, P4-3 part 4b-2b-2b-2). Manifests the lost database wrote above the anchor's were never named by a locator, so no reader is sent to them, and their sequences are written again. A chain that doesn't read whole, is another deployment's, or links two manifests at one sequence is refused and nothing is written. If the archive's locator can't be read the run anchors its checkpoints without one and reports it: a missed window fails an election, while a period anchored without a locator is still found from the next call's.

## Test vectors

`vectors/archive.json` (format `abolish-archive-vectors/1`, see [[vectors/README|vectors]]): manifests at their bounds (one object, one link, both lists full) with their encodings and CIDs, every decode rejection at its offset, locators of version 1 and their rejections as a reader that knows version 1 reads them, and transaction data read as an object, over-bound or inconsistent (a missing block, a block repeated, out of order or empty, a CID of another object, a dag-pb root whose length isn't where canonical form puts it, a non-minimal or nine-byte varint, trailing bytes). `packages/crypto/scripts/archive-vectors.py`, an independent Python implementation of this page, prints them.

`vectors/archive-v2.json` (format `abolish-archive-vectors/2`): version-2 manifests (evidence alone, evidence beside objects and links, two records for one contract and block, and every list full) with their encodings and CIDs, every version-2 decode rejection at its offset and each version-1 rejection's verdict under version 2, contract-event evidence records (from `output-root.json`'s Base Sepolia game and block, and at every bound) with their encodings and CIDs and every decode rejection at its offset, and locators of versions 1, 2 and 3 as a reader that knows versions 1 and 2 reads them. `packages/crypto/scripts/archive-v2-vectors.py`, an independent Python implementation, prints them.

`vectors/archive-v3.json` (format `abolish-archive-vectors/3`): version-3 manifests (runs alone, runs beside objects, links and evidence, two runs for one contract and `first`, the edges, and every list full) with their encodings and CIDs, every version-3 decode rejection at its offset and version 2's rules at theirs; contract-event runs (one of a single event, one whose events are `contract-event-v9.json`'s election-registry sequence, at every bound of a run's fields, and at `MAX_CONTRACT_EVENT_RUN`, past one chunk) with their encodings, CIDs and each event as its contract-event record, and every decode rejection at its offset; and locators of versions 1 to 4 as a reader that knows versions 1 to 3 reads them. `packages/crypto/scripts/archive-v3-vectors.py`, an independent Python implementation reusing only the two earlier generators' encoders and CIDs, prints them.

## Known-weak

- **Nothing archives yet.** The worker's uploads and its confirmation rule are P4-3 part 4, and the first funded upload waits for the owner ([[0005-permanent-archive]], Default). Until then the archive path reports nothing found, and the board is read from IPFS only. The worker writes contract-event evidence and runs only once a deployment supplies their source (part 4b-3b).
- **The writer's evidence is coarser than the rule.** The worker examines the periods its taken checkpoints name, each contract's in order, so a period whose first checkpoint is taken after a later period was examined is never examined, and its events are counted by the next record (4.4 sees them a period later; nothing fails). The record at close is the seal's period's, like any other; a separate one after the last anchored period is a later part. The source is trusted for liveness: one that never answers holds the archive's lock and with it the board's objects, so the worker's source must time its reads out (P4-3 part 4b-3b).
- **A wipe restarts the evidence.** The worker's place in each contract's sequence is operational, so after a wipe of Postgres it examines every anchored period again from the first, a bounded number a run. The same games give the same records and runs, which it marks as listed where the resumed chain lists them; a game the L1 resolved differently in between would give a second record and a run at the same `first`, which a reader takes in `cid` order, leaving a replay it breaks unverifiable, never failed (T-53). Runs of such a record that the resumed chain doesn't list stay unlisted, since their record is listed already.
- **The archived evidence decides nothing yet.** A run of a format-6 bundle that reads the archive takes the board contract's latest record it can prove for 4.6, in place of a bundle proof that doesn't hold or is too early for `t_A`, never one dated after the finalized L1 time, and a record can show the ballot extent held but never fail it (`evidence-unchecked`) until its game is read on L1 ([[verifier]], Archive, step 5, and Availability; P4-3 part 3b-3c-1). 4.4 replays each contract's archived events against every record of its evidence and holds the board's records to them ([[verifier]], Contract events, step 6; P4-3 part 3b-3c-2b-2), but for the same reason a replay that doesn't hold, or a boarded record the archive doesn't hold, leaves 4.4 unverifiable, never failed. 4.6 takes the board's archived events where the bundle's don't reach the proven count ([[verifier]], Availability, step 3; P4-3 part 3b-3c-3): replayed to the bundle's own root they count as its events would, and to an archived record, for no more than the record does. The board is the last of the four contracts the replay's run budgets are shared by, so a shared registry's archive (junk creations included) can spend them first and leave 4.6 the bundle's events alone: unverifiable, never wrong (T-52). Nothing archives yet in any case (part 4).
- **Evidence is worth its game.** A record names its game by index and address, but no reader checks the game on L1 before P1-19 reads dispute games, so until then the output root is the record's word, as a bundle's is (T-71). A record whose block no respected game claims is the worker's failure to write, never a verdict.
- **Evidence carries the L2's own bytes, and until its game is checked, the authority's.** A record whose root a respected game claims carries the header the L2 filled, among them `extraData` (the sequencer's, a few bytes on the OP Stack) and `logsBloom`, 256 bytes whose bits anyone with a log in that block can grind toward, and trie nodes holding other accounts' hashes along the proof's path; the authority then chooses nothing beyond which game and block it names, and the evidence check refuses a node the proof doesn't use. But until a reader checks the game on L1 (P1-19), the output root is the record's word, so the authority can build a whole record (a header of its choosing, a message-passer root and a made-up state whose leaf holds the true accumulator, with the root they hash to) that passes the evidence check: every byte of a record, up to 35,459, and of up to 1,024 records a manifest lists, is then its choice, and the unused-node rule doesn't reach the sibling references inside a node the proof walks (T-17). Once games are read, a record whose root no respected game claims is reported as worth nothing, but stays archived: the authority alone writes the archive, and can already post anything to Arweave under its own key.
- **A run is judged only by its replay.** A run that decodes may hold any blocks, timestamps, topics and data; only the accumulator's replay against evidence shows it is the contract's history, and the evidence is worth its game (above). Two runs at one `n` are both read only as far as the first that is taken (The event replay), so an authority that lists a false run before the true one leaves the replay unverifiable though the true run is archived (T-53: never failed). A contract's archived sequence grows with every event of every election through it, junk creations included, so a reader replaying a shared registry at close reads all of it once per run of the verifier, bounded by its budgets (T-52).
- **Base-layer transactions only**: one transaction per object costs a transaction's overhead each, about two per election per period. ANS-104 bundles, which would let a bundler pay by card, would be a new locator and manifest version carrying the bundle and item IDs, read without a gateway's index.
- **Chosen bytes**: each `transaction` is 32 bytes the authority can choose, since no verifier checks a signature behind it, so a version-1 manifest carries at most `32 · (8192 + 1024)` bytes of them, and a version-2 manifest also each reference's `contract`, `l2_block`, CID digest and `transaction` for a record nobody fetches, 92 bytes each, `1024 · 92 = 94,208` more, and a version-3 manifest each run reference's `contract`, `first`, `count`, CID digest and `transaction`, 96 bytes each, `1024 · 96 = 98,304` more, on top of the locator's 128 (T-17; [[contracts]], Known-weak). A run whose events aren't the contract's is the authority's choice of up to 16 MiB, as any object it uploads is; a reader fetches only the runs its replay needs, and an honest run carries only what our contracts emitted ([[contracts]], Contract-event record). Nothing in it is personal data unless the authority puts it there, and the authority can already post anything to Arweave under its own key.
- **The tree is the authority's**: a seized authority can post a manifest that links nothing earlier and overwrite the locator with it; the gap is reported (`archive-gap`, `locator-mismatch` while the logs last), and the earlier manifests stay on Arweave, found by anyone who kept a locator or a manifest's ID (T-69).
