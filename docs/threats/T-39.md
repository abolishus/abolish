# T-39: Cryptographic implementation flaws

- Area: Integrity and verifiability (G-7, G-8, G-9)
- Adversary: A-9, A-2, A-6
- Status: **Planned.** Residual: JavaScript gives no hard constant-time guarantees; `@noble/*` documents its own limits, which apply to us.

## Threat

Reused or biased encryption randomness (reused ElGamal randomness leaks vote differences), non-CSPRNG randomness, missing point or subgroup validation (invalid-curve and small-subgroup attacks), secret-dependent timing, or a hand-rolled or non-audited primitive creeping in.

## Mitigation

Primitives only from audited `@noble/*` (`packages/crypto` depends on nothing else, CI-checked, closure check in P1-9); point and scalar codecs with canonicity checks (P1-11): the group is ristretto255 ([[0007-group-and-hash]]), whose RFC 9496 decoding is canonical and has no cofactor, so there is no subgroup to check; the identity is rejected unless a field allows it, and scalars at or above the group order are rejected, never reduced; complaints answer no static-DH query (so Cheon's attack doesn't apply), because each share ciphertext proves knowledge of its DH ephemeral, so a complaint reveals only a DH value its poster already knows ([[share-encryption]]); secret randomness only from the platform CSPRNG, owned by `packages/crypto`, with deterministic randomness only behind a test seam; constant-time secret comparison; published vectors and property tests; `crypto-review` (P1-9, P1-11, P1-12).

Index: [[THREAT_MODEL]].

## History

- 2026-10-10 (P1-11): group fixed as ristretto255 ([[0007-group-and-hash]]). "Subgroup checks" replaced by canonical RFC 9496 decoding (no cofactor, so no subgroup to check); rejection of the identity (unless a field allows it) and of scalars at or above the group order added; static-DH loss bound under Cheon's attack (6.4 bits or less, with complaint queries per trustee key below 2³² by P1-12 and P1-13) added.
- 2026-10-10 (P1-11, implementation): built in `packages/crypto` ([[group]]): `scalar`, `element` and `elementOrIdentity` codecs as thin wrappers over `@noble/curves` 2.4.0, the element encoder re-decoding its own output; checked against RFC 9496 Appendix A.1–A.3, RFC 9380 Appendix K.3 and RFC 9497 Appendix A.1, our `group.json` vectors from an independent Python implementation, and fast-check properties. The static-DH factor search is published as `packages/crypto/scripts/static-dh-factors.ts`, with a test of its trial-division table.
- 2026-10-11 (P1-12, part 2): share encryption decodes strictly ([[share-encryption]]): the ML-KEM encapsulation key must pass FIPS 203's modulus check, the DH key, the DH ephemeral and a complaint's DH value are never the identity, and the DH secret is never 0. A ciphertext's proof of knowledge of its ephemeral means a complaint reveals only a DH value its poster knows, so complaints are no static-DH oracle. ML-KEM-768 (`@noble/post-quantum`) is checked against Go's accumulated FIPS 203 vectors and ChaCha20-Poly1305 (`@noble/ciphers`) against RFC 8439; `@noble/post-quantum` makes no constant-time claim for ML-KEM ([[share-encryption]], Residuals). The complaint-query budget below 2³² per trustee key that the mitigation named is retired: no oracle remains to bound.
- 2026-10-12 (P1-15, part 2b): the summed-share message decodes strictly (no identity or non-canonical `ct_DH`, a high-`s` signature rejected), and a recipient checks the context and the sender's signature before it decapsulates, so through this message only a registered seat can make a trustee run ML-KEM decapsulation on a chosen ciphertext (share intake still decapsulates any chosen `ct_M` for anyone, [[share-encryption]], Residuals, and a key recovered there also exposes recorded summed-share messages); nothing derived from a decryption is ever revealed and no result code is reported back to the sender, so it is no computational Diffie–Hellman oracle: a registered sender learns at most an accept or reject bit, a decisional query on the recipient's DH key, the setting of the hashed-ElGamal and X-Wing CCA arguments. A later change that reported `summed-decrypt` against `summed-check` to the sender, or revealed `ss_DH` or `K`, would need a proof of knowledge of the ephemeral first, as share encryption has ([[tally]], Summed-share message).
- 2026-10-12 (P3-4 part 2b-1, [[keyed-nullifier]]): Baby Jubjub, unlike ristretto255, has cofactor 8, so every `bjj-point` is decoded from affine coordinates below `p`, checked on the curve and in the prime-order subgroup (`isTorsionFree()`, which `@noble/curves`' Edwards decoding skips), and rejected as the identity unless a field allows it; scalars at or above `l` are rejected. A query point with a small-order component would otherwise make a seat's answer reveal its share modulo 8. `HashToScalarBJJ` is RFC 9380 `hash_to_field` over SHA-256 with an explicit `DST`, and the package's import test allows that generic layer in this one file only.
- 2026-10-12 (P3-4 part 2b-2a, [[nullifier-key]]): a dealt share reaches decapsulation only if its hash is the one its dealer signed for the recipient, so only a panel seat's signed dealing makes a node run ML-KEM decapsulation, and nothing about a decapsulation is revealed: a complaint names the dealer, which answers with the share itself.
- 2026-10-13 (P3-4 part 2b-2b, [[nullifier-reshare]]): a reshared share reaches decapsulation only if its hash is the one its dealer signed for the recipient, as for a dealt share, so only a predecessor seat's signed dealing makes a new seat's node run ML-KEM decapsulation.
- 2026-10-13 (P1-12c part 1, [[share-encryption]], Intake and receipts and Residuals): trustee intake runs the ballot record's admission checks, its membership proof included, before it decapsulates, so the remote decapsulation endpoint that intake is (ML-KEM's arithmetic makes no constant-time claim) is open only to holders of a registered member's secret, a Tier 0 one included, rather than to anyone. Rate limits are still needed, and may now be per nullifier.
- 2026-10-13 (P3-4 part 2b-3a, [[keyed-nullifier-hashes]]): TACEO's `babyjubjub` gadgets at `oprf-nr` v1.0.0 differ from the audited code (`50798b4`) only mechanically (`u1` to `bool`, a renamed Poseidon2 import, `sgn0`'s return type); our circuits use only the Edwards arithmetic, the subgroup check and the map, never the Montgomery code behind finding B, and every point reaching `add` must be on the curve, since its constraints fix the sum only while its denominators are nonzero.
- 2026-10-17 (P2-21 part 1, [[0009-membership-proof]], Amendment): the ballot client's Groth16 prover is snarkjs, not one of ours over `@noble/curves` (a second implementation of Semaphore's witness, and an estimated 5.5× slower). It runs in a prover worker of its own; the ballot worker verifies its output under the pinned key against inputs it computed and then re-randomises it with CSPRNG scalars in `packages/crypto`, so zero knowledge doesn't rest on snarkjs's own randomness (a ChaCha stream ffjavascript implements, seeded once from `crypto.getRandomValues`) or its correctness.
