## Scope

`apps/api` (Hono + oRPC): board read, ballot submit, election definitions.

Must include the T-10 no-join test for this app: no request log line, metric label or cache key carries both an account or session identifier and a ballot, nullifier or poll-participation value.

## Plan

1. **Read side and request log** (this part): every procedure of the contract, with `ballots.submit` failing closed; election definitions stored in core; the T-10 request-log test.
   2a. **Strict JSON bodies** (this part): a body whose objects repeat a key is refused before admission exists to read it (T-31).
   2b. **Heads and proofs in O(log n)** (this part): the board tree's perfect subtrees stored as each entry is appended, so a head or proof reads O(log n) rows (T-52), as part 1's known-weak required before part 2 boards ballots.
   2c. **Each board under its pinned version** (this part): entries encoded, hashed and chained under the board-entry version the election's stored definition pins, never version 1 by default, since every plurality or approval profile pins version 4 (verifier 2.3) and a board under version 1 would fail 2.3 and 4.x for every entry the server boards.
2. **Ballot admission**: `ballots.submit` decodes the record strictly and runs the admission checks (verifier 5.1 to 5.5, 5.7, 5.8) before `appendEntry`, with the segment taken from the anchoring clock. Needs P1-17b (membership proof verification) and the ballot record's decoder; until then the server boards nothing, and nothing is lost: a voter can submit directly once P1-18's direct submit exists (T-25).
   2d. **5.1 to 5.4 before boarding** (this part): the verifier's own admission, exported for one ballot at a time, run by core against the definition, the panel the release pins and the transcript at the board's start; the window by the server's clock and the segment by the anchoring clock.
   2e-1. **Repeats** (this part): 5.7, refusing a ballot with the tier, nullifier and message of one already boarded; the same bytes again get their entry.
   2e-2. **The L1 reference** (this part): 5.8 against finalized L1 blocks the worker reads from an L1 node, refusing only what the finalized chain already rejects.

## Built (part 2d)

- `packages/verifier` (`src/admission.ts`): `electionAdmission(definition, panel, entries)`, the verifier's admission for one ballot at a time. From the definition's bytes it runs what the report's rows run before admission: strict decoding and well-formedness (2.1), a readable board-entry version and profile (2.3), the transcript check against the panel (2.5's panel, 3.2, through `ceremonyChecks` unchanged), then the same `judgeFor` that `ballotChecks` uses (1.3's key and zero roots included). It refuses the election with the first check that stops every ballot, or returns `admit(payload)`, which refuses a payload of another record type and otherwise decodes strictly and runs 5.1 to 5.4. `readDefinition` and `isReadable` moved from `verify.ts` to `definition.ts` to be shared; no verdict changes. A changeset (minor).
- `packages/core` (`src/admission.ts`): `BallotAdmissions` (the pinned panels and the anchoring clock's epoch and period; a malformed panel throws at construction). `submit(sql, electionId, ballot, now)` reads the stored definition and only the board's first entry, where the operator boards the transcript, and tries each pinned panel until one isn't `panel-unpinned`. A decision is kept in memory per election (definitions and the first entry are write-once), admissions and refusals in separate least-recently-used caches of 1,024 each, so refusals can't evict an admission; a missing transcript is never kept. Then it refuses outside `[opens_at, closes_at]` at `now`, runs `admit`, and appends in segment `(now − epoch) / period`, raised to the board's last segment if a later-labelled ballot was boarded meanwhile (`appendEntry`'s new `raiseToPrevious`), so racing submissions never fail `segment-decreased` or land below a segment already boarded. Refusals are `SubmitError` (`unknown-election`, `not-open`, `rejected` with the verifier's code), with nothing written. `appendEntry` now also returns the encoded entry.
- `apps/api`: `ballots.submit` boards through it and answers `{ entry, link }` (201); `BALLOT_REJECTED` (422) carries the verifier's code, `ELECTION_NOT_OPEN` (409) an election that can't take ballots now, `ELECTION_NOT_FOUND` (404) one with no definition. The server takes `admissions` and a clock (`now`, the system clock by default; Date.now stays in the transport). `src/main.ts` reads `API_PINNED_PANELS` (JSON panels, keys as hex), `API_ANCHOR_EPOCH` and `API_ANCHOR_PERIOD`; without the panels it boards nothing, as before, and an anchoring clock without panels refuses to start.

## Known-weak (part 2d)

- **The L1 reference (5.8), repeats (5.7) and the close rule (5.5) aren't checked at submission** (part 2e). A member can board ballots naming a stale or unknown L1 block, or repeats of one ballot; each is a whole valid ballot, which the verifier rejects or ranks later, so none counts wrongly, but each costs a board entry (T-17, T-52).
- **The window and the segment come from the server's clock**, not from L1 time or L2 timestamps: a skewed clock refuses ballots near the ends, which voters can still submit directly (T-25), and labels segments that voters' clients check within one period ([[board]], Client checks). A clock that steps back labels ballots with the board's last segment until it catches up. The segment is never raised to the election's first segment `f`, which the server doesn't read yet.
- **Nothing boards the transcript yet.** Admission needs it as the board's first entry, where the verifier finds it anywhere by its hash: a board whose first entry is anything else (a mirrored registration event, an early direct-submitted ballot, once those are boarded) takes no ballot through the server, which a voter can still submit directly (T-25). Whoever boards first must board the transcript first, or the lookup must find it by hash with an index; and the coordinator that would board it is [[P2-13]]'s; until then only tests put it there. 3.1's L2 side (the trustee registry's record of the transcript and its approvals) isn't read, as in the verifier.
- **One anchoring clock per server**, for the anchor contract our definitions name; a definition naming another anchor contract gets segments from the wrong clock.
- **Every submission costs a membership and a validity proof's verification**, bounded only by the 32-request in-flight cap; there is no rate limit (T-52).
- **Only definition version 1 is stored** (`storeDefinition`), so admission runs under version 1 here, though the verifier's export reads versions 1 and 3 to 5.

## Known-weak (part 2e-1)

- **A retry gets its old entry, never a receipt of the board as it was then.** When the operator's receipts are signed by the server ([[receipts]]: the board of `i + 1` entries, the voter's entry last), the retry path must sign that historic state (computable from the stored subtrees), not the current head. A retry more than a period after boarding returns the old segment, which a client judging board client rule 1 against its retry time may refuse and then submit directly; its vote still counts. To settle with the receipt signer and the client (P2-8).
- **`repeat` carries no entry index**, so a client refused (one that also submitted directly, or re-proved the membership proof against client rule 3) can't check that an equivalent ballot is boarded and falls back to direct submission. The index is public and could go in the error's data; the contract's error data is `{ code }` for now.
- **A byte-identical retry pays the full admission**, and after `closes_at` is `not-open` like any ballot, though it is boarded; finding identical bytes first would need a payload-hash index.
- **The migration refuses a populated board, and no rebuild job exists yet** (reference election stage 8). A board with ballots (staging, if any were submitted since #248 with pinned panels configured) must be wiped by hand; a rebuild must compute the keys by replaying admission, and until it does a rebuilt board has none. The check doesn't lock `board_entries`, so an old API still running during the migration can board unkeyed ballots, which then take re-randomised copies: board entries only (T-52), the verifier still finds the repeats.
- **Only `BallotAdmissions` keys ballots.** `appendEntry` without the option boards a ballot without a key (tests do), and such a ballot makes nothing a repeat.
- Part 2d's other known-weak points stand, except repeats: the L1 reference (5.8) is part 2e-2's.

## Known-weak (part 2e-2)

- **One L1 node is trusted.** A node lying about a finalized block's hash or timestamp can make the server refuse honest ballots, which voters answer by submitting directly (T-25), or board bad references, which the verifier rejects. Several providers that must agree, or a light client, is not built.
- **Pending references are boarded unjudged.** A member can still board ballots naming a recent, not yet finalized block by a wrong hash, each costing one entry and its proofs' verification (T-52). Judging them against the node's unfinalized chain would refuse a ballot a reorganisation could still make valid, so this part doesn't.
- **An unreachable node turns the check off**, silently for voters: ballots are boarded unchecked, as before this part, with only the log line to show it.
- **The first ballot of each new `opens_at` costs about 25 sequential block reads** (the search from block 0); on a slow node that spends the batch's budget, and its ballots are boarded unchecked; the blocks read are kept, so the search finishes over later batches.
- **A load-balanced node can still answer a block from a backend that hasn't finalized it**, on another branch: that hash, or a wrong `l1_ref_min`, is kept for the process's life, and honest ballots could be refused until the worker restarts (voters submit directly). Checking each probe's `parentHash` links, or several providers, would close it; part of the trusted-node residual above (T-34).
- **A byte-identical retry of a ballot boarded `pending` or `unchecked` can now get 5.8's verdict** (`l1-ref-unknown`, after its block finalized by another hash) instead of its entry. The verifier rejects that ballot anyway, so the answer is right about what counts; finding the entry first would need a payload-hash index (part 2e-1's known-weak).
