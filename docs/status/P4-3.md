# P4-3: IPFS mirroring and permanent archive

- State: in progress (part 1, content addressing, merged in #PR; part 2, board data availability, next)
- Branch: `claude/p4-3`
- Phase: Phase 4: Censorship resistance

## Scope

IPFS mirroring of board + ballot client, plus the permanent archive per ADR.

## Plan

1. **Content addressing** (#PR): [[content-addressing]]'s CIDs and CARs in `packages/crypto`, with vectors from two independent IPFS implementations, so the parameters stop being provisional.
2. **Board data availability**: make a withheld anchored extent attributable ([[board]], Residuals, withheld tails): a content address per anchored segment bound into what is anchored, and a publication deadline, so a node or verifier can tell non-publication from absence. An ADR first (what is anchored changes, and with it P4-1's contract). It also closes [[P1-12c]]'s residual on a newest ballot that never reached the board, and makes receipts' `unresolved` evidence attributable ([[receipts]], Residuals).
3. **Archive manifests and their Arweave layout** ([[0005-permanent-archive]], Consequences), with an Arweave test harness for the reference election. The first real upload spends money and waits for the owner.
4. **Mirroring**: the worker pins every segment object, entry-hash list and display-text record on IPFS, and the ballot client's releases; community nodes pin by default (P4-5).

## What was built (part 1)

- `packages/crypto`: `contentDag` (fixed 1 MiB raw leaves, a balanced tree of dag-pb UnixFS `File` nodes of at most 1,024 links, every block once in depth-first pre-order), `objectCid`, `cidText` (base32, `b` prefix) and `objectCar` (CARv1). dag-pb, UnixFS and the dag-cbor CAR header are written by hand, so the package keeps to `@noble/*`.
- [[content-addressing]]: the parameters are no longer provisional; how to set Kubo and ipfs-unixfs-importer to them (Kubo's default is 174 links per node, not 1,024); the encodings byte for byte; Test vectors.
- `docs/spec/vectors/content-addressing.json` from `packages/crypto/scripts/content-addressing-vectors.mjs`, run outside the workspace: each CID and CAR from Kubo 0.36.0 (sha512-checked release) and from ipfs-unixfs-importer 17.1.1 with @ipld/car 5.4.7, refused unless they agree byte for byte.
- T-51 history.

## Tested (part 1)

- 15 vectors: one byte, 100 bytes, exactly one chunk, one chunk and a byte, three chunks, two identical chunks of zeros (one leaf, carried once), and under a small layout profile (256-byte chunks, 4 links) trees of 1, 4, 5, 16, 17, 21, 64 and 65 leaves, with partial groups at every level, and 17 identical chunks. Each CID and CAR is reproduced byte for byte (small CARs whole, larger ones by length and sha256).
- Properties (`FC_NUM_RUNS`): an object of at most one chunk is one raw block whose CID hashes it; every block is listed once with the root first and each CID hashing its block; any changed byte changes the CID. Refusals: an empty object, limits outside the layout.

## Known-weak (part 1)

- Nothing reads or writes these yet: the worker's pinning and the verifier's fetch by CID come with parts 3 and 4, and P4-6.
- The vectors cover the layout's deeper levels only under a small profile; a two-level tree under the real parameters needs an object over 1 GiB, which no vector carries.
