## Part 1: the ADR

- [[0020-entry-points]], option A: the ballot client only on the second domain (its RP ID, serving nothing else) and at `abolishus.eth` through a gateway that gives the name its own origin (`abolishus.eth.limo`), plus `apps/node`'s local origin; abolish.us serves `apps/web` and links to the client. Rejected: a ballot host on another US name (B) and listing the gateway as a related origin of the RP ID (C).
- Threat files T-41 and T-49 record the change.
- Tested: documentation only; `vp check` formats it.

Known-weak:

- Seizing the second domain orphans every recovery backup and puts its seizer inside the RP boundary (T-41, T-49).
- A voter's identity doesn't follow them to another entry point. Until P2-6 or P2-8 adds a voter-initiated transfer between the client's origins, a voter reaching the ENS or `apps/node` entry point during an outage can vote there only with an identity created there.
- The ENS gateway's operator is trusted for the bytes it serves, as any host is; the verifier's served-client check and `apps/node` are the checks.
- The TLD's legal facts come from the registries' own pages (cited in the ADR), not from counsel.

## Part 2a: the release record ADR

- [[0036-release-record]], option B: each release record's hash is appended to an immutable L1 release registry whose only writer is the release Safe of [[0020-entry-points]]; the registry keeps the releases in one chain (`previous`, `sequence`) and a revocation set in storage, so [[verifier]] 1.1 and `apps/node` prove a release published and not revoked from a finalized L1 header, as the verifier already proves anchors. Sigstore keyless signing and SLSA provenance stay as the CI evidence the Safe's signers check. Rejected: Sigstore as the trust root (A: GitHub and Sigstore's keys in the trust base, and an X.509 and Rekor parser in the verifier) and off-chain maintainer keys (C: a release signed for one voter need never be published).
- The ADR fixes what the record binds (the chain fields, the source commit, each site's files, directory CID and headers, the entry points and challenge origin, and the deployment the client is built for); its bytes are part 2b's.
- Threat file T-41 records the change.
- Tested: documentation only; `vp check` formats it.

Known-weak:

- A Safe quorum, or whoever compels one, can still publish a bad release; the registry makes it public, not impossible.
- `abolishus.eth.limo` serves the bytes without the record's headers (no `frame-ancestors`, no header CSP for the workers); part 3 must establish what the gateway can send before the name is listed (T-43).
- Releases are recorded on Sepolia only until the owner deploys the registry on mainnet and names the Safe's signers.
- The registry is one more L1 contract whose creation code 1.2 must bind before it is deployed (T-64).

## Part 2b-1: the release record's bytes

- [[release]]: record type `0x001f`, version 1: its place in one registry (`l1_chain_id`, `registry`, `sequence`, `previous`), the source commit, `deployment_hash` (the deployment record, `0x0020`, reserved for part 2b-3, so new contracts or pins need a new deployment-record version rather than a new release-record version), and up to two sites (the ballot client, the challenge page), each with its HTTPS origins, a `loopback` flag for `apps/node`, its response headers, up to 1,024 files (path, length, SHA-256, media type) and its directory CID. Strict decoding, twenty well-formedness rules in a fixed order with codes (strict grammars for origins, header names and values, paths and media types, so every text field has one reading), the release hash `H(DS("abolish/v1/release", record))`, how a host serves a site and which loopback origins `apps/node` may use.
- [[content-addressing]], Sites: a site is one UnixFS directory of plain dag-pb directory nodes (links in name order, `Type = Directory` only), never sharded at the record's bounds; its CID and CAR.
- [[versioning]] (`0x001f`, `0x0020` reserved), [[domain-separation]] (`abolish/v1/release`, `abolish/v1/deployment` reserved) and `packages/crypto`'s two registry tables, which a test compares with the spec; [[verifier]] 1.1 and its pinned trust roots name the record and the registry; [[registration]]'s challenge origin is the record's challenge site. T-41 history.

Tested:

- `docs/spec/vectors/site-directory.json` (10 sites) from `packages/crypto/scripts/site-directory-vectors.mjs`: Kubo 0.36.0 and ipfs-unixfs-importer 17.1.1 agree on every CID and CAR, byte for byte.
- `docs/spec/vectors/release-record.json` (97 vectors) from `packages/crypto/scripts/release-record-vectors.py`, standard library only, which first rebuilds every site of `site-directory.json` from the spec alone (a third implementation) and refuses any difference; every rule has an ill-formed vector, every bound a decode rejection.
- `packages/crypto/tests/release-record-vectors.test.ts` decodes every vector with codecs built from the file's own type descriptors (round trip, the release hash, every decode error code) and checks each well-formed record's sites against `site-directory.json`.

Known-weak:

- Nothing reads a release record yet: the codec, the rules and the site layout in `packages/crypto` are part 2c's, so until then the rules are checked only by the generator.
- `deployment_hash` names a record whose layout part 2b-3 defines, so a version-1 record's deployment can't be read until then.
- Header values are free text under a byte grammar: no rule judges a policy, so a release with a weak CSP is well formed (the Safe's signers and 1.1's report are the checks).
- A site at its bounds is 256 GiB; readers bound fetches by the record's lengths.
