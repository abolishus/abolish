# Share delivery on the board

How a ballot's delivery to each trustee is shown on the board, and how anyone decides from the board which ballots were delivered and which a proven complaint excludes: the share-receipt record (`0x000c`), the share-posting record (`0x000d`) and the share-complaint record (`0x000e`), each version 1; the delivery deadline and the complaint window; the board operator's boarding rules; and the delivery check that the counted set of [[tally]] applies. This is the delivery and counting step of [[0002-everlasting-privacy]] (option B, accepted by the owner: Deadline, Complaints, Complaint window), with the owner's 2026-10-12 decision on its fallback: a client never posts a seat whose receipt passes, posting is the voter's explicit last resort, and only postings sent through the contract path deliver. What each record proves is in [[share-encryption]] (Intake and receipts, Public posting, Complaints); this page puts it on the board. Notation is from [[notation]], the ballot hash from [[ballot-validity]]. Threats: T-41, T-29, T-25, T-17, T-15, T-31, T-34, T-52, T-54.

## Versions

None of the three types is pinned in an election's profile. Versions 1 and 2 of the ballot record (`0x0002`) fix all three at version 1, together with the windows below ([[versioning]], Three levels), so delivery can't drift from the ballots it delivers: the ciphertexts' associated data name ballot version 1's share-ciphertext rules, which version 2 keeps, and the ballot hash names the ballot's own version ([[share-encryption]], Ciphertext; [[ballot-validity]], Ballot hash, Ballot record (version 2)).

Share receipts and complaints reach the board through the board path only under board-entry versions 3 and 4, which allow them ([[board]], Allowed payloads); no board-entry version allows a share posting, which reaches the board only as a contract event (Direct submit); version 2 is never assigned, since a frozen vector of `board.json` uses it as the version that doesn't exist. Under board-entry version 1 no receipt could be boarded through the board path, so a profile that pins ballot version 1 or 2 MUST pin one of them: [[verifier]] 2.3 fails a profile pinning ballot version 1 or 2 with any other board-entry version (`profile-combination`), the ballot client refuses to cast in such an election, and P1-18's election registry MUST refuse to register such a definition, so the mistake is caught before the election exists rather than after. A later board-entry version that also allows receipts and complaints adds itself to this rule, as version 4 does; [[tally]], Destruction, narrows the choice to version 4 for every profile that pins tally-opening version 1.

## Records

### Share receipt (`0x000c`, version 1)

A trustee's share receipt ([[share-encryption]], Intake and receipts) as a record: its signed statement, then its signature.

| Field             | Type        | Meaning                                                                         |
| ----------------- | ----------- | ------------------------------------------------------------------------------- |
| `definition_hash` | `bytes[32]` | The election's definition hash                                                  |
| `ballot_hash`     | `bytes[32]` | The ballot hash of the public part the trustee checked ([[ballot-validity]])    |
| `seat`            | `u8`        | The trustee's seat, `i`                                                         |
| `share_hash`      | `bytes[32]` | `H(ct_i)`                                                                       |
| `signature`       | `p256-sig`  | The seat's signature under `abolish/v1/sig/share-receipt` over the first fields |

The fields before `signature` are exactly the 97-byte statement `m` the trustee signs ([[share-encryption]], Intake and receipts), so a node's receipt becomes a record with no new signature. 164 bytes with its header.

### Share posting (`0x000d`, version 1)

The client's public posting of one ciphertext with its ML-KEM message ([[share-encryption]], Public posting), made only by the voter's explicit choice (Client rules) and sent only through the contract path (Direct submit): a posting that reaches the board any other way delivers nothing.

| Field             | Type               | Meaning                                                                 |
| ----------------- | ------------------ | ----------------------------------------------------------------------- |
| `definition_hash` | `bytes[32]`        | The election's definition hash                                          |
| `ballot_hash`     | `bytes[32]`        | The ballot hash of the ballot the posting delivers                      |
| `seat`            | `u8`               | The seat the ciphertext is for, `i`                                     |
| `m`               | `bytes[32]`        | `m_i`, the ML-KEM message                                               |
| `ciphertext`      | `share_ciphertext` | `ct_i`, decoded strictly as [[share-encryption]] (Ciphertext) specifies |

A posting carries no signature: only a party that knows `m_i` can make one that passes, and a passing posting is the same whoever boards it ([[share-encryption]], Public posting). Since `ciphertext` decodes strictly, a ciphertext that doesn't decode makes the record fail to decode, so `posting-malformed` never arises for a record that decodes. Its check hashes `ct_i` as encoded in the record, which is `ct_i`'s one encoding. 1,308 + 64·`m` bytes with its header, for `m` options: 1,948 bytes at 10 options, 5,404 at `MAX_OPTIONS`.

### Share complaint (`0x000e`, version 1)

A trustee's complaint about a posting ([[share-encryption]], Complaints), signed so that an unfounded one is attributed.

| Field             | Type              | Meaning                                                     |
| ----------------- | ----------------- | ----------------------------------------------------------- |
| `definition_hash` | `bytes[32]`       | The election's definition hash                              |
| `ballot_hash`     | `bytes[32]`       | The ballot hash of the ballot whose posting it is about     |
| `seat`            | `u8`              | The complaining seat, `i`                                   |
| `proof`           | `complaint_proof` | `D` and its Chaum–Pedersen proof                            |
| `signature`       | `p256-sig`        | The seat's signature under `abolish/v1/sig/share-complaint` |

The signature is an ECDSA P-256 signature by seat `i`'s per-election signing key ([[trustee-identity]], Which key signs what), under `abolish/v1/sig/share-complaint`, over

```
m = definition_hash ‖ ballot_hash ‖ u8(seat) ‖ encode(proof)
```

161 bytes: the record's fields without its header and signature. It **attributes** the complaint to seat `seat` if and only if `seat` has registered keys ([[ceremony]], Transcript check) and the signature verifies under that seat's registered signing key, never its identity key; any other complaint is **unattributed**. 228 bytes with its header.

A proven complaint excludes its ballot whether or not it is attributed: its proof shows `D = ct_DH^x` for seat `i`'s registered `dh_i`, which needs `x`, and with it anyone sees the shares fail. The signature only decides whom an unfounded complaint is attributed to (T-29). `m` binds the definition, the ballot and the seat, so a complaint replayed against another election, ballot or seat is unattributed, never framing its signer; the proof itself binds the definition, the seat, the trustee's key and the ciphertext's hash ([[share-encryption]], Complaints).

### Decoding

Each record decodes strictly ([[notation]]): every `element` is canonical and not the identity where its table says so, every `scalar` is below `ℓ`, and nothing trails. Decoding doesn't compare `definition_hash`, `ballot_hash` or `seat` with the election; the delivery check does, so a record naming another election, ballot or seat is still read, and reported. A delivery record that fails to decode, including one under a version ballot version 1 doesn't fix (`profile-mismatch`), is a rejected entry ([[board]], Allowed payloads; [[verifier]] 2.3), listed in the report, never an election failure and never a receipt, posting or complaint. So is a posting that reached the board through the board path (`unexpected-record-type`, as the board entry carrying it is under every board-entry version).

## Windows

Version 1 of the three records fixes two windows, counted from `closes_at + l1_inclusion_bound` (the close rule's deadline, [[election-definition]]):

| Name               | Value   | Meaning                                                                                         |
| ------------------ | ------- | ----------------------------------------------------------------------------------------------- |
| `DELIVERY_WINDOW`  | 172,800 | Seconds by which a ballot's share receipts and postings must be sent: the **delivery deadline** |
| `COMPLAINT_WINDOW` | 432,000 | Seconds by which a complaint must be sent: the end of the **complaint window**                  |

A record's window is applied by its submission time ([[tally]], Tally window). A receipt or complaint that reached the board through the board path has its segment's anchoring period as its submission time, so it is **in time** if its entry's `segment` is at most

```
s_D = period(closes_at + l1_inclusion_bound + DELIVERY_WINDOW)    for receipts
s_K = period(closes_at + l1_inclusion_bound + COMPLAINT_WINDOW)   for complaints
```

where `period(t) = ⌊(t − epoch) / period⌋` under the anchoring clock ([[board]], Timing), so a record boarded in the deadline's own period is in time. That period can end moments after the deadline, so a client or trustee node MUST send its records by the deadline less the operator's boarding latency, and early enough that, if no board entry appears, it can still submit them through the contract path before the deadline, since a contract-path record is in time only by its submission time. A record sent through the contract path (Direct submit, below), and so every posting, is in time if its submission time is at or before the **deadline** `t_D = closes_at + l1_inclusion_bound + DELIVERY_WINDOW` (`t_K`, with `COMPLAINT_WINDOW`, for a complaint), whatever segment its contract event is boarded in. A record that is not in time is ignored: it delivers nothing and excludes nothing, wherever it is on the board.

Both windows, each followed by the contract-event window (a contract-path record sent at a window's end still has to reach the board), are in [[tally]]'s `W_S`, so `s_S ≥ s_K ≥ s_D` and every record that is in time, by either path, is in the counted extent, and the counted set is fixed before any summed share is sent ([[0002-everlasting-privacy]], Tally liveness). Receipts and complaints are the board-path records that can change a counted set, and contract-path receipts, postings and complaints the contract events that can: a receipt or a passing contract-path posting can complete a ballot's delivery, and a proven complaint excludes it ([[tally]], Tally window).

Why these values:

- **Two days for delivery.** A ballot cast at the close normally holds every receipt already (intake runs before the client shows "cast"). The window must first let trustee nodes see every counted ballot anchored, or recorded after forced inclusion, and still send its receipts through the contract path, even forced through L1 (Direct submit: about 28 hours with the deployed constants); the rest covers a client that retries intake because a trustee or the relay is down at the close, a voter who then chooses to post, and a receipt that reaches the board after its ballot. A longer window postpones the counted set and the tally (T-54).
- **Three more days for complaints.** A trustee that was offline during voting must process every posting addressed to it before the window closes, or it can't complain about an invalid one, and its summed shares then fail ([[tally]], Summed-share check), so it can't contribute to the tally. Every posting is a contract event, in L2 data every trustee's own L2 node reads, so the operator can't withhold one through the window. The time a trustee has is `COMPLAINT_WINDOW − DELIVERY_WINDOW` less the contract-event window (a posting submitted at `t_D` may become derivable from L1 only that much later) and less `F`, since a trustee node MUST send each complaint by `c_K = t_K − F`, so that, forced through L1 if the sequencer censors it, its submission time is still at or before `t_K` (Direct submit gives the bound). Three days after the last possible posting covers a weekend; more would postpone every election's seal ([[election-definition]], The seal).

## Boarding

The board operator never boards a share posting: a posting delivers only as a contract event (Direct submit), so it refuses every one sent through the board path, whoever sends it. It boards a share receipt or complaint only if all of the following hold, and refuses every other:

1. It names this election's definition, and `seat` is a seat of the registered key set.
2. A ballot whose ballot hash is the record's `ballot_hash` is already on the board, as a ballot entry or a contract event.
3. It is in time (Windows), boarded in a segment no later than `s_D`, or `s_K` for a complaint.
4. For a share receipt: its signature attributes it to `seat` (the `share-receipt` check against that ballot, with `share_hash` equal to the ballot's `share_hashes[seat]`). For a complaint: a contract-path posting for that ballot and seat, in time, is on the board and passes the public check (`posting-hash`, `posting-proof`, `posting-encapsulation`), the complaint is proven against it (`complaint-proof`, then decryption failing), and its signature attributes it to `seat`.
5. No passing record of the same type for the same ballot hash and seat is on the board yet (a receipt that passes `share-receipt`, a proven complaint), by either path. A failing record, such as junk sent through the contract path, never blocks a passing one.

So a boarded receipt carries no chosen bytes beyond a registered trustee's choice of ECDSA nonce, and a boarded complaint none beyond that and its choice of the proof's nonce `w`, and there is at most one passing record of each type per seat per boarded ballot through the board path (T-17, T-52). Postings reach the board only as the contract's events, never through the board path, so their chosen bytes are bounded by what the contract accepts (Direct submit, Residuals). Without rule 2, a corrupt trustee could archive chosen bytes in receipts for ballot hashes of its choosing. Refusing an unfounded complaint also keeps a readable share out of the permanent archive through the board path (the contract path can't, Residuals): its `D` and the posted `m_i` open the share at once (T-15). An unfounded complaint can't change a counted set, so refusing it costs the result nothing; it only loses the evidence against its signer, which the trustee could have published elsewhere anyway.

The verifier still reads whatever the board holds, as the delivery check below says: a record the operator should have refused is read like any other and, where it fails, ignored, and a posting boarded through the board path is a rejected entry. Reporting such a record against the operator is [[verifier]]'s (P1-19).

### Direct submit

A voter who bypasses our servers delivers to the trustees' intake directly (T-25), and its ballot reaches the board as a contract event. Its receipts must reach the board too, or the ballot is never delivered; and for any ballot, cast through our API or not, an operator that withholds board-path receipts or complaints silently keeps it out of the counted set, or keeps an invalid one in it. Postings have no other path at all. A contract path for share receipts, postings and complaints, emitted as events under the event accumulator ([[contracts]]), MUST exist before any election registry is deployed (P1-18; T-25, T-54), for every ballot, not only those the contract recorded. It is the only path for postings: a contract event's data is on L2, which every trustee's own L2 node reads, so no operator can keep a posting from the trustees through the complaint window and then publish it, keeping an invalid ballot counted that no trustee could complain about ([[0002-everlasting-privacy]], Decision, 2026-10-12; T-54). Trustee nodes MUST send their receipts through the contract path too, so an operator that refuses receipts can't keep a receipted ballot undelivered (Client rules). What the operator serves is never enough to stand down: before its first anchor, an entry can be shown to some readers and dropped from the checkpoint ([[board]], Residuals). So a record or ballot counts as **anchored** for these rules only once the timely checkpoint for its segment, which the node or client reads from L1 itself, covers it with an inclusion proof ([[board]], Consistency proofs, client rule 2), and as **recorded by the contract** only once its contract event is derivable from finalized L1 data, read through sources the node or client chose itself, never our API, one server's claim or a sequencer's soft confirmation ([[revoting]], R5; [[0004-l2-choice]], Finality). Let `F` be the L2's forced-inclusion delay plus the missed-slot margin ([[0004-l2-choice]]), and `c_D = t_D − F` the last moment a contract-path receipt is sure to land in time, even forced through L1. For every receipt it **owes** (below), a node sends the receipt through the contract path, by `c_D` at the latest, unless by then a passing receipt for that ballot and seat is anchored. A ballot is **shown absent** when the node holds the published data of every timely checkpoint for the segments up to `period(closes_at) + 1`, matching the anchored roots, none of it carries the ballot, and the contract hasn't recorded it. A checkpoint is only a root, so an operator can anchor a ballot and withhold its entries from the nodes until after `c_D` ([[board]], Residuals, withheld tails); a node that lacks any of that data can't show any ballot absent.

**What a node owes** ([[0002-everlasting-privacy]], Decision, 2026-10-12). Every ballot a node receipts passed admission at intake, its membership proof included ([[share-encryption]], Intake and receipts), so each names a (`tier`, `ν`) of a registered member. A node decides what it owes once L1 has finalized its first block after `closes_at`, when every L1 reference is decided ([[revoting]], Admission), and before `c_D`. For each (`tier`, `ν`) of a ballot it receipted, it applies [[revoting]]'s Selection (repeats, then the single newest block, a tie selecting nothing) to its **view**: the ballots it receipted, less those it can show absent, together with every ballot of that (`tier`, `ν`) it holds from the anchored board or the contract's records, each kept only if it passes the admission checks ([[ballot-validity]], Admission) and its L1 reference is admitted ([[revoting]], Admission), read from finalized L1 through sources the node chose. If it receipted the selected ballot's `ballot_hash`, under any L1 reference, it owes that receipt; otherwise, or on a tie, it owes nothing for that (`tier`, `ν`). A receipt is for a ballot hash, which leaves out the L1 reference ([[share-encryption]], Notes, One public part), and the delivery check reads it so: a ballot cast again with the same core after its block was reorganised away ([[revoting]], Client rule 4) keeps the receipts its first cast got, and the client treats those seats as receipted (Client rules), so a node owes them for the copy that is selected even if its own copy fails the L1 check. The node decides again whenever its view changes, until `c_D`, and owes every receipt any of those decisions named: sending one it no longer needs costs only gas, within the same bound. So a node owes at most one contract-path receipt per (`tier`, `ν`) of the election, and at most

```
Σ over the definition's tiers t of group_size_t
```

in all: one per member of each tier, which 2.4 recomputes from the group registry (under definition version 3 or 4 the cells' `members`, whose sum per tier is the same), whatever the operator withholds and however many ballots anyone delivers. A member holds one nullifier per tier ([[membership]], Scope), and only a member's ballot passes intake, so no flood of ballots, ineligible or re-voted, adds to it (T-52, T-54, T-25). Receipting a ballot never obliges a node to send any other: a re-vote it receipted replaces the ballot it supersedes in the node's view, so a voter's re-votes cost a node one receipt, never one per ballot.

Why the view, and not every ballot receipted: the delivery check reads only the ballot [[revoting]] selects for each (`tier`, `ν`) from the board (Delivery check), so a receipt for any other ballot delivers nothing. The node's view differs from the board only by ballots it receipted that never reached the board but that it can't show absent, and by ballots on the board it doesn't hold; either way the node can be wrong only about a voter whose newest ballot isn't on the board (Residuals). A ballot the node holds from the board is in its view whoever receipted it, so a newer ballot this seat never receipted (its intake failed, say) correctly leaves the node owing nothing for the ballot it supersedes.

It does the same for each complaint it makes, against `c_K = t_K − F`. A contract-path receipt costs the trustee gas, and the bound above, with P1-18's batched receipts (many signatures in one call, one forced deposit), is what makes the obligation payable; the capacity the windows leave for it is P1-12c part 2's, with the batch call. The windows MUST leave every counted ballot's anchoring, or its recording by the contract, confirmable on finalized L1 with time for the node to act by `c_D`, and the complaint window must leave a trustee time after the last posting:

```
DELIVERY_WINDOW                    ≥ max(2 · period + deadline + R, W_C) + F
COMPLAINT_WINDOW − DELIVERY_WINDOW ≥ W_C + F + R
```

where `period` and `deadline` are the anchoring clock's ([[board]], Timing; a ballot cast by the close is in a segment at most one period after it, anchored by that segment's end plus `deadline`), `W_C` is the contract-event window (P1-18; a ballot or posting submitted at a deadline, forced through L1 if need be, is recorded within it), and `R` is a margin for L1 finality and for the node to act. P4-1 and P1-18 MUST keep their values within these bounds (`deliveryWindowFits` checks them); with hourly periods, a 12-hour anchoring deadline, `F` of 13 hours (Base's 12-hour forced-inclusion delay and an hour of missed slots), `W_C` of 13 hours and `R` of one hour, they need 28 hours of the two days and 27 of the three that follow. The contract:

- accepts a receipt or complaint only if it names this definition and is signed by the registered per-election key of the seat it names (P-256 verification on L2), and accepts **any number** of them per seat and ballot hash, refusing only a byte-identical repeat. It can't tell a passing receipt from one whose `share_hash` isn't the ballot's, nor a proven complaint from a failing one, so no record ever occupies a slot: a seat that signs junk for a ballot it receipted, colluding with an operator that refuses the honest receipt, can't stop the voter sending that honest receipt through the contract afterwards. Extra records cost only the signing seat's gas;
- accepts a posting for a ballot hash it has recorded, or together with the ballot's tier (under ballot version 2, its cell, hashed as version 2, [[ballot-validity]], Ballot record (version 2)), nullifier and committed vote, from which it recomputes the ballot hash itself (a ballot cast through our API is never recorded by the contract). Either way it accepts the posting only if `H(DS("abolish/v1/share-ciphertext", ct))` equals that ballot's `share_hashes[seat]` (one SHA-256) and `sealed` is `4 + 64·m + 16` bytes for the definition's `m`, so only `m` is free in it, and it accepts **any number** of postings per seat and ballot hash, refusing only a byte-identical repeat. It can't run the public check (ML-KEM re-encapsulation and ristretto255 arithmetic), so it never lets a posting occupy a slot: a junk posting, made by anyone who saw `ct_i` in a pending transaction, fails the public check and is ignored, and the voter's own posting is still accepted beside it;
- never admits a ballot because of a delivery record: the ballot's tier (or cell), nullifier and committed vote in a posting call are carried only to bind the posting, and the ballot counts only if its own ballot entry or direct submission is admitted ([[verifier]] 5).

So, with the client rules below, no operator or third party can drop a receipted ballot that the delivery check selects without the trustee's node and every route the client has also failing, since neither stands down on anything short of an anchored receipt or one recorded by the contract in that sense, and the node's obligation is bounded by the electorate (What a node owes), except where the voter's newest ballot never reached the board (Residuals); and a trustee that receipts and never sends its receipt has signed a receipt the voter holds (Residuals). A seat, or an adversary that controls every route to it, can still refuse intake, and then the voter chooses between posting that seat, which the contract can't block, and leaving the ballot undelivered; nothing on the board attributes either (T-25, Residuals). A contract-path record names its ballot hash, or carries its tier (or cell) and nullifier, so the address that pays its gas is publicly linked to the ballot and, through the nullifier, to the voter's re-votes. The client MUST pay from a fresh, privately funded address, or through a relay that can't link it to the voter, as [[0004-l2-choice]] requires for direct submission (T-11, T-13); P1-18 and P2-8 carry this. A record it accepted is boarded as a contract event, late or not ([[verifier]] 4.4), and is in time by its submission time (Windows). P1-18 defines how the contract-event record carries it; the delivery check reads it as if it were the record itself, on the board where its contract event is.

### Client rules

A trustee that returns a valid receipt and never boards it would leave its seat undelivered, and an operator could do the same by refusing the client's copy. And a client that posted whenever its own boarding failed would let an operator that refuses receipts force every share onto the permanent board with `m_i`, readable by anyone who later breaks its classical encryption (T-15). So delivery never rests on one party boarding a receipt, and a client never posts a seat whose receipt passes ([[0002-everlasting-privacy]], Decision, 2026-10-12). The ballot client (P2-8) MUST, for every qualified seat `i`:

1. Treat seat `i` as receipted only if its receipt passes `share-receipt` against the exact ballot it casts (the receipt's statement rebuilt from that ballot, [[share-encryption]], Intake and receipts).
2. Never post a receipted seat, whatever happens to its receipt afterwards. It erases `m_i`, `e_i` and `w_i` for that seat at cast.
3. Keep every receipt and see one onto the board: submit it through the board path once its ballot entry is boarded, and check the operator's receipt for that entry ([[receipts]], Checks at cast), so a later drop is attributable; where the operator refuses the copy because a passing receipt is already boarded (Boarding, rule 5), obtain the operator's signed receipt and inclusion proof for that existing entry instead, and check it the same way. Until a passing receipt for its ballot hash and seat `i` is anchored (Direct submit) or recorded by the contract, whoever sent it, resubmit through every path it has, the contract path included, early enough to be in time even forced through L1; a receipt the operator only serves, unanchored, never stops it.
4. For a seat that isn't receipted, retry intake, and before treating private delivery as failed, try at least one route to seat `i`'s intake that doesn't pass through the operator: the trustee node's own intake endpoint, which the release lists with the pinned panel, reached through a network anonymiser so the trustee doesn't learn the voter's address (T-11). Only if every route fails, post `(i, ct_i, m_i)`, and only if the voter explicitly chooses to, after the client says that a posting lowers that seat's long-term privacy for this ballot: anyone who later breaks the share's classical encryption reads it, and a ballot with `k` or more seats posted is read whole ([[tally]], Residuals). The client asks as soon as delivery has failed, while the poll is open if it can, so a voter who declines can still re-vote, and stops retrying early enough that a posting forced through L1 still has a submission time at or before `t_D` (P1-18 fixes that margin). It posts only through the contract path. Until then it keeps only `ct_i` and `m_i` for that seat, never `e_i` or `w_i` (T-18), and it erases them once the voter declines or the deadline passes.

Trustee nodes board their receipts through the board path and, where that fails, send them through the contract path (Direct submit), so a receipted seat is delivered even when the client goes away; the client's own copies are a second route, never the only one. A seat that isn't receipted and that the voter doesn't post leaves the ballot undelivered: the voter is told so, and can re-vote while the poll is open.

## Delivery check

The verifier ([[verifier]] 5.9) takes the election's definition hash, its registered key set (each qualified seat's KEM key and signing key, [[ceremony]], Transcript check), `s_D`, `s_K`, `t_D` and `t_K`, the ballots [[revoting]] selects for each cell from the counted extent ([[tally]], Context), and every delivery record in the counted extent, in board order, each with its path: a board entry's payload with its segment, or a contract event's record with its submission time. A posting through the board path is a rejected entry (Decoding). For each selected ballot `b`, with `bh = ballot_hash(b)` recomputed from the decoded ballot:

- **Seat `i` is delivered** if it isn't in the registered key set, or if some record in time names this definition, `bh` and seat `i`, and is either a share receipt, by either path, whose `share_hash` is `b`'s `share_hashes[i]` and which passes `share-receipt` against `b`, or a contract-path posting that passes the public check against `b` (`posting-hash`, `posting-proof`, `posting-encapsulation`).
- **The ballot is delivered** if every seat `1, …, n` is: every qualified seat has a receipt or a passing contract-path posting in time.
- **A complaint about seat `i` is proven** if it names this definition, `bh` and seat `i`, is in time for the complaint window (by either path), a contract-path posting for `b` and seat `i` that is in time for the delivery deadline passes the public check, wherever its contract event is on the board, and the complaint passes `complaint-proof` and doesn't fail `complaint-unfounded` against that posting ([[share-encryption]], Complaints). Every passing posting for `b` and seat `i` carries the same `ct_i` (its hash is `share_hashes[i]`) and the same `m_i` (unique for `ct_M`), so which one is used doesn't matter.
- **The ballot is excluded** if any complaint about any of its seats is proven, attributed or not.

`b` stays in the counted set exactly when it is delivered and not excluded; otherwise it counts nothing, with no fallback to an earlier ballot of its nullifier ([[revoting]], No fallback). Neither outcome depends on the order of the records, on duplicates or on records for other ballots, so the operator's ordering decides nothing ([[verifier]] 6.1, R3).

The report lists, for each selected ballot, whether it was delivered, which seats were missing, and each proven complaint with its attribution; and, for the records:

| Code                   | Reported for                                                                                                                                                                                                                                                                                                                         |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `delivery-stray`       | A record naming another definition. Ignored                                                                                                                                                                                                                                                                                          |
| `delivery-seat`        | A record naming this definition and a selected ballot, for a seat that isn't in the registered key set. Ignored                                                                                                                                                                                                                      |
| `delivery-late`        | A record naming this definition and a selected ballot that isn't in time (by its segment through the board path, by its submission time through the contract path). Ignored                                                                                                                                                          |
| `share-receipt`        | A share receipt for a selected ballot that fails the check, or whose `share_hash` isn't the ballot's for its seat. Ignored; attributed to its seat if its signature verifies under that seat's registered signing key over the record's own fields (a seat that signed a share hash other than the ballot's), and otherwise no one's |
| `posting-*`            | A contract-path posting for a selected ballot that fails the public check, with its first failing code. Ignored; a complaint about it is void                                                                                                                                                                                        |
| `complaint-void`       | A complaint for a selected ballot with no passing contract-path posting in time for its seat. Ignored                                                                                                                                                                                                                                |
| `complaint-proof`      | A complaint for a selected ballot whose proof fails. Ignored                                                                                                                                                                                                                                                                         |
| `complaint-unfounded`  | A complaint whose proof verifies but whose shares open and pass. The ballot stands; the complaint is attributed to its signer if its signature attributes it, and otherwise no one's                                                                                                                                                 |
| `receipt-contradicted` | A share receipt that passes, for a seat whose complaint about the same ballot is proven: the seat signed that shares passed which a public proof shows don't. Attributed to that seat                                                                                                                                                |

Each record is reported with the first of these codes that applies, in table order, so a late record for this definition, a selected ballot and a registered seat is reported late, whatever else is wrong with it. Records naming a ballot that isn't selected (an earlier ballot of a re-voting nullifier, a ballot outside the counted extent) are read and set aside: they decide nothing, and nothing is reported for them. A record that doesn't decode is a rejected entry (Decoding).

Notes:

- **Seats that aren't qualified.** A ceremony can end with fewer than `n` qualified seats ([[ceremony]], Transcript check), and shares are encrypted only to qualified seats' keys. For a seat outside the registered key set the client encrypts nothing and sets the ballot's `share_hashes[i]` to 32 zero bytes; that seat needs no delivery and is never summed, and its share of the vote is simply never sent, so the tally needs `k` of the qualified seats. The ballot record's admission checks reject any other value there (`share-hash-unqualified`, [[ballot-validity]], Ballot record), so a ballot can't carry chosen bytes in the share hashes of the `n − q` seats that aren't qualified (T-17).
- **A receipt and a proven complaint for one seat.** A trustee receipts only shares that pass its own intake, and a proven complaint shows publicly that the same ciphertext's shares don't, so both can't be honest. The ballot is excluded, since the proof is public and the trustee can't sum it correctly either, and the receipt is reported against its seat (T-29).
- **Postings next to receipts.** A passing posting for a seat that also has a receipt is redundant, and the client never makes one (Client rules); but the contract can't tell, so one found among the contract events still delivers, and [[verifier]] 8.2 counts it as readable ([[tally]], Residuals). Only the client and the seat's own trustee know `m_i`, and the trustee could publish the share anyway (T-14).

## Residuals

- **Until the contract path exists, nothing can post and the operator can withhold receipts and complaints** (Direct submit, P1-18), for ballots cast through our API as well as direct-submitted ones: a seat that isn't receipted can't be delivered at all, a ballot whose receipts the operator refuses is silently left undelivered, and a complaint it refuses keeps an invalid ballot counted, so the complaining trustee's summed shares fail and the tally needs `k` other trustees (T-25, T-54). Nothing on the board attributes either.
- **A posting is the voter's chosen loss of everlasting privacy for that seat.** A posted share is protected only by the discrete logarithm in ristretto255, so a future adversary who breaks it reads the share, and a ballot with `k` or more seats posted whole ([[tally]], Residuals). The client posts only a seat that isn't receipted, only at the voter's explicit choice after saying so (Client rules); the owner accepted this as an extension of [[0002-everlasting-privacy]]'s fallback on 2026-10-12 (T-15).
- **A seat's `m_i` stays on the device until the voter decides.** For a seat that isn't receipted, the client keeps `ct_i` and `m_i` after cast, up to the delivery deadline, though never `e_i` or `w_i` (Client rules). That proves nothing about the vote to a coercer, but a device thief in that window could post the seat against the voter's wishes, dropping it to classical privacy (T-18, T-45, T-15).
- **A trustee node's contract-path obligation is bounded, but not yet shown payable.** Membership-checked intake and the node's view bound it by the electorate, one receipt per (`tier`, `ν`) (What a node owes), whatever an operator withholds, closing the flood that [[0002-everlasting-privacy]] (Decision, 2026-10-12) accepted only until [[P1-12c]]. What the windows and the L2's capacity allow a node to send by `c_D`, with P1-18's batched receipts, isn't fixed yet (P1-12c part 2), and the residual stays open until it is, which MUST happen before any election registry is deployed. Complaints aren't bounded this way yet: a contract-path posting needn't name an admitted ballot, so a node can't tell from a posting alone whether a complaint about it can matter; P1-12c part 2 bounds them with the posting call (T-25, T-52, T-54).
- **A newest ballot that never reached the board can cost an older one its fallback receipts.** A node's view keeps a ballot it receipted unless it can show it absent, so when a voter's newest ballot reached the trustees but not the board (the client went away mid-cast, or every route refused it), and an operator withholds board data so that no node can show it absent, every node owes only that newest ballot's receipt, and the older ballot the delivery check selects is delivered only if its receipts reached the board some other way: the nodes' board-path copies at intake, or the client, which keeps seeing every ballot's receipts onto the board (Client rules). An operator that refuses those copies and withholds its data can then drop the older ballot unattributed. The same holds, until P1-18 specifies the close rule (5.5), for a newest ballot cast in time but admitted too late; the node's view doesn't apply that rule yet. It needs the voter's newest ballot to be missing from the counted board, and it costs the voter a ballot they had already replaced. It is a trade: before P1-12c a node owed the older ballot's receipt too, at the price of the unbounded obligation the owner accepted only until P1-12c ([[0002-everlasting-privacy]], Decision), which rejected permanent operator drops of chosen ballots. So it MUST be closed, by making withheld board data attributable (P4-3), or accepted by the owner, before any election registry is deployed, and it is listed in STATUS (Known-weak) for the owner (T-25, T-54).
- **Refused intake still forces a choice.** A trustee that refuses intake, or an adversary that controls every route to it (the operator's relay and the voter's network), leaves the voter to choose between posting that seat, with its loss of everlasting privacy, and an undelivered ballot. Neither is attributed on the board: a refusal at intake leaves nothing signed (T-25, T-11).
- **A receipted seat can still go undelivered.** A trustee that returns a valid receipt and never sends it, with an operator that refuses the client's copy and every contract-path route the client has refused too (a relay the operator runs or a state actor compels), leaves the ballot undelivered, and the client may not post instead (Client rules). The voter holds the trustee's signed receipt, which shows off the board that the seat receipted, but nothing on the board attributes the drop; the client says so, so the voter can re-vote through another route while the poll is open (T-25, T-41).
- **A cheating client can still exclude its own voter's ballot** by posting an invalid share: a proven complaint excludes it after the close, too late to re-vote ([[0002-everlasting-privacy]], Re-voting; T-41, T-42).
- **A trustee that misses the complaint window** can't complain about an invalid posted share, so its summed shares fail and it can't contribute to the tally ([[0002-everlasting-privacy]], Tally liveness; T-54).
- **A voter can archive chosen bytes in postings**, about `n · (64·m + 36)` per ballot and re-vote, through the contract path, since neither the contract nor the public check opens `sealed` (Direct submit; T-17). Through the contract path anyone can also post, for the price of gas, postings naming a made-up ballot (a committed vote of their choosing), which the delivery check sets aside but the archive keeps, like any contract event's inclusion evidence (T-17).
- **The contract path archives what the board path refuses.** The contract can't check a receipt's ballot hash or a complaint's decryption, so a registered seat can archive, for gas, about 130 to 190 chosen bytes per made-up ballot hash in receipts and complaints, and an unfounded complaint next to a passing posting puts `D` and `m_i` on the permanent archive, opening that share with no cryptanalysis. Both are within what the seat could disclose itself (T-14), and both are attributed to it: the first is set aside, the second reported `complaint-unfounded` (T-17, T-15).
- **Failing postings for real ballots cost verifier work.** Anyone who has seen `ct_i` can send, for gas, any number of contract-path postings with a wrong `m`; each names a selected ballot, so every verifier runs the public check (ML-KEM re-encapsulation and ristretto255 arithmetic) on it, and the archive keeps its 32 chosen bytes. Bounded only by gas; P1-18 may price or cap postings per seat (T-52, T-17).
- **Receipts don't admit ballots.** A receipt says that the trustee's shares pass for this public part and that a record carrying it passed admission at intake ([[share-encryption]], Intake and receipts), but it never stands in for the ballot's own checks: the verifier admits each ballot entry from its own record (5.1 to 5.4) and its L1 reference (5.8), and a receipt adds nothing to them.
