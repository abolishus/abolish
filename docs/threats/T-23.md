# T-23: Board tampering

- Area: Integrity and verifiability (G-7, G-8, G-9)
- Adversary: A-2
- Status: **Planned.** Residual: entries added since the last anchor can be dropped or reordered undetectably by anyone but the voter holding a receipt, for one anchoring period plus the anchoring deadline (P4-1 sets both; [[board]]).

## Threat

An insider alters, drops or reorders board entries.

## Mitigation

Entries are hash-chained and committed to by an append-only Merkle tree (RFC 9162), and each names its election and position ([[board]], P1-16); the app's DB role has no UPDATE or DELETE, enforced by grants and triggers (P2-1); checkpoints (size, chain head and root after each anchoring period with entries) are anchored hourly to L1 (P4-1) and the board is mirrored to IPFS (P4-3); the verifier recomputes the chain and every anchored checkpoint from the entries, and requires every segment with entries to have a checkpoint anchored within its period's window (P1-19, [[verifier]] 4.1 and 4.2).

Built so far (P1-16): the envelope codec, entry and checkpoint hashes, the tree with inclusion and consistency proofs, and the board checks, in `packages/crypto`, tested against `docs/spec/vectors/board.json` (from an independent Python implementation) and transparency-dev's RFC 6962 vectors. Storage (P2-1, part 1): `board_entries` in `packages/core`, where the app role has SELECT and INSERT only and triggers reject every UPDATE, DELETE and TRUNCATE, the owner's included, and every append that isn't contiguous, in segment order and chained from the previous link. The table never hashes; `packages/crypto` computes hashes and links, and the table only checks that links match. The owner (`abolish_migrator`) can still disable its own triggers, so a malicious migration could rewrite rows; only the rebuild from chain + IPFS and the anchored checkpoints catch that. Not yet: anchoring (P4-1) and the verifier that runs the checks (P1-19).

Index: [[THREAT_MODEL]].

## History

- 2026-10-10 (P1-16): the chain, tree, checkpoints and board checks are specified and built ([[board]]). The tampering window is now one period plus the anchoring deadline, which P4-1 may set above an hour (it was "up to an hour"). Only entries a timely checkpoint covers are the board, so appended entries can't fail it.
- 2026-10-11 (P2-1): the board's Postgres table enforces append-only storage by grants and triggers, tested as each role. Residual: the schema owner can disable its own triggers.
- 2026-10-11 (P2-1, part 2): the server appends board entries only through `appendEntry`, which encodes, hashes and chains each entry with `@abolishus/crypto` (the verifier's own code) under a per-election lock; a board read back with `readBoard` passes `checkBoard` ([[board]]).
- 2026-10-11 (P2-4 part 1): `auditBoard` (core) recomputes every stored board with `checkBoard` and compares each row's stored entry hash and links, which the triggers never check; `apps/worker` runs it every 10 minutes and logs each bad board. It detects a writer that bypassed `appendEntry` with columns the payloads don't produce, within one audit period; a consistent rewrite or a rollback needs anchored checkpoints (P4-1). It repairs nothing.
- 2026-10-12 (P4-1 part 1): the L1 board anchor records each election's checkpoint hash once per segment, from the anchoring authority only and inside each period's window, so the board's state after every period is fixed on L1 ([[contracts]], Board anchor). Not deployed yet.
- 2026-10-13 (P2-3 part 2c): `appendEntry` encodes, hashes and chains each board under the board-entry version its stored definition pins, never version 1 by default, and refuses a board without a definition or under a version it can't write; reads and the audit (`board-unpinned`) use the same version. Before this, a board whose definition pinned version 4, as every plurality or approval profile must (verifier 2.3), would have had entry hashes and links the verifier never recomputes.
- 2026-10-17 (P4-1 part 2a): each checkpoint the anchoring job takes is stored append-only (`board_checkpoints`, triggers checking its election, segment, size, boundary and head against the board) and fences its segment against later appends, so a stored board can't grow behind a checkpoint that may already be anchored.
