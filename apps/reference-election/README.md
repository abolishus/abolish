# @abolishus/reference-election

The reference election (AGENTS.md, Reference election; P1-20): the single end-to-end proof that the system works. Internal and source-only; AGPL-3.0-only. It holds no domain logic: every protocol step is a call into `@abolishus/crypto`, the contracts are `packages/contracts`' own build, and the result is judged by `packages/verifier` alone.

## Running

From the repository root, with the toolchain on `PATH` (`.github/scripts/install-toolchain.sh`, for `anvil` and `forge`):

```
vp run reference-election
```

It builds `@abolishus/crypto`, `@abolishus/verifier` and `@abolishus/contracts`, starts two Anvils of its own on loopback (an L1, chain 31337, and an L2, chain 31338), and writes `reference-election-output/`. The verifier's built package and forge's contract artifacts are read by path, not as workspace dependencies, so the verifier runs as a third party would install it; only the root script's `--filter … build` orders those builds.

| Path                                                                  | What it is                                                                                                                                                                                                                                                                                            |
| --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| `honest/bundle/`                                                      | The honest election's verifier input: `bundle.json` (format 4) and `blocks.car`; its report is `honest/bundle-report.json`                                                                                                                                                                            |

It exits non-zero if any stage throws, any check of the honest report fails, a required check (`expectations.ts`) doesn't pass, the verdict isn't the one its inputs allow, or a control's report differs from the rows it pins.

## Controls

A control is something the verifier must not pass, with the rows and codes it must show, so the honest run's passes can't be vacuous or pass for an unrelated reason:

- **`rule-7`:** a second election, created by the same election registry and anchored through the same anchor, whose ceremony only 5 of the 7 seats took part in. The trustee registry must refuse its registration (`BelowQuorum`: the panel is pinned with rule 7's quorum of 6) and the election registry its definition (`CeremonyNotRecorded`). Offline, it is anchored and its threshold of 4 is met, so 4.1 and 4.2 pass, but 3.2 must fail with `ceremony-participation` (ADR 0006, rule 7; T-54).
- **`tampered-copy`:** the honest bundle with its board copy altered, as `board.bin`, and no logged checkpoint. The copy no longer matches its anchors (4.2 `l1-checkpoint-unknown`) or the definition's transcript hash (3.1 `ceremony-transcript-missing`), so 3.2 isn't reached.
- **`withheld-blocks`:** the honest bundle with the logged checkpoints and a well-formed block store holding rule-7's board and none of its own. The copy by CID stops at its first run (4.1 and 4.2 `checkpoint-missing`, 3.1 `ceremony-transcript-missing`, 3.2 `not-reached`): withholding leaves the election unverifiable from that store, never failed (T-53).

## What it covers so far

- **Stage 1, the key ceremony (partial):** a 4-of-7 panel with fresh identity keys runs the four rounds of `docs/spec/ceremony.md` through the production entry points, every seat taking part (ADR 0006, rule 7). The definition binds the transcript by its hash and the ceremony binds the definition's stub hash (T-37). The transcript is board entry 0, and the verifier's 3.2 must pass. On the L2 (part 2a, `src/l2.ts`), the trustee, group and election registries and the board are deployed from forge's build, the panel pinned in the trustee registry with a quorum of 6; the election is created there before its stub is written, so the definition names that deployment; every seat that took part checks the transcript and signs the key set the check returned, the trustee registry records the ceremony from those signatures, and the election registry registers the definition, whose hash and recorded ceremony the fixture reads back (T-37, T-14, T-71). The verifier doesn't read the L2 yet, so 3.1 can't pass, and no release pins the panel. In the elections of one question (part 2b-2a, `src/seats.ts`), each seat is `apps/trustee-node`'s own `CeremonySeat` over a store of its own: the fixture only relays the rounds as coordinator and collects the approvals, and the registration record is made from them; in `rule-7` every node that ran it must refuse to approve (`participation`). The poll of questions, a version-5 definition the node doesn't read yet, runs through `@abolishus/crypto`.
- **Stage 7, in part:** `BoardAnchor` is deployed on Anvil with the 1-hour period and 12-hour deadline of `docs/spec/contracts.md`; the ceremony's segment and the seal are anchored inside their windows. The verifier reads both back from a finalized block's header and `eth_getProof` nodes, and 4.1 and 4.2 must pass (T-23, T-24, T-53).
- **Stage 8, the board only (P4-3 part 2b-2c, `src/blocks.ts`, `src/node.ts`):** each board's segment objects and entry-hash lists are published as content-addressed blocks to a community node, `apps/node serve --blocks`, run in a process of its own from its source. Each bundle is then rebuilt from L1 alone: the checkpoints from BoardAnchor's `CheckpointAnchored` logs (each refused unless it hashes to its logged hash), and the board copy read by the CIDs they name, from `blocks.car`, holding the node's blocks as a user would export them, and, in `bundle-from-node/`, from the node's gateway alone. Both honest runs must show the copy read by CID from that source, whole (T-24, T-49, T-51). No database is wiped yet: nothing the fixture runs writes one.
- **Stage 9, in part:** the verifier runs in a process of its own, from its built package, with an empty environment, over the bundle directory alone and, for `bundle-from-node/`, the node's gateway (T-36). Over `questions/bundle-l1-blocks/` it also judges, in the same kind of process, whether each of the poll's alarmed receipts lost its ballot (`judgeDrop`; docs/spec/receipts.md, Drops): the forked receipt's ballot must be present at entry 1 and the never-boarded one a drop (T-26, T-25).

Everything else is listed as `not-yet` in `stages.json`, with the item that brings it.

## Stubs

`STUBS` in `src/election.ts`, written into `stages.json`: the L2 is a local Anvil, not Base Sepolia, with forge's `MockL1Block` at the `L1Block` predeploy reporting the L1 Anvil's latest block as each event's origin; the group registry's registrars and the L1 relay are placeholder addresses; the electorate is one placeholder Tier 0 group (the definition names the pinned membership key, which verifier 1.3 requires), the panel is given to the verifier as a local file, the anchoring authority is a one-byte contract Anvil lets the fixture send from rather than the Safe, and the seal is the segment after the ceremony's. Each placeholder is the Keccak-256 of a `reference-election/placeholder/…` label, so none can be taken for a deployment's.

## Keys

The fixture holds no private key (AGENTS.md, Testnets only): it sends from each Anvil's unlocked development account and from an impersonated address. Trustee identity secrets are fresh random bytes for each run. The trustee nodes' stores, which hold their per-election secrets and shares, are in a temporary directory outside the run's output (mode 0700), removed however the run ends.

## Tests

`vp run --filter @abolishus/reference-election test`: the RLP encoder against the published examples and a round-trip property, the anchor calldata's and the one-`bytes`-argument calldata's canonical layouts, CREATE addresses, the ceremony registration record's layout with each seat's signature, the trustee nodes' ceremony (every approval verifying, the record refusing an approval of another transcript, a 5-seat run refused by every node) and their intake (the receipts the nodes' keys sign, refused until registered and past the cutoff), the nodes' electorate check, the header rebuilt to an Anvil block's hash, `CheckpointAnchored` logs decoded against `board.json's` published checkpoint hashes, the segment objects and their CARv1, and the report and control expectations. The end-to-end run itself is the `reference-election` check.
