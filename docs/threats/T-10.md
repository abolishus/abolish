# T-10: Account-to-ballot linkage on the server

- Area: Ballot secrecy, unlinkability and privacy (G-3, G-4, G-5, G-12)
- Adversary: A-2, A-1
- Status: **Planned.** Residual: network metadata, T-11.

## Threat

A table, log line, cache key, queue job or metric joins an account (or a session, cookie or IP) to a ballot or poll participation.

## Mitigation

Accounts and voting identities are separate systems, including the recovery backup (T-20); the ballot path carries no account credential. A test asserts that no table can join them (P2-1, built): every table is classed as board or operational, no foreign key starts or ends at a board table, and no board column has an account-like name. The API's request log has one (P2-3, built): a line holds only the method, the contract route matched, the status and the duration, never an address, a header, a query string or a body, and the handlers' context holds the database alone, so no procedure can read a cookie, token or address. Accounts (P2-5 part 1, built) live in their own tables, which the no-join test classes separately: foreign keys from or to them stay among them, no column of theirs has a ballot-like name, and no view or function reads both classes. Account cookies are host-only on `apps/web`'s origin, and the API refuses (with 400, before reading anything) any request carrying an account cookie or an `Authorization` header, so no ballot or board request is ever handled next to an account. Queues and the worker's log have one (P2-4, built): each queue is on one side, its job data is strict and can't name the other side, a job's data, error and stack trace leave Redis once it finishes (BullMQ's events stream keeps its ID, its name, fixed to the queue's key, and timestamps), and a log line holds only the queue, outcome, error kind and duration. The API has no cache or metrics yet, and whichever part adds one extends the test. Migrations rules (`.claude/skills/migrations`).

- 2026-10-16 (P3-2 part 4d-1, [[registration]]): `POST /registrations/tier0` is built. It refuses an account credential like every route, takes its token in the body, and its handler sees the body alone. Its queue is in Redis, not a table: fixed keys under one hash tag, mapping each commitment to its group, with no time, order, token or key per commitment, and tests list every key the route writes and check that no token reaches one. No table is added, so the no-join tests gain nothing; the batch job's queue (part 4d-2) takes no data.

## History

- 2026-10-11 (P2-1): the schema no-join test is built. It covers tables only, and the column deny-list matches by name, so a renamed linking column would pass; review of each migration still has to catch that.
- 2026-10-11 (P2-3 part 1): the API's request-log test is built. It sends cookies, bearer tokens, forwarding headers, query values and ballot bodies, and fails if any reaches a log line or if a line has any field beyond method, route, status and duration. Internal errors are logged by kind only, since error messages can quote input. It doesn't cover the reverse proxy or hosting platform in front of the API, whose access logs P2-11 must configure (T-11).
- 2026-10-11 (P2-6 part 1): [[0017-identity-recovery-backup]] stores recovery envelopes through the ballot path with no account session, in an operational table with no account column; P2-6 part 3 classes it in the no-join test and refuses, rather than ignores, an account cookie or token on its routes.
- 2026-10-11 (P2-5 part 1): accounts (better-auth, passkeys only) in `account_*` tables, classed as their own kind in the no-join test, which now also fails on a foreign key leaving the account tables, an account column with a ballot-like name, a view, or a function that names tables of both classes. The account handler is for `apps/web`'s origin; the API refuses requests carrying an account cookie (any name under the account prefix, with or without `__Secure-`/`__Host-`) or an `Authorization` header. The name-based checks share the P2-1 caveat: a renamed linking column or a join written in application code isn't caught by them.
- 2026-10-11 (P2-4 part 1): the queue and worker-log no-join tests are built. Every queue is on the board or the account side and its strict job data can't name the other side (field names matched by a deny-list, as for columns); the worker re-parses data before handling it; a job's data, error and stack trace leave Redis when it finishes, even if its producer didn't ask, and the failure message BullMQ keeps in its events stream is only the error's fixed kind; a log line holds the queue, outcome, error kind and duration, plus public election IDs for audit findings. Tests queue an account field on a board queue, and make a handler throw a message quoting data, and fail if either reaches a log line or any Redis key, the events stream included.
- 2026-10-12 (P2-9 part 1): `apps/web` calls the API only from its server, with requests built from the contract and the poll ID, never from the visitor's request; a test sends a page request with an account cookie, a bearer token, a forwarding address and a user agent, and fails if any of them reaches the API. `apps/web` still sees which poll pages a visitor opens, as any site does (T-67).
- 2026-10-12 (P2-9 part 2a): `apps/web` serves the account handler under `/auth` from its own Node front (`src/node/serve.ts`), so the session cookie stays host-only on its origin. The pages never read the session: the front strips the `Cookie` header from every request but `/auth`, and their server functions build API requests as before. The front's log line holds the method, a route class from a fixed list (`page`, `server-fn`, `auth`, `asset`, `refused`), the status and the duration; a test sends a poll page request with a session cookie, a user agent and a query and fails if any of them, or the path, reaches a line. One process does hold account sessions and serve poll pages, so a compromised `apps/web` could join a session to the polls its browser views (T-67); it still never sees a ballot.
- 2026-10-12 (P2-6 part 3): `identity_backups` gets its own `identity` class in the no-join test, on the ballot side: no foreign key may touch it, no column of it may look like an account, and no function may read it with an account table; a test also pins its columns (`id`, `envelope`, `written_month`). The API's backup routes refuse a request carrying an account credential like every route, and tests check that a refused put, fetch or delete neither reads nor changes the stored backup, and that the request log never holds a locator, a row id or an envelope.
- 2026-10-12 (P2-6 part 3b): the worker's queue classes gain an operational side, for upkeep on neither side; the no-join test holds its fields to both deny-lists. Its first queue, `{identity-backup-prune}`, takes no data, and its log line is the queue, outcome and duration only.
- 2026-10-12 (P3-2 part 4a, [[0024-tier0-registration]]): Tier 0 registration is a ballot-path route carrying the commitment, its group and a Turnstile token, never an account credential; its table and queue go on the board side of the no-join tests (P3-2 part 4d). The challenge page that issues the token is on its own host with no account cookie, and never sees the commitment.
- 2026-10-13 (P3-2 part 4b, [[registration]]): the registration request's Turnstile token travels in the body, so the procedure reads no header. Its queue is one unordered map from each queued commitment to its one group, with no arrival time, request id, address or token, and one scheduled job per boundary rather than a job per request; a batch's in-flight record is deleted once final. The challenge page's host receives no cookie of ours.
- 2026-10-17 (P2-4 part 2b, `apps/worker`, `apps/api`): the API's first queue producer, `BallotQueue`, puts each submitted ballot on the board-side `{ballot-submit}` queue with its election and nothing else: no request value can reach it, since the handler's context still holds no header, cookie or address. It takes no job ID or option from its caller; it draws a random job ID so it can listen for the outcome before queuing, which like BullMQ's counter says nothing about the data. The job's data leaves Redis once judged; its return value, which stays in the events stream with its ID and timestamps, is only a board index or a refusal's code, and a test fails if a ballot or its election stays in any key. Not mitigated: the stream ties each outcome's board index to a millisecond time, finer than the board's segments, so joined with a proxy's access log (T-11) it could link an address to an entry; the queue keeps only its last 1,024 events (about 250 jobs), however slow the traffic. A job the worker finds more than a minute old is refused unjudged, so a ballot whose API gave up on it, or crashed before removing it, isn't boarded late; it stays in Redis only while no worker pinning panels runs.
