# Content addressing

How board data becomes IPFS blocks, CIDs and CAR files, so every party that holds the same bytes derives the same CID and the same CAR, and anyone can pin or re-upload a copy that matches what was published ([[0005-permanent-archive]], CID parameters). Threats: T-51 (data loss: independent pinners must reproduce our CIDs), T-49 (verification without us), T-24 (a gateway serving different data to different viewers can't pass a CID check).

Integrity never rests on a CID alone: every byte is checked against the L1-anchored roots (P1-16, P4-1). CIDs are for finding and deduplicating data.

## Parameters

IPFS implementations disagree on defaults (chunk size, leaf encoding, links per node), so every parameter is fixed here and implementations MUST set them explicitly.

| Parameter      | Value                                                                                                                               |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| CID version    | CIDv1                                                                                                                               |
| Multihash      | sha2-256 (`0x12`), 32-byte digest                                                                                                   |
| Text form      | multibase base32, lowercase (`b` prefix)                                                                                            |
| Leaf blocks    | raw (`0x55`), each holding one chunk of the object's bytes                                                                          |
| Chunking       | fixed size, 262,144 bytes; the last chunk holds the remainder                                                                       |
| Interior nodes | dag-pb (`0x70`) UnixFS v1 `File` nodes, with no `mode`, `mtime` or other metadata                                                   |
| DAG layout     | balanced, at most 1,024 links per interior node                                                                                     |
| Small objects  | an object of at most 262,144 bytes is a single raw block; its CID is that block's CID                                               |
| Empty objects  | not allowed: nothing the protocol stores is empty                                                                                   |
| CAR            | CARv1, exactly one root (the object's CID), blocks in depth-first pre-order from the root, each block exactly once, no other blocks |

An object is any one encoded byte string the protocol stores: a board segment (P1-16 defines its contents), a display-text record ([[display-text]]), an archive manifest (P4-3) or a ballot-client release (P2-8).
