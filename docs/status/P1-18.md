## Part 5 follow-up: the release build is forge-only

`crypto-review` on #109 passed with two non-blocking findings, both about what the package build now runs after `forge build`:

1. `wagmi generate` runs `@wagmi/cli`'s 54-package closure (a second native esbuild among it) with write access to `out/`. A malicious release in that closure could rewrite `bytecode`, `deployedBytecode` or `immutableReferences` there, or the solc binary forge caches, identically in both `repro-build` builds, while the ABIs and so the bindings test stay clean. #109's T-64 sentence, that forge's artifacts rather than the bindings are what verifier 1.2 uses, was no defence: the same job writes both.
2. wagmi formats its output with Prettier, calling `resolveConfig(process.cwd())`, which treats the package directory as a file and searches from `packages/` upward. Every config it finds can run code: `prettier.config.*` and `.prettierrc.{js,cjs,mjs,ts,cts,mts}` are code, and a data config (`.prettierrc`, `.prettierrc.{json,yaml,yml,json5,toml}`, or a `prettier` key in `package.json`) whose content is a string names a shared-config module that Prettier loads (corrected after #112's `crypto-review`; wagmi's `plugins: []` doesn't stop it). None of those paths is gated today, so a PR outside `crypto-review`'s scope could add one at `packages/` or the repository root that runs inside every contracts build. This is the class T-59 already records for `postcss.config.*` (P2-8).

What changed:

- **The release build is defined as forge-only** (README, Release build; T-64, Mitigation): verifier 1.2's pinned bytecode and immutable ranges, and every deploy artifact, come from `forge build` alone (default profile), on a fresh runner in a job that runs no npm code, with `out/build-info` removed and the remaining artifacts hashed before anything else runs; later jobs check against those hashes. The package build (`vp run build`) still makes the bindings and is what `repro-build` compares; its `out/` is never a release input. P1-19 (verifier 1.2) and P4-1 part 2 (the anchor's deployment) must build that way.
- [[verifier]] 1.2 defines the release build, so a third-party verifier doesn't depend on the README.
- T-64, T-55 and T-59 history lines record both findings.

## Part 5 second follow-up: forge's own inputs and creation code

`crypto-review` on #112 passed with three non-blocking findings:

1. **Verifier 1.2 binds runtime code only.** A deployer can deploy with its own initcode that writes extra storage (for example non-zero board-anchor checkpoint words for predictable future elections and segments past the creator's pre-creation check, [[contracts]], Pre-creation anchors) and then returns the release runtime code with the pinned immutables. 1.2 and the accumulator replay (4.4) still pass, and the verifier attributes those words to the anchoring authority, so an election fails or stays unverifiable with the blame on a Safe that never anchored. Not fixed here: it needs a design in [[verifier]] 1.2 and [[contracts]] (deploy through a pinned CREATE2 factory and recompute each address from the release creation code and pinned constructor arguments, or bind the creation transaction's input with inclusion evidence). **This must be decided and specified before P4-1 part 2 or anything else deploys a contract** (T-64).
2. **The release build didn't fix forge's own inputs.** forge reads `.env` from its working directory and the project root, `FOUNDRY_*` and `DAPP_*` variables (which can name a solc binary or remappings) and `~/.foundry/foundry.toml`; a root `.env` outside `crypto-review`'s scope could change the release bytecode. Fixed: the README and [[verifier]] 1.2 now fix the working directory (`packages/contracts`), the pinned forge 1.8.3, no `.env` in `packages/contracts`, `packages/` or the repository root, no `FOUNDRY_*`/`DAPP_*` variables and no global Foundry config, and a `forge config --json` check before building; and the source commit is the contracts commit on `main` that the verifier's release pins (now listed among [[verifier]]'s pinned trust roots), so third parties reproduce the same bytecode (T-36). Naming it in the deployment record instead was considered and rejected in review: the deployer (A-2) could then name unreviewed source.
3. **Prettier's data configs also run code** (a string value names a shared-config module). Fixed above and in T-59; the planned ban list now names every Prettier config file.

An in-session subagent review of this follow-up found one blocking point, fixed: naming the source commit in the deployment record would let the deployer choose unreviewed source, so the commit is pinned by the verifier's release instead. Its non-blocking points are applied: the job fails on any `.env` in `packages/contracts`, `packages/` or the root (forge may read one at its project root), `forge config --json` is checked against this package's `foundry.toml`, 1.2 states its own creation-code gap, and the gap is stated for every contract's storage, not only the anchor's checkpoint words.

## Part 4a (#158): [[0025-contract-event-evidence]]

An ADR, under rule A, on what a contract-event record (`0x0008`) carries and what evidence the archive keeps for it, which [[0005-permanent-archive]] had answered with raw transaction and receipt inclusion proofs and [[notation]] had left open (T-17).
