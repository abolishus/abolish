## Scope

The owner's top priority (2026-10-29): nothing on staging can create, open or count a real poll until the contracts exist on Base Sepolia (L2, 84532) and Sepolia (L1, 11155111) and the services pin them. No deploy script, deploy workflow or deployment record exists yet ([[P2-22]], Blocked, item 1; [[staging-testnet]], Not yet possible). This item builds all three, so the owner's deploy day is running one workflow and pasting its record's addresses into Railway.

## Parts

1. **The deploy script and its local run** (`packages/contracts/script/`, no `.github/` change). One Foundry script that deploys every contract the staging path needs in dependency order: the L2's group registry, election registry, trustee registry (pinning the launch panel), board, registration account and paymaster, with the Safe + TimelockController admin the `contracts` skill requires; the L1's board anchor (trusting the anchoring Safe), and the receipt-key registry [[0023-receipt-evidence]] calls for if it isn't built yet (then it is this part's first PR). Every pin a contract takes at construction (the panel's keys and threshold, the Tier 0 registrars and threshold, the Safe, the anchoring clock) comes from the script's environment, never a literal. It writes `packages/contracts/deployments/<chain-id>.json` (addresses, transaction hashes, runtime bytecode hashes, the deploying commit) and refuses to run if any spec precondition below fails. A test deploys it to two local Anvil chains and checks every recorded address's code hash and every pin read back through the generated bindings.
2. **The deployment record** ([[deployment]], record `0x0020`): a command in `packages/contracts` (or `packages/core`) that builds the canonical record from the two chains' JSON files plus the owner's off-chain inputs (origins, RP IDs, published groups, prover hashes), checks it against [[deployment]]'s well-formedness rules, and prints the Railway variables each service needs (`CREATE_*`, `REGISTRY_SYNC_*`, `TIER0_*`, `POLL_STUB_*`, `POLL_ROOT_GROUPS`, the seats' `TRUSTEE_CONFIG` fields) so no address is copied by hand. Workers' startup checks ([[P2-22]] part 4b) read it unchanged.
3. **`ci: testnet contract deploy`**, in two parts: 3a, `script/confirm.ts`, which confirms each record against its chain and the release build and adds the transactions and blocks (a feature PR); 3b, the workflow (rule B: its own small `ci:` PR, no auto-merge, the owner reviews): a `workflow_dispatch` workflow in the `staging` environment that installs the pinned toolchain, runs part 1's script with `TESTNET_DEPLOYER_KEY` on both chains, verifies every contract on the explorers with `ETHERSCAN_API_KEY`, runs part 2's check over the result and opens a PR committing `deployments/` and the record. Dry-run mode (simulate only, no broadcast) is the default input.
4. **Runbook**: [[staging-testnet]]'s "Not yet possible" and "Deploy day" rewritten around the workflow, listing each input variable, which key it is and what to do with the printed Railway variables; [[P2-22]]'s Blocked item 1 marked done once the workflow has deployed.

## Part 1b-1: the deploy script for the registries, the board, the anchor and the relay

- **The script** (`packages/contracts/script/Deploy.s.sol`; `packages/contracts/README.md`, Deploy script):
  - `runL1()` deploys the board anchor, trusting the anchoring Safe, and the L1 relay to Base's portal.
  - `runL2()` then deploys the trustee registry pinning the launch panel, the group registry with the Tier 0 registrars, the election registry and the board.
  - Every pin comes from the `DEPLOY_CONFIG` JSON, range-checked, except the epoch: the L2 run reads it from the deployed anchor, as [[contracts]] (Election registry, Deployment) requires. The launch panel's quorum must be `max(k, n − 1)` (Trustee registry, The quorum).
  - No key is read: forge broadcasts as the configured deployer.
  - Each contract's creation code comes from the built artifacts in `out/`.
  - Each run writes `deployments/<chain-id>.json`, only when broadcasting. It holds the target, chain, deployer and starting nonce, commit (40 lower-case hex digits, checked), each contract's address and runtime code hash, and `pins`, everything each contract took.
- **Addresses across chains.** The relay pins the L2 board, and the election registry pins the anchor and the relay ([[0028-board-contract-checks]], Deployment order). So each is the deployer's CREATE address at a configured nonce. Each run refuses to start unless the deployer's nonce is the configured one (`WrongNonce`). The L2 run comes second, and refuses to start unless, on the L1, three things hold:
  - the anchor and relay are where it will pin them, with the code hashes in the deployer's own L1 record (`L1NotDeployed`);
  - the relay pins this run's board (`L1RelayBoard`).

  So the L2 pins nothing of the L1's that isn't there.

- **The waiver's guard** ([[0044-testnet-deployments]]):
  - Any target but `staging` is refused (`NotStaging`).
  - Any chain pair is refused (`ChainRefused`) but Sepolia with Base Sepolia, or the local Anvil pair, L1 31337 and L2 31338. The spec's Testnet deployments section and the ADR now name the Anvil pair, and the reference election uses the same two IDs.
  - A run on another chain than its record's is `WrongChain`.
- **Tested** (`packages/contracts/test/deploy.test.ts`, two Anvil chains, Anvil's unlocked account). Both runs succeed in order, and then:
  - every recorded address holds the code its hash names;
  - every pin is in the record as configured, and reads back from the contracts through `cast`;
  - each chain names the other's contracts where they are.

  Each refusal stops before any transaction is sent:
  - on L1: another target, a bad or quoted commit, a mainnet pair, a mixed pair, a testnet record on the local chain, another nonce, a nonce or epoch past `u64`, the L2's chain, and a second run;
  - on L2: before the L1 record exists, a wrong quorum, an out-of-range registrar threshold, a board the relay doesn't pin, an anchor and relay at other nonces, and a second run.

  A dry run sends nothing and writes no record.

- **Known-weak:**
  - The records carry no transaction hashes. Forge keeps them in its broadcast files, which part 3's workflow adds.
  - A record is written when the run broadcasts, before forge has sent anything, so a broadcast that fails part-way leaves a record of contracts that may not all exist. Part 3's workflow confirms each record against the receipts and the chain's code before committing it.
  - `forge script` recompiles `out/` before running, so the deployed code matches the release build only because the compiler is deterministic. Part 3's workflow compares each deployed contract's code with the release build's, immutables masked.
  - The pins are read back through `cast`, not the generated bindings.
  - The registration paymaster, the registration account and the timelock admin aren't deployed. That is part 1b-2.
  - A deployer transaction on the L2 between the configured nonce and the L2 run fails it with `WrongNonce`. That needs a fresh configuration for both chains, since the relay already pins the predicted board.

## Part 1b-2a: the review follow-ups on #850

`crypto-review` and `claude-review` on #850 raised these. Each is now in `script/Deploy.s.sol`:

- **One commit on both chains.** The L2 run requires the L1 record's target and commit, as well as its deployer, to be its own configuration's (`L1RecordMismatch`). An L1 deployment from one commit can no longer pair with L2 contracts from another while each record looks fine on its own (T-64, T-34).
- **The Safe, as the record must name it** ([[contracts]], Board anchor, Deployment). The L1 run reads the anchoring authority's `getOwners()` and `getThreshold()` on L1 and records them under `pins.anchor.authority`. It refuses a threshold below 2 or above the owner count, a zero or repeated owner, and an authority whose getters don't answer (`AuthorityNotMultisig`, or a failed call). A 1-of-1 Safe passes the anchor's code check but is one key (T-69). The script checks the owners and threshold only. A module or guard that lets one key act as a 2-of-3 Safe is the anchoring runner's check before it signs (P4-1 part 2b; [[contracts]], Board anchor, Known-weak).
- **The clock's form.** The L1 run refuses a clock other than [[contracts]]'s (`ClockRefused`): an epoch that isn't a whole hour, a period other than 3,600 seconds, or a deadline other than 43,200. A zero deadline, which [[deployment]]'s `clock` rule calls ill-formed, is refused with them, before anything immutable is deployed (T-53, T-49).
- **Tested** in `packages/contracts/test/deploy.test.ts`: each new refusal sends nothing. On L1: an epoch that isn't a whole hour, another period, a zero or other deadline, a 1-of-1 Safe, a threshold above the owner count, a repeated owner, and an authority with no Safe getters or no code. On L2: another deployer or commit than the L1 record's. The L1 record's pins carry the Safe's owners and threshold as `test/utils/MockSafe.sol` gives them.
- **Known-weak:** who holds each registrar key, which [[deployment]] (Operators' deployment file) also asks for, isn't on any chain. The script can't read it, so part 2's record command takes it from the owner's off-chain inputs. The Safe's owners and threshold are recorded as they are at deployment; a Safe can change them afterwards ([[contracts]], Board anchor, Known-weak).

## Part 1b-2b: the registration paymaster and account

- **The script** now ends `runL2()` with two more deployments. First the signing service's `RegistrationAccount`, pinning EntryPoint v0.8 and the service's key. Then the `RegistrationPaymaster`, pinning that EntryPoint, this run's group registry, the account, the admin and the cap ([[contracts]], Registration paymaster and Registration account, Deployment). Both are recorded with their code hashes, and `pins.registration` gives the EntryPoint, the service's key, the admin with its delay, and the cap.
- **The admin.** The paymaster's admin must be the `TimelockController` behind our Safe (contracts skill, Rules). The script doesn't deploy it: the owner creates the Safe and the timelock on Base Sepolia (the [[staging-testnet]] runbook) and names both in the configuration. This narrows the item's scope ("with the Safe + TimelockController admin"): deploying the timelock from the script, from a vendored OpenZeppelin release, so its roles are fixed by its creation arguments, is left to a later part if the owner wants it. Before anything is sent, the script refuses (`RegistrationRefused`):
  - an admin without code or with only an EIP-7702 delegation;
  - an admin whose `getMinDelay()` is zero, which is in effect its proposer's one key;
  - a Safe that isn't a multisig (as the anchor's authority is judged);
  - a Safe that doesn't hold the timelock's proposer and canceller roles;
  - a deployer that holds the timelock's admin, proposer or canceller role (T-62);
  - an EntryPoint without code, or on Base Sepolia anything but the canonical v0.8 address;
  - a zero service key, or a zero cap.

  The record gives the EntryPoint's code hash, the admin's delay and the Safe's address, owners and threshold. The cap is a decimal string, since a wei amount can exceed what a JSON number carries.

- **The review nits held from #855:**
  - a zero or repeated Safe owner now has its own error, `AuthorityOwnerInvalid(index)`;
  - the test's `deployedCode` names the file it reads;
  - [[deployment]]'s note that nothing checks the anchor's epoch now says the deploy script refuses any other clock, though no well-formedness rule does.
- **Tested** (`test/deploy.test.ts`):
  - the two contracts deploy last, with their pins in the record and read back from the contracts: the account's EntryPoint and owner, and the paymaster's EntryPoint, registry, service account, admin and cap;
  - each refusal sends nothing: an EntryPoint without code, a zero service key, a zero cap, an admin without code, one that is a 7702 delegation, one with no delay, one with no timelock getters, one whose roles are anyone's, and one whose Safe isn't its proposer;
  - a cap of 2^60 wei round-trips through the record;
  - stand-ins: `test/utils/MockEntryPoint.sol` and `test/utils/MockTimelock.sol`.
- **Known-weak:**
  - The script checks the roles it can name: the Safe's, and the deployer's. It can't list every holder of a role, or tell OpenZeppelin's timelock from a contract that only answers like it, so a contract that grants a role elsewhere passes. That is the Safe owners' to check when they create the timelock, and the runbook says to use OpenZeppelin's.
  - The record names the admin's delay at deployment; a timelock can change its own delay through itself.
  - The paymaster's deposit and stake are the admin's to fund after deployment (P2-22 part 7b's runbook steps), not the script's.

## Part 2a: the record from the chain files and the owner's inputs

Part 2 is split: this part builds the canonical record; part 2b prints each service's Railway variables from it and the chain files.

- **The builder** (`packages/core/src/deployment-record.ts`, `buildDeploymentRecord`) takes the two chain files part 1b's script writes and the owner's inputs file, and returns the record, its one encoding (decoded back by crypto's strict decoder) and its deployment hash.
  - From the chain files: both chain IDs, the four L2 contracts, the anchor, the relay, the portal, the anchor's clock and authority, the commit, the registrars and their threshold, and the launch panel as the only listed panel and `initial_panel`.
  - From the inputs: `l2_from_block`, the sequencer drift, the dispute-game types, which seats are ours, the published groups, the three origin lists, both RP IDs, `backups`, the prover hashes, the token keys and the seat relays. The format is in `apps/admin-cli/README.md` (Deployment record). Every key is required and no other is allowed, so a misspelt one fails rather than vanishing.
  - The version is the lowest that carries the inputs (3 with relays, else 2 with token keys, else 1), so one set of pins has one record (T-31). Lists the spec orders are sorted; a repeat still breaks its rule.
- **Checked before anything is built** (T-64, T-34, T-37): the two files are one deployment (target, commit and deployer); each names the other's chain; the L1's board is the L2's; the L2's anchor and relay are the L1's; the epochs agree. Every contract is its deployer's CREATE address at its place in the script's order from the file's starting nonce (the anchor and relay on L1; the trustee, group and election registries and the board on L2), so an address edited in either file, or a file from another run, is refused (`address`). The launch panel's identifier, computed from its threshold and keys, is the one the trustee registry computed on chain, so keys out of order or another threshold are refused (`panel-id`). Then crypto's well-formedness rules judge the record, and the first one broken is the refusal.
- **Strict reading.** A JSON number is taken only as a safe integer (a u64 past 2^53 would already be rounded); `l2FromBlock` and group IDs are decimal strings. Addresses and hashes are `0x` hex of their exact length; the commit is 40 lower-case hex digits, as the script checks it. Addresses in mixed case must carry EIP-55's checksum. Every list and string is bounded by the record's limit, so none reaches the encoder too long. `-0` is refused. Only own properties are read. A refusal names the file and the JSON path of the first bad value.
- **The command:** `admin-cli deployment record --l1 <file> --l2 <file> --inputs <file>`, offline, prints `version`, `record` (hex) and `deploymentHash`. `TIER0_DEPLOYMENT_RECORD` takes `record` as it is.
- **Tested:**
  - `packages/core/tests/deployment-record.test.ts`, on the files `packages/contracts/test/deploy.test.ts` wrote on the Anvil pair (reindented). Every field is where the spec puts it, and the encoding decodes back with crypto's hash. The version follows the inputs. A property test: any order of the origins, game types, groups, token keys, relays and each seat's relays gives the same bytes.
  - Refusals: each mismatch, each contract moved off its CREATE address and both files at another starting nonce, a reordered panel and another threshold (`panel-id`), `ours` of another length, malformed values in each file with their paths (a broken checksum, `-0`, lists and strings past their bounds), the files swapped, and ill-formed records with crypto's rule (registrar threshold, game types, drift, an independent panel with two seats ours, no groups, a region without a self-paid group, a bad, repeated or shared origin, shared RP IDs, a bad token key, a relay for no seat).
  - `apps/admin-cli/tests/deployment.test.ts`: the command's output decodes and hashes, and each refusal's exit code and detail.
- **Known-weak:**
  - `l2_from_block` is the owner's input, not read from the chain: the files carry no block number, since forge writes them before it sends. Part 3's workflow has the receipts and can fill it in. A block after a contract's creation would hide its first events from readers ([[registration]], Outcome).
  - The record lists only the launch panel. A release that pins more panels needs them added here first.
  - The fixtures are a copy of the script's output: a change to the script's format fails here only when someone regenerates them. Part 3's workflow runs this command over the real files.
  - `JSON.parse` keeps the last of two equal keys, so a file read by eye can show a reviewer another value than the one built. The addresses are bound by CREATE and the panel by its identifier; the rest are the release Safe's signers' to check against the printed record.
  - The portal, the anchoring authority, the registrars and the commit are taken from the chain files with nothing on the other chain to check them against.
  - The command reads files, not the chains: that each address holds what the file says is the workflow's check (part 1b's known-weak), the verifier's (1.2) and the release Safe's signers'.

## Part 2b: the services' Railway variables

- **The command:** `admin-cli deployment variables --l1 <file> --l2 <file> --inputs <file> --coordinator <url>` (`deploymentVariables` in `packages/core/src/deployment-record.ts`; `apps/admin-cli/README.md`, Railway variables). It builds part 2a's record from the same files, refused the same way, and prints each service's variables that come from the deployment, so no address, key or pin is copied into a service by hand (T-34, T-37, T-71):
  - `api`: the ceremony coordinator's panel, chain and trustee registry, the Tier 0 group, the pinned panels and the anchor's clock;
  - `web`: the token issuer's chain, group registry, group and the record's hex, only once the inputs list token keys;
  - `setup-worker`: ballot admission's panels, clock, L1 chain, anchor and deadline; the Tier 0 job's chain, group, registry, registrars, threshold, EntryPoint, account and paymaster; the registry sync's chains, portal, four contracts and event version (the stubs' pin, 12); the roots step's groups, registrars and threshold; the stub step's panel and sequencer drift;
  - `creation-worker`: every `CREATE_*` but the URLs and the key;
  - `posting-worker`: its chain and board, the pinned panels and the clock;
  - `seat-<n>`, for each seat `ours` marks: its whole `TRUSTEE_CONFIG`, `pollSeconds` left at its default.

  Every value is lower-case hex or a decimal string, the form each parser takes (the trustee node's only in lower case). The registration account and paymaster, which the record doesn't carry, come from the L2 file and must be its deployer's CREATE addresses after the board (`address`). The services serve region 0 only, so a group in another region is refused (`region`).

- **Tested:**
  - `packages/core/tests/deployment-record.test.ts`: every service's values against the fixtures; each seat `ours` marks, and only those, gets a configuration whose `panelId` is its panel's (a property over `ours`); `web` only with token keys, its record decoding back; refusals: a record refusal, either registration contract moved, a group in region 7.
  - `apps/worker/tests/deployment-variables.test.ts`: the printed variables, with the owner's values filled in, read by the worker's own parsers (creation, stubs, roots, registry sync, Tier 0, pinned panels, posting) to the record's values.
  - `apps/admin-cli/tests/deployment.test.ts`: the command's output, its deployment hash the record command's, its refusals and the required `--coordinator`.
- **Known-weak:**
  - The creation blocks (`TIER0_REGISTRY_BLOCK`, `POSTING_BOARD_BLOCK`) aren't printed: the chain files carry no block, and the services check each against the chain's code, so `l2FromBlock` (at or before) won't do. Part 3's workflow has the receipts.
  - The anchoring runner's `ANCHOR_*` and the Tier 1 relay's `TIER1_*` aren't printed: neither service exists on staging yet, and Tier 1 is deferred (STATUS, Queue).
  - The API's own parsers and the trustee node's aren't run over the output here (neither app depends on core); core's test pins the exact strings, and the forms match those parsers' patterns.
  - The EntryPoint is the L2 file's pin, not checked offline (CREATE addresses don't depend on constructor arguments); the Tier 0 job refuses to start unless the account and paymaster name it on chain.
  - `--coordinator` isn't checked against the record's `api` origins; the seat checks its form at start, and a wrong one costs liveness, not integrity.
  - A pasted value can still go to the wrong service; each service refuses a value that isn't its deployment's only where it reads the chain at start (the Tier 0, creation and registry-sync checks).

## Part 3a: the deployment's confirmation against the chain

- **The command** (`packages/contracts/script/confirm.ts`; `packages/contracts/README.md`, Confirming a deployment): `RPC_URL=<url> vp node script/confirm.ts <record> <broadcast> <artifacts>`. It closes part 1b's known-weak items that part 3 was to take: a record written before forge sends, the transaction hashes, and the code compared with the release build (T-64, T-34). From forge's broadcast file it takes only the transaction hashes, and checks with the chain:
  - the RPC's, the broadcast's and the record's chain are one;
  - every broadcast transaction is a CREATE of a recorded contract under its name, and every recorded contract has one. The ballot check is the board's: it must be listed in the board's transaction, at the board's first CREATE address (nonce 1), which the board pins;
  - each transaction is the deployer's, to no one, at its starting nonce plus its place in the broadcast, mined and succeeded, and its receipt names the contract;
  - the code at each address hashes to the record's `codehash` and equals the build's `deployedBytecode` (`<artifacts>`, required, since `out/` is what `forge script` rebuilt) everywhere but its immutables. The board's `ballotCheck()` must then read back as the recorded ballot check, since the comparison lets any immutable through.

  It prints the record with each contract's `transaction` and `block` added, and refuses (exit 1) naming the contract. The URL comes from the environment: a provider's URL can carry a key. Core's chain-file reader ignores the two new fields, so part 2's commands read a confirmed record unchanged.

- **Tested** in `test/deploy.test.ts`, after the Anvil pair's deployment: both records confirm, each contract with its broadcast transaction and its receipt's block, the ballot check with the board's; the command prints the record, also run through a symlink from a path with a space, and exits 2 without its artifacts directory; `createAddress` against Anvil's deployer's well-known addresses and its nonce bounds. Refusals: another chain's record, an edited code hash, an edited address, a recorded contract no transaction created, a transaction that creates nothing recorded, one that isn't a CREATE, transactions out of order, another starting nonce, another deployer, a ballot check away from the board's first CREATE address, a hash never mined, two hashes swapped, a receipt that created another address than the record's, a reverted receipt, a board whose `ballotCheck()` names other code, a build differing by one byte outside the immutables, and an address whose code was replaced after the run.
- **Known-weak:**
  - The code is compared with whatever `<artifacts>` holds. That it is the release build (README, Release build) is the workflow's to arrange (part 3b).
  - Of the immutables, only the board's ballot check is read back. The others (the panel, registrars, Safe and the cross-chain addresses) come from the simulation; reading each back against `pins` is part 3a-2's (done, below).
  - Only runtime code is compared; constructor effects and creation code are verifier 1.2's binding, still unspecified ([[0044-testnet-deployments]]).
  - The services' creation blocks and `l2_from_block` are now in the confirmed records, but part 2's commands still take `l2FromBlock` from the owner's inputs and print no creation blocks; reading them from the records is a later part.
  - One RPC provider answers every question, and the record's code hashes came from a simulation against the same provider, so a provider that lies consistently (T-34) passes, its blocks included, and a wrong block in `l2_from_block` would hide events from readers. Part 3b should confirm against a second, independent provider and require the same output.
  - A reorg after the run could drop a confirmed transaction. The workflow should confirm after the chains' finality, not straight after the broadcast.

## Part 3a-2: every immutable and pin read back

- **The check** (`script/confirm.ts`, `reads`; README, Confirming a deployment): after the code comparison, each recorded contract's views are called and must return what the record's `pins` and its other addresses say, exactly (T-64, T-34). The code comparison lets any immutable through and a constructor's storage writes aren't in runtime code, so a contract built from other creation code with the release's runtime code passed part 3a-1. Read back:
  - L1: the anchor's `epoch`, `period`, `deadline` and `authority`, that Safe's `getOwners()` and `getThreshold()` (T-69); the relay's `portal` and `board`.
  - L2: the trustee registry's `panelCount()` (1, the only panel the record lists), `panelIds(0)`, `panelOf`, `kindOf` and each seat's `keyOf` against the compressed key (x, and y's parity); the panel's identifier is recomputed from its threshold, size and keys (`DS_PANEL`) before any of it is trusted. The group registry's `threshold`, `registrars()`, `trusteeRegistry`, `initialPanelId` and `domainSeparator()`, against EIP-712's for this chain and address, which covers the cached separator and chain ID. The election registry's seven immutables, the board's four, the account's two and the paymaster's five. The timelock's `getMinDelay()`, the admin Safe's owners and threshold, and the EntryPoint's code hash.
  - Every pin is taken in its form (20- or 32-byte hex, a safe integer or a decimal string), and a missing one is refused, naming its path.
  - Completeness: each contract's reads declare how many immutables they cover, and the sum must be the number the build's `immutableReferences` lists, so a new immutable without a read refuses every confirmation.
- **Tested** (`test/deploy.test.ts`, on the Anvil pair): both records still confirm; each of the 34 views, answered otherwise by a wrapped RPC, is refused naming its contract and view; a seat key with y's other parity and a return one word longer; the anchoring Safe's owners and threshold, the timelock's delay and the admin Safe's threshold; a record whose panel id isn't its keys' hash, whose keys don't match its size, missing a pin, with a cap in exponent form, or naming another EntryPoint code hash; and a build claiming an immutable nothing reads.
- **Known-weak:**
  - The L1 record's `l2ChainId` has nothing on L1 to read it from (the relay pins the portal, not a chain ID); core's record builder checks it against the L2 file.
  - The Safes' owners and thresholds and the timelock's delay are read as they are now, not at deployment: a change between the run and the confirmation is refused, which is the record being stale, not wrong.
  - Who else holds the timelock's roles isn't readable (part 1b-2b's known-weak).
  - The reads are against the same single provider as part 3a-1 (T-34); part 3b's second provider covers them too.
  - Each panel seat's key is checked through the registry's own view; that the stored point is on P-256 is the registry's constructor's check, whose code is the release's.
