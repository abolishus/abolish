## Scope

`apps/ballot`: a static, reproducible build; encryption and proving in a Web Worker; strict CSP; a no-analytics bundle test.

## Part 1: the shell, its CSP and the bundle tests

- `apps/ballot`: a Vite build of React and `@abolishus/ui` into `dist/` (declared for `repro-build`), with relative URLs so one build serves at any path, no module-preload polyfill, no inlined assets and no source maps, and React's licence beside it in `third-party-licenses.md` and IBM Plex's OFL-1.1 in `font-licenses.txt`. One screen so far: what the client is, with its strings in an i18n catalog.
- The CSP is a `<meta>` tag ahead of everything that loads, so it travels with the hash-addressed bytes: `default-src 'none'`; scripts, styles, fonts and images from `'self'`; `connect-src 'none'` until part 2 fetches an election; Trusted Types with no policy; `base-uri` and `form-action 'none'` (T-43).
- An origin of its own: on a path gateway (`/ipfs/<cid>/`, `/ipns/<name>/`) every CID shares one origin, so another CID's page could open or frame the client, read its document and replace `crypto.getRandomValues`, learning the vote and its randomness. The client shows a refusal there instead of running (`src/origin.ts`). It runs from our domains, `abolishus.eth` or a subdomain gateway (T-43, T-41).
- No dev-server script: Vite's development client needs inline styles and a WebSocket the CSP refuses, and a second, relaxed policy could leak into a release. Screens are worked on in Storybook.
- No ADR: nothing here is a one-way door. The CSP can only be tightened or widened by later releases, each pinned by the tests.

Tested:

- `test` (`tests/bundle.test.ts`) builds the app and checks the output: every bundled module is from `react`, `react-dom`, `scheduler`, this app or `@abolishus/ui`; only the page, scripts, styles and IBM Plex fonts are emitted; no analytics, tracking or error-reporting SDK marker (T-67, the brief's bundle test); no URL but a short list of inert strings; no `eval`, `new Function` or string timers; `index.html` has exactly the pinned CSP before the first load, no inline script, style or event handler, and only relative `./assets/` references. Checked by mutation: a `posthog` string, `'unsafe-inline'` in `script-src`, an inline `<script>` and a `fetch` to another origin each fail a test.
- `test:e2e` (`tests/page.e2e.ts`) serves the production build and loads it in headless Chromium: it renders with its stylesheet and self-hosted serif, with no CSP violation, console error or request to another origin; the browser refuses script text, a script URL, `innerHTML`, `insertAdjacentHTML` and an event-handler attribute (Trusted Types), a `fetch` to another origin and to its own, and an image from another origin; served under `/ipfs/<cid>/` it shows the refusal. `test` also checks the path-gateway rule.
- `test:storybook`: the screen's story in both themes, its play function and axe (WCAG 2.2 AA).
- By hand: two builds, one under another timezone, gave byte-identical `dist/` trees.

Known-weak:

- **The build can steer what the CI check sees.** #82 judges the output of a build that runs PR-controlled code, including any `apps/ballot/vite.config.*` (a `.js` or `.mjs` file takes precedence over `.ts`), any `postcss.config.*` from `apps/ballot` up to the root, and Tailwind `@plugin`/`@config` code in any CSS the build loads. Any of it could tell when the check runs and emit clean output only then. Review of those files is the remaining gate (T-59); CODEOWNERS for them is the owner's call.
- **Framing isn't prevented.** A `<meta>` policy can't set `frame-ancestors`; whoever serves the client must send it as a header (P2-11, P4-3). An IPFS gateway may not, so a hostile page could frame the client from a gateway (T-43).
- **The path-gateway refusal only recognises the `/ipfs/` and `/ipns/` convention.** A host that serves many CIDs on one origin under other paths isn't detected, and the refusal doesn't stop a same-origin page from attacking the voter some other way; it only keeps the voter from voting there. Listing only dedicated origins (P4-4) is the real fix.
- **Navigation isn't covered by the CSP.** `connect-src 'none'` stops subresource requests, not a top-level navigation, `window.open`, a link or a WebRTC connection to an attacker's STUN or TURN server, so injected code could still leak data that way. Trusted Types and `script-src 'self'` are what keep injected code from running at all.
- **The e2e runs in Chromium only.** CI installs Firefox and WebKit too, but their Trusted Types support differs; a voter on a browser without Trusted Types keeps the rest of the policy.
- **No release record yet.** The build is reproducible, but nothing signs `dist/` or publishes its hash and IPFS CID; that comes with the client's release pipeline (T-41), and the verifier's 1.1 check needs it.
- **The analytics markers are a deny-list.** The real guards are the package and URL allow-lists and `connect-src 'none'`. Tracking code copied into workspace source under another name would pass the bundle tests; review, and the CSP once the client talks to the API, are what stop it.

## Part 2a: the Web Worker and the election check

- **The worker** (`src/worker/worker.ts`): a script of its own that answers the page's requests and does nothing else. Requests and responses are versioned and matched by id (`src/worker/protocol.ts`); the worker accepts only exact, current-version requests, and a failure comes back as a bare `error`, never a message that could quote a secret. The build check finds none of a listed set of network and code-loading APIs in its script: a dedicated worker takes its CSP from its own response headers, not the page's `<meta>`, so on a host that sends none (IPFS, ENS) nothing else would restrict it, and the page does all I/O (T-43).
- **The `ballot-worker` policy** (`src/worker-policy.ts`): created when the module is evaluated, and `main.tsx` imports it first, so it exists before any other module's code runs (ES modules evaluate their imports in order), closing the window #86 recorded in which code already in the page could claim it. It mints a script URL for the worker's own bundled URL and throws on any other string. A browser without Trusted Types spawns the worker from the plain URL, which `worker-src 'self'` still confines. A worker that fails to load or errors is stopped, and later requests fail at once (`src/worker-client.ts`).
- **The election check**: `checkElectionToShow` in `packages/crypto` (inside the `crypto-review` gate, so no client composes it differently, and a challenge checker can reuse it): decode the definition, check it names the election asked for, check its hash is the one the caller read from the L2 election registry, check it's well formed, decode the display text under the definition's pin, and check the text against the definition's commitment and the spec's rules ([[display-text]], Checks). The registered hash is a required input, so no caller can get `ok` without it. Any failure is a refusal naming the first check that failed. The worker runs it, and `src/election.ts` turns a passed election into what the screens show: the text, the definition hash and the selection rules (T-34, T-41, G-6).
- The client depends on `@abolishus/crypto` (workspace; its `@noble/*` closure is the one #86 allowed). No new npm dependency.

Tested:

Undecodable definitions and texts are refused as undecodable, ill-formed ones with the vector's rule, each good definition under any other election id or any hash but its own (fast-check; the expected hash is computed with `node:crypto` from the spec's formula), and every good text under a definition that commits to another, with rule `commitment`. ## Part 2b-1: display text from the API, and CORS

The client can reach only the origins its `connect-src` lists, our staging API and Base Sepolia, so the API stands in for the IPFS pin the moderation policy describes.

- **Display text in core** (`packages/core/src/display-texts.ts`, `migrations/0011_display_texts.sql`): `storeDisplayText` stores a record for an election only once `checkElectionToShow` from `packages/crypto`, the client's own check, passes it against the stored definition (its hash recomputed from the stored bytes), so the server never serves text the client would refuse. Storing the same bytes again is a no-op; other bytes are a `conflict`. The table is operational (takedown-able, never a result; no foreign key to board tables, per the no-join test): the app role holds `SELECT`, `INSERT` and `DELETE`, never `UPDATE` or `TRUNCATE` (T-34, T-41, T-17).
- **Served under the moderation policy** (`readServedDisplayText`; [[moderation-policy]], Open polls): a hidden poll's text is withheld, except while a poll hidden only as a `threat` can still take ballots (before `closes_at` plus `l1_inclusion_bound`, by the server's clock): every ground cited since the poll was hidden must be `threat`, so a `threat` hide re-cited as `personal-data` is withheld at once and an `illegal` or `personal-data` hide re-cited as `threat` stays withheld ([[moderation-policy]] now says so). A delisted poll's text is served (T-68).
- **The route** `GET /elections/display-text` (`packages/api-contract`): the record as hex, at most `MAX_DISPLAY_TEXT` (a test ties the copy to the spec table); `ELECTION_NOT_FOUND`, `DISPLAY_TEXT_NOT_FOUND`, or `DISPLAY_TEXT_WITHHELD` (451).
- **CORS** (`apps/api/src/server.ts`, `API_CORS_ORIGINS`): only listed exact origins (`https:`, or `http:` on a loopback host; anything else stops the server at start) get `access-control-allow-origin`, refusals included so the client can tell why, with `vary: origin`. A preflight is answered only for a listed origin, the procedure's own method and no request header but `content-type`, and carries no body; credentials are never allowed, so a browser sends no cookie (T-10). A preflight is logged as `OPTIONS <route>` from the fixed list, never with its origin (T-11). Without the list no CORS header is sent.

## Part 2b-2: opening the election a link names

- **The link** (`src/link.ts`): `#election=<64 hex digits>` in the fragment, which no server, gateway or log sees (T-10, T-11). Anything else in the fragment is a broken link, never guessed at. A new fragment in the same tab opens its election from nothing. [[first-answer]]'s mockup hands off `#poll=<definition hash>&pick=<option>`; the website's real handoff ([[P2-22]], [[P2-20]]) must use this form or the client must learn that one.
- **The registry read** (`src/load.ts`, `src/deployment.ts`): `eth_chainId` must report the pinned chain, then `eth_call` to `definitionHashOf(bytes32)` (selector checked against its Keccak-256 in the test) at the registry address the build pins, at the L2's `finalized` head, so a registration that could still be reorganised away isn't believed; never at the `election_registry` a served definition names (T-34). The registry admits only definitions naming its own deployment, so the chain and address pins pin the rest. A zero word is "not registered", and the API isn't asked.
- **Fetching** the definition and display text from the API: no credentials, no referrer, no cache, no redirect; each answer read only up to the largest record it can carry as hex, then refused unread (T-52); exact JSON shapes, lowercase hex. 451 is "withheld" (the text route, not `GET /moderation/status`, decides, as part 2b-1 says the client must), 404 "not found", other errors and network failures "unreachable", anything else "bad answer".
- **The screens** (`src/open.tsx`): "Checking this poll" while the page fetches and the worker checks; one screen per problem, with "Try again" where trying again can help; the worker's refusal (`ElectionRefused`); or the questions (`AnswerQuestions`) with the arrival check, in the reader's language where the election has it (`pickLanguage`: exact tag, then primary language, then the election's first), its text marked with the translation's `lang` (WCAG 2.2 SC 3.1.2). A version-1 definition names no one who asked, so the frame names the election by its hash. Send and "Check the encryption first" say that nothing was sent: sealing and sending are part 3. The worker is spawned only once a link names an election, and a stopped one is replaced on the next try; a failed check stops only the worker it ran on. A new link or a retry aborts the requests of the load before it, and when two requests fail the problem shown follows a fixed precedence, so the same answers always give the same screen.
- **Staging pins no registry**: none is deployed (P1-12c's and P1-18's gates), so a staging build shows "This copy of the ballot can't check polls yet" for every link and asks no one anything. A release pins its own ([[P0-3]]).

- **Times aren't checked yet.** A poll that hasn't opened or has closed is still shown to answer; sending is part 3, which must refuse outside the voting window by the chain's clock, not the device's.
- **The API and the RPC learn which election an address opened.** The fragment hides it from the client's host and gateways only; the page then names the election to the API (in the query) and to the RPC (in the `eth_call`), with the reader's IP address, and once part 3 sends ballots from the same address the API could join the two at the network level (T-10, T-11). A relay or OHTTP in front of both is still to come.
- **Mixed sentences aren't tagged.** The poll's own text carries its translation's `lang`, but a sentence of the screens that quotes it ("You chose: …", the overvote message) is in the screens' language only.
- **A superseded load stops its requests but not a check already in the worker**; the worker answers it, and the page drops the answer.
- **One RPC and one API origin**, both staging's; an outage of either stops every poll. Fallback origins are a CSP and release question ([[P4-4]]).

## Part 3a: sealing in `packages/crypto` (#385)

Part 3 is split: 3a is the seal itself, in the gated package, because the plaintext votes and the encryption randomness reach `apps/ballot` only through `packages/crypto` APIs (AGENTS.md, the verifier's trust base); 3b and 3c wire it into the client (Next).

- **The seal** (`packages/crypto/src/seal.ts`) for ballot version 3, the version every poll [[P2-22]] creates (definition version 5): `sealBallotV3` shares the votes, encrypts each registered seat's shares to its registered key and returns the core's tracking code, shown before the choice; a seat outside the registered key set has no ciphertext and a zero share hash (its shares are sealed to a key made and dropped on the spot, since `encryptShares` takes a key per seat). `challengeSealV3` returns the opening of exactly that core and spends the seal. `castSealV3` derives `ν` under the cell's scope from the definition, proves validity over the core's share hashes, computes the ballot hash and `M` over the L1 block the caller read, and builds the prover's witness with `membershipProverInput` (so a bad secret, a non-member and leaves off the cell's root are refused before any proving; T-10, T-13). `finishSealV3` finishes the proof (verified, re-randomised, verified), assembles the record, checks its core is the one shown (Client rule 3) and runs `checkBallotV3` on it, returning the encoding, ballot hash, `ν` and each qualified seat's ciphertext for its intake, or throwing (Casting steps 2 to 4; T-42, T-45, T-47, T-55).
- **One committed vote per seal.** A second cast of the same seal (a proof that failed before any record existed, or a recast under a newer L1 block, [[revoting]] Client rule 4) reuses the first validity proofs, so the same core never carries two committed votes; another identity is refused. A retry of a record already sent resends its bytes. A seal is bound to an identity only once its witness is made, so a refused secret, non-member or bad leaves leave it castable by the right identity; a malformed L1 reference is refused before any proving. A seal whose validity was proved is never opened, a challenged one is never cast, and a seal opens once (the sharing's `proved`/`opened` mark, plus the seal's own).
- **The cast's randomness is dropped.** Once the witness is made, the seal keeps only the core, the committed vote and the qualified seats' ciphertexts: the sharing and every encapsulation are dropped and the ML-KEM messages zeroed, so a device inspected after the cast holds no opening of it (challenge Client rules; T-18, T-45). Bigints can't be zeroed in JavaScript; dropping them is as far as the platform goes.

Tested: `packages/crypto/tests/seal.test.ts`: a challenged seal's opening passes `checkChallengeOpeningV2` with the code shown and the votes sealed, for every vote the three questions allow (fast-check), in every cell, with and without a seat outside the registered key set (zero hash, nothing revealed); two seals of one vote show different codes; votes outside a question's limits, cells outside the partition and hand-built contexts refused; the witness's scope, index and 32-sibling path for members of two cells; a recast under the same block gives the same witness and under a newer one only a new message; another identity, a bad secret, a non-member and a missing leaf refused; challenge after cast (even a failed one), a second challenge and cast after challenge refused; a refused non-member first, then the right identity casts; malformed L1 references refused with the seal still open to a challenge; a cast whose proof was refused casts again with the same witness; a proof that doesn't verify refused. `packages/membership-prover/tests/seal.test.ts`, end to end with snarkjs: a ceremony run in the test, a sealed ballot cast and proved passes `checkBallotV3` with the ballot hash and `ν` the seal returned, each qualified seat's ciphertext hashing to its share hash; a recast under a newer block passes with the same ballot hash and `ν` and a new `M`; a proof for one cast doesn't finish another.

Known-weak:

- **Version 3 only.** Definition versions 6 and 7 (author panels, rolling electorates) need `sealBallotV4` and the rolling step; nothing creates them yet ([[P2-16]], [[P2-17]]).
- **Nothing calls it yet**: the client still reads only definition version 1 and asks for no seal (3b).
- **The L1 block is the caller's.** `castSealV3` binds whatever block it is given; reading it from L1 (2 deep, Client rules 1 to 3) and keeping the record of named blocks is the client's (3c).
- **No public posting yet.** [[share-encryption]] keeps a seat's ML-KEM message `m_i` after the cast for a seat that didn't receipt, so the voter can post it; the seal drops every `m_i` with the rest of the randomness, so posting needs the seal to keep the qualified seats' `m_i` until receipts settle (3c, with delivery).
- **The throwaway key's shares.** An unregistered seat's shares are encrypted to a key made in the seal and dropped, not withheld: they never leave the seal, and the opening reveals nothing for that seat, but they are computed.

## Part 3b-2b: the cast in the worker (#405)

- **The worker** (`src/worker/session.ts`, protocol version 3): `cast` takes a held seal, the identity secret, the cell's leaves and the L1 block, runs `castSealV3` (record, nullifier, validity proofs, `M` and the witness; the leaves must climb to the cell's root, T-10, T-13), zeroes its copy of the secret, sends the witness alone to the prover worker over the port the page handed it, and finishes with `finishSealV3` (the proof verified against signals computed here, re-randomised, verified again, the core checked to be the one shown, and the record run through `checkBallotV3`). The page gets the record, its hash and the qualified seats' share ciphertexts, never the witness (T-07, T-12, T-55). Refusals: `unknown` (no such seal, or a challenged one), the prover's codes (`secret`, `root`, `not-a-member`, `zkey`, `wasm`, `proof`, `rerandomised`, `prover`), and `ballot` with the verifier's code.
- **A seal the voter cast is never opened**: the worker marks it cast before anything else, so `challenge` answers `cast` even when the cast failed (T-45). A recast of the same seal (a failed proof, or a newer L1 block, revoting Client rule 4) keeps its committed vote; the worker keeps the identity commitment of the seal's first accepted cast and refuses another identity's secret as `secret` before `castSealV3`. The worker zeroes its copy of the secret on every path.
- **The page's side** (`worker-client.ts` `cast`, `prover-client.ts` `castBallot`): one prover worker per cast, as for `proveMembership`, which now shares its set-up. No screen calls it yet (3b-2c).

Known-weak:

- **The page supplies the leaves and the L1 block.** The leaves are checked against the cell's root, so wrong ones only refuse; the L1 block isn't checked here at all (3c reads it from L1, and the voting window by chain time).
- **No timing padding yet**: how long a cast takes, or whether it fails, is visible to the page (and a hijacked prover can choose when it fails); [[P2-21]] part 5 pads where the ballot is sent.
- **A cast that overlaps a new `check-election`** still finishes under the poll it began with; the page names the seal, and the screens (3b-2c) never check a new poll mid-cast.
- **The page's timeout covers the whole cast**: the validity proofs before the prover starts and the checks after it must fit in the prover's timeout plus 30 s, so a very slow phone could see a `WorkerFailure` for a cast that later finishes; the seal stays cast, so it is never opened.
- **Strings can't be wiped**: the witness's decimal strings live until garbage collection, in this worker and the prover's.

## Part 3b-2c-1: the tracking code before the choice, and the challenge (#409)

Part 3b-2c is split: 3b-2c-1 puts the seal and the challenge on the screens; 3b-2c-2 brings the voter's identity, their cell from it and the proving screen into the cast.

- **One action on "Check your answers"**: "Seal my answers". The cast-or-challenge choice moved after the seal, so the tracking code is always on screen before it ([[challenge]], Client rule 1; T-42).
- **The sealed screen** (`src/sealed.tsx`, `Sealed`): the worker seals the answers (`votesOf` in `src/answers.ts`: 0 or 1 per option, every question's in order, refused unless every answer fits) and the page shows the tracking code as a QR code, a fingerprint and its hex, then "Cast this ballot" and "Check the encryption first". It looks the same whether or not anyone scans it and stays until the voter chooses (T-44).
- **The QR code's text** (`src/tracking.ts`, now in [[challenge]], Client rule 1): `ABOLISH:TRACK:1:`, the election id, `:` and the tracking code, each as 64 upper-case hex digits, so it stays in QR's alphanumeric mode and always carries all 32 bytes.
- **A challenge** (`Opened`): the worker opens the seal and the page offers the opening's record bytes (`0x0003`) as a file, `abolish-opening-<first 16 hex digits>.bin`, through a `blob:` link it revokes when the screen goes. The casting device never shows what the opening holds or says it checks: it drew the screen, so only the checker that recorded the code can (T-42). An opening whose tracking code isn't the one shown is never handed over. Then the voter answers again from nothing chosen.
- **A cast** ends at "Your answers weren't sent" until 3c sends it; the page never asks to open that seal (T-45).
- **Which cell**: a version-5 poll of exactly one cell (`CheckedElection.cells`, every tier's cells counted) is sealed in cell 0. A poll of several cells is refused before sealing ("split by region") until 3b-2c-2 finds the voter's cell from their identity, and a version-1 poll is never sealed.
- **A failed seal or opening** (a refusal, a mismatched code or a worker that stopped) shows what stopped, and "Answer again" checks the poll anew, in a fresh worker if the last one stopped, since the worker holds the poll it seals for.

Tested: `tests/answers.test.ts`: `votesOf` is 1 exactly at each chosen option, every question's options in order, for any well-formed questions and fitting answers (fast-check), and refuses a misfit, an unsorted or out-of-range answer and a missing or extra one. `tests/tracking.test.ts`: the QR text carries the election id and all 32 bytes of the code in alphanumeric mode (fast-check), its exact layout, and no text or file name from a short, long or upper-case code. `tests/election.test.ts`: `cells` for both definition versions. `tests/frame.test.ts`: the new screens render no inline style (T-43). `test:storybook` (`src/open.stories.tsx`, `src/sealed.stories.tsx`): a two-question poll is sealed with its one cell and the votes in order, the code is shown as QR, fingerprint and hex before the choice, a cast ends at "not sent" without a challenge and starts again from nothing chosen; a challenge opens the seal it named and offers exactly the opening's bytes under its file name, without the vote; an opening of another code is never offered; a refused seal checks the poll again; a worker failure, a poll of several cells and a version-1 poll stop with their screens; each screen light and dark, with axe.

Known-weak:

- **No checker exists yet.** A voter can scan the code and save the opening, but nothing reads either: the checker ([[challenge]], The checker; P5-4) is the other device's app. Until then a challenge checks nothing for the voter.
- **The download isn't run under the client's CSP in a browser test**: Storybook checks the link's bytes and name, and the bundle check still bans the network APIs; a `blob:` download is a navigation, which the policy doesn't govern.
- **Several cells, Tier 1 and Tier 2 voters**: refused or sealed in the one cell until 3b-2c-2 reads the voter's identity; a one-cell poll's seal is the voter's only if they are in its tier, which nothing checks before the cast.
- **The worker keeps a seal the voter chose to cast** until the next check, since there is no request to drop one; the page never asks to open it, but the worker would (3c marks it cast).
- **The opening isn't wiped**: it lives in the screen's state and the `Blob` until garbage collection, and it can't be saved once the voter leaves the screen (the screen says so, and saving is its first action).
- **The ballot shell**: a `blob:` download doesn't save in Android's WebView and needs a delegate in WKWebView, so the Capacitor shell ([[P5-4]]) needs a native save path for the opening.

## Part 3b-2c-2b-1: the identity on the device, the cell before the seal, the cast through the proof (#420)

Part 3b-2c-2b is split: 3b-2c-2b-1 reads a voting identity the device holds and puts the cell search and the cast on the screens; 3b-2c-2b-2 makes the identity, registers it ([[registration]]) and backs it up ([[identity-backup]]), which is what puts one on a device (Next).

- **The identity store** (`src/identity.ts`): the secret and the tier groups registration added its commitment to (`{ tier, group }`, one to three, one per tier, ascending), in this origin's IndexedDB under one key, and nowhere else. Every read is checked as strictly as a decoder (version 1, exactly these keys, `isIdentitySecret`, tiers 0 to 2, u64 groups, no holes) and hands out a fresh copy of the secret, which the page zeroes once the worker has its own. ## Part 3b-2c-2b-2a: the identity before registration, the Tier 0 request and its outcome (#425)

Part 3b-2c-2b-2 is split: 3b-2c-2b-2a keeps an identity before it is in any group and builds the pieces of a Tier 0 registration the screens will call; 3b-2c-2b-2b brings the challenge page, the frame and the screens that make and register an identity; 3b-2c-2b-2c the backup (Next).

- **The identity store, version 2** (`src/identity.ts`): an identity is kept from the moment it is made, whatever registration's outcome ([[registration]], Outcome), so a record now holds none to three memberships and the Tier 0 request it waits on (`tier0Request`: the region asked for, a u32, and when the route last accepted it), `null` for none, and never a request beside a Tier 0 membership. Version 1 (at least one membership, no request) was never written outside the tests and is unreadable, never migrated. The region is kept so a repeat, and later the direct path, asks for the same one (T-16). A device holding an identity in no tier yet stops at "not listed" when it opens a poll until 2b's screens say why.
- **The outcome** (`packages/crypto`, `tier0Registration`): where a commitment stands among the deployment's published Tier 0 groups (signed and self-paid, each with its region code, from the signed release) at one L2 block: `registered` when its counted occurrence is in a group of the region it asked for, `moved` (an alarm, [[registration]], Outcome) when it is counted in another region's group, `not-yet` when it is in none (or only as a removed leaf). Each group is replayed strictly under the release's registrars and ranked by the first-occurrence rule, the code `tierMembership` and the verifier's 2.4 share, from the registry's whole record set, so the client never asks the service or an indexer about its own commitment (T-11, T-13, T-71).
- **The request** (`src/registration.ts`): the challenge frame's `src` (the client's origin and `tier0-register` in the fragment, percent-encoded), the one message it accepts from the frame (from the pinned challenge origin and its own frame's window, exactly `{ v: 1, token }` with a token of Turnstile's form, from a plain object), the route's body (64 lowercase hex digits, a canonical decimal region, the token; a value the route would refuse before Turnstile is refused here, so no solve is spent on it), and the answer: each refusal the route defines only at its own status, a `400` as `malformed` only in the route's own shape (`BAD_REQUEST`; a bare one is an edge's, which mustn't keep the direct path from being offered, T-25), and anything else (a proxy's page, an unknown code, an answer over 4 KiB, a `200` that isn't `{}`) `unreachable`. The request carries no cookie, referrer or credential and follows no redirect (T-10).
- **The retry heuristic** (`retryDue`): a request may be sent again once `(MAX_REGISTRATION_HOLD + 2) · REGISTRATION_PERIOD` = 4,800 seconds of finalized L2 time have passed since it was accepted with the outcome still `not-yet`, so finality is counted as it happened rather than guessed.

Tested: `packages/crypto` `tests/self-paid.test.ts`: for every tier of `self-paid.json` that ranks its leaves, each commitment's outcome in each region is the one the vectors' ranking gives (region codes offset from the vectors' indices, so a mix-up can't pass); a removed leaf counts nowhere and a later self-paid copy is the occurrence; the registry is read only up to the block given; a history the registry can't log is refused (`group-history`, `group-created`); arguments outside their forms throw. `tests/tier-membership.test.ts`: over `regional-cells.json`'s signed groups with random region codes (fast-check), a commitment is registered in its first adder's region and moved in any other; a commitment no published group adds, or only an unpublished one, is `not-yet`. `apps/ballot` `tests/identity.test.ts`: what is stored reads back for any secret, none to three memberships and any request beside no Tier 0 membership (fast-check); version 1 and 3, a request beside a Tier 0 membership and every malformed request (an extra or missing key, a negative, past-u32, fractional, string, bigint or -0 region, a negative, unsafe, fractional, -0 or `Date` time) are refused. `tests/registration.test.ts`: the frame's `src` and its refusal of anything but a bare HTTPS origin; any token of Turnstile's form is accepted and anything else ignored (fast-check), as is a message from another origin, another frame, or with another version, an extra key or another prototype; the body is the route's three fields for any commitment, region and token (fast-check), and refuses forbidden commitments, regions outside u32 and tokens outside the form; every route answer is read as its kind, and fifteen others as `unreachable`; `retryDue` at its boundary (fast-check). `tests/worker.e2e.ts`: a version-1 record is unreadable.

Known-weak:

- **Nothing calls it yet**: no screen makes or registers an identity until 2b, and the outcome needs the registry's records, which the client can't read until a group registry is deployed and pinned (`STAGING.registrars` is `undefined`) and 2b reads its logs from the L2.
- **The challenge frame needs the owner**: the client's policy has no `frame-src`, and the challenge page needs an origin of its own ([[registration]], Challenge page) served with its own headers; both are `ci:` changes (the policy check in `.github/tools/ci/src/ballot.ts`, the deploy workflow) that 2b proposes.
- **The retry compares two clocks**: `acceptedAt` is the device's, the finalized block's time the chain's; a device clock far ahead delays a retry, one far behind allows it early, which costs only a solve (a repeat is harmless, [[registration]], Answers).
- **The outcome is only as good as the L2 endpoint**: the client reads the registry's records from one endpoint with no light client, so a lying endpoint can invent a self-paid addition (which carries no registrars' approval) and show `registered` or a false `moved`, or hide an addition. Signed additions are checked under the release's registrars. The same trust as the cell search (`tierMembership`); 2b should confirm a `moved` against a second endpoint before telling the voter to start again (T-16, T-11).
- **No direct path**: the registry has no self-paid call on staging yet ([[P3-2]] part 5b), so a refused registrant has no other way in (T-25).

## Part 3b-2c-2b-2b-2a: the group registry's log, and the outcome in the worker (#438)

Part 3b-2c-2b-2b-2 is split: 3b-2c-2b-2b-2a reads the group registry from the L2 and works out a registration's outcome in the worker; 3b-2c-2b-2b-2b puts the outcome on the screens; 3b-2c-2b-2b-2c brings the challenge page and its frame, which may be wired only once a waiting voter can see the outcome (Next).

- **The whole log, from the L2** (`src/load.ts`, `loadGroupRegistry`): the RPC's chain is checked first, then the finalized head (number and timestamp), then every log of the registry's address from its deployment block to that head, by `eth_getLogs` over ranges of `LOG_RANGE` (10,000) blocks with no topic filter, so the requests name the registry and block ranges only, never a group, region or commitment (T-10, T-11, T-13). Each log is checked as strictly as the API's answers: of the registry's address, inside the range asked, not removed, one to four 32-byte topics, data within `MAX_EVENT_DATA`, lowercase hex and canonical quantities, and strictly after the last log read by block and log index, so a log repeated across ranges or served out of order is refused, not counted twice (the first-occurrence rule ranks by place in the log). A secret that isn't one, or whose commitment is forbidden, is `secret`; a record that doesn't decode, `record`; a history the registry can't log, `registry` with the replay's code. A clock far behind, or an endpoint inflating the time, offers "Send it again" early; a clock far ahead delays it. A repeat needs the voter's tap and a solve, and changes nothing ([[registration]], Answers); noting the acceptance in chain time would close it.
- **The page holds its copy of the secret across the worker's outcome**, which replays the whole registry, so that the membership is kept only beside the identity whose secret was read (`recordTier0Membership` compares the secrets); `note()` holds it the same way across a commitment. Comparing commitments instead would let the page zero it as soon as the worker has its own (T-12).

## Part 3b-2c-2b-2c-1: the backup passkey and the backup (#451)

Part 3b-2c-2b-2b-2c-2 waits on a `ci:` change (the challenge origin in `frame-src`, and `apps/challenge` deployed with staging) and on a Turnstile site key for that host, so the backup ([[0017-identity-recovery-backup]], Option A; [[identity-backup]]) came first. Part 3b-2c-2b-2c is split: 2c-1 is the client's machinery for a backup, without screens; 2c-2 the screens, recovery and the starting again after `moved` (Next).

- **The ceremonies** (`src/backup.ts`, T-20): the backup passkey is a discoverable credential of the deployment's `backupRpId` (staging: `ballot-staging.up.railway.app`, the host decided for the client on 2026-10-17), user handle 32 random bytes, user name and display name one fixed label for every voter, user verification required, no attestation, and the PRF evaluated with the spec's salt (Option A, step 2). The client goes on only if the authenticator data shows UV and the PRF's `results.first` is exactly 32 bytes; data that sets BS without BE, or isn't WebAuthn's shape, is refused. An authenticator that answers the PRF only at evaluation is asked again, by the new credential's ID alone. The browser's copy of the PRF output is zeroed as soon as it is read, whatever else is wrong (T-41).
- **One passkey per device:** the new passkey's ID is kept (`saveBackupCredential`, beside the identity under its own key) before anything else can fail, and a device that keeps one only ever evaluates it, allowing that credential alone, so it never makes a second (Option A, step 6). The record also notes BS, read anew on every use, and when an envelope was last stored. Excluding the kept ID at creation, as step 6 also says, would only matter if the client created while holding one, which it never does.
- **The seal in the worker** (`backup-seal`, protocol version 7): the page reads the identity afresh after the ceremony, hands the PRF output and the secret to the worker, which seals with `sealIdentityBackup` and zeroes both, and zeroes its own copies (T-12, T-41). The locator and envelope come back.
- **The request** (`putIdentityBackup`): `POST /backups` with both as lowercase hex in the body, no credential, referrer, cache or redirect (T-10); only the route's own refusals read as `rejected`, anything else as `unreachable`. The JSON answer reader moved from `registration.ts` to `answer.ts` for both.
- **The read-back** (`fetchIdentityBackup`): after the store the client fetches the envelope under the same locator and records it as stored only if the route gives back exactly those bytes, so an envelope accepted but not kept isn't reported as a backup (T-66).
- **The steps** (`backUp`): no ceremony without an identity to back up or with an unreadable credential record; then the passkey, the seal, the store, the read-back and the record's update. The outcome carries BE and BS apart, so the screens can say "can't sync" or "not synced yet". Run again it reseals with a fresh nonce under the same locator, which is how a backup outlives the route's 24-month retention.

Tested: `tests/backup.test.ts` against a stand-in authenticator: the options of both ceremonies (the salt checked against `docs/spec/vectors/identity-backup.json`; fresh handle and challenge per creation); the flags over arbitrary authenticator data (fast-check); every refusal (no PRF, no UV, PRF outputs of the wrong length, BS without BE, cancellation, other errors, answers outside WebAuthn's shape, another credential than the kept one), each with the browser's PRF copy zeroed; the request's shape and every answer; and `backUp` end to end over the real worker session, with the stored envelope opened by `@abolishus/crypto` to the identity's secret under the PRF output and its locator the spec's, the read-back (no envelope, another one, no answer), the order of the steps (the passkey kept before the seal), every stop before anything is kept or sealed, and the page's secret and PRF copies zeroed. `tests/session.test.ts`: the seal opens to the secret under its locator for arbitrary PRF outputs and secrets (fast-check), a fresh nonce each time, non-secrets refused, both inputs zeroed, the held poll untouched. `tests/worker-protocol.test.ts` and `tests/identity.test.ts`: the new request's and record's shapes, strictly.

Known-weak:

- **No screens yet**: nothing calls `backUp`, and nothing tells the voter a passkey that isn't backed up (BS clear) dies with its authenticator. Part 2c-2.
- **A passkey that can't serve** (no PRF, no UV) is left in the voter's passkey provider, unkept, and the next try makes another. It isn't kept on purpose: a device that kept it would evaluate only it, and could never back up. Passing it in `excludeCredentials` would refuse a new passkey on the same authenticator outright. The Signal API could ask the provider to drop it; not yet. The same goes for a new passkey whose ID the browser refused to keep.
- **The well-known file gates the screens**: staging serves the client from the RP ID's own host, so no `/.well-known/webauthn` is needed yet, but [[0017-identity-recovery-backup]] (Consequences) asks for it in the signed release, with a test that it lists no `apps/web` origin, before backups ship. Part 2c-2 doesn't offer `backUp` to voters on a release build until that file, its test and [[P1-19]]'s served-file check exist.

Staging only: an RP ID can't move for existing credentials, so a release's backup RP ID is a host we control, and staging passkeys never carry over.

- **The record notes no identity**: a stored envelope may hold an identity the device later replaces (starting again after `moved`); part 2c-2 clears the time then and backs up anew.

## Part 3c-1a: the casts' records and the ballot route's answer (#471)

Part 3c (sending) starts with the two pieces a send needs before any screen calls them; 3c-1b wires them into the cast.

- **The casts' records** (`src/casts.ts`; [[revoting]], Client rule 3): for each election and tier, in a database of their own (`abolish-ballot-casts`), every version-3 ballot record this device let leave, with the operator's checked answer once one passed. `recordCast` keeps a ballot only if it names a block strictly newer than every one recorded for that election and tier, in one transaction with the read, so two tabs can't both keep a cast on one block and the device never ties itself (T-45, T-38), and only beside casts naming the same definition (`other-election` otherwise); it is called before the ballot leaves the device, and a retry resends these bytes, never a new ballot (T-25). Each tier's casts are their own (Client rule 7). The block is read from the ballot's bytes, never stored beside them, so the two can't disagree. `recordBoarded` keeps the first checked answer for exactly the recorded bytes; another for the same bytes is `conflict` and changes nothing. A stored record is read as strictly as a decoder (version, keys, every ballot decoding as version 3 and naming one definition, strictly ascending blocks, an entry carrying exactly the cast's bytes, every entry naming one election, and a 32-byte link): anything else is `unreadable`, never read as no casts, and is never replaced.

- **No tie escape yet** ([[revoting]], Client rule 5): `recordCast` refuses any block not newer than a recorded one, so the voter's explicit escape (one more ballot on a watched cast's block) needs its own path, with its own screen, in a later part.
- **A boarded entry's segment isn't checked** against the accepted range ([[receipts]], Checks at cast, check 5): it is only the operator's word until receipts are signed, and the range needs the anchoring clock, which the client doesn't read yet.
- **A lost casts database reads as no casts**: it lives apart from the identity, so clearing one store but not the other leaves an identity with no records; a recovered client's checks (board ballots under its nullifiers, [[0017-identity-recovery-backup]], Consequences) cover this case too, in part 3c's later slices.
- **The list is unbounded**: each write rewrites the election and tier's whole list, up to a megabyte per ballot. Only the voter's own re-votes grow it.

## Part 3c-1b-1: sending from the cast's screens (#479)

The cast now ends on the board: the records and the ballot route of part 3c-1a, wired into `Ballot` (`src/open.tsx`).

- **Gated on delivery:** a build sends nothing until it delivers each seat's share ciphertext to its intake (`ElectionSource.delivers`, `false` in `main.tsx`; `no-delivery` before the L1 block, the records or the proof). A boarded ballot whose shares never reach the trustees outranks the voter's earlier ballot and then fails delivery, voiding their vote ([[0002-everlasting-privacy]], Synchronous intake; [[revoting]], Selection), so delivery comes before any build sends (found by the in-session review).
- **Before the proof:** once the L1 block is read, this device's casts in the voter's election and tier are read, before the prover artifacts and the secret. Unreadable casts stop the cast (`casts-unreadable`), never read as none; a block not newer than the newest recorded one stops it too (`not-newer`, "wait a moment"), so no ballot that would tie or lose to one this device sent is ever proved ([[revoting]], Client rule 3; T-45). The tier is the one the voter's cell was found in, carried from the search through the seal (Client rule 7).
- **Recorded, then sent:** the proved ballot is recorded only if `castAsAsked` (`src/casts.ts`) passes: it decodes as a version-3 ballot record naming exactly the poll's definition, the voter's cell and the L1 block number and hash the client read; anything else is `cast-faulty` and never sent (T-38, T-45). `recordCast` then checks the newest block again in its own transaction, so another tab's cast in between stops this one (`not-newer`); storage the browser refuses is `casts-unwritable`, and nothing unrecorded is sent (T-25).
- **Each answer has its screen** (`src/sealed.tsx`): a boarded answer that passes `checkBoarded` under the poll's pinned board-entry version (`CheckedElection.boardEntryVersion`, new) is kept with `recordBoarded` and shown as "Your ballot is on the board" with its entry index and tracking code, saying it is the board's unsigned word (T-26); a `rejected` answer with `repeat` is the same screen without an index, since a copy on the board counts as this ballot ([[revoting]], Keyed by content); `busy`, `unavailable`, `unreachable` and a boarded answer that fails the check offer "Send again", which sends the recorded bytes, never a new ballot (T-25); another rejection shows its code with no retry, since the operator chose it after the proof saw the witness (T-55); `not-open`, `not-found` and `malformed` stop; a checked answer that differs from the one kept for the same bytes is `answer-conflict`, never shown as on the board (T-38).
- The "nothing was sent" screen (`NotSent`) is gone, and casting no longer says this version can't send.

Tested: `tests/casts.test.ts`: `castAsAsked` passes every vector ballot against its own fields, and refuses another definition hash, cell, block number or block hash (fast-check) and bytes that aren't a version-3 ballot. `tests/election.test.ts`: a version-5 election carries its pinned board-entry version, version 1 none. `src/open.stories.tsx` (interaction and axe): a build that doesn't deliver stops before the records, the proof or any send; the whole cast with the casts read in the voter's tier before the proof, recorded as asked, sent once and the checked answer kept; unreadable casts and a block already used stop before any proof; another tab's record during the proof, a ballot not as asked and an unwritable record stop before sending; busy, then a failed send, then boarded, sends the identical bytes three times after one proof and one record; an entry carrying other bytes is unconfirmed and not kept; a `repeat` reads as on the board; a rejection names its check; a closed poll and a contradicting answer stop. `src/sealed.stories.tsx`: each new screen, in both themes for the board's. `tests/frame.test.ts`: every new screen renders without inline style.

Known-weak:

- **No build sends yet, and none may before delivery exists**: `delivers` is `false`, so every real cast stops at `no-delivery`, and `l1Block` still answers nothing besides. The cast's share ciphertexts (`CastResult.ciphertexts`) are dropped and the cast record has no place for them; delivery (part 3c-1b-2) needs them, and the qualified seats' `m_i` for public posting, kept in the record before the ballot leaves, under a new record version. Only the stories and tests exercise the send path.
- **An unsent cast is lost on reload**: the record survives, but nothing offers to send it again after the page closes; a new cast then waits for a newer block. Resuming it is part 3c-1b-2.
- **No timing padding at send** ([[P2-21]] part 5): the request leaves as soon as the proof is done (T-11, T-13).
- **A checked answer that can't be kept** (`missing`, `unreadable`, `unwritable`) is still shown as on the board: the check passed, but this device forgets where the board put it.
- **No signed receipt**, as in part 3c-1a (T-26).
- **A `repeat` leaves nothing on the device**: the operator answers identical bytes with their entry, so a `repeat` means other bytes with the same `M` are boarded, which only someone who saw this ballot could make, or an operator's claim; nothing is kept that `answer-conflict` or a later receipt check could hold it to (T-38; P2-3's receipts).
- **The record's core isn't compared with the tracking code shown**: `castAsAsked` checks the definition, cell and block, and the worker's seal already checks the core it casts is the one it showed.

## Part 3c-1b-2a: each seat's share kept with its cast (#485)

Delivery's first half: what a cast must keep before its ballot leaves, so delivery to each seat's intake and the posting a voter may choose both survive a reload ([[delivery]], Client rules 2 and 4; [[challenge]], Client rules, step 3; [[share-encryption]], Order of construction).

- **`packages/crypto` keeps `m_i` through the cast** (`src/seal.ts`): `castSealV3` used to zero every ML-KEM message at the first cast, which left nothing to post for a seat that never receipts. It now copies each qualified seat's `m_i` before the erasure, then zeroes the originals and drops the polynomials, the ephemerals `e_i` and the nonces `w_i` as before (T-18). An unqualified seat's `m_i` goes with its throwaway key. `finishSealV3` returns `{ seat, ciphertext, m }` per qualified seat (`CastShare`, exported). A recast of the same seal returns the same ciphertexts and messages.
- **The worker hands them to the page** with the ballot (`CastResult.ciphertexts`, `src/worker/protocol.ts`, `session.ts`).
- **The cast record keeps them** (`src/casts.ts`, record version 2): each cast holds its qualified seats' shares beside its ballot. `recordCast` takes the shares and throws on any that aren't exactly the ballot's qualified seats', in seat order: one per non-zero share hash, each ciphertext hashing to that seat's share hash (`shareCiphertextHash`), each `m` 32 bytes. That is the worker's own output, so a mismatch is this client's fault. A stored record is read as strictly: a share missing, extra, out of order, for the unqualified seat, of another seat or with an `m` of another length makes the casts `unreadable`. Version 1 (no shares) is unreadable; no build wrote one, since none records a cast before it delivers.
- `Ballot` (`src/open.tsx`) records the cast's shares with its ballot. `delivers` stays `false`.

Tested: `packages/membership-prover/tests/seal.test.ts` (real proofs): every kept `m_i` makes a posting that passes `checkPosting` under its seat's registered key and fails with one bit flipped, and a recast keeps the same shares. `tests/casts.test.ts`: the stored casts round-trip with their shares (fast-check), copies handed out, and every malformed share list unreadable and refused by `storedCasts`. `tests/worker.e2e.ts`, in Chromium under the client's CSP: the worker's cast carries every registered seat's share, each passing the public posting check; casts kept with their shares across loads; shares that aren't the ballot's qualified seats' refused with the store untouched; a version-1 record unreadable. `src/open.stories.tsx`: the cast is recorded with the worker's shares.

Known-weak:

- **`m_i` sits unencrypted at rest** beside the ballot, like the rest of the records (T-18): until a seat receipts, whoever reads this origin's storage can strip that share's ML-KEM layer. Erasing a receipted seat's `m_i` (Client rule 2) comes with the receipts, part 3c-1b-2b. Until then the worker's seal holds it too, for as long as the page lives.
- **Nothing delivers yet**: no intake route exists (the trustee node has no endpoint, [[P2-13]]), and the node's intake reads definition version 1 only, while the client casts under version 5.

## Part 3c-1b-2b-1: each seat's receipt checked and kept in place of its `m_i` (#491)

Delivery's receipts, before any delivery: what a seat's intake answers is checked for exactly the cast ballot, and a passing receipt takes that seat's `m_i`'s place in every cast it receipts ([[delivery]], Client rules 1 and 2; [[share-encryption]], Intake and receipts).

- **`packages/crypto` checks a receipt for a cast** (`castReceiptSeatV3`, `src/seal.ts`): the seat a share receipt record (`0x000c` version 1) receipts, only if it names exactly the ballot's definition, its ballot hash recomputed from the ballot and that seat's share hash, and its signature verifies under the seat's signing key in the key set the election was made with (never keys the caller passes, and never an election `questionBallotElection` didn't make). The ballot hash binds no L1 block, so one receipt counts for every recast of a seal.
- **The worker runs it** (`receipt` request, `src/worker/protocol.ts`, `session.ts`), where the poll's checked key set is; `unknown` for no poll held or a ballot that isn't its cast, `refused` otherwise. The worker client turns a pass into a `CheckedReceipt`, the only value `recordReceipt` takes, so an intake's raw answer can't erase `m_i` unchecked.
- **The cast record keeps receipts** (`src/casts.ts`, record version 3): each qualified seat's share holds its `m_i` or its receipt, never both, and a stored receipt is read back only if it fits the ballot (its signature isn't re-checked on the page). `withReceipt`/`recordReceipt` put a receipt in place of `m_i` in every cast it fits, keeping a seat's first; `withCast`/`recordCast` carry a receipt to a recast of the same seal, so a receipted seat's `m_i` is never stored again.

Tested: `packages/crypto/tests/cast-receipt.test.ts` over `intake-v3.json` (independent Python receipts): every accepted delivery's receipt passes for its seat; a receipt for another ballot, every single-byte change, truncation and extension, a seat with no registered key or another seat's key all fail; another election and non-version-3 bytes throw. `tests/cast.test.ts`: real intake (`intakeBallot` with each seat's ceremony keys) on a real cast's shares gives receipts the worker passes, and a forged signature, a truncated record, another poll's ballot and no poll held are refused. `tests/casts.test.ts`: round-trips with receipted seats, every malformed share (both or neither of `m` and a receipt, a receipt for another seat, ballot, share or definition, one that isn't a record) unreadable, the erasure across a recast, the carry to a later recast and not to another seal's cast. `tests/worker-protocol.test.ts`: the request's shape.

Known-weak:

- **`m_i` outlives a receipt elsewhere**: the worker's seal still holds it for as long as the page lives, the cast result the page held keeps its copy, and the browser may keep replaced IndexedDB bytes on disk until it compacts them (T-18). Erasing the seal's copy needs a `packages/crypto` API, part 3c-1b-2b-2.
- **Nothing calls it yet**: no delivery exists, `delivers` stays `false`, so no build records a cast, let alone a receipt.

## Part 3c-1b-2b-2a: a receipted seat's `m_i` erased from the worker's seal (#500)

The first item #485's review left for delivery: once a seat's receipt passes, its `m_i` leaves the worker's seal too, not only the records ([[delivery]], Client rule 2; T-18).

- **`packages/crypto` erases it** (`receiptSealV3`, `src/seal.ts`): for a seal `castSealV3` cast, the seat a receipt receipts, only if the ballot carries the seal's ballot hash (any recast of it, since that binds no L1 block; compared before any signature is checked) and `castReceiptSeatV3` passes it under the election's own key set. On a pass that seat's `m_i` is zeroed and dropped from the seal. A refused receipt, a ballot of another seal and a receipt that doesn't parse erase nothing (T-25); a seal not yet cast throws. A seat already receipted passes again.
- **A recast hands none** (`finishSealV3`): a receipted seat's `CastShare` has no `m` (`m` is now optional).
- **The worker runs it** (`receipt`, `src/worker/session.ts`): after `castReceiptSeatV3` passes, on every seal it cast, so the one the ballot came from loses that seat's `m_i`; a ballot of no held seal (after a reload) is still answered as before.
- **The records take such a share only with its receipt** (`withCast`, `src/casts.ts`): a share without `m` keeps an earlier cast's receipt that fits the ballot; with none held it is `unreceipted`, a new `recordCast` outcome the cast shows as `cast-faulty` and never sends, since the device would then hold neither the seat's `m_i` nor its receipt.

Tested: `packages/membership-prover/tests/seal.test.ts` (real proofs and each seat's own intake): a seal not cast throws; a forged signature, a truncated receipt, another seal's ballot and another seal for this ballot erase nothing (a recast hands every `m_i` as before); a passing receipt erases its seat's `m_i` from every later recast and from no other seat or seal, passes again for a recast, and leaves the copy handed out earlier alone. `apps/ballot/tests/cast.test.ts`: the worker's refused receipts erase nothing and a passing one erases its seat's `m_i` from the recast it hands the page; every receipt passes for the recast too. `apps/ballot/tests/casts.test.ts`: a recast share without `m` takes the earlier cast's receipt; with no cast, no receipt held, or only another seal's, it is `unreceipted`.

Known-weak:

- **The page records the receipt after the worker erased `m_i`**: if `recordReceipt` then fails, the device holds the receipt only in memory, and every later recast of that seal (a reorganisation's included) is `unreceipted` and stops as `cast-faulty`, whose screen doesn't yet say a new ballot recovers. Delivery (part 3c-1b-2b-2b) must record each receipt before it recasts, or erase only once the page has kept it (found by the in-session review).
- **`m_i` outlives a receipt elsewhere**, as in part 3c-1b-2b-1: the cast result the page held keeps its copy, and replaced IndexedDB bytes may stay on disk until the browser compacts them (T-18).
- **Nothing calls it yet**: no delivery exists and `delivers` stays `false`.

## Part 3c-1b-2b-2b-1: a kept `m_i` checked as a posting before any offer (#504)

One of the two things #485's review left for delivery: a stored `m_i` is checked as a posting before the voter is ever offered to post it, since storage checks only its length ([[delivery]], Client rule 4; T-18, T-15).

- **`packages/crypto` checks it** (`castPostingSeatV3`, `src/seal.ts`): for a version-3 ballot of `election`, whether a ciphertext and `m_i` kept for `seat` pass `checkPosting` (the hash against the seat's share hash, the ephemeral's proof and the ML-KEM re-encapsulation) under the seat's KEM key in the key set the election was made with, never a key the caller supplies. `posting-seat` for a seat with no registered key; throws on a seat outside the panel, a ballot of another election and bytes that aren't a version-3 record, as `castReceiptSeatV3` does.
- **The worker runs it** (`posting`, `src/worker/session.ts`, with its request and result in `src/worker/protocol.ts` and `BallotWorker.posting`): against the poll it holds; a ballot that isn't a cast of it, a seat outside its panel or no poll held is `unknown`, a failing posting `refused` with its code. The worker zeroes its copy of `m_i` once judged.

Tested: `packages/crypto/tests/cast-receipt.test.ts` over `intake-v3.json`'s records and ciphertexts (the vectors keep no `m_i`, so a made-up one reaches only the re-encapsulation): the seat's own ciphertext fails only at `posting-encapsulation`, another seat's at `posting-hash`, a seat whose registered KEM key is another seat's at `posting-proof`, an `m_i` of another length is `posting-malformed`, an unregistered seat `posting-seat`, and seats 0, −1, 1.5, 17 and NaN, a ballot of another election and a truncated record throw. `packages/membership-prover/tests/seal.test.ts`: every kept `m_i` of a ballot sealed and proved end to end passes, and a flipped bit doesn't. `apps/ballot/tests/cast.test.ts`: each seat's `m_i` from the worker's cast passes; a flipped bit, another seat's `m_i` and another seat's ciphertext are refused; the worker's copy is zeroed and the caller's isn't; another ballot, seat 17 and a fresh worker are `unknown`. `apps/ballot/tests/worker-protocol.test.ts`: the request's exact keys and types (`m` exactly 32 bytes, the seat a whole number).

Known-weak:

- **Nothing calls it yet**: no posting is offered, since no delivery exists and `delivers` stays `false`. The offer (part 3c-1b-2b-2b-2 or later) must run it on the share it would post and treat a refusal as unreadable storage.
- **Erasing an unreceipted seat's `ct_i` and `m_i`** once the voter declines or `c_D` passes is still to come, with delivery.
- **The ballot is judged as given** (found by the in-session review): the check binds `ct_i` and `m_i` to the ballot's share hash and `vss`, not the ballot to anything, so a stored record altered elsewhere (its nullifier, say) still passes, and a posting under it would name a ballot hash no board carries while giving up the real share's ML-KEM layer. The offer must name a ballot taken from the board's or the contract's copy (or the worker's own seal), never from storage alone.

## Part 3b-2c-2b-2b-2d: a new identity after a move both L2 endpoints show (#512)

What the `moved` alarm of part 3b-2c-2b-2b-2b left out: a way back for the voter, taken only once a second L2 endpoint of another operator shows the same move ([[registration]], Outcome; [[deployment]], Security notes; T-16, T-11). One endpoint alone could fake a move to make a registered voter discard an identity that counts (T-18).

- **The second endpoint** (`src/deployment.ts`): `Deployment.confirmRpc`, staging's `https://base-sepolia-rpc.publicnode.com` (Allnodes, beside Coinbase's `https://sepolia.base.org`), the origin the `ci:` PR #470 added to `connect-src`. `confirming` gives the deployment read through it; the registry's whole log is read there as from the first (`loadGroupRegistry`), from its own chain check and finalized head.
- **Confirmed, disputed or unconfirmed** (`src/register.tsx`): on a `moved` from the first endpoint the screens keep the identity's commitment (the page's secret is zeroed before the second download, as before the first), read the log through the second endpoint, read the identity again and recompute its outcome there. Confirmed only for the same commitment moved to the same group, with both reads past the retry bound (`retryDue`): before it, a signed batch already sent for the voter's own region may still land and count first ([[membership]], Cell tree), undoing the move (found by the in-session review). Not yet, registered at the same block or another group is `outcome-disputed`: one endpoint misreports the log, nothing changes, retry offered. A second read that fails, is refused, is before the bound, or is at a later block and shows the identity registered (the first may only lag) leaves the alarm unconfirmed, with "Check again". Another identity on the device meanwhile restarts the poll's check.
- **Starting again** (`replace`, `replaceMovedIdentity` in `src/identity.ts`): only on the voter's tap, which reads both endpoints afresh, so a confirmation shown long ago is never acted on (found by the in-session review); a move overtaken by then reads as its new outcome (registered, say). Then, with the commitment and region checked again in the same step, and in one transaction with the store's read, the identity is replaced with a new one made on the device, only while it holds that secret, still waits on a Tier 0 request and is in no group of any tier. Otherwise `not-replaced` (kept, "Your voting identity was kept") or `unwritable`. The poll's check then offers the new identity's registration as any made identity's.
- [[registration]] (Outcome) says when the client may discard a moved secret, the one exception to keeping it whatever the outcome.
- The alarm's text no longer says this client can't replace an identity; the confirmed screen says the old one is discarded from the device and that a backup of it still holds it until the new one is backed up.

Tested: `src/open.stories.tsx` (interaction and axe): one endpoint's move on a build with no second one, a second read that fails or whose log is refused, either read before the retry bound, and a later second block showing the identity registered stay unconfirmed with nothing kept, sent or replaced, and check again; a move both show is read from the second endpoint for the same identity and, on the tap, read afresh from both, replaced and offered for registration, every secret handed out zeroed; a move overtaken by the tap is kept as registered with nothing replaced; not yet, registered at the same block and another group on the second endpoint are disputes that change nothing; another identity's commitment at the tap keeps it; a replacement the store refuses or can't write stops. `src/register.stories.tsx`: the unconfirmed and confirmed alarms in both themes, the working screen and the dispute. `tests/worker.e2e.ts`, in Chromium under the client's CSP: a replacement only of the identity holding that secret while it waits and is in no group (none held, one waiting on nothing, another secret, one in a Tier 2 group all `changed`), a replacement equal to the old secret or not an identity secret thrown, and the old secret gone once replaced. `tests/load.test.ts`: the second endpoint's deployment differs only in its RPC, every request of its read goes to it alone, and staging names it.

Known-weak:

- **Two endpoints, and one operator for both new origins** (T-43): a move is confirmed by Coinbase's and Allnodes' nodes, so two colluding or compromised operators can still fake one and make a registered voter discard their identity. A release should name endpoints of more operators and require them all.
- **The old identity is discarded**, not kept: its commitment stays counted in the other region's cell, where nobody holds its secret any more, padding that cell (T-16). Keeping it would let this device vote twice in a Tier 0 poll.
- **The new request goes the same way**: through the operator's registration route, which, with Cloudflare and our hosting, is among the parties that could have made the move (T-11, T-69). The direct path through an endpoint of the voter's choice ([[registration]], The direct path) isn't in the client yet.
- **The backup still holds the moved identity** until the voter backs up the new one, which replaces the envelope; a recovery from it in between restores the moved identity, and the recovery screens' area warning is the only check.
- **A Tier 0 identity costs one solve** (T-01): starting again is no costlier than registering the first time.
- **A batch held past the retry bound** can still land after the voter started again: the old commitment then counts in their own region with nobody holding its secret, and the new one is registered beside it (T-16, T-13). The bound is the registration service's own hold; a sequencer or service that delays a signed batch longer can still cause this.

## Part 3c-1b-2b-2b-2a: the operator's intake relay (#528)

Client rule 4's first route ([[delivery]], Client rules 4), which delivery waits on: the trustee node's endpoint exists (`POST /v1/intake`, [[P2-13]] #483) and takes version-5 ballots since #525, but nothing on the operator's side reaches it, and a node's own origin isn't in the client's `connect-src`.

- **`POST /v1/intake/seats/{i}`** (`apps/api/src/intake.ts`): the client posts the node's own `Delivery` envelope (stub, approved transcript, ballot record, `ct_i`), which the relay decodes (400 otherwise) and sends on to seat `i`'s endpoint, answering as the node does: 200 with the receipt, 422 with the refusal's code, 503 when busy. A node that is down, times out, negotiates anything but the hybrid group or answers anything else is 502, logged by kind only. Nothing is judged: the node admits and signs, the client checks (Client rules 1).
- **The voter's address stays with the operator** (T-11): each delivery goes on a connection of its own (no kept-alive socket) with the body, its type and length, and nothing of the client's request.
- **Post-quantum outbound** (T-39): TLS 1.3 offering only `X25519MLKEM768`, the node's certificate checked against the system's roots.
- **Bounded** (T-52): its own slots (8) inside the server's, taken once the body is read and decodes; the body at `MAX_DELIVERY`, the answer at `MAX_INTAKE_ANSWER` (4 KiB), the node's time at 25 s.
- **Configuration**: `API_INTAKE_ENDPOINTS`, each default-panel seat's endpoint as the release lists it, seat 1 first; with the ceremony's coordinator configured, one per panel key or the server won't start. The request log names the route's template, never the seat. CORS: `POST` and `content-type` only, from the listed origins.

Tested: `apps/api/tests/intake.test.ts`, against `apps/trustee-node`'s real endpoint over TLS with the hybrid group and against raw nodes: the receipt and a refusal's code come back as the node gave them, to the right seat only; any delivery (fast-check) reaches the node byte for byte; the node sees only `host`, `content-type`, `content-length` and `connection` whatever the client sent (a forwarding chain, origin, user agent), on a new connection each time; a seat with no endpoint, a malformed seat or a query string is 404, a truncated or extended body 400, another type 415, past the bound 413, an account credential 400, all with nothing sent on; no relay configured is 503; a node's failure, another type, a non-code refusal, an oversize answer, a redirect and no answer in time are 502 with their log line, a busy node 503; a classical-only node, an untrusted certificate and a node that is down get nothing; past the slots 503, freed once the node answers; the preflight and the log's templates; endpoints that aren't plain `https:` URLs, or none or seventeen, refused.

Known-weak:

- **The inbound leg's TLS is the deployment's proxy**: [[0002-everlasting-privacy]] holds every intake endpoint, ours included, to `X25519MLKEM768`, and the server can't check what the proxy in front negotiates (T-39). [[P2-11]]'s deployment must, and a browser that doesn't offer the group leaves a recorded `ct_i` exposed to a later quantum break of that handshake.
- **The operator sees the voter's address beside the delivery**, as it does beside the ballot on the board path (T-11); the client's route through an anonymiser to the node's own endpoint is the one that hides it from both.
- **Default panel only**: an author panel's seats ([[P2-16]]) aren't relayed, since their endpoints aren't in the release.
- **Nothing calls it yet**: the client's delivery is the next part, and no deployment takes a ballot until [[P2-13]] part 3's electorate check (which waits on part 4c-2 for version-5 stubs).

## Part 3c-1b-2b-2b-2b: delivery before sending, through the operator's relay (#529)

Synchronous intake on the client's side ([[0002-everlasting-privacy]], Synchronous intake; [[delivery]], Client rules 1 to 4): once a cast is recorded, each qualified seat's `ct_i` goes to its intake through the relay of part 3c-1b-2b-2b-2a, every receipt that passes is kept in place of that seat's `m_i`, and the ballot is sent only once every qualified seat is receipted.

- **What a seat's intake takes** (`packages/crypto`): `sealingElectionV5` now returns the transcript bytes it checked beside the election, and `encodeElectionStubV5` gives the stub's bytes (the definition with `ceremony_transcript_hash` zeroed, header included), which `electionStubV5Hash` now hashes.
- **The worker hands them over** (`intake` request, `src/worker/protocol.ts`, `session.ts`, `BallotWorker.intake`; protocol version 9): the held poll's stub and the transcript its seal keys came from, copied, or `no-election` for no poll held or another one. The page never picks the transcript out of the board itself (T-37).
- **The relay's route** (`src/intake.ts`, `deliverShare`): `POST {api}/v1/intake/seats/{seat}` with the trustee node's `Delivery` envelope (stub, transcript, the whole ballot record, `ct_i`; four `bytes<2^20>`), `application/octet-stream` and nothing else, with no credential, referrer or redirect (T-10). A receipt is read only as `application/octet-stream` and only up to 4 KiB (`readBytes`, `src/answer.ts`; T-52); a refusal only as a node's code; 503 is busy, 502 unavailable, 400, 404, 413 and 415 `not-relayed`, anything else and a network failure unreachable. `m_i` never leaves the device here.
- **The cast's screens** (`src/open.tsx`): after `record`, the delivering screen; the shares go four at a time; each answer that is a receipt goes to the worker's `receipt` check (which erases that seat's `m_i` from the seal) and, on a pass, to `recordReceipt` before anything else, so the record is never behind the worker (part 3c-1b-2b-2a's known-weak). A receipt that fails the check is no receipt; a passing receipt for another seat than the one asked counts for its own seat. Any seat left unreceipted is "Your ballot hasn't reached every trustee yet" with "Send again", which delivers only the seats left, with the same bytes, then sends; nothing reaches the board meanwhile, since a ballot boarded undelivered would outrank the voter's earlier one and then fail delivery ([[revoting]], Selection). A receipt the store can't keep stops as `casts-unwritable` or `casts-unreadable`, a worker that lost the poll or failed during the check as `cast-failed`, all before sending.
- **`delivers` now means every route**: the flag stays `false` in every build until Client rule 4's other routes (a node's own endpoint through an anonymiser, and the posting offer) exist, so no ballot is made and no relay ever holds one; reading L1 alone can't open a relay-only build (found by CI's `crypto-review`). The stories run the delivery with it set.

Tested: `packages/crypto/tests/questions-vectors.test.ts`: every valid version-5 vector's stub bytes hash, by the spec's formula with `@noble/hashes`, to the vector's own stub hash, and decode to the definition with a zero transcript hash. `tests/sealing-election.test.ts`: the transcript returned is the one boarded. `apps/ballot/tests/session.test.ts`: the worker's stub and transcript open as the node opens them (the stub decodes with no transcript hash, the transcript checks under its stub hash and the two make exactly the registered definition); copies; nothing for another poll, none or after a refused check. `tests/intake.test.ts`: the request's URL, method, headers and options; the envelope read back by hand, not with the codec, field by field for any delivery and seat (fast-check); a seat outside 1 to 16 throws with nothing sent; each answer read in its own shape, and a receipt of another type or past the bound, a refusal that isn't a code, too long, not UTF-8 or past the bound, a 500 and a 201 unreachable. `tests/worker-protocol.test.ts`: the request's exact keys and types. `src/open.stories.tsx` (interaction and axe): a cast delivers each seat's `ct_i` with the worker's stub and transcript and the whole record, checks and keeps both receipts before the ballot is sent; a refusal from one seat leaves it undelivered and unsent, and "Send again" delivers that seat alone with the same bytes, then sends; busy, failing and unreachable intakes leave every seat undelivered; a receipt the worker refuses is not kept; another seat's receipt doesn't stand for the seat asked; a receipt the store refuses stops; a worker that lost the poll or fails at the check stops, nothing sent. `src/sealed.stories.tsx`: the delivering and undelivered screens.

Known-weak:

- **One route only**: the operator's relay. Client rule 4 asks for at least one route that bypasses the operator (a node's own endpoint through an anonymiser) before delivery counts as failed; that needs the nodes' origins in `connect-src` (a `ci:` change) and an anonymising path (T-11, T-25). Until then an operator that refuses a seat's delivery while keeping the whole ballot record can board that ballot itself: it outranks the voter's earlier ballot and fails delivery, voiding their vote (found by the in-session review). The undelivered screen says so and asks the voter to answer again while the poll is open, never that the earlier ballot stands; and `delivers` stays `false`, so no build makes a ballot until the second route and the posting offer land.
- **No posting offer yet**: a seat that never receipts blocks the cast, rather than being offered to the voter as a posting (Client rule 4), and its `m_i` stays in the record until a later part erases it on the voter's choice or at `c_D` (T-18).
- **A receipt the store refuses leaves the record behind the worker** (found by the in-session review): the worker has erased that seat's `m_i` from its seal, but the stored record still holds `m_i` and no receipt, though the node receipted. The cast stops there; the part that resumes casts or offers postings from the store must deliver such a seat again (its node answers with the same receipt) before ever offering to post it (Client rule 2; T-15, T-18).
- **An unsent cast isn't resumed after a reload**: its record holds its shares and any receipts, but the page that recorded it is the only one that delivers or sends it.
- **The receipts aren't seen onto the board** (Client rule 3): they are kept, but nothing submits them through the board path or checks that a node boarded its own.
- **The operator sees the voter's address beside each delivery**, as at the ballot route (T-11), and every seat's delivery leaves at once with the ballot's send after it, which ties them together for anyone watching the operator's traffic.

## Part 3c-1b-2b-2b-2c: resuming a cast the board never confirmed (#536)

What part 3c-1b-2b-2b-2b left for a later part: a cast recorded but never seen onto the board, because the page that recorded it went away (a reload, a crash, a closed tab) or stopped (a receipt the store refused, a worker that failed), is finished from the record on the next visit, with the same bytes ([[revoting]], Client rule 3; [[delivery]], Client rule 4; T-25, T-18).

- **The cast to resume** (`unsentCast`, `src/casts.ts`): the newest of an election and tier's casts, if no checked answer of the board is kept for it, with its tracking code (the core hash, `cellCoreHash` of the record's definition, cell, `vss` and share hashes, the code shown before the voter cast it) and every seat that still holds its `m_i`, with its `ct_i`. Only the newest: an older one is outranked by it wherever both are boarded. A newest cast that isn't a version-3 record of the poll's definition is `other-election`, and nothing is sent from it.
- **On opening a poll** (`src/open.tsx`): a build that delivers reads its casts in each of the poll's tiers before showing the questions ("Opening your ballot"), and the first tier's unsent cast is offered on a new screen, "Your last ballot here wasn't sent", with its tracking code, "Send again" and "Answer again", which stays offered whatever the resend answers. Nothing leaves before the tap. "Send again" runs the same delivery and send as a fresh cast: each seat still holding `m_i` is delivered to its intake through the relay with the worker's stub and transcript, each passing receipt checked by the worker and kept before anything else, and the ballot sent only once every qualified seat is receipted; a receipted seat is never delivered again. "Answer again" leaves it, and the new cast replaces it. Casts that can't be read offer nothing here (the cast's own read stops on them); a cast of another definition stops as `cast-faulty`. A build without every route (`delivers` false, every build so far) reads nothing and resumes nothing.
- This settles part 3c-1b-2b-2b-2b's known-weak about a receipt the store refuses: the record still holds that seat's `m_i`, so the next visit delivers it again and its node answers with the same receipt, before any offer to post it.

Tested: `tests/casts.test.ts`: no casts and a boarded newest (whatever came before it) resume nothing; the newest unboarded cast resumes with exactly its seats holding `m` (fast-check over stored casts), as copies; its tracking code is the core hash of `ballot-v3.json`'s generator for each valid committed vote, in a record built around it; another definition and bytes that aren't a version-3 record are `other-election`. `src/open.stories.tsx` (interaction and axe): a recorded, unsent cast is shown on opening with nothing sent until the tap, then only its unreceipted seat delivered with the recorded bytes, its receipt checked and kept, and the same bytes sent and their answer kept, with nothing found, sealed, proved or recorded; a cast every seat receipted is sent with no delivery; "Answer again" leaves it for the questions; a seat that still refuses leaves it undelivered and unsent, and it can still be left for a new answer; a cast of another definition is never sent; a build that doesn't deliver reads no casts. `src/sealed.stories.tsx` and `tests/frame.test.ts`: the new screens.

Known-weak:

- **A `repeat` answer keeps no entry**: a resend the operator answers as a copy already on the board is shown as sent, but nothing is recorded for it, so the next visit offers the same cast again, and sending it again is answered the same way. Recording it needs the operator's receipt and inclusion proof for the existing entry (Client rule 3).
- **A cast the voter leaves keeps its `m_i`** until a later part erases unreceipted shares when the voter declines a posting or `c_D` passes (T-18).
- **Only this device's record**: a cast recorded on another device, or before a recovery, is unknown here.
- **The identity isn't read on resuming** (found by the in-session review): a cast recorded under an identity the device has since replaced after a confirmed `moved` (part 3b-2c-2b-2b-2d) is still offered, under the old identity's nullifier. Sending it adds nothing the voter couldn't have done when they cast it, and a ballot under the new identity in the same poll counting beside it is that replacement's known-weak (T-16); recording the identity's commitment beside each cast would let the client offer only the current identity's.
- **One tier at a time**: only the first of the poll's tiers holding an unsent cast is offered; another tier's waits for the next visit (Client rule 7 casts tiers separately anyway).
- **A cast of another definition stops the poll on this device** (`cast-faulty`, with no way on), as it already stopped a new cast at `record`.
- **Nothing calls it in a build yet**: `delivers` stays `false`, so no build records a cast to resume.

## Part 3c-1b-2b-2b-2d-1a: the board path's judge and store for share receipts (#544)

Client rule 3's first half needs somewhere to send a receipt: the operator's board path for share receipts ([[delivery]], Boarding), which a seat's node uses too. Nothing boarded a receipt before, and the board table's own payload check refused them. This part builds the judge and the store; the route and the client's submission are part 3c-1b-2b-2b-2d-1b.

- **The judge is the verifier's** (`electionAdmission`'s `receipt`, `packages/verifier/src/admission.ts`): rule 1 (the record decodes strictly as the share receipt the election's ballot version fixes, names this definition, and names a seat of the registered key set), then rule 4 against the boarded ballot its ballot hash names (`check`: crypto's `castReceiptSeatV3`, so the ballot hash is recomputed from the ballot, the share hash is that ballot's own for the seat, and the signature verifies under that seat's registered signing key). Only definition version 5's receipts are judged yet (ballot version 3, what the client casts); another version's are `unsupported-version`, never judged under the wrong ballot hash (T-36). `ElectionAdmission` also gives `l1InclusionBound`, for the window.
- **The store** (`BallotAdmissions.submitReceipt`, `packages/core/src/admission.ts`): the election's admission as for ballots; rule 3 by the anchoring clock (`not-open` from the segment after `s_D`, and an entry `appendEntry` would raise past it, `segment-late`, is refused too); rule 1; rule 2 by the ballot hash admission now stores with each ballot it boards (`board_ballot_hashes`, `readBallotByHash`, one read whatever the board holds, T-52); rule 4; then `appendEntry` with a receipt key. Rule 5 by `board_share_receipts`, read under the board's lock: the same bytes again return their entry, and a passing receipt in other bytes for a seat whose receipt the board path already carries returns that earlier entry as `earlier`, writing nothing, so a sender is handed the entry to check and keep (Client rules 3). At most one receipt per seat of a ballot hash reaches the board this way, and each carries no chosen bytes beyond a registered seat's signature nonce (T-17, T-52). Refusals are `ReceiptError`s (`unknown-election`, `not-open`, `rejected` with the verifier's code, `receipt-ballot` or `share-receipt`), each writing nothing.
- **Migration 0027**: the two tables, append-only by grants and triggers like `board_ballot_keys`, each row checked against the entry it names (a ballot; a share receipt after a ballot of its hash); and the board's payload check now takes `0x000c`, which board-entry versions 3 to 7 allow ([[board]], Allowed payloads). Ballots boarded before it have no hash row, so a receipt for one is refused as naming no ballot until the board is rebuilt.

Tested: `packages/verifier/tests/receipt-admission.test.ts`, over an election whose ceremony `tests/receipt-poll.ts` runs (verifier-ballots-v3.json's definition and admitted ballots under the test's panel and transcript, the receipts signed by each seat's key over the spec's statement, never with the check): each seat's honest receipt of each ballot passes against it and against no other; another definition, a seat outside the key set, and every decoding failure (truncated, trailing, another type, version 2, empty) are refused at rule 1; another seat's signature or share hash, or a ballot hash that isn't the ballot's, fail rule 4; rule 4 on bytes that aren't a ballot of the election is false and never throws; any single-byte change of an honest receipt stops it (fast-check); a definition of version 1 refuses every receipt. `packages/core/tests/share-receipts.test.ts`: every seat's receipt of every ballot boarded once, in the segment of its time, the board passing `checkBoard`; a retry returns its entry; an earlier receipt for the seat returns as `earlier`, another seat's still boards; each rule's refusal, writing nothing; the last second of `s_D` boards and the next is refused, and so is a receipt a later-labelled entry would raise past it; an unknown election, one with no transcript, a time before the clock's epoch; `appendEntry`'s receipt key (one per ballot hash, panel and seat, a ballot of that hash before it, malformed keys refused, `lastSegment`); both tables' Drizzle shape, grants, append-only triggers for the app and the owner, and their row checks. `tests/append.test.ts`: the payload check takes share receipts on a board whose version allows them.

Known-weak:

- **Nothing calls it yet**: the API's route and the client's submission are part 3c-1b-2b-2b-2d-1b, and the trustee node's own board-path sending after them.
- **Rules 2 and 5 read the board path only**: a ballot direct-submitted to the contract, boarded as a contract event, has no hash row, so its receipts are refused here (they still have the contract path), and a passing receipt the contract recorded doesn't stop a board-path copy, which adds at most one entry per seat of a ballot (T-52). Contract events of the board aren't boarded at all yet ([[P4-2]]).
- **Definition version 5 only**: the other versions' receipts, and version 6's author seats (panel 2), are refused until their ballots are cast by a client.
- **The table takes any `0x000c` payload**: only `submitReceipt` writes receipts, but a second writer calling `appendEntry` without judging one could board it, or key a failing one that then stands in for its seat under rule 5; a deferred constraint tying each `0x000c` entry to a judged key would take the rules into the database (found by the in-session review).
- **Complaints aren't boarded**: the board's payload check still refuses `0x000e`, `0x000f` and the later types until their writers exist.

## Part 3c-1b-2b-2b-2d-1b-1: the API's route for share receipts (#549)

The route part 3c-1b-2b-2b-2d-1a's judge and store waited on: `receipts.submit` (`POST /receipts`), the operator's board path for share receipts ([[delivery]], Boarding), which the client (next part) and a seat's node (after it) call.

- **The contract** (`packages/api-contract`): `{ electionId, record }`, the receipt record as hex of at most `MAX_SHARE_RECEIPT` (256) bytes, every version being a fixed size under 200; the answer is `{ entry, link, earlier }` as for a ballot, with `RECEIPT_REJECTED` (core's code), `ELECTION_NOT_OPEN` (after `s_D` too), `ELECTION_NOT_FOUND`, `RATE_LIMITED` and `RECEIPTS_UNAVAILABLE`. JSON with hex like every other route, not the octet-stream body the plan named: the contract's schemas, strict objects and duplicate-key refusal then cover it, and the CORS preflight is the one every route has. The field is `record`, since the contract's own test bans any key containing `ip`.
- **Judged in the worker, not the API** (T-52): a new board-side queue, `{receipt-submit}` (`{electionId, record}`), run beside `{ballot-submit}` with the same admissions, up to 8 at once, and refused as `stale-job` after `BALLOT_MAX_AGE_MS` as ballots are. The API's `ReceiptQueue` shares `BallotQueue`'s producer (random job ID, outcome heard before queuing, 20 s, 4,096 waiting), now one private `SubmitQueue` behind both. The outcome is the entry's position and `earlier`, or the refusal's code, never the receipt (T-10).
- **The answer is the board's** (T-23): a receipt boarded is answered only if the entry at the worker's position carries the bytes sent (`readBoardedEntry`); an `earlier` one is answered with whatever the board holds at that position (core's new `readEntryAt`), which the sender checks against its ballot itself (Client rules 3). Either missing is a 500, and so is an `earlier` entry whose record header (type and version) isn't the one sent, so a worker's wrong position never hands a sender a ballot as its receipt.
- **A retry is found after `s_D`** (core's `submitReceipt`, found by the in-session review): the byte-identical replay lookup now runs before rule 3, writing nothing, so a sender whose answer was lost just before `s_D` learns on retrying after it that its receipt is boarded, rather than taking the seat for undelivered and being offered a posting (Client rule 4; T-15). A late receipt that fails rule 1 is now `rejected` rather than `not-open`.

Tested: `apps/api/tests/receipts.test.ts`, through a worker on live Redis and Postgres, over `receipt-poll.ts`'s election: every seat's receipt of two ballots boarded and answered with the entry and link the board holds, the request log naming only the route; the same bytes again, later, the same answer; an earlier receipt keyed for a seat answered as `earlier` with its own entry, nothing written; a non-record, another definition, an unboarded ballot hash and another seat's signature refused with their codes, nothing written; the last second of `s_D` boarded, the next refused and a retry of the boarded bytes then answered with their entry (and in `packages/core/tests/share-receipts.test.ts`, other bytes still refused); an unknown election never queued; no queue, `ELECTION_NOT_OPEN`; no worker, `RECEIPTS_UNAVAILABLE`; a worker's position the board doesn't back, either way, or an `earlier` entry of another record type, a 500 (checked by removing the header check); each receipt version within the bound, the worker's copy equal to the contract's. `apps/worker/tests/receipts.test.ts`: outcomes by position and code, and no receipt or election left in any Redis key or log line; an earlier receipt by position alone; no worker, unavailable and the job removed; a stale job refused unjudged; a dropped schema failing by kind; the outcome schema strict. `packages/api-contract`: the route listed, strict, with no banned field.

Known-weak:

- **Nothing calls it yet**: the client's submission is next, and the trustee node's board-path sending after it.
- **No rate limit** beyond the server's slots and the queue's bound: a flood of receipts can keep 8 worker connections busy and fill the queue's 4,096, after which honest senders hear unavailable and retry or use the contract path (T-52, T-25). Per-address limits are the proxy's (P2-11).
- **The operator still sees the sender's address** beside the receipt, as at the ballot route (T-11); a receipt names its ballot hash, so this ties the address to that ballot for anyone holding the operator's logs, which keep no address (`server.ts`), but the proxy's may.

## Part 3c-1b-2b-2b-2d-1b-2: the client's submission of each kept receipt (#569)

Client rule 3's first half from the client: once its ballot is boarded, every receipt a cast keeps goes through the operator's board path (`receipts.submit`, part 3c-1b-2b-2b-2d-1b-1), and the operator's answer is checked as a ballot's is before it is kept ([[delivery]], Client rule 3; [[receipts]], Checks at cast; T-25, T-38).

- **When** (`src/open.tsx`, `boardReceipts`): after the ballot's checked answer is kept, and after a `repeat` (the copy on the board has the same ballot hash), the cast's receipts with no entry are read from the store and submitted one at a time, once "Your ballot is on the board" is shown, so an operator that stalls the receipt route can't hold the voter on the sending screen with their ballot boarded (found by the in-session review). What the voter is shown doesn't change: every seat receipted the ballot before it was sent, and the nodes board their own receipts too. A worker that stops, or a store this device can't read or write, ends the submissions; a cast gone from the store skips only that seat.

## Part 3c-1b-2b-2b-2d-2a: an unreceipted seat's `ct_i` and `m_i` erased at the posting cutoff (#571)

The half of Client rule 4's erasure that doesn't wait on the offer ([[delivery]], Client rule 4; T-18): a seat no route receipted may be posted only until `c_D = t_D − F`, and after it the `ct_i` and `m_i` kept for it only wait to be read off a seized device by anyone who later breaks the share's classical encryption.

- **The cutoff** (`src/lapse.ts`): `postingCutoff` is `closes_at + l1_inclusion_bound + DELIVERY_WINDOW − F` (crypto's `deliveryDeadlines`), with `F` the release's (`Deployment.forcedInclusion`, 46,800 s on staging, the trustee node's `RELEASE_WINDOWS`), never a client's own setting. `CheckedElection` now carries the definition's `l1InclusionBound`. `postingLapsed` holds only once both the L2's finalized head's timestamp (`loadChainTime`, `src/load.ts`, after the chain ID check) and the device's clock are past the cutoff in whole seconds; at the cutoff itself a posting may still be sent. Both, so neither an RPC reporting a head from the future nor a clock set ahead alone erases what a posting in time would need (T-25); either one lagging only keeps the shares longer.
- **The erasure** (`withSharesErased`, `eraseShares`, `src/casts.ts`): every seat still holding its `m_i`, in every cast of the election and tier, is left with nothing but its seat, in one transaction with the read; receipted seats keep their `ct_i`, receipt and board entry for Client rule 3. The record is version 5, an erased share stored as `{ seat, ciphertext: null, m: null, receipt: null, boarded: null }` and read back only in exactly that form; version 4 is unreadable (no build wrote it). The worker's shares can never be taken as erased (`withCast` throws), and a receipt never takes an erased seat's place.
- **When** (`src/open.tsx`, `resume`): on opening a poll in a build that delivers, a tier whose casts keep an `m_i` with the cutoff past by the device's clock reads the chain's time (once per visit, and never otherwise), and if both are past, erases that tier's shares and reads its casts again. A chain read that fails or answers wrongly erases nothing. A newest cast holding an erased seat is never offered for resuming (`unsentCast`): its seat can be neither delivered nor posted in time.

Tested: `tests/lapse.test.ts`: the cutoff by the spec's formula (fast-check) and a worked value; a negative or non-bigint `F` and a negative bound refused; lapsed exactly when both clocks are strictly past (fast-check), the cutoff's own second not past, and a clock that isn't finite refused. `tests/casts.test.ts`: version-5 records with erased shares round-trip (fast-check over the stored casts); version 4, an `m` without its ciphertext, an erased share with a receipt or board entry, for another seat or of undefineds, unreadable; erasure takes exactly the seats holding `m` in every cast and leaves everything else, read back as written (fast-check); none for casts keeping no `m`; stored with nothing but the seat; a newest cast holding an erased seat isn't resumed; a receipt for an erased seat changes nothing; worker shares shaped as erased throw; a recast after erasure. `tests/load.test.ts`: the finalized head's timestamp, asked for with the chain ID and nothing else; another chain, answers that aren't a block and a failed network refused. `tests/worker.e2e.ts`, in Chromium: erasure of two casts of one tier, kept across a reload, another tier untouched, `none` with nothing to erase and `unreadable` for a record of another version. `src/open.stories.tsx` (interaction and axe): past the cutoff by both clocks the shares are erased and nothing is resumed; before it by the device's clock the chain isn't read; past it on the device but not on the chain, or with the chain unreadable, nothing is erased; casts keeping no `m` read no chain.

Known-weak:

- **Only on opening the poll**: a voter who never opens it again keeps its unreceipted shares on the device. Erasing from every poll's records at the client's start needs each record to carry its cutoff, since the records hold no definition.
- **One endpoint for the chain's time** (T-43): the RPC the client already reads. It can only delay erasure (the device's clock must agree before anything is erased), never hasten it alone.
- **The RPC and a spoofed clock together can hasten it** (found by the in-session review; T-43, T-25): the operator's RPC with the device's time spoofed (NTP, say) can erase an unsent cast's unreceipted shares during the poll, losing its resume; the voter can still answer again. Judging chain time from a second endpoint or from L1 is a later part.
- **`F` is written twice** (found by the in-session review): in the client's deployment and the trustee node's `RELEASE_WINDOWS`, with nothing binding them. A client `F` larger than the release's would erase before the true `c_D`; the release record ([[P0-3]]) should pin it once for both.
- **A receipt for an erased seat is `missing`** (found by the in-session review): the cast stops rather than counting the seat receipted. Nodes refuse intake from `c_I`, before `c_D`, so this needs a node that answers late.
- **The browser may keep the replaced bytes on disk** until it compacts the database, as with a receipt (T-18).
- **No offer yet**: erasing once the voter declines a posting comes with the offer.
- **Nothing calls it in a build yet**: `delivers` stays `false`.

## Part 3c-1b-2b-2b-2d-2b-1: the posting offer and the voter's decline (#578)

Client rule 4's choice for a seat no route receipts ([[delivery]]; T-15, T-18, T-25), asked as soon as delivery fails, so a voter who leaves the ballot can answer again while the poll is open.

- **The check before the offer** (`postable`, `src/open.tsx`): each unreceipted seat's `ct_i` and `m_i` are read back from the cast record and must pass the worker's `posting` check (part 3c-1b-2b-2b-1) against the ballot the worker cast on this page, the only ballot a posting may name (`castPostingSeatV3`). A share that fails is an unreadable record (`casts-unreadable`); a worker without the poll is `cast-failed`; a seat erased or with another ciphertext is `cast-faulty`; a seat another tab receipted since is never posted, and a cast every seat receipted is sent. Every `m` copy the page handed on is zeroed once judged. A cast found recorded on opening the poll (`resumed`) names a ballot read from storage alone, so it gets no offer: the voter sends it again or answers anew, as before.
- **The offer** (`src/posting-offer.tsx`, `PostingOffer`): try the trustees again (primary), leave this ballot (secondary), or, only in a build with a contract path (`ElectionSource.post`), post the missing parts publicly. The posting's cost is said beside its button, never as the default: those parts lose their long-term protection, anyone who later breaks today's encryption reads them, and enough posted parts open the whole ballot.
- **Posting** (`post`): the shares are checked again (the record may have changed since the offer), handed to `post`, and only once it answers `recorded` is the ballot sent, so a ballot never reaches the board with a seat neither receipted nor posted. A posting refused or unanswered returns to the offer with a note, and nothing is sent. No build has `post` yet.
- **The decline** (`decline`; `withPostingDeclined`, `declinePosting`, `src/casts.ts`): the declined cast's seats still holding `m_i` lose their `ct_i` and `m_i`, in it and in every cast holding the same `ct_i` (a recast of the same seal), receipted seats and other seals' casts untouched; a cast holding an erased seat is never resumed. The worker then zeroes and drops every `m_i` its seals keep for that ballot (`declineSealV3` in `packages/crypto`, the worker's `decline` request), even if the store refused. The voter is told the ballot won't count and to answer again.

Tested: `packages/membership-prover/tests/seal.test.ts`: `declineSealV3` erases every kept `m_i` only for a cast of its seal, a recast hands none, another seal's ballot erases nothing, an uncast seal throws. `tests/cast.test.ts`: the worker's `decline` erases its seal's `m_i` for the cast, nothing for bytes that aren't a record or with no poll held. `tests/casts.test.ts`: the decline erases exactly the declined cast's `m`-holding seats in every cast of the seal, read back as written (fast-check); another seal's cast and receipted seats untouched, the declined cast never resumed; `missing` for a ballot no cast has. `tests/worker-protocol.test.ts`: the `decline` request and response. `src/open.stories.tsx` (interaction and axe): the offer after a failed delivery, with the stored share checked against the cast ballot and its `m` zeroed; no posting in a build without `post`; a posting checked again, posted, then sent; refused and unanswered postings back to the offer; the decline erasing the record and the worker's copies; a decline the store refuses; a refused or unknown check; an erased share; a seat receipted since. `src/posting-offer.stories.tsx`: the offer in both themes, with and without posting, and the left ballot.

Known-weak:

- **No contract path yet**: `post` is absent in every build, so the offer is to try again or leave; `delivers` stays `false`.
- **No offer for a resumed cast**: its ballot is read from storage alone, which no posting may name. Comparing it with the board's or the contract's copy would let it be offered.
- **The record doesn't say a seat was posted**: a posted seat keeps its `m_i` until `c_D`, and a resumed cast would deliver it again.
- **The browser may keep the replaced bytes on disk** until it compacts the database, and the worker's dropped `m_i` arrays are zeroed but the JS heap may hold copies (T-18).
- **Two tabs can race a posting against a receipt** (found by the in-session review): a tab that passed the check and posts while another tab keeps a receipt for the same seat would post a receipted seat (Client rule 2). No build posts yet; the part that adds `post` holds one lock per election (`navigator.locks`) from the check through the posting, taken by delivery too.
- **A share that fails the check offers no decline** (found by the in-session review): the record is unreadable and the voter can't erase it at once; it is erased at the posting cutoff.
- **The worker's posting check takes any cast of the poll** (found by the in-session review): only the page's `resumed` flag keeps a stored ballot from being offered; binding the check to a seal the worker cast would be a second guard.
- **The posting threshold isn't named**: the client doesn't hold the panel's `k`, so the offer says "enough of your ballot's parts" rather than the number.

## Part 3c-1b-2b-2b-2d-2b-2a: who sends a posting and pays its gas (#586)

[[0042-posting-relay]], `Accepted (agent) — owner may veto`: the operator's posting relay sends `submitPosting` from its own posting key, an account used for nothing else that pays its own gas (option A), so voters never transact to post; the voter's own fresh wallet (option B) is the fallback once the relay refuses. A trustee node relaying (option C) waits for independent trustees and a way to take requests without an inbound port. The ADR fixes the route (unauthenticated, no credentials, nothing logged but the election and an outcome), the relay's answer as a hint only (`recorded` is the client's own reading of the board's `SharePosted` events at the L2's finalized head), the checks before the relay pays (strict decoding, a registered election before `c_D`, the public check, a simulated call), its caps (two ballot hashes per (`tier`, `ν`), a per-election gas budget, never paying twice for the same bytes) and the forced path through L1 when the sequencer doesn't include it. Threat files: T-13, T-15, T-25, T-52.

Known-weak:

- **Nothing is built yet**: `post` is still absent in every build.
- **The relay sees `m_i` before the chain does** (T-15), and the voter's network address beside the ballot, as the ballot route does (T-11).

## Part 3c-1b-2b-2b-2d-2b-2b-1: the posting relay in the spec (#590)

[[posting-relay]], under [[0042-posting-relay]]: `POST /postings` on the ballot path with the posting and its ballot record as hex; the route's checks (strict decoding with the posting's ballot hash recomputed, the election registered and before `c_D − POSTING_SEND_MARGIN` by the API's index, the public check against the registered key set) before a pair takes one of `POSTING_QUEUE_MAX` places in a Redis hash with no arrival time and no job per request; the posting worker's re-decoding, repeat check, time check against the latest L2 block, simulation (gas limit a quarter above what it used and at least the portal's minimum for the calldata, at most 10,000,000), caps (two ballot hashes per election and (`tier`, `ν`), the election budget) and sending, the in-flight entry kept until the posting's event is final, and the forced path through an L1 deposit after ten minutes, only by `c_F = min(c_I, c_P − F − 30 min)` and outside every registered election's Capacity intervals; and what the client relies on: `recorded` from the board's events at the finalized head, and its own deadline `c_P = c_D − 1 h`, by which it falls back unless the posting is at the finalized head (a sighting at the latest head only delays it), and before which it falls back on a refusal, half an hour of busy answers, a `sent` with neither the event nor a deposit with enough gas, or a deposit whose `F` passed without the event. Every relayed call fits a deposit's 120,000-byte cap, and its gas limit is at least the portal's minimum for its data. Threat files: T-13, T-18, T-25, T-52, T-54.

Two refinements of the ADR, recorded in its Consequences: the relay deposits only by `c_F` and outside every election's Capacity intervals, which [[delivery]] (Capacity) sizes for the seats' forced records alone; and the "about 108 KB" request bound counted only version-3 ballots (with version 4's author half the largest pair is about 87.5 KB of calldata).

Known-weak:

- **No forced path after `c_F` or inside any election's Capacity interval**: such a posting rides the sequencer alone; the voter's own wallet (part 2d) is the answer, and its deposit isn't counted by Capacity.
- **A budget can be spent by a few** members making up ballots, within the caps, sending later voters to their own wallets (T-13).
- **The relay pays for chosen bytes in `sealed`** (T-17), within the caps, and for a front-run repeat, once per posting.
- **`POSTING_GAS_LIMIT_MAX` isn't measured** against the largest pair yet; part 2b-2's contract test measures it.
- **Nothing is built yet**: `post` is still absent in every build.
