# P2-4: `apps/worker`

- State: in progress (part 1, worker scaffold, hashtagged queues and the T-10 no-join test, merged in #64; part 2a, batched membership proofs in ballot admission (`finishBallotSteps` in `packages/crypto`, `admitAll` in `packages/verifier`), merged in #N; part 2b, the worker's admission queue, next)

## Scope

`apps/worker` (BullMQ, hashtagged queues): proof batch verification, IPFS pinning, tally coordination.

Must include the T-10 no-join test for this app: no queue job payload, job ID or worker log line carries both an account or session identifier and a ballot, nullifier or poll-participation value.

## Plan

1. **Worker scaffold** (this part): `apps/worker` on BullMQ with ioredis, one hash tag per queue, the T-10 no-join tests for job data, Redis and the worker's log, and a first job: the scheduled board audit (`auditBoard` and `listBoards` in core; T-23, T-66).
2. Proof batch verification, with ballot admission (P2-3 part 2) and the membership verifier (P1-17b), in two parts:
   - **2a, batched admission** (this part): each ballot's admission checks stopped at its membership proof, many ballots' proofs verified together, every verdict the one checking the ballot alone gives ([[ballot-validity]], Batched admission).
   - **2b, the worker's admission queue:** the API hands each submission to a hashtagged BullMQ queue and answers once its job completes; the worker takes the jobs waiting together, admits them with `admitAll` and boards the admitted ones in order, so the API process no longer verifies proofs (T-52). The job carries the election and the ballot only (T-10).
3. IPFS pinning, with the archive (P4-3); tally coordination, with the tally (P1-15).

## Part 1

- Built: `apps/worker` (`src/queues.ts`, `src/jobs.ts`, `src/worker.ts`, `src/main.ts`); `auditBoard` and `listBoards` in `packages/core/src/audit.ts`.
- Dependencies: `bullmq` 6.3.11 and `ioredis` 5.11.1 (the pair BullMQ's own tests pin); `msgpackr-extract` (an optional prebuilt native binary msgpackr loads whenever present) kept out by `ignoredOptionalDependencies`. The catalog change needs the owner's review (CODEOWNERS), so this PR doesn't auto-merge on checks alone.
- Tested: core `tests/audit.test.ts` (a property test that every board `appendEntry` builds passes; a wrong entry hash, a wrong link and a board `checkBoard` rejects each fail at the right entry; `listBoards`); worker `tests/no-join.test.ts` (sides, deny-lists, strict data with a property test, hash-tag names) and `tests/worker.test.ts` against live Redis and Postgres (the schedule and its first run, good and bad boards, an account field on a board queue and a handler error quoting data neither logged nor left in any Redis key, the events stream included; every key under its hash tag; msgpackr's native accelerator absent).
- Independent review (`crypto-review` checklist): two blocking findings, both fixed. Failure messages stayed in BullMQ's events stream, which `removeOnFail` doesn't clear (the worker now throws only fixed-kind `JobError`s, with a test that fails without it); and denying `msgpackr-extract`'s install script didn't stop its prebuilt binary loading (now not installed, with a test). Non-blocking, fixed: one board's unexpected error no longer stops the others (`audit-error` finding), an `error` listener on the scheduler's queue, cleanup when the schedule can't be set, the shutdown's rejection handled, the `prev_link` check's reach commented, and the threat files no longer claim the audit catches rollbacks. A second pass found nothing blocking; applied: a job named other than its queue's key is refused (BullMQ's events stream keeps names and IDs, now stated), `close()` closes the queue even when a worker's close fails, the Redis-dump test fails on an unchecked key type, and an unused dependency is dropped.
- Known-weak: field names are matched by deny-list, so a renamed field passes the no-join test; an audit reads a whole board into memory and runs every board in one job, so one huge board can hold the job past BullMQ's lock and stall it (one job per board, or yielding, when boards grow); the audit misses a consistent rollback, truncation or rewrite (P4-1's anchors catch those); producers' options are a convention until the first producer's helper enforces them; the audit only detects (a finding is a log line; alerting comes with deploys, P2-11); Dragonfly itself isn't in CI (Redis 7 is), so the hash-tag rule is checked by key shape, not by Dragonfly's lock mode.

## Part 2a

- Built: `packages/crypto` `stepBallot`, `stepBallotV2`, `stepBallotV3` and `stepBallotV4` (each version's admission checks up to the membership proof, as opaque steps only this module makes) with `finishBallotStep` and `finishBallotSteps` (many steps' proofs by `verifyDecodedMembershipProofs`, then each passing ballot's validity proofs); `checkBallot` to `checkBallotV4` and trustee intake are now the step finished alone, unchanged in result. `packages/verifier` `steppedJudgeFor` (what `judgeFor` now wraps) and `electionAdmission`'s `admitAll`, which `admit` now calls with one payload. [[ballot-validity]] (Batched admission), T-52's history.
- Tested: in each ballot version's vector suite (ballot.json, ballot-v2.json, ballot-v3-records.json, ballot-v4-records.json, from independent implementations with snarkjs's verdicts), every vector batched together, across elections, gets the vector's result and exactly `checkBallot`'s; a property over any multiset of version-1 vectors in any order, past a batch of 64 (runs capped at 3, each up to 80 Groth16 proofs); forged steps, a copied step and a non-array refused. In `packages/verifier`, `admitAll` over each verifier-ballots.json case gives the verifier report's 5.1 to 5.4 verdicts, and over any multiset of a copy's payloads (non-ballots, an empty and a truncated payload among them) exactly `admit`'s; the whole crypto and verifier suites pass unchanged.
- Known-weak: nothing calls `admitAll` yet, so the API still verifies each submission's proofs alone, on its own process (part 2b). The verifier's own board walk still checks proofs one at a time; batching it is the same change to `ballotChecks`, not planned yet. Batching doesn't bound flooding: a junk ballot that reaches the membership proof costs at most its own batch of 64 the gain (T-52).
