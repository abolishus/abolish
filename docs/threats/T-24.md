# T-24: Equivocation (split view)

- Area: Integrity and verifiability (G-7, G-8, G-9)
- Adversary: A-2, A-1
- Status: **Planned.** Residual: before its segment's anchoring deadline, a voter checking via our API alone can be shown a fork. Receipts must be re-checked against L1 after the deadline, and the client must refuse an envelope labelled with a segment other than the current period ([[board]]). Whoever holds the election's anchoring key can fail a running election, publicly and attributably, by anchoring checkpoints for different segments that no single board matches (equivocating within one segment is refused by the L1 board anchor, [[contracts]]) (`checkpoint-inconsistent`, attributable from L1 and any copy that matches a checkpoint). Not mitigated yet: a checkpoint that extends every receipt with entries never published, or forks only after the last receipt, leaves the election unverifiable for good, and no voter's receipt attributes it ([[board]], Residuals; P4-1, P4-3).

## Threat

The server shows different boards to different viewers, for example omitting one voter's ballot only from the copy that voter sees.

## Mitigation

Receipts are checked against L1-anchored checkpoints, which everyone sees identically: each anchor names its election and segment, the verifier checks every checkpoint anchored for the election, and two different ones for a segment fail as equivocation; an inclusion proof shows the entry is in the anchored tree, and a consistency proof shows the anchored tree extends the one the voter was shown when casting (RFC 9162; [[board]]; P1-13, P1-16, P4-1); community nodes (P4-5) and the verifier read from chain + IPFS, not our API.

Index: [[THREAT_MODEL]].

## History

- 2026-10-10 (P1-16): board tree, inclusion and consistency proofs and checkpoints specified and built in `packages/crypto`; receipts that carry them are P1-13's.
- 2026-10-11 (P1-16 follow-up, #37): checkpoints no board can match fail the election as `checkpoint-inconsistent` instead of reading as a bad copy; client rule 2 checks every timely checkpoint against the receipt, earlier ones included.
- 2026-10-11 (P1-13, receipts): the receipt carries the operator's signature on the size, root and head of the board it showed the voter, with the voter's entry last ([[receipts]]); checking it against the anchored checkpoints is [[P1-13b]].
- 2026-10-12 (P4-1 part 1): the L1 board anchor stores one checkpoint per election and segment, refusing a second even if equal, so L1 never holds an equivocation, and a verifier reads every anchor of an election from per-segment storage slots with storage proofs, from the election's lowest anchored segment to the seal, never from a log list an RPC node could shorten ([[contracts]], Board anchor). Not deployed yet.
- 2026-10-12 (P1-19 part 3a): `packages/verifier` reads an election's anchors from the board anchor's storage, proven against one L1 header's state root (strict RLP, Merkle–Patricia proofs), from `max(lowest, f)` to the last ended period, and matches each word against the copy or a checkpoint whose hash is the word; a word nothing matches is unverifiable, never failed ([[verifier]], Anchors from L1). The header itself is still a local input, so no run is verified yet.
- 2026-10-12 (P1-13b part 2a): client rule 2 is replaced by [[receipts]], Later checks: the client rebuilds the board tree from every segment's entry-hash list and compares every counted checkpoint's root, and an anchored board its receipt's root isn't a prefix of is a `forked` verdict a third party can check with a consistency proof.
- 2026-10-13 (P4-3 part 2a, [[0029-board-data-availability]]): decided, not built. Checkpoint version 2 names each segment's CIDs on L1, and before any result each trustee panel's threshold of seats must attest that it holds the ballot extent (by `t_A ≤ c_I`) and the counted extent (before any summed share), or the election fails `unavailable`, listing who attested, complained or did nothing. A withheld or forked extent through the counted set then fails the election instead of leaving it unverifiable, unless a panel threshold colludes; the tail after it (openings, tally, destruction statements) stays unverifiable, and under the transitional panel the attestation is the operator's own.
