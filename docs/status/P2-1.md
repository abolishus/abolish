# P2-1: `packages/core` and Drizzle schema

- State: in progress
- Branch: `claude/p2-1`
- Phase: Phase 2: Open polls end to end at Tier 0

## Scope

`packages/core` + Drizzle schema: append-only board tables (grants + triggers), the account/ballot no-join test, and migrations roles.

## Plan

Built in parts, each its own PR on this branch's name:

1. **Package, roles, migrations and the board table** (this part): `packages/core`, the two database roles, the migration runner, `board_entries` with its grants and triggers, and the no-join test.
2. **Appending through `@abolishus/crypto`**: `appendEntry` computes the entry hash and link with the crypto package and inserts the row. It waits for #40 (`ci:` building `@abolishus/crypto` before checks and tests), because core can't import crypto in CI until then.
3. **Rebuild from chain + IPFS**, when there are chain-index tables (P3-5) and IPFS mirroring (P4-3).

## Built (part 1)

- `packages/core`, private, AGPL-3.0-only, source-only. Dependencies: `drizzle-orm` 0.45.3 (no dependencies of its own) and `postgres` 3.4.9 (postgres.js, no dependencies).
- `src/db/roles.sql`: `abolish_migrator` and `abolish_app`, `NOLOGIN`, idempotent and safe to run concurrently.
- `src/db/migrate.ts`: forward-only runner with a sha256 ledger. It refuses changed or missing applied migrations and takes an advisory lock per schema.
- `src/db/migrations/0000_board.sql`: `board_entries` with CHECKs on every field's length and range, append-only triggers (for every role, owner included), an append-order trigger (contiguous index, non-decreasing segment, `prev_link` = previous `link`, entry 0 from zeros), and grants (`abolish_app`: SELECT, INSERT).
- `src/db/schema/`: the Drizzle table and `TABLE_CLASSES`.
- Decision: hand-written SQL migrations, no `drizzle-kit` (see the package README). A test ties the Drizzle schema to the migrated table.
- Threats: T-23, T-10.

## Tested

- As `abolish_app`: appending and reading a chain through Drizzle; UPDATE, DELETE and TRUNCATE fail; it can't disable triggers or drop the table.
- As `abolish_migrator` (the owner): UPDATE, DELETE and TRUNCATE fail; it can't set `session_replication_role`.
- Every append rule and field CHECK rejects its mutation, with the expected error code. A fast-check property interleaves well-formed appends with mutated ones and checks the table accepts exactly the well-formed ones.
- No-join: every table is classified, no foreign key touches a board table, and no board column has an account-like name.
- Migrations: idempotent; a changed or missing applied migration is refused; bad file names and schema names are rejected.

## Known-weak

- **The schema owner can disable its own triggers** (`ALTER TABLE … DISABLE TRIGGER`), so a malicious or mistaken migration could rewrite board rows. Postgres isn't authoritative: the rebuild from chain + IPFS and the anchored checkpoints catch it (T-23).
- **The table doesn't hash.** It checks that `prev_link` equals the previous `link`, not that either is the right hash; part 2's `appendEntry` computes them with `@abolishus/crypto`, and the verifier recomputes everything.
- **The no-join column check matches names**, so a linking column with an innocent name would pass. Logs, caches and queues aren't covered yet (P2-3, P2-4; T-10).
- **Local sessions:** the session hook's `abolish` user can't create roles, so these tests need it to be granted `SUPERUSER` (or `CREATEROLE`) locally; CI's service user is a superuser. Changing the hook is a `.claude/` change for the owner.
