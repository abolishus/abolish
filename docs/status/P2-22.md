## Scope

The write path [[P2-9]] part 3 waits on. Today polls exist only in the reference election's runner (`apps/reference-election/src/l2.ts`, on a local L2) and in `packages/sdk`'s simulation. Nothing lets a person on the website turn a question into an election the registry has admitted and the API lists. This item builds that path for everyday polls, end to end: the account's draft, the on-chain creation, the electorate roots, the key ceremony with the launch panel, the registration, the board's first entry and the poll opening for answers, with the website's creation flow on top (`everyday-create-flow.tsx` and the other `everyday-create-*` mockups in `apps/web/src/mockups/`).

The contract side is specified ([[contracts]], Election registry; [[election-definition]]; [[ceremony]]; [[trustee-identity]]). What isn't decided is the operations around it, and this item decides them first (part 1) because they set what every later part builds:

- **Who is the creator on L2, and who pays?** `createElection()` makes the caller the only account that can register the definition, and creation is permissionless for gas ([[contracts]], Election identifier; T-25). An author with a passkey account can't sign L2 transactions. The proposal: the operator's service account creates and registers on behalf of authors, pays the gas, and the account-side record says whose poll it is; the on-chain creator is then the operator, public, "the account that runs the election, not a voter". Costs: the operator can refuse to create a poll (T-25, answered by the direct-creation path anyone can use), and the key that signs is a hot key whose custody is a new threat to write down.
- **Who runs the ceremony coordinator?** `apps/trustee-node` has the seat's side and `LocalCoordinator`; no coordinator service exists ([[P2-13]], Transport). During launch every seat of the default panel is ours ([[0027-trustee-panels-and-live-results]]; the transitional panel is everyday polls only), so the coordinator and the seats run on our machines, per the transitional-operations runbook of [[P2-16]] part 6.
- **Which definition version does the deployed registry admit?** Rule 9 serves exactly the profiles its bytecode lists; version 6's ballot has no served version until [[P2-16]] part 5 ([[contracts]], Registration rule 9). The first end-to-end poll uses the newest version the registry serves (a fixed electorate, one or more questions, version 5 with ballot version 3 at the time of writing), and moves up as the P2-16 and [[P2-17]] parts land.
- **The electorate must already exist.** Every tier's `root_l2_block` is in the past at registration ([[contracts]], rule 7): a voter has to be in a Tier 0 group before the poll is created. That is the fixed-electorate behaviour; rolling electorates ([[0028-rolling-electorates]], [[P2-17]]) remove it later, and this item's creation flow takes the roll as a flag when those parts have merged.
- **Abuse.** Each creation costs the operator gas. Account-gated creation, a per-account quota, Turnstile on the submit and a global ceiling on creations per day; none keeps a voter's identity, since creators are authors, not voters (T-10's no-join rule still classes every new table).

## Rules

- **Each step is idempotent and resumable.** A poll is a state machine in Postgres (`drafted`, `created` (the `ElectionCreated` event is in finalized L2 history, [[contracts]]: a creator MUST wait for finality before putting the identifier in a stub), `rooted`, `ceremony`, `registered`, `open`, `failed`), advanced by worker jobs that can crash and rerun at any step without a second creation, a second registration or a second ceremony run. The website shows these in plain words ("Setting up your poll"), never a hash or a code.
- **Nothing about a voter is stored.** A poll's creator record lives on the account side; the T-10 no-join tests, on every new table, column, queue and log line, must keep it unjoinable to any ballot, nullifier, receipt or participation value.
- **Everything the website shows is checked against the definition.** The page shows the question the creator wrote and the hash the registry holds; before opening, the worker decodes what the registry holds and compares it with the draft (T-34).
- **No hard-coded strings, CSP-safe, server-rendered, analytics fixed** — the same rules as [[P2-19]]; a new route gets a template in `src/analytics.ts` and no draft's text or poll ID is kept in analytics (T-67).
- **Protocol code is gated.** Building the definition, the stub and the ceremony inputs, and anything in `packages/crypto`, `packages/core`'s admission and the contracts' bindings, is inside the `crypto-review` gate; the in-session subagent review applies to `packages/core`, `apps/api` and `apps/worker` changes that touch it (AGENTS.md, Before opening any PR, step 5).

## Part 2: drafts and submission

- `account_polls` (migration `0012`, numbered after `0011_display_texts`, which merged first, `packages/core/src/db/schema/polls.ts`): the creator record of rule 15 and the author's draft, one row per poll from its first draft on, in the no-join test's account class. Its states are rule 12's, checked by the table; `submitted_at` is kept once set, since the daily limit counts by it. Deleting an account deletes its rows (rule 16).
- `packages/core/src/poll-drafts.ts`: a draft is one translation of display text version 2 (language, title, description, and per question its text, description, options and selection range), the tiers that can answer, and `closes_at`. `pollDraftProblem` checks it with the definition's own rules from `packages/crypto`: definition version 5's question rules (`definitionQuestionsRule`, now exported, the same function `electionDefinitionV5Rule` calls) and display text version 2's encoding and shape rules (`displayTextV2ShapeRule`, now exported for text no definition commits to yet), plus a lone-surrogate check (a lone half would be registered as U+FFFD, T-34), a 32 KiB cap on the encoded text and the tiers. At submission it also checks `closes_at`: at least 30 minutes of setup (rule 10) and an hour open, and at most 366 days ahead. Each refusal names its rule and, for `option-count` and `selections`, the question.
- Create, read, list (newest 100), edit and delete a draft, and submit it. Only `drafted` can be edited, deleted or submitted. Submission checks, cheapest first, the poll, the draft at that time and the account's limits, then the Turnstile token for `poll-create`, then all of them again under the account's advisory lock before moving the poll to `submitted`, so an edit or a second submission during the token's round trip can't slip past a check. Limits (rule 18, starting values): 20 unsubmitted drafts, 3 polls between `submitted` and `open`, 10 submissions in any 24 hours.
- `apps/web/src/node/drafts.ts`, served by the front under `/drafts` (`GET /drafts`, `POST /drafts/{create,read,update,delete,submit}`): the session names the account; every POST needs our `Origin` and JSON; inputs are strict Zod objects at the codec's field bounds; errors are fixed codes (`DRAFT_REFUSED` with the rule, `NOT_EDITABLE`, `TOO_MANY_*`, `TURNSTILE_*`, `SIGNED_OUT`). The front forwards the account cookie to `/auth` and `/drafts` only and logs `drafts` as a route class.

Two departures from the plan above, neither a one-way door:

- **The routes are on `apps/web`, not in `packages/api-contract` and `apps/api`.** The API refuses every request carrying an account credential (ADR 0017, T-10), so an account's routes belong beside the account handler on `apps/web`'s origin, where the session cookie already is. The worker, not the API, reads submitted polls.
- **The per-account limits are in Postgres, not Dragonfly** (rule 18 says Dragonfly). They count rows of `account_polls` under a per-account lock in the same transaction as the state change, which is exact and needs no second store on `apps/web`. The global daily ceiling stays the worker's, checked before the creation transaction (part 3).

Tested: `packages/core/tests/poll-drafts.test.ts` checks every rule in order with the failing question (U+0000, which jsonb can't hold, is refused under `text`), the 32 KiB cap at its edge, the submission window at both ends, and a fast-check property that any draft it accepts builds display text and questions that `encodeDisplayTextV2`, `electionDefinitionV5Rule` and `displayTextV2Rule` accept; the Drizzle table against the migration; that only the owning account can read, edit, delete or submit; the draft limit and the setup limit under concurrent requests; the daily limit at the 24-hour edge; that a refused or unavailable challenge changes nothing and that a submission refused before the challenge never calls Turnstile; the table's state and `submitted_at` checks; that an edit landing during the challenge is judged again under the lock; that a stored draft holds only the draft's fields, since the no-join test can't see inside the jsonb; and the account cascade. `definition-v5.property.test.ts` checks `definitionQuestionsRule` against the spec's rows. `apps/web/tests/serve.test.ts` drives the routes over HTTP with a real passkey session: an author saves, lists, edits and submits, another account sees nothing; refusals carry the rule; a signed-out request, another or a missing `Origin`, a non-JSON body and unknown routes are refused; the log line is `drafts`. The no-join and grant tests include the table.

Known-weak:

- **A submitted poll can't be withdrawn yet**, and nothing moves it on: the worker's jobs are parts 3 to 5, and retrying or discarding a failed poll is part 5. Part 5 must keep a discarded poll's submission counted for 24 hours.
- **Part 3 must widen the no-join deny-list deliberately** to store the `election_id` rule 15 puts on this table: `election` is on the account side's deny-list today.
- **Any tier can be chosen**, though only Tier 0 has groups; the worker refuses a tier with no published group at the `rooted` step (part 3), and the website (part 6) offers only what exists.
- **Edits aren't rate-limited**, only bounded in size and count; the proxy's per-address limits are P2-11's.
- **One language per draft.** Display text can carry 32 translations; the form writes one.
- **Submission assumes 30 minutes of setup.** A retry under rule 10 can push `opens_at` past what submission allowed for, so part 3's worker must re-check `closes_at` against the actual `opens_at` before each stub and fail the poll in plain words, or registration would refuse it (`timing`).
- **`displayTextV2ShapeRule` is public now and skips the commitment.** Anything that shows a registered election must keep calling `displayTextV2Rule`; nothing enforces that yet.
- **`/drafts` wants `content-type: application/json` exactly**, with no `charset` parameter; part 6's form must send that.

## Part 3a: the creation step

- `0013_poll_creation.sql` adds `poll_creation_txs`, an operational, append-only ledger of the creation key's transactions (key, nonce, signed bytes, hash, time sent), one per key and nonce, naming no account, poll or election; and on `account_polls`, `creator_address` and `create_tx_hash` (which transaction is the poll's), the `election_id` and `created_block` of its finalized `ElectionCreated`, and `failure`, the code a failed poll's page words. The table's checks hold the record whole, keep it off a draft (a later retry must clear it), require it and the identifier for every state past `submitted`, and set a failure exactly when `failed`. The ledger outlives polls and accounts, so deleting an account during setup frees no ceiling slot and leaves no nonce unsent. The no-join test now allows exactly `account_polls.election_id` among account columns: rule 15's creator record, whose poll an election is, which part 2 left to this part.
- `packages/core/src/poll-creation.ts`, `advancePollCreations`: per run, first every transaction in the ledger whose nonce the node hasn't seen included is sent again (whatever became of its poll or author, so later nonces can land); then each included one is judged at finality: `created` with the identifier, or `failed` with `creation-reverted`, `creation-replaced` (the node knows nothing of the transaction and its nonce is spent in finalized history: another transaction of the key took it, the runbook's sign of compromise) or `creation-timeout` (not final two hours after it was recorded, `CREATION_DEADLINE_MS`). Then up to 20 submitted polls without a creation, oldest submission first: `closes_at` is checked again against now plus setup and the shortest opening (`closes-too-soon`, before any gas), the global ceiling (`CREATE_DAILY_CEILING`, 200 in any 24 hours, counted from the ledger) is checked under one advisory lock for every key, the nonce is the larger of the node's pending count and the ledger's last nonce for the key plus one, and the signed creation is committed before it is broadcast (rule 12). A run reports counts only.
- `apps/worker`: `{poll-create}`, an account-side queue with no data, every 30 seconds; `ViemPollCreationChain` (the gas estimate with 20% headroom, a fee cap of three latest base fees plus the tip, a node that already holds the bytes counts as a send that took, a transaction the node holds without a receipt is `included`, never `unknown`; a creation is read only from finalized history, as the key's own call to the configured registry in the node's block at that height, with one `ElectionCreated` naming the key and the identifier the counter gives, or the node is refused); `checkPollCreationDeployment` at startup (the chain, and a registry whose `electionIdAt(0)` is ours for that chain and address); `CREATE_L2_RPC_URL`, `CREATE_CHAIN_ID`, `CREATE_REGISTRY`, `CREATE_KEY` and optional `CREATE_DAILY_CEILING`, all or none, never quoted. A worker holding the key runs `{poll-create}` and nothing else, and refuses to start with any anchoring, Tier 0 or ballot configuration beside it (rule 2); `main.ts` deletes `CREATE_KEY` from its environment once read.

Tested: `packages/core/tests/poll-creation.test.ts` drives the step against a chain with a mempool that finalizes when told: one creation per poll in submission order, recorded before it is sent; a refused send resent with the same bytes and never signed again; a creation the node dropped resent ahead of new ones at its own nonce; two runs at once on separate connections signing each poll once at distinct nonces; an author deleting their account during setup, whose creation is still sent and still counts against the ceiling; waiting while included and not final; revert, replacement and timeout, a timed-out creation still sent until it lands; the ceiling at the 24-hour edge; `closes-too-soon` signing nothing; the tables' checks, the ledger's grants and its Drizzle table; and a fast-check property over any interleaving of submissions, runs, inclusion, finality, dropped mempools, refused sends and time passing, that no poll or nonce is signed twice, every poll's transaction is in the ledger, no 24 hours sends more than the ceiling, and once the node is quiet nothing recorded is left in setup. `apps/worker/tests/poll-create-chain.test.ts` deploys the election registry on Anvil and runs core's step through the adapter with a fresh funded key: the poll is `created` only after finality, with the identifier `electionIdAt` gives and the key as `creatorOf`; the adapter's pending, included and final states, a repeated send and the fee cap; a final revert; a receipt that isn't the key's refused; the startup check's refusals; a malformed key refused unquoted. `poll-create-env.test.ts` checks the configuration, and `worker.test.ts` that a worker holding the key schedules only `{poll-create}`, keeps its keys under that tag, logs an idle run as its job line alone, and refuses any other job beside it.

Known-weak:

- **`created` is not yet safe to put in a stub.** The creator's per-slot anchor check ([[contracts]], Board anchor, Pre-creation anchors: prove at a finalized L1 block that no checkpoint is set from the creation's `f` on, or abandon the identifier) is part 3b's, before the stub; until then nothing past `created` runs.
- **No fee bumping.** The fee cap is three base fees ahead, so only a sharper rise strands a creation; one that does holds every later nonce of the key, its poll fails at the deadline, and its bytes are resent until they land. Replacing it at a higher fee needs a second transaction at the same nonce, which the ledger's one-per-nonce key refuses today; a later part can add a replacement record.
- **One key.** `CREATE_KEY_NEXT` and the runbook's rotation, sweep and status commands aren't built; part 3b adds the sweep and status commands, and rotation waits until a second key is needed.
- **The ledger is never pruned.** It grows by at most the ceiling a day (about 70,000 small rows a year at 200); a prune of included transactions older than a year can come with the sweep command.
- **The node is trusted for liveness and finality.** One L2 node's `finalized` tag decides `created`; a node lying about finality could move a poll early, which the reorg risk of T-25 then applies to. The adapter refuses a receipt outside the node's own chain at that height, nothing more.

## Part 3b-1: the per-slot check

The spec's MUST before any ceremony ([[contracts]], Board anchor, Verification, Pre-creation anchors), which part 3a left as its first known-weak:

- `0015_poll_anchor_check.sql` (numbered after P2-10's `0014_moderation_appeals`) adds to `account_polls` the event's `l1_origin_timestamp` (exactly when there is an `election_id`), `anchors_checked_block` (the finalized L1 block the check proved at, required for every state past `created`) and `abandoned_ids` (0 to 3), and the failure `creation-anchored`. Polls already `created` have no recorded origin, so the migration abandons them back to `submitted`; an abandoned identifier gets no definition, so that is always safe.
- `packages/core/src/poll-anchor-check.ts`, `checkCreationAnchors`: per run, one finalized L1 block `C`; each created, unchecked poll waits until `C` is later than its origin by more than the release's ceiling on `max_sequencer_drift` (1,800 seconds), or the verifier's pinned origin drift if larger, and until `C` is no earlier than when the poll was seen `created` (after a sequencer stall an event's L2 time, and so its origin, can lag the creation's real time), then reads the checkpoint word of every segment from `f` (the origin's period, 0 before the epoch) to the last period ended before `C` (`anchorCheckSegments`). All zero: checked at `C`. Any set: the identifier is abandoned, its poll back to `submitted` with the creation cleared, to be created again (the old transaction stays in the ledger and in the ceiling); the third abandoned identifier fails the poll, keeping that identifier for the runbook. A range too long to read (a check left for over a year) abandons the identifier without counting it, so one poll never holds up the rest. Every write is keyed by the identifier read, so a poll another run abandoned and created again is never marked by a stale run. Never the lowest-segment word, as the spec says.
- `packages/verifier`'s `checkpointWords` proves each word against a header's state root through the same account and storage walk as `anchorsFromState`; `apps/worker`'s `ViemCreationAnchors` rebuilds the finalized header from the node's fields (refused unless it hashes to the block's hash; fields through Amsterdam's `blockAccessListHash`) and proves `eth_getProof` nodes at it, never an `eth_call`. `CREATE_L1_RPC_URL`, `CREATE_L1_CHAIN_ID` and `CREATE_ANCHOR` join the creation worker's variables (all or none), the anchor's clock read from its finalized code at startup; the `{poll-create}` job runs the check after the creation step and logs `checked`, `abandoned` and `failed["creation-anchored"]` as counts.

Tested: `packages/core/tests/poll-anchor-check.test.ts` (a fast-check property that the range is exactly the ended segments from `f`, and nothing before the drift; waiting, checking, an empty range, anchors outside the range unread, abandon and its cleared creation, the third abandon failing, one block per run, a malformed reader answer moving nothing, a poll another run moved left alone, the table's checks); `packages/verifier/tests/l1.test.ts` (`checkpointWords` against an independently built trie: order, zeros, another election's slot, missing proofs, an absent anchor, malformed arguments); `apps/worker/tests/creation-anchors.test.ts` on Anvil with the real `BoardAnchor` (the startup check, words proven across proof chunks, a word written after the block unseen, a header that doesn't hash refused, a block not read refused, and core's check through the reader abandoning one identifier and passing another).

Known-weak:

- **The L1 node is trusted for which block is finalized**, as the creation step trusts its L2 node. One that hid an anchor would let a ceremony run for an election that then fails `checkpoint-inconsistent`, on that election only.
- **The creation's L1 origin isn't checked against L1 here.** `f` comes from the finalized event, as the verifier takes it; an earlier origin within the drift only widens the range read, and a bogus one is the verifier's 4.4 to refuse.
- **No deadline on the check**: a stalled L1 finality leaves a poll in `created`. Part 3b-2's stub step must re-check `closes_at` before building anything.
- **The anchor and its clock are the configured `CREATE_ANCHOR`'s**, the clock read with an unproven call at startup; part 3b-2's stub must name the same anchor, and compare its epoch with the election registry's.
- **The event's origin isn't checked against its L2 block's time** (`origin ≤ τ ≤ origin + drift`, as the verifier's 4.4 checks). A creation whose origin fails that is a doomed identifier the ceremony would still run for: liveness only. 3b-2 can record `τ` and abandon such an identifier.
- **Abandoned identifiers aren't kept**: only the third, on the failed poll. If the runbook needs every anchor that took one (T-69 attribution), an operational append-only table can keep them.
- **A retry from `failed`** (part 5) must clear `l1_origin_timestamp` with the identifier and decide whether `abandoned_ids` restarts.

## Part 3b-2: the roots

- `packages/crypto`'s `statedTierElectorate` (in `tier-membership.ts`): the electorate a creator states for a fixed Tier 0 tier, from the group registry's own sequence up to `root_l2_block`. Each listed group is replayed strictly by the same code `tierMembership` uses (now shared as `listedGroupLeaves`), and the regions, cells, roots and counts are `deriveTierCells`', so what a poll states is what the ballot client's recount and the verifier's 2.4 rebuild. A region with no counted member is refused (`empty`), since no definition can state it; a Tier 1 or Tier 2 choice is refused (`tier-unsupported`): a Tier 1 group's leaves are the additions the deployment's count takes (`countTier1Additions`), which this doesn't decide.

- **The transport's envelopes still aren't in `docs/spec/`** (apps/trustee-node's known-weak).

## Part 5a: the registration step

- `packages/crypto`, `encodeCeremonyRegistration` and `decodeCeremonyRegistration`: the record `registerCeremony(bytes)` takes ([[contracts]], Trustee registry, Registration), `panel_id ‖ stub_hash ‖ ceremony_transcript_hash ‖ u8(seats) ‖ seat × seats ‖ u8(count) ‖ approval × count`, each seat's signing key as its point `(x, y)`. The encoder refuses what checks 2 and 7 to 9 refuse (no seats, seats or approvals out of order, a key that isn't a canonical point, a high-s signature); the decoder is strict and gives back each key's one compressed encoding. The reference election's runner now builds its records with it, so the real trustee registry on Anvil admits the encoder's bytes in every run.
- `0019_poll_registration.sql`: the creation key's ledger (`poll_creation_txs`) gains `kind` (`create`, `register-ceremony`, `register-definition`), since registrations spend the same nonces, and holds transactions up to 128 KiB; the daily ceiling, and the status command's `lastDay`, count creations only. `account_polls` gains `ceremony_tx_hash`, `register_tx_hash` and `registered_block`, required from `registered` on and never with a block in `ceremony`, and the failures `registration-refused`, `-reverted`, `-replaced`, `-timeout` and `-mismatch`.
- `packages/core/src/poll-registration.ts`, `advancePollRegistrations`: for each poll in `ceremony` of the key whose stub has an approved run, more than `REGISTRATION_MARGIN_SECONDS` (5 minutes) before its `opens_at`, `pollRegistration` rechecks the run with crypto (the transcript under the panel and its hash, rule 7's qualified seats, the key set's hash, a quorum of approvals in seat order each verifying under its pinned key), completes the stub with the transcript's hash, and checks the definition's rules and that its stub hash is the approved one. Both transactions are signed at consecutive nonces (the ceremony's first), recorded in the ledger and on the poll under the lock every signer of the key takes, committed, then sent (rule 12). A poll moves to `registered` once its `registerDefinition` is final with a `DefinitionRegistered` event naming its election and its stub completed with the approved transcript's hash (whatever panel the step is configured with by then); reverted, replaced, naming anything else, or unknown to the node both past `REGISTRATION_DEADLINE_MS` and past `opens_at` with the margin (when the registry can no longer admit it), it fails. An included registration is never timed out, so a poll is never failed under a registration that can still land. A transaction past the ledger's 128 KiB, or bytes with no encoding, fail that poll rather than stopping the run. A stub naming another panel is left and counted; a run that fails the recheck fails the poll before any gas. The creation step's ledger helpers (`lockSigning`, `nextNonce`, `unincluded`) are shared, so a creation never takes a registration's nonce.

Known-weak:

## Part 5c: the read-back and opening

- `packages/core/src/poll-opening.ts`, `openPolls`: per run, up to 20 registered polls, least recently touched first. A poll waits until the registry sync has recorded its `DefinitionRegistered` (`election_registrations`), which it does only from finalized logs checked against the registry's accumulator (T-71), so the read-back is independent of the creation key's own read of its registration. `pollReadBack` (rule 13) rebuilds the whole definition: the draft's questions, `closes_at` and display-text commitment (the draft's text under the salt the recorded text carries, which must re-encode to the recorded bytes), the roots step's electorate, the stub step's `opens_at`, the approved transcript's hash, and every other field from the approved stub; its stub hash must be the poll's, the event's hash must be its hash, and once the sync has stored the definition (`election_definitions`) the stored bytes must equal it. A registration the sync recorded but couldn't store is judged by its hash alone, so one that isn't the draft's fails rather than waits. Otherwise, once stored, and while the stub's anchor is the clock's and `closes_at` hasn't passed, the transcript is boarded as entry 0 in the anchoring clock's current segment, never below the creation's first segment `f` (a clock behind it leaves the poll, `early`); then the display text is stored (`storeDisplayText`, the client's own check) and the poll moves to `open`, keyed by the identifier read. Such a poll is left in `registered` and counted (`unboarded`).
- `apps/worker`: `{poll-open}`, an account-side queue with no data, every minute, beside the stub step (never with the creation key). The clock is read at startup from the finalized code of the anchor the election registry names (and so every stub pins) through the registry sync's L1 node, never configured, so the stub step now needs that node to start. Known-weak:

- **The comparison is ours, against our own records.** Nothing the author signs binds the registered definition to the draft ([[0032-poll-creation-operations]], Known-weak); the read-back catches a registry, index or creation worker that registered something else, not an operator who changed the draft row and the stub together.

A poll whose stub pins another anchor waits (`otherAnchor`) until a worker with that anchor runs.

- **A retry from `failed`** (part 5d) must decide whether an `open-mismatch` can be retried at all: the identifier is registered, so a new stub can't be.

## Part 5d-2: the author's view of a failed poll, retry and discard

- `packages/core/src/poll-failures.ts`: `POLL_FAILURES`, the sixteen codes the steps write to `failure`, in the order the table's check lists them (a test reads the check, and a step code missing from the list fails type-checking); `REGISTERED_FAILURES` (`registration-mismatch`, `open-mismatch`, `open-timeout`) and `retryableFailure`. - `AccountPoll` carries `failure`, and `/drafts` (`GET /drafts`, `POST /drafts/read`) answers a failed poll with `failure` and `retryable`. `apps/web/src/messages.ts` words each code (`POLL_FAILURE_MESSAGES`, a `pollFailure_*` message per code, typed so a new code without words fails type-checking): what happened, whether the question was published, and what the author can do, never the code, a hash or an identifier. The screens that show them are part 6.
- `retryFailedPoll` (`POST /drafts/retry`): under the account's lock and the poll's row lock, a failed poll of the account goes back to `drafted` with everything setup wrote cleared (`DRAFTED` in `poll-drafts.ts`), for the author to edit and submit again through `submitPollDraft`. Refused, writing nothing: another account's or an unknown poll (`NOT_FOUND`), one not failed (`NOT_FAILED`), one whose election is registered (`REGISTERED`) and an account at `MAX_DRAFTS` drafts (`TOO_MANY_DRAFTS`).
- `discardFailedPoll` (`POST /drafts/discard`): deletes a failed poll of the account under its row lock, with the same refusals but the draft limit.
- `0022_poll_submissions.sql`: `account_poll_submissions`, one row per submission (the account and the time), account class, `SELECT, INSERT` for the app, deleted with its account, backfilled from every `submitted_at`. `submitPollDraft` inserts one in the transaction that moves the poll to `submitted`, and the daily limit counts this table, not `account_polls`.
- `packages/core/src/poll-creation.ts`: the creation step's verdicts (created, reverted, replaced, timed out) are keyed by the poll's recorded creation, and `closes-too-soon` by its submission time, as well as by `submitted`.

Decisions (none a one-way door: account-side, operational state):

- **A retry returns the poll to its draft, never straight to `submitted`** (T-72). The resubmission is an ordinary one: its draft is judged at its own time, so its closing time must leave the setup still ahead (part 2's "submission assumes 30 minutes of setup"; a poll that failed `closes-too-soon`, or after two hours of `ceremony-timeout`, needs a later one), it needs a Turnstile solve, and it counts against the setup and daily limits. A failure that needs an edit (`closes-too-soon`, `tier-unavailable`) gets one. Retry and discard themselves spend nothing, so they need no solve.
- **A retry starts setup over under a new identifier.** The creation step creates the resubmitted poll again; the old identifier is left unused, as an abandoned one is (rule 16), which the runbook's compromise step already assumes ("the authors can retry, which creates a new election"). What the earlier parts said a retry must clear, it clears: the creation (part 3a, `0013`), `l1_origin_timestamp` and `anchors_checked_block` with the identifier (part 3b-1), `electorate` (part 3b-2), `stub_hash` (part 4a) and the registration transactions and block (part 5a), plus `failure` and `submitted_at`. The test compares the retried row with a fresh draft's in every column but the identity, text and times, so a column a later migration adds must be cleared too.
- **`abandoned_ids` restarts at 0** (part 3b-1's question). It bounds the identifiers one submission abandons to a quorum anchoring ahead (T-69); a retry is a new submission, counted and paid for again, so the per-account daily limit and the global ceiling bound the creations a retried poll can spend.
- **A poll whose election is registered is neither retried nor discarded** (part 5c's question on `open-mismatch`, answered for all three such codes). No new stub can register under a registered identifier (rule 10), and a retry under a new one would leave the registered election, which the listing shows once the registry sync stores it and moderation can act on, without its creator record, which moderation's own-poll refusal and the author's appeals read (T-68). Discarding it would do the same. It stays in the author's list like an open poll; the author can read its draft and start a new one. A poll is refused the same way, whatever its code, when the registry sync has recorded a registration under its identifier.
- **Every submission counts for its 24 hours** (part 2's "Part 5 must keep a discarded poll's submission counted for 24 hours"): the limit counts `account_poll_submissions`, so discarding (which deletes the poll) and retrying (which clears `submitted_at`) give nothing back, and one poll retried after each failure counts each time. A discard deletes the row rather than keeping a tombstone: nothing on chain names an identifier that was never registered.
- **The creation step's writes are keyed by what they judged.** Before this part a submitted poll left `submitted` only through that step; now another run's failure, the author's retry and a resubmission can land while a run waits on the node, and its verdict on the old creation would fail the new submission (`creation-reverted`) or break the table's checks (`created` with no creation). The later steps were already keyed by the identifier or the stub.

- **Nothing shows the words yet.** The website's screens are part 6, and so is the flow that turns "try again" into a retry, an edit and a submission; the messages are in English only.
- **`retryable` is the code's.** A poll with a retryable code whose identifier the registry sync saw registered is answered `retryable` and then refused `REGISTERED`; that takes a step and the chain disagreeing (a bug or a stolen key).
- **A registered failed poll stays in the author's list for good**, as an open poll does; only deleting the account removes it (rule 16, its election then unattributed).
- **Retry and discard drop the third identifier `creation-anchored` kept** (part 3b-1) for the runbook's attribution (T-69); its creation stays in the ledger and the identifier on chain under the key, so the runbook's compromise step has the operator record a failed poll's identifier before its author retries or discards it; part 3b-1's append-only table of abandoned identifiers is still the fix if that proves too easy to miss.
- **A stolen creation key can still register an old stub.** An approved stub of a retried or discarded identifier can be registered by the key before its `opens_at` (T-72's thief); its election is then listed with no creator record.
- **The submissions are never pruned**: at most ten rows per account a day; deleting an account deletes them, as before (an account is cheap, T-01).
- **The runbook's "set up again" has no code.** Its compromise step marks polls failed for the authors to retry; `failure` admits only the steps' codes, so an operator must use one of them (a retryable one) until a code of its own is added.
- **`closes-too-soon` is keyed by the millisecond of submission**, as the clock writes it; a poll submitted twice within one millisecond would need a failure and a retry in between, which no step can do that fast.

## Part 6c: submission

- `apps/web/src/components/poll-form.tsx`: a fifth section, "Ready to ask?", with "Submit poll". Only the saved draft, unchanged since its save or its load, is submitted: anything else is "Save your draft first". The closing time is judged again by the clock at submission, its problems listed as "Your poll wasn't submitted". Then the Turnstile check appears in the section, and its token is sent at once; editing or saving takes the check down, an edit made during a save leaves the draft unsaved, and the form takes no edits while the submission is on its way. A refusal is an alert in words (`tooManyInSetup`, `tooManyToday`, `challengeRefused`, `challengeUnavailable`, `refused`, signed out); a token is spent on one request, so submitting again takes a new check. A submitted poll goes back to the account page as a new document. The section says Cloudflare runs the check and sees the browser's address while it does (T-11).
- `apps/web/src/account/challenge.ts`: the `Challenge` the form takes (so stories use a stand-in) and `turnstileChallenge(siteKey)`, which loads Cloudflare's script for explicit rendering once, on the first submission and never with the page, renders one widget for the action with no form field for its token, resolves with one well-formed token and removes the widget on every way out (a token, an error, a timeout, an unsupported browser, an abort). A script that fails to load is removed and tried again next time.
- `apps/web/src/security.ts`, `src/start.ts`: the poll editor's pages (`isChallengePage`, exactly `/account/polls/<letters and digits>`) add `https://challenges.cloudflare.com` to `script-src` and as `frame-src`; every other page's policy is as before, and `connect-src` stays `'self'` everywhere (T-43, T-55). The editor's links out are plain ones, so no other page runs under the widened policy.
- `apps/web/src/account/drafts.ts`: `submit(id, token)`, the token in `x-turnstile-token`, and the handler's `TOO_MANY_IN_SETUP`, `TOO_MANY_TODAY`, `TURNSTILE_REFUSED` and `TURNSTILE_UNAVAILABLE` worded for the account page and the form.
- `TURNSTILE_SITE_KEY` (`src/data.ts`, `fetchChallengeKey`; `src/node/main.ts`): the widget's public site key reaches the editor in its page's loader data. Optional, so a deployment without one keeps running: its editor says polls can't be submitted here. A malformed one is refused at start.

Tested: `tests/challenge.test.ts`, with the document and Cloudflare's API stood in: nothing loaded before a solve; the script's URL, loaded once across solves; the widget's site key, action and `response-field: false`; malformed tokens (empty, a space, over 2048 characters, not a string) refused; the error, timeout and unsupported callbacks and an abort each failing the solve and removing the widget, and a token given during `render` itself still removing it; an aborted signal loading nothing; a failed load, and a load defining no API, removed and retried from a fresh tag; a widget that won't render. `tests/drafts-client.test.ts`: the submission's path, body, header and fetch options, and each refusal worded. `tests/security.test.ts`: the editor's policy adds exactly the two sources and nothing else, `connect-src` stays ours, and which paths are the editor (not `/account`, a trailing slash, a deeper path, capitals, percent-encoding or `/_serverFn/`). `tests/ssr.test.ts`: only the editor's pages carry Turnstile's origin, their HTML loads no Cloudflare script and carries the site key, and the new server function answers the key. `tests/deployable.test.ts`: the built server's editor policy and site key, and a malformed site key refused at start. `poll-form.stories.tsx` (interaction and axe, both themes, desktop and phone): a saved draft submitted with the check shown only after Submit, the token sent once and the page left; a new draft that must be saved, and saved again after an edit, before it can be submitted; an edit, and a save, taking the check down; an edit during a save keeping the draft unsaved and unsubmittable; no edits while the submission is sending; a closing time too soon refused before any check; a refused token followed by a second check; a check that can't run; the setup limit; a poll submitted meanwhile; no site key.
