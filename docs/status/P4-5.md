# P4-5: `apps/node`

- State: in progress (part 1, the block mirror over the trustless gateway API, merged in #334; part 2, fetching and pinning every election's board objects from L1's CIDs, merged in #358; part 3a, verifying what was pinned from L1, L2 and the node's own blocks, merged in #416; part 3b, format 5's run of L1 headers, so 5.8, selection and the per-tier results are reported, next)
- Branch: `claude/p4-5`
- Phase: Phase 4: Censorship resistance

## Scope

`apps/node`: a one-command community node (verifier + IPFS + chain reader, no DB).

The duties the docs give it, with their sources:

- **Pin every election's data** on IPFS by default ([[0005-permanent-archive]]; [[P4-3]] plan item 4; T-51).
- **Verify from chain + IPFS**, never our API ([[0005-permanent-archive]]; [[board]], A copy from L1's CIDs; T-24, T-49), with live board checks while an election runs ([[board]]; [[revoting]]).
- **Serve the ballot-client release it has checked** at a local origin of its own, so the gateway is out of the path ([[0020-entry-points]]; T-41, T-43). The client must not warn there.
- **Relay receipt commitments**, batching many voters' words, and serve entry-hash lists to a voter's own node ([[0023-receipt-evidence]]; [[receipts]]).
- **Explain the forced L1 path** when the L2 censors ([[0004-l2-choice]]; T-50).
- No database or cache, one command (the brief).

## Plan

Each part is one PR on this branch's name.

1. **The block mirror** (#334): `abolish-node serve --blocks <dir>` holds the blocks of every CARv1 file in a directory, each read with the verifier's block store (hashed against its CID, at most `CHUNK_SIZE`), and answers the raw-block requests of the IPFS trustless gateway API with them. It is the server side of the network sources [[P4-3]] part 2b-2b-2 adds to the verifier, and it needs nothing that isn't built.
2. **Fetch and pin**: from an L1 RPC and the deployment's anchor, follow every checkpoint's segment CIDs and fetch their blocks from other gateways through the verifier's network sources, checked against the anchored roots, and write them to the directory part 1 serves. Waits on P4-3 part 2b-2b-2 (network sources) and uses `readBoardCopy`; reading L1 trusts no RPC answer ([[verifier]], L1 evidence).
3. **Verify**: run the verifier over what part 2 fetched, from L1 and IPFS alone, and publish the reports at the node's origin; the reference election runs it with our servers and domain offline ([[P4-6]]). In parts: 3a (#416), format-4 bundles gathered from L1, L2 and the directory, with the reports served; 3b, format 5's run of finalized L1 headers, from the earliest block a ballot names to the finalized head, so 5.8, selection (6.1) and the per-tier results are reported.
4. **The ballot client**: fetch the signed release ([[P2-8]], [[P4-4]] part 2), check it with the verifier's served-client check (1.1), and serve it at the node's own origin with the release's headers, `frame-ancestors` included. Waits on the release record.
5. **Relaying and lists**: the receipt-commitment relayer and entry-hash lists ([[0023-receipt-evidence]]); the forced-path guide (T-50); a runbook and one-command packaging.

## Part 1: the block mirror

- `apps/node` (`@abolishus/node`, private, AGPL-3.0-only, source-only), with a README of its duties, threats and known-weak points.
- `src/store.ts`: reads every `*.car` directly in the directory (symlinks followed), in name order, with `readBlockStore` from `@abolishus/verifier`; a file that isn't a CARv1 (`not-a-car`) or can't be read (its error code) is reported and skipped, and one cut short serves the blocks before the cut. A lookup tries each file in turn and takes the first block that hashed to the CID.
- `src/cid.ts`: parses only the layout's CIDs (`0x01 ‖ raw or dag-pb ‖ sha2-256`, 36 bytes) in their canonical text form, multibase base32 lowercase without padding, so a block has one URL; anything else is a 400.
- `src/gateway.ts`: `GET` and `HEAD /ipfs/{cid}` with `?format=raw` or `Accept: application/vnd.ipld.raw`, answered with `application/vnd.ipld.raw`, `immutable` caching, `access-control-allow-origin: *`, `nosniff` and an attachment disposition; 404 for a CID it doesn't hold or another path, 406 for any other format, 405 for other methods, 400 for a GET that declares a body; `vary: accept`, and a case-insensitive Accept match that honours `q=0`. No paths below a CID, no CAR responses and no pages, so nothing served runs in a browser at its origin, which part 4 gives to the ballot client (T-43). Nothing about a request is written anywhere (T-11). At most 1,024 connections (more are closed on accept), headers within 10 s and 8 KiB, requests within 30 s, idle keep-alive connections 5 s; a request that declares a body is refused with its connection closed, so the body is never read; an error after listening is reported, never fatal (T-52).
- `src/cli.ts`: `abolish-node serve --blocks <dir> [--port 8080] [--host 127.0.0.1]`, loopback by default; prints a JSON line per file and the address it listens on; SIGINT or SIGTERM stops it.

Tested (`vp run --filter @abolishus/node test`):

- The CID parser: every layout CID round-trips through `cidText`; anything it accepts from arbitrary text is the canonical spelling of a layout CID; upper case, padding, a missing or capital prefix, non-zero spare bits, another codec, hash, digest length or version, and a CIDv0 are refused.
- The gateway over loopback: every block of a 2.5 MiB object (a dag-pb root over three raw leaves) is served with its headers, and `readObjectAsync` rebuilds the object over HTTP; for random sets of objects across files, exactly the blocks held are served (property); a CAR whose block doesn't hash serves nothing for it while another file's block is served; HEAD; the Accept header; and every refusal.
- The connection limit (a connection past it is closed and serving goes on), the headers timeout (a 408 and a closed connection), and refusals of declared bodies (the connection closed, a 100 MB declaration answered at once).
- The command line: usage errors, an unreadable directory, and a run that reports each file (a symlink followed, a directory and a non-CAR reported), serves, and exits 0 when stopped.

Known-weak:

- Each CAR is held in memory whole, and the directory is read once at start.
- The connection limit is for all clients together, not per address: one client can hold every slot, so a published node needs a proxy's per-address limits in front (T-52).
- No `format=car` responses: an IPFS client must fetch block by block.
- Nothing fills the directory yet: an operator exports CARs from an IPFS node by hand until part 2.

## Part 2: fetch and pin

- `abolish-node fetch --blocks <dir> --l1 <url> --anchor <address> --gateway <url>... [--from-block <n>] [--max-bytes <n>]` pins into the directory `serve` mirrors every segment object and entry-hash list the board anchor's checkpoints name, one canonical CARv1 per object, `<cid>.car`, written through a temporary file and a rename; a file already holding those bytes is left alone.
- `src/l1.ts`: the finalized block's header, rebuilt from the node's fields and refused unless it hashes to the block's hash; the anchor's `CheckpointAnchored` logs up to that block, decoded only in the contract's one layout and only if the checkpoint hashes to the logged hash; and, per election, the checkpoints proven with the verifier's `anchorsFromState` from `eth_getProof` nodes at that block: the lowest-segment word, then every segment's word from the lowest anchored one to the highest logged (256 slots a request). Where the range starts is the node's `eth_getStorageAt` answer, used only to choose slots: the reader proves the lowest word itself, so a node naming a higher one (or none) leaves a needed proof out (`l1-proof-missing`). A proven word no log matches is `l1-checkpoint-unknown`, and the election is reported and skipped. Pinning judges no timing, so the reader is given a clock of period 1 from time 0, under which every segment up to the highest logged has ended (the board checks' windows are the verifier's, part 3).
- `src/pin.ts`: each counted checkpoint's two objects read with `readObjectWithinAsync`, the directory's own blocks first (`mirrorThen`, so a block already held costs no request), then each gateway (`gatewaySource` from the verifier). An object is bounded by its checkpoint's run, the entries since the next smaller size (51 bytes plus `MAX_BOARD_PAYLOAD` each for the object, 32 each for the list), and by a budget per election (`--max-bytes`, 1 GiB by default); outcomes `pinned`, `held`, `unavailable`, `inconsistent` (past its run's bound: the authority's) and `over-budget`.
- Each election's proof nodes are held up to 256 MiB, and header quantities up to 32 bytes; an election whose proofs can't be read (a refusal, a timeout, past the limit) is reported and skipped like an L1 error, and the run goes on to the next.
- `src/rpc.ts`: a JSON-RPC client over `fetch` with a 60 s timeout, no redirects, answers of at most 64 MiB read as they stream, and errors that never name the URL (a hosted node's key may be in it).
- Exit codes: 0 done (whatever couldn't be fetched, reported line by line), 1 L1's block or logs couldn't be read, 2 usage or a directory that can't be read or written.

Tested (`vp run --filter @abolishus/node test`, with `anvil` and `forge`):

- Against BoardAnchor on Anvil, anchored from an impersonated authority: two elections' three checkpoints pin exactly their six objects (multi-block and single-block), each file the object's canonical CAR, every block then served by the mirror; a second run reports every object `held` and sends no request.
- Withheld and altered blocks are `unavailable`, an entry-hash list longer than its run is `inconsistent`, and a 40-byte budget pins the 32-byte list and reports the rest `over-budget`; the other objects are still pinned.
- A node that lies: a forged, well-formed log for a segment the anchor doesn't hold is counted `unproven` and never pinned; a withheld or altered log leaves its election unpinned (`l1-checkpoint-unknown`) while another election pins; a log withheld below the lowest logged segment is found the same way, and a node naming a higher lowest segment, or none, to hide it is caught by the missing proof; altered proof nodes give `l1-proof-missing`; logs from another address, in another layout or of another shape are refused and counted; a header that doesn't hash to its block, one of too few fields and one with a quantity wider than 32 bytes are refused; one election's refused proof request is reported while the next election is pinned; a repeated log counts once.
- `checkpointFromLog`: property tests (`FC_NUM_RUNS`) that every checkpoint reads back from a log in the contract's layout, written independently, and that a change to any nibble of the topics or data is refused.
- The JSON-RPC client: its own request's result; errors, other statuses, other ids, missing results, non-JSON and network failures refused without the URL; an endless answer stopped near 64 MiB. The command line: usage errors, a run that pins, and exit 1 with an unreachable node, naming no part of its URL.

Known-weak:

- The node is trusted for which block is finalized (the verifier trusts its header the same way today, [[verifier]], Bundle) and for the logs: a node can keep checkpoints from being pinned, never make anything else pinned. An operator should name a node they run.
- One run, then it stops: continuous pinning needs a scheduler, and a running `serve` reads the directory only at start, so it needs a restart to serve what was added (part 5 packages both).
- Every log from `--from-block` is read in one `eth_getLogs` request, which hosted nodes may refuse over a long range.
- An election whose anchored range is long costs one `eth_getProof` per 256 segments of it, and the anchoring authority can anchor a segment far below an election's first one (anchors below `f` don't count for it, [[contracts]], Board anchor, Verification): a node reads up to `MAX_SEGMENTS_READ` slots' proofs for such an election before giving up.
- Every gateway named sees which CIDs, and so which elections, the node pins (T-11).
- Runs are cut from every proven checkpoint, where the verifier's `readBoardCopy` counts only those inside the election's window: a checkpoint the anchoring authority stores below `f` or past the seal, with a size between two honest ones, shrinks an honest run's bound, so its object is reported `inconsistent` and not pinned. Only the anchoring key can do that, and it is attributable on L1; the node can't count checkpoints until it reads `f` and the seal from the definition (part 3).
- The run planning (bounds, budget, outcomes) mirrors `readBoardCopy`'s, and the header and log decoding mirror the reference election's; neither is shared code yet.
- Nothing about the board is judged: the objects are the bytes their CIDs name, which part 3's verifier run authenticates against the anchored heads and roots.

## Part 3a: verify (#416)

- `abolish-node verify --blocks <dir> --reports <dir> --l1 <url> --anchor <address> --l2 <url> --registry <address> [--from-block <n>] [--l2-from-block <n>] [--max-bytes <n>]`: for every election the anchor's `CheckpointAnchored` logs name, a format-4 bundle gathered with no input from our servers, the board copy read by CID from the directory alone (`mirrorStore`), and the verifier's `verifyBundle` over it. Each verified election gets `<reports>/<election>/bundle.json` and `report.json`, written through a temporary file and a rename; `abolish-verify --gateway <node>` on that directory gives the same checks. Exit codes: 0 done, 1 L1's or L2's block, L1's logs or the anchor's clock unreadable, 2 usage or a directory.
- The inputs: the anchors and `now` proven at the finalized L1 block by part 2's reader, which now also returns its proof nodes and proves the definition's receipt-key slots for 2.9 (`provenCheckpoints`, `proofNodes`); every logged checkpoint; the definition from the election registry's one `DefinitionRegistered` for the election and `f` from the period holding its one `ElectionCreated`'s L1 origin (`src/l2.ts`, each log through `checkContractEvent` under the newest version this release reads, the registry's own role until the definition names the others); the panel from the definition's trustee registry's one `PanelPinned` for its `panel_id`; `epoch`, `period` and `deadline` from the anchor's getters at the finalized L1 block (`anchorTiming`); and the seal as the highest proven checkpoint's segment. All of them up to the L2 node's finalized block.
- Skipped and reported, the others still verified: `l2-creation-missing`, `l2-definition-missing` (not registered, not final yet, or a log failing the event check), `l2-repeated`, `l2-panel-missing`, `definition-anchor`, `definition-registry` and `definition-chain` (a definition naming another anchor, registry or chain than the node reads, by address and `eth_chainId`: its evidence wouldn't be its own), `creation-outside-clock`, `unanchored`, an L1 error, an RPC error naming its chain (`l1:` or `l2:`), or a bundle the verifier's parser rejects. A log marked removed, outside the range read or of another address is dropped, whatever the L2 node's filter returned.
- Bounds (T-52): an election's proofs are held up to `MAX_BUNDLE_PROOF_BYTES` (64 MiB, so its bundle's JSON stays far below the runtime's longest string), each node counted with `PROOF_NODE_OVERHEAD` (64 bytes) and an empty node refused, which the pinner now gets too (`proofNodes`); a report is streamed, never held whole, and `HEAD` only reads its size.
- `serve --reports <dir>` answers `GET` and `HEAD /reports/<election>` (lowercase hex, one URL per report) with the report as written, read at each request, as `application/json` under `default-src 'none'; sandbox`, `no-cache`, at most 256 MiB; anything else under `/reports/` is 404, and so is every report without `--reports`.
- The reference election runs `abolish-node verify` in a process of its own after stage 9, against both Anvils and the node's directory, with no input from the fixture: every registered election's checks and verdict must equal the verifier's on the fixture's own bundle (the honest election, the rejected-ballot control and the poll of questions, whose 2.9 needs the receipt-key proofs), and rule-7's election, whose definition the registry refused, must be skipped as `l2-definition-missing`. Its output is `reference-election-output/node/`.
- `tests/anvil.ts` holds the Anvil fixture part 2's tests had inline, now shared.

Tested (`vp run --filter @abolishus/node test`, with `anvil` and `forge`):

- Against BoardAnchor on Anvil with an L2 node scripted in the test, its logs ABI-encoded there with the topics of `contract-event-v8.json`: the bundle holds the definition's bytes, the anchor's clock, the seal 2 of checkpoints in segments 1 and 2, `f` 1 from a creation in period 1, the finalized header's RLP, every logged checkpoint and the pinned panel; the report's checks and verdict equal the verifier's own `loadBundle` and `verifyBundle` on the written bundle read through the node's gateway, at the finalized block's number with both anchors; a log of another contract under the same topics is dropped.
- The L2 node lies about which logs match: it also returns another contract's registration, one marked removed and one past its finalized block, each of which would make the election `l2-repeated` if read.
- One run with an election for each skip, each reported with its code while an honest one is still verified: no registration (its log a byte past the canonical encoding), no creation, two registrations, another anchor, another registry, another L1 and another L2 chain ID, a creation before the epoch and one past the last `u32` segment, a panel no `PanelPinned` names, an election the L1 node forged a log for but never anchored (`unanchored`), and one whose segment-1 log the L1 node withheld (`l1-checkpoint-unknown at segment 1`); an L2 node that refuses every request is that election's `l2:` error.
- `proofNodes`: 256 slots a request, an empty node refused, and each node's overhead counted against the budget.
- By mutation: `f` one too high, the seal one too high, no logged checkpoints in the bundle, the anchor, registry or L1 chain check dropped, and the L2 reader's address, removed and range checks dropped each fail a test.
- `tests/l2.test.ts` (fast-check, `FC_NUM_RUNS`): any `eth_getLogs` answer (arbitrary values, logs of every shape) is read or refused with `L2Error` or `RpcError`, never another throw; a finalized block number is taken only as a canonical quantity.
- The command line end to end against an HTTP L2 node, then `serve --reports` answering the report byte for byte with its headers and 404 for an unknown election, uppercase hex, a trailing slash and the bare prefix; exit 1 with an unreachable L2 node, naming no part of its URL; exit 2 without `--l2` or with a short registry address. A gateway given no reports directory answers none.

Known-weak:

- The L2 node is trusted for the creation, the definition and the panel, and the L1 node for the anchor's clock: nothing proves them yet ([[verifier]] 2.1, 3.1 and 4.4 will, with the registries' accumulators under an output root as P3-5 part 3b's sync does). The verifier reports them as local inputs, so the verdict stays unverifiable while they are (T-53).
- The seal is the highest anchored segment, not one derived from the definition ([[election-definition]], The seal, waits on P1-18's window): a running election's report reads as if its board ended at its latest anchor, an anchoring authority that anchors past an honest seal moves it, and the board check `unsealed` can never fire, so a missing seal checkpoint goes unreported even against the inputs.
- Format 4 only: without format 5's headers, 5.8, selection (6.1), the tally (7.1 to 7.3) and the per-tier results stay unverifiable or not reached (part 3b).
- One run, then it stops, as `fetch` does: a scheduler runs both (part 5). Every election's whole board is read again each run.
- The L2 logs are read in two `eth_getLogs` requests per election over the whole range from `--l2-from-block`, which hosted nodes may refuse over a long range; the L1 logs as in part 2.
- The node takes the default panel from `PanelPinned`; an author panel ([[P2-16]]) isn't read yet, so an election with one is judged against the default panel alone, as format 4 holds one panel.
