# P1-12: Ballot commitments and validity proofs

- State: done (parts 1, 2, 3a, 3b and 4 merged in #53, #58, #98, #101 and #131; #101's last finding accepted by the owner as a residual until [[P1-12c]], see Blocked (part 3b, resolved) below)
- Branch: `claude/p1-12`
- Phase: Phase 1: Threat model, spec, crypto core, circuits, verifier, reference election (CLI only)

## Scope

Ballot commitments and validity proofs per [[0002-everlasting-privacy]] and the tally ADR: Pedersen and VSS commitments, disjunctive Chaum–Pedersen (CDS) proofs, hybrid-KEM share encryption, Fiat–Shamir with full statement binding.

## Plan

The item is built in parts, each its own PR on this branch's name:

1. **Commitments, VSS and validity proofs** (done, #53): [[ballot-validity]]. The committed vote, the trustees' share check, the statement hash and the option and sum proofs.
2. **Share encryption** (done, #58): the hybrid KEM and AEAD that carry each trustee's shares (`abolish/v1/kem/share`), `H(ct_i)`, per-election trustee KEM keys with P1-14 part 2, and the public check of a posted ciphertext. The owner's answer in [[0002-everlasting-privacy]] (Decision) names X25519 with ML-KEM-768, while the ADR's option B puts the Diffie–Hellman half in the commitment group (ristretto255) so that a trustee's complaint can prove a DH value with a Chaum–Pedersen proof. Part 2 must reconcile the two: either ristretto255 DH (which the complaint proofs need, and which is the same curve as X25519 in another encoding) with an ADR recording the reading, or X25519 with a complaint proof that works over it.
3. Split in two:
   - **3a, ballot hash and share receipts** (done, #98): the ballot hash (`abolish/v1/ballot`), trustee intake and the share receipt's signed statement and check.
   - **3b, delivery on the board** (done, #101): the records that carry share receipts, postings and complaints to the board, the complaint's signature, the delivery deadline and the complaint window, each by submission time inside `W_S` ([[tally]], Tally window): [[delivery]].
4. **The ballot record** (`0x0002`, version 1; done, #131): the committed vote with the tier, nullifier, L1 reference and membership proof, and its admission checks (What was built (part 4)), once P1-17b had encoded the membership proof (#111). No complaint-query limit is needed: the ciphertext's proof of knowledge of its ephemeral leaves no static-DH oracle ([[share-encryption]], Complaints). [[0007-group-and-hash]] (Consequences) and [[0002-everlasting-privacy]] (Static-DH oracle) still ask P1-13 for a posting bound below 2³² queries per trustee key; both are owner-accepted, so they stay as written, and P1-13 should read them as superseded by this proof (#58).

## What was built (part 1)

- [[ballot-validity]], a new spec page:
  - **Committed vote.** For each option, `k` Pedersen VSS commitments to the sharing polynomials of `(v_j, r_j)`, the first being `C_j`. It also carries the `n` share-ciphertext hashes, one option proof per option, and the sum proof with one branch per allowed value.
  - **Shares.** Each trustee checks its shares against the VSS commitments (Pedersen 1991).
  - **Statement hash** (`abolish/v1/ballot-statement`, new plain-hash tag). It covers the definition hash, the ballot record type and version, the tier, the nullifier, every VSS commitment and every share-ciphertext hash, hashed once.
  - **Proofs.** The option proof (each `C_j` opens to 0 or 1) and the sum proof (`C_Σ` opens to a value from `min` to `max`) are CDS disjunctions of Schnorr proofs base `h`, in compact form. A proof carries only challenges and responses, and the verifier recomputes the prover commitments.
  - **Challenges.** Each challenge's input is `statement_hash`, the position (option index, or `min` and `max`), the commitment, and every recomputed prover commitment.
  - **Check codes:** `validity-shape`, `option-proof`, `sum-proof`.
  - **Residuals:** trustees can open any ballot; binding is computational; cast-as-intended is P1-13's; the prover isn't constant time.
- [[domain-separation]]:
  - the two Fiat–Shamir tags are now specified, and `abolish/v1/ballot-statement` is added;
  - the Fiat–Shamir rule allows a statement digest under its own tag, provided the challenge still carries the position, the allowed-value set and the prover commitments.
- [[verifier]] 5.4 names the codes. [[versioning]]'s `0x0002` row points at the committed vote. The spec README and the vectors README are updated, and `circuit.json` gains the new tag's field element.
- `packages/crypto/src/ballot-validity.ts`:
  - `shareVote`, `proveValidity`, `checkValidity`, `checkShares`, `statementHash`, and the `COMMITTED_VOTE` and `SHARES` codecs.
  - Internal `shareVoteWith` and `proveValidityWith` take explicit randomness. The package entry point doesn't export them, and a test checks that.
  - Every sharing is frozen and registered when it is made, and the prover refuses any other, so no caller can choose a commitment's randomness (a hand-built `r_j = 0` would publish an openable commitment, T-15). A test checks that a copy and a hand-built sharing are refused.
- Threat files T-15, T-28, T-30 and T-32.

## Known-weak (part 1)

- **Share hashes are opaque.** They are bound into every proof, but nothing yet defines or checks the ciphertexts behind them (part 2).
- **Nothing on the board carries a committed vote yet** (part 3).
- **The prover's scalar arithmetic isn't constant time.** It uses JavaScript `bigint`. The scalar multiplications run the same whatever the vote, but their order within a proof depends on the real branch (T-18).
- **`VoteSharing` holds secrets as `bigint`s,** which JavaScript can't zeroise; the caller can only drop its references.
- **No published vectors exist for this composition.** The independent implementation and the review carry the weight (T-36, [[0002-everlasting-privacy]]).

## Known-weak (part 2)

- **`@noble/post-quantum` has no independent audit** (self-audited at 0.6.1). Testnets only until one exists; funding it is the owner's ([[0002-everlasting-privacy]], Decision).
- **ML-KEM's published vectors aren't vendored.** Go's accumulated hashes are copied into the test with their URL; neither `golang/go` nor C2SP's CCTV is an allowlisted publisher, so CI's provenance step doesn't re-fetch them. NIST ACVP vectors need a publisher added in a `ci:` PR.
- **No published vectors for the combination** (it isn't X-Wing). The independent implementation and the review carry the weight (T-36).
- **Not constant time.** ML-KEM in `@noble/post-quantum` makes no constant-time claim; `x`, `e_i` and `w` are `bigint`s that can't be zeroised. The derived byte arrays (`dk`, `ss_M`, `K`) are overwritten after use.
- **Nothing on the board carries a posting or complaint yet** (part 3).
- **KEM keys aren't registered yet** (P1-14 part 2), so nothing checks a key's possession before shares are encrypted to it.

## What was built (part 3b)

- [[delivery]], a new spec page:
  - **Records**, each version 1, never pinned: ballot version 1 fixes them ([[versioning]], Three levels, as #93 does for the summed-share message): the share receipt (`0x000c`: the 97-byte receipt statement and its signature), the share posting (`0x000d`: definition, ballot hash, seat, `m`, the ciphertext, unsigned) and the share complaint (`0x000e`: definition, ballot hash, seat, the complaint proof, and a signature under the new tag `abolish/v1/sig/share-complaint` over the 161-byte statement). A proven complaint excludes its ballot whoever signed it; the signature only attributes an unfounded one.
  - **Board-entry version 3**: the same layout as version 1, also allowing share receipts and complaints, never postings (which reach the board only as contract events). Version 1's allowed set is frozen, and version 2 is skipped because `board.json`'s frozen `unknown-version` vector uses it as the version that doesn't exist. A profile pinning ballot version 1 must pin board-entry version 3 (`profile-combination`, verifier 2.3).
  - **Windows**: `DELIVERY_WINDOW` = 2 days and `COMPLAINT_WINDOW` = 5 days (with the bounds `DELIVERY_WINDOW ≥ max(2 · period + deadline + R, W_C) + F` and `COMPLAINT_WINDOW − DELIVERY_WINDOW ≥ W_C + F + R` on P4-1's and P1-18's constants, checked by `deliveryWindowFits`) after `closes_at + l1_inclusion_bound`, constants of the records' version 1, in `W_S`. A board-path record is in time if its segment is at most `s_D` (or `s_K`), the period holding the deadline; a contract-path record if its submission time is at most the deadline itself (`t_D`, `t_K`).
  - **Boarding**: the operator never boards a posting, and boards a receipt or complaint only for a ballot already on the board, in time, one per type, ballot and seat, and only if it passes (attributed receipt; proven and attributed complaint against a contract-path posting). So boarded receipts and complaints carry no chosen bytes beyond a trustee's nonces (postings can: Known-weak), and unfounded complaints (which would publish a readable share) stay off the archive.
  - **Delivery check**: a selected ballot counts only if every qualified seat has a passing receipt (either path) or contract-path posting in time and no complaint about it is proven; a board-path posting is a rejected entry; order-independent; reports `delivery-stray`, `delivery-seat`, `delivery-late`, `share-receipt`, `posting-*`, `complaint-void`, `complaint-proof`, `complaint-unfounded` (attributed) and `receipt-contradicted` (attributed). A seat outside the registered key set needs no delivery, and its share hash is 32 zero bytes.
  - **Direct submit**: a contract path for the three records MUST exist before any election registry is deployed (P1-18), for every ballot, and is the only path for postings, so no operator can withhold one through the complaint window: a posting call can carry the ballot's public part, the contract checks the ciphertext against its share hash and accepts any number of postings per seat, so junk can't occupy a voter's slot. Trustee nodes send every receipt through it.
  - **Client rules** (P2-8), per the owner's 2026-10-12 decision ([[0002-everlasting-privacy]], Decision): a receipt counts only if it passes against the ballot cast; a receipted seat is never posted; the client resubmits its receipts through every path until one is anchored or recorded by the contract (derivable from finalized L1); a seat that isn't receipted is posted only at the voter's explicit choice, after the client says it lowers that seat's long-term privacy, and only through the contract path, keeping only `ct_i` and `m_i` meanwhile.
- [[board]], [[versioning]] (registry rows, board-entry versions, the fixed-not-pinned rule), [[election-definition]] (`profile-types`, deadlines), [[tally]] (the counted set and `W_S`), [[verifier]] 2.3 and 5.9, [[parameters]], [[share-encryption]], [[ceremony]], [[domain-separation]], the spec README and the vectors README.
- `packages/crypto`: `delivery.ts` (the three record codecs, `signShareComplaint`, `shareComplaintStatement`, `deliverySegments`, `deliveryDeadlines`, `checkDelivery` over board-path and contract-path entries, `shareReceiptRecord`), board-entry version 3 in `board.ts` (`encodeBoardEntry` takes the version explicitly, with no default), `PARAMETERS` and the record-type table.
- Threat files T-15, T-17, T-25, T-29, T-41 and T-54.

## Known-weak (part 3b)

- **The verifier doesn't run the delivery check yet.** `packages/verifier` reads board-entry version 1 only (a definition pinning version 3 is unverifiable, `unsupported-version`), and doesn't check `profile-combination` or run `checkDelivery`: P1-19, once the ballot record exists to select ballots from.
- **No contract path for delivery records yet** (P1-18): until it exists, nothing can post at all, and the operator can withhold board-path receipts and complaints, leaving ballots undelivered or invalid ballots counted, unattributed (T-25, T-54).
- **A receipted seat can still go undelivered** if its trustee never sends the receipt and the operator and every contract-path route of the client's refuse the client's copy; the client may not post instead (the owner's decision), so the voter has only the signed receipt as off-board evidence ([[delivery]], Residuals; T-25, T-41).
- **A voter-chosen posting lowers that seat's long-term privacy** to the classical DH (T-15), accepted by the owner on 2026-10-12.
- **Operator breaches of the boarding rules aren't reported yet**: a record the operator should have refused is read and, where it fails, ignored; reporting it against the operator is P1-19's.
- **The zero share hash for an unqualified seat** MUST be enforced by the ballot record's admission checks, which come with the ballot record; until then a ballot can carry `32 · (n − q)` chosen bytes there (T-17). Closed by part 4 (`share-hash-unqualified`).
- **Postings carry chosen bytes** ([[delivery]], Direct submit; T-17): neither the contract nor the public check opens `sealed`, so a voter can archive about `n · (64·m + 36)` bytes per ballot and re-vote (about 66 KB at `MAX_OPTIONS`, `n = 16`). Not mitigated; a proven complaint excludes the ballot but can't remove its postings.
- **`checkDelivery` takes contract-path records with their submission time**, which P1-18's contract-event record must supply; until then no caller has contract-path records to give it.
- **`packages/core` appends version-1 board entries only**: it doesn't read the election's pinned board-entry version yet, so it can't board delivery records (`encodeBoardEntry` now takes the version explicitly, with no default).

## What was built (part 4)

- [[ballot-validity]], Ballot record: record type `0x0002`, version 1, a cast ballot: `definition_hash`, `tier`, `nullifier`, `l1_ref_number`, `l1_ref_hash` and `membership_proof` at fixed offsets (bytes 3 to 363), then `committed_vote`. Every field is bound: the first three and the committed vote by `ballot_hash`, the L1 reference by `M`, and the proof is the one field left out (it is malleable).
  - **Decoding** is strict (tier `invalid-enum`; nullifier, proof points and commitments `non-canonical` at their offsets), and doesn't compare the definition or tier with the election.
  - **Admission**, verifier 5.1 to 5.4 in order: `ballot-stray`, `ballot-tier`, `validity-shape`, `share-hash-unqualified` ([[delivery]]'s zero share hash for a seat outside the registered key set, closing its `32 · (n − q)` chosen bytes, T-17), `membership-proof` (signals from the definition's tier root and scope, the record's nullifier and `M` recomputed from the record), `option-proof`, `sum-proof`.
  - **Casting**: the order the ballot client builds a record in, and that it runs the admission checks on its own record, its proof's verification included, before sending it.
  - **Cast ballots only.** A challenged ballot has no nullifier, L1 reference or proofs, and an election pins one version of `0x0002`, so how a challenged ballot reaches the board is P1-13's (its own type, fixed by the spoiled-ballot opening's version and allowed by a board-entry version, or inside the opening). [[board]]'s payload table says so.
- `packages/crypto/src/ballot.ts`: `BALLOT`, `encodeBallot`, `decodeBallot`, `ballotElection` (the context, from a definition pinning ballot version 1 and a key set `checkCeremonyTranscript` returned for its transcript; nothing else is accepted), `ballotSignals` (the public signals a client proves over) and `checkBallot`. `membership-proof.ts` gains the internal `verifyDecodedMembershipProof`, which takes only proofs its own decoder made, so a record's proof isn't decoded twice.
- Spec edits: [[versioning]] (version 1), [[board]] (the payload row), [[delivery]] (the zero share hash is enforced), [[revoting]], [[receipts]], [[verifier]] 5.4 (the order and the three new codes), the spec README and the vectors README. Threat files T-17, T-28 and T-38.
