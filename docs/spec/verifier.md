# Verifier

What an independent verifier must check to accept an Abolish election result, using chain and IPFS data alone, with our servers and domains offline (G-9, T-36). `packages/verifier` implements this list, and a third party can implement it from this spec in any language. Its inputs, procedure and report are under [Inputs, procedure and report](#inputs-procedure-and-report) (P1-19).

Each check names the threats it closes and the STATUS item that specifies it. A check whose section isn't written yet is still required: until it exists, no verifier can claim the election verified. Checks marked **(P1-3)** take the shape of [[0002-everlasting-privacy]] (accepted by the owner, option B); their sections are written by P1-12 to P1-15.

## Principles

- **Trust nothing served.** Every input comes from L1, the L2, IPFS, the permanent archive or local files, and is checked against L1 anchors or the evidence it carries. Nothing is accepted because an Abolish server said so, and no Abolish server or domain is contacted (T-24, T-49, T-69).
- **Fail loudly.** Each check ends in pass, fail or unverifiable (data missing, a source unreachable, a root not yet settled, or, for the report-only 8.5 alone, not applicable). Unverifiable is never reported as pass.
- **Two kinds of check.** Anyone can post a ballot, so a bad ballot must never fail an election (T-52, T-53), and every conforming verifier must reach the same verdict on the same data (T-36):
  - **Admission checks** decide whether one ballot or opening counts: decoding of the record inside a board entry, 5.1 to 5.5, 5.7, 5.8, 6.1's admission part and 6.2. A failure rejects that entry only. A rejected entry is listed in the report (8.3), never counted and never displaces an earlier ballot (6.1, R4).
  - **Election checks** are everything else: 1.2, 1.3, 2.1 to 2.6, 2.8, 2.9, 3.x, the board-entry envelope and hash chain in 4.1, 4.2 to 4.6, 5.6, 5.9, 6.3, 7.1 to 7.3, 7.5 and 8.1 to 8.4. The election is verified only if every election check passes.
  - **Report-only checks** (1.1, 2.7, 7.4, 7.6, 8.5) never decide the election's verdict. 1.1 and 2.7 because their inputs come from whoever serves them, not from chain and IPFS election data: a served client or display text that doesn't match is reported loudly (1.1 as a separate client-integrity verdict, G-13), and mismatching text is treated as unavailable. 7.4, 7.6 and 8.5 because they attribute and report what the board holds, while the result rests on other checks; 8.5 reports signed claims of destruction, which can't be proven, and making it decide would give any trustee a veto (T-54).
  - An admission check that can't be evaluated (its evidence is missing) never rejects the entry: it makes 6.1, and so the election, unverifiable. The archived evidence for each entry (4.4) must cover everything its admission checks need.
  - Our contracts accept a direct submission only if it passes their framing checks and, for a ballot, its membership proof, so non-members can't post at all, and revert otherwise (P1-18; [[contracts]], Board, Ballots). Framing checks every length, count, offset, enum, scalar and `field<bn254>` and the cheap part of each ristretto255 element's decoding ([[0028-board-contract-checks]], 3B), so no record whose framing is broken reaches an L2 event or the board, and no one can make 4.1 or 5.6 fail by posting junk. An element that passes framing but doesn't decode makes its record a rejected entry, like any other admission failure. The archive keeps nothing beyond the record but the event accumulators' storage proofs, so no transaction's other bytes reach it ([[contracts]], Contract-event record; [[notation]], Result-critical fields; T-17). A record that decodes but fails another admission check is boarded as a rejected entry.
- **Strict decoding first.** Every record is decoded strictly ([[notation]]) before any other check uses it, and rejected entries are reported, never skipped silently (T-31, T-52).
- **Pinned trust roots.** The verifier's release pins what can't be derived from data: the L1 and L2 chain IDs, the addresses of the anchor contract, the forced-ballot relay and our L2 contracts, the anchor's deployed clock (`epoch`, `period`, `deadline`) and anchoring authority ([[contracts]], Board anchor), the canonical L2 portal on L1, the L2 derivation rules it applies with the L2's `max_sequencer_drift` (bounding the registry events' L1 origins, 4.4) and the dispute-game types it counts as permissionless for the close statements' floor (6.3; [[close]], The floor), the release-signing identities, the commit of `main` whose contracts source the deployed contracts were built from (1.2), the long-term identity keys of the named trustees with `k` and `n` ([[0006-trustees]]), each pinned panel's **kind** (`independent`, a panel meeting every rule of [[0006-trustees]] and named by the owner, or `transitional`, held by us during launch) with, per seat, its holder's name and whether the seat is ours ([[0027-trustee-panels-and-live-results]], Part 3; 2.5 and 8.4 read them), and the verification key of every proof system it accepts, per ballot record version (Semaphore's per-depth keys, or the zero-knowledge UltraHonk key of our Noir circuit), built from reviewed source. Changing any of them is a new verifier release (T-64, T-71, T-05). No proof is ever verified under a key taken from election data alone.

## Checks

### 1. Ballot client and contracts

- 1.1 A served ballot client matches a signed, reproducible release: its bytes hash to a release hash signed by the release identity (T-41, G-13; P1-19, P2-8).
- 1.2 The bytecode at every contract address the election uses matches the release build of reviewed source, with the byte ranges of each contract's immutables masked, and every masked word equals the value the release pins for it (the anchor's clock and authority, the registry's deployment addresses and `epoch`) (T-64; P1-18, P1-19, P4-1). The release build is `forge build` of `packages/contracts` at the contracts commit the verifier's release pins (a commit on `main`), by the pinned forge, from `packages/contracts`, with the default profile and the settings in its `foundry.toml`, no `.env` file anywhere from `packages/contracts` up to the repository root, no `FOUNDRY_*` or `DAPP_*` variable and no global Foundry config, run by itself on a fresh runner in a job that runs no npm code (the procedure is in `packages/contracts/README.md`, Release build); it is never the output of the package's own build script, which runs npm code after forge. A runtime-code match alone never passes 1.2: a deployer's own initcode can return the release runtime code after writing any storage and emitting any logs. Until binding each deployment to the release creation code and pinned constructor arguments is specified and checked, 1.2 is unverifiable (`not-implemented`), whoever made the deployment, and the binding MUST be specified before any deployment (T-64; [[contracts]], Board anchor, Known-weak, Constructor effects aren't bound).
- 1.3 Every verification-key hash in the election definition (today only the membership key hash, `abolish/v1/membership-vk`, over the pinned depth-32 Semaphore key, [[membership]]), and every key inside a verifier contract the election uses, equals the pinned key for the ballot version the profile names; a definition naming any other key fails (T-05, T-04, T-64; P1-17b, P1-18).

- 2.4 Its electorate is a group root per tier at a fixed L2 block, and that root matches the root computed from that tier's own group additions on the board, never the L2 state alone, so a tier's root can't be registered under another tier's label. An addition counts toward tier t only if its authorisation binds t's group identifier, the chain ID and the registry address (for Tier 0 the registrars' EIP-712 approvals, [[contracts]], Group registry, from a registry whose logged registrars and threshold equal the ones the release pins, every group of any other failing, replayed by the verifier with its own member count so that a record whose signed position or size disagrees with it fails the definition as `group-history`; for a self-paid Tier 0 group none, since anyone may add to it: its additions are bound to it by the registry's own event, the record's `group_id` in a log of the registry the definition names, under the chain ID the release pins, replayed with the verifier's own count against the index the registry logged, and they rank below every signed group's in the first-occurrence rule ([[contracts]], Group registry, Self-paid additions; [[membership]], Cell tree); for Tier 1 the addition's `k` vouches, whose scopes and messages bind the group identifier, the chain ID and the registry address, counted across every Tier 1 group of the registry in one order as [[vouching]] (Counting across the deployment) specifies, over the registry's archived history (the group's additions on the board being exactly its counted ones, which 4.4 checks, Contract events, Tier 1 boarding), with each vouch's Tier 2 root rebuilt by this check's Tier 2 rules, a definition naming Tier 1 groups of more than one registry failing, and an addition that doesn't count never failing the definition ([[0014-tier1-vouching]]); for Tier 2 the document proof bound to the commitment actually inserted), and the verifier attributes additions by that binding, never by the L2 event's group field alone, so a signed batch can't be replayed into another tier (T-08, T-13, T-06, T-01, T-71; P1-18, P3-2). Each tier's `root_l2_block` is strictly before the L2 block that registered the definition, and a definition with one at or after that block fails, so no root can name additions that weren't public on L2 before voting ([[election-definition]], The electorate is in the past; T-08, T-13, T-25, T-34). Under definition version 7 with `electorate_mode` 2 (rolling; [[0028-rolling-electorates]]; P2-17), each rolling tier's listed groups must exist at its `root_l2_block` with the tier its label names, each is replayed strictly as above (`group-history` for a record that fails; a Tier 1 group is counted by [[vouching]]'s rule instead, only its counted additions appending leaves, and fails only as [[vouching]] states, reaching through the last accepted step), and their additions are taken in chain order into the tier's rolling tier tree ([[membership]], Rolling tier tree), with no first-occurrence rule; a definition whose `root` or `group_size` differs from that tree's root or member count (its distinct live commitments) at `root_l2_block` fails, as does one whose `root_l2_block` is at or after the registering block. - 2.8 Its tally partition is well formed. Under definition version 1 the partition is the tiers only: each cell is exactly one tier of the electorate (2.4), and the partition has exactly one cell for each tier and no other cells, so no tier is repeated, omitted or merged with another; the rule is fixed, not chosen by the author (a rule field in the definition, if it has one, must equal it): each ballot goes to the cell of the tier its membership proof's public inputs fix (5.1, 5.2, 5.3: the tier-binding scope of [[membership]], or the tier bound in the signal; the root alone never decides it, since two tiers may share a root), so no relay or operator can move it between cells; a voter in several tiers has one unrelated nullifier per tier group ([[membership]], Scope), so each tier counts at most one of their ballots, which G-2 allows; so every cell holds only its own tier's ballots and is reported under that tier's label; and a definition version 1 has no regions. Under definition version 3 ([[0019-regional-cells]]) a ballot's region comes only from a membership proof against a per-tier, per-region root fixed in the definition (one root per cell, as in 2.4; the cells' trees of one tier hold disjoint sets of counted leaves (first occurrence) which together are the tier's counted leaves, checked from the board's group additions, so a voter can't choose a cell by choosing which root to prove against), never from a field the voter chooses or can grind, nor from any per-ballot value (the nullifier, a commitment, a VSS commitment, a ciphertext hash, a proof or signal field); the verifier recomputes each cell's admitted electorate as the cell's `members`, as 2.4 recomputes it (a stated value that differs fails), and no cell of a split tier is below `MIN_CELL_ELECTORATE` ([[parameters]]). Version 3 meets this with one cell tree per cell over its regions' groups, the first-occurrence rule (one commitment counts in one cell of its tier), and the fold of [[election-definition]] (Regional cells): each region of at least `MIN_CELL_ELECTORATE` members is a cell, the rest fold into one remainder cell, and a tier whose remainder is below the floor, or that would have one cell, isn't split. The verifier recomputes the fold from the region counts 2.4 checked and fails 2.8 if the definition's cells differ (the `cells` rule checks the same from the stated counts), so the floor binds every cell of a split tier, and a tier that isn't split has none and is flagged by 8.2 when small. A ballot under version 3 (ballot version 2) names its cell's position in the partition, and the verifier takes the cell's tier, root and scope from the definition (5.1 to 5.3; [[ballot-validity]], Admission (version 2), `ballot-cell` for a cell the partition doesn't have), so the remainder cell shows the cell, never the region within it. The floor bounds who may vote in a cell, not how many do: a cell can still hold one counted ballot, which 8.2 flags (T-16). Under definition version 7 with `electorate_mode` 2 the partition is one cell per rolling tier, in `rolling_electorate`'s order: a rolling tier is never split, its ballots go to its cell by the tier their proof's scope binds (the rolling scope binds the tier, [[membership]], Scope), and there is no floor, so 8.2 flags a small tier as for an unsplit one ([[0028-rolling-electorates]], Regional cells). Every tier is opened and small ones are flagged (8.2): tiers are never merged or withheld ([[0006-trustees]], Small cells); a coarser total is never opened to fill a gap (one partition, [[0002-everlasting-privacy]]; T-16). Trustee nodes run 2.8 before releasing any share and the ballot client runs it before casting, because a failure found after the tally can't take an opening back. This is an election check: a malformed partition fails the election (T-01, T-14, T-16, T-29, T-36, T-45; P1-10b, P1-15).
- 2.9 Under definition versions 4 and later (each lists `receipt_keys` as version 4 does), every key in `receipt_keys` judges the election ([[election-definition]], Receipt keys): its word in the receipt-key record of the anchor the release pins for `l1_anchor` ([[contracts]], Board anchor, Receipt keys), proven from L1 state at the verifier's finalized block `B`, shows it registered before `opens_at` and not retired by then. A word the release code can't write ([[contracts]], Board anchor, Receipt keys) fails it (`receipt-key-record`). Keys are judged in list order, and the first failure is reported. Versions 1 and 3 list no keys, so 2.9 has nothing to check, and their receipts are never evidence a third party can attribute ([[receipts]], Receipt keys). So the keys that judge an election's receipts are the anchoring authority's, fixed before voting opened, and a release, operator or creator can't add one (T-26, T-69, T-71; P1-13b).

### 3. Key ceremony

- 3.1 The ceremony transcript decodes strictly, its hash matches the one registered with the trustee keys on L2, and every proof in it is checked, with its Fiat–Shamir context (chain ID, registry address, election identifier, the stub hash recomputed from the definition ([[election-definition]], Stub hash and the ceremony), panel and the run identifier) rebuilt from the election being verified, never read from the transcript, so one election's ceremony can't be registered for another (T-37, T-40; P1-14). The registration itself is the trustee registry's `CeremonyRegistered` record for the definition's stub and panel: the verifier checks each approval in it against the panel its release pins and counts the distinct seats whose approvals verify, requiring at least the quorum its release pins for that panel, never the contract's own `q`, which it compares with its pin and reports if they differ ([[contracts]], Trustee registry; T-71, T-37, T-14). The record also carries the registered key set the approvals sign, which the board takes signing keys and qualified seats from ([[0028-board-contract-checks]], 2B): the verifier recomputes its `key_set_hash` from the record and fails 3.1 with `key-set-mismatch` unless it equals the `key_set_hash` of the key set its own transcript check returns ([[ceremony]], Key set hash), so a set a quorum signed that isn't the transcript's fails the election rather than passing (T-37, T-14). **(P1-3)** The verifier computes the qualified set itself, from its own check of every proof and complaint, never from the transcript's claim, and recomputes from that set alone the registered key set of [[0002-everlasting-privacy]] (each trustee's KEM and signing keys); plurality and approval have no joint public key (a ranked-choice mix key, if the follow-up ADR in [[0003-tally-scheme]] needs one, is checked as that ADR says). A failed proof is non-fatal only for a trustee excluded before the definition was registered; if the key set or panel bound into the definition includes any trustee whose proof fails, or differs from the recomputed one, the election fails (rogue-key attack, T-40, T-14, T-37). Every trustee message in the ceremony (its registration, its ceremony entry registering its per-election keys, possession answers and complaints) is signed by its trustee's pinned identity key, and every later statement (receipts, shares, tally shares, destruction) by the per-election signing key registered in that entry ([[trustee-identity]], Which key signs what); only signed failures are attributed to a trustee (T-37, T-29). Under definition versions 6 and 7 with an author panel, 3.1 also checks the author panel's ceremony ([[ceremony]], Author panel): its transcript is the board's copy of the bytes the definition's `author_transcript_hash` binds, found as the default panel's is, checked with the context rebuilt from the definition (`author_stub_hash` and `author_panel_id` recomputed from it) and the author keys the definition lists, never a release's pins (only `duplicate-key` also reads the pinned default keys, [[ceremony]], Author panel); and its registration, which no contract records, is the author approvals records on the board, which must approve it (at least `max(k_A, n_A − 1)` distinct author seats, each approval checked against the key set this verifier's own check returns): records that don't fail 3.1 with `author-approvals`, and a copy with none leaves it unverifiable with `author-approvals-missing`, as a missing transcript does. The author panel's registered key set is that check's output, and nothing on L2 is compared with it: the default panel's registration binds it through `stub_hash`, which keeps `author_transcript_hash` (T-37, T-17, T-14; P2-16).
- 3.2 At least the number of trustees the panel rules require took part, and every complaint and disqualification in the transcript is resolved as the spec says. [[ceremony]] (Transcript check) specifies 3.1 and 3.2 for plurality and approval: the transcript-level codes `ceremony-order`, `ceremony-shape`, `ceremony-signature` and `ceremony-quorum` (fewer than `k` qualified seats), each seat's disqualification reasons, and the registered key set. Under [[0006-trustees]] rule 7, adopted by the owner on 2026-10-12, at least `n − 1` seats must take part: below `max(k, n − 1)` qualified seats 3.2 fails with `ceremony-participation` (Key ceremony; T-40, T-54; P1-14). With an author panel the same holds for it, with `k_A` and `n_A`: below `k_A` qualified author seats 3.2 fails with `ceremony-quorum`, and below `max(k_A, n_A − 1)` with `ceremony-participation`, each naming the author panel, so neither panel's margin can be shrunk at its ceremony ([[0027-trustee-panels-and-live-results]], Liveness; T-54; P2-16).

### 4. Board, anchors and archive

- 4.1 Every board-entry envelope decodes strictly (the record it carries is an admission check), every entry names the election and its own position, segments never decrease, spoiled-ballot openings are in canonical order, and the hash chain is unbroken from the first entry to the last ([[board]], Board checks; T-23, T-31, T-42; P1-16).
- 4.2 Every board checkpoint anchored on L1 is recomputed from the board: it ends at its segment's boundary, its chain head and Merkle root match, and its `object_cid` and `hashes_cid` name the segment object and entry-hash list of its last entry's segment. Every segment holding entries has an anchored checkpoint ([[board]], Board checks; T-23, T-24; P1-16, P4-1).
- 4.3 Every archive manifest reachable from L1 `archiveLocator` fields (the pinned anchor's latest locator in state and its `ArchiveLocated` logs, [[contracts]], Archive locator) and from the manifest chain is found and matches what it names; any missing link is reported ([[0005-permanent-archive]]; T-51; P1-19, P4-3).
- 4.4 Every one of our contracts' L2 events that the election's checks use has a board entry carrying its contract-event record (`0x0008`), which passes the event check of the contract-event version its profile pins against the definition's L2 contracts (`unknown-contract`, `unknown-event`, `event-topics`, `event-data`; [[contracts]], Contract-event record): the events that name the election, each of its tiers' group creation (which fixes the tier, 2.4) and group additions and removals up to each `root_l2_block`, and its panel's key and ceremony registrations (2.5, 3.1). A Tier 1 group's additions on the board are exactly its counted ones: each `Tier1MemberAdded` naming the group that [[vouching]] (Counting across the deployment) counts, one per leaf of the tier tree, and a boarded one of the group in those blocks that doesn't count fails; other groups' additions and the Tier 2 history the count reads need only be in the archive (Contract events, Tier 1 boarding; T-52, T-53; P3-3). The archived event sequence of each contract, as contract-event records that each pass the event check, which for a contract shared by many elections includes every other election's events, reproduces that contract's on-chain event accumulator at every anchored period and at close under the rules of [[contracts]] (Event accumulator, Verification) and their codes (`index`, `order`, `block-range`, `accumulator`), against the storage proofs that are the only evidence archived for them ([[contracts]], The shared event sequence; Contract-event record, Evidence). The L1 origin that the election's `ElectionCreated` and `DefinitionRegistered` events carry is one finalized L1 block, no later than the event's L2 timestamp and no more than the pinned `max_sequencer_drift` before it, and, for the registration, never earlier than the same election's creation's ([[contracts]], Election registry, Events, The L1 origin). The check passes with an annotation naming which proof type settled each output root it relied on (TEE-only or ZK), and the report lists every TEE-only root (8.3) ([[0005-permanent-archive]], T-71; P1-18, P1-19).
- 4.5 Every event one of our contracts accepted because of its caller (a forced ballot relayed from L1, the only such event, P1-18 part 4c) names its L1 relay call, and matches exactly one call our relay recorded, read from L1 state: the relay's stored call hash for the event's index, proven at the verifier's finalized L1 block, equals the one recomputed from the event's index, L1 block, stamp, gas limit and whole record ([[contracts]], L1 relay, Verification). One that matches no call (forged by L2 governance) fails (`relay-unmatched`), and so do two events naming one call (`relay-duplicate`); a recorded call with no event is reported, never failed. No transaction is archived ([[contracts]], Contract-event record), so any other deposit reaching our contracts is checked by the evidence its event carries, like any other call, since nothing trusts its sender (T-71, [[0004-l2-choice]] as amended by [[0025-contract-event-evidence]]; P1-18, P1-19).
- 4.6 The board was available to the trustees before any result: for the ballot extent (the board through `C_A`, the counted checkpoint with the largest segment at or before `s_A`) and the counted extent (through `C_S`, at or before `s_S`), each panel's threshold of qualified seats signed an availability attestation (record type `0x001b`) naming that checkpoint, through the L2 contract path only, with a submission time by `t_A = c_I + F` and `t_A' = t_S + A' + F` respectively; otherwise the election fails `unavailable`, attributed to no single party, and the report lists the seats that attested, those that sent a availability complaint (`0x001c`) with the CID it names, and those that did neither. It reads only L1 and the L2's events, replayed against the board contract's event accumulator proven at or after each deadline, never the board copy, so it is decided whether or not a copy can be found, and a point whose evidence isn't held is unverifiable, never failed ([[availability]], Availability check; [[0029-board-data-availability]]; T-24, T-25, T-53, T-54; P4-3).

### 5. Ballots

- 5.1 Every ballot's membership proof verifies against the electorate root for its tier in the election definition (under definition versions 3 and 4, the root of the cell a version-2 ballot names; under definition version 5, of the cell a version-3 ballot names; under a rolling definition version 7, never a root the definition states but the root of the step a version-5 ballot names, of its cell's tier, which the verifier computes itself from the listed groups' events, once that step is one the poll accepts (`root-step-range`, and on the contract path `root-step-mismatch` for a supplied root other than it; [[ballot-validity]], Admission (version 5); [[membership]], Rolling checks)), under the pinned protocol-wide depth-32 verification key, as [[membership]] (Checks) specifies; a definition with a tier root of 0 fails, since Semaphore's circuit lets anyone prove membership of root 0 (T-04, T-05, T-13; P1-17, P1-17b).
- 5.2 Its nullifier uses the scope the verifier derives from the election-definition hash, the tier and the tier's root (under definition versions 3 to 5, the cell's tier and root) (`abolish/v1/nullifier-scope`, [[membership]]), or under a rolling definition version 7 from the definition hash and the tier alone (`abolish/v1/rolling-nullifier-scope`, [[membership]], Rolling scope), never a scope from anywhere else (T-12, T-13, T-04; P1-17).
- 5.3 The proof's message is `M` of [[revoting]] (Message), recomputed from the ballot record and the definition: it binds the ballot hash, the election definition, the ballot's tier (under ballot versions 2 to 5 its cell's tier, the cell bound through the ballot hash, and under version 5 the step too) and the L1 block the re-vote rule ranks by, so the proof can't be moved to another ballot or replayed (T-38, T-32; P1-12, P1-13, P1-17).
- 5.4 Every validity proof verifies, with its Fiat–Shamir challenge recomputed from the full statement table, including the ballot's nullifier ([[domain-separation]]), and constrains the ballot to the election's rules: no over-vote, no negative vote, the approval limit if any, and under ballot versions 3 to 5 each question's limits, by one range proof per question under `abolish/v1/fs/ballot-validity/question-sum` (under ballot versions 4 and 5 over each vote commitment `C_j = E^D_{j,0} · E^A_{j,0}`, the product of its two halves, computed and never carried, [[ballot-validity]], Ballot record (version 4)), with `option-proof` naming the first failing flat option and `sum-proof` the first failing question ([[ballot-validity]], Checks: `validity-shape`, `option-proof`, `sum-proof`; Checks (version 3); T-28, T-30, T-32; P1-12, P2-14). **(P1-3)** [[ballot-validity]] (Ballot record, Admission) fixes the order and codes of 5.1 to 5.4 for ballot version 1, and adds `ballot-stray` (another definition hash), `ballot-tier` (a tier the definition doesn't list; under ballot version 2, `ballot-cell`, a cell the partition doesn't have, Admission (version 2)) and `share-hash-unqualified` (a share hash other than 32 zero bytes for a seat outside the registered key set, [[delivery]], Notes; T-17).
- 5.5 The ballot entry is inside the poll's window by its own path, under the close rule of [[close]] ([[0030-close-rule]]): an ordinary contract-path ballot by its L2 block's timestamp, `opens_at ≤ τ_b ≤ closes_at`; a ballot forced through our L1 relay by the L1 timestamp its matched relay call recorded (4.5); a board-path ballot by its entry's segment, at most `s_A = period(closes_at) + 1` (`window-before-open`, `window-after-close`, `window-boarded-late`, the last also reported against the board operator). Each copy of a ballot is judged by its own entry, before repeats (5.7). Whether an ordinary ballot in a block at or before close was in fact made before it is the close check's (6.3), which uses only L2 data derived from finalized L1 data (T-35, T-50, T-45, [[0004-l2-choice]]; P1-18).
- 5.6 Direct-submitted ballots on L2 are on the board, and one the close rule (5.5) admits is on it within the counted extent (`segment ≤ s_S`, [[tally]], Tally window), counting only a board entry whose contract-event record passes 4.4; a ballot found on L2 but missing from the board, or first so boarded after the counted extent, fails the check, attributed to the board operator unless its L2 block became derivable from finalized L1 too late to board in time, which is a settlement overrun, unattributed ([[tally]], Tally window; T-25, T-50; P1-18, P3-5).
- 5.7 A repeat of an earlier admitted ballot is rejected (rejected entries don't count as earlier ballots, R4): the same tier, nullifier and message `M` (5.3), whatever the entry's other bytes; Groth16 proofs are malleable, so byte comparison alone isn't enough ([[revoting]], Selection step 1; T-38; P1-13).
- 5.8 The L1 block the ballot names is no older than an hour before `opens_at`, is on the finalized L1 chain with the hash the ballot gives, and has a timestamp at or before `closes_at` (`l1-ref-before-open`, `l1-ref-after-close`, `l1-ref-unknown`, checked in that order); under ballot version 5 the step the ballot names then lies in the window before that block, `t − ROOT_WINDOW < τ_n ≤ t` for its timestamp `t` (`root-step-stale`, `root-step-future`; [[membership]], Root clock and steps). A ballot naming a block beyond the finalized head is pending only until L1 finalizes a block after `closes_at`, and rejected after that, so no reference can keep an election unverifiable, and for this check a verifier of a closed election needs L1 only from just before an hour before opening to the first block after close ([[revoting]], Admission; T-45, T-35, T-53, T-36; P1-13).
- 5.9 Every share receipt (`0x000c`), posting (`0x000d`), complaint (`0x000e`), share-receipt batch (`0x0016`), share-complaint batch (`0x0017`) and obligation root (`0x001a`) in the counted extent decodes strictly under the version the ballot version fixes (a record that doesn't is a rejected entry, listed in 8.3, and so is a posting, a batch or a root anywhere but in a contract event, and a batch or a root under ballot versions 4 and 5, which fix none), and the delivery check of [[delivery]] runs over them for every selected ballot (under ballot versions 4 and 5, with delivery records of version 2, over every seat of both panels, each record checked against its own panel's share hashes and registered key set, [[delivery]], Version 2): a share receipt is checked against its ballot's recomputed ballot hash and `share_hashes` and the seat's registered signing key, and so is each pair of a receipt batch, read as the receipt it states, with the batch's one signature, and each entry of a complaint batch is read as the complaint it states, attributed by its batch's signature, each obligation root is read once and, if its signature verifies, it fills its seat's slot for its kind, is in time, is within the bound `2M` and its leaves are available by the counted-extent attestations and consistent with it, each of its leaves as the receipt or complaint it states (`root-signature`, `root-repeat`, `root-count`, `root-withheld`, `root-inconsistent`; [[delivery]], Leaf availability), a contract-path posting against the ballot's `share_hashes` and the seat's registered KEM key (2.5, 3.1), and a complaint against a passing contract-path posting, as [[share-encryption]] specifies (Intake and receipts: `share-receipt`; Public posting: `posting-hash`, `posting-proof`, `posting-encapsulation`; Complaints: `complaint-proof`, `complaint-unfounded`), each only if it names this definition, a qualified seat and is in time (`DELIVERY_WINDOW`, `COMPLAINT_WINDOW`, by its segment through the board path and by its submission time through the contract path: `delivery-stray`, `delivery-seat`, `delivery-late`). A selected ballot stays in the counted set only if every qualified seat has a passing receipt or contract-path posting in time and no complaint about it is proven, attributed or not; otherwise it counts nothing, with no fallback to an earlier one (6.1). A failing receipt, posting or complaint is ignored and never excludes a ballot; an unfounded complaint is reported against the trustee its signature attributes it to, and a passing receipt contradicted by a proven complaint against its seat (`receipt-contradicted`) ([[delivery]], Delivery check; [[tally]]; T-41, T-29, T-15, T-25; P1-12).

### 6. Re-voting and spoiled ballots

- 6.1 For each tier and nullifier, at most one ballot is counted, chosen by the re-vote rule of [[revoting]] ([[0011-revote-rule]]): the admitted ballot naming the highest L1 block counts, and two distinct ballots naming that same block tie and count nothing. Its admission part (5.7, 5.8) is an admission check, and the rest is an election check. The rule meets R1 to R6, R6 with the close rule's accounting for its wait ([[close]]); any later rule MUST meet all of them too (T-33, T-38, T-45, T-25, T-23); [[revoting]] (Requirements) shows how:
  - **R1 Replay.** A replay of any earlier ballot of the nullifier is rejected, whatever its bytes. Groth16 membership proofs can be re-randomised by anyone without the witness, so byte comparison isn't enough (see 5.7).
  - **R2 No freezing.** No value chosen when a ballot is cast can stop a later ballot by the same voter from counting. A coercer who watches one cast must not be able to make it final.
  - **R3 Order independence.** The counted ballot doesn't depend on the order in which the board operator writes unanchored entries, or on whether it withholds an earlier ballot until later, alone or together with a coercer. This holds whether ballots arrive through our API or by direct submit.
  - **R4 Stable admission.** An entry that fails admission never changes whether another entry is admitted. An exclusion decided later (a complaint after close, say) never re-evaluates later ballots.
  - **R5 Client state from anchors.** Whatever state the client needs to cast a valid re-vote, it takes from anchored board data or L1 data it has checked itself, or from its own records, never from a server's claim.
  - **R6 Liveness.** At any time up to close, an honest client can cast a re-vote that will count after a wait of at most a stated bound, and the close rule accounts for that bound. [[revoting]] states the wait: about 3 L1 slots, during which a watched voter can void the watched ballot with a tie, and the close rule ([[close]]) takes it from the last moment a ballot counts: in an L2 block by `closes_at` on the ordinary path, in an L1 block by `closes_at` through the relay.
  - **Visibility.** A re-vote is public: anyone who has seen one of the voter's ballots or receipts, and so knows the nullifier, sees that the voter voted again, when (to the L1 block) and how often, and whether a tie voided a ballot (T-45). Deniable re-voting would need hidden nullifiers and an ADR (Achenbach, Kempka, Löwe and Müller-Quade, USENIX JETS 2015).
  - Settled by [[revoting]]:
    - a selected ballot that fails a later check counts nothing, with no fallback to an earlier one ([[0002-everlasting-privacy]]), so complaints can't revert a re-vote;
    - spoiled ballots never take part;
    - selection is per (tier, nullifier): the scope binds the tier and its root, so one secret in two tier groups yields two unrelated nullifiers, even when the two groups have the same root, and a person's ballots in different tiers are neither linked nor ranked against each other ([[membership]], Scope; T-13). **(P1-3)**
- 6.2 No spoiled ballot is counted, and every published opening is checked and reported. A challenged ballot is never boarded on its own: its core travels inside a spoiled-ballot opening record (`0x0003`), which never enters 6.1 or the tally, so an opening can never spoil, count or displace a cast ballot ([[challenge]]; [[0021-challenged-ballots]]). Each opening in the sealed extent decodes strictly under the version the profile pins (2.3) and is checked against the core it carries and the registered key set, never against a board entry: the opening rebuilds every VSS commitment and every registered seat's ciphertext and share hash (`opening-stray`, `opening-tier`, `opening-shape`, `opening-unqualified`, `opening-vss`, `opening-ciphertext`, in that order; under opening version 2, which opens the cores of ballot versions 2 and 3, `opening-cell` in place of `opening-tier`; under opening version 3, which opens ballot versions 4 and 5's cores, the same checks over both halves and both panels' seats), and a passing opening reports its tracking code (the core hash, under the pinned ballot version) and the vote it opens to, flagged `opening-vote-outside` if no valid ballot could carry it, naming the first question outside under opening version 2 ([[challenge]], Checks; Opening version 2). Openings are boarded only through the board path, in segments after the counted extent's last, `s_S`, up to the period containing `t_S + OPENING_WINDOW` (`opening-early`, `opening-late`), never when it opens a commitment of a ballot admitted in the counted extent, at any option: under an equal `definition_hash`, a ballot commitment equal to some opened `C_j`, or to `h^s` or `g · h^s` for a scalar `s` the opening reveals other than the public 0 and 1 (any polynomial coefficient, any seat's share, any seat's `e_i` or `w_i`; [[challenge]], Opened commitments; under opening version 3 also each `r_j` and each out-of-rules `v_j`, and a version-4 or version-5 ballot either of whose halves' constant terms equals any VSS commitment of the opening, [[challenge]], Opening version 3), never decided by the tracking code or the whole `vss`, since an opened commitment or its randomness can be cast under other share hashes, another tier or re-blinded coefficients (`opening-cast`, which would open a counted vote), and never twice for one core (`opening-repeat`). Every one of these is a report, attributed to the board operator as [[challenge]] (Publication) says, and none fails the election or changes what counts. Publishing an opening is opt-in and off by default: the default check runs on the voter's own second device or a checker they choose, against the tracking code it recorded before the cast-or-challenge choice, with the opening handed over directly (QR code or file), never through our API (T-42, T-44). The board orders openings canonically within each period ([[board]], Spoiled-ballot openings), so an opening's timing and position link it only to a period after close. Residual (T-12, T-47): a published opening can still be linked to its voter through the publisher's network metadata (T-11), and it usually shows the voter's real choice; anyone holding an opening can cast its core under their own nullifier ([[challenge]], Residuals; T-42, T-45, T-47; P1-13). **(P1-3)**
- 6.3 The close check: the default panel's seats each sign a close statement (record type `0x0015`) naming `L_δ`, the last finalized L1 block at or before `closes_at + δ`, and the L2 head derivable from L1 data up to it; the close head `B` is the `k`-th largest claim among the seats whose valid statements agree with each other. With `B`, each cell's counted set is recomputed from the counted extent's admitted ballots without the ordinary ballots in blocks after `B`, removed before repeats are resolved; if any cell's counted set differs from the one 7.1 counts, the election fails `close-contested`, unattributed, since a ballot that may have been made after close would change the result. `B` never decides which ballots count. With fewer than `k` such seats there is no `B`: the check passes and the report says the close is unchecked, naming the seats that sent no counted statement and listing the counted ballots with only ordinary copies. Equivocation and a false `L_δ` are attributed to their seats, and claims below a permissionless dispute game's floor are reported against them without leaving `B`; disagreeing claims are always listed, since they prove a false one without L1 data ([[close]], Close head and Close check; [[0030-close-rule]]; T-35, T-45, T-50, T-53, T-54, T-36, T-71; P1-18).

### 7. Tally

- 7.1 The aggregates are recomputed from the selected ballots alone, selected from the counted extent (the entries with `segment ≤ s_S`, [[tally]], Tally window; nothing in a later segment changes them), per cell of the registered partition (2.8) and per option, with per-tier and other coarser totals derived from the cells ([[tally]], Aggregates and Coarser totals; T-29, T-08, [[0003-tally-scheme]]; P1-15). If a cell's counted set (selection, delivery and complaints), computed over the whole sealed extent with each record's window applied by submission time, differs from the one over the counted extent, the election fails `tally-late`, attributed to the board operator for an entry it could have boarded in time and otherwise unattributed as a settlement overrun, never to a trustee; a late entry that changes no counted set fails nothing ([[tally]], Tally window and Opening checks; T-25, T-45, T-29, T-50). **(P1-3)**
- 7.2 Each cell's published opening, one `(Σv, Σr)` per option, signed or not, must open the product of that cell's ballot commitments with a count of at most the cell's counted ballots, giving the published result; a cell with no such opening fails the election (T-54), and two different passing openings of one cell fail it as evidence that binding is broken. Trustees' summed shares are never on the board: they go only between trustees, which check each against the product of the cell's public VSS commitments before combining any `k` ([[tally]]: `tally-missing`, `tally-opening`, `tally-conflict`, `tally-range`, under definition version 5 `tally-question-range`, and `tally-aggregate` per opening; [[0015-tally-publication]]; [[0002-everlasting-privacy]]; T-29, T-14, T-15; P1-15). A passing opening counts whether or not its signature attributes it to a seat; a failing one is attributed only as 7.3 says, and an unattributed failure is no one's ([[tally]], Opening record). Under tally-opening version 3 (an author panel), each panel's partial openings are checked against that panel's aggregate, a cell lacking either panel's passing partial opening fails `tally-missing` or `tally-opening` with that panel, the author panel checked first, or `tally-author-late` when the default panel's is missing while some cell lacks an author opening boarded by the author deadline, and the count, the sum of the two, is what `tally-range` and `tally-question-range` check and the result reports ([[tally]], Opening checks (version 3); [[0027-trustee-panels-and-live-results]], Part 1, Tally). Ranked-choice decryption shares get their checks from the follow-up ADR in [[0003-tally-scheme]]. **(P1-3)**
- 7.3 Every tally opening (record type `0x0006`) in the board's sealed extent decodes strictly under the version the profile pins (2.3); one that doesn't is a rejected entry, listed in 8.3, and opens no cell, so a cell left with no opening fails 7.2 (`tally-missing`). Each opening is sorted into the openings of a cell of the registered partition or a stray opening, by its `definition_hash` and `cell`, and attributed to its `signer` only if its signature verifies under that seat's per-election signing key registered by the ceremony (3.1); under tally-opening version 3 an opening is also sorted by its `panel` and attributed only to a seat of that panel, by that panel's registered key set (3.1 and 3.2 per panel; [[tally]], Opening record (version 3)). An opening whose `aggregate_hash` isn't its cell's over the recomputed counted set is reported `tally-aggregate`, attributed like any other failing opening as an opening over a set other than the counted extent's, and never passes ([[tally]], Opening record; T-29, T-31; P1-15).
- 7.4 Every opening on the board is for a cell of the partition registered in the election definition, per option, over the selected ballots ([[0002-everlasting-privacy]], [[0006-trustees]]); any other opening, such as one for an individual ballot or for overlapping sets whose difference is one ballot (which fails `tally-opening` as an opening of its cell), and every stray opening (another election's definition hash, or a cell the partition doesn't have), is reported with the trustee its signature attributes it to, or as unattributed (7.3); a summed share found on the board ([[0015-tally-publication]]) is reported as an unattributable disclosure, never against its signer alone: its sender, every recipient, anyone who seized a trustee before destruction and anyone who later decrypts a harvested copy hold it (T-14, T-15, T-16, T-29; P1-15). Every tally opening in the sealed extent that the boarding rule of [[tally]] (Opening record, Boarding) refuses (a failing, unattributed or stray one, or a second by the same seat for the same cell, and under tally-opening version 3 for the same panel, or a default partial opening boarded before every cell of the partition has a passing author one, `tally-early`) is also reported against the board operator. This check reports and attributes; it doesn't fail the election, whose result rests on 7.1 to 7.3.
- 7.5 Under a live definition (version 6 or 7 with `results_mode` 2), the running totals. The verifier recomputes the scheduled snapshots, their L1 heads, every cell's running sets and each tier's release choice from the sealed board, the definition and finalized L1 alone, never from a release, a coordinator or the operator ([[tally]], Live results: Schedule, Running set, Release choice), and takes each cell's first passing running opening of a chosen release as the cell's running totals at that release ([[tally]], Running opening record, Which running openings are a release's). Two different passing openings of one release and cell fail the election (`running-conflict`), as evidence that binding is broken, which the final tally's opening rests on too (7.2); so does a passing one whose count of an option exceeds the running set's size (`running-range`), or, per question, whose total lies outside the question's limits times that size (`running-question-range`), neither of which binding allows, since every entering ballot passed its validity proofs (T-29, T-16). Nothing else about releases fails the election or changes its result, which rests on 7.1 to 7.3: a chosen release with no passing opening in a cell is skipped, and an opening the release choice didn't choose is a breach 7.6 reports. Under a sealed definition there are no releases and 7.5 passes ([Releases](#releases); P2-15).
- 7.6 Every running opening (record type `0x0018`) in the board's sealed extent decodes strictly under the version tally-opening version 2 fixes; one that doesn't is a rejected entry, listed in 8.3. Each is sorted into an opening of a chosen release in a cell or outside the schedule, attributed to its `signer` only if its signature verifies under that seat's per-election signing key registered by the ceremony (3.1), and judged against the boarding rule ([[tally]], Running opening record, Boarding). Every running opening that rule refuses (a stray, unscheduled, failing or unattributed one, or a second by the same seat for the same release and cell) is reported against the board operator, and against the seat its signature attributes it to, except a replay of a message that seat already signed; one outside the schedule that opens the running set at the snapshot it names is also reported as a disclosure the batch rule never bounded (T-16, T-29, T-17, T-15). The report lists each tier's decisions and releases, each cell's running totals per release with the seats that signed them, and each tier's totals at a release where every cell has some ([[tally]], Coarser totals); a tier's running totals are never summed with another tier's. This check reports and attributes; it doesn't fail the election ([Releases](#releases); P2-15).

## Inputs, procedure and report

How `packages/verifier` runs the checks above and reports them (P1-19). This section grows with the checks: today the verifier reads local inputs, can read the anchors and `now` from an L1 state proof and the election identifier, pinned version and anchor address from the election definition, and runs 4.1, 4.2, the decoding and well-formedness part of 2.1, 2.3's profile combination (Definition), 8.5's not-applicable case, 4.4's event check over the board's contract-event records ([Contract events](#contract-events)), which can fail 4.4 but never pass it, and, given a pinned panel, the key-ceremony transcript check: 3.2, and the parts of 2.5 and 3.1 that need no L2 state ([Key ceremony](#key-ceremony)), then ballot admission, the openings and, for format 5, selection, delivery, the close check, the tally checks and 8.5 as far as the bundle decides them, and 4.4's L1-origin checks (the sections below). Every other check is reported unverifiable with `not-implemented`, so no run can report an election verified yet. The bundle and the report are tool formats, not protocol bytes: nothing hashes, signs or anchors them. They are versioned so that a reader rejects a format it doesn't know.

### Bundle

A run reads one bundle: a directory with two files, `bundle.json` and the board copy, either `board.bin` or `blocks.car` to read it from by CID ([Board by CID](#board-by-cid)). A directory holding both is rejected, whichever the verifier could read, and so is one holding neither, unless the run reads the copy by CID from gateways (Board by CID, Gateways), which a directory holding `board.bin` is also rejected with. Five formats exist: format 1 gives the anchors and `now` as they are, format 2 gives the L1 evidence they are read from ([Anchors from L1](#anchors-from-l1)), format 3 is format 2 with the election definition in place of the election identifier, the pinned version and the anchor's address, which are read from it ([Definition](#definition)), format 4 is format 3 with the trustee panel the release pins, which the key-ceremony checks run against ([Key ceremony](#key-ceremony)), and format 5 is format 4 with a run of finalized L1 headers, which ballots' L1 references (5.8) are judged against ([L1 references](#l1-references)).

`board.bin` is the board copy: `encode(entry_0) ‖ encode(entry_1) ‖ …` in index order, which is the segment objects of [[board]] concatenated in segment order. The verifier splits it by the version-1 entry layout: 47 fixed bytes (record header, `election_id`, `index`, `segment`), then the payload's `u32` length `L`, then `L` bytes, so each entry is `51 + L` bytes. Splitting stops at the first entry where fewer than 51 bytes remain, or fewer than `L` bytes after them. The entries before that point are the copy the verifier holds. The count of bytes from that point on is reported as `unreadableBytes`, and those bytes are never decoded. Splitting reads only lengths, and it splits an entry whose `L` is over `MAX_BOARD_PAYLOAD` ([[parameters]]) like any other: the bytes are already held, and 4.1's strict decode fails it (`decode`, `length-over-max`), so an operator who anchors one answers for it rather than leaving every copy short. The header, fields and payload are judged by 4.1. Since the board checks ignore every entry past the anchored extent ([[board]], Board checks), unreadable bytes past it change nothing. Unreadable bytes inside it leave the copy short (`checkpoint-missing`, unless an earlier board check fails first), which is unverifiable from that copy (T-53). `MAX_BOARD_PAYLOAD` bounds what is admitted to the board, not what a verifier hashes: the board checks hash every entry inside the anchored extent before decoding any, so an anchored entry with a length near 2^32 is hashed in full (up to 4 GiB). Only the anchoring authority, or a mirror serving bytes within the anchored extent, can cause that, and it costs the verifier time, not its verdict.

**Residual: anchored encodings `board.bin` can't carry.** The split is the only one a self-delimiting concatenation allows, so an entry the operator hashed and anchored with bytes past its payload (or any other encoding that doesn't split back into itself) can't be represented in any copy. Every copy then fails `copy-mismatch` or `checkpoint-missing`, and the election stays unverifiable for good, never failed, with nothing naming the operator. This is the same outcome as [[board]]'s withheld or forked tails (Residuals), and the same candidate fix closes it: bind a content address of each segment object into what is anchored (P4-1, P4-3), so an anchor that names no splittable object is provably the anchoring authority's.

`bundle.json` is UTF-8 JSON, an object with exactly these members. Invalid UTF-8, a byte-order mark, and an object anywhere in the file that repeats a member name all reject the bundle, so no two readers can take one file for different inputs:

Format 1 has `now` and `anchors` and no `l1`; format 2 has `l1` and neither of the others; format 3 has `definition`, `clock` and `l1` (without `anchor`) and no other member, format 4 has those and `panel`, and format 5 has format 4's and `l1Blocks`, so the definition is the only source of the three values it gives. The definition's bytes are only held here: decoding them is check 2.1, so a definition that doesn't decode is reported, never a rejected bundle (except an empty one, which bundle hex forbids). Hex is lowercase with a non-zero, even number of digits, exactly 64 for 32 bytes, 40 for an address, 66 for a panel key and 216 for a checkpoint, and a header must be an RLP list of at least 15 byte strings with a 32-byte parent hash and state root and canonical integers of at most 8 bytes for its number and time. An integer is a JSON string of decimal digits with no sign and no leading zero (except `"0"`), within its type, and `period` is at least 1. Any other member, value or shape, or a missing or unreadable file, or one that isn't a regular file (a device or a FIFO, which may never end), rejects the whole bundle before any check runs, and a rejected bundle has no report: it isn't evidence about any election. A checkpoint's position in `anchors`, from 0, names it in the report.

**Every bundle input is unauthenticated, or as authentic as the inputs it is proven from.** The clock, the election identifier and the pinned version should come from the election definition (P1-10b) and the verifier's pinned roots, the anchor's address from the pinned roots, `f` from the election's creation event (4.4), and the header from a source the verifier trusts for finalized L1 (P1-19: a pinned checkpoint and the beacon chain's light-client protocol, or a block hash the user vouches for). A local file proves none of that. So each run records where each input came from: `local-file`; `l1-state-proof` for `now` and `anchors` read from the evidence of formats 2 and 3; or `definition` for the election identifier, the pinned version and the anchor's address read from the definition of formats 3 and 4. The `panel` of formats 4 and 5 is `local-file` until the release pins its panels, and format 5's `l1Blocks` is `local-file` until the verifier trusts a finalized head (P1-19 part 3b). An `l1-state-proof` input counts as authenticated, because the header, the anchor's address and `f` it is proven from are listed as inputs of their own (`l1Header`, `anchorAddress`, `firstSegment`), each `local-file` today except an anchor address from the definition. A `definition` input counts as authenticated for the same reason: the definition is an input of its own (`definition`), `local-file` until 2.1 proves its hash is the one the L2 election registry holds. Any run with an unauthenticated input reports `unverifiable` as its verdict, whatever the checks find, and reports separately what they found against those inputs. So a crafted bundle can neither verify nor fail an election (T-53, T-24). Trusting the header, and reading the clock from the definition and `f` from the archive, replace the remaining local inputs, one by one, in later parts.

### Board by CID

A bundle of any format may hold `blocks.car` instead of `board.bin`: a local block store, from which the verifier reads the board copy by the CIDs the counted checkpoints name on L1, as [[board]] (A copy from L1's CIDs) specifies, with our servers offline (T-24, T-49, T-51). It is the reader of [[0029-board-data-availability]]'s fetch by CID over blocks a user exported from any IPFS node; the same read can also ask gateways over the network (Gateways, below).

`blocks.car` is a CARv1 file (the IPLD CAR specification, version 1): a varint-prefixed dag-cbor header `{roots, version: 1}`, then sections, each a varint length, then a CID and the block's bytes. Varints are unsigned LEB128, minimal and below `2^53`. The header's length must be minimal and the header whole within the file, and it must start `0xa2 0x65 "roots"` and end `0x67 "version" 0x01` (dag-cbor's key order puts `roots` first), or the bundle is rejected; nothing between them is read, so the roots are never parsed (the CIDs come from L1), and a CARv2, whose pragma is `{version: 2}`, is no CARv1. Sections are read in order until the first that isn't whole within the file, has a non-minimal length, or doesn't start with a CIDv0 (`0x12 0x20` and a 32-byte digest) or a CIDv1 (version 1, a codec and a multihash that fit in the section). The bytes from there on are counted, never read, so a store cut short still serves the blocks before the cut, as `board.bin`'s unreadable bytes do. Only a block a read can use is kept: one under a 36-byte CID of the layout's form (`0x01 ‖ (0x55 | 0x70) ‖ 0x12 ‖ 0x20 ‖ digest`, the only form the reader asks for, so a CIDv0 or another codec is never served), of at most 1 MiB, whose SHA-256 is the digest; of those, only the first in the file for each CID is kept, and it is that CID's only answer. The reader takes the first answer that hashes to the CID it asked for ([[content-addressing]], Reading by CID), so it reads the same as it would from every section, and nothing in the store is trusted. The verifier thus hashes each section's block at most once and holds a few numbers per block kept, never more than the file itself: a store of tiny, repeated or wrong sections can't exhaust its memory, or make it hash answers again on every request for a block the anchoring authority repeats (T-52). The file is read whole, as `board.bin` is, so one over 2 GiB can't be read and rejects the bundle.

The read runs after the definition (formats 3 to 5) and the anchors are read, with no copy to match words against: each anchored word must match a checkpoint in `checkpoints` (from its `CheckpointAnchored` log), or the run stops `l1-checkpoint-unknown` as in [Anchors from L1](#anchors-from-l1). Where the definition, the anchors or steps 1 and 2 of the board checks stop the run before a copy is needed, the read doesn't run and the copy is empty; the run then reports the same stop. Otherwise the copy is the runs read, in order, with `unreadableBytes` 0, and the procedure goes on as for `board.bin` (anchors are read again with the copy, and a checkpoint that hashes to a word is the one its log gave). The read takes a byte budget for the whole copy, by default `2^30` (1 GiB) and set on the command line: the anchoring authority chooses how large a run's object may be, and a run of identical chunks costs a few blocks to serve at any size, so the budget is the reader's only bound on what it holds (T-52). A copy past it stops `over-budget`. A copy that stops short of the anchored extent fails `checkpoint-missing` in the board checks: unverifiable from this store, never the election's failure (T-53). The report's `board.byCid` says how the read came out.

**Gateways.** The read may also ask IPFS gateways the user names, over the trustless gateway API's raw-block requests (the IPFS HTTP Gateways specifications, Trustless Gateway): `GET <base>/ipfs/<cid>?format=raw` with `Accept: application/vnd.ipld.raw`, the CID in [[content-addressing]]'s text form, as `apps/node` answers them. A base is an `http:` or `https:` URL with no credentials, query or fragment (a trailing `/` dropped), and a run names from 1 to 16. For each block the reader asks for, `blocks.car` is asked first, when the bundle holds it, so a block it holds costs no request and tells no gateway anything; then each gateway in the order named gets one request, until one answers with status 200 and a body of at most the reader's limit (at most 1 MiB) whose SHA-256 is the CID's digest. That block is the only answer, and later gateways aren't asked. No request is sent for a CID not of the layout's form, the only form the reader asks for. A request that fails, times out (30 s for headers and body together), redirects (never followed, so no request reaches a host the user didn't name), answers any other status, declares a `Content-Length` past the limit, or sends more than the limit (the body is read as it streams and dropped once past it, so no answer costs more than a small multiple of the limit in memory, whatever its encoding) is that gateway's failure for that block, never the read's; a block no source serves is `unavailable`. So a gateway can withhold blocks but never change them: what it serves is the bytes its CID names, and the board checks authenticate them against L1, so a gateway, like a store, can only leave the copy short (T-49, T-24, T-53). Every gateway named sees which CIDs the run asks for, which tell it which election, and which segments, the user is checking, and from what network address; over `http:` so does anyone on the network path, who can also block the requests, though never change a block (T-11). `https:` is the gateway to prefer, and a local node or an exported `blocks.car` tells no one. The time a run takes is bounded only by the blocks the anchored CIDs name, times the gateways, times the timeout: a gateway that answers slowly makes the run slow, never wrong (T-52).

### Anchors from L1

A format-2 bundle gives the evidence the anchors are read from, as [[contracts]] (Board anchor, Verification) specifies, never a list of logs an RPC node could shorten (T-24):

1. `B`'s hash is Keccak-256 of `header` as given, and `now` is its timestamp. The report gives the hash, number and time, so anyone can compare `B` with a node they trust.
2. The anchor's account is the value at `keccak256(anchor)` in the state trie under `B`'s state root (the Merkle–Patricia trie of the Ethereum Yellow Paper, Appendices C and D, with RLP of Appendix B decoded strictly), found by following `nodes` by their Keccak-256 hashes from the root. Its storage root is the third of its four fields. An account, once all four fields are well formed, whose code hash (the fourth) is that of empty code is read as absent: no account without code is the anchor.
3. A slot's word is the value at `keccak256(slot)` in the storage trie, an RLP string of the word without its leading zeros, or zero if the nodes prove the key absent.
4. The lowest-segment word is `lowest + 1`, or 0 if there is no anchor. Otherwise the verifier reads, in segment order, the word of every segment `s` from `max(lowest, f)` to the largest with `epoch + (s + 1)·period ≤ now` (no later one can be anchored yet), never past the seal (`lastSegment`). A range of more than `2^20` segments (about 120 years of hourly periods) stops with `l1-range-too-long` before any segment's word is read, so a bundle's own clock and `f` can't keep a run going for hours.
5. Only once every word is read, then in segment order, for each non-zero word at segment `s`, the checkpoint is the one the copy gives after `s` if its hash matches: the copy's entries up to the first whose segment field is over `s`, read from the raw bytes before anything is authenticated, with its chain head, Merkle root and the CIDs of the segment object and entry-hash list of the segment of its last entry ([[board]], Segments and checkpoints). Otherwise it is a checkpoint in `checkpoints` whose hash is the word (the hash binds the election and segment), whatever its source. Its `anchoredAt` is the end of `s`'s period, which gives the board checks the same result as the true time ([[contracts]], Board anchor, Verification). The anchors are passed to the board checks in segment order, which `{"checkpoint": n}` counts in.

A run that can't read or match a word stops at the first problem, in the order above (the account, the lowest-segment word, the range, the words in segment order, then matching in segment order), with these codes, each leaving 4.1 `not-reached` and 4.2 unverifiable, never failed: no one but L1 itself settles them, and a copy or an evidence set can be wrong without the election being so (T-53):

| Code                    | Meaning                                                                                                                                                  |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `l1-proof-missing`      | A node the walk needs isn't in `nodes` (a changed node, or a header whose state root differs, has another hash and so is missing)                        |
| `l1-proof-malformed`    | A node, account or storage value that no Ethereum trie holds (non-canonical RLP, a bad hex-prefix path, a stored zero)                                   |
| `l1-anchor-absent`      | The nodes prove no account at the anchor's address, or one without code                                                                                  |
| `l1-range-too-long`     | More than `2^20` segment words to read                                                                                                                   |
| `l1-checkpoint-unknown` | A non-zero word at `{"segment": s}` matches neither the copy nor any given checkpoint: someone must produce the checkpoint, from the log that carried it |

### Receipt keys from L1

Under definition versions 4 and 5, 2.9 reads the receipt-key record of the anchor the definition's `l1_anchor` names ([[contracts]], Board anchor, Receipt keys) from the bundle's L1 evidence at `B`, as Anchors from L1 reads checkpoints, never from a call or a list of logs (T-26, T-71):

1. The anchor's account is read as in step 2 of Anchors from L1. If it can't be, 2.9 is unverifiable with that step's code (`l1-proof-missing`, `l1-proof-malformed` or `l1-anchor-absent`) and `at` `{}`.
2. For each key `p ‖ x` in `receipt_keys`, in list order, its word is the value at `keccak256(slot)` in the storage trie, as step 3 of Anchors from L1, with `slot = keccak256(abi.encode(x, keccak256(abi.encode(uint256(p), A + 4))))`. A key whose word can't be read (`l1-proof-missing` or `l1-proof-malformed`) is left unread: the other keys are still read, since a later key's failure is final whatever the unread word holds.
3. A word the release code can't write ([[contracts]], Board anchor, Receipt keys: a high bit set, `retired_at` set with `registered_at` zero or above it, or either time after `B`'s timestamp) is `receipt-key-record`. Otherwise its low 64 bits are `registered_at` and the next 64 `retired_at`, judged by [[election-definition]]'s rule (Receipt keys) with `B`'s timestamp: `receipt-key-retired` if registered before `opens_at` and retired at or before it, at any `B`; otherwise, while `B`'s timestamp is before `opens_at`, the key is unsettled; from `opens_at` on, it is `receipt-key-unregistered` unless registered before `opens_at`, and judges the election otherwise.
4. The row: 2.9 fails with the first key in list order that is `receipt-key-record`, `receipt-key-retired` or `receipt-key-unregistered`, with `at` `{"key": i}` (its position in `receipt_keys`, from 0). Otherwise, if any key was left unread or is unsettled, 2.9 is unverifiable with the first such key's code (the L1 code, or `receipt-key-unsettled`) and `at` `{"key": i}`: a later block, or the missing node, settles it. Otherwise it passes.

The same bundle evidence proves both the anchors and the keys, so `nodes` holds the proofs of every listed key's slot beside the board's. The anchor's address is the definition's, read as given until 1.2 compares it with the release's pin (Definition, Residuals), so a passing 2.9 is as authentic as that address.

### Definition

A format-3 bundle's definition gives the board checks three of their inputs, so none of them can disagree with the election being verified:

1. The definition is decoded as [[election-definition]] (Decoding) says, then checked for well-formedness (Well-formedness), each under its own version's layout and rules; this verifier reads definition versions 1, 3, 4, 5 and 6, and the hash it reports and the stub hash the key ceremony binds (Key ceremony, step 4) are taken over the version's own encoding. A record version this verifier doesn't know, other than 0 (which `profile-version` and the self-pin of Decoding forbid, so no definition can carry it), leaves 2.3 unverifiable with `unsupported-version` and `at` `{}`, as in step 2, so releases never disagree on a verdict (T-36). Any other definition that doesn't decode fails 2.1 with `decode` and `at` `{"decodeError": <code>}`; one that breaks a rule fails 2.1 with the first rule's code (`protocol-major` to `timing`, with `cells` under versions 3 to 5, `receipt-keys` under versions 4 and 5 and `questions` under version 5) and `at` `{}`, except that under version 5 `option-count` and `selections` have `at` `{"question": q}`, `q` the first failing question as a JSON number (P2-14). Under version 6 (read since [[P2-16]] part 4a) version 5's rules are reported the same way and then `results`, `civic-sealed` and `author-panel`, each with `at` `{}`. A release that reads definition version 7 ([[P2-17]] part 4) reports version 6's rules the same way and then `rolling-class` and `rolling-tier`, each with `at` `{}`; until then version 7 is unverifiable the same way. Every well-formedness rule is reported on 2.1, whichever later check its rule serves, since it is one property of the definition's bytes. In either case 4.1 and 4.2 are unverifiable with `not-reached`: the board checks have no election to run for.
2. The board-entry version is the one the profile pins for `0x0007` ([[versioning]]). A version this verifier can't read (it reads 1 and 3 to 7; it reads version 6, a live poll's, and version 7, an author panel's, so that 2.3 fails the profiles pinning them, since it passes no live definition and no author panel yet; a later release that passes them would verify what this one fails, which T-36 allows only because no election registry a release pins registers a version-6 definition yet, [[contracts]], Registration, rule 9, so the later releases must pass them only under registry pins this release doesn't carry) leaves 2.3 unverifiable with `unsupported-version` and `at` `{}`, and 4.1 and 4.2 with `not-reached`; a later release may read it, so it is never a failure. Version 5 adds the close statement to version 4's payloads, which only the close check reads (6.3, not built: P1-19), so this release reads a version-5 board's envelopes and every other record as it reads version 4's, and doesn't yet list a statement that fails to decode as version 1 among the rejected entries (8.3); 6.3 stays unverifiable, so no election verifies meanwhile. A version it reads whose combination with the profile's ballot, tally-opening and contract-event versions 2.3 forbids fails 2.3 with `profile-combination` and `at` `{}` (every version but 5, which alone allows the close statement); the checks below still run under that version, so the report shows what the board holds. A profile that pins a contract-event version this verifier doesn't read (it reads 1, 2 and 3), or ballot version 2 with a spoiled-ballot opening version this verifier doesn't know, or a definition version 3 or 4 whose profile pins a ballot version it doesn't know, and that 2.3 doesn't fail on any other ground, leaves 2.3 unverifiable with `unsupported-version` and `at` `{}`, since a later release may know that version to open version-2 cores, or to name its cell, or read that contract-event version as naming the close rule's events; the checks below still run (T-36).
3. Otherwise the board checks run with the definition's `election_id`, that version, and its `l1_anchor` as the anchor's address. 2.1 stays unverifiable with `not-implemented` until the verifier checks the definition's hash against the L2 election registry the release pins. 2.9 passes under definition versions 1 and 3, which list no receipt keys; under versions 4 to 6 it is read from the same L1 evidence as the anchors ([Receipt keys from L1](#receipt-keys-from-l1)), whatever the board checks find.

The report gives the definition's hash (`abolish/v1/election-definition`) whenever it decodes, so anyone can compare it with the registry's.

**Residuals.** The clock still comes from the bundle: the seal, `lastSegment`, is a function of the definition and the post-close windows `W` ([[election-definition]], The seal), and `W` isn't fixed until P1-18's contract-event window is (the openings' `OPENING_WINDOW` is, [[challenge]]); `epoch`, `period` and `deadline` come from the release's pinned anchor deployment (P1-19 part 3b). Until the release pins the anchor's address, the definition's `l1_anchor` is read as given: 1.2 must then compare it with the pin, and `anchorAddress` must not count as authenticated through the definition before that comparison exists, even once 2.1 authenticates the definition. And the header isn't bound to the definition's `l1_chain_id`; trusting the header (part 3b) binds it. Under definition versions 3 and 4 the regional cells are checked only by the `cells` rule, from the stated region counts: 2.4's per-cell recomputation from the board's group additions, 2.8's fold from those counts, and 5.1 to 5.3 against each cell's root come with the same checks for version 1 (P1-19), and until then each stays unverifiable with `not-implemented` (T-16).

### Key ceremony

A format-4 bundle's panel lets the verifier run the transcript check of [[ceremony]] (Transcript check). It runs once the definition gives the board checks their inputs (Definition), whatever those checks then find: the transcript's bytes are authenticated by the definition's hash of them, never by the board checks.

1. **The panel** (part of 2.5). The panel's identifier, recomputed from the bundle's panel, must equal the definition's `panel_id`, and its `k` and `n` the definition's `threshold` and `panel_size`. Otherwise 2.5 fails with `panel-unpinned` and `at` `{}`, and 3.1 and 3.2 are unverifiable with `not-reached`: the ceremony context binds the pinned panel's identifier, so a transcript checked against any other panel only fails its signatures. Under definition version 6, 2.5 then fails with `panel-kind` and `at` `{}` if the `poll_class` is on the civic record (2 or 3) and the release pins the definition's `panel_id` with the kind `transitional` (Pinned trust roots; T-14). A panel the release doesn't pin has no kind to read, so `panel-kind` stays undecided for it, never failed: a release that pins it as `independent` passes it, so failing it here would let releases disagree (T-36). No release pins a panel yet (the bundle's panel is a local input, Bundle), so none is decided until the release that pins the transitional panel ([[P2-16]] part 6). Next, with an author panel, 2.5 fails with `default-seat` and `at` `{"seat": i}`, `i` the first author seat (from 1) whose key is one of the bundle panel's keys, compared as their compressed encodings, which are unique ([[trustee-identity]], Author panel identifier, rule 4; T-14); a definition that fails both is reported with `panel-kind`, or with `default-seat` by a release that doesn't pin its panel: the same failure, under another code. No ballot is judged against the key set of an election 2.5 fails (Ballot admission). 2.5 otherwise stays unverifiable with `not-implemented` until the verifier compares the recomputed key set with the keys registered on L2.
2. **The version** (part of 2.3). If the profile pins a ceremony-transcript version (`0x0005`) this verifier can't read, 3.1 and 3.2 are unverifiable with `unsupported-version` and `at` `{}`: a later release may read it, so it is never a failure (T-36).
3. **The transcript** is the payload of the first entry of the copy, by position from 0 (whatever its `index` field), that decodes as a board entry under the pinned version, carries the definition's `election_id`, and whose `ceremony_transcript_hash` (over the payload, header included) is the definition's, whatever the payload's record type: bytes the definition binds that aren't a transcript fail step 4's decoding (`decode`, with the [[notation]] code for their record type), never go missing. Any copy of those bytes is the transcript, so its position, and whether it lies inside the anchored extent, don't matter; another transcript on the board, such as an abandoned run's ([[ceremony]], Approval and re-runs), is never read. If no entry matches, 3.1 is unverifiable with `ceremony-transcript-missing` and `at` `{}`, and 3.2 with `not-reached`: like a short copy, that is the copy's problem, never the election's failure (T-53).
4. **The check** runs over the transcript, pinned to version 1, with the context rebuilt from the definition (`l2_chain_id`, `trustee_registry`, `election_id`, the stub hash recomputed from it under its own version, so a transcript made for another version's stub of the same election fails its signatures) and the bundle's panel, never from the transcript (T-37); under definition version 6 with an author panel, the default run's `duplicate-key` also reads the definition's `author_keys` ([[ceremony]], Author panel; T-14). Its outcome sets the rows, with `at` `{"entry": n}` naming the transcript's entry on a failing row (a passing or `not-implemented` row has no `at`):

| Outcome                                                         | 3.1                                           | 3.2                            |
| --------------------------------------------------------------- | --------------------------------------------- | ------------------------------ |
| The transcript doesn't decode                                   | fail, `decode` (with `"decodeError"` in `at`) | unverifiable, `not-reached`    |
| `ceremony-order`, `ceremony-shape` or `ceremony-signature`      | fail, with the code                           | unverifiable, `not-reached`    |
| `ceremony-quorum`                                               | unverifiable, `not-implemented`               | fail, `ceremony-quorum`        |
| Valid, with at least `k` but fewer than `n − 1` qualified seats | unverifiable, `not-implemented`               | fail, `ceremony-participation` |
| Valid, with at least `max(k, n − 1)` qualified seats            | unverifiable, `not-implemented`               | pass                           |

The definition binds these bytes, so a transcript that fails is the election's failure, whoever boarded it. A transcript version other than its pin (`profile-mismatch`) and an unreadable pinned transcript version (step 2) are 2.3's matters, reported on 3.1 and 3.2 as above; 2.3 itself stays `not-implemented` for them. 3.1 never passes yet: it also needs the trustee registry's record of the transcript and its approvals on L2 (3.1's registration part), which the verifier doesn't read until it reads L2 state. 3.2 applies [[0006-trustees]] rule 7, which the owner adopted on 2026-10-12: an election opens only if at least `n − 1` seats took part, where taking part means being qualified (a disqualified seat holds no usable share), so 3.2 needs `max(k, n − 1)` qualified seats and fails with `ceremony-participation` below that. With an author panel 3.1 and 3.2 hold per panel, as step 5 checks, and no key set is registered for the checks below unless 3.2 holds for both. A ceremony with only `k` qualified seats would leave the tally no margin: one of them compelled or lost after the close, and no cell can ever be opened (T-54, T-40).

5. **The author panel** (part of 3.1 and 3.2, definition version 6 with an author panel, since [[P2-16]] part 4d-1). Its transcript is found as in step 3, by the definition's `author_transcript_hash`, and checked as in step 4 with the author context ([[ceremony]], Author panel): the definition's `author_threshold` and `author_keys` as the panel, its identifier under `abolish/v1/author-panel`, `author_stub_hash` recomputed from the definition, and the bundle panel's keys as the other panel's for `duplicate-key`; never a release's pins for the author panel. Its outcome sets the author panel's part of each row as step 4's table does, with `"panel": "author"` in `at` beside `entry` (and `decodeError`); a copy without the author transcript gives 3.1 `ceremony-transcript-missing` with `at` `{"panel": "author"}` and 3.2 `not-reached`; quorum (`k_A`) and participation (`max(k_A, n_A − 1)`) fail 3.2 as for the default panel, with 3.1's author part `not-reached`. Once the run meets participation, every author approvals record of this election in the copy (record type `0x0019`, wherever it sits) is checked as [[ceremony]] (Author panel, Check) specifies, against the key set the run's check returned: if they approve the transcript, 3.1's author part holds; if records name the transcript and don't, 3.1 fails with `author-approvals`; if none names it, 3.1 is unverifiable with `author-approvals-missing`; both with `at` `{"panel": "author"}`. Each row is then the first failure among its parts in this order (the default panel's run, then the author panel's transcript, then its approvals, then, for 3.1, the default panel's registration on L2, which is never read yet), else the first part that isn't a pass, else a pass, so a failing or missing author part is reported ahead of 3.1's `not-implemented`. 3.1 still never passes. The default panel's registered key set is returned for the checks below only when 3.2 passes for both panels, 2.5 hasn't failed `default-seat` and the author approvals approve the transcript, so no later part can judge shares against an author panel whose registration didn't hold or that shares a seat with the default panel; admission still judges no ballot beside an author panel, since nothing passes the author panel's key set to it yet ([[P2-16]] part 4d-3), and 2.3 refuses every author panel anyway.

Once the check reaches the seats, the report's `ceremony` gives what it found, so anyone can see who qualified and why the others didn't. Beside an author panel its `author` gives the same for the author panel's run, once that run's check reached the seats and the default panel's did, with `approvals`, the author seats whose approvals count, once the run met participation.

**Residuals.** The panel is a local input until the release pins its panels, and the definition is one until 2.1 reads the registry, so a format-4 run's `verdict` stays `unverifiable` whatever the transcript is: a crafted bundle can make 3.1 or 3.2 fail against its own inputs, never the election's verdict (T-53). Nothing yet requires the transcript to be on the board by any point: an election whose board never carries it stays unverifiable from every copy, never failed, until a later part fixes by when it must be boarded.

### Ballot admission

Once a format-4 bundle's ceremony checks registered a key set (3.2 passes), the verifier runs the admission checks of [[ballot-validity]] (Ballot record: Decoding, Admission), 5.1 to 5.4, over every ballot of the election on the copy, then the close rule's window (5.5) over each copy by its own path, and rejects the repeats among the ballots those admit (5.7). Like the transcript, it runs whatever the board checks found: each ballot is judged from its own bytes, its own entry, the definition, the clock and the registered key set, never from another entry, so admission is stable (6.1, R4), and the verdict rests on 4.1 and 4.2 anyway.

1. **When it runs.** The ballot version is the one the profile pins: version 1 under definition version 1, version 2 (which names a cell) under definition versions 3 and 4, version 3 (which names a cell and carries one range proof per question) under definition version 5 (P2-14), and version 4 (version 3's with each vote split into a default half and an author half) under definition version 6 ([[P2-16]]). Under definition version 6, 6.2 runs under opening version 3 (Spoiled-ballot openings), and 5.9 with delivery records of version 2, 6.3, 7.1 to 7.3 and 8.5 once 6.1 passes (Counted set and tally), and 7.4 (Tally openings), each over version 4's default half, which without an author panel is the whole sharing. A definition with an author panel has its ballots judged by no release yet: 3.2 can pass beside it (Key ceremony, step 5), but the key set it registers is the default panel's alone, and nothing passes the author panel's key set to admission until [[P2-16]] part 4d-3, so admission is `not-reached` there (T-37). Under any other ballot pin, 5.1 to 5.5 and 5.7 are unverifiable with `unsupported-version` and `at` `{}` (a later release may read it, T-36), except ballot version 1 under definition version 3, 4, 5 or 6, which 2.3 fails beside a cell partition and which can't be judged against one: there they are unverifiable with `not-reached`. Otherwise, unless 3.2 passed, or if 2.5 fails (`panel-kind` or `default-seat`, Key ceremony, step 1), or if the definition names a membership key other than the pinned one (which fails 1.3, for ballot versions 2 to 4 as for version 1) or gives a tier (under definition versions 3 to 6, a cell) the root 0 (which anyone can prove membership of, T-04), they are unverifiable with `not-reached`: no ballot is judged under a panel that isn't registered or can't hold the election, or a key or root no ballot can be checked against. They run whatever 2.3 found, so a profile 2.3 fails for its spoiled-ballot opening pin still has its ballots judged.
2. **The ballots** come from every entry of the copy, by position from 0, that decodes as a board entry under the pinned version and carries the definition's `election_id` (any other entry is 4.1's to report), by one of two paths ([[close]], Window):
   - **the board path:** an entry whose payload is of type `0x0002` carries that payload as its ballot;
   - **the ordinary path:** under a profile pinning contract-event versions 2 to 7, an entry whose payload is a contract-event record (`0x0008`) that decodes strictly under that version and passes the event check ([[contracts]], Event check) as the board's `BallotSubmitted` against the definition's `board` carries the event's `record` as its ballot, with `τ_b` the record's `l2_timestamp`. A record that doesn't decode or fails the event check carries no ballot: it is 4.4's to report (Contract events), and so is any other event. Under contract-event version 1 the board emits no event, so every ballot is a board-path one;
   - **the relayed path:** under a profile pinning contract-event versions 3 to 7, such a record that passes as the board's `RelayedBallotSubmitted` carries the event's `record` as its ballot ([[contracts]], Board, Relayed ballots). Its window is the stamp of the relay call 4.5 matches with the event, never the event's own word ([[close]], Window), and this release doesn't build 4.5 (P1-19): a relayed ballot that 5.1 to 5.4 admit is set aside, neither admitted nor rejected, and 5.5 and 5.7 (and 5.8, where it runs) are unverifiable with `not-implemented` and `at` `{"entry": n}` of the first, whatever the other ballots show, since it may be inside the window or not, a repeat or the copy that stands (T-71, T-35); for the same reason a later copy of any ballot is then listed as a candidate repeat, as where 5.5 can't run, never rejected. Selection (6.1) and the openings' `opening-cast` (6.2) are then not reached.

   Under a contract-event pin other than 1 to 7, ordinary ballots can't be found: 5.1 to 5.4 judge the board path's ballots alone, and 5.5 and 5.7 are unverifiable with `unsupported-version` and `at` `{}`, since a passing row would say no ballot it can't read was rejected (T-36); repeats are then listed as candidates, as below. Otherwise each ballot is decoded strictly under the pinned ballot version and admitted or rejected by the checks in [[ballot-validity]]'s order (version 2: Admission (version 2), with `ballot-cell` in place of `ballot-tier`, the root and scope of the cell it names and `M` under that cell's tier; version 3: Admission (version 3), version 2's order with each question's range proof judged against the definition's questions, never against limits the ballot implies, `option-proof` naming the first failing flat option and `sum-proof` the first failing question; version 4: Admission (version 4), version 3's order with both halves' shapes judged against the definition's two panels, so an author half on a poll without an author panel fails `validity-shape`, and `share-hash-unqualified` naming the first such seat with its panel, default seats first); the first failure is its result. A ballot they admit is then judged by the window of its own path, 5.5 ([[close]], Window): a board-path ballot whose entry's segment is above `s_A = period(closes_at) + 1`, with `period(t) = ⌊(t − epoch) / period⌋` under the bundle's clock (which may be below 0 for a close before the epoch), is rejected with `window-boarded-late`, which is also the report against the board operator; an ordinary ballot with `τ_b < opens_at` with `window-before-open`, and one with `τ_b > closes_at` with `window-after-close`. A board-path ballot has no opening test.

3. **The rows.** Each code fails these rows; a decoding failure is no row's:

| Code                                                                    | Fails         |
| ----------------------------------------------------------------------- | ------------- |
| `ballot-stray`, `ballot-tier`, `ballot-cell`                            | 5.1           |
| `membership-proof`                                                      | 5.1, 5.2, 5.3 |
| `validity-shape`, `share-hash-unqualified`, `option-proof`, `sum-proof` | 5.4           |
| `window-before-open`, `window-after-close`, `window-boarded-late`       | 5.5           |
| `repeat`                                                                | 5.7           |

A membership proof is checked once against `[ρ, ν, m̂, ŝ]` (the root and scope of the definition's tier, or of the cell a version-2 ballot names, the record's nullifier, and `F(M)` recomputed from the record), so its failure can't say which of the root, the scope or the message it was made under. A row fails with the code and `at` `{"entry": n}` of the first rejected entry, by position, whose code fails it, and passes otherwise, also when the copy holds no ballot. So a passing row means only that no ballot was rejected with one of its codes: a ballot rejected by an earlier check never reaches the later ones (its membership proof is never checked after `validity-shape`, say), and a ballot that doesn't decode fails no row, so every row can pass while `rejected` isn't empty. An admission row's failure rejects entries only: it never fails the election (Principles), and the report's `ballots` lists every rejection, so 8.3's list of rejected entries starts here.

4. **Repeats (5.7).** Over the ballots 5.1 to 5.5 admit (for format 5, those 5.8 then doesn't reject, [L1 references](#l1-references)), of either path, in copy order, step 1 of [[revoting]]'s Selection finds every repeat: a ballot with the same `tier` (version 2: its cell's tier), `ν` and `M` as one at an earlier position, with `M` recomputed from the record (5.3), never compared as bytes, so a copy whose membership proof was re-randomised is found too (T-38). It is rejected with `repeat`. A ballot 5.1 to 5.5 reject never makes another a repeat (R4), so a late copy never stands in for a timely one, and a timely copy stands whatever happened to the others ([[close]], Window). Under format 4 the input to 5.7 is the ballots every other admission check admits, and 5.8 doesn't run; it can't change which copies are rejected, since `M` binds the L1 reference (`l1_ref_number`, `l1_ref_hash`), so 5.8 admits or rejects every copy of a ballot alike. Format 5 runs 5.8 first, as [[revoting]]'s Selection takes the ballots every admission check admits, and reports its code, not `repeat`, at a copy of a ballot 5.8 rejects, so 5.7 may pass under format 5 where format 4 fails it, never with another entry admitted. Where 5.5 can't run (step 2), a repeat isn't rejected: it is listed as a candidate in `repeats`, and 5.7 is unverifiable.

Once it runs, the report's `ballots` gives `admitted`, the number of ballot entries 5.1 to 5.5 and 5.7 admit (where 5.5 can't run, those 5.1 to 5.4 admit, candidate repeats included), `rejected`, each rejected ballot entry in copy order with its `entry`, its `code` (an admission code, a window code, `repeat`, or `decode` with `decodeError`, the [[notation]] code) and, for `option-proof`, `option`, the first failing option (under ballot version 3, flat option), and for ballot version 3's `sum-proof`, `question`, the first failing question, and for ballot version 4's `share-hash-unqualified`, `panel` (1 for the default panel, 2 for the author panel: the `panel` byte of [[ballot-validity]], Context (version 4)) and `seat`, the first such seat from 1, and `repeats`, each candidate repeat in copy order with its `entry`, empty wherever 5.5 runs. An admitted ballot isn't yet counted: its L1 reference (5.8, under format 5 only), selection (6.1, [Selection](#selection)) and delivery (5.9, [Counted set and tally](#counted-set-and-tally)), both under format 5 only, are decided over the admitted ballots below, the close check (6.3, [Close check](#close-check)) after delivery, and whether it is on the board in time (5.6) by a later part, so 5.6 stays `not-implemented`.

**Residuals.** The copy and the clock are local inputs, so the admission rows and `ballots` report what the copy holds, and the window rows what the clock makes of its segments, including entries past the anchored extent, which 4.1 and 4.2 don't authenticate: a mirror can add ballots there, or leave out or add ones elsewhere, and so change the rows and `ballots`, never the verdict, which rests on 4.1, 4.2 and the election checks. Selection (6.1) takes only the ballots in the anchored extent of a sealed board ([Selection](#selection)). Until 2.4 and 2.8 recompute the trees from the board, admission takes the definition's tier and cell roots as stated: a definition whose cells put one commitment in two cells of a tier would let its holder have two ballots admitted, under two nullifiers, which 5.7 doesn't find; the verdict can't pass while 2.4 and 2.8 are unverifiable (T-16, P1-19). An ordinary ballot's `τ_b` is its contract-event record's `l2_timestamp`, which only the event accumulator authenticates, and 4.4 doesn't replay it yet: until it does, a copy's ordinary ballots are judged by timestamps no one has proven, so a mirror can move one into or out of the window, again changing the rows, never the verdict (T-53, T-71).

### L1 references

A format-5 bundle gives a run of finalized L1 headers (`l1Blocks`, Bundle), and wherever ballot admission runs and 5.5 can run (Ballot admission, step 2), the verifier judges each ballot 5.1 to 5.5 admit by its L1 reference (5.8), as [[revoting]] (Admission) specifies, before repeats (5.7). The check reads only the reference the ballot's `M` binds and the run, never another entry, so admission stays stable (R4) and every copy of a ballot gets the same verdict.

1. **When it runs.** Wherever 5.1 to 5.5 and 5.7 are unverifiable with `not-reached` or `unsupported-version` (Ballot admission, step 1), so is 5.8, with the same code and `at`; and so it is with `unsupported-version` and `at` `{}` where a contract-event pin hides the ordinary path (step 2), since a passing row would say no ballot it can't read was rejected (T-36). Under format 4, 5.8 stays `not-implemented`.
2. **The run.** Its last header is `head`, the latest finalized block read. `l1_ref_min` is searched in the run from its first block, which must show where the window starts: unless the first block is block 0, its timestamp must be before `opens_at − 3600`. A run that starts later can't place `l1_ref_min`, which may lie below it: 5.8 is unverifiable with `l1-blocks-short` and `at` `{}`, no reference is judged, and 5.7 runs as under format 4. Otherwise `l1_ref_min` is the first block of the run whose timestamp is at or after `opens_at − 3600`; if the head is before it, every reference is pending ([[revoting]], Before the window).
3. **Each reference** is judged by [[revoting]]'s steps 1 to 4, against the run: `l1-ref-before-open` below `l1_ref_min`, then `l1-ref-after-close` if the block numbered `min(l1_ref_number, head)` is later than `closes_at`, then **pending** if `l1_ref_number > head`, then `l1-ref-unknown` if the run's block of that number has another hash; otherwise the reference is admitted. Every lookup lies in the run, between `l1_ref_min` and `head`. A rejected ballot is listed in `rejected` with its code, never counted and never makes another a repeat. A pending ballot is neither admitted nor rejected: it stays among the ballots 5.7 compares, since whatever L1 later decides for it, it decides for its copies, and only the first copy is listed in `pending`; a copy after it is rejected with `repeat`, a code that holds only while 5.8 is unverifiable: once the run reaches past close, the copy gets the first copy's 5.8 code instead if that rejects it. 6.2's `opening-cast` still compares openings with every ballot 5.1 to 5.5 admit, whatever 5.8 finds for it.
4. **The row.** If any ballot is pending (and not a repeat), 5.8 is unverifiable with `l1-ref-pending` and `at` `{"entry": n}`, the first such entry: it may yet be admitted or rejected, and must not let the row pass or fail for the others. Otherwise 5.8 fails with the code and `at` `{"entry": n}` of the first entry it rejected, and passes if it rejected none, also when the copy holds no ballot. Like every admission row, its failure rejects entries only, never the election; its unverifiability leaves the election unverifiable (Verdicts). `admitted` in `ballots` counts the ballots 5.1 to 5.5, 5.7 and 5.8 admit, so never a pending one.

Once a run reaches a head after `closes_at`, no reference is pending and the verdicts don't depend on which head ([[revoting]], Every verifier reaches the same verdict), so a bundle need carry L1 only from a block before `opens_at − 3600` to the first block after close ([[revoting]], Bounded evidence).

**Residuals.** The run is a local input (`l1Blocks`, `local-file`): its parent links make it one chain, but nothing yet shows that chain is Ethereum's finalized one, since trusting a finalized head is part 3b's. Until then a crafted run can admit or reject any reference, changing the row and `ballots`, never the verdict. The only tie to the anchors' evidence is that a run holding `l1.header`'s number must hold that header; a run that doesn't reach it is unconstrained by it. A run is as long as the poll in L1 blocks (about 7,200 headers a day), which the user supplies and pays for in reading; a later part may replace it with the history the beacon chain or EIP-2935 commits to, under the same rules.

### Selection

Wherever 5.8 runs (format 5), the verifier decides 6.1 once the set it selects from is fixed, by [[revoting]]'s Selection over the ballots every admission check admitted from the counted extent. The rule is a function of that set alone (R3), so 6.1 never passes over a set a later entry or finding could still change: short of each condition below, it is unverifiable, and the conditions are checked in this order, the first unmet one giving the row's code.

1. **Admission settled.** Every admission row, 5.1 to 5.5, 5.7 and 5.8, passed or failed. One that can't be evaluated may yet admit or reject a ballot (Principles), so 6.1 is unverifiable with `not-reached` and `at` `{}`; so it is under format 4, where 5.8 doesn't run, and wherever the key-ceremony checks run but ballot admission can't (Ballot admission, step 1). Where the definition stopped the board checks, Procedure step 6 makes 6.1 `not-reached` with no `at`, as it does 5.8.
2. **The board.** 4.1 and 4.2 passed, so the copy's prefix up to the anchored extent is the board ([[board]], Board checks); otherwise `not-reached` and `at` `{}`. Only entries in the anchored extent take part from here on: one past it is no one's claim.
3. **The seal.** The seal's window has closed: `epoch + (lastSegment + 1)·period + deadline < now` under the bundle's clock. With 4.2 passing, that means the seal's checkpoint is counted and fixes the board's final extent; before it, an entry may still be boarded within the counted extent. Otherwise `not-sealed` and `at` `{}`.
4. **Timestamps.** Unless 4.4 passed, no entry of the anchored extent carries an ordinary-path ballot (Ballot admission, step 2), admitted or not: its window (5.5) rests on its record's `l2_timestamp`, which only 4.4's accumulator replay authenticates, so the operator could have moved it into or out of the window (T-35, T-71). Otherwise `not-reached` and `at` `{"entry": n}`, the first such entry.
5. **The counted extent.** No admitted ballot of the anchored extent is in a segment above `s_F = period(closes_at) + 1`, the floor of `s_S` ([Spoiled-ballot openings](#spoiled-ballot-openings), step 3). A board-path ballot above it is already rejected (`window-boarded-late`), but an ordinary one may be boarded later, and whether it is within the counted extent (`segment ≤ s_S`, [[tally]], Tally window) waits on `s_S`; otherwise `not-implemented` and `at` `{"entry": n}`, the first such entry.
6. **The selection.** The admitted ballots of the anchored extent, every one of them in the counted extent, go through [[revoting]]'s Selection: 5.7 has already rejected every repeat, so step 1 finds none, and steps 2 and 3 group them by (`tier`, `ν`) (under ballot versions 2 and 3, the cell's tier) and choose, in each group, the single ballot naming the highest L1 block, or list a tie. 6.1 passes, also when nothing is admitted: no failure of it is possible from the board, since a tie or an exclusion is the rule's outcome, never a breach. The report's `ballots` gains `selected`, each group's counted ballot, and `ties`, every ballot naming its tied group's highest block (a lower one of that group is in neither), each in copy order with its `entry`.

A selected ballot isn't yet counted: delivery (5.9) and a proven complaint can still exclude it, with no fallback to an earlier ballot of its group ([[revoting]], Selection, step 4; [Counted set and tally](#counted-set-and-tally)), and the close check (6.3, [Close check](#close-check)) recomputes each cell's counted set without the ordinary ballots after its head; none of them changes `selected`.

**Residuals.** Until 4.4 can pass, condition 4 holds only for a board whose anchored extent holds no ordinary ballot (or whose profile pins contract-event version 1, which 2.3 fails); and until `s_S` is known (P1-18's contract-event window), condition 5 can't pass for an admitted ballot boarded after `s_F`. The run of L1 headers that settles 5.8 and the clock that places the seal are local inputs (`l1Blocks`, `clock`), so a crafted one can change `selected` and `ties`, never the verdict, which stays unverifiable while they are (Verdicts; T-53). Condition 4 sees only the ordinary ballots the board holds: an operator that boards none of a voter's direct-submitted ballots leaves nothing for it to wait on, so 6.1 can pass over a set that lacks them. That is 5.6's to catch (a ballot found on L2 but missing from the board), and while 5.6 is unverifiable so is the verdict (T-25, T-71).

### Spoiled-ballot openings

Wherever ballot admission runs, the verifier then checks every spoiled-ballot opening of the election on the copy (6.2) against the same definition and registered key set, and judges it against [[challenge]]'s Publication rules as far as the bundle decides them. Like admission, it runs whatever the board checks found, and each opening is judged from its own bytes, the definition, the key set, the clock and the ballots admission admitted, so no opening changes another's checks (R4).

1. **When it runs.** This release reads spoiled-ballot opening versions 1 to 3: version 1 opens ballot version 1's cores, under definition version 1; version 2, with `cell` in place of `tier`, opens ballot versions 2 and 3's, under definition versions 3 and 4 (ballot version 2) and 5 (ballot version 3) ([[challenge]], Opening version 2); and version 3 opens both halves of ballot version 4's, under definition version 6 ([[challenge]], Opening version 3), only without an author panel, since admission judges no ballot beside one (Ballot admission, step 1). Under a profile whose spoiled-ballot opening pin (`0x0003`) is another version, or whose ballot pin is neither the definition's own ballot version nor version 1 (as for admission, step 1), 6.2 is unverifiable with `unsupported-version` and `at` `{}`: a later release may read that opening version, or open that ballot version's cores (T-36). Otherwise, under any pins but the definition's own ballot version beside the opening version that opens its cores, a profile 2.3 fails (`profile-combination`), 6.2 is `not-reached`: no opening is judged against an election whose ballots it can't be an opening of. So is it wherever 5.1 to 5.4 are `not-reached` (Ballot admission, step 1): an opening of shares made to an unregistered panel can't be judged (T-37), and `opening-cast` compares with admitted ballots.
2. **The openings** are the payloads of type `0x0003` of every entry of the copy, by position from 0, that decodes as a board entry under the pinned version and carries the definition's `election_id`. Each is decoded strictly under the pinned version and checked by [[challenge]]'s Checks in order (under version 2, against the definition's cells and questions, with `opening-cell` in place of `opening-tier` and `m` the total over the questions under definition versions 5 and 6; under version 3, version 2's checks over both halves, default half first, each against its own panel's `k`, `n` and registered key set, so an author half on a poll without an author panel fails `opening-shape`, T-17, T-37); the first failure is its `code` (`decode`, with `decodeError`, or an `opening-*` check code, with the first failing `option` for `opening-vss`, a flat option under definition versions 5 and 6, and `seat` for `opening-ciphertext`, each under version 3 with `panel`, 1 for the default half and 2 for the author half). A passing opening reports its tracking code (under version 2, the core hash under the ballot version the profile pins, since the opening carries none; under version 3, ballot version 4's), its vote (under version 3, each `v_j` the sum of both halves' constant terms) and, if no valid ballot could carry that vote, `voteOutside` (`opening-vote-outside`, the client's evidence, no one's on the board), under versions 2 and 3 with `question`, the first question outside its rules (0 under definition versions 3 and 4).
3. **The floor.** `s_S` needs `W_S`, whose contract-event window P1-18 hasn't fixed, so the verifier doesn't know it yet. It knows its floor, `s_F = period(closes_at) + 1` ([[tally]], Tally window: `s_S` is the later of that and another period), with `period(t) = ⌊(t − epoch) / period⌋` under the bundle's clock, which may be below 0 for a close before the epoch. An entry in a segment at or below `s_F` is in the counted extent whatever `s_S` is.
4. **The breaks** an opening is known to make of the Publication rules, in that table's order: `opening-early` if its entry's segment is at or below `s_F` (the envelope's, so an opening that doesn't decode can be early too); `opening-cast`, with `ballot`, the first such ballot's position, if it passed and opens a commitment ([[challenge]], Opened commitments; under version 3, Opening version 3's, against both halves of each version-4 ballot) of a ballot 5.1 to 5.5 admitted at or below `s_F`, by either path; and `opening-repeat`, with `of`, the first such entry's position, if an earlier entry of the copy carries an opening that decodes with the same core hash, whatever that opening's checks found (the operator boards one opening per core). `opening-late`, `opening-early` above `s_F` and `opening-cast` of a ballot above it wait on `s_S`.
5. **The row.** An opening is settled when it has a `code` or a break. If any opening isn't settled, 6.2 is unverifiable with `not-implemented`: it may yet be early, late or cast, and an unsettled opening must not let the row pass or fail for the others. Otherwise 6.2 fails with the first opening's `code`, or its first break's code, and `at` `{"entry": n}` (with `decodeError` for `decode`), or passes if the copy holds no opening. A later release that knows `s_S` may report an earlier break of the same opening (`opening-early` above `s_F`, say) and so another code at the same entry, never another status. Like an admission row's, the failure never fails the election: an opening never counts, displaces or fails anything ([[challenge]], Publication).

Once it runs, the report's `openings` lists every opening entry in copy order with its `entry`, `code` and, where they apply, `decodeError`, `option`, `seat` and `panel`, or for a passing opening `coreHash` (hex), `votes` (each `v_j` as a decimal string) and `voteOutside` (`true`, only when it applies, with `question` under opening versions 2 and 3), and `breaks`, each with its `code` and, for `opening-cast`, `ballot` and, for `opening-repeat`, `of`.

**Residuals.** The copy and the clock are local inputs, so the row and `openings` report what they hold: a mirror can add, drop or reorder openings, or drop the ballot that makes one cast, and change them, never the verdict. Until `s_S` is known, an opening boarded after `s_F` but within the counted extent, during the tally window or after `t_S + OPENING_WINDOW` goes unreported, and 6.2 can't pass while any honest opening is on the copy. Openings past the sealed extent are read like any other until the verifier limits itself to it.

### Tally openings

Wherever the ceremony checks registered a key set (3.2 passes), under definition versions 1, 3, 4, 5 and 6 (under version 6 only without an author panel; beside one the registered key set is the default panel's alone, and its halves are tallied per panel, [[P2-16]] part 4d-3, so 7.4 is `not-reached`), the verifier reads every tally opening of the election on the copy (7.3, 7.4): it sorts each into an opening of a cell or a stray opening, attributes it by the registered signing keys ([[tally]], Opening record: Signature, Which openings are a cell's), and judges it against [[tally]]'s Boarding rule as far as the bundle decides that rule without the counted set. Sorting and attribution read only the opening's own bytes, the definition and the registered key set, and the one rule that compares openings (a second by the same seat) only earlier entries, so dropping an entry never changes another's cell, attribution or other breaks (R4).

1. **When it runs.** Under a profile whose tally-opening pin (`0x0006`) isn't version 1, 7.4 is unverifiable with `unsupported-version` and `at` `{}`: a later release may read that version (T-36). Otherwise, unless 3.2 passed, it is unverifiable with `not-reached`: with no registered key set no opening can be attributed. It doesn't need ballot admission: an opening is attributed whatever membership key or tier roots the definition names. Nor does it need 2.3 to pass: it runs whatever 2.3 finds for another pin (`profile-combination` for a ballot or spoiled-ballot opening pin that doesn't fit, or `unsupported-version` for one a later release may read), since sorting and attribution read only the tally-opening version.
2. **The openings** are the payloads of type `0x0006` of every entry of the copy, by position from 0, that decodes as a board entry under the pinned version and carries the definition's `election_id`. Each is decoded strictly under version 1; one that doesn't decode is a rejected entry (`code` `decode`, with `decodeError`), opens no cell, and the Boarding rule refuses it. A decoded opening is an opening of cell `c` if its `definition_hash` is the definition's and its `cell` is `c`, a position in the partition ([[election-definition]], Notes, Tally partition): under definition version 1 a position in `electorate`, whose cells are its tiers; under versions 3 to 6 a cell's number, counting every tier's `cells` in `electorate` order from the first tier's first cell ([[election-definition]], Layout (version 3)), so it names a cell, not a tier; and stray otherwise; its `signer` is the seat its signature attributes it to, or `null`.
3. **The breaks** an opening is known to make of the Boarding rule, in that rule's order: `tally-stray` for a stray opening; `tally-missing` for an opening of a cell whose number of entries isn't `m`, the definition's `option_count` (under definition versions 5 and 6, the total of its questions' option counts, [[tally]], Context) (it fails its cell's opening checks whatever the counted set, [[tally]], Opening checks); `tally-unattributed` if its signature attributes it to no seat; and, for an opening of a cell attributed to a seat when an earlier entry of the copy carries an opening of the same cell attributed to the same seat, whatever that one's checks find (the operator boards at most one per seat and cell), with `of`, the first such entry's position: `tally-second` if its signed message ([[tally]], Signature) differs from that first one's, which shows the seat signed two different openings of the cell, or `tally-repeat` if it is the same, which anyone can replay, so it is the operator's breach alone and never its signer's (T-29). An unattributed opening is by no seat, so it is never a second or a repeat and never makes another one so. `tally-aggregate` and `tally-opening` against the cell's aggregate need the counted set (7.1): once it is known ([Counted set and tally](#counted-set-and-tally), step 6), an opening of a cell with `m` entries breaks `tally-aggregate` if its `aggregate_hash` isn't its cell's over the counted set, and otherwise `tally-opening`, with `option`, the first option it doesn't open, if it doesn't open every one, each after `tally-missing`, in [[tally]]'s Opening checks order, and before `tally-unattributed`; until then neither is reported.
4. **The row.** An opening is settled when it has a `code` or a break, and every opening is settled once the counted set is known (an opening of a cell that breaks nothing then passes every opening check and the boarding rule). If any opening isn't settled, 7.4 is unverifiable with `not-implemented`: it may yet be over another set or fail to open its cell's aggregate, and an unsettled opening must not let the row pass or fail for the others. Otherwise 7.4 fails with the `code`, or the first break's code, and `at` `{"entry": n}` (with `decodeError` for `decode`) of the first opening that has either, or passes if none has, also when the copy holds no tally opening. A later release that knows the counted set where this one doesn't may report a break of the same opening earlier in that order (`tally-aggregate`, say) and so another code at the same entry, never another status. Every break is a record the operator should have refused, so it is reported against the operator, and, except `tally-repeat`, also against its signer, if any ([[tally]], Boarding). 7.4 is report-only: it never fails the election, whose result rests on 7.1 to 7.3.

Once it runs, the report's `tallies` lists every tally-opening entry in copy order with its `entry`, then `code` and `decodeError` for one that doesn't decode, or `cell` (for an opening of a cell) and `signer` (a seat, or `null`), then `breaks`, each with its `code` and, for `tally-second` and `tally-repeat`, `of`, and for `tally-opening`, `option`. Once the counted set is known, the board is sealed and authenticated (6.1 passed), so only the entries in the anchored extent are read and listed: an entry past it isn't on the board.

**Residuals.** The copy is a local input, so the row and `tallies` report what it holds: a mirror can add, drop or reorder openings and so change them (dropping a seat's first opening of a cell, say, makes its second the first), never the verdict. Until the counted set is known, openings past the sealed extent are read like any other. Under definition versions 3 and 4 the partition is the one the definition states, taken as stated until 2.8 recomputes it from the board: a definition stating other cells than the fold's moves openings between a cell and stray, which changes the row and `tallies`, never the verdict, which can't pass while 2.8 is unverifiable (T-16). A summed share disguised as a failing opening ([[0015-tally-publication]], T-15) is reported only once the counted set shows the opening failing.

### Counted set and tally

Wherever selection (6.1) passes, the verifier runs delivery (5.9) over the selected ballots, and from the ballots it keeps forms each cell's counted set, against which it runs the tally checks (7.1 to 7.3), the two breaks of 7.4 that need it, and 8.5 ([[delivery]], Delivery check; [[tally]], Context, Opening checks and Destruction checks). 6.1's pass means the copy's anchored extent is the sealed board ([Selection](#selection), conditions 2 and 3), so only the entries in it are read. The counted set comes from the counted extent alone (`segment ≤ s_S`, [[tally]], Tally window), and `s_S` isn't known yet, only two floors of it: `s_F = period(closes_at) + 1` ([Spoiled-ballot openings](#spoiled-ballot-openings), step 3) and `s_K = period(closes_at + l1_inclusion_bound + COMPLAINT_WINDOW)`, since `W_S` holds the complaint window ([[delivery]], Windows: `s_S ≥ s_K ≥ s_D`). Their maximum is `s_G`, and every entry at or below `s_G` is in the counted extent. Each step below runs only where these floors decide it, and leaves its rows unverifiable otherwise, never a pass over a set that a later entry could change (T-25, T-29, T-54).

1. **When it runs.** Unless 6.1 passed, 5.9, 6.3 ([Close check](#close-check)), 7.1, 7.2 and 7.3 are unverifiable with `not-reached` and `at` `{}`, and so is 8.5 under a board-entry version that allows `0x000f` (otherwise it stays not applicable, 8.5) or where the definition stops the board checks, so no board-entry version is known (Procedure step 6). 6.1 never passes under a contract-event pin other than 1 to 7, since 5.5 is then unsupported (Ballot admission, step 2); should it be reached there anyway, all of them are unverifiable with `unsupported-version` and `at` `{}` (T-36). Under definition version 5 they are all unverifiable with `not-implemented` and `at` `{}`: its ballots are version 3, whose delivery this release doesn't check. Under definition version 6 with an author panel they are all `not-reached` with `at` `{}`: admission judges no ballot beside one yet (Ballot admission, step 1), so 6.1 never passes there, and the author seats' delivery is never judged against a key set taken on trust (T-37). Under definition version 6 without one, everything below runs, over each counted ballot's default half: ballot version 4's default half is then the whole sharing, opened by the default panel under tally-opening version 1 with the definition's questions, as under version 5 ([[tally]], Context). If `closes_at + l1_inclusion_bound` is before the clock's `epoch` (which 2.6 fails, since `opens_at` must be at or after it), the windows can't be placed on the clock, and they are all `not-reached` with `at` `{}`.
2. **The delivery records** are those in the anchored extent, of entries that decode as board entries under the pinned version and carry the definition's `election_id`:
   - **through the board path,** every payload of type `0x000c`, `0x000d` or `0x000e`, with its entry's segment. One whose segment is above `s_G` is outside its own window whatever `s_S` is (its segment is above `s_K ≥ s_D`), so it delivers and excludes nothing, in the counted extent or not: it isn't read, so it is listed neither in `records` nor, if it doesn't decode, in `rejected`, and a later release that knows `s_S` may list such a record that is in the counted extent;
   - **through the contract path,** the `record` of every contract-event record that decodes under the pinned contract-event version and passes the event check as the board's `ShareReceiptSubmitted`, `SharePosted`, `ShareComplaintSubmitted`, `ShareReceiptBatchSubmitted`, `ShareComplaintBatchSubmitted` or `ObligationRootSubmitted`, with the record's `l2_timestamp` as its submission time. Its window rests on that timestamp, which only 4.4's accumulator replay authenticates, so unless 4.4 passed, the first entry carrying one makes 5.9, 6.3, 7.1 to 7.3 and 8.5 (where it applies) unverifiable with `not-reached` and `at` `{"entry": n}`; and once it has, one above `s_G` makes them `not-implemented` at its entry, since it may or may not be in the counted extent, unless its submission time is after `t_K`, the complaint window's end: it is then late whatever `s_S` is, so, like a board-path record above `s_G`, it isn't read, and a record sent after the windows never holds the rows open (T-35, T-71). This release doesn't read an obligation root's leaves yet ([[P1-12f]] parts 2 and 3) and no attestation makes them available ([[P4-3]] part 2c), so once 4.4 has passed, the first root naming the definition that is read here makes 5.9, 6.3, 7.1 to 7.3 and 8.5 (where it applies) unverifiable with `not-implemented` at its entry, since its leaves may deliver any ballot; a root naming another definition is `delivery-stray`, listed in `records` with its entry, and delivers nothing (T-25, T-53). Under ballot version 4, which fixes no obligation-root version, every root read here is a rejected entry (5.9, listed in `rejected`), whatever definition it names; so is every batch ([[delivery]], Versions). No contract-path record delivers or excludes there at all, since the board's events carry only delivery records of version 1, batches and roots ([[delivery]], Version 2), so under ballot version 4 one above `s_G` isn't read, whatever its submission time, as a board-path one isn't, and holds nothing open.
3. **Delivery (5.9).** The delivery check of [[delivery]] runs over the selected ballots (6.1's `selected`, each decoded: its tier under ballot version 1, its cell under versions 2 and 4, its nullifier and committed vote, from which it recomputes the ballot hash) and the records of step 2 in copy order, with the registered key set, the definition's `panel_size`, and `s_D`, `s_K`, `t_D` and `t_K` from the definition and the bundle's clock; under ballot version 4 it is the version-2 check ([[delivery]], Delivery check (version 2)), over every seat of both panels, with the default panel's registered key set and, without an author panel, an empty author key set, so a record naming an author seat is `delivery-seat` and delivers nothing (T-37). 5.9 then passes: an excluded ballot is the rule's outcome, never a breach, and a failing record is ignored ([[delivery]], Delivery check). The report's `delivery` lists each selected ballot it excludes, in copy order, with `entry`, `missing` (the qualified seats with no receipt or passing posting in time, ascending) and `complaints` (each proven complaint about it, with `entry`, `pair` for a batch's entry, `seat` and `signer`, a seat or `null`); `records`, each record the check reported, in copy order, with `entry`, `pair` for a batch's pair (its index in the batch, from 0), `code` (a code of [[delivery]]'s table) and, for `share-receipt`, `complaint-unfounded` and `receipt-contradicted`, `signer`; and `rejected`, each record that doesn't decode, with `entry` and `decodeError` (8.3). Under ballot version 4 each seat is named by its panel too (1 default, 2 author): `missing` lists `{"panel", "seat"}` objects, default seats first and each panel ascending, each complaint has `panel` before `seat`, and each record has `panel` and `seat`, those it names; no entry has `pair`, since no batch decodes there.
4. **The counted set (7.1).** Each cell's counted set is the selected ballots the delivery check keeps that are in the cell: under definition version 1 the cell is the tier's position in `electorate`, under versions 3, 4 and 6 the cell the ballot names ([[tally]], Context); under version 6 the aggregates are over the default half's commitments (`vss`), the whole sharing without an author panel. From them [[tally]]'s aggregates are recomputed for every cell of the partition, an empty cell's being the identity. 7.1 then passes: `tally-late` can't fail here, since every board-path ballot above `s_F` is already rejected (5.5), every board-path delivery record above `s_G` is outside its window, and step 2 left no contract-path record and 6.1 no admitted ordinary ballot above the floors, so the counted set over the whole sealed extent, each record's window applied by its submission time, is the one over the counted extent.
5. **The openings (7.2, 7.3).** Under a tally-opening pin other than 1, 7.1 to 7.3 are unverifiable with `unsupported-version` and `at` `{}`, and so is 8.5 where it applies, since the tally-opening version fixes the destruction statement's (T-36); 5.9 still runs. Otherwise every tally-opening payload in the anchored extent, of an entry as in step 2, in copy order, is checked by [[tally]]'s Opening checks against each cell's counted set. 7.3 passes: an opening that doesn't decode is a rejected entry that opens no cell, and sorting and attribution are reported (7.4), never failed on their own. 7.2 fails at the first failing cell, in cell order, with its code (`tally-missing`, `tally-opening`, `tally-conflict`, `tally-range` or `tally-question-range`) and `at` `{"cell": c}`, with `option` where the code names one (the first failing option of the first opening over the counted set, for `tally-opening`; the first count over the cell's ballots, for `tally-range`) and `question` for `tally-question-range`; otherwise it passes. The report's `cells` lists every cell in partition order with `cell`, `tier` (the tier it belongs to), `counted` (its counted ballots), then, for a cell that passes, `counts`, one decimal string per option, or else `code`, with `option` or `question` where they apply, then `signers`, the seats a passing opening of the cell is attributed to, ascending (empty if every passing opening is unattributed, or none passes). `tiers` gives each tier of the partition, in `electorate` order, with `tier`, `counted` (its cells' total) and, where every cell of the tier passes, `counts`, the per-option sums of its cells' counts ([[tally]], Coarser totals): the result, derived and never opened. They are the substance of 8.1 and 8.4, which stay unverifiable with `not-implemented`: 8.1 reports each tier's and cell's anonymity-set size and turnout from 2.4's recomputed member counts, and 8.4 names the seats by the identities and panel kind the release pins ([[0027-trustee-panels-and-live-results]], Part 3), neither of which this release reads.
6. **7.4's last breaks.** With the counted set known, 7.4 ([Tally openings](#tally-openings)) reads only the anchored extent, and each opening of a cell with `m` entries that `tally-aggregate` or `tally-opening` fails (step 5) has that break, so every opening is settled and 7.4 passes or fails.
7. **Destruction (8.5),** under a board-entry version that allows `0x000f`. Every destruction-statement payload in the anchored extent, of an entry as in step 2, with its segment, is read by [[tally]]'s Destruction checks against the registered key set. The destruction segment there is `min(s_O + 1, s_T)` if every cell has a passing opening (one that passes `tally-missing`, `tally-aggregate` and `tally-opening`), with `s_O` the latest segment of a cell's first passing opening, and `s_T` otherwise, where `s_T` is the period containing `t_S + TALLY_WINDOW` and `t_S` the end of period `s_S` plus the anchor's `deadline`. `s_T` grows with `s_S`, so it is at least `s_G + 1 + ⌊(deadline + TALLY_WINDOW) / period⌋`, and the destruction segment lies between `earliest`, its value with `s_T` at that floor, and `latest`, `s_O + 1`, unbounded while a cell has no passing opening. Each registered seat is `destruction-missing` with no attributed statement in the anchored extent, `destruction-early` if its first attributed statement is below `earliest`, `destroyed` if it is at or above `latest`, and undecided between them. 8.5 is unverifiable with `not-implemented` and `at` `{"seat": i}`, the first undecided seat, while any seat is undecided; otherwise it fails with the code and `at` `{"seat": i}` of the first registered seat, ascending, that isn't `destroyed`, and passes if every one is. It is report-only: a missing or early statement never fails the election or makes it unverifiable, and `destroyed` never means the material is gone (T-14, T-54). The report's `destruction` gives `earliest`, `latest` when it is bounded, `seats` (each registered seat ascending, with `seat`, `code` once decided and `entry`, its first attributed statement's, where it has one), and, each in copy order, `duplicates` (`entry`, `seat`), `unattributed` (`entry`), `stray` (`entry`, `signer`) and `rejected` (`entry`, `decodeError`), which [[tally]]'s Boarding rule says the operator should have refused (`rejected` also listed in 8.3).

**Residuals.** The copy, the clock and the run of L1 headers are local inputs, so a crafted bundle can change which ballots are selected, delivered and counted, the cells' counts, and every row here, never the verdict, which stays unverifiable while any input is (Verdicts; T-53). Step 2 sees only the contract-path records the board holds: an operator that boards none of a ballot's contract-path receipts or postings leaves the ballot undelivered, and nothing here can tell that from records never sent. The trustees combine over the same anchored counted extent ([[tally]], Tally window), so their openings still pass, and the missing events are the required entries that 4.4 and 5.6 must find on L2 (T-25, T-71); while those are unverifiable, so is the verdict. Under definition versions 3 and 4 the cells come from the definition as stated until 2.8 recomputes them (T-16). No fixture yet reaches a sealed, authenticated board with ballots, so these steps are exercised on synthetic inputs, not end to end (P1-20). Until `s_S` is known, a board whose contract-path delivery records or ordinary ballots lie in the anchored extent never reaches a counted set (step 2; [Selection](#selection), conditions 4 and 5), and an honest election whose trustees state destruction between `earliest` and `latest` leaves 8.5 unverifiable. Delivery under ballot version 3 (definition version 5) waits on `@abolishus/crypto` reading it. The seal (`lastSegment`) is the bundle's, so a clock whose seal ends before the destruction window can make an honest seat look `destruction-missing`, again changing only a report-only row.

### Close check

Wherever the counted set's delivery has run (5.9 passed, [Counted set and tally](#counted-set-and-tally), step 3), the verifier decides 6.3 by [[close]]'s Close head and Close check over the sealed board. Until then 6.3 takes the row 5.9 takes: `not-reached` (or `not-implemented` and `unsupported-version`, with the same `at`) wherever step 1 or 2 there stops 5.9. The close head never decides which ballots count; 6.3 only fails the election when a late ordinary ballot would change a counted set (T-35, T-45, T-54).

1. **`L_δ`** is the last finalized L1 block whose timestamp is at or before `closes_at + l1_inclusion_bound`, found in the format-5 bundle's run of L1 headers (Bundle; [[close]], Terms). If the run's first block is after that time, or its head isn't after it (a later block could still be at or before it), 6.3 is unverifiable with `l1-blocks-short` and `at` `{}`.
2. **The statements** are, in the anchored extent, of entries as in [Counted set and tally](#counted-set-and-tally) step 2, every payload of type `0x0015` (through the board path, with its segment; only board-entry versions 5 to 7 carry one, and each fixes it at version 1), and the `record` of every contract-event record that passes the event check as the board's `CloseStatementSubmitted` (through the contract path, with its `l2_timestamp`; only contract-event versions 3 and 4 frame one). A contract-path statement is in time by that timestamp, which only 4.4's replay authenticates, so unless 4.4 passed the first entry carrying one makes 6.3 unverifiable with `not-reached` and `at` `{"entry": n}` (T-35, T-71). Statements are judged by their own window wherever they are, so the head is the same over the counted extent and the sealed one ([[close]], Close head).
3. **The head.** [[close]]'s Close head judges every statement in copy order against the definition's hash, the default panel's registered key set, `L_δ` and `t_C`, `s_C` from the definition and the bundle's clock, and gives each seat's code and the close head `B`, the `k`-th largest counted claim, or none with fewer than `k` counted seats. The floor is not read: it needs the pinned dispute games, read from L1 state, and it only ever reports, so no claim is listed `close-below-floor` and no verdict changes for it ([[close]], The floor).
4. **The ballots.** The close check compares the counted extent's admitted ballots by path, and an ordinary ballot by its L2 block, which only 4.4's replay authenticates; selection (6.1) already waits on 4.4 for every ordinary ballot of the anchored extent, so this release judges boards whose admitted ballots all came by the board path, and an ordinary or relayed one makes 6.3 unverifiable with `not-implemented` at its entry. [[close]] takes the admitted ballots before repeats; with board-path ballots alone, the ones 5.7 rejected are left out, which changes no counted set, since a repeat has its original's (`tier`, `ν`, `M`) and path. A release that judges ordinary ballots must pass them in, since a timely repeat keeps a ballot whose first copy is late.
5. **The row.** [[close]]'s Close check runs with `B`, the admitted ballots and the delivery check's verdicts by ballot hash. With no head the close is unchecked and 6.3 passes; with a head it fails `close-contested` with `at` `{"cell": c}`, the first cell whose counted set differs without the late ordinary ballots, and passes otherwise. The report's `close` gives `head` (`B` as a decimal string, or `null`), `lDelta` (`number` decimal, `hash` hex), `seats` (each registered seat ascending, with `seat`, `code` and, for `close-counted`, `claim`), `statements` (each in copy order with `entry`, `code` and `decodeError`, `seat` or `signer` as [[close]] attributes it, `seat` `null` for a board-path `close-late`), `claims` (every distinct valid claim, by number then hash, each `number` and `hash`), `late` (the late ordinary ballots' entries) and, with no head, `unchecked` (each counted ballot with no copy outside the ordinary path).

**Residuals.** The run of headers and the copy are local inputs, so a crafted bundle can move `L_δ`, the statements' verdicts and the head, and so the row, never the verdict (T-53). The board path's close statements are the operator's to board: one it withholds leaves the seat `close-missing`, never a failure, and `n − k + 1` silent seats leave the close unchecked ([[close]], Residuals; T-54). Without the floor, a low claim a resolved dispute game refutes is not reported against its seat.

### Releases

Under a live definition (version 6 or 7 with `results_mode` 2), wherever 7.1 passes, the verifier recomputes what [[tally]] (Live results) fixes, from the sealed board, the definition, the registered key set and the bundle's run of finalized L1 headers, and checks and reports the running openings against it (7.5, 7.6, and 8.2's `live-final-batch`). Nothing here reads a release, a coordinator's schedule or the operator's word: every value below is one an honest node computes from the same fixed snapshots ([[tally]], What a node does), so a release the verifier recomputes differently is the opening's breach, never the verifier's (T-16, T-29, T-34). Running totals never decide the result, which is the final tally's (7.1 to 7.3); 7.5 fails only on evidence that binding is broken.

1. **When it runs.** Under a sealed definition (versions 1 to 5, or 6 and 7 with `results_mode` 1) there are no releases, and no running opening can be on the board, whose board-entry version refuses `0x0018` (4.1; [[tally]], Tally-opening version 2): 7.5 and 7.6 pass, and 8.2 reports no `live-final-batch`. Under a live one, unless 7.1 passed ([Counted set and tally](#counted-set-and-tally), step 4), both are unverifiable with `not-reached` and `at` `{}`; 7.1's pass means 6.1 passed, so the board is sealed and authenticated and every snapshot is fixed (each ends before close, [[tally]], Schedule), and only the anchored extent is read. Under a tally-opening pin other than 2 they are unverifiable with `unsupported-version` and `at` `{}` (T-36); [[P2-15]] part 3 extends [Counted set and tally](#counted-set-and-tally), step 5, which today runs 7.1 to 7.3 under pin 1 alone, to pin 2 under a live definition, which fixes the same tally-opening checks (Tally-opening version 2, [[tally]]). This release reads no definition version 7 and fails every live definition at 2.3 (Definition), so it reports 7.5 and 7.6 unverifiable with `not-implemented`, with no `at`, as every check it doesn't build, under every definition, sealed ones included, until [[P2-15]] part 3 builds this section; the steps below are what that release does.
2. **The snapshots.** From the definition's `opens_at`, `closes_at` and `live_every` and the bundle's clock, the scheduled snapshots are `σ_r = s_open + r · live_every − 1` for `r = 1, 2, …` while `σ_r < s_close` ([[tally]], Schedule). Snapshot `r`'s L1 head `h_r` is the last block of the bundle's run of finalized L1 headers whose timestamp is before the end of period `σ_r`, `epoch + (σ_r + 1) · period`. If for some `r` the run's first block isn't before that time, or its head isn't at or after it (a block of the run could be missing at the end), 7.5 and 7.6 are unverifiable with `l1-blocks-short` and `at` `{"snapshot": r}`, the first such `r`. A run that covers 5.8 (from an hour before `opens_at` to the first block after `closes_at`) covers every snapshot. A missing slot is no gap: the run holds every block, and `h_r` is simply the last one before the time.
3. **The running sets.** Snapshot `r`'s entries, `S_r`, are the anchored extent's entries with `segment ≤ σ_r`. For each tier and each nullifier of it that isn't in an earlier running set of the tier, its ballots in `S_r` (ballot entries of either path that decode, carry the definition's `election_id` and name the tier, 5.4's `ballot-tier` or `ballot-cell` passing) are read with `h_r` as the finalized L1 head, each copy by its own entry:
   - a ballot whose membership check (5.1 to 5.3) needs a rolling step that isn't final from L1 blocks at or before `h_r` ([[membership]], Root clock and steps) is **pending**, and counts toward condition 1;
   - otherwise one whose membership check fails doesn't count;
   - otherwise one that fails any other admission check (5.4, 5.5, 5.7, or 5.8 against the run of headers) is **rejected**, and counts; under 5.8 a ballot whose L1 reference names a block above `h_r` is **pending** instead, and counts; a ballot that is neither is **admitted** at `r`.

   Copies with the same message `M` are one ballot (5.7): it counts if any of its copies in `S_r` counts, and is admitted at `r` if any is, since a copy that fails admission never counts as an earlier ballot (R4). So a copy the operator boards with a broken proof ahead of a voter's real one, or a copy rejected for its own window ahead of a timely one, changes nothing. The nullifier enters cell `c`'s running set `R_{r,c}` with ballot `b` if exactly one ballot counts, it is admitted at `r`, it names cell `c` (under definition version 6 or 7 the cell its record names, as 7.1 places it), and it is **fully receipted** in `S_r`: for every qualified seat of every panel the definition has, `S_r` holds a share receipt for `b`, through either path, that passes [[delivery]]'s receipt checks with the registered key set (Delivery check (version 2)), each read by its entry's segment, which bounds its submission. A pair of a receipt batch never counts: ballot versions 4 and 5, the only ones a live definition pins, fix no batch version, so 5.9 rejects a batch under them, and an honest node never counts one ([[delivery]], Versions). A posting never lets a ballot enter. Once in, it stays with `b` in every later running set of its cell ([[tally]], Running set). Every value here is stable: `S_r` and `h_r` only grow with `r`, admission is stable (R4), and boarded receipts stay. A ballot's L1 reference or step that becomes final only after `h_r` is read as pending at `r` even though the verifier, after close, can decide it, since an honest node at `r` could not.

4. **The release choice.** For each tier, with `B` the definition's `live_batch`, the decision at each `r ≥ 2` releases the latest candidate `q` from `r − 1` down to just after the latest chosen release that passes rule 1 (batch) and rule 2 (lag) in every cell of the tier, cells in partition order and the batch before the lag in each, or nothing ([[tally]], Release choice). A chosen release stays chosen whether or not any opening of it reaches the board, and counts in every later decision.
5. **The running openings** are the payloads of type `0x0018` of every entry of the anchored extent that decodes as a board entry under the pinned version and carries the definition's `election_id`. Each is decoded strictly under version 1; one that doesn't decode is a rejected entry (`code` `decode`, with `decodeError`; 8.3). A decoded one is an **opening of release `q` in cell `c`** if its `definition_hash` is the definition's, its `cell` is `c`, a position in the partition (as for tally openings, [Tally openings](#tally-openings), step 2), and its `snapshot` is `q`, a release step 4 chose for `c`'s tier; otherwise it is **outside the schedule**. Its `signer` is the seat its signature attributes it to ([[tally]], Running opening record, Signature), or `null`. Its breaks of the boarding rule ([[tally]], Running opening record, Boarding), in this order: `running-stray` if it names another definition or a cell the partition doesn't have, with no other break but `running-unattributed`; `running-unscheduled` if it names a cell of the partition and a `snapshot` that isn't a chosen release of the cell's tier; `running-missing` if its number of entries isn't `m`, the definition's option total; for an opening of a release with `m` entries, `running-aggregate` if its `aggregate_hash` isn't the cell's over `R_{q,c}`, and otherwise `running-opening`, with `option`, the first option it doesn't open (`g^{V_j} · h^{R_j} ≠ Ĉ_{q,c,j}`), if any; `running-unattributed` if its signature attributes it to no seat; and, for an opening of a release attributed to a seat when an earlier entry carries an opening of the same release and cell attributed to the same seat, whatever that one's checks find, with `of`, the first such entry's position: `running-repeat` if its signed message `m` is the same as that one's, which anyone can replay, and `running-second` otherwise. An opening of a release **passes** if it has none of `running-missing`, `running-aggregate` and `running-opening`. An unscheduled opening whose `snapshot` `q` is a scheduled snapshot also **discloses** if it would pass against `R_{q,c}` as an opening of `q` would: it is a count over a set the batch rule never bounded against the releases ([[tally]], Running opening record, Boarding; T-16).
6. **The rows.** 7.5 runs over each cell in partition order and each chosen release of its tier in snapshot order: it fails with `running-conflict` if two passing openings of the release and cell have different `opening` lists (the `(V, R)` per option; openings by different seats differ in `signer` and `signature`, which is no conflict), then with `running-range` and `option`, the first option whose `V_{q,c,j}`, read as an integer from 0 to `ℓ − 1`, exceeds `|R_{q,c}|`, then with `running-question-range` and `question`, the first question whose options' counts sum outside `min_q · |R_{q,c}|` to `max_q · |R_{q,c}|` ([[tally]], Opening checks), each on the first passing opening and with `at` `{"cell": c, "snapshot": q}` plus `option` or `question`; it passes if no release and cell fails. 7.6 fails with the `code`, or the first break's code, and `at` `{"entry": n}` (with `decodeError` for `decode`) of the first running opening that has either, and passes if none has, also when the board holds none. Every break is a record the operator should have refused, so it is reported against the operator, and, except `running-repeat`, against its signer, if any: the board checks passed (step 1), so the verifier's snapshots and running sets are the ones an honest node computed, and a seat signs a running opening only of a release it computed (T-29). 7.6 is report-only.
7. **The final tally against releases (8.2).** For each cell whose tier chose `m ≥ 1` releases, numbered `1` to `m` in snapshot order, every ballot in some release first entered at release `u + 1` for one `u` from 0 to `m − 1` (released ballots stay), and the final tally's counted set (7.1) holds it or not. Let `x_u` be those that entered at release `u + 1` and are counted, `y_u` those that entered there and aren't (a re-voter whose new ballot counts, a tie, an exclusion), and `z` the counted ballots in no release. The cut `d` ([[tally]], The final tally against releases) is the least non-zero size among, in this order: each `y_u`, `u` ascending; `z`, or each `x_u` if `z` is empty; and each `x_u ∪ y_u`. These are the edges entering the vertex sets of [[tally]]'s graph with the final tally as vertex `m + 1`, grouped by whether a set holds `m` and `m + 1` (every edge ends at one of them), so `d` is the least positive directed cut, the same as the maximum flow computes; the vectors check both. The cell reports `d`, `flagged` when `d < B`, and the **side**, the first of those sets in that order whose size is `d`, with its kind (`uncounted`, `unreleased`, `counted` or `entered`), its release `u + 1` (`null` for `unreleased`) and its ballots by the entry of their first copy, ascending. A cell whose tier chose no release reports none: its only total is the final one, which 8.2's small-count rule already covers. The flag never fails anything.

The report's `releases` gives `snapshots` (each `snapshot` `r` with `segment` `σ_r` and `l1Head`, `number` and `hash`), `tiers` (each tier in `electorate` order with `tier`, `decisions`, each with `at`, `release` (`q` or `null`) and `refused`, each earlier candidate tried with the rule it failed, `batch` or `lag`, and `releases`, each chosen `snapshot` with the tier's `counts`, the per-option sums of its cells' counts where every cell of the tier has counts for it, or `null`), `cells` (each cell in partition order with `cell`, `tier`, `releases`, each chosen release of its tier with `snapshot`, `size` (`|R_{q,c}|`), `entered` (the entries since the previous chosen release), `counts` (one decimal string per option, from its first passing opening, or `null`) and `signers` (the seats its passing openings are attributed to, ascending), then `finalBatch` (`cut`, `flagged` and `side`, with `kind`, `release` and `ballots`), or `null`) and `openings` (each running-opening entry in copy order with `entry`, then `code` and `decodeError`, or `cell`, `snapshot`, `signer` (a seat or `null`), `kind` (`release` or `outside-schedule`), for an opening of a release `passes`, for an unscheduled one `discloses`, then `breaks`, each with its `code` and, for `running-second` and `running-repeat`, `of`, and for `running-opening`, `option`, then `blamed`, the seat reported beside the operator, or `null`).

**Residuals.** The copy and the run of headers are local inputs, so a crafted bundle can change the running sets, the releases and every row here, never the verdict, which stays unverifiable while any input is (T-53). Running totals rest on [[tally]]'s rules, so the residuals of live results apply (padding, operator withholding until [[P2-13]]'s check exists, trustee-withheld receipts; [[tally]], Residuals of live results): the verifier recomputes the releases an honest node made, and can't tell whether a quiet interval was made quiet. A release the operator didn't board is reported with no counts, never as a failure ([[tally]], Residuals of live results, Suppressed releases). The release choice counts every chosen release, published or not, so `live-final-batch` is computed over releases some of which no one may have seen; that can only lower `d`, and over-flags rather than misses. No fixture yet reaches a live election, so `live-verifier.json`'s model and `running-opening.json`'s records exercise these steps, not an end-to-end run ([[P2-15]] part 7).

### Contract events

For formats 3 to 5, wherever the definition gives the board checks their inputs (Definition), the verifier runs the part of 4.4 that the board copy decides by itself: every contract-event record of the election on the copy passes the event check ([[contracts]], Contract-event record, Event check). Only the board operator boards a contract-event record, of a log one of our contracts emitted, and every log the release contracts emit passes the check, so a record that fails it, or doesn't decode, is the operator's and never a submitter's: it fails 4.4, an election check (T-17, T-31, T-53, T-71).

1. **When it runs.** Under a profile whose contract-event pin (`0x0008`) isn't version 1 to 7, 4.4 is unverifiable with `unsupported-version` and `at` `{}`: a later release may read that version (T-36). (Every well-formed definition pins `0x0008` exactly once, by 2.1's `profile-types`.) Otherwise it runs whatever 2.3 finds, since the check reads only the record's own bytes, the contract-event version and the definition's L2 addresses, and it needs no panel, so format 3 runs it as format 4 does.
2. **The records** are the payloads of type `0x0008` of every entry of the copy, by position from 0, that decodes as a board entry under the pinned version and carries the definition's `election_id`; an entry that doesn't is 4.1's to report. Each is decoded strictly under the pinned contract-event version (a record of the other version is `profile-mismatch`, [[contracts]], Layout (versions 1 to 4)) and then checked under that version's event tables against the definition's `election_registry`, `trustee_registry`, `group_registry` and `board`, which 2.1's `chain` rule keeps pairwise distinct.
3. **The anchored extent.** Only the anchored board is anyone's claim, and the board checks ignore every entry past the anchored extent ([[board]], Board checks), so no one can fail an election by appending entries to a copy of its board (T-53). When 4.1 and 4.2 pass, only the entries inside the anchored extent (the `entries − unauthenticated` first ones of `board` in the report) are read. When they don't, the copy isn't authenticated, and every entry is read, but a record that would fail 4.4 leaves it unverifiable instead, with the same code and `at`.
4. **The L1 origins.** Each record read that passes the event check as the election registry's `ElectionCreated` or `DefinitionRegistered` naming the definition's `election_id` is then checked as [[contracts]] (Election registry, The L1 origin) says, in that order: `l1-origin-unknown` if the bundle's run of finalized L1 headers (format 5) holds a block of the origin's number whose hash or timestamp isn't the origin's (a run that doesn't hold that number decides nothing, so without a run the check isn't made); `l1-origin-drift` unless the origin's timestamp is at or before the record's `l2_timestamp`, by at most the `max_sequencer_drift` this release pins, 1,800 seconds (Base's, [[0004-l2-choice]]; never the definition's own value); and, for `DefinitionRegistered`, `l1-origin-order` if its origin's number or timestamp is below that of the first record read that passes as the same election's `ElectionCreated` (none read, nothing compared). Only the election's own two events are judged, never another election's in the shared sequence (T-71, T-69, T-34).
5. **The row.** The first record read, in copy order, that doesn't decode gives `decode` with `at` `{"entry": n, "decodeError": <code>}`, and the first that fails the event check or an L1-origin check gives its code (`unknown-contract`, `unknown-event`, `event-topics`, `event-data`, `l1-origin-unknown`, `l1-origin-drift` or `l1-origin-order`) with `at` `{"entry": n}`: 4.4 fails with it inside the anchored extent, and is unverifiable with it otherwise (step 3). If no record read fails, including a copy holding none, 4.4 is unverifiable with `not-implemented`, never a pass: what it doesn't decide yet (below) is part of 4.4 itself. A later release that decides more may report another code at an earlier entry, or a failure where this one is unverifiable, never a pass where this one fails: a record that fails the event check fails under its version's frozen tables for good ([[contracts]], Event check).

**What it doesn't decide yet.** The required entries: which events must be boarded (the events that name the election, its tiers' group creations and their additions and removals up to each `root_l2_block`, self-paid ones included, its panel's key and ceremony registrations) is known only from the L2, through the archive (P4-3) and the L2 reads that 2.4, 2.5 and 3.1 wait on. Tier 1 boarding (below) is stated, and waits on the same: which additions count is known only from the registry's whole archived history. The accumulator's replay ([[contracts]], Event accumulator, Verification), over each contract's whole archived sequence against storage proofs at output roots settled on L1, with the TEE-only roots annotated (P4-3, P1-19 part 3b), which is also what authenticates the `l2_timestamp` step 4 compares with an origin, and the first check of step 4 for an origin older than the run of headers, which needs finalized L1 from the creation on (trusting a finalized head is part 3b's).

**Tier 1 boarding.** Anyone may log a `Tier1MemberAdded` naming any Tier 1 group, at about 1.5 million gas, and the registry can't tell one that counts from one that doesn't ([[contracts]], Group registry, Tier 1 additions, Only checks no other addition can change). So for each Tier 1 group a definition lists, the board MUST carry the group's `GroupCreated` and exactly its additions that [[vouching]] (Counting across the deployment) counts, in blocks up to its tier's `root_l2_block` (a rolling tier's through its last accepted step, as 2.4 and [[P2-17]] part 2b-2 require), and need carry nothing else of the group registry for it (T-52, T-53, T-06):

- **Counted additions only.** Counted additions are bounded by the Tier 2 members' slots (each spends `VOUCH_K` slots, of the `VOUCH_SLOTS` each Tier 2 secret has, for good), never by what senders pay; uncounted ones (made-up roots, copies of counted additions) are not, so requiring them would let anyone grow every Tier 1 election's board without bound, the cost the shared event sequence exists to avoid ([[contracts]], Election registry, The shared event sequence; T-52). Each counted addition is one leaf, in log order, and the board's additions of the group in those blocks are exactly the counted ones (below), so a board that passes 4.4 shows the tier's leaves and member count, as it does a Tier 0 tier's.
- **The rest stays in the archive.** Whether a boarded addition counts, and that none is missing, rests on the registry's whole Tier 1 and Tier 2 history in those blocks: other groups' additions (slots are deployment-wide), the Tier 2 groups' records that fix each root a vouch names, and any record that breaks that history. 2.4 replays them from the archive, authenticated by the accumulator, never from the board. A Tier 2 group the definition also names as a tier is boarded for that tier under 4.4's rule for any tier (its creation, additions and removals up to its `root_l2_block`); its records after that block, which a vouch's root may need, stay in the archive. A `MembersAdded` or `MembersRemoved` naming a Tier 1 group changes nothing in it ([[vouching]], Counted additions), so none is required.
- **The count decides, and the board must agree.** The tier's leaves are 2.4's count over the archive, never the operator's selection, and 4.4 compares the board with that count once its required entries are decided: a counted addition missing from the board fails 4.4, as any missing required event does, and so does a boarded `Tier1MemberAdded` naming the group, in those blocks, that doesn't count, so the board can neither hide a member nor show junk as one. Both are the operator's, since only the operator boards a contract-event record, and neither changes a tier tree. A boarded `Tier1MemberAdded` naming a group the definition doesn't list for a Tier 1 tier, or in a later block, fails nothing: it passes the event check like any other event of a shared contract on the board (T-53, T-06, T-13). A counted addition boarded twice is left to the Residuals below.
- **The operator's replay.** The board operator decides what to board by its own replay of the counting rule. An addition's verdict depends only on earlier events ([[vouching]], Order), so it is fixed once the addition's L2 block is final, and boarding it then never needs revisiting.

**Residuals.** No ordering rule is applied to the board's records. The board carries only the events the election's checks use, out of sequences shared by every election, so the `n` of one contract's boarded records have gaps, and rule 1 of Event accumulator, Verification (numbered with no gap, `b` and `τ` never decreasing) is defined over a contract's whole archived sequence, not a board's subset. Neither [[contracts]] nor [[board]] says in what order the operator boards contract events, late ones included ([[tally]], Tally window: contract events are always boarded), so whether one contract's boarded records must appear in increasing `n`, and whether a record boarded twice fails anything, is open (P1-18); until it is decided, a reordered or repeated record changes no row here, and the accumulator's replay still catches a record that isn't the contract's own. Under step 3, a copy the anchors don't authenticate can change 4.4's code and `at`, never its status between pass and fail. The L2 addresses records are checked against come from the definition, which is unauthenticated until 2.1 proves its hash against the L2 election registry: a crafted definition naming other contracts (with the same `election_id` and `l1_anchor`) makes every honest anchored record fail `unknown-contract`, turning `verdictAgainstInputs` to `failed`, never the verdict, as with 1.3's `membership-key` (T-53).

### Procedure

1. Read and parse the bundle, or reject it.
2. Split `board.bin`, or read the copy from `blocks.car` ([Board by CID](#board-by-cid)).
3. For formats 3 to 5, read the definition ([Definition](#definition)). If it stops the board checks, 4.4 is unverifiable with `not-reached`; go to step 6.
4. For formats 2 to 4, read the anchors and `now` from L1 ([Anchors from L1](#anchors-from-l1)). If that stops with a code, 4.1 is unverifiable with `not-reached` and 4.2 unverifiable with the code; go to step 6.
5. Run the board checks of [[board]] (Board checks) with the election identifier, pinned version, anchors, clock and `now`. They stop at the first failure, and the code decides the rows of 4.1 and 4.2:

| Outcome                                                                                                   | 4.1                         | 4.2                         |
| --------------------------------------------------------------------------------------------------------- | --------------------------- | --------------------------- |
| All pass                                                                                                  | pass                        | pass                        |
| `wrong-election` at a checkpoint, `checkpoint-equivocation`, `checkpoint-size`, `checkpoint-inconsistent` | unverifiable, `not-reached` | fail, with the code         |
| `checkpoint-missing`, `copy-mismatch`                                                                     | unverifiable, with the code | unverifiable, with the code |
| `decode`, `wrong-election` at an entry, `wrong-index`, `segment-decreased`, `opening-order`               | fail, with the code         | unverifiable, `not-reached` |
| `checkpoint-boundary`, `checkpoint-cid`, `unanchored`, `unsealed`                                         | pass                        | fail, with the code         |

6. For formats 3 to 5, unless step 3 stopped the board checks, run 4.4's event check over the copy's contract-event records ([Contract events](#contract-events)), with the anchored extent of step 5 when 4.1 and 4.2 pass. For formats 4 and 5, unless step 3 stopped the board checks, also run the key-ceremony checks ([Key ceremony](#key-ceremony)), then ballot admission ([Ballot admission](#ballot-admission)), with, for format 5, the L1 references ([L1 references](#l1-references)), selection ([Selection](#selection)) the counted set ([Counted set and tally](#counted-set-and-tally)) and the close check ([Close check](#close-check)), the openings ([Spoiled-ballot openings](#spoiled-ballot-openings)) and the tally openings ([Tally openings](#tally-openings)); if it did, 2.5, 3.1, 3.2, 5.1 to 5.5, 5.7, 5.9, 6.2, 6.3, 7.1 to 7.4 and 8.5, and for format 5 also 5.8 and 6.1, are unverifiable with `not-reached`.
7. Unless step 3 stopped the board checks, report 2.9 (passing under definition versions 1 and 3, and as [Receipt keys from L1](#receipt-keys-from-l1) says under versions 4 and 5) for formats 3 to 5; report 8.5 unverifiable with `not-applicable` if the board-entry version they use (the bundle's for formats 1 and 2, the definition's for 3 to 5) doesn't allow `0x000f` (8.5), and, for formats 3 to 5, 1.3 failed with `membership-key` and `at` `{}` if the profile pins ballot version 1, 2, 3 or 4 (versions 2 to 4 prove membership of their cell's tree under the same key, [[ballot-validity]], Ballot record (version 2), Ballot record (version 3) and Ballot record (version 4)) and the definition's `membership_vk_hash` isn't the pinned depth-32 key's; under any other ballot pin 1.3 isn't failed here, since a later release may pin that version's key (T-36) (1.3 also covers the keys inside verifier contracts, which the verifier doesn't read yet, so it never passes). Report every other check unverifiable with `not-implemented`.

### Verdicts

- `verdictAgainstInputs` is `failed` if any election check fails, otherwise `unverifiable` if any election or admission check is unverifiable, otherwise `verified`. Report-only checks never change it. An admission check that fails only rejects its entry. One that can't be evaluated makes 6.1 unverifiable (Principles), so it counts as unverifiable here.
- `verdict` equals `verdictAgainstInputs` when every input is authenticated, and is `unverifiable` otherwise. Anyone can make a bundle whose `verdictAgainstInputs` is `failed`, so it is never the election's verdict: a consumer never shows it without `verdict` and `inputs` beside it (T-53).

### Command line

`abolish-verify [--max-board-bytes <n>] [--gateway <url>]... [--] <bundle-directory>` runs the procedure over one bundle. `--max-board-bytes` sets the byte budget of a copy read by CID ([Board by CID](#board-by-cid)), a positive decimal integer with no sign or leading zero, below `2^53`. Each `--gateway` names a gateway the copy's blocks are asked of, in the order given (Board by CID, Gateways), up to 16. On success it writes the report to stdout as JSON followed by a newline, and a summary to stderr. A rejected bundle writes no report, only the reason, to stderr.

The exit code depends on `verdict` alone, never on `verdictAgainstInputs`, so a script that reads only the exit code can't be made to read a crafted bundle's findings as the election's (T-53):

| Code | Meaning                                                                                                                                          |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 0    | `verdict` is `verified`                                                                                                                          |
| 20   | `verdict` is `failed`                                                                                                                            |
| 21   | `verdict` is `unverifiable`                                                                                                                      |
| 22   | The bundle was rejected; there is no report                                                                                                      |
| 64   | Usage: no bundle, an empty one, more than one, an unknown option, a budget that isn't one, a gateway that isn't one or more than 16, or `--help` |

0 means verified and nothing else, which is why `--help` (whose text goes to stdout, unlike every other usage error's) exits 64. No code is one Node exits with on its own: 1 for an uncaught error, 3 to 14 for its internal failures, over 128 for a signal. Any code not in the table, including 1 when the report can't be written, is a failure of the verifier itself and says nothing about the election.

The summary's first line is `verdict: <verdict>`. While any input is unauthenticated it continues ` (unauthenticated inputs: <names>; against those inputs: <verdictAgainstInputs>)`, so `verdictAgainstInputs` is never shown without `verdict` and the inputs beside it. A line follows for each failed check: its `id`, `fail`, its `code` and its `at` as JSON. Where the report has `tiers`, the results follow: a header, `results per tier, never summed across tiers:` when `verdict` is `verified` and `results per tier, not verified (verdict: <verdict>):` otherwise, so figures from a bundle that doesn't verify never read as the election's result (T-53); then a line for each tier in `electorate` order, `tier <t>: <counted> counted; counts <c_1>, …, <c_m>` (its `counts` in option order) or, where it has no `counts`, `; no counts (an opening of its cells didn't pass 7.2)`, with Tier 0 written `tier 0 (not Sybil-resistant)` (8.1; T-01); and under a tier with more than one cell, a line for each of its cells in partition order, `cell <c>: <counted> counted;` then its `counts` the same way or `no counts (<code>)`. No line sums two tiers ([[PROJECT_BRIEF]], Design direction; T-01). Anything quoted from the bundle (a rejected member name, say) is printed as printable ASCII only: every other character and the backslash are written as `\u{<hex>}`, so a bundle can't put control or bidirectional characters on a terminal.
