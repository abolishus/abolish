# @abolishus/api

The public API: implements the oRPC contract in [`@abolishus/api-contract`](../../packages/api-contract) over `node:http`. Internal and source-only; AGPL-3.0-only.

Every answer is a claim the caller checks with `@abolishus/crypto`: a definition against its hash in the L2 election registry, entries with `checkBoard`, heads and proofs against anchored checkpoints (T-23, T-24, T-34). The handlers parse, call `@abolishus/core` and serialise; no protocol logic lives here.

## Transport

- Inputs come from the query (GET) or a JSON body (POST) alone. A GET with a body, and a POST with a query string, are refused, so nothing keyed on the URL sees a different request (T-31).
- At most `maxInFlight` requests (32 by default) are handled at once, counted from the first byte; past it a request gets 503 before anything is read. A board page can hold 8 MiB and costs several times that in memory, so this bounds memory however many clients connect (T-52). A connection idle in both directions for 15 s is destroyed, a request must arrive within 30 s (headers within 10 s), and a request holding a slot for 60 s is destroyed, so a client that stalls its upload, stops reading its answer or reads it slowly loses its slot. A few sockets can still take every slot for up to a minute at a time; per-address limits belong to the proxy in front (P2-11).
- POST bodies: `application/json` only (oRPC's own reader would accept multipart and files of any size), at most `MAX_REQUEST_BODY` bytes, cut off as soon as they exceed it (T-52).
- `cache-control: no-store` and `x-content-type-options: nosniff` on every response.
- **CORS for the ballot client.** `corsOrigins` (`API_CORS_ORIGINS`, comma-separated) lists the exact origins whose pages may read answers: each must be an `https:` origin, or `http:` on a loopback host. A request from a listed origin gets `access-control-allow-origin` with that origin (refusals included, so the client can tell why); a preflight is answered only for a listed origin, the procedure's own method and no request header but `content-type`. Credentials are never allowed, so a browser sends no cookie (T-10). Without the list no CORS header is sent. Every route is public, so the list only keeps other sites' pages from using their visitors' browsers as clients (T-52).
- **No account credentials (T-10).** A request carrying an account cookie (any cookie named under `ACCOUNT_COOKIE_PREFIX`, with or without `__Secure-` or `__Host-`) or any `Authorization` header is refused with 400 before anything else is read. Accounts live on `apps/web`'s origin (`@abolishus/core`, Accounts), whose host-only cookies never reach this host from a browser, so one arriving means a misconfigured or hostile client; refusing it means no ballot or board request is ever handled next to an account.

## The ceremony's coordinator

The seats' side of the key ceremony's coordinator ([[0032-poll-creation-operations]], rule 5; P2-22 part 4c-2): `apps/trustee-node`'s `HttpCoordinator` routes, beside the contract rather than in it, since their bodies are that transport's binary envelopes (`apps/trustee-node`, README, Transport). Each parses, calls core's coordinator and answers by status; the worker's `{ceremony-coordinate}` job opens runs and closes rounds at their deadlines.

| Route                                   | Answer                                                                                                                     |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `GET  /v1/ceremony/seats/{i}/requests`  | 200, `application/octet-stream`: core's `coordinatorRequests` for seat `i` (16 at most; none for a seat outside the panel) |
| `POST /v1/ceremony/seats/{i}/messages`  | core's `postCeremonyMessage`: 204 kept (or already kept: a retry is answered as the first post), 403 refused, 409 not open |
| `POST /v1/ceremony/seats/{i}/approvals` | core's `postCeremonyApproval`, answered the same way                                                                       |

- Seats don't authenticate: core keeps a message only if it is the seat's own, signed over the closed rounds, and an approval only if it verifies under the seat's pinned key, so anyone else's post changes nothing (T-54).
- `{i}` is 1 to 99 with no leading zero, and a query string matches no route. A POST body is `application/octet-stream` of at most `MAX_CEREMONY_POST` bytes (one transcript record and its stub hash), and one with no decoding is refused with 400; a GET with a body is refused.
- Core's work for them (the fit check's signatures and the database) runs under slots of their own (`ceremony.maxInFlight`, 4 by default) inside the server's, taken only once the body is read: past them a request gets 503, so posts that each verify up to 48 signatures never take the slots ballots and the board are served from, and a stalled upload holds none (T-52). The slots bound concurrency, not CPU.
- The request log names each by its template (`POST /v1/ceremony/seats/{seat}/messages`), never the seat's index.
- The coordinator needs every one of `API_CEREMONY_PANEL_THRESHOLD` and `API_CEREMONY_PANEL_KEYS` (the default panel, as the worker's `POLL_STUB_` variables give it), `API_CEREMONY_L2_CHAIN_ID` and `API_CEREMONY_TRUSTEE_REGISTRY` (`0x` and 40 hex digits), or none, in which case the routes answer 503. The server refuses to start with only some, or with a threshold and keys that aren't a panel. They are checked for form only: core refuses every post for a stub that doesn't pin them, so values that differ from the worker's end runs at their deadlines, and the worker logs it.

## The intake relay

The operator's route to each seat's intake ([[delivery]], Client rules 4; P2-8 part 3c-1b-2b-2b-2a): the ballot client posts `apps/trustee-node`'s delivery envelope (`Delivery`: the election's stub and approved transcript, the whole ballot record and the seat's `ct_i`) to `POST /v1/intake/seats/{i}`, and the relay sends it on to seat `i`'s intake endpoint and answers as that endpoint does: 200 with the share receipt (`application/octet-stream`), 422 with the refusal's code (`text/plain`), 503 with `retry-after` when the node's queue or the relay's slots are full. A node that is down, times out (25 s), negotiates anything but the hybrid group, or answers anything else (another status or type, a code that isn't one, more than `MAX_INTAKE_ANSWER` bytes, a redirect) is answered with 502 and logged by kind only (`intake-relay-unreachable`, `-timeout`, `-answer`).

- Nothing is judged here: the node admits the ballot and signs the receipt, and the client checks the receipt against the ballot it cast (Client rules 1), so a relay that lies can only refuse, which the client's route that bypasses the operator answers (T-25).
- **The voter's address stays here (T-11).** The node sees the API's address on a connection of its own for each delivery (no kept-alive socket), and the request carries the body, its type and length, and nothing of the client's request: no forwarding header, origin or user agent.
- **The outbound leg is post-quantum (T-39).** TLS 1.3 offering only `X25519MLKEM768`, as every intake endpoint negotiates ([[0002-everlasting-privacy]], Consequences), with the node's certificate checked against the system's roots. The inbound leg is the deployment's TLS proxy, which ADR 0002 holds to the same group; the server can't check that (P2-11).
- `{i}` is 1 to 99 with no leading zero, and a query string matches no route; a seat with no endpoint is refused with 404 before the body is read. The body is `application/octet-stream` of at most `MAX_DELIVERY` bytes (four records of up to 1 MiB each, with their lengths), and one with no decoding is refused with 400 before any node is asked.
- Deliveries are relayed under slots of their own (`intake.maxInFlight`, 8 by default) inside the server's, taken once the body is read and decodes, so a stalled upload holds none (T-52). A preflight from a listed origin is allowed for `POST` and `content-type` only, as for every route.
- The request log names the route by its template (`POST /v1/intake/seats/{seat}`), never the seat's index.
- `API_INTAKE_ENDPOINTS` lists each default-panel seat's endpoint as the release lists it, comma-separated, seat 1 first: `https:` URLs with no credentials, query or fragment, sixteen at most. Without it the route answers 503. Where the ceremony's coordinator is configured too, the server refuses to start unless the list has one endpoint per `API_CEREMONY_PANEL_KEYS` key. Author panels' seats ([[P2-16]]) aren't relayed.

## Request log (T-10, T-11)

One line per request: method, the contract route it matched (from a fixed list, never the raw URL), status and duration. Never an address, a header, a query string or a body. Internal errors, including answers that fail the contract's output schema, are logged by their kind only, since messages can quote input. The handlers' context holds the database and nothing else, so no procedure can read a cookie, a token or an address. `tests/api.test.ts` fails if any of these reaches a line.

## Running

`vp run --filter @abolishus/api start` (plain Node, no TypeScript transform: `erasableSyntaxOnly` in `tsconfig.json` and a test that starts `src/main.ts` keep it that way) with `DATABASE_URL` (a user granted `abolish_app`, never the owner), and optionally `API_HOST` (default `127.0.0.1`), `API_PORT` (default `8787`) and `API_CORS_ORIGINS`. `REDIS_URL` (the worker's Redis or Dragonfly) turns on ballot submission through the worker's queue; the worker pins the panels and the anchoring clock (`apps/worker`, Running). Tier 0 registration takes all three of `API_TIER0_GROUP` (region 0's published `group_id`), `TURNSTILE_SECRET_KEY` and `API_CHALLENGE_HOST` (the challenge origin's host), or none, and needs `REDIS_URL` for its queue; the server refuses to start with only some. The ceremony's coordinator takes its four `API_CEREMONY_` variables, or none (The ceremony's coordinator). The intake relay takes `API_INTAKE_ENDPOINTS` (The intake relay). The listing's `answered` order takes `BALLOT_ANCHOR_EPOCH` and `BALLOT_ANCHOR_PERIOD`, both or neither, with the worker's values, since it counts the voters boarded in the last week's segments by that clock; without them it answers `SORT_UNAVAILABLE`. The posting relay takes `API_POSTING_REDIS_URL` (a Redis or Dragonfly of its own that never evicts, persists or snapshots: its queue holds `m_i`, docs/spec/posting-relay.md, Queue) and `BALLOT_PINNED_PANELS` (the worker's value), both or neither, with `BALLOT_ANCHOR_EPOCH` and `BALLOT_ANCHOR_PERIOD`; the server refuses to start with only one, or with the relay's store on `REDIS_URL`'s host and port.

`src/migrate.ts` applies pending migrations to `DATABASE_SCHEMA` (default `abolish`) and exits. It connects with `DATABASE_URL` as a user granted `abolish_migrator` and switches to that role, so the tables belong to the group role rather than the login.

## Image

`vp run build` type-checks, then bundles `main.ts` and `migrate.ts` into `dist/` with every dependency inlined, plus core's migrations (`vite.config.ts`, `pack`). The `Dockerfile` puts `dist/` on the Node base pinned by digest and nothing else, so the image carries no `node_modules`, package manager or test code. Building, deploying and the database setup it expects are in [`docs/runbooks/railway.md`](../../docs/runbooks/railway.md). `tests/image.test.ts` runs the bundle copied away from the repository: `migrate.mjs` against an empty schema, then `main.mjs` as a login granted only `abolish_app`.

## Tests

`vp run --filter @abolishus/api test` needs `TEST_DATABASE_URL` and `REDIS_URL`, as `@abolishus/core`'s tests do, and runs uncached. The tests start the server on a free port and check every answer with `@abolishus/crypto`.

## Decisions

- **No Hono yet.** AGENTS.md names Hono + oRPC. Nothing so far needs middleware beyond the body bound, the log and the account-credential refusal, which `node:http` does in a few lines. Accounts (P2-5) didn't need it either: they are served by `apps/web` on its own origin, not here, so the API never handles an account request.
