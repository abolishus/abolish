# Verifier

What an independent verifier must check to accept an Abolish election result, using chain and IPFS data alone, with our servers and domains offline (G-9, T-36). `packages/verifier` implements this list, and a third party can implement it from this spec in any language. Its inputs, procedure and report are under [Inputs, procedure and report](#inputs-procedure-and-report) (P1-19).

Each check names the threats it closes and the STATUS item that specifies it. A check whose section isn't written yet is still required: until it exists, no verifier can claim the election verified. Checks marked **(P1-3)** take the shape of [[0002-everlasting-privacy]] (accepted by the owner, option B); their sections are written by P1-12 to P1-15.

## Principles

- **Trust nothing served.** Every input comes from L1, the L2, IPFS, the permanent archive or local files, and is checked against L1 anchors or the evidence it carries. Nothing is accepted because an Abolish server said so, and no Abolish server or domain is contacted (T-24, T-49, T-69).
- **Fail loudly.** Each check ends in pass, fail or unverifiable (data missing, a source unreachable, a root not yet settled, or, for the report-only 8.5 alone, not applicable). Unverifiable is never reported as pass.
- **Two kinds of check.** Anyone can post a ballot, so a bad ballot must never fail an election (T-52, T-53), and every conforming verifier must reach the same verdict on the same data (T-36):
  - **Admission checks** decide whether one ballot or opening counts: decoding of the record inside a board entry, 5.1 to 5.5, 5.7, 5.8, 6.1's admission part and 6.2. A failure rejects that entry only. A rejected entry is listed in the report (8.3), never counted and never displaces an earlier ballot (6.1, R4).
  - **Election checks** are everything else: 1.2, 1.3, 2.1 to 2.6, 2.8, 2.9, 3.x, the board-entry envelope and hash chain in 4.1, 4.2 to 4.5, 5.6, 5.9, 6.3, 7.1 to 7.3 and 8.1 to 8.4. The election is verified only if every election check passes.
  - **Report-only checks** (1.1, 2.7, 7.4, 8.5) never decide the election's verdict. 1.1 and 2.7 because their inputs come from whoever serves them, not from chain and IPFS election data: a served client or display text that doesn't match is reported loudly (1.1 as a separate client-integrity verdict, G-13), and mismatching text is treated as unavailable. 7.4 and 8.5 because they attribute and report what the board holds, while the result rests on other checks; 8.5 reports signed claims of destruction, which can't be proven, and making it decide would give any trustee a veto (T-54).
  - An admission check that can't be evaluated (its evidence is missing) never rejects the entry: it makes 6.1, and so the election, unverifiable. The archived evidence for each entry (4.4) must cover everything its admission checks need.
  - Our contracts accept a direct submission only if it passes their framing checks and, for a ballot, its membership proof, so non-members can't post at all, and revert otherwise (P1-18; [[contracts]], Board, Ballots). Framing checks every length, count, offset, enum, scalar and `field<bn254>` and the cheap part of each ristretto255 element's decoding ([[0028-board-contract-checks]], 3B), so no record whose framing is broken reaches an L2 event or the board, and no one can make 4.1 or 5.6 fail by posting junk. An element that passes framing but doesn't decode makes its record a rejected entry, like any other admission failure. The archive keeps nothing beyond the record but the event accumulators' storage proofs, so no transaction's other bytes reach it ([[contracts]], Contract-event record; [[notation]], Result-critical fields; T-17). A record that decodes but fails another admission check is boarded as a rejected entry.
- **Strict decoding first.** Every record is decoded strictly ([[notation]]) before any other check uses it, and rejected entries are reported, never skipped silently (T-31, T-52).
- **Pinned trust roots.** The verifier's release pins what can't be derived from data: the L1 and L2 chain IDs, the addresses of the anchor contract, the forced-ballot relay and our L2 contracts, the anchor's deployed clock (`epoch`, `period`, `deadline`) and anchoring authority ([[contracts]], Board anchor), the canonical L2 portal on L1, the L2 derivation rules it applies with the L2's `max_sequencer_drift` (bounding the registry events' L1 origins, 4.4) and the dispute-game types it counts as permissionless for the close statements' floor (6.3; [[close]], The floor), the release-signing identities, the commit of `main` whose contracts source the deployed contracts were built from (1.2), the long-term identity keys of the named trustees with `k` and `n` ([[0006-trustees]]), each pinned panel's **kind** (`independent`, a panel meeting every rule of [[0006-trustees]] and named by the owner, or `transitional`, held by us during launch) with, per seat, its holder's name and whether the seat is ours ([[0027-trustee-panels-and-live-results]], Part 3; 2.5 and 8.4 read them), and the verification key of every proof system it accepts, per ballot record version (Semaphore's per-depth keys, or the zero-knowledge UltraHonk key of our Noir circuit), built from reviewed source. Changing any of them is a new verifier release (T-64, T-71, T-05). No proof is ever verified under a key taken from election data alone.

## Checks

### 1. Ballot client and contracts

- 1.1 A served ballot client matches a signed, reproducible release: its bytes hash to a release hash signed by the release identity (T-41, G-13; P1-19, P2-8).
- 1.2 The bytecode at every contract address the election uses matches the release build of reviewed source, with the byte ranges of each contract's immutables masked, and every masked word equals the value the release pins for it (the anchor's clock and authority, the registry's deployment addresses and `epoch`) (T-64; P1-18, P1-19, P4-1). The release build is `forge build` of `packages/contracts` at the contracts commit the verifier's release pins (a commit on `main`), by the pinned forge, from `packages/contracts`, with the default profile and the settings in its `foundry.toml`, no `.env` file anywhere from `packages/contracts` up to the repository root, no `FOUNDRY_*` or `DAPP_*` variable and no global Foundry config, run by itself on a fresh runner in a job that runs no npm code (the procedure is in `packages/contracts/README.md`, Release build); it is never the output of the package's own build script, which runs npm code after forge. A runtime-code match alone never passes 1.2: a deployer's own initcode can return the release runtime code after writing any storage and emitting any logs. Until binding each deployment to the release creation code and pinned constructor arguments is specified and checked, 1.2 is unverifiable (`not-implemented`), whoever made the deployment, and the binding MUST be specified before any deployment (T-64; [[contracts]], Board anchor, Known-weak, Constructor effects aren't bound).
- 1.3 Every verification-key hash in the election definition (today only the membership key hash, `abolish/v1/membership-vk`, over the pinned depth-32 Semaphore key, [[membership]]), and every key inside a verifier contract the election uses, equals the pinned key for the ballot version the profile names; a definition naming any other key fails (T-05, T-04, T-64; P1-17b, P1-18).

### 2. Election definition

- 2.1 The definition decodes strictly, and its hash (`abolish/v1/election-definition`) equals the hash registered on L2 before voting opened. The election fails if the definition's own `election_registry`, the registry the release pins, shows any other definition, or any re-registration, for its `election_id`; registrations on any other contract are ignored (only its creator can register one there, so this can't be used against someone else's election). Another registration that repeats its `ceremony_transcript_hash` doesn't affect it ([[election-definition]], Stub hash; T-34, T-37; P1-10b, P1-18). It is well formed ([[election-definition]], Well-formedness); under definition versions 5 and 6 the `option-count` and `selections` rules also name the first failing question (P2-14), under version 6 `results`, `civic-sealed` and `author-panel` follow version 5's rules (P2-16), and under version 7 `rolling-class` and `rolling-tier` follow version 6's, with `electorate` reading the electorate mode (P2-17).
- 2.2 It binds the chain ID and contract addresses the ballots were submitted to, so nothing can be replayed from another chain or deployment (T-30, T-32; P1-10b).
- 2.3 Its election type (under definition version 5, each question's method) and tally scheme are ones this verifier supports, its profile pins a version for every record type the election uses, and every record the election's authors write (the definition, board-entry envelopes, the ceremony transcript) uses exactly the version its profile pins (`profile-mismatch` otherwise), and no version it pins was retired before the definition was registered. A profile that pins ballot version 1, 2, 3, 4 or 5 must pin a board-entry version that allows share receipts and complaints (3, 4 or 5), and one that pins tally-opening version 1 a board-entry version that allows destruction statements (4 or 5); one that pins any other board-entry version fails (`profile-combination`; [[delivery]], Versions; [[tally]], Destruction). A plurality or approval profile pins both, and so does a definition version 5's (ballot version 3, tally-opening version 1), so each must pin board-entry version 4 or 5. A profile whose own definition is version 3 or 4 (regional cells) must pin ballot version 2, which names its cell, and a profile that pins ballot version 2 must be a definition version 3's or 4's, since a tiers-only partition has no cells to name; and a profile pinning ballot version 2 must pin spoiled-ballot opening version 2, which opens version-2 cores, and one pinning ballot version 1 opening version 1, since an election whose ballots couldn't be challenged can't be checked as cast-as-intended (T-42, T-47; [[challenge]], Versions, Opening version 2) (`profile-combination`; [[ballot-validity]], Ballot record (version 2); [[election-definition]], Notes; [[0019-regional-cells]]). A profile whose own definition is version 5 (questions) must pin ballot version 3, which carries one range proof per question, and display-text version 2, which carries the questions' text; one that pins ballot version 3 must be a definition version 5's, one that pins display-text version 2 a definition version 5's, 6's or 7's, and one whose definition is version 1, 3 or 4 must pin display-text version 1. A display-text version this verifier doesn't know fails here rather than being unverifiable, under every definition version: a later display-text version comes with a later definition version that pins it, so releases never split on it (`profile-combination`; [[election-definition]], Notes; [[display-text]], Layout (version 2); [[0026-multi-question-ballots]]). A profile pinning ballot version 3 must pin spoiled-ballot opening version 2, which opens version-3 cores too ([[ballot-validity]], Ballot record (version 3)). Two exceptions are unverifiable with `unsupported-version` rather than failed, unless the profile fails on another ground, since a later release may know the version: a profile pinning ballot version 2 beside a spoiled-ballot opening version this verifier doesn't know, and a definition version 3 or 4 whose profile pins a ballot version it doesn't know, which a later release may define as naming its cell; and the same two for ballot version 3 and definition version 5 (T-36). A profile whose own definition is version 6 (poll class, results mode and author panel) must pin display-text version 2, ballot version 4, which carries the author half beside the default half, and spoiled-ballot opening version 3, which opens version-4 cores; a profile pinning ballot version 4 must be a definition version 6's, or a version 7's under `electorate_mode` 1, and must pin opening version 3 ([[ballot-validity]], Ballot record (version 4); [[challenge]], Opening version 3). A sealed version-6 poll without an author panel pins tally-opening version 1, which counts ballot version 4's default half, then the whole sharing ([[tally]]). A version-6 definition with an author panel fails (`profile-combination`) until [[P2-16]] part 3 specifies the author panel's ceremony and registered key set and a tally-opening version that opens each panel's half, since without them no verifier can check its key set or its count; and a live one (`results_mode` 2) also needs the tally-opening version of [[P2-15]], which fixes the running opening's ([[election-definition]], Notes; [[0027-trustee-panels-and-live-results]]). A live definition also fails (`profile-combination`, built with [[P2-15]] part 1c) if it has an author panel, or if the release pins fewer than `k` of its default panel's seats as ours, unless its profile pins a tally-opening version that fixes the nodes' withholding check ([[tally]], Live results, What a node does; [[P2-13]]). Nothing may lift the author-panel refusal for live definitions before then. As for ballot version 3, a profile pinning ballot version 4 beside a spoiled-ballot opening version this verifier doesn't know, and a definition version 6 whose profile pins a ballot version it doesn't know, are unverifiable (`unsupported-version`) rather than failed, unless the profile fails on another ground. A profile whose own definition is version 7 must pin display-text version 2 and spoiled-ballot opening version 3, and under `electorate_mode` 1 ballot version 4, as version 6 does, and under `electorate_mode` 2 (rolling) ballot version 5, which carries the step its membership proof used; a profile pinning ballot version 5 must be a version-7 definition's under `electorate_mode` 2, and one pinning ballot version 4 under a version-7 definition must be one under mode 1 ([[ballot-validity]], Ballot record (version 5); [[challenge]], Opening version 3; [[election-definition]], Notes; [[0028-rolling-electorates]], What the verifier checks). What this row says of a version-6 definition's author panel, results mode and tally-opening version holds for version 7 under either mode, and a ballot version 5 counts its default half as ballot version 4 does ([[tally]]). As for ballot version 4, a profile pinning ballot version 5 beside a spoiled-ballot opening version this verifier doesn't know, and a version-7 definition whose profile pins a ballot version it doesn't know, are unverifiable (`unsupported-version`) rather than failed, unless the profile fails on another ground. A record anyone can post (a ballot or a spoiled-ballot opening, whose versions the profile pins, or a share receipt, posting or complaint, whose versions the ballot version fixes) with an unpinned version is rejected at admission with `profile-mismatch` and listed in 8.3, never an election failure; so is a tally opening, which counts whoever signed it, as a rejected entry of 7.3 ([[versioning]]; T-31, T-34, [[0003-tally-scheme]]).
- 2.4 Its electorate is a group root per tier at a fixed L2 block, and that root matches the root computed from that tier's own group additions on the board, never the L2 state alone, so a tier's root can't be registered under another tier's label. An addition counts toward tier t only if its authorisation binds t's group identifier, the chain ID and the registry address (for Tier 0 the registrars' EIP-712 approvals, [[contracts]], Group registry, from a registry whose logged registrars and threshold equal the ones the release pins, every group of any other failing, replayed by the verifier with its own member count so that a record whose signed position or size disagrees with it fails the definition as `group-history`; for Tier 1 the Safe's EIP-712 struct until [[0014-tier1-vouching]] replaces it in P3-3; for Tier 2 the document proof bound to the commitment actually inserted), and the verifier attributes additions by that binding, never by the L2 event's group field alone, so a signed batch can't be replayed into another tier (T-08, T-13, T-06, T-01, T-71; P1-18, P3-2). The group registry fixes each group's tier when it creates the group, and a definition whose `tier` label for a group differs fails. Each tier's root is the root of its tier tree, the depth-32 Poseidon tree the verifier rebuilds from the counted additions ([[membership]], Tier tree), never the root a group contract reports. A tier whose root differs from it or is 0, or whose group has more than 2³² additions, fails the definition: a LeanIMT root would let one registration carry many identities, and Semaphore's circuit lets anyone prove membership of root 0 (T-03, T-04, T-05, T-06; P1-17). For a group in a group contract that logs no signed sequence, an addition with a forbidden commitment (non-canonical, `0`, `1` or `Poseidon2(0, 1)`) keeps its index but gets leaf 0 and isn't counted in the group size, never failing the definition, and a removal counts only under the same binding as an addition and names a leaf index; for a group in the group registry, whose records are signed in sequence, the verifier instead replays the group as [[contracts]], Group registry, Verification specifies, and any record that fails that replay (a forbidden commitment, a stray or repeated removal, a position or size that disagrees with its own count) fails every definition naming the group as `group-history`; and a definition that lists a tier with no counted, unremoved addition at the root's block (tier-tree root `Z_32`) fails ([[membership]], Tier tree). The verifier recomputes each tier's member count at `root_l2_block` as the number of additions counted toward the tier under the binding above whose commitment isn't forbidden and that aren't removed by that block, and a definition whose stated `group_size` differs fails, as for regional cells in 2.8, so a definition can't overstate a tier's anonymity set ([[election-definition]]; T-13, T-16; P1-10b). Under definition version 3 the same holds per group, with every group of a tier read at the tier's one `root_l2_block` and its `tier` label checked for each group; then the verifier applies the first-occurrence rule across the tier's groups, recomputes each region's count and each cell's tree, root and member count ([[election-definition]], Regional cells; [[membership]], Cell tree), and a definition whose stated `regions`, cell `root` or cell `members` differs from them, or with a cell root of 0, or a cell of more than 2³² leaves, fails (T-13, T-16, T-03, T-04). Each tier's `root_l2_block` is strictly before the L2 block that registered the definition, and a definition with one at or after that block fails, so no root can name additions that weren't public on L2 before voting ([[election-definition]], The electorate is in the past; T-08, T-13, T-25, T-34). Under definition version 7 with `electorate_mode` 2 (rolling; [[0028-rolling-electorates]]; P2-17), each rolling tier's listed groups must exist at its `root_l2_block` with the tier its label names, each is replayed strictly as above (`group-history` for a record that fails), and their additions are taken in chain order into the tier's rolling tier tree ([[membership]], Rolling tier tree), with no first-occurrence rule; a definition whose `root` or `group_size` differs from that tree's root or member count (its distinct live commitments) at `root_l2_block` fails, as does one whose `root_l2_block` is at or after the registering block. The replay continues through the last accepted step, not only to `root_l2_block`, so the board must carry the groups' events through close, which [[P2-17]] part 2 adds to [[contracts]] (Election registry, The shared event sequence; 4.4), and the verifier computes the root of each step a ballot names, never taking one from the ballot or a submitter ([[membership]], Root clock and steps, Rolling checks; T-08, T-13, T-36).
- 2.5 Its trustee panel (keys, `k`, `n`, panel identifier) matches what the verifier recomputes from the ceremony transcript in 3.1 (not the transcript's own claim) and the keys registered on L2 and equals a panel the release pins (`panel_id`, `k`, `n`). Under definition version 6 ([[0027-trustee-panels-and-live-results]]; P2-16): a definition whose `poll_class` is on the civic record (2 or 3) fails unless the release pins that default panel with the kind `independent` (`panel-kind`), so no poll under the transitional panel is on the civic record (T-14); and its author panel, if it has one, fails if any author key is a key of the default panel (`default-seat`, [[trustee-identity]], Author panel identifier, rule 4), so no trustee holds shares of both halves (T-14). 2.5 reports the first failure in this order: `panel-unpinned`, then `panel-kind` (`at` `{}`), then `default-seat` (`at` `{"seat": i}`, `i` the first author seat, from 1, whose key is a default seat's). The author panel's keys come from the definition, never from the pins, and its identifier is recomputed under its own tag (T-37); its ceremony is checked by 3.1 and 3.2 per panel (P2-16 part 3). The ballot client runs this check before making any share, and trustee nodes run it before receipting one, because shares made under a wrong threshold or to substituted keys can't be taken back ([[election-definition]]; T-37, T-14, [[0006-trustees]]; P1-12, P1-14, P1-18).
- 2.6 Its timing (open, close, the L1-inclusion bound δ, `l1_inclusion_bound`, and the L2 sequencing bounds it assumes) is well formed, `opens_at` is at or after the anchoring clock's `epoch` ([[election-definition]], The seal), δ lies within the bounds the immutable election registry enforces at registration and the release pins (`MIN_INCLUSION_BOUND` to `MAX_INCLUSION_BOUND`, [[parameters]]; [[close]]), the L2's configuration stayed within the sequencing bounds for the whole poll (which the registry admits only up to `MAX_SEQUENCING_WINDOW` and `MAX_SEQUENCER_DRIFT`, [[parameters]]), and its `sequencing_window`, at 12 seconds per L1 block plus the missed-slot margin, fits inside the forced-inclusion delay of the contract-event window the immutable contracts fix ([[tally]], Tally window), so no definition can outrun the counted extent (T-35, T-50, [[0004-l2-choice]]; P1-18).
- 2.7 Where display text is available, it matches the definition's commitment and is well formed for it, under display-text version 2 with exactly the definition's questions, each with exactly its options ([[display-text]]; T-17, T-41, T-53); a record that fails is reported and treated as unavailable (Principles).
- 2.8 Its tally partition is well formed. Under definition version 1 the partition is the tiers only: each cell is exactly one tier of the electorate (2.4), and the partition has exactly one cell for each tier and no other cells, so no tier is repeated, omitted or merged with another; the rule is fixed, not chosen by the author (a rule field in the definition, if it has one, must equal it): each ballot goes to the cell of the tier its membership proof's public inputs fix (5.1, 5.2, 5.3: the tier-binding scope of [[membership]], or the tier bound in the signal; the root alone never decides it, since two tiers may share a root), so no relay or operator can move it between cells; a voter in several tiers has one unrelated nullifier per tier group ([[membership]], Scope), so each tier counts at most one of their ballots, which G-2 allows; so every cell holds only its own tier's ballots and is reported under that tier's label; and a definition version 1 has no regions. Under definition version 3 ([[0019-regional-cells]]) a ballot's region comes only from a membership proof against a per-tier, per-region root fixed in the definition (one root per cell, as in 2.4; the cells' trees of one tier hold disjoint sets of counted leaves (first occurrence) which together are the tier's counted leaves, checked from the board's group additions, so a voter can't choose a cell by choosing which root to prove against), never from a field the voter chooses or can grind, nor from any per-ballot value (the nullifier, a commitment, a VSS commitment, a ciphertext hash, a proof or signal field); the verifier recomputes each cell's admitted electorate as the cell's `members`, as 2.4 recomputes it (a stated value that differs fails), and no cell of a split tier is below `MIN_CELL_ELECTORATE` ([[parameters]]). Version 3 meets this with one cell tree per cell over its regions' groups, the first-occurrence rule (one commitment counts in one cell of its tier), and the fold of [[election-definition]] (Regional cells): each region of at least `MIN_CELL_ELECTORATE` members is a cell, the rest fold into one remainder cell, and a tier whose remainder is below the floor, or that would have one cell, isn't split. The verifier recomputes the fold from the region counts 2.4 checked and fails 2.8 if the definition's cells differ (the `cells` rule checks the same from the stated counts), so the floor binds every cell of a split tier, and a tier that isn't split has none and is flagged by 8.2 when small. A ballot under version 3 (ballot version 2) names its cell's position in the partition, and the verifier takes the cell's tier, root and scope from the definition (5.1 to 5.3; [[ballot-validity]], Admission (version 2), `ballot-cell` for a cell the partition doesn't have), so the remainder cell shows the cell, never the region within it. The floor bounds who may vote in a cell, not how many do: a cell can still hold one counted ballot, which 8.2 flags (T-16). Under definition version 7 with `electorate_mode` 2 the partition is one cell per rolling tier, in `rolling_electorate`'s order: a rolling tier is never split, its ballots go to its cell by the tier their proof's scope binds (the rolling scope binds the tier, [[membership]], Scope), and there is no floor, so 8.2 flags a small tier as for an unsplit one ([[0028-rolling-electorates]], Regional cells). Every tier is opened and small ones are flagged (8.2): tiers are never merged or withheld ([[0006-trustees]], Small cells); a coarser total is never opened to fill a gap (one partition, [[0002-everlasting-privacy]]; T-16). Trustee nodes run 2.8 before releasing any share and the ballot client runs it before casting, because a failure found after the tally can't take an opening back. This is an election check: a malformed partition fails the election (T-01, T-14, T-16, T-29, T-36, T-45; P1-10b, P1-15).
- 2.9 Under definition versions 4 and later (each lists `receipt_keys` as version 4 does), every key in `receipt_keys` judges the election ([[election-definition]], Receipt keys): its word in the receipt-key record of the anchor the release pins for `l1_anchor` ([[contracts]], Board anchor, Receipt keys), proven from L1 state at the verifier's finalized block `B`, shows it registered before `opens_at` and not retired by then. A key registered before `opens_at` and retired at or before it fails the election (`receipt-key-retired`), whenever it is read. Otherwise, while `B`'s timestamp is before `opens_at`, 2.9 is unverifiable, since a registration or retirement before `opens_at` may still come; once it is at or after, a key not registered before `opens_at` fails the election (`receipt-key-unregistered`). A word the release code can't write ([[contracts]], Board anchor, Receipt keys) fails it (`receipt-key-record`). Keys are judged in list order, and the first failure is reported. Versions 1 and 3 list no keys, so 2.9 has nothing to check, and their receipts are never evidence a third party can attribute ([[receipts]], Receipt keys). So the keys that judge an election's receipts are the anchoring authority's, fixed before voting opened, and a release, operator or creator can't add one (T-26, T-69, T-71; P1-13b).

### 3. Key ceremony

- 3.1 The ceremony transcript decodes strictly, its hash matches the one registered with the trustee keys on L2, and every proof in it is checked, with its Fiat–Shamir context (chain ID, registry address, election identifier, the stub hash recomputed from the definition ([[election-definition]], Stub hash and the ceremony), panel and the run identifier) rebuilt from the election being verified, never read from the transcript, so one election's ceremony can't be registered for another (T-37, T-40; P1-14). The registration itself is the trustee registry's `CeremonyRegistered` record for the definition's stub and panel: the verifier checks each approval in it against the panel its release pins and counts the distinct seats whose approvals verify, requiring at least the quorum its release pins for that panel, never the contract's own `q`, which it compares with its pin and reports if they differ ([[contracts]], Trustee registry; T-71, T-37, T-14). The record also carries the registered key set the approvals sign, which the board takes signing keys and qualified seats from ([[0028-board-contract-checks]], 2B): the verifier recomputes its `key_set_hash` from the record and fails 3.1 with `key-set-mismatch` unless it equals the `key_set_hash` of the key set its own transcript check returns ([[ceremony]], Key set hash), so a set a quorum signed that isn't the transcript's fails the election rather than passing (T-37, T-14). **(P1-3)** The verifier computes the qualified set itself, from its own check of every proof and complaint, never from the transcript's claim, and recomputes from that set alone the registered key set of [[0002-everlasting-privacy]] (each trustee's KEM and signing keys); plurality and approval have no joint public key (a ranked-choice mix key, if the follow-up ADR in [[0003-tally-scheme]] needs one, is checked as that ADR says). A failed proof is non-fatal only for a trustee excluded before the definition was registered; if the key set or panel bound into the definition includes any trustee whose proof fails, or differs from the recomputed one, the election fails (rogue-key attack, T-40, T-14, T-37). Every trustee message in the ceremony (its registration, its ceremony entry registering its per-election keys, possession answers and complaints) is signed by its trustee's pinned identity key, and every later statement (receipts, shares, tally shares, destruction) by the per-election signing key registered in that entry ([[trustee-identity]], Which key signs what); only signed failures are attributed to a trustee (T-37, T-29).
- 3.2 At least the number of trustees the panel rules require took part, and every complaint and disqualification in the transcript is resolved as the spec says. [[ceremony]] (Transcript check) specifies 3.1 and 3.2 for plurality and approval: the transcript-level codes `ceremony-order`, `ceremony-shape`, `ceremony-signature` and `ceremony-quorum` (fewer than `k` qualified seats), each seat's disqualification reasons, and the registered key set. Under [[0006-trustees]] rule 7, adopted by the owner on 2026-10-12, at least `n − 1` seats must take part: below `max(k, n − 1)` qualified seats 3.2 fails with `ceremony-participation` (Key ceremony; T-40, T-54; P1-14).

### 4. Board, anchors and archive

- 4.1 Every board-entry envelope decodes strictly (the record it carries is an admission check), every entry names the election and its own position, segments never decrease, spoiled-ballot openings are in canonical order, and the hash chain is unbroken from the first entry to the last ([[board]], Board checks; T-23, T-31, T-42; P1-16).
- 4.2 Every board checkpoint anchored on L1 is recomputed from the board: it ends at its segment's boundary, its chain head and Merkle root match, and its `object_cid` and `hashes_cid` name the segment object and entry-hash list of its last entry's segment. Every segment holding entries has an anchored checkpoint ([[board]], Board checks; T-23, T-24; P1-16, P4-1).
- 4.3 Every archive manifest reachable from L1 `archiveLocator` fields (the pinned anchor's latest locator in state and its `ArchiveLocated` logs, [[contracts]], Archive locator) and from the manifest chain is found and matches what it names; any missing link is reported ([[0005-permanent-archive]]; T-51; P1-19, P4-3).
- 4.4 Every one of our contracts' L2 events that the election's checks use has a board entry carrying its contract-event record (`0x0008`), which passes the event check of the contract-event version its profile pins against the definition's L2 contracts (`unknown-contract`, `unknown-event`, `event-topics`, `event-data`; [[contracts]], Contract-event record): the events that name the election, each of its tiers' group creation (which fixes the tier, 2.4) and group additions and removals up to each `root_l2_block`, and its panel's key and ceremony registrations (2.5, 3.1). The archived event sequence of each contract, as contract-event records that each pass the event check, which for a contract shared by many elections includes every other election's events, reproduces that contract's on-chain event accumulator at every anchored period and at close under the rules of [[contracts]] (Event accumulator, Verification) and their codes (`index`, `order`, `block-range`, `accumulator`), against the storage proofs that are the only evidence archived for them ([[contracts]], The shared event sequence; Contract-event record, Evidence). The L1 origin that the election's `ElectionCreated` and `DefinitionRegistered` events carry is one finalized L1 block, no later than the event's L2 timestamp and no more than the pinned `max_sequencer_drift` before it, and, for the registration, never earlier than the same election's creation's ([[contracts]], Election registry, Events, The L1 origin). The check passes with an annotation naming which proof type settled each output root it relied on (TEE-only or ZK), and the report lists every TEE-only root (8.3) ([[0005-permanent-archive]], T-71; P1-18, P1-19).
- 4.5 Every event one of our contracts accepted because of its caller (a forced ballot relayed from L1, the only such event, P1-18 part 4c) names its L1 relay call, and matches exactly one call our relay recorded, read from L1 state: the relay's stored call hash for the event's index, proven at the verifier's finalized L1 block, equals the one recomputed from the event's index, L1 block, stamp, gas limit and whole record ([[contracts]], L1 relay, Verification). One that matches no call (forged by L2 governance) fails (`relay-unmatched`), and so do two events naming one call (`relay-duplicate`); a recorded call with no event is reported, never failed. No transaction is archived ([[contracts]], Contract-event record), so any other deposit reaching our contracts is checked by the evidence its event carries, like any other call, since nothing trusts its sender (T-71, [[0004-l2-choice]] as amended by [[0025-contract-event-evidence]]; P1-18, P1-19).

### 5. Ballots

- 5.1 Every ballot's membership proof verifies against the electorate root for its tier in the election definition (under definition versions 3 and 4, the root of the cell a version-2 ballot names; under definition version 5, of the cell a version-3 ballot names; under a rolling definition version 7, never a root the definition states but the root of the step a version-5 ballot names, of its cell's tier, which the verifier computes itself from the listed groups' events, once that step is one the poll accepts (`root-step-range`, and on the contract path `root-step-mismatch` for a supplied root other than it; [[ballot-validity]], Admission (version 5); [[membership]], Rolling checks)), under the pinned protocol-wide depth-32 verification key, as [[membership]] (Checks) specifies; a definition with a tier root of 0 fails, since Semaphore's circuit lets anyone prove membership of root 0 (T-04, T-05, T-13; P1-17, P1-17b).
- 5.2 Its nullifier uses the scope the verifier derives from the election-definition hash, the tier and the tier's root (under definition versions 3 to 5, the cell's tier and root) (`abolish/v1/nullifier-scope`, [[membership]]), or under a rolling definition version 7 from the definition hash and the tier alone (`abolish/v1/rolling-nullifier-scope`, [[membership]], Rolling scope), never a scope from anywhere else (T-12, T-13, T-04; P1-17).
- 5.3 The proof's message is `M` of [[revoting]] (Message), recomputed from the ballot record and the definition: it binds the ballot hash, the election definition, the ballot's tier (under ballot versions 2 to 5 its cell's tier, the cell bound through the ballot hash, and under version 5 the step too) and the L1 block the re-vote rule ranks by, so the proof can't be moved to another ballot or replayed (T-38, T-32; P1-12, P1-13, P1-17).
- 5.4 Every validity proof verifies, with its Fiat–Shamir challenge recomputed from the full statement table, including the ballot's nullifier ([[domain-separation]]), and constrains the ballot to the election's rules: no over-vote, no negative vote, the approval limit if any, and under ballot versions 3 to 5 each question's limits, by one range proof per question under `abolish/v1/fs/ballot-validity/question-sum` (under ballot versions 4 and 5 over each vote commitment `C_j = E^D_{j,0} · E^A_{j,0}`, the product of its two halves, computed and never carried, [[ballot-validity]], Ballot record (version 4)), with `option-proof` naming the first failing flat option and `sum-proof` the first failing question ([[ballot-validity]], Checks: `validity-shape`, `option-proof`, `sum-proof`; Checks (version 3); T-28, T-30, T-32; P1-12, P2-14). **(P1-3)** [[ballot-validity]] (Ballot record, Admission) fixes the order and codes of 5.1 to 5.4 for ballot version 1, and adds `ballot-stray` (another definition hash), `ballot-tier` (a tier the definition doesn't list; under ballot version 2, `ballot-cell`, a cell the partition doesn't have, Admission (version 2)) and `share-hash-unqualified` (a share hash other than 32 zero bytes for a seat outside the registered key set, [[delivery]], Notes; T-17).
- 5.5 The ballot entry is inside the poll's window by its own path, under the close rule of [[close]] ([[0030-close-rule]]): an ordinary contract-path ballot by its L2 block's timestamp, `opens_at ≤ τ_b ≤ closes_at`; a ballot forced through our L1 relay by the L1 timestamp its matched relay call recorded (4.5); a board-path ballot by its entry's segment, at most `s_A = period(closes_at) + 1` (`window-before-open`, `window-after-close`, `window-boarded-late`, the last also reported against the board operator). Each copy of a ballot is judged by its own entry, before repeats (5.7). Whether an ordinary ballot in a block at or before close was in fact made before it is the close check's (6.3), which uses only L2 data derived from finalized L1 data (T-35, T-50, T-45, [[0004-l2-choice]]; P1-18).
- 5.6 Direct-submitted ballots on L2 are on the board, and one the close rule (5.5) admits is on it within the counted extent (`segment ≤ s_S`, [[tally]], Tally window), counting only a board entry whose contract-event record passes 4.4; a ballot found on L2 but missing from the board, or first so boarded after the counted extent, fails the check, attributed to the board operator unless its L2 block became derivable from finalized L1 too late to board in time, which is a settlement overrun, unattributed ([[tally]], Tally window; T-25, T-50; P1-18, P3-5).
- 5.7 A repeat of an earlier admitted ballot is rejected (rejected entries don't count as earlier ballots, R4): the same tier, nullifier and message `M` (5.3), whatever the entry's other bytes; Groth16 proofs are malleable, so byte comparison alone isn't enough ([[revoting]], Selection step 1; T-38; P1-13).
- 5.8 The L1 block the ballot names is no older than an hour before `opens_at`, is on the finalized L1 chain with the hash the ballot gives, and has a timestamp at or before `closes_at` (`l1-ref-before-open`, `l1-ref-after-close`, `l1-ref-unknown`, checked in that order); under ballot version 5 the step the ballot names then lies in the window before that block, `t − ROOT_WINDOW < τ_n ≤ t` for its timestamp `t` (`root-step-stale`, `root-step-future`; [[membership]], Root clock and steps). A ballot naming a block beyond the finalized head is pending only until L1 finalizes a block after `closes_at`, and rejected after that, so no reference can keep an election unverifiable, and for this check a verifier of a closed election needs L1 only from just before an hour before opening to the first block after close ([[revoting]], Admission; T-45, T-35, T-53, T-36; P1-13).
- 5.9 Every share receipt (`0x000c`), posting (`0x000d`) and complaint (`0x000e`) in the counted extent decodes strictly under the version the ballot version fixes (a record that doesn't is a rejected entry, listed in 8.3, and so is a posting anywhere but in a contract event), and the delivery check of [[delivery]] runs over them for every selected ballot (under ballot versions 4 and 5, with delivery records of version 2, over every seat of both panels, each record checked against its own panel's share hashes and registered key set, [[delivery]], Version 2): a share receipt is checked against its ballot's recomputed ballot hash and `share_hashes` and the seat's registered signing key, a contract-path posting against the ballot's `share_hashes` and the seat's registered KEM key (2.5, 3.1), and a complaint against a passing contract-path posting, as [[share-encryption]] specifies (Intake and receipts: `share-receipt`; Public posting: `posting-hash`, `posting-proof`, `posting-encapsulation`; Complaints: `complaint-proof`, `complaint-unfounded`), each only if it names this definition, a qualified seat and is in time (`DELIVERY_WINDOW`, `COMPLAINT_WINDOW`, by its segment through the board path and by its submission time through the contract path: `delivery-stray`, `delivery-seat`, `delivery-late`). A selected ballot stays in the counted set only if every qualified seat has a passing receipt or contract-path posting in time and no complaint about it is proven, attributed or not; otherwise it counts nothing, with no fallback to an earlier one (6.1). A failing receipt, posting or complaint is ignored and never excludes a ballot; an unfounded complaint is reported against the trustee its signature attributes it to, and a passing receipt contradicted by a proven complaint against its seat (`receipt-contradicted`) ([[delivery]], Delivery check; [[tally]]; T-41, T-29, T-15, T-25; P1-12).

### 6. Re-voting and spoiled ballots

- 6.1 For each tier and nullifier, at most one ballot is counted, chosen by the re-vote rule of [[revoting]] ([[0011-revote-rule]]): the admitted ballot naming the highest L1 block counts, and two distinct ballots naming that same block tie and count nothing. Its admission part (5.7, 5.8) is an admission check, and the rest is an election check. The rule meets R1 to R6, R6 with the close rule's accounting for its wait ([[close]]); any later rule MUST meet all of them too (T-33, T-38, T-45, T-25, T-23); [[revoting]] (Requirements) shows how:
  - **R1 Replay.** A replay of any earlier ballot of the nullifier is rejected, whatever its bytes. Groth16 membership proofs can be re-randomised by anyone without the witness, so byte comparison isn't enough (see 5.7).
  - **R2 No freezing.** No value chosen when a ballot is cast can stop a later ballot by the same voter from counting. A coercer who watches one cast must not be able to make it final.
  - **R3 Order independence.** The counted ballot doesn't depend on the order in which the board operator writes unanchored entries, or on whether it withholds an earlier ballot until later, alone or together with a coercer. This holds whether ballots arrive through our API or by direct submit.
  - **R4 Stable admission.** An entry that fails admission never changes whether another entry is admitted. An exclusion decided later (a complaint after close, say) never re-evaluates later ballots.
  - **R5 Client state from anchors.** Whatever state the client needs to cast a valid re-vote, it takes from anchored board data or L1 data it has checked itself, or from its own records, never from a server's claim.
  - **R6 Liveness.** At any time up to close, an honest client can cast a re-vote that will count after a wait of at most a stated bound, and the close rule accounts for that bound. [[revoting]] states the wait: about 3 L1 slots, during which a watched voter can void the watched ballot with a tie, and the close rule ([[close]]) takes it from the last moment a ballot counts: in an L2 block by `closes_at` on the ordinary path, in an L1 block by `closes_at` through the relay.
  - **Visibility.** A re-vote is public: anyone who has seen one of the voter's ballots or receipts, and so knows the nullifier, sees that the voter voted again, when (to the L1 block) and how often, and whether a tie voided a ballot (T-45). Deniable re-voting would need hidden nullifiers and an ADR (Achenbach, Kempka, Löwe and Müller-Quade, USENIX JETS 2015).
  - Settled by [[revoting]]:
    - a selected ballot that fails a later check counts nothing, with no fallback to an earlier one ([[0002-everlasting-privacy]]), so complaints can't revert a re-vote;
    - spoiled ballots never take part;
    - selection is per (tier, nullifier): the scope binds the tier and its root, so one secret in two tier groups yields two unrelated nullifiers, even when the two groups have the same root, and a person's ballots in different tiers are neither linked nor ranked against each other ([[membership]], Scope; T-13). **(P1-3)**
- 6.2 No spoiled ballot is counted, and every published opening is checked and reported. A challenged ballot is never boarded on its own: its core travels inside a spoiled-ballot opening record (`0x0003`), which never enters 6.1 or the tally, so an opening can never spoil, count or displace a cast ballot ([[challenge]]; [[0021-challenged-ballots]]). Each opening in the sealed extent decodes strictly under the version the profile pins (2.3) and is checked against the core it carries and the registered key set, never against a board entry: the opening rebuilds every VSS commitment and every registered seat's ciphertext and share hash (`opening-stray`, `opening-tier`, `opening-shape`, `opening-unqualified`, `opening-vss`, `opening-ciphertext`, in that order; under opening version 2, which opens the cores of ballot versions 2 and 3, `opening-cell` in place of `opening-tier`; under opening version 3, which opens ballot versions 4 and 5's cores, the same checks over both halves and both panels' seats), and a passing opening reports its tracking code (the core hash, under the pinned ballot version) and the vote it opens to, flagged `opening-vote-outside` if no valid ballot could carry it, naming the first question outside under opening version 2 ([[challenge]], Checks; Opening version 2). Openings are boarded only through the board path, in segments after the counted extent's last, `s_S`, up to the period containing `t_S + OPENING_WINDOW` (`opening-early`, `opening-late`), never when it opens a commitment of a ballot admitted in the counted extent, at any option: under an equal `definition_hash`, a ballot commitment equal to some opened `C_j`, or to `h^s` or `g · h^s` for a scalar `s` the opening reveals other than the public 0 and 1 (any polynomial coefficient, any seat's share, any seat's `e_i` or `w_i`; [[challenge]], Opened commitments; under opening version 3 also each `r_j` and each out-of-rules `v_j`, and a version-4 or version-5 ballot either of whose halves' constant terms equals any VSS commitment of the opening, [[challenge]], Opening version 3), never decided by the tracking code or the whole `vss`, since an opened commitment or its randomness can be cast under other share hashes, another tier or re-blinded coefficients (`opening-cast`, which would open a counted vote), and never twice for one core (`opening-repeat`). Every one of these is a report, attributed to the board operator as [[challenge]] (Publication) says, and none fails the election or changes what counts. Publishing an opening is opt-in and off by default: the default check runs on the voter's own second device or a checker they choose, against the tracking code it recorded before the cast-or-challenge choice, with the opening handed over directly (QR code or file), never through our API (T-42, T-44). The board orders openings canonically within each period ([[board]], Spoiled-ballot openings), so an opening's timing and position link it only to a period after close. Residual (T-12, T-47): a published opening can still be linked to its voter through the publisher's network metadata (T-11), and it usually shows the voter's real choice; anyone holding an opening can cast its core under their own nullifier ([[challenge]], Residuals; T-42, T-45, T-47; P1-13). **(P1-3)**
- 6.3 The close check: the default panel's seats each sign a close statement (record type `0x0015`) naming `L_δ`, the last finalized L1 block at or before `closes_at + δ`, and the L2 head derivable from L1 data up to it; the close head `B` is the `k`-th largest claim among the seats whose valid statements agree with each other. With `B`, each cell's counted set is recomputed from the counted extent's admitted ballots without the ordinary ballots in blocks after `B`, removed before repeats are resolved; if any cell's counted set differs from the one 7.1 counts, the election fails `close-contested`, unattributed, since a ballot that may have been made after close would change the result. `B` never decides which ballots count. With fewer than `k` such seats there is no `B`: the check passes and the report says the close is unchecked, naming the seats that sent no counted statement and listing the counted ballots with only ordinary copies. Equivocation and a false `L_δ` are attributed to their seats, and claims below a permissionless dispute game's floor are reported against them without leaving `B`; disagreeing claims are always listed, since they prove a false one without L1 data ([[close]], Close head and Close check; [[0030-close-rule]]; T-35, T-45, T-50, T-53, T-54, T-36, T-71; P1-18).

### 7. Tally

- 7.1 The aggregates are recomputed from the selected ballots alone, selected from the counted extent (the entries with `segment ≤ s_S`, [[tally]], Tally window; nothing in a later segment changes them), per cell of the registered partition (2.8) and per option, with per-tier and other coarser totals derived from the cells ([[tally]], Aggregates and Coarser totals; T-29, T-08, [[0003-tally-scheme]]; P1-15). If a cell's counted set (selection, delivery and complaints), computed over the whole sealed extent with each record's window applied by submission time, differs from the one over the counted extent, the election fails `tally-late`, attributed to the board operator for an entry it could have boarded in time and otherwise unattributed as a settlement overrun, never to a trustee; a late entry that changes no counted set fails nothing ([[tally]], Tally window and Opening checks; T-25, T-45, T-29, T-50). **(P1-3)**
- 7.2 Each cell's published opening, one `(Σv, Σr)` per option, signed or not, must open the product of that cell's ballot commitments with a count of at most the cell's counted ballots, giving the published result; a cell with no such opening fails the election (T-54), and two different passing openings of one cell fail it as evidence that binding is broken. Trustees' summed shares are never on the board: they go only between trustees, which check each against the product of the cell's public VSS commitments before combining any `k` ([[tally]]: `tally-missing`, `tally-opening`, `tally-conflict`, `tally-range`, under definition version 5 `tally-question-range`, and `tally-aggregate` per opening; [[0015-tally-publication]]; [[0002-everlasting-privacy]]; T-29, T-14, T-15; P1-15). A passing opening counts whether or not its signature attributes it to a seat; a failing one is attributed only as 7.3 says, and an unattributed failure is no one's ([[tally]], Opening record). Ranked-choice decryption shares get their checks from the follow-up ADR in [[0003-tally-scheme]]. **(P1-3)**
- 7.3 Every tally opening (record type `0x0006`) in the board's sealed extent decodes strictly under the version the profile pins (2.3); one that doesn't is a rejected entry, listed in 8.3, and opens no cell, so a cell left with no opening fails 7.2 (`tally-missing`). Each opening is sorted into the openings of a cell of the registered partition or a stray opening, by its `definition_hash` and `cell`, and attributed to its `signer` only if its signature verifies under that seat's per-election signing key registered by the ceremony (3.1). An opening whose `aggregate_hash` isn't its cell's over the recomputed counted set is reported `tally-aggregate`, attributed like any other failing opening as an opening over a set other than the counted extent's, and never passes ([[tally]], Opening record; T-29, T-31; P1-15).
- 7.4 Every opening on the board is for a cell of the partition registered in the election definition, per option, over the selected ballots ([[0002-everlasting-privacy]], [[0006-trustees]]); any other opening, such as one for an individual ballot or for overlapping sets whose difference is one ballot (which fails `tally-opening` as an opening of its cell), and every stray opening (another election's definition hash, or a cell the partition doesn't have), is reported with the trustee its signature attributes it to, or as unattributed (7.3); a summed share found on the board ([[0015-tally-publication]]) is reported as an unattributable disclosure, never against its signer alone: its sender, every recipient, anyone who seized a trustee before destruction and anyone who later decrypts a harvested copy hold it (T-14, T-15, T-16, T-29; P1-15). Every tally opening in the sealed extent that the boarding rule of [[tally]] (Opening record, Boarding) refuses (a failing, unattributed or stray one, or a second by the same seat for the same cell) is also reported against the board operator. This check reports and attributes; it doesn't fail the election, whose result rests on 7.1 to 7.3.

### 8. Report

- 8.1 Results are reported per tier, and per cell where the partition has regions, each with its anonymity-set size and its turnout; under definition version 5, per question and option, each question with its method rendered from its limits, and never a figure joining two questions, since none is opened ([[0026-multi-question-ballots]], No cross-tabulation). For a tier that is the group size at the definition's root, as 2.4 recomputes it (never the definition's stated value alone); for a regional cell (definition version 3) it is the cell's member count, as 2.4 and 2.8 recompute it, and the cell is labelled with the regions its groups were created with in the group registry ([[0019-regional-cells]], Consequences). Under a rolling definition (version 7 with `electorate_mode` 2; [[0028-rolling-electorates]], Anonymity set and reporting), no single size stands for a tier, whose electorate grew during the poll: each tier's result reports its member counts at opening (as 2.4 recomputes it), at its last boundary (with the step, or that no boundary fell in the poll) and at the smallest step a ballot with a verifying membership proof named, its eligible count (the distinct commitments live at some accepted step) and its growth per anchoring period, each computed by the verifier from the listed groups' events as [[membership]] (Reported counts) defines it, never read from the definition or a release; its turnout is its counted ballots among its eligible count, which they never exceed, with no ratio when that count is 0, and the result says it describes the people who answered ("58.4% yes among 2,418 people who answered; 9,105 could answer during the poll"), never a share of a fixed population; the tier is labelled with the regions its listed groups were created with, as a regional cell is. Tier 0 results are labelled as not Sybil-resistant, and a rolling Tier 0 result also as open to new identities during the poll (T-01, T-06, T-13, T-16; P1-19, P2-17, P3-6).
- 8.2 Small counts are flagged next to each result and each cell: a tally over few voters can reveal individual votes. Under a rolling definition the same rule also flags each tier's count at the smallest step used, the anonymity set of its worst-placed ballot, and its eligible count ([[membership]], Reported counts; T-13, T-16). Each cell also reports, and flags by the same small-count rule, the number of its counted ballots with postings that pass the public check of [[0002-everlasting-privacy]] at fewer than `k` distinct seats (a passing posting counts as readable, since its share can't be checked publicly, and so does every one that publishes `m_i` anywhere on the board or archive, whether or not it delivered: a contract-path posting after its deadline, or a posting boarded through the board path, which is a rejected entry ([[delivery]])): a future adversary reads the others, and the opening gives the sum of the rest ([[tally]], Residuals; T-15, T-16; P3-6, P1-19).
- 8.3 An election whose profile pins a record version marked broken is reported unverifiable (entries rejected at admission don't count as use), never verified. Everything reported unverifiable, every missing archive link, every TEE-only root and every rejected entry is listed with its reason (P1-19).
- 8.4 The report names the trustee panel that held shares for the election, and which trustees signed each cell's passing openings (7.3), or that it is unsigned (or, for ranked choice, whose decryption shares were combined), by the pinned identities, and whether our labelled seat took part ([[0006-trustees]]; T-37, T-14).
- 8.5 For each registered seat, the report says whether it stated that it destroyed its per-election key material after the tally: `destroyed`, `destruction-early` or `destruction-missing`, by its first destruction statement (record type `0x000f`) in the sealed extent attributed to it and the destruction segment ([[tally]], Destruction checks). A statement that doesn't decode is a rejected entry (8.3); stray, unattributed and duplicate statements are listed and reported against the board operator. Destruction can't be proven, so this is a report of signed claims only: it never fails the election or makes it unverifiable, and `destroyed` never means the material is gone (T-14, T-40, T-69, T-54; P1-15). Under a pinned board-entry version that doesn't allow `0x000f`, which 2.3 already fails for a profile pinning tally-opening version 1, 8.5 is reported not applicable (status `unverifiable`, code `not-applicable`; a report-only check never changes the verdict), never `destruction-missing`. When it applies, how its per-seat lines appear in the report is P1-19's, with its implementation.

## Inputs, procedure and report

How `packages/verifier` runs the checks above and reports them (P1-19). This section grows with the checks: today the verifier reads local inputs, can read the anchors and `now` from an L1 state proof and the election identifier, pinned version and anchor address from the election definition, and runs 4.1, 4.2, the decoding and well-formedness part of 2.1, 2.3's profile combination (Definition), 8.5's not-applicable case, 4.4's event check over the board's contract-event records ([Contract events](#contract-events)), which can fail 4.4 but never pass it, and, given a pinned panel, the key-ceremony transcript check: 3.2, and the parts of 2.5 and 3.1 that need no L2 state ([Key ceremony](#key-ceremony)). Every other check is reported unverifiable with `not-implemented`, so no run can report an election verified yet; 8.5 under board-entry version 4 is one of them until the tally checks exist. The bundle and the report are tool formats, not protocol bytes: nothing hashes, signs or anchors them. They are versioned so that a reader rejects a format it doesn't know.

### Bundle

A run reads one bundle: a directory with two files. Five formats exist: format 1 gives the anchors and `now` as they are, format 2 gives the L1 evidence they are read from ([Anchors from L1](#anchors-from-l1)), format 3 is format 2 with the election definition in place of the election identifier, the pinned version and the anchor's address, which are read from it ([Definition](#definition)), format 4 is format 3 with the trustee panel the release pins, which the key-ceremony checks run against ([Key ceremony](#key-ceremony)), and format 5 is format 4 with a run of finalized L1 headers, which ballots' L1 references (5.8) are judged against ([L1 references](#l1-references)).

`board.bin` is the board copy: `encode(entry_0) ‖ encode(entry_1) ‖ …` in index order, which is the segment objects of [[board]] concatenated in segment order. The verifier splits it by the version-1 entry layout: 47 fixed bytes (record header, `election_id`, `index`, `segment`), then the payload's `u32` length `L`, then `L` bytes, so each entry is `51 + L` bytes. Splitting stops at the first entry where fewer than 51 bytes remain, or fewer than `L` bytes after them. The entries before that point are the copy the verifier holds. The count of bytes from that point on is reported as `unreadableBytes`, and those bytes are never decoded. Splitting reads only lengths, and it splits an entry whose `L` is over `MAX_BOARD_PAYLOAD` ([[parameters]]) like any other: the bytes are already held, and 4.1's strict decode fails it (`decode`, `length-over-max`), so an operator who anchors one answers for it rather than leaving every copy short. The header, fields and payload are judged by 4.1. Since the board checks ignore every entry past the anchored extent ([[board]], Board checks), unreadable bytes past it change nothing. Unreadable bytes inside it leave the copy short (`checkpoint-missing`, unless an earlier board check fails first), which is unverifiable from that copy (T-53). `MAX_BOARD_PAYLOAD` bounds what is admitted to the board, not what a verifier hashes: the board checks hash every entry inside the anchored extent before decoding any, so an anchored entry with a length near 2^32 is hashed in full (up to 4 GiB). Only the anchoring authority, or a mirror serving bytes within the anchored extent, can cause that, and it costs the verifier time, not its verdict.

**Residual: anchored encodings `board.bin` can't carry.** The split is the only one a self-delimiting concatenation allows, so an entry the operator hashed and anchored with bytes past its payload (or any other encoding that doesn't split back into itself) can't be represented in any copy. Every copy then fails `copy-mismatch` or `checkpoint-missing`, and the election stays unverifiable for good, never failed, with nothing naming the operator. This is the same outcome as [[board]]'s withheld or forked tails (Residuals), and the same candidate fix closes it: bind a content address of each segment object into what is anchored (P4-1, P4-3), so an anchor that names no splittable object is provably the anchoring authority's.

`bundle.json` is UTF-8 JSON, an object with exactly these members. Invalid UTF-8, a byte-order mark, and an object anywhere in the file that repeats a member name all reject the bundle, so no two readers can take one file for different inputs:

| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

Format 1 has `now` and `anchors` and no `l1`; format 2 has `l1` and neither of the others; format 3 has `definition`, `clock` and `l1` (without `anchor`) and no other member, format 4 has those and `panel`, and format 5 has format 4's and `l1Blocks`, so the definition is the only source of the three values it gives. The definition's bytes are only held here: decoding them is check 2.1, so a definition that doesn't decode is reported, never a rejected bundle (except an empty one, which bundle hex forbids). Hex is lowercase with a non-zero, even number of digits, exactly 64 for 32 bytes, 40 for an address, 66 for a panel key and 216 for a checkpoint, and a header must be an RLP list of at least 15 byte strings with a 32-byte parent hash and state root and canonical integers of at most 8 bytes for its number and time. An integer is a JSON string of decimal digits with no sign and no leading zero (except `"0"`), within its type, and `period` is at least 1. Any other member, value or shape, or a missing or unreadable file, or one that isn't a regular file (a device or a FIFO, which may never end), rejects the whole bundle before any check runs, and a rejected bundle has no report: it isn't evidence about any election. A checkpoint's position in `anchors`, from 0, names it in the report.

**Every bundle input is unauthenticated, or as authentic as the inputs it is proven from.** The clock, the election identifier and the pinned version should come from the election definition (P1-10b) and the verifier's pinned roots, the anchor's address from the pinned roots, `f` from the election's creation event (4.4), and the header from a source the verifier trusts for finalized L1 (P1-19: a pinned checkpoint and the beacon chain's light-client protocol, or a block hash the user vouches for). A local file proves none of that. So each run records where each input came from: `local-file`; `l1-state-proof` for `now` and `anchors` read from the evidence of formats 2 and 3; or `definition` for the election identifier, the pinned version and the anchor's address read from the definition of formats 3 and 4. The `panel` of formats 4 and 5 is `local-file` until the release pins its panels, and format 5's `l1Blocks` is `local-file` until the verifier trusts a finalized head (P1-19 part 3b). An `l1-state-proof` input counts as authenticated, because the header, the anchor's address and `f` it is proven from are listed as inputs of their own (`l1Header`, `anchorAddress`, `firstSegment`), each `local-file` today except an anchor address from the definition. A `definition` input counts as authenticated for the same reason: the definition is an input of its own (`definition`), `local-file` until 2.1 proves its hash is the one the L2 election registry holds. Any run with an unauthenticated input reports `unverifiable` as its verdict, whatever the checks find, and reports separately what they found against those inputs. So a crafted bundle can neither verify nor fail an election (T-53, T-24). Trusting the header, and reading the clock from the definition and `f` from the archive, replace the remaining local inputs, one by one, in later parts.

### Anchors from L1

A format-2 bundle gives the evidence the anchors are read from, as [[contracts]] (Board anchor, Verification) specifies, never a list of logs an RPC node could shorten (T-24):

1. `B`'s hash is Keccak-256 of `header` as given, and `now` is its timestamp. The report gives the hash, number and time, so anyone can compare `B` with a node they trust.
2. The anchor's account is the value at `keccak256(anchor)` in the state trie under `B`'s state root (the Merkle–Patricia trie of the Ethereum Yellow Paper, Appendices C and D, with RLP of Appendix B decoded strictly), found by following `nodes` by their Keccak-256 hashes from the root. Its storage root is the third of its four fields. An account, once all four fields are well formed, whose code hash (the fourth) is that of empty code is read as absent: no account without code is the anchor.
3. A slot's word is the value at `keccak256(slot)` in the storage trie, an RLP string of the word without its leading zeros, or zero if the nodes prove the key absent.
4. The lowest-segment word is `lowest + 1`, or 0 if there is no anchor. Otherwise the verifier reads, in segment order, the word of every segment `s` from `max(lowest, f)` to the largest with `epoch + (s + 1)·period ≤ now` (no later one can be anchored yet), never past the seal (`lastSegment`). A range of more than `2^20` segments (about 120 years of hourly periods) stops with `l1-range-too-long` before any segment's word is read, so a bundle's own clock and `f` can't keep a run going for hours.
5. Only once every word is read, then in segment order, for each non-zero word at segment `s`, the checkpoint is the one the copy gives after `s` if its hash matches: the copy's entries up to the first whose segment field is over `s`, read from the raw bytes before anything is authenticated, with its chain head, Merkle root and the CIDs of the segment object and entry-hash list of the segment of its last entry ([[board]], Segments and checkpoints). Otherwise it is a checkpoint in `checkpoints` whose hash is the word (the hash binds the election and segment), whatever its source. Its `anchoredAt` is the end of `s`'s period, which gives the board checks the same result as the true time ([[contracts]], Board anchor, Verification). The anchors are passed to the board checks in segment order, which `{"checkpoint": n}` counts in.

A run that can't read or match a word stops at the first problem, in the order above (the account, the lowest-segment word, the range, the words in segment order, then matching in segment order), with these codes, each leaving 4.1 `not-reached` and 4.2 unverifiable, never failed: no one but L1 itself settles them, and a copy or an evidence set can be wrong without the election being so (T-53):

| Code                    | Meaning                                                                                                                                                  |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `l1-proof-missing`      | A node the walk needs isn't in `nodes` (a changed node, or a header whose state root differs, has another hash and so is missing)                        |
| `l1-proof-malformed`    | A node, account or storage value that no Ethereum trie holds (non-canonical RLP, a bad hex-prefix path, a stored zero)                                   |
| `l1-anchor-absent`      | The nodes prove no account at the anchor's address, or one without code                                                                                  |
| `l1-range-too-long`     | More than `2^20` segment words to read                                                                                                                   |
| `l1-checkpoint-unknown` | A non-zero word at `{"segment": s}` matches neither the copy nor any given checkpoint: someone must produce the checkpoint, from the log that carried it |

### Receipt keys from L1

Under definition versions 4 and 5, 2.9 reads the receipt-key record of the anchor the definition's `l1_anchor` names ([[contracts]], Board anchor, Receipt keys) from the bundle's L1 evidence at `B`, as Anchors from L1 reads checkpoints, never from a call or a list of logs (T-26, T-71):

1. The anchor's account is read as in step 2 of Anchors from L1. If it can't be, 2.9 is unverifiable with that step's code (`l1-proof-missing`, `l1-proof-malformed` or `l1-anchor-absent`) and `at` `{}`.
2. For each key `p ‖ x` in `receipt_keys`, in list order, its word is the value at `keccak256(slot)` in the storage trie, as step 3 of Anchors from L1, with `slot = keccak256(abi.encode(x, keccak256(abi.encode(uint256(p), A + 4))))`. A key whose word can't be read (`l1-proof-missing` or `l1-proof-malformed`) is left unread: the other keys are still read, since a later key's failure is final whatever the unread word holds.
3. A word the release code can't write ([[contracts]], Board anchor, Receipt keys: a high bit set, `retired_at` set with `registered_at` zero or above it, or either time after `B`'s timestamp) is `receipt-key-record`. Otherwise its low 64 bits are `registered_at` and the next 64 `retired_at`, judged by [[election-definition]]'s rule (Receipt keys) with `B`'s timestamp: `receipt-key-retired` if registered before `opens_at` and retired at or before it, at any `B`; otherwise, while `B`'s timestamp is before `opens_at`, the key is unsettled; from `opens_at` on, it is `receipt-key-unregistered` unless registered before `opens_at`, and judges the election otherwise.
4. The row: 2.9 fails with the first key in list order that is `receipt-key-record`, `receipt-key-retired` or `receipt-key-unregistered`, with `at` `{"key": i}` (its position in `receipt_keys`, from 0). Otherwise, if any key was left unread or is unsettled, 2.9 is unverifiable with the first such key's code (the L1 code, or `receipt-key-unsettled`) and `at` `{"key": i}`: a later block, or the missing node, settles it. Otherwise it passes.

The same bundle evidence proves both the anchors and the keys, so `nodes` holds the proofs of every listed key's slot beside the board's. The anchor's address is the definition's, read as given until 1.2 compares it with the release's pin (Definition, Residuals), so a passing 2.9 is as authentic as that address.

### Definition

A format-3 bundle's definition gives the board checks three of their inputs, so none of them can disagree with the election being verified:

1. The definition is decoded as [[election-definition]] (Decoding) says, then checked for well-formedness (Well-formedness), each under its own version's layout and rules; this verifier reads definition versions 1, 3, 4 and 5, and the hash it reports and the stub hash the key ceremony binds (Key ceremony, step 4) are taken over the version's own encoding. A record version this verifier doesn't know, other than 0 (which `profile-version` and the self-pin of Decoding forbid, so no definition can carry it), leaves 2.3 unverifiable with `unsupported-version` and `at` `{}`, as in step 2, so releases never disagree on a verdict (T-36). Any other definition that doesn't decode fails 2.1 with `decode` and `at` `{"decodeError": <code>}`; one that breaks a rule fails 2.1 with the first rule's code (`protocol-major` to `timing`, with `cells` under versions 3 to 5, `receipt-keys` under versions 4 and 5 and `questions` under version 5) and `at` `{}`, except that under version 5 `option-count` and `selections` have `at` `{"question": q}`, `q` the first failing question as a JSON number (P2-14). A release that reads definition version 6 (P2-16 part 4) reports version 5's rules the same way and then `results`, `civic-sealed` and `author-panel`, each with `at` `{}`; until then version 6 is unverifiable the same way. A release that reads definition version 7 ([[P2-17]] part 4) reports version 6's rules the same way and then `rolling-class` and `rolling-tier`, each with `at` `{}`; until then version 7 is unverifiable the same way. Every well-formedness rule is reported on 2.1, whichever later check its rule serves, since it is one property of the definition's bytes. In either case 4.1 and 4.2 are unverifiable with `not-reached`: the board checks have no election to run for.
2. The board-entry version is the one the profile pins for `0x0007` ([[versioning]]). A version this verifier can't read (it reads 1, 3 and 4) leaves 2.3 unverifiable with `unsupported-version` and `at` `{}`, and 4.1 and 4.2 with `not-reached`; a later release may read it, so it is never a failure. A version it reads whose combination with the profile's ballot and tally-opening versions 2.3 forbids fails 2.3 with `profile-combination` and `at` `{}`; the checks below still run under that version, so the report shows what the board holds. A profile that pins ballot version 2 with a spoiled-ballot opening version this verifier doesn't know, or a definition version 3 or 4 whose profile pins a ballot version it doesn't know, and that 2.3 doesn't fail on any other ground, leaves 2.3 unverifiable with `unsupported-version` and `at` `{}`, since a later release may know that version to open version-2 cores, or to name its cell; the checks below still run (T-36).
3. Otherwise the board checks run with the definition's `election_id`, that version, and its `l1_anchor` as the anchor's address. 2.1 stays unverifiable with `not-implemented` until the verifier checks the definition's hash against the L2 election registry the release pins. 2.9 passes under definition versions 1 and 3, which list no receipt keys; under version 4 it is read from the same L1 evidence as the anchors ([Receipt keys from L1](#receipt-keys-from-l1)), whatever the board checks find.

The report gives the definition's hash (`abolish/v1/election-definition`) whenever it decodes, so anyone can compare it with the registry's.

**Residuals.** The clock still comes from the bundle: the seal, `lastSegment`, is a function of the definition and the post-close windows `W` ([[election-definition]], The seal), and `W` isn't fixed until P1-18's contract-event window is (the openings' `OPENING_WINDOW` is, [[challenge]]); `epoch`, `period` and `deadline` come from the release's pinned anchor deployment (P1-19 part 3b). Until the release pins the anchor's address, the definition's `l1_anchor` is read as given: 1.2 must then compare it with the pin, and `anchorAddress` must not count as authenticated through the definition before that comparison exists, even once 2.1 authenticates the definition. And the header isn't bound to the definition's `l1_chain_id`; trusting the header (part 3b) binds it. Under definition versions 3 and 4 the regional cells are checked only by the `cells` rule, from the stated region counts: 2.4's per-cell recomputation from the board's group additions, 2.8's fold from those counts, and 5.1 to 5.3 against each cell's root come with the same checks for version 1 (P1-19), and until then each stays unverifiable with `not-implemented` (T-16).

### Key ceremony

A format-4 bundle's panel lets the verifier run the transcript check of [[ceremony]] (Transcript check). It runs once the definition gives the board checks their inputs (Definition), whatever those checks then find: the transcript's bytes are authenticated by the definition's hash of them, never by the board checks.

1. **The panel** (part of 2.5). The panel's identifier, recomputed from the bundle's panel, must equal the definition's `panel_id`, and its `k` and `n` the definition's `threshold` and `panel_size`. Otherwise 2.5 fails with `panel-unpinned` and `at` `{}`, and 3.1 and 3.2 are unverifiable with `not-reached`: the ceremony context binds the pinned panel's identifier, so a transcript checked against any other panel only fails its signatures. 2.5 otherwise stays unverifiable with `not-implemented` until the verifier compares the recomputed key set with the keys registered on L2.
2. **The version** (part of 2.3). If the profile pins a ceremony-transcript version (`0x0005`) this verifier can't read, 3.1 and 3.2 are unverifiable with `unsupported-version` and `at` `{}`: a later release may read it, so it is never a failure (T-36).
3. **The transcript** is the payload of the first entry of the copy, by position from 0 (whatever its `index` field), that decodes as a board entry under the pinned version, carries the definition's `election_id`, and whose `ceremony_transcript_hash` (over the payload, header included) is the definition's, whatever the payload's record type: bytes the definition binds that aren't a transcript fail step 4's decoding (`decode`, with the [[notation]] code for their record type), never go missing. Any copy of those bytes is the transcript, so its position, and whether it lies inside the anchored extent, don't matter; another transcript on the board, such as an abandoned run's ([[ceremony]], Approval and re-runs), is never read. If no entry matches, 3.1 is unverifiable with `ceremony-transcript-missing` and `at` `{}`, and 3.2 with `not-reached`: like a short copy, that is the copy's problem, never the election's failure (T-53).
4. **The check** runs over the transcript, pinned to version 1, with the context rebuilt from the definition (`l2_chain_id`, `trustee_registry`, `election_id`, the stub hash recomputed from it under its own version, so a transcript made for another version's stub of the same election fails its signatures) and the bundle's panel, never from the transcript (T-37). Its outcome sets the rows, with `at` `{"entry": n}` naming the transcript's entry on a failing row (a passing or `not-implemented` row has no `at`):

| Outcome                                                         | 3.1                                           | 3.2                            |
| --------------------------------------------------------------- | --------------------------------------------- | ------------------------------ |
| The transcript doesn't decode                                   | fail, `decode` (with `"decodeError"` in `at`) | unverifiable, `not-reached`    |
| `ceremony-order`, `ceremony-shape` or `ceremony-signature`      | fail, with the code                           | unverifiable, `not-reached`    |
| `ceremony-quorum`                                               | unverifiable, `not-implemented`               | fail, `ceremony-quorum`        |
| Valid, with at least `k` but fewer than `n − 1` qualified seats | unverifiable, `not-implemented`               | fail, `ceremony-participation` |
| Valid, with at least `max(k, n − 1)` qualified seats            | unverifiable, `not-implemented`               | pass                           |

The definition binds these bytes, so a transcript that fails is the election's failure, whoever boarded it. A transcript version other than its pin (`profile-mismatch`) and an unreadable pinned transcript version (step 2) are 2.3's matters, reported on 3.1 and 3.2 as above; 2.3 itself stays `not-implemented` for them. 3.1 never passes yet: it also needs the trustee registry's record of the transcript and its approvals on L2 (3.1's registration part), which the verifier doesn't read until it reads L2 state. 3.2 applies [[0006-trustees]] rule 7, which the owner adopted on 2026-10-12: an election opens only if at least `n − 1` seats took part, where taking part means being qualified (a disqualified seat holds no usable share), so 3.2 needs `max(k, n − 1)` qualified seats and fails with `ceremony-participation` below that. A ceremony with only `k` qualified seats would leave the tally no margin: one of them compelled or lost after the close, and no cell can ever be opened (T-54, T-40).

Once the check reaches the seats, the report's `ceremony` gives what it found, so anyone can see who qualified and why the others didn't.

**Residuals.** The panel is a local input until the release pins its panels, and the definition is one until 2.1 reads the registry, so a format-4 run's `verdict` stays `unverifiable` whatever the transcript is: a crafted bundle can make 3.1 or 3.2 fail against its own inputs, never the election's verdict (T-53). Nothing yet requires the transcript to be on the board by any point: an election whose board never carries it stays unverifiable from every copy, never failed, until a later part fixes by when it must be boarded.

### Ballot admission

Once a format-4 bundle's ceremony checks registered a key set (3.2 passes), the verifier runs the admission checks of [[ballot-validity]] (Ballot record: Decoding, Admission), 5.1 to 5.4, over every ballot of the election on the copy, then the close rule's window (5.5) over each copy by its own path, and rejects the repeats among the ballots those admit (5.7). Like the transcript, it runs whatever the board checks found: each ballot is judged from its own bytes, its own entry, the definition, the clock and the registered key set, never from another entry, so admission is stable (6.1, R4), and the verdict rests on 4.1 and 4.2 anyway.

1. **When it runs.** The ballot version is the one the profile pins: version 1 under definition version 1, version 2 (which names a cell) under definition versions 3 and 4, version 3 (which names a cell and carries one range proof per question) under definition version 5 (P2-14). Under any other ballot pin, 5.1 to 5.5 and 5.7 are unverifiable with `unsupported-version` and `at` `{}` (a later release may read it, T-36), except ballot version 1 under definition version 3, 4 or 5, which 2.3 fails beside a cell partition and which can't be judged against one: there they are unverifiable with `not-reached`. Otherwise, unless 3.2 passed, or if the definition names a membership key other than the pinned one (which fails 1.3, for ballot versions 2 and 3 as for version 1) or gives a tier (under definition versions 3 to 5, a cell) the root 0 (which anyone can prove membership of, T-04), they are unverifiable with `not-reached`: no ballot is judged under a panel that isn't registered or a key or root no ballot can be checked against. They run whatever 2.3 found, so a profile 2.3 fails for its spoiled-ballot opening pin still has its ballots judged.
2. **The ballots** come from every entry of the copy, by position from 0, that decodes as a board entry under the pinned version and carries the definition's `election_id` (any other entry is 4.1's to report), by one of two paths ([[close]], Window):
   - **the board path:** an entry whose payload is of type `0x0002` carries that payload as its ballot;
   - **the ordinary path:** under a profile pinning contract-event version 2, an entry whose payload is a contract-event record (`0x0008`) that decodes strictly under that version and passes the event check ([[contracts]], Event check) as the board's `BallotSubmitted` against the definition's `board` carries the event's `record` as its ballot, with `τ_b` the record's `l2_timestamp`. A record that doesn't decode or fails the event check carries no ballot: it is 4.4's to report (Contract events), and so is any other event. Under contract-event version 1 the board emits no event, so every ballot is a board-path one. The relayed path needs contract-event version 3 ([[contracts]], Event tables (version 3); `RelayedBallotSubmitted`), which this release doesn't read.

   Under a contract-event pin other than 1 or 2, ordinary ballots can't be found: 5.1 to 5.4 judge the board path's ballots alone, and 5.5 and 5.7 are unverifiable with `unsupported-version` and `at` `{}`, since a passing row would say no ballot it can't read was rejected (T-36); repeats are then listed as candidates, as below. Otherwise each ballot is decoded strictly under the pinned ballot version and admitted or rejected by the checks in [[ballot-validity]]'s order (version 2: Admission (version 2), with `ballot-cell` in place of `ballot-tier`, the root and scope of the cell it names and `M` under that cell's tier; version 3: Admission (version 3), version 2's order with each question's range proof judged against the definition's questions, never against limits the ballot implies, `option-proof` naming the first failing flat option and `sum-proof` the first failing question); the first failure is its result. A ballot they admit is then judged by the window of its own path, 5.5 ([[close]], Window): a board-path ballot whose entry's segment is above `s_A = period(closes_at) + 1`, with `period(t) = ⌊(t − epoch) / period⌋` under the bundle's clock (which may be below 0 for a close before the epoch), is rejected with `window-boarded-late`, which is also the report against the board operator; an ordinary ballot with `τ_b < opens_at` with `window-before-open`, and one with `τ_b > closes_at` with `window-after-close`. A board-path ballot has no opening test.

3. **The rows.** Each code fails these rows; a decoding failure is no row's:

| Code                                                                    | Fails         |
| ----------------------------------------------------------------------- | ------------- |
| `ballot-stray`, `ballot-tier`, `ballot-cell`                            | 5.1           |
| `membership-proof`                                                      | 5.1, 5.2, 5.3 |
| `validity-shape`, `share-hash-unqualified`, `option-proof`, `sum-proof` | 5.4           |
| `window-before-open`, `window-after-close`, `window-boarded-late`       | 5.5           |
| `repeat`                                                                | 5.7           |

A membership proof is checked once against `[ρ, ν, m̂, ŝ]` (the root and scope of the definition's tier, or of the cell a version-2 ballot names, the record's nullifier, and `F(M)` recomputed from the record), so its failure can't say which of the root, the scope or the message it was made under. A row fails with the code and `at` `{"entry": n}` of the first rejected entry, by position, whose code fails it, and passes otherwise, also when the copy holds no ballot. So a passing row means only that no ballot was rejected with one of its codes: a ballot rejected by an earlier check never reaches the later ones (its membership proof is never checked after `validity-shape`, say), and a ballot that doesn't decode fails no row, so every row can pass while `rejected` isn't empty. An admission row's failure rejects entries only: it never fails the election (Principles), and the report's `ballots` lists every rejection, so 8.3's list of rejected entries starts here.

4. **Repeats (5.7).** Over the ballots 5.1 to 5.5 admit (for format 5, those 5.8 then doesn't reject, [L1 references](#l1-references)), of either path, in copy order, step 1 of [[revoting]]'s Selection finds every repeat: a ballot with the same `tier` (version 2: its cell's tier), `ν` and `M` as one at an earlier position, with `M` recomputed from the record (5.3), never compared as bytes, so a copy whose membership proof was re-randomised is found too (T-38). It is rejected with `repeat`. A ballot 5.1 to 5.5 reject never makes another a repeat (R4), so a late copy never stands in for a timely one, and a timely copy stands whatever happened to the others ([[close]], Window). Under format 4 the input to 5.7 is the ballots every other admission check admits, and 5.8 doesn't run; it can't change which copies are rejected, since `M` binds the L1 reference (`l1_ref_number`, `l1_ref_hash`), so 5.8 admits or rejects every copy of a ballot alike. Format 5 runs 5.8 first, as [[revoting]]'s Selection takes the ballots every admission check admits, and reports its code, not `repeat`, at a copy of a ballot 5.8 rejects, so 5.7 may pass under format 5 where format 4 fails it, never with another entry admitted. Where 5.5 can't run (step 2), a repeat isn't rejected: it is listed as a candidate in `repeats`, and 5.7 is unverifiable.

Once it runs, the report's `ballots` gives `admitted`, the number of ballot entries 5.1 to 5.5 and 5.7 admit (where 5.5 can't run, those 5.1 to 5.4 admit, candidate repeats included), `rejected`, each rejected ballot entry in copy order with its `entry`, its `code` (an admission code, a window code, `repeat`, or `decode` with `decodeError`, the [[notation]] code) and, for `option-proof`, `option`, the first failing option (under ballot version 3, flat option), and for ballot version 3's `sum-proof`, `question`, the first failing question, and `repeats`, each candidate repeat in copy order with its `entry`, empty wherever 5.5 runs. An admitted ballot isn't yet counted: its L1 reference (5.8, under format 5 only) and selection (6.1, [Selection](#selection), under format 5 only) are decided over the admitted ballots below, and whether it is on the board in time (5.6), delivery (5.9) and the close check (6.3) by later parts, so they stay `not-implemented`.

**Residuals.** The copy and the clock are local inputs, so the admission rows and `ballots` report what the copy holds, and the window rows what the clock makes of its segments, including entries past the anchored extent, which 4.1 and 4.2 don't authenticate: a mirror can add ballots there, or leave out or add ones elsewhere, and so change the rows and `ballots`, never the verdict, which rests on 4.1, 4.2 and the election checks. Selection (6.1) takes only the ballots in the anchored extent of a sealed board ([Selection](#selection)). Until 2.4 and 2.8 recompute the trees from the board, admission takes the definition's tier and cell roots as stated: a definition whose cells put one commitment in two cells of a tier would let its holder have two ballots admitted, under two nullifiers, which 5.7 doesn't find; the verdict can't pass while 2.4 and 2.8 are unverifiable (T-16, P1-19). An ordinary ballot's `τ_b` is its contract-event record's `l2_timestamp`, which only the event accumulator authenticates, and 4.4 doesn't replay it yet: until it does, a copy's ordinary ballots are judged by timestamps no one has proven, so a mirror can move one into or out of the window, again changing the rows, never the verdict (T-53, T-71).

### L1 references

A format-5 bundle gives a run of finalized L1 headers (`l1Blocks`, Bundle), and wherever ballot admission runs and 5.5 can run (Ballot admission, step 2), the verifier judges each ballot 5.1 to 5.5 admit by its L1 reference (5.8), as [[revoting]] (Admission) specifies, before repeats (5.7). The check reads only the reference the ballot's `M` binds and the run, never another entry, so admission stays stable (R4) and every copy of a ballot gets the same verdict.

1. **When it runs.** Wherever 5.1 to 5.5 and 5.7 are unverifiable with `not-reached` or `unsupported-version` (Ballot admission, step 1), so is 5.8, with the same code and `at`; and so it is with `unsupported-version` and `at` `{}` where a contract-event pin hides the ordinary path (step 2), since a passing row would say no ballot it can't read was rejected (T-36). Under format 4, 5.8 stays `not-implemented`.
2. **The run.** Its last header is `head`, the latest finalized block read. `l1_ref_min` is searched in the run from its first block, which must show where the window starts: unless the first block is block 0, its timestamp must be before `opens_at − 3600`. A run that starts later can't place `l1_ref_min`, which may lie below it: 5.8 is unverifiable with `l1-blocks-short` and `at` `{}`, no reference is judged, and 5.7 runs as under format 4. Otherwise `l1_ref_min` is the first block of the run whose timestamp is at or after `opens_at − 3600`; if the head is before it, every reference is pending ([[revoting]], Before the window).
3. **Each reference** is judged by [[revoting]]'s steps 1 to 4, against the run: `l1-ref-before-open` below `l1_ref_min`, then `l1-ref-after-close` if the block numbered `min(l1_ref_number, head)` is later than `closes_at`, then **pending** if `l1_ref_number > head`, then `l1-ref-unknown` if the run's block of that number has another hash; otherwise the reference is admitted. Every lookup lies in the run, between `l1_ref_min` and `head`. A rejected ballot is listed in `rejected` with its code, never counted and never makes another a repeat. A pending ballot is neither admitted nor rejected: it stays among the ballots 5.7 compares, since whatever L1 later decides for it, it decides for its copies, and only the first copy is listed in `pending`; a copy after it is rejected with `repeat`, a code that holds only while 5.8 is unverifiable: once the run reaches past close, the copy gets the first copy's 5.8 code instead if that rejects it. 6.2's `opening-cast` still compares openings with every ballot 5.1 to 5.5 admit, whatever 5.8 finds for it.
4. **The row.** If any ballot is pending (and not a repeat), 5.8 is unverifiable with `l1-ref-pending` and `at` `{"entry": n}`, the first such entry: it may yet be admitted or rejected, and must not let the row pass or fail for the others. Otherwise 5.8 fails with the code and `at` `{"entry": n}` of the first entry it rejected, and passes if it rejected none, also when the copy holds no ballot. Like every admission row, its failure rejects entries only, never the election; its unverifiability leaves the election unverifiable (Verdicts). `admitted` in `ballots` counts the ballots 5.1 to 5.5, 5.7 and 5.8 admit, so never a pending one.

Once a run reaches a head after `closes_at`, no reference is pending and the verdicts don't depend on which head ([[revoting]], Every verifier reaches the same verdict), so a bundle need carry L1 only from a block before `opens_at − 3600` to the first block after close ([[revoting]], Bounded evidence).

**Residuals.** The run is a local input (`l1Blocks`, `local-file`): its parent links make it one chain, but nothing yet shows that chain is Ethereum's finalized one, since trusting a finalized head is part 3b's. Until then a crafted run can admit or reject any reference, changing the row and `ballots`, never the verdict. The only tie to the anchors' evidence is that a run holding `l1.header`'s number must hold that header; a run that doesn't reach it is unconstrained by it. A run is as long as the poll in L1 blocks (about 7,200 headers a day), which the user supplies and pays for in reading; a later part may replace it with the history the beacon chain or EIP-2935 commits to, under the same rules.

### Selection

Wherever 5.8 runs (format 5), the verifier decides 6.1 once the set it selects from is fixed, by [[revoting]]'s Selection over the ballots every admission check admitted from the counted extent. The rule is a function of that set alone (R3), so 6.1 never passes over a set a later entry or finding could still change: short of each condition below, it is unverifiable, and the conditions are checked in this order, the first unmet one giving the row's code.

1. **Admission settled.** Every admission row, 5.1 to 5.5, 5.7 and 5.8, passed or failed. One that can't be evaluated may yet admit or reject a ballot (Principles), so 6.1 is unverifiable with `not-reached` and `at` `{}`; so it is under format 4, where 5.8 doesn't run, and wherever the key-ceremony checks run but ballot admission can't (Ballot admission, step 1). Where the definition stopped the board checks, Procedure step 6 makes 6.1 `not-reached` with no `at`, as it does 5.8.
2. **The board.** 4.1 and 4.2 passed, so the copy's prefix up to the anchored extent is the board ([[board]], Board checks); otherwise `not-reached` and `at` `{}`. Only entries in the anchored extent take part from here on: one past it is no one's claim.
3. **The seal.** The seal's window has closed: `epoch + (lastSegment + 1)·period + deadline < now` under the bundle's clock. With 4.2 passing, that means the seal's checkpoint is counted and fixes the board's final extent; before it, an entry may still be boarded within the counted extent. Otherwise `not-sealed` and `at` `{}`.
4. **Timestamps.** Unless 4.4 passed, no entry of the anchored extent carries an ordinary-path ballot (Ballot admission, step 2), admitted or not: its window (5.5) rests on its record's `l2_timestamp`, which only 4.4's accumulator replay authenticates, so the operator could have moved it into or out of the window (T-35, T-71). Otherwise `not-reached` and `at` `{"entry": n}`, the first such entry.
5. **The counted extent.** No admitted ballot of the anchored extent is in a segment above `s_F = period(closes_at) + 1`, the floor of `s_S` ([Spoiled-ballot openings](#spoiled-ballot-openings), step 3). A board-path ballot above it is already rejected (`window-boarded-late`), but an ordinary one may be boarded later, and whether it is within the counted extent (`segment ≤ s_S`, [[tally]], Tally window) waits on `s_S`; otherwise `not-implemented` and `at` `{"entry": n}`, the first such entry.
6. **The selection.** The admitted ballots of the anchored extent, every one of them in the counted extent, go through [[revoting]]'s Selection: 5.7 has already rejected every repeat, so step 1 finds none, and steps 2 and 3 group them by (`tier`, `ν`) (under ballot versions 2 and 3, the cell's tier) and choose, in each group, the single ballot naming the highest L1 block, or list a tie. 6.1 passes, also when nothing is admitted: no failure of it is possible from the board, since a tie or an exclusion is the rule's outcome, never a breach. The report's `ballots` gains `selected`, each group's counted ballot, and `ties`, every ballot naming its tied group's highest block (a lower one of that group is in neither), each in copy order with its `entry`.

A selected ballot isn't yet counted: delivery (5.9) and a proven complaint can still exclude it, with no fallback to an earlier ballot of its group ([[revoting]], Selection, step 4), and the close check (6.3) recomputes each cell's counted set without the ordinary ballots after its head; those are later parts', and none of them changes `selected`.

**Residuals.** Until 4.4 can pass, condition 4 holds only for a board whose profile pins contract-event version 1, or whose anchored extent holds no ordinary ballot; and until `s_S` is known (P1-18's contract-event window), condition 5 can't pass for an admitted ballot boarded after `s_F`. The run of L1 headers that settles 5.8 and the clock that places the seal are local inputs (`l1Blocks`, `clock`), so a crafted one can change `selected` and `ties`, never the verdict, which stays unverifiable while they are (Verdicts; T-53). Condition 4 sees only the ordinary ballots the board holds: an operator that boards none of a voter's direct-submitted ballots leaves nothing for it to wait on, so 6.1 can pass over a set that lacks them. That is 5.6's to catch (a ballot found on L2 but missing from the board), and while 5.6 is unverifiable so is the verdict (T-25, T-71).

### Spoiled-ballot openings

Wherever ballot admission runs, the verifier then checks every spoiled-ballot opening of the election on the copy (6.2) against the same definition and registered key set, and judges it against [[challenge]]'s Publication rules as far as the bundle decides them. Like admission, it runs whatever the board checks found, and each opening is judged from its own bytes, the definition, the key set, the clock and the ballots admission admitted, so no opening changes another's checks (R4).

1. **When it runs.** This release reads spoiled-ballot opening versions 1 and 2: version 1 opens ballot version 1's cores, under definition version 1, and version 2, with `cell` in place of `tier`, opens ballot versions 2 and 3's, under definition versions 3 and 4 (ballot version 2) and 5 (ballot version 3) ([[challenge]], Opening version 2). Under a profile whose spoiled-ballot opening pin (`0x0003`) is another version, or whose ballot pin is neither the definition's own ballot version nor version 1 (as for admission, step 1), 6.2 is unverifiable with `unsupported-version` and `at` `{}`: a later release may read that opening version, or open that ballot version's cores (T-36). Otherwise, under any pins but the definition's own ballot version beside the opening version that opens its cores, a profile 2.3 fails (`profile-combination`), 6.2 is `not-reached`: no opening is judged against an election whose ballots it can't be an opening of. So is it wherever 5.1 to 5.4 are `not-reached` (Ballot admission, step 1): an opening of shares made to an unregistered panel can't be judged (T-37), and `opening-cast` compares with admitted ballots.
2. **The openings** are the payloads of type `0x0003` of every entry of the copy, by position from 0, that decodes as a board entry under the pinned version and carries the definition's `election_id`. Each is decoded strictly under the pinned version and checked by [[challenge]]'s Checks in order (under version 2, against the definition's cells and questions, with `opening-cell` in place of `opening-tier` and `m` the total over the questions under definition version 5); the first failure is its `code` (`decode`, with `decodeError`, or an `opening-*` check code, with the first failing `option` for `opening-vss`, a flat option under definition version 5, and `seat` for `opening-ciphertext`). A passing opening reports its tracking code (under version 2, the core hash under the ballot version the profile pins, since the opening carries none), its vote and, if no valid ballot could carry that vote, `voteOutside` (`opening-vote-outside`, the client's evidence, no one's on the board), under version 2 with `question`, the first question outside its rules (0 under definition versions 3 and 4).
3. **The floor.** `s_S` needs `W_S`, whose contract-event window P1-18 hasn't fixed, so the verifier doesn't know it yet. It knows its floor, `s_F = period(closes_at) + 1` ([[tally]], Tally window: `s_S` is the later of that and another period), with `period(t) = ⌊(t − epoch) / period⌋` under the bundle's clock, which may be below 0 for a close before the epoch. An entry in a segment at or below `s_F` is in the counted extent whatever `s_S` is.
4. **The breaks** an opening is known to make of the Publication rules, in that table's order: `opening-early` if its entry's segment is at or below `s_F` (the envelope's, so an opening that doesn't decode can be early too); `opening-cast`, with `ballot`, the first such ballot's position, if it passed and opens a commitment ([[challenge]], Opened commitments) of a ballot 5.1 to 5.5 admitted at or below `s_F`, by either path; and `opening-repeat`, with `of`, the first such entry's position, if an earlier entry of the copy carries an opening that decodes with the same core hash, whatever that opening's checks found (the operator boards one opening per core). `opening-late`, `opening-early` above `s_F` and `opening-cast` of a ballot above it wait on `s_S`.
5. **The row.** An opening is settled when it has a `code` or a break. If any opening isn't settled, 6.2 is unverifiable with `not-implemented`: it may yet be early, late or cast, and an unsettled opening must not let the row pass or fail for the others. Otherwise 6.2 fails with the first opening's `code`, or its first break's code, and `at` `{"entry": n}` (with `decodeError` for `decode`), or passes if the copy holds no opening. A later release that knows `s_S` may report an earlier break of the same opening (`opening-early` above `s_F`, say) and so another code at the same entry, never another status. Like an admission row's, the failure never fails the election: an opening never counts, displaces or fails anything ([[challenge]], Publication).

Once it runs, the report's `openings` lists every opening entry in copy order with its `entry`, `code` and, where they apply, `decodeError`, `option` and `seat`, or for a passing opening `coreHash` (hex), `votes` (each `v_j` as a decimal string) and `voteOutside` (`true`, only when it applies, with `question` under opening version 2), and `breaks`, each with its `code` and, for `opening-cast`, `ballot` and, for `opening-repeat`, `of`.

**Residuals.** The copy and the clock are local inputs, so the row and `openings` report what they hold: a mirror can add, drop or reorder openings, or drop the ballot that makes one cast, and change them, never the verdict. Until `s_S` is known, an opening boarded after `s_F` but within the counted extent, during the tally window or after `t_S + OPENING_WINDOW` goes unreported, and 6.2 can't pass while any honest opening is on the copy. Openings past the sealed extent are read like any other until the verifier limits itself to it.

### Tally openings

Wherever the ceremony checks registered a key set (3.2 passes), under definition versions 1, 3, 4 and 5, the verifier reads every tally opening of the election on the copy (7.3, 7.4): it sorts each into an opening of a cell or a stray opening, attributes it by the registered signing keys ([[tally]], Opening record: Signature, Which openings are a cell's), and judges it against [[tally]]'s Boarding rule as far as the bundle decides that rule without the counted set. Sorting and attribution read only the opening's own bytes, the definition and the registered key set, and the one rule that compares openings (a second by the same seat) only earlier entries, so dropping an entry never changes another's cell, attribution or other breaks (R4).

1. **When it runs.** Under a profile whose tally-opening pin (`0x0006`) isn't version 1, 7.4 is unverifiable with `unsupported-version` and `at` `{}`: a later release may read that version (T-36). Otherwise, unless 3.2 passed, it is unverifiable with `not-reached`: with no registered key set no opening can be attributed. It doesn't need ballot admission: an opening is attributed whatever membership key or tier roots the definition names. Nor does it need 2.3 to pass: it runs whatever 2.3 finds for another pin (`profile-combination` for a ballot or spoiled-ballot opening pin that doesn't fit, or `unsupported-version` for one a later release may read), since sorting and attribution read only the tally-opening version.
2. **The openings** are the payloads of type `0x0006` of every entry of the copy, by position from 0, that decodes as a board entry under the pinned version and carries the definition's `election_id`. Each is decoded strictly under version 1; one that doesn't decode is a rejected entry (`code` `decode`, with `decodeError`), opens no cell, and the Boarding rule refuses it. A decoded opening is an opening of cell `c` if its `definition_hash` is the definition's and its `cell` is `c`, a position in the partition ([[election-definition]], Notes, Tally partition): under definition version 1 a position in `electorate`, whose cells are its tiers; under versions 3 to 5 a cell's number, counting every tier's `cells` in `electorate` order from the first tier's first cell ([[election-definition]], Layout (version 3)), so it names a cell, not a tier; and stray otherwise; its `signer` is the seat its signature attributes it to, or `null`.
3. **The breaks** an opening is known to make of the Boarding rule, in that rule's order: `tally-stray` for a stray opening; `tally-missing` for an opening of a cell whose number of entries isn't `m`, the definition's `option_count` (under definition version 5, the total of its questions' option counts, [[tally]], Context) (it fails its cell's opening checks whatever the counted set, [[tally]], Opening checks); `tally-unattributed` if its signature attributes it to no seat; and, for an opening of a cell attributed to a seat when an earlier entry of the copy carries an opening of the same cell attributed to the same seat, whatever that one's checks find (the operator boards at most one per seat and cell), with `of`, the first such entry's position: `tally-second` if its signed message ([[tally]], Signature) differs from that first one's, which shows the seat signed two different openings of the cell, or `tally-repeat` if it is the same, which anyone can replay, so it is the operator's breach alone and never its signer's (T-29). An unattributed opening is by no seat, so it is never a second or a repeat and never makes another one so. `tally-aggregate` and `tally-opening` against the cell's aggregate wait on the counted set (7.1), which needs selection (6.1); a later release that reports them puts them after `tally-missing`, in [[tally]]'s Opening checks order, and before `tally-unattributed`.
4. **The row.** An opening is settled when it has a `code` or a break. If any opening isn't settled, 7.4 is unverifiable with `not-implemented`: it may yet be over another set or fail to open its cell's aggregate, and an unsettled opening must not let the row pass or fail for the others. Otherwise 7.4 fails with the first opening's `code`, or its first break's code, and `at` `{"entry": n}` (with `decodeError` for `decode`), or passes if the copy holds no tally opening. A later release that knows the counted set may report a break of the same opening earlier in that order (`tally-aggregate`, say) and so another code at the same entry, never another status. Every break is a record the operator should have refused, so it is reported against the operator, and, except `tally-repeat`, also against its signer, if any ([[tally]], Boarding). 7.4 is report-only: it never fails the election, whose result rests on 7.1 to 7.3.

Once it runs, the report's `tallies` lists every tally-opening entry in copy order with its `entry`, then `code` and `decodeError` for one that doesn't decode, or `cell` (for an opening of a cell) and `signer` (a seat, or `null`), then `breaks`, each with its `code` and, for `tally-second`, `of`.

**Residuals.** The copy is a local input, so the row and `tallies` report what it holds: a mirror can add, drop or reorder openings and so change them (dropping a seat's first opening of a cell, say, makes its second the first), never the verdict. Openings past the sealed extent are read like any other until the verifier limits itself to it. Under definition versions 3 and 4 the partition is the one the definition states, taken as stated until 2.8 recomputes it from the board: a definition stating other cells than the fold's moves openings between a cell and stray, which changes the row and `tallies`, never the verdict, which can't pass while 2.8 is unverifiable (T-16). A summed share disguised as a failing opening ([[0015-tally-publication]], T-15) is reported only once the counted set shows the opening failing.

### Contract events

For formats 3 to 5, wherever the definition gives the board checks their inputs (Definition), the verifier runs the part of 4.4 that the board copy decides by itself: every contract-event record of the election on the copy passes the event check ([[contracts]], Contract-event record, Event check). Only the board operator boards a contract-event record, of a log one of our contracts emitted, and every log the release contracts emit passes the check, so a record that fails it, or doesn't decode, is the operator's and never a submitter's: it fails 4.4, an election check (T-17, T-31, T-53, T-71).

1. **When it runs.** Under a profile whose contract-event pin (`0x0008`) isn't version 1 or 2 (version 3 included, until P1-19 reads it), 4.4 is unverifiable with `unsupported-version` and `at` `{}`: a later release may read that version (T-36). (Every well-formed definition pins `0x0008` exactly once, by 2.1's `profile-types`.) Otherwise it runs whatever 2.3 finds, since the check reads only the record's own bytes, the contract-event version and the definition's L2 addresses, and it needs no panel, so format 3 runs it as format 4 does.
2. **The records** are the payloads of type `0x0008` of every entry of the copy, by position from 0, that decodes as a board entry under the pinned version and carries the definition's `election_id`; an entry that doesn't is 4.1's to report. Each is decoded strictly under the pinned contract-event version (a record of the other version is `profile-mismatch`, [[contracts]], Layout (versions 1 to 3)) and then checked under that version's event tables against the definition's `election_registry`, `trustee_registry`, `group_registry` and `board`, which 2.1's `chain` rule keeps pairwise distinct.
3. **The anchored extent.** Only the anchored board is anyone's claim, and the board checks ignore every entry past the anchored extent ([[board]], Board checks), so no one can fail an election by appending entries to a copy of its board (T-53). When 4.1 and 4.2 pass, only the entries inside the anchored extent (the `entries − unauthenticated` first ones of `board` in the report) are read. When they don't, the copy isn't authenticated, and every entry is read, but a record that would fail 4.4 leaves it unverifiable instead, with the same code and `at`.
4. **The row.** The first record read, in copy order, that doesn't decode gives `decode` with `at` `{"entry": n, "decodeError": <code>}`, and the first that fails the event check gives its code (`unknown-contract`, `unknown-event`, `event-topics` or `event-data`) with `at` `{"entry": n}`: 4.4 fails with it inside the anchored extent, and is unverifiable with it otherwise (step 3). If no record read fails, including a copy holding none, 4.4 is unverifiable with `not-implemented`, never a pass: what it doesn't decide yet (below) is part of 4.4 itself. A later release that decides more may report another code at an earlier entry, or a failure where this one is unverifiable, never a pass where this one fails: a record that fails the event check fails under its version's frozen tables for good ([[contracts]], Event check).

**What it doesn't decide yet.** The required entries: which events must be boarded (the events that name the election, its tiers' group creations and their additions and removals up to each `root_l2_block`, its panel's key and ceremony registrations) is known only from the L2, through the archive (P4-3) and the L2 reads that 2.4, 2.5 and 3.1 wait on. The accumulator's replay ([[contracts]], Event accumulator, Verification), over each contract's whole archived sequence against storage proofs at output roots settled on L1, with the TEE-only roots annotated (P4-3, P1-19 part 3b), and the L1 origins of the election's `ElectionCreated` and `DefinitionRegistered`, which need the pinned `max_sequencer_drift` and finalized L1 blocks.

**Residuals.** No ordering rule is applied to the board's records. The board carries only the events the election's checks use, out of sequences shared by every election, so the `n` of one contract's boarded records have gaps, and rule 1 of Event accumulator, Verification (numbered with no gap, `b` and `τ` never decreasing) is defined over a contract's whole archived sequence, not a board's subset. Neither [[contracts]] nor [[board]] says in what order the operator boards contract events, late ones included ([[tally]], Tally window: contract events are always boarded), so whether one contract's boarded records must appear in increasing `n`, and whether a record boarded twice fails anything, is open (P1-18); until it is decided, a reordered or repeated record changes no row here, and the accumulator's replay still catches a record that isn't the contract's own. Under step 3, a copy the anchors don't authenticate can change 4.4's code and `at`, never its status between pass and fail. The L2 addresses records are checked against come from the definition, which is unauthenticated until 2.1 proves its hash against the L2 election registry: a crafted definition naming other contracts (with the same `election_id` and `l1_anchor`) makes every honest anchored record fail `unknown-contract`, turning `verdictAgainstInputs` to `failed`, never the verdict, as with 1.3's `membership-key` (T-53).

### Procedure

1. Read and parse the bundle, or reject it.
2. Split `board.bin`.
3. For formats 3 to 5, read the definition ([Definition](#definition)). If it stops the board checks, 4.4 is unverifiable with `not-reached`; go to step 6.
4. For formats 2 to 4, read the anchors and `now` from L1 ([Anchors from L1](#anchors-from-l1)). If that stops with a code, 4.1 is unverifiable with `not-reached` and 4.2 unverifiable with the code; go to step 6.
5. Run the board checks of [[board]] (Board checks) with the election identifier, pinned version, anchors, clock and `now`. They stop at the first failure, and the code decides the rows of 4.1 and 4.2:

| Outcome                                                                                                   | 4.1                         | 4.2                         |
| --------------------------------------------------------------------------------------------------------- | --------------------------- | --------------------------- |
| All pass                                                                                                  | pass                        | pass                        |
| `wrong-election` at a checkpoint, `checkpoint-equivocation`, `checkpoint-size`, `checkpoint-inconsistent` | unverifiable, `not-reached` | fail, with the code         |
| `checkpoint-missing`, `copy-mismatch`                                                                     | unverifiable, with the code | unverifiable, with the code |
| `decode`, `wrong-election` at an entry, `wrong-index`, `segment-decreased`, `opening-order`               | fail, with the code         | unverifiable, `not-reached` |
| `checkpoint-boundary`, `checkpoint-cid`, `unanchored`, `unsealed`                                         | pass                        | fail, with the code         |

6. For formats 3 to 5, unless step 3 stopped the board checks, run 4.4's event check over the copy's contract-event records ([Contract events](#contract-events)), with the anchored extent of step 5 when 4.1 and 4.2 pass. Report every other check unverifiable with `not-implemented`.

### Verdicts

- `verdictAgainstInputs` is `failed` if any election check fails, otherwise `unverifiable` if any election or admission check is unverifiable, otherwise `verified`. Report-only checks never change it. An admission check that fails only rejects its entry. One that can't be evaluated makes 6.1 unverifiable (Principles), so it counts as unverifiable here.
- `verdict` equals `verdictAgainstInputs` when every input is authenticated, and is `unverifiable` otherwise. Anyone can make a bundle whose `verdictAgainstInputs` is `failed`, so it is never the election's verdict: a consumer never shows it without `verdict` and `inputs` beside it (T-53).

### Command line

`abolish-verify [--] <bundle-directory>` runs the procedure over one bundle. On success it writes the report to stdout as JSON followed by a newline, and a summary to stderr. A rejected bundle writes no report, only the reason, to stderr.

The exit code depends on `verdict` alone, never on `verdictAgainstInputs`, so a script that reads only the exit code can't be made to read a crafted bundle's findings as the election's (T-53):

| Code | Meaning                                                                       |
| ---- | ----------------------------------------------------------------------------- |
| 0    | `verdict` is `verified`                                                       |
| 20   | `verdict` is `failed`                                                         |
| 21   | `verdict` is `unverifiable`                                                   |
| 22   | The bundle was rejected; there is no report                                   |
| 64   | Usage: no bundle, an empty one, more than one, an unknown option, or `--help` |

0 means verified and nothing else, which is why `--help` (whose text goes to stdout, unlike every other usage error's) exits 64. No code is one Node exits with on its own: 1 for an uncaught error, 3 to 14 for its internal failures, over 128 for a signal. Any code not in the table, including 1 when the report can't be written, is a failure of the verifier itself and says nothing about the election.

The summary's first line is `verdict: <verdict>`. While any input is unauthenticated it continues ` (unauthenticated inputs: <names>; against those inputs: <verdictAgainstInputs>)`, so `verdictAgainstInputs` is never shown without `verdict` and the inputs beside it. A line follows for each failed check: its `id`, `fail`, its `code` and its `at` as JSON. Anything quoted from the bundle (a rejected member name, say) is printed as printable ASCII only: every other character and the backslash are written as `\u{<hex>}`, so a bundle can't put control or bidirectional characters on a terminal.
