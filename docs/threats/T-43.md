# T-43: Script injection in the ballot client

- Area: Client integrity and cast as intended (G-6, G-13)
- Adversary: A-3
- Status: **Partial by design.** A browser extension with page access is outside what a web page can defend against.

## Threat

XSS or a malicious extension reads the plaintext or the voting secret.

## Mitigation

Strict CSP, no third-party runtime code, encryption and proving in a Web Worker (P2-8).

## History

- 2026-10-12 (P2-8 part 1): the ballot client's CSP is built: a `<meta>` policy with `default-src 'none'`, scripts, styles, fonts and images from `'self'` only, no network access yet, Trusted Types with no policy, and no `<base>` or form posts; a bundle test allows no npm runtime code but React's, and an e2e test shows Chromium refusing injected script, markup, event handlers, foreign images and requests. The client refuses to run on an IPFS path gateway, where every CID shares its origin and another CID's page could read it. Still open: the Web Worker (part 2); framing, which a `<meta>` policy can't forbid and needs a header from the host; and navigation, which CSP doesn't govern, as a leak path for code that does run.
- 2026-10-12 (P2-8 follow-up): the path-gateway refusal now decodes the path as a gateway would (percent-encoding, repeated slashes, `.` segments, backslashes) before comparing, and refuses a path with a `..` segment after decoding or one it can't decode. The bundle and CSP check in #82 judges the build of the client's own config, which could detect the check and emit clean output only then (T-59).
- 2026-10-12 (`ci:` ballot worker policy): the owner-reviewed check now sees what a Web Worker bundles (Vite builds workers apart from the page, and before this their modules never reached the check), allows `@abolishus/crypto`'s build and its four `@noble/*` libraries, and pins `worker-src 'self'` and one named Trusted Types policy, `ballot-worker`, for the worker's script URL. A dedicated worker takes its CSP from its own response headers, not the page's `<meta>`, so on a host that sends none (IPFS, ENS) nothing restricts it: the check rejects any network or code-loading API (`fetch`, `XMLHttpRequest`, WebSockets, `importScripts`, nested workers, dynamic `import()`) in a script the page doesn't load itself, and WebRTC anywhere. It's a heuristic over bytes, so code that builds those names at run time evades it; P2-8 part 2's e2e must show the worker can't reach the network. Until part 2 creates `ballot-worker` first thing, code already running in the page could create it and write markup through it.
- 2026-10-12 (P2-9 part 1): `apps/web` sends a CSP header with a nonce per response: scripts from `'self'` and nonced inline scripts only, `connect-src 'self'`, no framing, `<base>` or plugins, plus `no-referrer` and same-origin opener and resource policies. It is weaker than the ballot client's, allowing `'self'` scripts beside the nonce and no Trusted Types yet, since the framework renders inline scripts; no vote is cast there.
- 2026-10-12 (P2-8 part 2a): the ballot client creates `ballot-worker` in a module `main.tsx` imports first, so the policy exists before any other module's code runs (a bundle test pins it ahead of React's code) and later code can't claim it; it mints a script URL for the worker's own bundled URL only. The page does all I/O, and the worker's script contains none of a listed set of network and code-loading APIs. That rests on the bytes: the build check bans those APIs from the worker's script (the list misses some fetching APIs, such as `WebSocketStream`, the Cache API and `FontFace`), and an e2e that serves the worker with no CSP header (as a gateway would) observed no request in one run. Code that builds an API name at run time would evade both, and nothing in the browser would stop it.
- 2026-10-17 (P2-21 part 1, [[0009-membership-proof]], Amendment): proving needs `'wasm-unsafe-eval'` in `script-src` (WebAssembly compilation, never JavaScript `eval`) and `'self'` in `connect-src` for the key; single-threaded snarkjs needs no `blob:` workers, but runs in a second worker the `ballot-worker` policy must mint. Its bundle contains `fetch(` and `new Worker` on branches proving never reaches; the proposal stubs both at build time so the worker ban (`WORKER_BANNED`), the only network defence on gateway hosts, still holds for the prover worker's chunk. Proposed for the owner, not changed: the CSP stays as it is until an owner-reviewed `ci:` change.
- 2026-10-17 (`ci:` membership prover, owner-approved): the pinned CSP now has `script-src 'self' 'wasm-unsafe-eval'` and `connect-src 'self'` before the two origins. The first lets any of the client's scripts compile WebAssembly (never evaluate JavaScript: an e2e shows `eval` still refused and a module compiled); the second lets the page fetch anything of its own origin, which on an IPFS or ENS gateway is only the client's own release, the prover's key and witness calculator among it. The page may leave exactly two scripts for workers to start, the ballot worker's (`assets/worker-*.js`) and the prover worker's (`assets/prover-*.js`), which `ballot-worker` mints, and loads neither itself; `WORKER_BANNED` applies to both, so the prover worker's chunk, snarkjs included, may name no network or code-loading API. Residual: the ban is still a heuristic over bytes, and the `.zkey` and `.wasm` files the build may emit are pinned by sha256, but the client's own re-check is what protects a voter served other bytes.
- 2026-10-18 (P2-22 part 6c): `apps/web`'s policy is widened on the poll editor's pages alone (`/account/polls/<new or id>`): `script-src` adds `https://challenges.cloudflare.com` and `frame-src` allows it, for the Turnstile widget a poll's submission needs; `connect-src` stays `'self'`. Every other page's policy is unchanged, the editor's links out are plain ones that load a new document, and the script is loaded only when the author presses Submit. No vote is cast on `apps/web`, and the ballot client's policy is untouched. Residual: on that page, once loaded, Cloudflare's script runs with the page's origin (see T-55).

Index: [[THREAT_MODEL]].

- 2026-10-17 (P2-8 part 2b, owner decision): `connect-src` is the API's origin and one L2 JSON-RPC origin, staging's (`https://api-staging.abolish.us`, `https://sepolia.base.org`), instead of `'none'`; the client's own origin is not listed. Both are untrusted sources: every answer is checked against the registry before it is shown (T-34), so a hostile one can refuse service or see which election a client asks for, not change a ballot. The bundle check lets scripts name only these origins, exactly or under a path, never a lookalike host, and a worker still may not fetch (`WORKER_BANNED`), since it gets no CSP from the page on a gateway host. Residual: the L2 endpoint, public and rate-limited, learns that an address asked for an election.
