# T-31: Encoding ambiguity and parser differentials

- Area: Integrity and verifiability (G-7, G-8, G-9)
- Adversary: A-2, A-9
- Status: **Partial** (P1-2 accepted by the agent, owner may veto: explicit byte layouts). P1-10 built the primitive codecs and framing; record layouts and the Solidity and Noir consumers are still missing.

## Threat

Two byte strings decode to the same value, or two implementations decode the same bytes differently, so a hash, signature or anchor commits to something other than what a verifier checks.

## Mitigation

Canonical encodings defined in `docs/spec/`, hand-written strict decoders that reject non-canonical forms, round-trip property tests, and cross-language vectors consumed by TS, Solidity and Noir (P1-2 ADR, P1-8, P1-10). No schema library defines protocol bytes.

Built so far (P1-10): the strict primitive codecs, record framing and `DS` framing in `packages/crypto`, tested against `docs/spec/vectors/primitives.json` and with fast-check round-trip and rejection properties. Built in P1-11: the `scalar` and `element` codecs of [[group]], tested against `group.json` and RFC 9496's invalid encodings. P1-10b specified the election-definition and display-text layouts, version 1, frozen by their vectors ([[0008-draft-record-layouts]] rejects draft layouts). P1-17c added the first Noir consumer, for the tag fields and byte packings in `circuit.json` only. Not yet: the remaining record layouts, and Solidity and Noir consumers of the record vectors (P1-18, P1-17). Until those exist, a misreading shared by the spec and the TypeScript code goes undetected.

Index: [[THREAT_MODEL]].

## History

- 2026-10-11 (P1-17c): the first Noir consumer: the packing of circuit-facing values ([[notation]]) and the tag-to-field rule ([[domain-separation]]), with `circuit.json` run by TS and by Noir. Each record's packing comes with the circuit that takes it.
- 2026-10-11 (P1-10b): election-definition and display-text record layouts (version 1) specified, built and vectored, and frozen by those vectors; later field changes become new versions ([[0008-draft-record-layouts]]).
- 2026-10-12 (P2-3 part 2a): the API refuses a request body whose objects repeat a key (equal once unescaped) with 400 before any procedure reads it, so no component in front of the API can read a different input from the same bytes. Protocol bytes are still the hand-written codecs; this covers only the JSON envelope.
- 2026-10-13 (P2-14 part 1b): ballot version 3's statement, ballot and core hashes take version input 3, and a proof made over version 2's statement is rejected in the vectors; spoiled-ballot opening version 2 opens the cores of ballot versions 2 and 3 under the pinned ballot version's core hash, so one tracking code never names cores of two versions ([[challenge]], Opening version 2).
- 2026-10-15 (P1-12d, [[delivery]], Share-receipt batch, Capacity; [[contracts]], Event tables (version 4)): a batch has one encoding per set of pairs and signature: its pairs are strictly ascending by ballot hash, so none repeats and none reorders, and its own signature tag keeps its statement from ever reading as a single receipt's.
- 2026-10-16 (P1-12f part 1a, [[delivery]], Obligation root): specified, not built. A root's leaves are strictly ascending by ballot hash, so a set of receipts or complaints has one leaf object, one canonical CID and one root; the obligation tree's own tags keep its nodes from being the board tree's.
- 2026-10-16 (P2-16 part 3b, [[tally]], Author panel): tally-opening version 3's partial opening is signed under its own tag, `abolish/v1/sig/partial-opening`, over its header and panel, so it never reads as a version-1 opening's header-less message; summed-share message and destruction statement version 2 keep version 1's tags because their signed bytes start with the record type and version, and tally-opening version 3 fixes both, so no election chooses them.
