## Decided (part 2a)

[[0029-board-data-availability]]: option D, `Accepted (agent) — owner may veto`.

- **Checkpoint version 2** names the segment object's and entry-hash list's CIDs on L1, with CID rules the authority fails on. The verifier can then fetch from chain + IPFS alone.
- **The trustee panels are the availability committee, before any result.** Each panel's threshold of seats attests, through the L2 contract path only, that it held the ballot extent (the board through `period(closes_at) + 1`) by `c_I`, and the counted extent before any summed share. Otherwise the election fails `unavailable`, listing who attested, complained or did nothing.
- **Rejected or deferred.** A reachability-judged deadline is rejected (verdicts would depend on the verifier's network, T-53). Archive listing alone is rejected (the authority can list and withhold). EIP-4844 blobs are kept as a later upgrade for entry-hash lists (capacity and cost rule out payloads).

Known-weak (part 2a):

- Nothing is built yet.
- Under the transitional panel, the attestation is the operator's own, so [[P1-12c]]'s residual stays until [[P1-7]] names independent trustees, or the owner accepts it for those polls.
- The tail after the counted extent (openings, tally, destruction statements) stays unverifiable, never failed, when withheld: a quorum there would be a veto over the result (T-54).
- Attest-then-withhold leaves the election unverifiable, with the attesters named.
- A colluding panel threshold can attest to withheld data, as it can open ballots.
- Trustees fetch on a deadline: up to about 20 hours for the ballot extent under the deployed constants. Part 2c adds the allowance to `deliveryWindowFits`; a longer `DELIVERY_WINDOW` would move `COMPLAINT_WINDOW` and the seal later.
- The verdict depends on the L2's history staying retrievable (as every contract event does), and the tally window shrinks by the counted extent's fetch allowance plus `F + R`.
- Under a live poll, a panel threshold that dislikes the running trend can refuse to attest, as it can refuse the tally.
- A board-path ballot first boarded after the ballot extent is never counted: a voter whose newest ballot the operator holds back keeps the older one counted and must direct-submit to change it.

## Independent review (part 2a)

## Known-weak (part 2b-2a)

- Nothing calls it yet: the verifier still reads `board.bin` (part 2b-2b) and the reference election doesn't rebuild from L1's CIDs (part 2b-2c).
- Where the anchored CIDs don't name the runs their checkpoints bound (a segment left unanchored, a checkpoint inside a segment, a CID of other bytes), the copy by CID stops short and the election is unverifiable from the CIDs, where a whole copy would fail it ([[board]], Residuals); 20 of the 56 board vectors are such boards. Part 2c's attestations make withholding attributable.
- **The reader's budget is the only memory bound.** A run's bound is what its entries can encode at `MAX_BOARD_PAYLOAD` each, and the anchoring authority chooses the entry count, so the bound is the authority's to set; a segment object of identical chunks needs only a few distinct blocks at any length. `readBoardCopy` therefore takes `maxBytes` from its caller and stops `over-budget` past it, after the run's root alone. An authority can still make every reader whose budget is under the run it anchors report the election unverifiable, cheaply; a protocol cap on segment-object bytes (the operator checkpointing before it) would close that, and is left for part 2b-2b to decide with the verifier's budget (T-52).
- The entry-hash lists aren't read: a client that rebuilds roots from the lists alone ([[receipts]], Entry-hash lists) still needs a reader of its own, with the length fixed at `32 · (n_i − n_{i−1})`.

## Independent review (part 2b-2a)

An in-session subagent reviewed the diff against `.github/review/crypto-review.md` and ran hostile roots against it. One blocking finding, fixed:

- **A root's claim cost what it claimed.** The walk memoised node shapes by position, so checking a lone root claiming a huge `filesize` built a shape per node of the claimed tree, and the first leaf allocated the whole length. An anchoring authority could exhaust any reader rebuilding the board from L1 (2 TiB claimed: 7 s and 1.2 GB; 64 TiB: the process died) with one block. Shapes are now keyed by height, chunks covered and whether the last chunk is among them (at most three per level), and leaves are kept as they hash and joined at the end, so work and memory follow the blocks served. The spec says so, and a test with lone roots claiming `2^50` and `7 · 2^50` bytes fails on the old code.

Non-blocking, applied:

- [[board]]: a CID of other bytes that split into the run's count gives a full copy failing `copy-mismatch`, not a short one, and the same bytes from every source; and an anchored entry over `MAX_BOARD_PAYLOAD` is among the residual's cases.
- [[content-addressing]]: a raw root over 1 MiB is unavailable, never hashed.
- Each answer is copied before it is hashed, so what is checked is what is kept.
- A test of a running election whose later anchor lands before an earlier period's.

Not applied: a bound tighter than `MAX_BOARD_PAYLOAD` per entry (Known-weak above).

CI's `crypto-review` then found one more blocking issue, fixed: repeated blocks made "work and memory follow the blocks served" false, since a DAG of identical chunks under an authority-chosen size costs a few blocks to serve at any length. `readObjectWithin` now reports a canonical root over its bound as `over-bound` with its length, `readBoardCopy` takes a byte budget for the whole copy and stops `over-budget` past it, the spec says what the authority can force, and T-52 records the residual.

## What was built (part 2b-2b-1)

- [[verifier]], Board by CID: a bundle of any format may hold `blocks.car`, a CARv1 block store, instead of `board.bin` (both, or neither, rejects it). The copy is read by the CIDs the counted checkpoints name on L1 ([[board]], A copy from L1's CIDs), after the definition and the anchors are read with no copy, so each anchored word needs its checkpoint from its `CheckpointAnchored` log. Where the run stops before it needs a copy, the read doesn't run (`not-reached`) and the run reports that stop. The read takes a byte budget for the whole copy, 1 GiB by default, set with `--max-board-bytes`. The report's `board.byCid` gives the store's sections read and unreadable bytes, and where the copy stopped short.
- The CAR rules: minimal LEB128 varints below `2^53`; a header that starts `{roots` and ends `version: 1}` in dag-cbor (a CARv2 is rejected); sections read until the first that isn't whole or doesn't start with a CIDv0 or CIDv1, the rest counted and never read; only blocks a read can use kept (a layout-form CIDv1, at most 1 MiB, hashing to its digest), the first per CID served alone, in sorted offsets rather than an object per section. The roots are never read.
- `packages/verifier`: `readBlockStore`, `readBoardByCid`, `loadBundle` and `DEFAULT_MAX_BOARD_BYTES`; `runCli` is async (and so the reference election's verifier script awaits it).
- T-49 and T-52 history.

## Independent review (part 2b-2b-1)

An in-session subagent reviewed the diff against `.github/review/crypto-review.md` and ran hostile stores against it. It found no path to a wrong verdict. Two blocking findings, both fixed in `readBlockStore`:

- **Memory.** Every section became an object in a map, so a store of tiny sections cost about 36 times its size (48 MB of 5-byte sections took 1.1 GB; 190 MB ran out of memory). Now only blocks a read can use are kept, as sorted offsets: the same 48 MB store takes 17 MB of heap.
- **Hash amplification.** Every repeat of a CID was served, and the reader hashes each answer until one matches, so an anchoring authority repeating one leaf could put many bogus answers ahead of it and make the run take hours (16 leaves behind 200,000 bogus answers took 5 s; linear in both). Each kept block is now hashed once at load and served alone: the same case takes 0.1 s.

Non-blocking, applied: the spec says only the header's ends are checked; tests for a non-minimal header length, a non-minimal varint inside a CID and a format-3 bundle whose definition doesn't decode; the file is no longer copied; the spec says a CIDv0 is never served and a file over 2 GiB can't be read. Not changed: the second anchoring pass gives the same anchors as the first (each must hash to the same proven word), which the reviewer confirmed; the by-CID copy of a board with a skipped segment stays unverifiable where `board.bin` fails it `unanchored`, as part 2b-2a records (Known-weak there).

## What was built (part 2b-2b-2)

- [[verifier]], Board by CID, Gateways: the read by CID also asks IPFS gateways the user names (`--gateway <url>`, up to 16, in order) over the trustless gateway API's raw-block requests, `GET <base>/ipfs/<cid>?format=raw` with `Accept: application/vnd.ipld.raw`, which `apps/node` (P4-5 part 1) answers. `blocks.car` is asked first where the bundle holds it; a bundle with neither copy is read from the gateways alone, and one holding `board.bin` is rejected when gateways are named.
- Each request: status 200 only, no redirect followed, a 30 s timeout for headers and body, a declared `Content-Length` past the reader's limit refused unread, the body read as it streams and dropped past the limit (at most 1 MiB), and the answer kept only if its SHA-256 is the CID's digest; the first gateway that serves a block is its only answer. Anything else is that gateway's failure for that block, and a block no source serves is `unavailable`.
- The report's `board.byCid` gains `gateways` (`requests`, `blocks`); `storeBlocks` and `storeUnreadableBytes` appear only where `blocks.car` was read.
- `packages/verifier`: `gatewaySource`, `parseGateway`, `MAX_GATEWAYS`, `DEFAULT_GATEWAY_TIMEOUT_MS`; `readBoardByCid` and `loadBundle` take gateways beside the store.
- T-11, T-24, T-49 and T-52 history.

## Tested (part 2b-2b-2)

- Every `board.json` board read from a local HTTP gateway holding its own entries' segment objects gives the same checks, entry count and stop as from a `blocks.car` holding the same blocks.
- A `blocks.car` holding one block and a gateway holding the rest give `board.bin`'s checks, with exactly one request per block the store lacks; an empty gateway, and one serving altered blocks, leave the copy short at checkpoint 0, unavailable, with no failed check.
- A 2 MiB object read back by CID from the HTTP gateway, one raw-block request per block in the walk's order, each with the raw `Accept` header.
- Property (`FC_NUM_RUNS`): up to 16 gateways each holding the block whole, altered, nothing or failing: the block is served exactly when one holds it whole, by the first such, with no later gateway asked.
- An endless body is cancelled within one stream chunk of the limit (and of 1 MiB when the reader asks for more), and the next gateway serves the block; a declared length past the limit is refused unread; statuses 201, 203, 206, 301, 404 and 500 are no answer; a real 302 to a server holding the block isn't followed; a server that never answers, and one that sends headers and then nothing, both give up within the timeout; no request is sent for a CID of another length, version, codec or hash, or for a limit that isn't a non-negative integer.
- `parseGateway` and the command line refuse non-HTTP schemes, credentials, an empty or set query or fragment, an empty URL and more than 16 gateways as usage (64); a bundle with neither copy and no gateway is rejected (22).

## Known-weak (part 2b-2b-2)

- Every gateway named sees which CIDs the run reads, and so which election and segments the user checks, from their network address (T-11). Running a local `apps/node`, or exporting `blocks.car`, avoids it.
- A run's time is bounded only by the blocks the anchored CIDs name, times the gateways, times the 30 s timeout: requests are sequential, one block at a time, and a slow gateway makes a run slow, never wrong. The timeout isn't settable on the command line.
- The verifier doesn't find gateways itself: the user names them. The entry points and community nodes the release lists ([[P4-4]], [[P4-5]]) aren't read as defaults.
- The reference election still reads `board.bin` and doesn't rebuild from L1's CIDs (part 2b-2c).

## Independent review (part 2b-2b-2)

An in-session subagent reviewed the diff against `.github/review/crypto-review.md`, probed it with a gzip bomb inflating to 1 GiB (cut off at the limit), a 2,000-layer `Content-Encoding` chain (refused) and hostile URLs, and removed each check in turn: every removal fails a test. It found no blocking issue. Non-blocking, applied:

- `gatewaySource` checks each base as `parseGateway` does, so a library caller can't pass a `blob:` URL whose path is a whole URL; tested.
- The report's `gateways` is present wherever the run named gateways (the spec said "asked").
- An answer costs a small multiple of the limit in memory (the chunks, one stream chunk past them and the joined copy), not the limit; the spec, the comment and T-52 say so.
- Over `http:` the network path sees, and can block, the requests too; the spec, T-11 and the command line's help say so and prefer `https:`.
- A changeset for `@abolishus/verifier` (minor: new exports, and `CidRead`'s store fields now optional).

Not applied: an overall deadline for a run, or moving a gateway that timed out to the end (Known-weak above: slow, never wrong); and rethrowing errors other than network ones from a request, since any error there ends in `unavailable`, unverifiable from that source, never a verdict.
