# T-73: Verification providers and the number's keyed hash

- Area: Ballot secrecy, unlinkability and privacy (G-3, G-4, G-5, G-12)
- Adversary: A-1, A-2, A-10
- Status: **Planned.** Decided in [[0038-verified-accounts]]; built by [[P2-31]] parts 2 and 3. Residual: each provider learns who uses Abolish, and whoever holds the account table and every phone-hash key recovers every verified number.

## Threat

Every account is verified by email and by phone ([[PROJECT_BRIEF]], Identity), so:

- the SMS provider learns each verified number, when it was checked and its line type, and the email provider each address and when it was written to: a list of who uses Abolish, held by parties beside our hosting and Cloudflare (T-11), under their own retention, and open to compulsion (T-69) or breach;
- the phone number's keyed hash is only as strong as its keys: about 10^10 numbers per country code are enumerated in minutes by whoever holds the table and every key;
- the email ciphertext is decryptable by the running account side, so a compromise of `apps/web` yields every address;
- a party that can receive SMS for numbers it doesn't own (a SIM swap, a compelled or compromised carrier) can take a victim's verified phone, or verify accounts in bulk.

## Mitigation

- **Nothing about voting reaches a provider.** Each is sent only a number or an address, a code, and for notifications ([[P2-27]]) what the message says; never an account ID, a poll, an answer or a ballot. Verification happens on the website before an account takes a Tier 0 token, never when voting (T-10).
- **The number is never stored.** Only its nested HMAC chain under keys kept in `apps/web`'s environment, never in the database or a log; rotation rewrites every stored value under a new key without the numbers, so a leaked key stops mattering after the next rotation ([[0038-verified-accounts]], The number's keyed hash; T-65).
- **The address is encrypted at rest**, unique by a keyed hash, so a dump or backup of the database alone yields no addresses and no numbers (T-66).
- **No tracking.** The email provider is transactional-only, with open and link tracking off (T-67).
- **A moved number never moves an account.** Taking a number another account holds costs that account its verified phone only; sign-in is its passkeys.

Residuals, not mitigated: the providers' own records; enumeration by whoever holds the table and every key; a live compromise of the account side; a state that can make or redirect numbers at will (A-1), which also bounds nothing about its Sybils (T-01).

## History

- 2026-10-22 (P2-31 part 1, [[0038-verified-accounts]]): added with the decision to verify every account by email and phone.
- 2026-10-22 (P2-31 part 2a): e-mail verification in `packages/core` keeps each address only as AES-256-GCM ciphertext bound to its account and a keyed hash of its lowercased form, codes only as hashes, and answers a request for another account's address exactly as any other, so the route reveals nothing about who has an account. The per-address send counts are timed to the hour and the per-account ones to the second, so a dump narrows an address only to the accounts that asked for a code in that hour.
- 2026-10-22 (P2-31 part 2b): the website's `/email` routes and the Postmark adapter. The provider is called after the request is answered, so a request for a code answers the same, and as fast, whether a code went, a notice went, the address's cap held it back or the provider didn't take it: neither an outage nor the time a send takes tells a capped address apart. A failed send reaches only the operator's log, by kind. Postmark is sent the address, the subject and the plain-text body with open and link tracking off, and no tag or metadata; expired codes and their ciphertext are pruned every 10 minutes.
- 2026-10-22 (P2-31 part 3a): phone verification in `packages/core` stores no number in any form but its nested HMAC chain, not even while a code waits (the page sends the number again with the code), and holds no code (the provider does). A number another account holds, or one held after an account let it go, is refused only once its right code is entered, so asking for a code reveals nothing about who has an account; only whoever has the phone learns the number is someone's. Days held and verified are kept to the day, per-number sends to the hour and per-account ones to the second.
- 2026-10-22 (P2-31 part 3b): the Twilio adapter and the website's `/phone` routes. Twilio is sent the number, the channel and the typed code as form fields and nothing else, no friendly name, custom code or locale. The send is called after the request is answered, so a request for a code answers the same, and as fast, whether a code went or the number's cap held it back; a failed send reaches only the operator's log, by kind. The lookup is made for every number, capped or not. Neither the number nor the code reaches the request log.
