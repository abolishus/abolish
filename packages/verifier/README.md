# @abolishus/verifier

The independent verifier for [Abolish](https://github.com/abolishus/abolish) elections: downloads the public bulletin board and recomputes and checks the whole election without trusting our servers.

**Status: early.** It reads a local bundle, can read an election's anchors from the board anchor's L1 state, can check an election definition's decoding and well-formedness, and runs the board checks (4.1 and 4.2 of [`docs/spec/verifier.md`](../../docs/spec/verifier.md)). Every other check is reported unverifiable, so no run reports an election verified yet. Prereleases are published as `next`, signed and with provenance (see the repository README, "Releases").

## Use

```ts
import { readBundle, verifyBundle } from "@abolishus/verifier";

const report = verifyBundle(readBundle("path/to/bundle"));
```

A bundle is a directory with `board.bin` (the board copy: its encoded entries in index order), or `blocks.car` (a CARv1 block store, from which the copy is read by the CIDs the counted checkpoints name on L1, within a byte budget set by `--max-board-bytes`, 1 GiB by default), and `bundle.json` (the election identifier, the pinned board-entry version, the anchoring clock, and either `now` and every anchor for the election (format 1) or the L1 evidence they are read from (format 2): an L1 block header, the `eth_getProof` trie nodes of the board anchor's slots, and any checkpoints no copy matches). Format 3 gives the election definition instead of the election identifier, the version and the anchor's address, and takes all three from it; decoding it (definition versions 1, 3, 4 and 5, each under its own layout and rules) and its well-formedness are reported under 2.1, a board-entry version (1, 3, 4 or 5) that doesn't fit its ballot and tally-opening versions fails 2.3, and the report gives its hash, to compare with the one the L2 election registry holds. Every contract-event record of the election on the copy is decoded under the profile's contract-event version and checked against the definition's L2 contracts (4.4's event check): one that fails fails 4.4 inside the anchored extent, and leaves it unverifiable with its code on a copy the board checks don't authenticate; 4.4 never passes yet, since which events must be boarded and the accumulators' replay need L2 reads and the archive. Format 4 adds the trustee panel the release pins, and runs the key-ceremony transcript check against it: the transcript is the board entry whose hash the definition names, checked with its context rebuilt from the definition and the panel (3.2, and the parts of 2.5 and 3.1 that need no L2 state). Once 3.2 passes, every ballot of the election on the copy, on the board path or (under contract-event versions 2 and 3) the ordinary path as the board's `BallotSubmitted` event (a ballot relayed through L1, under version 3, is set aside until 4.5 matches its relay call, leaving 5.5 and 5.7 unverifiable), is admitted or rejected against the definition and the registered key set (5.1 to 5.4; under definition versions 3 and 4 a ballot is version 2, judged against the root and scope of the cell it names), then by its own path's window under the close rule (5.5), and the report lists each rejected ballot; a rejected ballot never fails the election. Format 5 adds a run of finalized L1 headers, and each admitted ballot's L1 reference is judged against it (5.8): a block before the window, after close or with another hash rejects the ballot, and one beyond a head before close leaves it pending. A later copy of an admitted ballot, with the same tier, nullifier and membership message (re-randomised proofs included), is rejected as a repeat (5.7). Once every admission row is settled, the copy authenticated by 4.1 and 4.2, the board sealed, no ordinary ballot left waiting on 4.4 and every admitted ballot at or below the floor of the counted extent, selection (6.1) picks each tier and nullifier's counted ballot, the one naming the highest L1 block, or lists a tie, and the report gives `selected` and `ties`; short of any of these it is unverifiable, never decided over a set that could still change. Every spoiled-ballot opening on the copy is then checked against the same key set (6.2): the report lists each one's failed check, or its tracking code and vote, and the publication rules it is known to break (boarded at or before the counted extent's earliest possible end, opening an admitted ballot's commitment from before then, or repeating an earlier opening's core); an opening never counts or fails anything. Every tally opening on the copy is sorted into a cell of the partition (under definition versions 3 and 4, the cells every tier states, numbered across the tiers) or stray and attributed by the same key set's signing keys (7.4), and the report lists each one with the boarding-rule breaches decided without the counted set (stray, another number of entries than options, unattributed, or a seat's second opening of a cell, or a replay of its first); whether an opening is over the counted set and opens it waits on the counted set. Once selection passes, delivery (5.9) runs over the selected ballots and the share receipts, postings and complaints in the anchored extent: a ballot without every registered seat's receipt or passing posting in time, or with a proven complaint, counts nothing, and the report's `delivery` lists each excluded ballot and every record the check reports. Each cell's counted set is then the selected ballots delivery keeps in it, and the tally checks run over it (7.1 to 7.3): every cell needs a passing opening of its aggregate, the report's `cells` gives each cell's counted ballots and counts, and 7.4 adds each opening's `tally-aggregate` or `tally-opening` break. Under board-entry versions 4 and 5, 8.5 reports each registered seat's destruction statement as destroyed, early or missing, or leaves it undecided while the unknown end of the tally window could still place it either side (`destruction`). The close check (6.3) finds `L_δ` in the run of L1 headers, judges the default panel's close statements and recomputes the counted sets without the ordinary ballots after the close head (`close`); the report's `tiers` gives each tier's result, derived from its cells. 4.4 also checks the L1 origins of the election's own creation and registration events against the pinned sequencer drift and the run. A contract-path delivery record leaves all of it unverifiable until 4.4 authenticates its timestamp, and definition version 5's ballots wait on the delivery check reading them. A definition pinning ballot version 1 or 2 with a membership key other than the pinned one fails 1.3. `electionAdmission(definition, panel, entries)` is the same admission for one ballot at a time, as a board operator runs it before boarding: from the definition's bytes, the pinned panel and board entries that may carry the transcript, it refuses the election (with the first check that stops every ballot) or returns `admit(payload)`, which decodes one ballot strictly and runs 5.1 to 5.4 with the judge the report uses, so the two never disagree, and `admitAll(payloads)`, which gives each payload `admit`'s verdict with the membership proofs batched (`docs/spec/ballot-validity.md`, Batched admission). Their exact format, the procedure and the JSON report are under "Inputs, procedure and report" in `docs/spec/verifier.md`.

- **Inputs from a local file authenticate nothing.** Anchors and `now` read from L1 state are only as authentic as the header, the anchor's address and the first segment they are proven from, which are still local files, and so is the definition; until those and the clock come from trusted sources, the report's `verdict` is always `unverifiable`. The report names the L1 block (`l1.blockHash`), so it can be compared with a node you trust. `verdictAgainstInputs` says what the checks found against the bundle's inputs. A crafted bundle can neither verify nor fail an election (T-53, T-24).
- **A bad copy is never the election's failure.** A short or altered copy (`checkpoint-missing`, `copy-mismatch`) is unverifiable from that source, and bytes past the anchored extent change no verdict (T-53); they can change the ballot admission rows, 6.2, 7.4 and the report's `ballots`, `openings` and `tallies`, which report what the copy holds. The counted set and the tally (5.9, 7.1 to 7.3, 8.5) read only the anchored extent of a sealed board. So do a live poll's releases (7.5, 7.6 and the report's `releases`), once 7.1 passed.
- **Malformed bundles are rejected whole** (`BundleError`), before any check runs.

### Command line

```sh
vp node packages/verifier/src/bin.ts path/to/bundle   # from a checkout
```

It prints the JSON report on stdout and a summary on stderr, and exits on `verdict` alone: 0 verified, 20 failed, 21 unverifiable, 22 bundle rejected, 64 usage. Any other code is the verifier's own error, not a verdict. `runCli(args, { stdout, stderr })` runs the same from code. The package doesn't install an `abolish-verify` binary yet: a published gated package may not declare `bin` until CI's policy allows it.

### Keys run

```sh
vp node packages/verifier/src/bin.ts keys path/to/evidence   # keys.json inside
```

`runKeys(parseKeysEvidence(json), pin, runAt)` judges the Tier 0 token keys of every release in the L1 release registry (`docs/spec/verifier.md`, Token keys across releases): every release, revoked or not, read from the registry's state under one L1 header, its release record and deployment record found by hash among those given, every pair of version-2 deployments by the rules across releases, and each period's key first listed before its period began (T-74, T-10). It contacts nothing and writes `abolish-keys-report/1`. No registry is deployed yet, so this release pins none (`PINNED_RELEASE_REGISTRY`), and every run from the command line is unverifiable with `release-registry-unpinned`.

The checks themselves live in `@abolishus/crypto`; this package reads inputs, maps outcomes onto the spec's checks and reports them (T-36).
